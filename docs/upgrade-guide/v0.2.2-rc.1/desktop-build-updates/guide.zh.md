# 桌面发布使用构建序号

[English](guide.md) | 中文

## 变更

桌面发布者必须提供显式构建身份。源码与捆绑运行时保留上游版本；`dshRelease.buildSequence` 对桌面更新排序，包括同版本的多个构建。`revision` 标识源码提交，不用于发布排序。重新签名或重新构建产生不同字节时，必须分配新序号。

旧客户端读取原更新源以获取过渡包；过渡客户端与普通客户端读取 `/dsh-updates/v2/{mac,win}`。迁移示例为过渡应用 `0.2.2-rc.4` / 运行时 `0.2.2-rc.1`，然后是序号更大的普通应用 `0.2.2-rc.1`。这些是示例，不是已分配的发布。v2 拒绝运行时降级、同序号身份冲突，以及旧 `minimumVersion`。

## 迁移

1. 清点所有历史发布：过渡应用版本必须高于全部旧版本，不能只看 `latest`。保持源码版本同步，分配依次递增的序号。构建输入记录 `version`、`dshRelease`（`schemaVersion: 2`、`runtimeVersion`、`buildSequence`、完整 Git `revision`、`kind`）和 `platforms: ["darwin", "win32"]` 或单个平台。`kind: bridge` 仅用于过渡；普通构建的应用版本与运行时版本必须相等。
2. 使用[打包命令](../../../../apps/desktop-shell/README.zh.md)生成最终产物及其发布清单。不要在构建前填写猜测的摘要，也不要复用过期暂存。将生成的清单与其精确产物一同保留；发布接受该输出，不接受构建输入。
3. 先把首个普通构建发布到 v2，再让原更新源指向过渡包。各平台的 v2 运行时版本都必须不低于过渡包运行时，构建序号必须严格大于过渡包；两个发布方向都会检查。永久保留过渡清单和所有旧版依赖（含推导出的 blockmap），本次迁移保持清理关闭。过渡包虽然先分配较小序号，其更新源指针却后公开。

过渡包一旦发布，其清单、产物与 blockmap 永久不可删除：v1 指针不能改指更低的应用版本，旧客户端只能经由过渡包进入新协议，删掉其中任何一个文件都会让旧客户端永久失去升级路径。v2 的清理只作用于 v2 目录，绝不能指向 v1；发布到更新源时，在根目录保留一份保留规则说明，与数据放在一起。
4. 使用[发布命令](../../../../apps/desktop-shell/README.zh.md)，传入生成的清单与发布说明。v2 使用 `--minimum-build-sequence`，v1 使用 `--minimum-version`。省略参数会继承各平台原有下限。`--republish` 只重试完全相同的产物；字节变更需要更大序号。`--dry-run` 仍读取远端状态。
5. 发布前必须在隔离的 macOS 和 Windows 环境验证真实旧 rc.2/rc.3 → 过渡包 → 普通构建 N → 同版本构建 N+1。保留旧安装包原始字节；Windows 的机器级安装必须使用独立机器。验证 macOS designated requirement 连续性、运行身份、设置保留和 pending 缓存清理。下载完成或单元测试通过不代表原生安装成功。

无需手动编辑 `desktop-state.json`。清理收据指明精确的目标构建和产物；无关构建与旧收据都不能证明成功。
