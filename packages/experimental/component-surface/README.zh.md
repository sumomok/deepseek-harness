# @deepseek-ai/dsh-experimental-component-surface

[English](README.md) | 中文

## 概述

`show_component`：智能体把一块界面——一段提示加一行按钮、一条记录的详情、一张记录表、一行筛选条件、一个数字——放进对话旁边的内容栏，组件取自本包自己的目录，并在任何东西被画出来之前按该目录逐项判定。

这个包两个半边都有。宿主半边把工具交给模型、校验每一次调用、并认领[内容面](../content-surface/README.zh.md)条目流里的 `component` 种类；浏览器半边认领内容栏 `content.surface.kind` 槽的 `component` 键，把每条条目的 spec 画出来。组件本身不属于任何一半：渲染器来自[`component-kit`](../component-kit/README.zh.md)，它不认识布局，而本包做的就是把它的一块摆进某一列里。

用户在一块界面里做了什么，则沿另一个方向回来，走本行自己的一条命令：`/component-action`。

同一条内容栏也接纳没人让模型摆的块：部署自己写下视图，外壳侧栏把它们列出来，一次点击就把其中一个放进去，全程不问模型。

智能体做的任何事都不写会话事件。一次调用的记录就是循环本就写下的 `tool/call`，一次动作的记录就是命令注册表本就写下的 `command/run`，所以两个方向都由智能体写下的日志重放出来。本包写下的唯一一条事件属于用户自己：打开某个已配置视图的那次点击。

<a id="composition"></a>
## 组合

[`overlay/component-surface.patch.yml`](overlay/component-surface.patch.yml) 把这一行和组件行一起叠在服务线控制台组合之上——那份组合已经带了内容面与内容栏。覆盖文件自己的注释里写着启动命令。

这一行分三块各自独立生效。工具只需要工具运行时，所以没有内容栏的组合照样提供它、照样记录它的调用；抽取器需要内容面路由器，没有路由器时调用就只留在日志里没人读——后来才长出内容栏的组合要的正是这个；回程通道则三样都要：命令注册表、那个路由器，以及条目所在的投影注册表——没有内容栏就没有任何一块界面可供动作指认，所以那时命令干脆不存在，而不是对每一次手势都回一句拒绝。

<a id="configuration"></a>
## 配置

四个配置项。`views` 与 `homeView` 说的是人写下的块，与模型做什么无关，下一节就是它们的全部说明；`dataSource` 与 `dataDefaultPageSize` 说的是模型向这个部署要来、而不是自己写出来的行，再下一节是它们的。其余一切都是固定的。

部署可能想调的那几个数——spec 字节上限、节点上限、嵌套上限、动作字节上限——被校验两次：这里一次，浏览器座位对着从线上收到的值再一次。座位收不到 Cordis 配置，所以按部署可变的上限就是两边会对不上的上限：结果是内容栏里悄悄少一块，而不是模型能据以纠正的一次拒绝。在座位能读到部署设置之前，它们是 [`src/component-call.ts`](src/component-call.ts) 里的协议常量；等座位能读设置那天，上限和提供设置的那条路由一起到来。嵌套上限连在那里也没有写死：它是从目录量出来的，所以某个组件声明了一个嵌套属性，上限就正好为它加宽，合法文档不会被当成畸形拒掉。

动作的上报档位既不是上限，也不是配置。它说的是一次手势意味着什么——按下的确认就是智能体停下来等的那个答案——所以它和动作一起声明在目录里；部署去改它，改的是智能体被告知发生了什么。

<a id="views-the-deployment-writes"></a>
## 部署自己写的视图

一个视图就是一次 `show_component` 调用携带的同样三个值——一个条目 id、一句短标题、一份 spec——只不过由人写在 `cordis.yml` 里，而不是由模型写在一次工具调用里。正因为如此，一种条目种类、一个抽取器、一个座位就能同时服务两边：不同的是谁写的 spec，而不是它是什么。

```yml
- id: show-component
  name: '@deepseek-ai/dsh-experimental-component-surface'
  config:
    homeView: site-overview
    views:
      - id: site-overview
        title: 站点概览
        spec:
          nodes:
            - id: sites
              component: toy.table
              props:
                selectMode: radio
                tableConfig:
                  gridItems:
                    - { relatedMetaAttr: name, alias: 站点 }
                displayValueList:
                  - { name: 一号站点 }
            - id: detail
              component: toy.record
              props:
                dataList: { $from: 'node:sites.selectionDetail' }
                columnNum: 1
          layout:
            node: stack
            dir: col
            gap: md
            children:
              - { node: component, id: sites, flex: 2 }
              - { node: component, id: detail, flex: 1 }
```

`homeView` 点名会话第一次落在空白草稿上时侧栏自动打开的那个视图，好让新对话一开始就有内容；不写它，那条内容栏就一直空着，直到用户或智能体选一个。它必须点名一个已配置的视图，而且它驱动的是一次真实的点击，留下的记录与真人点一下完全一样。

每个视图都在加载期由判定调用的那一套判定过一遍——同一份目录、同样的上限、id 用同一套字符集——所以部署能写的，正好就是模型能发的。过不了这套判定的视图会让这一行加载失败，并同时点名人要去改的那个视图和它里面的那个值：

```
component-surface: views[0] "site-overview" — spec.nodes[0].component — names no component of this deployment. Available components: …
```

是响亮失败而不是悄悄跳过：被悄悄丢掉的视图，就是一条用户点了以后内容栏空空、而任何地方都不说为什么的菜单项。id 重复、以及 `homeView` 点名了不存在的视图，都以同样方式失败。

有两处注册只在配了视图时才存在。`GET /component-surface/views` 回的是导航菜单据以搭建的目录——`{"views":[{"id","title"},…],"homeView"?}`——除此之外别无他物：spec 从不走这条路由，所以页面无法索取部署没有配置过的视图。`/show-content-view <id>` 是一次点击真正执行的东西；它追加下面那条事件，对宿主接住的点击在对话里什么也不画，对点名不到视图的点击只回一句 `没有这个视图。`——那也是它那行对话唯一会画的东西。点击已经在屏幕上的那个视图会再追加一次，这正是让那条条目回到切换条最前面、而不是什么都不发生的原因。

`content-component/shown` 是本包写下的唯一一条会话事件。它只进日志——没有任何部分进入模型请求，因为模型对内容栏的了解只来自它自己调用的那个工具——而且它带的是整份 spec 而不是视图 id，所以部署后来改掉或删掉这个视图，日志重放出来的仍然是用户当时真正看到的东西。条目由折叠调用的那个抽取器从它折出来，落在这个视图拥有的那条条目 id 上。

<a id="rows-read-from-the-deployments-own-data"></a>
## 从部署自己的数据里取行

默认关。部署写 `dataSource: true` 之后，这一行会等齐一次取数需要的两条缝才提供工具：`bizBackend`（[`auth-gate`](../auth-gate/README.zh.md) 在配了 `bizUpstream` 时注册它）与 `approval`。少任何一条，`show_component` 就不注册——描述里许诺一个背后空无一物的参数，比这一行压根没加载还糟。

```yml
- name: '@deepseek-ai/dsh-experimental-auth-gate'
  config:
    bizUpstream: https://<host>/ini-server/
- name: '@deepseek-ai/dsh-user-approval'
- id: show-component
  name: '@deepseek-ai/dsh-experimental-component-surface'
  config:
    dataSource: true
    dataDefaultPageSize: 200
```

`bizUpstream` 是部署自己的 API 前缀，以 `/` 结尾；它没有默认值，不写就是这个部署声明自己不提供数据。

开着的时候，一次调用可以在 `spec` 旁边送 `dataSource`：每一个想让行被读进来、而不是自己写出来的 `toy.table` 块对应一项。

| 字段 | 必填 | 是什么 |
|---|---|---|
| `nodeId` | ✅ | 本次调用自己的某个 `toy.table` 块 |
| `meta` | ✅ | 这张表在后端的名字 |
| `metaLabel` | ✅ | 同一张表在用户自己语言里的名字，最多 20 字符、且是平铺的一行；审批卡片上写的就是它 |
| `conditions` | | 最多十条 `{key, op, value}`；`op` 取筛选条提供的那十六种之一，值是文本、数字、是非，或前两者组成的最多二十项列表 |
| `matchMode` | | `AND`（默认）或 `OR` |
| `page` | | `{pageSize}`，1 到 500 之间；调用不写时取 `dataDefaultPageSize` |
| `asc` / `desc` | | 一个属性、一个方向；两个一起送会被拒 |

在这里被点名的块不送 `displayValueList` 也不送 `rawValueList`；**没有**被点名的 `toy.table` 块仍然要自带行。两条都在问任何人之前就判掉。

读哪些属性不是参数。它是那个块自己的 `tableConfig.gridItems[].relatedMetaAttr`，隐藏列也算在内，所以一次调用要的正好是它声明要画的那几列——任何一次取数都问不到块没点名的属性。

### 顺序，以及每一步花掉什么

1. 判 `dataSource` 与它点名的每一个块——连同这次调用的其余部分一起判：判的是一份副本，每张待填的表里放一行占位行。标题过长、第十三块、这套部署没有的组件、第三十一列，都与行无关，所以都在这里被拒，而不是等人答完之后。什么都还没问，什么都还没花。
2. 从网关读一下手上到底有没有凭据，这一步不花钱也不碰网络。这次会话一枚都没有的话就在这里被拒——允许一次本进程做不到的取数，对答应的人没有任何意义。
3. 问用户一次——不管一次调用点了几张表，都只有一张卡片；而且每次调用都问，因为 `allowed-once` 是审批服务唯一的放行值。
4. 读这张表的字典，把这次取数点到的每一个属性都对着字典核一遍：每一列的 `relatedMetaAttr`、每一条筛选的 `key`、以及用来排序的那个属性。表里没有的就在这里被拒，并附上字典自己前十个名字——因为再往下它根本不算错：列会照常回来、只是没有那个键，那一列就在用户面前画成空白；筛选和排序则交给后端自行解释，而一个把不认识的筛选直接忽略掉的后端，会把用户批的那次「筛过的」取数答成一直取到页大小为止。字典同时为调用没写表头的每一列补上表头。
5. 一张接一张地取行，每一行都被收到调用声明过的那些列上——后端答的是它自己挑的属性，还会往拿到的每一组属性前面插它自己的行标识，而卡片报出去的是声明过的列。第一次失败就结束整次调用，已经取到的行一并丢掉。
6. 把行代进去，再用手写调用走的同一道判定判一次这份填好的调用——这一次判的是只有行才能决定的两件事：到了多少行，填好之后有多少字节。
7. `content-component/resolved` 记下整条填好的条目。

走不到第 7 步就不追加也不画，所以每一种失败都让内容栏保持原样——而且取数调用自己的那条 `tool/call` 也不产生条目，因为它参数里的那些块缺了它们必须带的行。

### 用户被问的是什么

卡片是中文的，不出现控制台平时不给人看的任何术语，表在后端的名字单独占一行——想核对到底问了什么的人看得到，不想看的人不会被它挡路。下面这段是卡片写出来的样子；今天画它的审批窗会把这几行连成一段，这一条记在文末的限制里。

那行标识是这张卡片上唯一不是模型写的部分，所以模型写的任何东西都够不着它。每张表的描述会先按它在三百字符正文预算里分到的那一份被裁掉，**之后**才接上它那行标识和结尾的承诺，于是无论表头多长、标签多长，都推不掉这两样；而模型往卡片上贡献的每一个词——`metaLabel` 与每个列表头——除非是不带 `「」` 括号、不带控制或格式字符、不带 Unicode 行/段分隔符的平铺一行，否则一律被拒，于是谁都画不出卡片从没写过的一行。

```
用您的账号查一份数据：从「图层配置」里取最多 200 条，只取「名称、图层id、所属地图主题」这几列。
数据表：SpaceLayer

取回来的数据画成表格放在右边，小助手看不到表里的内容；您在表里勾选的行，会作为您的选择告诉小助手。
```

每张表都有自己的一段和自己那行标识，无论一共几张。列按调用自己写的表头点名，一次至多三个，剩下的计数；调用没给表头的列只计数不点名，因为它剩下的唯一名字就是后端用来存这一列的属性名，而能把它翻过来的字典要等这个问题答完之后才读。筛选照同一条规矩，且从不写值——被筛的列全都有表头时按表头加算子写，只要有一列没有就整句改成计数，因为一个条件里可能是别人的身份信息，而卡片的职责是说清将要读什么，不是把它复述一遍。最后一句是任何时候都必须在的：勾中的行会经 `/component-action` 离开面板，作为用户自己的回答到达模型，所以一张许诺「这些数据不会进对话」的卡片，许诺的是本行并不做的事。

### 记下了什么，模型被告知什么

`content-component/resolved` 带着调用 id、条目 id、标题、整份填好的 spec，以及每张表一项的 `fetched`——点名块、表、到了多少行、一共匹配多少行、这次读取要的是哪些属性——记下来的行也只带这些属性，因为后端答的是它自己挑的属性，而这一行只留调用声明过的列。它不带凭据、不带请求地址、不带排障标识。内容栏就是从这条记录重放的，理由和一次视图点击要写一条记录一样：行根本不在 `tool/call` 里，而靠重新取一次来重放，等于在没人要求的时刻再读一次这个人的数据。

模型被告知的是同样的计数与属性名，行里的内容一个字也没有。

<a id="the-catalog"></a>
## 目录

一个工具管所有组件，而不是一个组件一个工具。有哪些块是部署的目录，而目录写进一份描述里一次，比摊在一份越来越长、模型每次请求都要读的工具清单里便宜。目录是 `component-call.ts` 里的静态常量表；当一个不归本包维护的包需要贡献组件时，再把它换成注册式的缝。

目前有五项：

| 组件 | 名称 | 画出来是什么 | 什么会回来 | 另一块能读到什么 |
|---|---|---|---|---|
| `el.confirm-bar` | 确认条 | 可选标题、可选说明，以及一到五个按钮，每个按钮带 id、文字和可选的语气 | `press`，带着被按下的按钮 id | 什么都没有 |
| `toy.record` | 记录详情 | 一到六十行，每行一个不超过 64 字的标签和一个不超过 400 字的值；可选的标签宽度 40 到 240，可选的列数 1、2 或 3 | 什么都没有 | 什么都没有 |
| `toy.table` | 数据表 | 一到三十列铺在一到五百行上，每一列按字段名从行里取值，可选地交给五种单元格渲染器之一去画；可选的勾选列、可点名称、最多五个自定义操作按钮，以及操作列宽 | `select`、`row-click`、`sort`、`operation` | `selectionDetail`，第一行被勾选的行被读成一组「名称—值」 |
| `el.filter-bar` | 筛选条件 | 一到四十个属性供用户在其上编条件；可只放行十六种匹配策略中的一部分 | `submit`、`change` | 什么都没有 |
| `el.metric` | 指标球 | 一个 0 到 100 的指标画成注水的球；可选的文字、尺寸与三种颜色 | 什么都没有 | 什么都没有 |

动作和输出是两回事。动作是要告诉智能体的消息，也是日志里的一条记录；输出是留在内容栏里的一个值，供同一次调用的另一块去画。所以数据表把一次勾选上报了两遍——一遍给智能体，是用户勾了哪些行；一遍给内容栏，让记录详情能从中画出来，全程不惊动智能体。只有目录里当真有属性收得下的读法才声明成输出：一块上报了、却没人读得到的东西，等于目录先给模型一条绑定、再把它拒掉。

记录详情里一行的标签，上限取的是字段名的上限，而不是另设一个更短的数字：`selectionDetail` 正是要读进那张列表的，而没写表头的列贡献的就是它取值的那个字段名。两个上限对不齐，等于目录先提供一条绑定、再把它拒掉。

不上报任何动作的组件，会在工具描述里自己那一行上说出这件事——否则模型以为块会答话，摆下一个只用来看的块然后干等。每个组件的属性写在这一行下面，由它的 `propsSchema` 派生，而不是写在它旁边，所以「提供给模型的」和「用来判定调用的」不会漂开，模型也不必先花一次被拒的调用去问清楚该送什么。这一行一路写到底：嵌套的列表要说清它的一个条目带什么，因为只写了名字的列表，模型要一条属性一次被拒的调用才问得出来。它略去的是拒绝语句本来就会说出的每一条边界——字符串长度、token 的字符集——因为描述是每次请求都要付的，而拒绝只付一次。

记录里 `display` 为空串的那一行仍在原位：组件画出名称，旁边什么也不画——这正是记录有这个属性、但没填值的样子。

组件的属性用一套只有七种形状的小 schema 声明：有长度上限的字符串（可再限定字符集）、落在声明区间里的数字、`true` 或 `false`、固定取值集合（字符串或数字）、由更多已声明属性组成的对象、键名由调用方自己定的对象，以及以上任何一种组成的、有条数上限的列表。列表里的条目如果是用户要去点的东西，还要点名哪个属性用来标识它；什么都不回传的列表——比如一条记录的各行——不声明这个属性，两行共用一个标签是数据本身而不是错误。这个联合类型本身就是安全边界，不是写起来方便，理由见下面的信任边界一节。

键名由调用方自己定的对象，就是一行表格数据：键是各列去取值的字段名，没法像组件自己的属性那样预先列出来。它改用别的方式收口——键有字符集和长度、有个数上限，值只能是标量——描述里写成 `{<field>: text|number|boolean}`。

schema 说不出的是一个字符串**意味着**什么。把某个字符串读成路径、颜色或单元格渲染器名的组件，要在 schema 旁边声明这层读法（一共只有三种），由 [`src/sanitize.ts`](src/sanitize.ts) 在入口处执行：不是单斜杠开头同源路径的路径、`#RGB`／`#RRGGBB`／`rgb()`／`rgba()` 之外的颜色，都会被丢掉；白名单之外的渲染器名退回朴素渲染器，而不是让单元格没有东西画它。声明过的读法会写进工具描述里，因为这一遍是丢值而不是拒绝整次调用，模型没被告知写法就永远不知道自己写的那个值为什么消失了。渲染器名同时还声明成一组固定取值，所以点名白名单之外渲染器的调用会直接被拒；那条退回留给白名单收窄之前存下来的记录。数据表声明了渲染器名，指标球声明了它的三种颜色，`path` 是目前还没人声明的那一种；这一遍照跑，因为另一种做法是让规则跟着第一个需要它的组件一起到场，而在那之前它一次都没跑过。

键名由调用方自己定的对象，自己声明它这几个键的读法，而不是共用组件那一份：它的键是数据——`color` 既是某个单元格渲染器的配置项，也可能就是别人记录里普普通通的一列，而按名字挂在组件那一层的规则会把两者一起收紧。

<a id="what-a-call-is-judged-against"></a>
## 一次调用要过哪些判定

按顺序，每一步都能结束这次调用：条目 `id` 与 `title`；spec 的嵌套深度；它的字节大小；spec 与节点各自允许携带的属性名；每个节点的 id、它在本次调用内的唯一性、以及它点名的组件；该组件的每一个属性；然后是这些节点之上的摆法；最后是某个节点从另一个节点读来的那些属性。

后两步放在最后，因为它们说的都是整份 spec 而不是某一个节点：有哪些节点、每个节点各上报什么，要等所有节点都进来才定得下来。

深度在大小之前量，因为两者都要走一遍文档，而只有深度这一遍在写法上就有界——它在上限处停下，而不是走到值的底部。这个上限取 spec 携带的两份文档中更深的那份——节点的属性，和摆法这棵树——再多留一层摆法的余量，好让「多开了一层 stack」的摆法在开出它的那个 stack 上被拒，而不是换回一句「spec 最多能嵌多深」。

每一条拒绝都点名出错的参数路径，因为这条路径是模型唯一的通道：一次带十二个节点的调用只换回一句话，这句话不说出 `spec.nodes[3].props.buttons[1].id` 或 `spec.layout.children[1].children[0].id`，下一次调用就只能猜。点名了本部署没有的组件时，拿回的是完整目录而不是一个数字，于是纠正不需要再多一个来回。

通过判定的节点离开这里时，属性已经被收紧过一遍：三个读者——工具、日志上的折叠、浏览器座位——都只从这一条路进来，而需要调用方记得再跑一遍的第二遍，早晚会有人不跑。

<a id="how-the-blocks-are-arranged"></a>
## 那些块怎么摆

不带 `layout` 的 spec 就是它一直以来的那种读法：块按调用写下的顺序自上而下排——摆法出现之前写下的每一份 spec 也因此照画不误。`layout` 是一棵由 stack 组成的树，而 stack 是唯一的原语：一个方向、三档间距之一、是否折行，以及放进去的每个孩子占多大份额。孩子要么是一块，要么是又一层 stack，两者用同一个名字要份额：切分一行的是它的孩子，不论哪一种。最外层那个 stack 不要份额：它本来就占满整条条目，写在它身上的份额切不到任何东西，所以是点名拒绝而不是收下不理。嵌套就能表达内容栏需要的任何矩形切分；两个看似该有的第二原语都不是原语：grid 就是同一种嵌套，而切换条本来就是内容栏拿多条条目在做的事。

每个节点恰好被摆一次。树里漏掉的节点，是调用花了钱却没人看见的块；被摆两次的节点，是两块共用一个身份——而回程手势正是按这个身份指认的，座位也按它做 memo。两者都拒：前者拒在节点上，后者拒在第二次点名它的那个位置上。

上限是十二个节点、每个 stack 十二个孩子、同时最多开四层 stack。收住这棵树的正是节点上限：每个叶子都是节点，每个节点只摆一次，而 stack 不能空着，所以摆法不可能比它所排的那份 spec 更宽更多。

宿主只判形状和上限，对摆法的其他含义一无所知。stack 长什么样是座位的事，所以方向和间距写成词而不是尺寸。

<a id="what-one-block-reads-from-another"></a>
## 一块从另一块读什么

属性的值可以写成 `{"$from": "node:<id>.<输出名>[<索引>]"}` 而不是一个值，它就代表那一块此刻上报的东西。词表只有这一条引用：一个节点、它声明过的一个输出、可选地取其中一项。没有表达式、没有条件、没有循环——值是在座位里、在外壳自己的同源上下文里拼出来的，在那里求值的语言就是一台没人要的模板引擎。

宿主判的是这条引用，永远不是那个值：源节点是不是本次调用摆下的、是不是它自己、输出是不是该组件声明过的、索引是不是这个输出可能有的、以及输出携带的东西是不是目标属性收得下——全部来自目录，在任何东西被画出来之前。属性最终握着什么是座位的事，而且永不进日志：驱动了详情块的那次勾选不是模型可见的输入，所以没有任何东西需要把它记下来。

输出能不能喂给某个属性，按种类和上限判：种类相同，且它可能携带的东西没有超出属性收得下的——更长的字符串、更宽的数字、固定集合之外的取值、更多的条目、更多的键。下限**不**比，一张列表的条目会不会重复也不比：输出是用户到此刻为止做过的事，它列了几项、其中有没有两项相同，都是某一刻的事实而不是承诺；还没有第一项可读时，属性画的是座位那句等待文案，而不是一个值。

被组件读成「比文本更窄的东西」的属性，任何层级上都不许绑定。收紧那一遍跑在入口处、跑在调用自己写出的值上；被绑定的属性没有这样一个值，所以声明在它下面的路径、颜色或渲染器名会变成一条没人执行的读法。拒绝语句点名这个属性，而它想要的那个值，调用本来就可以自己写出来。

宿主自己要回读的属性同样不许绑定，拒绝语句会说出是哪个属性、为什么。数据表的行就是这一类：回程手势指认的东西——被勾中的那一行、被排序的那一列——是从写下这些行的那次调用里读出来的，而解析出来的值只活在页面的一次渲染里，任何记录里都没有它。所以数据表喂不了自己的行；目录里唯一提供的绑定，是把表的 `selectionDetail` 喂给旁边那块记录详情。

于是值只朝一个方向流。凡是会上报东西的组件，都要回读自己的属性，也就没有任何属性可以被别人写进去，绑定链因此闭不上环，这里也就不去找环。守住这条的是目录自己的测试，而不是运行时的一遍检查。

绑定要么是一整个属性的值，要么就不是绑定。写在列表条目或嵌套对象里的 `{"$from": …}` 就地被拒，理由是另一种做法等于每次重画都要在座位里把所有值走一遍去找引用。

<a id="one-entry-several-calls"></a>
## 一条条目，多次调用

一次调用拥有它 `id` 点名的那条条目；条目 id 与节点 id 用同一套字符集——字母、数字、下划线和连字符。用同一个 id 再调一次就替换掉那条条目显示的内容——两次调用都留在对话记录里，因为日志记的是发生过什么，但内容栏的切换条上只有一个标签、一块内容。换一个 id 则是在它旁边多加一条条目。

折叠认得日志里的三种形态。两种是调用：顶层的 `tool/call`，它的 `arguments` 是原始 JSON；以及 Code Mode 的 `tool/code-dispatch-start`，它的 `arguments` 已经解码——模型经 `run_code` 走到这个工具时，只会留下后一种。第三种是 `content-component/shown`，也就是打开某个已配置视图的那次点击。三种都给出同样三个值，所以智能体去修正用户打开的那块内容时，改的就是那一块，而不是在它旁边另开一块。

被工具拒绝的调用同样留在日志里——循环记的是调用本身，不是它的结局——抽取器对它跑同一套判定，所以被拒的调用不产生条目，而不是产生一条座位没东西可画的条目。视图的事件走完全相同的一遍：它的 spec 在加载期已经判过一次，这里对记录本身再判一次，才让日志始终只有一种读法。

把一条已存记录还原成条目时不查目录。目录是会增删改的构建期常量表，而一份在某个组件改名之前写下的持久化检查点必须仍能还原；真正知道自己手上有哪些渲染器的是座位，画不出来也由它去说。还原时确实要查的是这条记录有没有带上它要读的那两个字段：检查点就是一份普通 JSON，它带着的类型只是一种主张；在那里抛一次，丢的不是这一条条目，而是内容栏里所有种类的全部条目，所以本次构建读不出来的记录会还原成一条条目，由座位在上面写出那句提示。

<a id="what-comes-back"></a>
## 回程

一块界面通过跑一条命令来上报用户做了什么：`/component-action <json>`，整个输入就是一个 JSON 对象——`entryId`、`componentId`、`actionId`、`nodeId`，以及只带该动作所声明属性的 `payload`。文档里带了别的属性，无论在哪一层，都整条拒收而不是裁掉。

| 动作 | payload | 档位 |
|---|---|---|
| `el.confirm-bar` `press` | 被按下按钮的 `buttonId` | `wake` |
| `toy.table` `select` | `rowIndexes`，勾一行给一个，最多可以是表格画了多少行 | `context` |
| `toy.table` `row-click` | 一个 `rowIndex` | `context` |
| `toy.table` `sort` | 该列的 `prop` 和取 `asc`／`desc`／`none` 的 `order` | `silent` |
| `toy.table` `operation` | 被按下按钮的 `opId` 和按在哪一行的 `rowIndex` | `wake` |
| `el.filter-bar` `submit` | 一到十条 `conditions`，每条带 `key`、`op`、`value`；条上画了 AND／OR 选择时，再带用户选的 `matchMode` | `wake` |
| `el.filter-bar` `change` | 用户改完一处之后此刻成立几条的 `count` | `silent` |

界面送上来的东西没有一样是按原样显示的。条目、节点、组件、动作都是拿去和日志比对的标识符；智能体与用户随后读到的那些词——条目标题、组件名称、按下的按钮名、某一行的名字、某一列的表头、某个匹配策略的说法——都是从目录里、从模型自己写下的那份 spec 里读回来的。上报的按钮不在这条条目画出来的那些按钮里、行号超出它列出来的那些行、操作不在它带的那几个里、属性不在这张筛选条上、节点不属于这条条目、属性不是该动作声明过的，都一律不上报任何东西，点击的人会被告知这个动作没能记下来。有一种拒绝与它们分开：手势带的东西超过了该动作能收的量——筛选条件比一次能提交的条数多、任何一处超过上限——答的是那句说内容太多的话，因为这些拒绝里只有它是人做得了什么的。

一行按表格画出来的第一列显示的内容命名；那一列什么都不显示、或者调用把所有列都藏了时，按它的位置命名——`#4`、第 4 行。一次勾选点名前五行，其余只报个数。通知里引到的每一样东西都是有人写下的自由文本：模型给这条条目起的标题、它写在某一列上的表头、按钮上的字、某一行第一格显示的内容，以及唯一一样不是模型自己的话——用户敲进筛选条的值。它们全都按同一种方式读回来，因为一句话里如果这个引用值和下一个的待遇不一样，那这句话就能被其中任何一个改写：给智能体看的那句把每一个都按 JSON 写字符串的方式写出来，值里的任何东西都关不掉包着它的引号；给用户看的那行把写下的原样读回来，凡是会让它跑出一行的字符换成空格。

这不新增任何会话事件。命令的输入本来就是一条持久的、只进日志的记录：注册表在 handler 跑起来之前就把动作文档逐字写进 `command/run`，结算就是与之配对的 `command/done`；handler 造出的通知，则在智能体认领它时由循环写成 `user/message`。

智能体正在读的那次按下不会在对话里留下自己的一行。这条命令是为那条记录而发的，不是为了向刚刚亲手按下按钮的人讲述这件事，所以本行在命令名上注册了自己的聊天视图——否则聊天视图自带的默认卡片会打出 `component-action · Completed`——它空出来的那一行由 [`content-column`](../content-column/README.zh.md) 为此装的样式表折叠掉。对话里关于这样一次按下所显示的，是智能体认领的那条通知。

有两种结局是例外，也正是那个视图必须是个组件而不是一片空白的全部理由。被拒的按下什么都没到达智能体，于是通知和回答都永远不会来。智能体停下来等的那次按下如果只进了收件箱，它会被读到，但要等到用户下次开口。两种情况下，按下的那个人都只能从这一行知道这件事，所以它画的是 handler 自己那句话——这个动作没能记下来。、说清是哪种拒绝的 内容太多了，少选几项或写短一些再试。、或 已记下，你下次发消息时对话会看到。——除此之外关于这条命令什么都不画；拒绝按失败的样子画，等待中的按下按普通一行画。两种行都不是空的，折叠规则都不碰。

### 一次按下答的是什么

答的是投递到哪，不是声明的档位。`deliverAction` 报的是通知落在哪里——什么都没送、为它开了一轮、因为智能体此刻开不了轮次而进了收件箱、或者因为这个手势本来要的就是收件箱——四种里只有一种会带一句话回来，就是第三种：用户回答了智能体停下来等的那个问题，而在他们下次开口之前什么都不会发生。屏幕告诉用户「对话已经拿到你的答案了」，而对话其实正等着他们，这就是屏幕亲口让人白等。

第四种一句话都不带，这正是它必须和第三种分开的理由。勾一行是用户在干活而不是在问，没有人在等它的回答；每勾一行回一句，就是用户每碰一行、对话里就多一行——夹在智能体的回复中间，而人打开对话本来是为了读那些回复。不带文案的成功结算正是聊天行什么都不画的那一种，所以勾过的表格不会在对话里留下任何东西。

### 按下态

从日志里折出来，任何一块都不自己记。用户一挑别的条目，内容栏就把这个种类的 DOM 丢掉，于是一块自己记着按下标记的界面再回来时干干净净，同一个决定会被上报两次；因此座位读的是本行随命令一起注册的 `componentActions` 投影。它折的是一次按下本来就写下的那两条记录——`command/run` 按 `(entryId, nodeId)` 开一格，与之按 `commandId` 配对的 `command/done` 把它结算成 `sent`、`queued` 或 `refused`——浏览器就在内容栏读自己条目流的那个地方读这份值。每一块拿到自己那一格，作为 [`component-kit`](../component-kit/README.zh.md) 的 `state` prop；`refused` 仍然可按，因为再上报一次是唯一还能做的事。

只有 `wake` 会进到格子里。一块界面的状态说的是它被摆出来要等的那个答案，而一块界面上报的所有手势共用一格：所以勾选如果占了这一格，表格就会把一次勾选当成答案上报，随后把它下面那颗行按钮拒掉；筛选条则会在用户第一次改完一处（选完属性、选完策略、或者离开值输入框）时就把自己的查询按钮禁掉。`context` 与 `silent` 的手势照样上报，但把这一块留在原样——折叠不给它写格子，座位也不在页面那张等待表里给它记一行，因为根本没有结算会来。

一次手势只算给此刻在显示的那次调用：格里的 `seq` 是这次按下的日志位置，条目的 `seq` 是摆放它那次调用的位置，所以同一个 id 下后来的调用从未作答开始。

日志唯一盖不住的是这趟往返，而它由整个页面兜着，不由那一块自己兜。浏览器那半边维护一张表，记着还没有记录的那些按下，键是会话、条目、摆放它的那次调用和块——座位给每一块的 React 身份就是这四段，因为切换会话时内容栏是把座位重画而不是卸载，两个会话里落在同一个日志位置的调用否则会共用同一个挂载着的块连同它的等待：按下离开时这一块写下自己那一行，之后每次被重画都把它读回来，于是在这段窗口里做一次标签页往返，回来看到的仍是一条说着「正在发送」的条，而不是一条可以再答一次的条。一块等的是比它当前看得见的那次更晚被记下的手势，在此之前读作 `sending`。

只有两件事会清掉一行。一是记录到了。二是这次派发回话说不会有记录了——文档超量、调用被拒、网关不在——这也正是派发要有返回值的原因：没跑起来的命令不会留下任何结算可等，于是这一块说这个动作没能记下来，并接受下一次按下，而不是钉在 `sending` 上、所有按钮全死。第二件事给出的是页面按自己所见做出的判断，它按这次按下所锚定的日志位置存着：宿主在传输断掉之前已经写下的记录，照样像任何别的结算那样把这一块结算掉。

### 三档

每个动作自己声明它发生了意味着什么，投递方式由此决定：

| 档 | 手势 | 会发生什么 |
|---|---|---|
| `silent` | 给表格排序、提交前改筛选条件 | 智能体什么都收不到 |
| `context` | 勾选一行、点开一行 | 在智能体的收件箱里等，下一步被读到；同一个手势再来一次会把它替换掉 |
| `wake` | 按下确认、提交、删除 | 当场开一轮 |

档同时决定这次手势算不算这一块自己的答案：`wake` 算，另外两档不算——见上面的按下态。

`press`、表格的 `operation`、筛选条的 `submit` 是 `wake`：智能体把一个决定摆到用户面前然后停住了，而没人认领的答案它永远听不见。落在正忙着的智能体身上的 `wake` 改为暂存，和 `context` 一样——正在跑的这一轮读自己的收件箱，不需要另开一个轮次边界。

勾选行和点开一行是 `context`：它们改变智能体下一步该想的事，但不回答任何它停下来等的问题。全部取消勾选也照样上报，而不是当成「什么都没发生」略过——什么都不告诉智能体，它会一直以为上次听说的那些行还勾着。点开一行只有在调用要求「行可点开」的表格上才会上报，而且是点行里任何一格都算：组件的名称链接由 `isNameClick` 决定画不画，而它对任何一格的点击都只发同一个事件，所以一张没有什么可点开的表格，点它的格子什么都不上报。

同一个手势再发生一次，会把上一次那条还没被认领的通知替换掉。用户勾中了哪些行是一个事实，不是一部勾选史；收件箱自己没有上限；用户在表格上干活，否则每勾一次就排一条通知，而每一条都会被下一条改写。键是条目、块、动作三者合起来——点开一行不会盖掉一次勾选——替换用的是 `Inbox.replace`，它把上一条作废、把新的一条放回它的位置，所以智能体日志的记账把它算作仍在等待的工作，而不是被丢掉没跑的工作。智能体已经认领的通知永远不改写：模型已经读过它了，晚来的手势排在它后面。`wake` 也永远不被替换，因为两个问题的两个回答就是两个回答。

给表格排序、以及提交前改筛选条件是 `silent`：行按什么顺序画是用户在整理自己的屏幕，没提交的筛选条件是用户还在敲。

### 唤醒预算

每个智能体三轮。否则用户在按钮上连点就会变成一条没有尽头的轮次链；过了第三次，按下就按 `context` 暂存，直到智能体认领到一条来自人的消息，预算才整份回补。本行自己排进去的通知永远不回补它。

### 审批闸在哪

不在这里。本行不提供任何写工具，也不为自己申请审批——命令 handler 可能在没有开着的轮次时运行，而那时申请审批会直接抛错。闸是部署自己的 `tools/pre-execute` 策略，管的是在一次按下所开的那一轮里模型伸手去拿的那个写工具；组合测试钉住的正是这一点：被策略问过的既有写工具不会跑起来。

<a id="trust"></a>
## 信任边界

`spec` 是模型的输出，会在外壳自己的同源上下文里变成一块被渲染的界面。它是被限住的，不是被信任的，第一道限住它的是属性 schema：那个联合类型里根本没有哪一种成员能表达富文本或函数体，所以模型伸手去写 `formatter` 或 `onClick` 时，拦住它的是根本没有那个属性可写，而不是某个消毒器认出了一段函数体。组件没声明的属性是被直接拒绝而不是被丢掉，所以模型写了就会知道自己写了，而且拒绝里点着名。

第二道是上面那一遍收紧，管的是 schema 说不出的那部分：声明过的读法逐个值执行，读法之外的值被从这一块里丢掉而不是拒回模型——因为这一遍也跑在没有模型在等的地方，比如一条存下来的记录送去座位的路上。这一遍同时丢掉未声明的属性；走校验进来的调用永远轮不到这一手，那一支是另一次构建写下的记录才会撞上的。

浏览器座位对着从线上收到的 payload 再跑一遍同样的判定，这也是目录与校验器各自成一个模块、除了彼此谁都不 import 的原因：座位读得到它们，又不会把一份工具运行时拖进页面，两半也就不会各按一套规则判。

这一遍交出来的属性是深冻结的。渲染器可能用一个 Vue 2 组件来画一块内容，而 Vue 把组件收到的 props 逐个属性改写成响应式的——这会让座位自己那份 memo 和 Vue 树对「什么变了」各执一词。Vue 会绕过冻结的值，所以在交出去的那一步冻上就把这件事了结了，对 React 渲染器同样成立：借给渲染器的东西，它可以读，不可以写。

<a id="the-seat"></a>
## 座位

浏览器半边只有一次带键注册：内容栏开放键域 `content.surface.kind` 上的 `component` 键。座位把条目标题画在上面，下面按 spec 的 `layout` 摆出各块；spec 没写 `layout` 时，就按调用写下的顺序自上而下竖着摞。当内容栏被别的种类占着时，条目根本不会交到它手上，它也就什么都不画。`visibility` 留在页面上的是内容栏为这个种类准备的外壳，不是那些块——块的 DOM 随这一次不画一起消失。

摆法只有嵌套的 flex 行与列，别的一概没有：一个方向、三档间距之一、行放不下时要不要换行，以及每块占剩余空间的几份。座位这一遍读是复读而不是判定——宿主已经点名它拒的是哪条路径，写成模型看得懂的一句话，而这里跑的时候没有人可告知——所以本次构建看不懂的那棵树退回竖排，而不是把整条条目变白。两遍读接受的同一套词表，只在 `component-call.ts` 里声明一次。

画之前，座位会把这次调用自己的那套判定重新对着 payload 跑一遍。这不是对同仓宿主的不信任：一条条目的 payload 可能来自另一份组合写下的持久化检查点，那份组合的目录和上限不是本次构建的，所以它带着的类型只是一种主张。这次复校用的就是工具判定调用时用的那个零 import 模块——那个模块之所以零 import，正是为了这个。本次构建不接受的 payload，在内容栏里变成一句话而不是几块内容。

### 一块借给另一块的东西

一块内容通过 `onOutput` 发出它对自己此刻状态的读数——表格勾中的那一行，铺成记录详情要的那组行——座位把这些值放在 React 状态里，只在摆下它们的那次调用还在屏幕上时有效。写成 `{ "$from": "node:<id>.<output>[<index>]" }` 的属性，取的就是被指名那块最后发出的值，而这次代入发生在页面里：代入后的值不进 payload、不到宿主、也不进会话日志。正因如此，一份记录才能跟着表格的选中走，而不必让每一次勾选都变成必须被记录的模型可见输入；也正因如此，这套词表只有一条引用，没有表达式、没有条件、没有循环。

座位先代入再判定，所以一块内容据以绘制的值，走的是这次调用被判定时的同一份 schema。这一点要紧，因为发出来的值不是任何宿主判定过的值：宿主查的是这个产出**能不能**站到那个属性的位置上，从来不查它会装什么。必填属性还没有东西可代入的那一块，会被排除在这次判定之外而不是让判定失败，并在原位画上组件行的等待提示；代入后装不下的值也一样，让被喂的那些块继续等，于是没被喂过的块照画。

同一条目 id 下的后一次调用从「什么都没发过」开始，因为它画出来的块确实什么都没发过：把上一次调用的值带过来，等于拿一张已经不在的表的行去喂新的记录块。

每一块都按自己的身份做记忆化——它所属的条目、该条目当前的序号、这个节点、折叠里记在它名下的那次手势，以及（对读取别块的那一块而言）它的引用此刻代入成了什么——所以没有被喂过的那一块，在座位因为别的块发了东西而重读 payload 时，保留它已经拿到的那个对象。这不是优化：`el-table` 把新的行数组读成「行被换掉了」并清空选中，所以旁边那块每被喂一次就换一份属性的表格，会把刚喂给它的那次勾选丢掉。渲染器按节点写下的目录 id 从组件行的表里取；表里没有这一项时，就在那块的位置上把这件事说出来——组合里装了不匹配的组件行时，用户看到的就是它。

座位自己不带词典。它通过组件行的命名空间 `componentKit` 取文案，因为「这一块画不出来」这句话属于组件，而不属于把它们摆进来的那个包。

## Model Experience

### `show_component` 的提供

#### What the model sees

一个工具 `show_component`，必填 `id` 字符串、必填 `title` 字符串、必填 `spec` 对象，`spec.nodes` 数组必填、`spec.layout` 可选。描述里带着完整目录，一个组件两行：先是 `- id — label — purpose`——不上报动作的组件，那一行末尾多一句 `Nothing comes back from it.`——下面再跟一行 `props:`，点名这个组件声明的每一个属性：可以不送的打 `?`，数字带 `(min–max)`，固定取值集合带 `(a|b|c)`，是非项带 `(true|false)`，列表写成 `[一个条目是什么] (min–max)`，由已声明属性组成的对象写成 `{…}`，键名由模型自己定的对象写成 `{<field>: text|number|boolean}`。另一块能从中读到东西的组件还多一行 `outputs:`，点名每个值并用同一套写法写出它的形态——绑定写得出来靠的就是这一行：引用点名的是这些 id 之一，而目标属性收不收得下这个值，也是照这一行判的。再往下是 `id` 的复用规则、节点数与字节上限、未声明属性一律拒绝这条规则、讲摆法的一段和讲「从另一块读」的一段，以及那句说明回程的话：用户在一块界面里做了什么会到模型这里，并带上发生在哪条条目、哪一块，除非那个组件的行上已经说了不会。目录行里的组件名就是终端用户看到的中文名，所以模型在对话里提起某一块时，提的就是用户看到的那个叫法。本包不贡献任何系统提示词分节。部署组合了数据来源时，这份说法里再多一个可选的 `dataSource` 数组和一段话：一项里有哪些字段、十六种匹配算子的名字、行数上限、被点名的块自己不送行而它的 `gridItems` 仍然说明读哪些属性、每次调用问用户一次且拒绝什么也不画、回来的是计数与属性名而不是行。没组合的部署里，参数和这段话都不存在，所以那些部署的请求字节一个都没变。

#### Token effect

一份固定描述加参数 schema，出现在每一次这个工具可见的请求里。描述每多一个目录条目就多两行——另一块能从中读到东西的多三行——第二行的长短取决于那个组件整棵属性树，表格那一行最长，因为它的列是对象里的一个列表。`spec` 的 schema 保持浅——一个对象、一个数组，外加一个不加约束的 `layout`——因为每个组件各自的属性写在目录行里、摆法自己的词表写在描述里，而不是写成嵌套 JSON Schema。

#### KV Cache effect

描述在行加载时组装一次，只取决于目录，因此在一个部署内每次请求里工具块逐字节相同，前缀成立。

### 工具调用结果

#### What the model sees

被接受的调用回一句 `Now showing "<title>" in the content panel: <labels>.`，后面跟着点名要复用哪个 id 的那句话。被拒绝的调用回 `Error: show_component: <路径> — <哪里不对、该改成什么>`；点名了不存在的组件时，再附上完整目录，属性行也在里面，于是改过的那次调用不必再挨一次拒绝才知道换的这个组件收什么。取过数的调用每填一块多一句——`Read 20 of 89 matching rows from "SpaceLayer" into block "rows", for the attributes zh_label, layer_id.`——行里的内容一个字也没有。没取成的那次只回一句话，说清是六种里的哪一种：手上没有凭据、用户没有同意、后端答的是别的、这张表没有叫这个名字的属性（附字典自己前十个，于是下一次调用同样不用再吃一次拒绝）、什么都没匹配上，或者到手的行超过一份 spec 装得下的量。

#### Token effect

每次调用一行短句。点名未知组件的那条拒绝会长出一份目录，而这正是它的用处：它顶掉了第二次失败调用。

#### KV Cache effect

只追加；结果跟在可复用的请求前缀之后，不让任何已缓存的内容失效。

## Known Limitations and Deferred Work

- **按行裁剪是后端的事，本行无法证明它真的发生** — 部署自己的前端有一套行/列权限判定，但在读不到登录态时它是提前返回把数据放开、而不是收紧，所以它根本不是权限边界。后端若不按拿到的 token 裁行，一次取数就可能把这个人本不该看到的行画上他自己的屏幕、写进他自己的会话日志——而退出并不清洗已经写下的日志。要闭掉这条，需要的是那套后端的主人给的答案，不是这里的代码。
- **那行标识写的时候单占一行，画出来并不单占一行** — 审批窗把理由里的换行渲染成空格，于是 `数据表：SpaceLayer` 读起来像句子里的一个从句，而不是正文下面的一行小字。让那行可信的每一条仍然成立——它依旧是卡片上模型写的任何词都够不着的那一部分——但要核对的人得在一段话里把它找出来。保住那些换行是审批窗那边的事。
- **卡片上那张表的名字，是模型对它的说法** — `metaLabel` 由调用写下，不是从后端字典里读来的。字典要等用户答完才读，所以模型把表标错时，人已经先信了它。先读名字再问，等于在提问之前就花掉凭据，而这个顺序是本行唯一不接受的。它下面那行标识能做的，是让人有机会看出对不上；做不到的，是拦住一个看起来合理的错标签被当成对的。
- **表头只在调用没写时才来自字典** — 带了 `alias` 的列保留调用写的那个，不管后端把这个属性叫什么。模型把某一列叫成别的东西，因此只有懂这张表的人看得出来。
- **一次失败的取数会让上一张表留在屏幕上，且没有任何地方说它是旧的** — 条目原封不动，所以一次读不成的替换显示的是上一次成功调用摆下的东西。模型会被告知，也该在对话里说明；要让那一块自己说出来，得让条目带上一个「这份是旧的」状态位，那是另一件事。
- **本行要的列比部署自己那个页面少** — 组件库把方案里的每一列都送出去、隐藏列也送；这里的一次调用只送它声明过的那几列。这是有意的收紧而不是对齐失败，也是同一张表在这里画出来会比在部署自己页面上少的原因。
- **进日志的行就是 checkpoint 的重量** — 一份填好的 spec 最多 65536 字节，每条活着的条目一份，内容面写的每个 checkpoint 都带着它。这和图表把整份 option 存进去是同一笔代价，而这条路线每取一次数就付一次。
- **只有一页，永远没有第二页** — `page` 说的是一页多大而不是第几页，所以没有办法要第 201 到 400 行。想读得更宽就把 `pageSize` 调大，上限是表自己的 500 行；再宽就该由模型去收紧条件。
- **部署自己写的视图读不到自己的数据** — `dataSource` 是这次调用的参数，所以 `cordis.yml` 里配的视图带的永远是写它的人手敲进去的那些行。一个首页视图想显示实时数据，今天没有办法说出这件事。要让视图自己取数，就得把问题挪到用户点开它的那一刻去问——配置出来的视图没有一次模型回合可以挂这个问题——那是下一片，不是这一片。
- **表画不出来的单元格是被丢掉、不是被拒绝** — 行里只有文本、数字和是非；空值、嵌套记录或列表会被从行里去掉而不是让整次取数失败，因为「这一格没有」本来就是表对它的画法。后端回来的存储行与显示行数量对不上时，存储行整份不写，因为表的这两个列表是一一对应的。
- **不做服务账号，这是定下的** — 会话里没有登录凭据就拒绝，让访客去登录。另一条路会让审批卡片开头那三个字「用您的账号」，对那个兜底账号的实际归属者变成假话。
- **一次取数的记录在读取时是必需的** — `content-component/resolved` 不带 `ignorable` 标记，理由和 `content-component/shown` 一样：`Session.append` 没有给追加方设置它的途径。本仓库的任何构建都认识这个类型。
- **payload 白名单是界面那半边的承诺，不是宿主在执行的东西** — 命令注册表在任何 handler 跑起来之前就把命令输入逐字记下了，所以一份超量的动作文档在本行拒绝它的时候早已进了日志。宿主仍在执行的是字节上限和已声明属性：超过上限、或带了该动作没声明的属性，这个动作就完全不会投递给智能体。只送该动作声明过的东西是座位的义务，而两个半边都在本包里。
- **折叠行写的是机制而不是那块界面** — 一条通知在对话里是一行折叠行，表头写着「上下文注入 · content-component」（英文界面是 `Context injection · content-component`），一个术语加一个插件 id 摆在终端用户面前；旁边那句一行摘要是个可伸缩的格子，控制台三栏布局的聊天列宽度会把它挤到零宽。展开也好不到哪去：露出来的是给模型看的那句英文，连同句子里的内部标识符——`The user pressed "Approve" in content panel entry "budget" ("Budget approval"), on the 确认条 block "ask".`——写给智能体的那份说法，直接摆给做出这个动作的人看。行与展开的正文都由 [`ui-conversation`](../../client/ui-conversation/README.zh.md) 对所有产出方一视同仁地画；这一整条的复查触发器是 `develop` 线上那个「按产出方给显示名」的改动，按产出方定制的展开态文案也归在那里。
- **这条命令会出现在终端用户的斜杠菜单里** — `commands.register` 没有任何办法把一行挡在输入框提供的那张菜单之外，于是 `/component-action` 就列在那儿，旁边还跟着 `<json>` 提示，而那张菜单里别的每一行都是给人打的。这一行能做的只是把话说清楚：描述写成终端用户读的中文，点明是内容面板里的按钮、由页面自己发出。真在那里手打一行，它谁也对不上，答的是与丢掉的按下同一句拒绝；而只要这行的格式足以点出一条条目和一个块，它还会把那一块重画成这句拒绝——手势折叠读的是一行里带的标识符，只有 handler 才拿它们去对当前在显示的条目。把它从菜单里去掉是 `dsh-commands` 的改动——描述符上加一个 `listed` 字段——等第二个需要它的行出现时一起做。
- **唤醒预算只在内存里** — 已花掉的唤醒记在一张以智能体对象为键的表里，所以重启之后每个智能体都重新拿到整份预算，恢复出来的会话也无从知道它的那些按下已经开过几轮。那张记着还没被认领的 `context` 通知的表也是同样的键、同样地忘掉：重启之后一块界面的第一次勾选，会在日志里那条通知旁边再排一条，代价是模型多读一句已经被改写的话，仅此而已。
- **一次什么都没填的按下，看上去就是按钮没反应** — 筛选条一开始就带着一个空条件行，所以用户能做的第一次按下提交的是零个条件；那次按下什么都不上报，块上也不画任何一行，因为画一行就等于说发生了什么。用户拿到的是一个按下去屏幕毫无变化的按钮。把按钮置灰是正解，而它不是本地的：那一块得知道编辑器里有几条完整的条件，那正是 `change` 手势自己带的计数，而拿一个每次改完一处就送来的计数去驱动按钮的状态，需要两个包对「按钮什么时候可以动」达成一致。触发条件是第一次有人反馈「点了没反应」。
- **一块界面说不出手势为什么被拒** — 折叠把被拒的手势结算成同一种状态，所以不管是指向了屏幕上不存在的东西，还是带的东西超过了动作能收的量，块上画的都是 这个动作没能记下来，可以再试，而旁边聊天行画的是 handler 自己那句 内容太多了，少选几项或写短一些再试。。两句话就同一次按下在用户面前互相矛盾。要在块上把它们分开，得给 `ComponentActionState` 加一个成员，那是本包的折叠与 [`component-kit`](../component-kit/README.zh.md) 的状态表和词典之间的契约；触发条件是第一个聊天行不在块旁边的部署。
- **手势折叠按块而不按动作** — 按 `(entryId, nodeId)` 一格。今天够用只是因为一个组件至多声明一个 `wake`，而别的档根本不进格子：等哪个组件声明第二个 `wake` 的那天，那一块画出来的就是这两个里最后上报的那个的状态。解法是把格子的键按 `actionId` 长一位，改在 [`src/action-state.ts`](src/action-state.ts) 和它旁边的投影里，这笔账由第二个 `wake` 来付。
- **日志开了却没合上的那次按下会一直读作「正在发送」** — `command/run` 与 `command/done` 分别写在 handler 前后，宿主在两者之间停下就会留下一个没合上的格子，而之后没有任何东西会去合上它。那一块要等后来的调用替换掉这条条目才恢复可按。压根没产生任何记录的那次按下是另一回事，它会自己了结：派发如实回话，页面把那一行丢掉，这一块恢复可答。
- **三句结算文案在任何界面里都是中文** — `这个动作没能记下来。`、`内容太多了，少选几项或写短一些再试。` 与 `已记下，你下次发消息时对话会看到。` 由 handler 写下，而 handler 拿不到浏览器的语言：命令结果就是一个字符串，会话日志又必须留下用户当时真正看到的那些字。于是在非中文控制台里，它们画在聊天行里，紧挨着一条条上文案——那些文案来自 [`component-kit`](../component-kit/README.zh.md) 的字典，是已经本地化的。真正的解法要么是改成由客户端翻译的 key，要么是让命令结果带上语言，触发器是控制台开始提供中文以外的界面。
- **回程通道没有装配转录覆盖** — `content-console` 泳道驱动的是 ACP 智能体，而 ACP 协议没有命令方法，任何录下来的转录都载不动一次按下。那条泳道照样组合了命令注册表，因为它钉住的那段描述告诉模型按下会回来；按下这件事由针对真实控制台组合的 Playwright 场景覆盖，那里的浏览器、RPC 网关、命令注册表和会话日志都是发行的那一套。
- **模型看不见内容栏里现在有什么** — 没有读取路径。智能体只知道自己发过哪些调用，不知道用户正在看哪一条、有没有谁被关掉、任何一块此刻显示着什么。
- **有属性收得下才声明输出，没有就不声明** — 目录里现在只有一个：数据表的 `selectionDetail`，被记录块的 `dataList` 收下。数据表同样知道调用写下的那些被勾中的行，筛选条也知道自己此刻握着哪些条件，两者都没有声明——因为这里没有任何属性收得下它们，而没人收得下的输出，等于先给模型一条绑定再拒掉它。等到出现把行或条件当输入吃进去的组件时再声明：一行目录加渲染器里的一次 `publish`，因为现在两个渲染器都不发它们。目录里其余组件什么都不上报，绑定点名它们时也会被这么告知。
- **被读成「比文本更窄的东西」的属性不许绑定** — 路径、颜色、单元格渲染器名都是在入口处、对着调用自己写下的值读的；被绑定的属性没有这样一个值，所以整条属性直接被拒，而不是让一个跳过了读法的值抵达渲染器。这条覆盖属性的任何层级——所以数据表的行可以绑，而它的 `tableConfig` 一点也不能绑。
- **空输出会让被它喂的块停在等待行** — 相容判定只看种类和上限，所以绑到表格 `selectionDetail` 上的写法在还没人勾时就被接受，而不是因为用户还没勾就回头拒掉这次调用。下限在画的时候依然算数：目录里每一个可绑属性都要求至少一项，所以一份空勾选代入进去会把这份文档判定为拒，被喂的块一律画等待行，直到用户勾上一行。改成静态也比下限只会更糟：直接把这条绑定拒掉，这对块就根本写不出来，而勾选在用户动手之前本来就是空的。
- **一次绑定只读一块，既跨不了条目也不含表达式** — `$from` 指名一个节点、它声明过的一个产出，最多再取其中一项。没有运算、没有条件、没有默认值，也够不到另一条条目里的块，因为座位自己的 props 一次只带一条条目。模型想要一个算出来的值，就把那个值直接写下来。
- **摆法被读了两遍，两个模块必须一致** — 宿主判定 `layout` 并点名它拒的是哪条路径；座位在线上边缘再读一遍同一棵树，因为它判定节点的那一遍只跑画得出来的那些、而 `layout` 不进那一遍；读不懂就退回竖排。两边共用全部词表——方向、间距、上限，以及每种节点可以带哪几个键——写了两遍的是走法本身，而只加在一边的走法规则，表现成「模型被告知这次调用没问题，而内容栏不理它」。要把两者合并，得在判定旁边导出一个布局读取器，触发器是第二条必须写两遍的规则。
- **等待中的块只说自己在等** — 必填属性没有东西可代入的块画一行字，代入后装不下的块画的也是同一行字。用户分不出「请在上面勾一行」和「勾上的东西这里画不了」，而后者是这次调用写错了、不是用户能处理的事。要分开就得再加一句话，并且让座位在丢掉那次拒绝之前知道自己落在哪一种情形里。
- **空值就按空值画** — `toy.record` 里 `display` 为空串的那一行保留名称，旁边什么也不显示。这是有意的：另一种读法是把整行丢掉，那会让用户根本看不出这条记录有这个属性。模型若想表达「这项没设置」，就把这几个字写出来。
- **目录里有五项** — 把一个真实组件库的其余部分映射成目录条目，以及把那些组件打进浏览器产物的打包链路，都是另一片工作。
- **还没有组件声明 `path`** — 这条读法已经执行、也有测试，第一个要指向某个静态资源的组件才是把它放到真实屏幕上的那一刻。渲染器名和颜色两条已经有人声明了：数据表和指标球。
- **有一种匹配策略没人算得了** — 一次调用能收窄到的那十六种，就是条件编辑器画出来的那十六种：用户挑得到、而本包叫不出名字的策略，意味着人辛辛苦苦编好的筛选被告知没能记下来。`NOT_BETWEEN` 是组件库自己的 `matchUtil` 没有分支的那一个，所以带着它的条件是作为「用户要的是什么」的陈述抵达模型的，被要求去跑它的后端自己回答自己。本包不评估任何条件。
- **调用不点名就没有 AND／OR** — `confStyle.showMatchMode` 默认关着，块打开它才画：这个控件只有在答案会把它带回去的时候才值得画出来。画了它的那张条会把模式连同条件一起提交，通知里也会说出用户选的是哪一种。
- **五百行的表很少放得下** — 行数上限是表格的，而 `spec` 卡在 65536 字节，几百行几列的表先撞到的是后者。拒绝语句会说出这件事，并点名字节数。动作上限从另一头同样咬人：一次提交十条、每条二百字的筛选，超过 4096 字节，答的是那句内容太多的话。把一张满行的表整个勾上不在此列——勾选上限**就是**行数上限，字节上限也留够了装下它。
- **条件编辑器自己没有上限** — 一张筛选条一次最多提交十条条件，而按下它自带的增加按钮，那个 vendored 编辑器就一直加行。于是第十一条会被建起来，屏幕上没有任何东西说它送不出去，送它的那一次按下答的是那句说内容太多的话。那一块自己只说这个动作没能记下来，因为它折出来的结算不带原因；原因在旁边的聊天行里。要把编辑器拦住，上限得在缝的渲染器那一侧，而本包给不了它——[`component-kit`](../component-kit/README.zh.md) 是给任何摆放它的人画块的，不能反过来 import 一个落位包。
- **值控件的形态取决于本 schema 不带的一个字段** — 属性的 `dataType` 只有在这条属性同时声明「值是手填而不是从服务里挑」时，条件编辑器才会去读。本包声明 `dataType` 而不声明那个字段，所以补上它是渲染器的事；不补的渲染器，无论 `dataType` 写什么，每条条件都画成纯文本输入框。
- **块里自己填的东西一旦不被选中就不会留下** — 座位只画被选中的那条条目，内容栏被别的种类占着时更是什么都不画，所以无论是切换种类，还是在两条 `component` 条目之间切换，用户在当时那些块里填过的东西都会丢掉。已经上报出去的手势会留下，因为它在日志里而不在这一块里。
- **本次构建不能完整接受的条目会整条画不出来** — 座位是对整份 payload 重新判定的，所以只要有一个节点写的组件本目录已经不带了，这条条目连本来能画的那些块也一起没了。唯一的例外是被别块喂的那种块：它拿到的值来自页面而不是来自调用，所以装不下的值只让被喂的那些块继续等，其余照画。
- **上限是协议常量，不是配置** — 原因与「要先有什么才能把它们变成部署的选择」，上面的配置一节已经写了。
- **视图点击的记录在读取时是必需的** — `content-component/shown` 不带 `ignorable` 标记，因为 `Session.append` 没有给追加方设置它的途径，所以会话词汇表里没有本包的运行时会拒绝含有它的整份日志，而不是跳过这条事件。本仓库的任何构建都认识这个类型；单独构建、且去掉了本包的运行时则不认识。控制台另外两个内容行处境相同，原因也相同。
- **没有配置视图的部署不提供目录路由** — 只有 `views` 里有条目时才会认领那条路由和那条命令，所以侧栏去问一个没配视图的部署时，拿到的是 web 服务器兜底回的东西，而不是一份空目录。这与本行根本没被组合时拿到的东西一样，也是侧栏本就兜住的情况；代价只是两者分辨不出来。
- **视图点击没有装配后的记录覆盖** — `content-console` 通道驱动的是 ACP 智能体，而 ACP 协议没有命令方法，所以没有任何录制记录能带上一次点击，正如没有任何记录能带上一次按下。那条通道仍然配了一个视图，因为对它的加载期判定本就是启动那份组合所证明的一部分；点击之后发生的事，由本包自己的组合测试和针对真实控制台的 Playwright 场景覆盖。
- **一条条目带着自己整份 spec** — 内容栏的投影按存活条目保存已校验的 spec，因此它随线上值与持久化检查点一起走。字节上限就是限住它的东西。
- **不变式只经调度路径上报** — `Session.append` 把抛错的监听器记进日志后继续跑，所以实时审计只有在提交事件经由 context 调度时才能到达调用方；启动时对已加载会话的那一遍不受影响。
- **画出来的那一块没有组装快照覆盖** — 这把工具模型可见的全部内容（含拼进工具描述的目录与结果文本）由 [`examples/content-console`](../../../examples/content-console/README.zh.md) 泳道钉住，那条泳道真实组合了这一行并跑通一次完整调用。座位随后把它画成什么样，则是针对真实控制台组合的 Playwright 场景。
