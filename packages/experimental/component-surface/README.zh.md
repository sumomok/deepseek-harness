# @deepseek-ai/dsh-experimental-component-surface

[English](README.md) | 中文

`show_component`：智能体把一块界面——一段提示加一行按钮、一条记录的详情、一张记录表、一行筛选条件、一个数字——放进对话旁边的内容栏，组件取自本包自己的目录，并在任何东西被画出来之前按该目录逐项判定。

这个包两个半边都有。宿主半边把工具交给模型、校验每一次调用、并认领[内容面](../content-surface/README.zh.md)条目流里的 `component` 种类；浏览器半边认领内容栏 `content.surface.kind` 槽的 `component` 键，把每条条目的 spec 画出来。组件本身不属于任何一半：渲染器来自[`component-kit`](../component-kit/README.zh.md)，它不认识布局，而本包做的就是把它的一块摆进某一列里。

用户在一块界面里做了什么，则沿另一个方向回来，走本行自己的一条命令：`/component-action`。

这里不写任何会话事件。一次调用的记录就是循环本就写下的 `tool/call`，一次动作的记录就是命令注册表本就写下的 `command/run`，所以两个方向都由智能体写下的日志重放出来，把这一行卸掉也不会让任何历史会话读不出来。

## 组合

[`overlay/component-surface.patch.yml`](overlay/component-surface.patch.yml) 把这一行和组件行一起叠在服务线控制台组合之上——那份组合已经带了内容面与内容栏。覆盖文件自己的注释里写着启动命令。

这一行分三块各自独立生效。工具只需要工具运行时，所以没有内容栏的组合照样提供它、照样记录它的调用；抽取器需要内容面路由器，没有路由器时调用就只留在日志里没人读——后来才长出内容栏的组合要的正是这个；回程通道则三样都要：命令注册表、那个路由器，以及条目所在的投影注册表——没有内容栏就没有任何一块界面可供动作指认，所以那时命令干脆不存在，而不是对每一次手势都回一句拒绝。

## 配置

没有配置项。部署可能想调的那几个数——spec 字节上限、节点上限、嵌套上限、动作字节上限——被校验两次：这里一次，浏览器座位对着从线上收到的值再一次。座位收不到 Cordis 配置，所以按部署可变的上限就是两边会对不上的上限：结果是内容栏里悄悄少一块，而不是模型能据以纠正的一次拒绝。在座位能读到部署设置之前，它们是 [`src/component-call.ts`](src/component-call.ts) 里的协议常量；等座位能读设置那天，上限和提供设置的那条路由一起到来。嵌套上限连在那里也没有写死：它是从目录量出来的，所以某个组件声明了一个嵌套属性，上限就正好为它加宽，合法文档不会被当成畸形拒掉。

动作的上报档位既不是上限，也不是配置。它说的是一次手势意味着什么——按下的确认就是智能体停下来等的那个答案——所以它和动作一起声明在目录里；部署去改它，改的是智能体被告知发生了什么。

## 目录

一个工具管所有组件，而不是一个组件一个工具。有哪些块是部署的目录，而目录写进一份描述里一次，比摊在一份越来越长、模型每次请求都要读的工具清单里便宜。目录是 `component-call.ts` 里的静态常量表；当一个不归本包维护的包需要贡献组件时，再把它换成注册式的缝。

目前有五项：

| 组件 | 名称 | 画出来是什么 | 什么会回来 |
|---|---|---|---|
| `el.confirm-bar` | 确认条 | 可选标题、可选说明，以及一到五个按钮，每个按钮带 id、文字和可选的语气 | `press`，带着被按下的按钮 id |
| `toy.record` | 记录详情 | 一到六十行，每行一个不超过 40 字的标签和一个不超过 400 字的值；可选的标签宽度 40 到 240，可选的列数 1、2 或 3 | 什么都没有 |
| `toy.table` | 数据表 | 一到三十列铺在一到五百行上，每一列按字段名从行里取值，可选地交给五种单元格渲染器之一去画；可选的勾选列、可点名称、最多五个自定义操作按钮，以及操作列宽 | `select`、`row-click`、`sort`、`operation` |
| `el.filter-bar` | 筛选条件 | 一到四十个属性供用户在其上编条件；可只放行十六种匹配策略中的一部分 | `submit`、`change` |
| `el.metric` | 指标球 | 一个 0 到 100 的指标画成注水的球；可选的文字、尺寸与三种颜色 | 什么都没有 |

不上报任何动作的组件，会在工具描述里自己那一行上说出这件事——否则模型以为块会答话，摆下一个只用来看的块然后干等。每个组件的属性写在这一行下面，由它的 `propsSchema` 派生，而不是写在它旁边，所以「提供给模型的」和「用来判定调用的」不会漂开，模型也不必先花一次被拒的调用去问清楚该送什么。这一行一路写到底：嵌套的列表要说清它的一个条目带什么，因为只写了名字的列表，模型要一条属性一次被拒的调用才问得出来。它略去的是拒绝语句本来就会说出的每一条边界——字符串长度、token 的字符集——因为描述是每次请求都要付的，而拒绝只付一次。

记录里 `display` 为空串的那一行仍在原位：组件画出名称，旁边什么也不画——这正是记录有这个属性、但没填值的样子。

组件的属性用一套只有七种形状的小 schema 声明：有长度上限的字符串（可再限定字符集）、落在声明区间里的数字、`true` 或 `false`、固定取值集合（字符串或数字）、由更多已声明属性组成的对象、键名由调用方自己定的对象，以及以上任何一种组成的、有条数上限的列表。列表里的条目如果是用户要去点的东西，还要点名哪个属性用来标识它；什么都不回传的列表——比如一条记录的各行——不声明这个属性，两行共用一个标签是数据本身而不是错误。这个联合类型本身就是安全边界，不是写起来方便，理由见下面的信任边界一节。

键名由调用方自己定的对象，就是一行表格数据：键是各列去取值的字段名，没法像组件自己的属性那样预先列出来。它改用别的方式收口——键有字符集和长度、有个数上限，值只能是标量——描述里写成 `{<field>: text|number|boolean}`。

schema 说不出的是一个字符串**意味着**什么。把某个字符串读成路径、颜色或单元格渲染器名的组件，要在 schema 旁边声明这层读法（一共只有三种），由 [`src/sanitize.ts`](src/sanitize.ts) 在入口处执行：不是单斜杠开头同源路径的路径、`#RGB`／`#RRGGBB`／`rgb()`／`rgba()` 之外的颜色，都会被丢掉；白名单之外的渲染器名退回朴素渲染器，而不是让单元格没有东西画它。声明过的读法会写进工具描述里，因为这一遍是丢值而不是拒绝整次调用，模型没被告知写法就永远不知道自己写的那个值为什么消失了。渲染器名同时还声明成一组固定取值，所以点名白名单之外渲染器的调用会直接被拒；那条退回留给白名单收窄之前存下来的记录。数据表声明了渲染器名，指标球声明了它的三种颜色，`path` 是目前还没人声明的那一种；这一遍照跑，因为另一种做法是让规则跟着第一个需要它的组件一起到场，而在那之前它一次都没跑过。

键名由调用方自己定的对象，自己声明它这几个键的读法，而不是共用组件那一份：它的键是数据——`color` 既是某个单元格渲染器的配置项，也可能就是别人记录里普普通通的一列，而按名字挂在组件那一层的规则会把两者一起收紧。

## 一次调用要过哪些判定

按顺序，每一步都能结束这次调用：条目 `id` 与 `title`；spec 的嵌套深度；它的字节大小；spec 与节点各自允许携带的属性名；每个节点的 id、它在本次调用内的唯一性、以及它点名的组件；最后是该组件的每一个属性。

深度在大小之前量，因为两者都要走一遍文档，而只有深度这一遍在写法上就有界——它在上限处停下，而不是走到值的底部。

每一条拒绝都点名出错的参数路径，因为这条路径是模型唯一的通道：一次带八个节点的调用只换回一句话，这句话不说出 `spec.nodes[3].props.buttons[1].id`，下一次调用就只能猜。点名了本部署没有的组件时，拿回的是完整目录而不是一个数字，于是纠正不需要再多一个来回。

通过判定的节点离开这里时，属性已经被收紧过一遍：三个读者——工具、日志上的折叠、浏览器座位——都只从这一条路进来，而需要调用方记得再跑一遍的第二遍，早晚会有人不跑。

## 一条条目，多次调用

一次调用拥有它 `id` 点名的那条条目；条目 id 与节点 id 用同一套字符集——字母、数字、下划线和连字符。用同一个 id 再调一次就替换掉那条条目显示的内容——两次调用都留在对话记录里，因为日志记的是发生过什么，但内容栏的切换条上只有一个标签、一块内容。换一个 id 则是在它旁边多加一条条目。

折叠认得调用在日志里的两种形态：顶层的 `tool/call`，它的 `arguments` 是原始 JSON；以及 Code Mode 的 `tool/code-dispatch-start`，它的 `arguments` 已经解码。模型经 `run_code` 走到这个工具时，只会留下后一种。

被工具拒绝的调用同样留在日志里——循环记的是调用本身，不是它的结局——抽取器对它跑同一套判定，所以被拒的调用不产生条目，而不是产生一条座位没东西可画的条目。

把一条已存记录还原成条目时不查目录。目录是会增删改的构建期常量表，而一份在某个组件改名之前写下的持久化检查点必须仍能还原；真正知道自己手上有哪些渲染器的是座位，画不出来也由它去说。还原时确实要查的是这条记录有没有带上它要读的那两个字段：检查点就是一份普通 JSON，它带着的类型只是一种主张；在那里抛一次，丢的不是这一条条目，而是内容栏里所有种类的全部条目，所以本次构建读不出来的记录会还原成一条条目，由座位在上面写出那句提示。

## 回程

一块界面通过跑一条命令来上报用户做了什么：`/component-action <json>`，整个输入就是一个 JSON 对象——`entryId`、`componentId`、`actionId`、`nodeId`，以及只带该动作所声明属性的 `payload`。文档里带了别的属性，无论在哪一层，都整条拒收而不是裁掉。

| 动作 | payload | 档位 |
|---|---|---|
| `el.confirm-bar` `press` | 被按下按钮的 `buttonId` | `wake` |
| `toy.table` `select` | `rowIndexes`，勾一行给一个，最多可以是表格画了多少行 | `context` |
| `toy.table` `row-click` | 一个 `rowIndex` | `context` |
| `toy.table` `sort` | 该列的 `prop` 和取 `asc`／`desc`／`none` 的 `order` | `silent` |
| `toy.table` `operation` | 被按下按钮的 `opId` 和按在哪一行的 `rowIndex` | `wake` |
| `el.filter-bar` `submit` | 一到十条 `conditions`，每条带 `key`、`op`、`value`；条上画了 AND／OR 选择时，再带用户选的 `matchMode` | `wake` |
| `el.filter-bar` `change` | 用户改完一处之后此刻成立几条的 `count` | `silent` |

界面送上来的东西没有一样是按原样显示的。条目、节点、组件、动作都是拿去和日志比对的标识符；智能体与用户随后读到的那些词——条目标题、组件名称、按下的按钮名、某一行的名字、某一列的表头、某个匹配策略的说法——都是从目录里、从模型自己写下的那份 spec 里读回来的。上报的按钮不在这条条目画出来的那些按钮里、行号超出它列出来的那些行、操作不在它带的那几个里、属性不在这张筛选条上、节点不属于这条条目、属性不是该动作声明过的，都一律不上报任何东西，点击的人会被告知这个动作没能记下来。有一种拒绝与它们分开：手势带的东西超过了该动作能收的量——筛选条件比一次能提交的条数多、任何一处超过上限——答的是那句说内容太多的话，因为这些拒绝里只有它是人做得了什么的。

一行按表格画出来的第一列显示的内容命名；那一列什么都不显示、或者调用把所有列都藏了时，按它的位置命名——`#4`、第 4 行。一次勾选点名前五行，其余只报个数。通知里引到的每一样东西都是有人写下的自由文本：模型给这条条目起的标题、它写在某一列上的表头、按钮上的字、某一行第一格显示的内容，以及唯一一样不是模型自己的话——用户敲进筛选条的值。它们全都按同一种方式读回来，因为一句话里如果这个引用值和下一个的待遇不一样，那这句话就能被其中任何一个改写：给智能体看的那句把每一个都按 JSON 写字符串的方式写出来，值里的任何东西都关不掉包着它的引号；给用户看的那行把写下的原样读回来，凡是会让它跑出一行的字符换成空格。

这不新增任何会话事件。命令的输入本来就是一条持久的、只进日志的记录：注册表在 handler 跑起来之前就把动作文档逐字写进 `command/run`，结算就是与之配对的 `command/done`；handler 造出的通知，则在智能体认领它时由循环写成 `user/message`。

智能体正在读的那次按下不会在对话里留下自己的一行。这条命令是为那条记录而发的，不是为了向刚刚亲手按下按钮的人讲述这件事，所以本行在命令名上注册了自己的聊天视图——否则聊天视图自带的默认卡片会打出 `component-action · Completed`——它空出来的那一行由 [`content-column`](../content-column/README.zh.md) 为此装的样式表折叠掉。对话里关于这样一次按下所显示的，是智能体认领的那条通知。

有两种结局是例外，也正是那个视图必须是个组件而不是一片空白的全部理由。被拒的按下什么都没到达智能体，于是通知和回答都永远不会来。智能体停下来等的那次按下如果只进了收件箱，它会被读到，但要等到用户下次开口。两种情况下，按下的那个人都只能从这一行知道这件事，所以它画的是 handler 自己那句话——这个动作没能记下来。、说清是哪种拒绝的 内容太多了，少选几项或写短一些再试。、或 已记下，你下次发消息时对话会看到。——除此之外关于这条命令什么都不画；拒绝按失败的样子画，等待中的按下按普通一行画。两种行都不是空的，折叠规则都不碰。

### 一次按下答的是什么

答的是投递到哪，不是声明的档位。`deliverAction` 报的是通知落在哪里——什么都没送、为它开了一轮、因为智能体此刻开不了轮次而进了收件箱、或者因为这个手势本来要的就是收件箱——四种里只有一种会带一句话回来，就是第三种：用户回答了智能体停下来等的那个问题，而在他们下次开口之前什么都不会发生。屏幕告诉用户「对话已经拿到你的答案了」，而对话其实正等着他们，这就是屏幕亲口让人白等。

第四种一句话都不带，这正是它必须和第三种分开的理由。勾一行是用户在干活而不是在问，没有人在等它的回答；每勾一行回一句，就是用户每碰一行、对话里就多一行——夹在智能体的回复中间，而人打开对话本来是为了读那些回复。不带文案的成功结算正是聊天行什么都不画的那一种，所以勾过的表格不会在对话里留下任何东西。

### 按下态

从日志里折出来，任何一块都不自己记。用户一挑别的条目，内容栏就把这个种类的 DOM 丢掉，于是一块自己记着按下标记的界面再回来时干干净净，同一个决定会被上报两次；因此座位读的是本行随命令一起注册的 `componentActions` 投影。它折的是一次按下本来就写下的那两条记录——`command/run` 按 `(entryId, nodeId)` 开一格，与之按 `commandId` 配对的 `command/done` 把它结算成 `sent`、`queued` 或 `refused`——浏览器就在内容栏读自己条目流的那个地方读这份值。每一块拿到自己那一格，作为 [`component-kit`](../component-kit/README.zh.md) 的 `state` prop；`refused` 仍然可按，因为再上报一次是唯一还能做的事。

只有 `wake` 会进到格子里。一块界面的状态说的是它被摆出来要等的那个答案，而一块界面上报的所有手势共用一格：所以勾选如果占了这一格，表格就会把一次勾选当成答案上报，随后把它下面那颗行按钮拒掉；筛选条则会在用户第一次改完一处（选完属性、选完策略、或者离开值输入框）时就把自己的查询按钮禁掉。`context` 与 `silent` 的手势照样上报，但把这一块留在原样——折叠不给它写格子，座位也不在页面那张等待表里给它记一行，因为根本没有结算会来。

一次手势只算给此刻在显示的那次调用：格里的 `seq` 是这次按下的日志位置，条目的 `seq` 是摆放它那次调用的位置，所以同一个 id 下后来的调用从未作答开始。

日志唯一盖不住的是这趟往返，而它由整个页面兜着，不由那一块自己兜。浏览器那半边维护一张表，记着还没有记录的那些按下，键是会话、条目、摆放它的那次调用和块——座位给每一块的 React 身份就是这四段，因为切换会话时内容栏是把座位重画而不是卸载，两个会话里落在同一个日志位置的调用否则会共用同一个挂载着的块连同它的等待：按下离开时这一块写下自己那一行，之后每次被重画都把它读回来，于是在这段窗口里做一次标签页往返，回来看到的仍是一条说着「正在发送」的条，而不是一条可以再答一次的条。一块等的是比它当前看得见的那次更晚被记下的手势，在此之前读作 `sending`。

只有两件事会清掉一行。一是记录到了。二是这次派发回话说不会有记录了——文档超量、调用被拒、网关不在——这也正是派发要有返回值的原因：没跑起来的命令不会留下任何结算可等，于是这一块说这个动作没能记下来，并接受下一次按下，而不是钉在 `sending` 上、所有按钮全死。第二件事给出的是页面按自己所见做出的判断，它按这次按下所锚定的日志位置存着：宿主在传输断掉之前已经写下的记录，照样像任何别的结算那样把这一块结算掉。

### 三档

每个动作自己声明它发生了意味着什么，投递方式由此决定：

| 档 | 手势 | 会发生什么 |
|---|---|---|
| `silent` | 给表格排序、提交前改筛选条件 | 智能体什么都收不到 |
| `context` | 勾选一行、点开一行 | 在智能体的收件箱里等，下一步被读到；同一个手势再来一次会把它替换掉 |
| `wake` | 按下确认、提交、删除 | 当场开一轮 |

档同时决定这次手势算不算这一块自己的答案：`wake` 算，另外两档不算——见上面的按下态。

`press`、表格的 `operation`、筛选条的 `submit` 是 `wake`：智能体把一个决定摆到用户面前然后停住了，而没人认领的答案它永远听不见。落在正忙着的智能体身上的 `wake` 改为暂存，和 `context` 一样——正在跑的这一轮读自己的收件箱，不需要另开一个轮次边界。

勾选行和点开一行是 `context`：它们改变智能体下一步该想的事，但不回答任何它停下来等的问题。全部取消勾选也照样上报，而不是当成「什么都没发生」略过——什么都不告诉智能体，它会一直以为上次听说的那些行还勾着。点开一行只有在调用要求「行可点开」的表格上才会上报，而且是点行里任何一格都算：组件的名称链接由 `isNameClick` 决定画不画，而它对任何一格的点击都只发同一个事件，所以一张没有什么可点开的表格，点它的格子什么都不上报。

同一个手势再发生一次，会把上一次那条还没被认领的通知替换掉。用户勾中了哪些行是一个事实，不是一部勾选史；收件箱自己没有上限；用户在表格上干活，否则每勾一次就排一条通知，而每一条都会被下一条改写。键是条目、块、动作三者合起来——点开一行不会盖掉一次勾选——替换用的是 `Inbox.replace`，它把上一条作废、把新的一条放回它的位置，所以智能体日志的记账把它算作仍在等待的工作，而不是被丢掉没跑的工作。智能体已经认领的通知永远不改写：模型已经读过它了，晚来的手势排在它后面。`wake` 也永远不被替换，因为两个问题的两个回答就是两个回答。

给表格排序、以及提交前改筛选条件是 `silent`：行按什么顺序画是用户在整理自己的屏幕，没提交的筛选条件是用户还在敲。

### 唤醒预算

每个智能体三轮。否则用户在按钮上连点就会变成一条没有尽头的轮次链；过了第三次，按下就按 `context` 暂存，直到智能体认领到一条来自人的消息，预算才整份回补。本行自己排进去的通知永远不回补它。

### 审批闸在哪

不在这里。本行不提供任何写工具，也不为自己申请审批——命令 handler 可能在没有开着的轮次时运行，而那时申请审批会直接抛错。闸是部署自己的 `tools/pre-execute` 策略，管的是在一次按下所开的那一轮里模型伸手去拿的那个写工具；组合测试钉住的正是这一点：被策略问过的既有写工具不会跑起来。

## 信任边界

`spec` 是模型的输出，会在外壳自己的同源上下文里变成一块被渲染的界面。它是被限住的，不是被信任的，第一道限住它的是属性 schema：那个联合类型里根本没有哪一种成员能表达富文本或函数体，所以模型伸手去写 `formatter` 或 `onClick` 时，拦住它的是根本没有那个属性可写，而不是某个消毒器认出了一段函数体。组件没声明的属性是被直接拒绝而不是被丢掉，所以模型写了就会知道自己写了，而且拒绝里点着名。

第二道是上面那一遍收紧，管的是 schema 说不出的那部分：声明过的读法逐个值执行，读法之外的值被从这一块里丢掉而不是拒回模型——因为这一遍也跑在没有模型在等的地方，比如一条存下来的记录送去座位的路上。这一遍同时丢掉未声明的属性；走校验进来的调用永远轮不到这一手，那一支是另一次构建写下的记录才会撞上的。

浏览器座位对着从线上收到的 payload 再跑一遍同样的判定，这也是目录与校验器各自成一个模块、除了彼此谁都不 import 的原因：座位读得到它们，又不会把一份工具运行时拖进页面，两半也就不会各按一套规则判。

这一遍交出来的属性是深冻结的。渲染器可能用一个 Vue 2 组件来画一块内容，而 Vue 把组件收到的 props 逐个属性改写成响应式的——这会让座位自己那份 memo 和 Vue 树对「什么变了」各执一词。Vue 会绕过冻结的值，所以在交出去的那一步冻上就把这件事了结了，对 React 渲染器同样成立：借给渲染器的东西，它可以读，不可以写。

## 座位

浏览器半边只有一次带键注册：内容栏开放键域 `content.surface.kind` 上的 `component` 键。座位把条目标题画在上面，下面按调用写下的顺序竖着摞出各块；当内容栏被别的种类占着时，条目根本不会交到它手上，它也就什么都不画。`visibility` 留在页面上的是内容栏为这个种类准备的外壳，不是那些块——块的 DOM 随这一次不画一起消失。

画之前，座位会把这次调用自己的那套判定重新对着 payload 跑一遍。这不是对同仓宿主的不信任：一条条目的 payload 可能来自另一份组合写下的持久化检查点，那份组合的目录和上限不是本次构建的，所以它带着的类型只是一种主张。这次复校用的就是工具判定调用时用的那个零 import 模块——那个模块之所以零 import，正是为了这个。本次构建不接受的 payload，在内容栏里变成一句话而不是几块内容。

每一块都按自己的身份做记忆化——它所属的条目、该条目当前的序号、这个节点、以及折叠里记在它名下的那次手势——所以栈里别处的重画不会动到它已经拿到的那份 props。渲染器按节点写下的目录 id 从组件行的表里取；表里没有这一项时，就在那块的位置上把这件事说出来——组合里装了不匹配的组件行时，用户看到的就是它。

座位自己不带词典。它通过组件行的命名空间 `componentKit` 取文案，因为「这一块画不出来」这句话属于组件，而不属于把它们摆进来的那个包。

## Model Experience

### `show_component` 的提供

#### What the model sees

一个工具 `show_component`，必填 `id` 字符串、必填 `title` 字符串、必填 `spec` 对象，`spec.nodes` 数组必填。描述里带着完整目录，一个组件两行：先是 `- id — label — purpose`——不上报动作的组件，那一行末尾多一句 `Nothing comes back from it.`——下面再跟一行 `props:`，点名这个组件声明的每一个属性：可以不送的打 `?`，数字带 `(min–max)`，固定取值集合带 `(a|b|c)`，是非项带 `(true|false)`，列表写成 `[一个条目是什么] (min–max)`，由已声明属性组成的对象写成 `{…}`，键名由模型自己定的对象写成 `{<field>: text|number|boolean}`。再往下是 `id` 的复用规则、节点数与字节上限、未声明属性一律拒绝这条规则，以及那句说明回程的话：用户在一块界面里做了什么会到模型这里，并带上发生在哪条条目、哪一块，除非那个组件的行上已经说了不会。目录行里的组件名就是终端用户看到的中文名，所以模型在对话里提起某一块时，提的就是用户看到的那个叫法。本包不贡献任何系统提示词分节。

#### Token effect

一份固定描述加参数 schema，出现在每一次这个工具可见的请求里。描述每多一个目录条目就多两行，第二行的长短取决于那个组件整棵属性树——表格那一行最长，因为它的列是对象里的一个列表；`spec` 的 schema 保持浅——一个对象一个数组——因为每个组件各自的属性写在目录行里，而不是写成嵌套 JSON Schema。

#### KV Cache effect

描述在行加载时组装一次，只取决于目录，因此在一个部署内每次请求里工具块逐字节相同，前缀成立。

### 工具调用结果

#### What the model sees

被接受的调用回一句 `Now showing "<title>" in the content panel: <labels>.`，后面跟着点名要复用哪个 id 的那句话。被拒绝的调用回 `Error: show_component: <路径> — <哪里不对、该改成什么>`；点名了不存在的组件时，再附上完整目录，属性行也在里面，于是改过的那次调用不必再挨一次拒绝才知道换的这个组件收什么。

#### Token effect

每次调用一行短句。点名未知组件的那条拒绝会长出一份目录，而这正是它的用处：它顶掉了第二次失败调用。

#### KV Cache effect

只追加；结果跟在可复用的请求前缀之后，不让任何已缓存的内容失效。

## Known Limitations and Deferred Work

- **payload 白名单是界面那半边的承诺，不是宿主在执行的东西** — 命令注册表在任何 handler 跑起来之前就把命令输入逐字记下了，所以一份超量的动作文档在本行拒绝它的时候早已进了日志。宿主仍在执行的是字节上限和已声明属性：超过上限、或带了该动作没声明的属性，这个动作就完全不会投递给智能体。只送该动作声明过的东西是座位的义务，而两个半边都在本包里。
- **折叠行写的是机制而不是那块界面** — 一条通知在对话里是一行折叠行，表头写着「上下文注入 · content-component」（英文界面是 `Context injection · content-component`），一个术语加一个插件 id 摆在终端用户面前；旁边那句一行摘要是个可伸缩的格子，控制台三栏布局的聊天列宽度会把它挤到零宽。展开也好不到哪去：露出来的是给模型看的那句英文，连同句子里的内部标识符——`The user pressed "Approve" in content panel entry "budget" ("Budget approval"), on the 确认条 block "ask".`——写给智能体的那份说法，直接摆给做出这个动作的人看。行与展开的正文都由 [`ui-conversation`](../../client/ui-conversation/README.zh.md) 对所有产出方一视同仁地画；这一整条的复查触发器是 `develop` 线上那个「按产出方给显示名」的改动，按产出方定制的展开态文案也归在那里。
- **这条命令会出现在终端用户的斜杠菜单里** — `commands.register` 没有任何办法把一行挡在输入框提供的那张菜单之外，于是 `/component-action` 就列在那儿，旁边还跟着 `<json>` 提示，而那张菜单里别的每一行都是给人打的。这一行能做的只是把话说清楚：描述写成终端用户读的中文，点明是内容面板里的按钮、由页面自己发出。真在那里手打一行，它谁也对不上，答的是与丢掉的按下同一句拒绝；而只要这行的格式足以点出一条条目和一个块，它还会把那一块重画成这句拒绝——手势折叠读的是一行里带的标识符，只有 handler 才拿它们去对当前在显示的条目。把它从菜单里去掉是 `dsh-commands` 的改动——描述符上加一个 `listed` 字段——等第二个需要它的行出现时一起做。
- **唤醒预算只在内存里** — 已花掉的唤醒记在一张以智能体对象为键的表里，所以重启之后每个智能体都重新拿到整份预算，恢复出来的会话也无从知道它的那些按下已经开过几轮。那张记着还没被认领的 `context` 通知的表也是同样的键、同样地忘掉：重启之后一块界面的第一次勾选，会在日志里那条通知旁边再排一条，代价是模型多读一句已经被改写的话，仅此而已。
- **一次什么都没填的按下，看上去就是按钮没反应** — 筛选条一开始就带着一个空条件行，所以用户能做的第一次按下提交的是零个条件；那次按下什么都不上报，块上也不画任何一行，因为画一行就等于说发生了什么。用户拿到的是一个按下去屏幕毫无变化的按钮。把按钮置灰是正解，而它不是本地的：那一块得知道编辑器里有几条完整的条件，那正是 `change` 手势自己带的计数，而拿一个每次改完一处就送来的计数去驱动按钮的状态，需要两个包对「按钮什么时候可以动」达成一致。触发条件是第一次有人反馈「点了没反应」。
- **一块界面说不出手势为什么被拒** — 折叠把被拒的手势结算成同一种状态，所以不管是指向了屏幕上不存在的东西，还是带的东西超过了动作能收的量，块上画的都是 这个动作没能记下来，可以再试，而旁边聊天行画的是 handler 自己那句 内容太多了，少选几项或写短一些再试。。两句话就同一次按下在用户面前互相矛盾。要在块上把它们分开，得给 `ComponentActionState` 加一个成员，那是本包的折叠与 [`component-kit`](../component-kit/README.zh.md) 的状态表和词典之间的契约；触发条件是第一个聊天行不在块旁边的部署。
- **手势折叠按块而不按动作** — 按 `(entryId, nodeId)` 一格。今天够用只是因为一个组件至多声明一个 `wake`，而别的档根本不进格子：等哪个组件声明第二个 `wake` 的那天，那一块画出来的就是这两个里最后上报的那个的状态。解法是把格子的键按 `actionId` 长一位，改在 [`src/action-state.ts`](src/action-state.ts) 和它旁边的投影里，这笔账由第二个 `wake` 来付。
- **日志开了却没合上的那次按下会一直读作「正在发送」** — `command/run` 与 `command/done` 分别写在 handler 前后，宿主在两者之间停下就会留下一个没合上的格子，而之后没有任何东西会去合上它。那一块要等后来的调用替换掉这条条目才恢复可按。压根没产生任何记录的那次按下是另一回事，它会自己了结：派发如实回话，页面把那一行丢掉，这一块恢复可答。
- **三句结算文案在任何界面里都是中文** — `这个动作没能记下来。`、`内容太多了，少选几项或写短一些再试。` 与 `已记下，你下次发消息时对话会看到。` 由 handler 写下，而 handler 拿不到浏览器的语言：命令结果就是一个字符串，会话日志又必须留下用户当时真正看到的那些字。于是在非中文控制台里，它们画在聊天行里，紧挨着一条条上文案——那些文案来自 [`component-kit`](../component-kit/README.zh.md) 的字典，是已经本地化的。真正的解法要么是改成由客户端翻译的 key，要么是让命令结果带上语言，触发器是控制台开始提供中文以外的界面。
- **回程通道没有装配转录覆盖** — `content-console` 泳道驱动的是 ACP 智能体，而 ACP 协议没有命令方法，任何录下来的转录都载不动一次按下。那条泳道照样组合了命令注册表，因为它钉住的那段描述告诉模型按下会回来；按下这件事由针对真实控制台组合的 Playwright 场景覆盖，那里的浏览器、RPC 网关、命令注册表和会话日志都是发行的那一套。
- **模型看不见内容栏里现在有什么** — 没有读取路径。智能体只知道自己发过哪些调用，不知道用户正在看哪一条、有没有谁被关掉、任何一块此刻显示着什么。
- **没有布局，块与块之间也没有联动** — 一份 spec 就是自上而下的一列节点。没有行列树、没有宽度，也没有办法让一块的状态去驱动另一块的属性。
- **空值就按空值画** — `toy.record` 里 `display` 为空串的那一行保留名称，旁边什么也不显示。这是有意的：另一种读法是把整行丢掉，那会让用户根本看不出这条记录有这个属性。模型若想表达「这项没设置」，就把这几个字写出来。
- **目录里有五项** — 把一个真实组件库的其余部分映射成目录条目，以及把那些组件打进浏览器产物的打包链路，都是另一片工作。
- **还没有组件声明 `path`** — 这条读法已经执行、也有测试，第一个要指向某个静态资源的组件才是把它放到真实屏幕上的那一刻。渲染器名和颜色两条已经有人声明了：数据表和指标球。
- **有一种匹配策略没人算得了** — 一次调用能收窄到的那十六种，就是条件编辑器画出来的那十六种：用户挑得到、而本包叫不出名字的策略，意味着人辛辛苦苦编好的筛选被告知没能记下来。`NOT_BETWEEN` 是组件库自己的 `matchUtil` 没有分支的那一个，所以带着它的条件是作为「用户要的是什么」的陈述抵达模型的，被要求去跑它的后端自己回答自己。本包不评估任何条件。
- **调用不点名就没有 AND／OR** — `confStyle.showMatchMode` 默认关着，块打开它才画：这个控件只有在答案会把它带回去的时候才值得画出来。画了它的那张条会把模式连同条件一起提交，通知里也会说出用户选的是哪一种。
- **五百行的表很少放得下** — 行数上限是表格的，而 `spec` 卡在 65536 字节，几百行几列的表先撞到的是后者。拒绝语句会说出这件事，并点名字节数。动作上限从另一头同样咬人：一次提交十条、每条二百字的筛选，超过 4096 字节，答的是那句内容太多的话。把一张满行的表整个勾上不在此列——勾选上限**就是**行数上限，字节上限也留够了装下它。
- **条件编辑器自己没有上限** — 一张筛选条一次最多提交十条条件，而按下它自带的增加按钮，那个 vendored 编辑器就一直加行。于是第十一条会被建起来，屏幕上没有任何东西说它送不出去，送它的那一次按下答的是那句说内容太多的话。那一块自己只说这个动作没能记下来，因为它折出来的结算不带原因；原因在旁边的聊天行里。要把编辑器拦住，上限得在缝的渲染器那一侧，而本包给不了它——[`component-kit`](../component-kit/README.zh.md) 是给任何摆放它的人画块的，不能反过来 import 一个落位包。
- **值控件的形态取决于本 schema 不带的一个字段** — 属性的 `dataType` 只有在这条属性同时声明「值是手填而不是从服务里挑」时，条件编辑器才会去读。本包声明 `dataType` 而不声明那个字段，所以补上它是渲染器的事；不补的渲染器，无论 `dataType` 写什么，每条条件都画成纯文本输入框。
- **块里自己填的东西一旦不被选中就不会留下** — 座位只画被选中的那条条目，内容栏被别的种类占着时更是什么都不画，所以无论是切换种类，还是在两条 `component` 条目之间切换，用户在当时那些块里填过的东西都会丢掉。已经上报出去的手势会留下，因为它在日志里而不在这一块里。
- **本次构建不能完整接受的条目会整条画不出来** — 座位是对整份 payload 重新判定的，所以只要有一个节点写的组件本目录已经不带了，这条条目连本来能画的那些块也一起没了。
- **上限是协议常量，不是配置** — 原因与「要先有什么才能把它们变成部署的选择」，上面的配置一节已经写了。
- **一条条目带着自己整份 spec** — 内容栏的投影按存活条目保存已校验的 spec，因此它随线上值与持久化检查点一起走。字节上限就是限住它的东西。
- **不变式只经调度路径上报** — `Session.append` 把抛错的监听器记进日志后继续跑，所以实时审计只有在提交事件经由 context 调度时才能到达调用方；启动时对已加载会话的那一遍不受影响。
- **画出来的那一块没有组装快照覆盖** — 这把工具模型可见的全部内容（含拼进工具描述的目录与结果文本）由 [`examples/content-console`](../../../examples/content-console/README.zh.md) 泳道钉住，那条泳道真实组合了这一行并跑通一次完整调用。座位随后把它画成什么样，则是针对真实控制台组合的 Playwright 场景。
