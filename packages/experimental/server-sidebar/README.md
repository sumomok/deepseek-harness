# @deepseek-ai/dsh-experimental-server-sidebar

English | [中文](README.zh.md)

## Summary

A fixed-width product-console sidebar: a drop-in replacement for the shipped [`dsh-client-ui-sidebar`](../../client/ui-sidebar/README.md) that removes session/workspace browsing entirely and replaces it with four sections — 工作台 (workbench, one persistent default conversation), 导航 (navigation, the pages and views the deployment configured), 我的工作流 (my workflows, a user's own named shortcuts back to conversations they taught the agent something in, filed under groups they name themselves), and 临时工作流 (everything none of those rows already shows). It replaces ui-sidebar in a composition rather than sitting beside it, because `sidebar` is a single slot and its child slots may be declared only once.

<a id="replacing-the-shipped-sidebar"></a>
## Replacing the shipped sidebar

This package targets a "customer form" composition: an end customer using the product never needs to know a conversation is a durable, resumable object with a Workspace behind it. Every session/workspace management step (creating one, reconnecting one, choosing which one is "current") happens inside this package's own actions; the vocabulary itself — 会话/session, 工作区/workspace — is banned from every string this package's own dictionaries carry, and the composition disables the shipped controls that would otherwise leak it (see De-terminology below).

- **Four child slots survive** — `sidebar.brand.mark`, `sidebar.brand.name`, `sidebar.settings`, and `sidebar.footer.action` keep the kinds and scopes `dsh-client-ui-sidebar` declared, reused by type import rather than restated, so ui-settings's existing registration keeps working unchanged (a brand package filling either identity slot is disabled in the customer composition instead — see Brand and hero facade below). `sidebar.workspaces` is dropped outright: this shell has no session-browsing region for it to seat in. `ui-workspace`'s `sidebar.workspaces` registration goes through `ctx.slots.inject`, which is declaration-gated (it waits for a declaration and simply never fires without one — `SlotRegistry.inject`'s own contract) rather than a hard requirement, so `ui-workspace` composes with that half of it permanently inert. It is composed, not disabled: `dsh-client-ui-conversation` requires its `uiWorkspace` service, so disabling it would leave the whole conversation column and every sibling that depends on it unactivated. Its other registration — `conversation.hero.workspace`, a slot `dsh-client-ui-conversation` always declares — therefore does land, and the hero row carrying it is hidden by `terminology-guard.ts` instead (see Brand and hero facade below).
- **The New Session button is gone.** There is no "start an ad-hoc conversation" affordance in this shell; every entry point (工作台, a 导航 page, a 我的工作流 row) resolves or creates its own session internally.
- **The 56px collapse rail is gone.** This shell never calls a collapse action and always renders its full content regardless of the `collapsed` owner prop — see the Known Limitations entry on the residual coupling this leaves with the surrounding shell's own track geometry.
- **The pointer-driven scrollbar behavior is unchanged** — the column's scrollbars draw while the pointer is inside it and for two seconds after it leaves, canceling a pending hide if the pointer returns, tracked geometrically rather than by DOM containment (so a portalled overlay that is a DOM descendant of the column, as ui-settings renders its panel, does not read as "the pointer left").

<a id="workbench"></a>
## Workbench

工作台 is the one persistent default conversation this shell lands on — but landing on it means something different depending on how you got there.

- **Loading** the sidebar with no session currently selected (`openWorkbenchOnLoad`) resolves the recorded `workbenchSessionId` and reopens it whenever it is still live, whatever content it already carries — continuity semantics: the page resumes exactly where it left off.
- **Clicking** it (`openWorkbenchOnClick`) always lands on a clean page instead — clean-draft semantics: it reopens the recorded session only when it is live and still *clean*, which is two conditions together (`isCleanWorkbenchDraft`): it has run no turn (`SessionSummary.blank`), and its content column carries nothing beyond the deployment's own configured automatic home. None recorded, a recorded one that is gone, one that has run a turn, and one whose content column shows anything else all take the create path instead: a session against the recent Workspace, with `workbenchSessionId` repointed at it. That path resolves through `connectWorkspace`, whose reuse scan hands back the first blank session the Workspace holds in the session list's own order — normally this same draft, and any other blank session of that Workspace when one comes first, with `workbenchSessionId` repointed at whichever it was (see Known Limitations); what the visitor gets there is the configured automatic home shown again, not a new conversation.

**`SessionSummary.blank` alone cannot answer a click.** That bit tracks conversation turns and nothing else — standalone events never lower it (see `sessionBlank` in `dsh-host-apiproxy`) — so a draft the visitor has already navigated somewhere in still reads as blank: one 导航 click, and the content column is showing a published report on a session the next workbench click would happily reuse, landing on that report instead of on a clean page. What the session already shows is therefore the second half of the judgment, read off the session list's own `projectionValues.contentSurface.entries` — the same feed, and the same defensive untyped read, `dsh-experimental-server-layout`'s `ShellFrame` uses for the content column's own empty check. The configured automatic home is the one entry that does not disqualify a draft, because the click path itself is what put it there (see below); counting it as content would leave every clean click unable to reuse the draft its own previous click had just populated.

Both share one open-or-create mechanism (`client/workflow-actions.ts`'s private `openOrCreateWorkbench`) and differ only in what qualifies the recorded session for reuse. `workbenchSessionId` is a weak reference for exactly the same reason a workflow's `homeSessionId` is (see below): nothing here owns session deletion, and a stale pointer degrades to a fresh conversation rather than corrupting the document that names it.

The load path's mount-time auto-open withholds its one-shot attempt rather than spending it against an unready Workspace baseline: reopening a live recorded session needs no Workspace at all, but creating one does, and `recentWorkspaceId` cannot distinguish "the Workspace baseline has not loaded yet" from "this deployment genuinely has none" — so the effect waits for either a live recorded session or a resolved Workspace before it tries, and gives up permanently the moment a session becomes current by any other means.

**A configured automatic home auto-shows on a clean click, never on the load path.** When the deployment configures one (content-frame's `homePage` or component-surface's `homeView` — see Navigation below), `onOpenWorkbench` runs that target's own command against the session `openWorkbenchOnClick` just resolved — the freshly created session on a create outcome, or the reused one on a reused-clean outcome — the instant after that resolution settles, so a new or clean-draft conversation opens onto a populated column instead of an empty one. A reused draft that already shows it skips the call (`hasShownHome`): that target is the only content a clean draft may carry, and repeating the command would append a second record for what is already on display. This runs only from the click handler: the load path's own continuity semantics (resume exactly where a live session left off) would be broken by forcing content onto a session that already carries something else, so `openWorkbenchOnLoad` never calls it. The auto-open command is an ordinary menu invocation — it appends the same session event and leaves the same durable log record a user's own click would.

<a id="navigation"></a>
## Navigation

导航 lists everything the deployment configured as one click away from the content column, merged from two catalogs (`client/nav-catalog.ts`): [`content-frame`](../content-frame/README.md)'s pages, read from `/content-frame/settings`, and [`component-surface`](../component-surface/README.md)'s composed views, read from `/component-surface/views`. Both reads happen once before this entry registers, over hardcoded route paths and locally validated JSON shapes rather than imported values or types — a cross-package value import is not this repository's sanctioned way to couple two client-adjacent plugins, and this package's own tests import each owning constant so the copies stay mechanically checkable. Every row carries which catalog it came from, because the two are opened by different commands and land as different content-surface entry kinds. Each row's button states both as attributes: `data-server-sidebar-nav-kind` (`page` or `view`) and `data-server-sidebar-nav-entry` (that catalog's own entry id). A page and a view may share an id, so only the pair names one row.

**Menu order is pages, then views, each in its own declaration order.** Navigation order follows deployment configuration and is never user-reordered (decision ⑤); a fixed source order keeps that true across the pair without a third configuration field to keep in step.

Clicking a row runs that row's own command against the current session (creating one first when none is open, through the same resolution the workbench and every workflow action share — see `client/session-resolution.ts`), through `ctx.remote.commands.execute` — the same command seam a session log can replay, not a direct service call. A page runs content-frame's `show-content-page`, whose handler appends `content/shown` with `by: 'user'`; a view runs component-surface's `show-content-view`, whose handler appends `content-component/shown` with `by: 'user'`.

**A row the deployment has since dropped answers differently by kind.** The navigation menu is built once at load, so a page or view removed from configuration after that is still a row until the next reload, and a workflow replay can name a stop the deployment no longer configures. A dead view row draws component-surface's own sentence, 没有这个视图。, in the chat where its command row sits; a dead page row draws nothing at all, because content-frame's command row is hidden unconditionally and its refusal is developer-register English no end user should read. Aligning the two is content-frame's change, not this package's; until then a page that vanishes vanishes silently.

**A composition with only one of the two packages is ordinary, not an error.** Each read is contained: an unreachable route, a non-200 answer, or an unusable document contributes no rows instead of taking the whole sidebar down, so a deployment that composes only content-frame gets a pages-only menu and one that composes neither gets the empty copy.

Each catalog also carries its own optional automatic home — content-frame's `homePage`, component-surface's `homeView` — read alongside its rows and consumed by the workbench's click handler above. A value naming nothing that same response configures is contained rather than thrown: unlike the node-side `Config` validation, which fails the whole load, this browser-side read reports it with `console.warn` and treats the field as absent, because a load-bearing shell surface should not go down over one misconfigured field on an otherwise-working deployment. **Configuring both is the one exception and fails at load**: the content column shows one thing at a time, so a deployment that named two has expressed an intent this shell cannot carry out, and honoring whichever route answered first would leave the other configured value doing nothing with nothing to say why.

<a id="my-workflows"></a>
## My Workflows

我的工作流 is a user's own named shortcuts, persisted per account: per `$DSH_HOME` in a deployment that runs one process per signed-in user, and per console member with `perMember` (see the end of this section). One workflow binds exactly one conversation (v1 boundary; see Known Limitations): `{id, name, order, homeSessionId, navSnapshot, savedAt, groupId?}`.

- **Save** — the "存为工作流" (Save as workflow) action lives in the conversation's own session header (`conversation.session.header.actions`, order 30, after the subagent catalog and background jobs), not a sidebar "+" button: a regular seat for a session-scoped, occasional action already existed, and adding a second interaction pattern for the same kind of action was not justified. It is visible only once the current conversation carries at least one user-authored message (decision ③, checked via `chat.legacy.nodes` — see Known Limitations for the v1 approximation this implies), matching the intuition that a workflow is a shortcut back to a conversation the user actually started, not an empty one. Saving captures the current session id as `homeSessionId` and, as `navSnapshot`, the content column's currently-shown stops that the 导航 menu itself lists, oldest first — anything else the column carries is left out (see Known Limitations).
- **Open** — clicking a workflow reopens `homeSessionId` directly when it is still live. **Restoring only fills in what is missing** (decision ⑦): reopening a live session never touches its content, since there is nothing missing to fill.
- **Degrade** (decision ⑧) — when `homeSessionId` is gone, opening the workflow creates a fresh session against the recent Workspace, replays `navSnapshot` onto it in order (oldest first, so the last one replayed ends up on display, matching what was on display when the workflow was saved), and repoints `homeSessionId` at the new session. A fresh session starts empty, so "fill in what is missing" is trivially the whole snapshot.
- **Rename / remove** — hover-revealed icon buttons (the former favorites menu's own idiom), not a native right-click context menu; see Known Limitations.
- **Reorder** — native HTML5 drag-and-drop: every row is `draggable`, and dragging one over another row's top or bottom half previews an insertion line there (CSS-only); dropping commits through `reorderWithinGroup()` (`client/workflow-actions.ts`), which states the destination lane's complete next sequence and rewrites each named row's `order` field to its position in it (0..n-1) — a full rewrite, not a pairwise swap, so a drop anywhere always produces a clean, contiguous order regardless of what the previous values were. The same call re-files a row dragged in from another lane, so a within-lane reorder and a cross-lane move are one mechanism. This follows user drag order (decision ⑤).
- **Unread indicator** (decision ④) — a workflow whose `homeSessionId` has unseen output draws a green dot, reusing the session status feed's own `completionUnread` bit ("stopped outside the main view and not yet opened") verbatim rather than a second last-seen bookkeeping mechanism the original brief suggested as a fallback: that bit already means exactly this, and it clears once the session is on the main view — see Known Limitations for why this is unit-tested only, not covered end to end.
- **Displaced sessions are not deleted.** A workbench click that lands on a fresh session (see Workbench above) does not delete the session it displaces: a workflow that already binds it keeps managing it through its own `homeSessionId` unaffected, and one bound by nothing simply stops being pointed at by anything. This composition has no session concept for a user to see or clean up (decision ②), so an unbound displaced session just recedes rather than requiring disposal.

### The navigation snapshot's stored form

`navSnapshot` is a list of `{kind, entryId}` pairs — `kind` is `page` or `view`, and `entryId` is that catalog's own id — because the two kinds are replayed through different commands and land as different content-surface entry kinds, so an id alone no longer says what to do with it. Only entries the 导航 menu lists are captured, since a stop is replayed by re-running its own command and both commands refuse an id the deployment does not configure (see Known Limitations).

**A document still storing the pre-view `string[]` form is refused at load, not reinterpreted.** Every stored id meant a page, so reading one as such would be exact — but a document the process silently reinterprets is one nothing ever converts, and this repository's pre-release stance rejects old on-disk formats outright. The refusal names the offending entry and the one-time converter that fixes it:

```sh
pnpm --filter @deepseek-ai/dsh-experimental-server-sidebar run convert-nav-snapshot ~/.dsh/settings.yaml --dry-run
pnpm --filter @deepseek-ai/dsh-experimental-server-sidebar run convert-nav-snapshot ~/.dsh/settings.yaml
```

The path is required rather than defaulted (a converter that guesses which document it is rewriting is one that can rewrite the wrong one). Run it on `$DSH_HOME/settings.yaml` before the first start of a build whose settings service imports that file (see Workflows below): the import then carries the converted section into this row's entry. A section the import already refused stays in `settings.yaml.imported`; converting that file and renaming it back to `settings.yaml` makes the next start import it again, together with every other section it holds. It rewrites each stored id to `{kind: 'page', entryId: id}`, writes the empty `groups` list the current format carries when the document has none, leaves an already-current document byte-identical, and writes nothing at all under `--dry-run`. The YAML path edits through `yaml`'s document model rather than a parse/serialize round trip, so an operator's own comments and key order survive.

### Groups

The durable format carries `groups` — `{id, name, pinned, order}` per group — and an optional `groupId` on each workflow naming the group it is filed under; a workflow naming none is ungrouped. `TEMPORARY_GROUP_ID` (`"temporary"`, deliberately not a UUID) is reserved for the conversations a user never named, and nothing durable carries it: that section derives its rows from the live session list and takes its title from the locale dictionary, so the id's one live use is as that section's key in the browser-local fold map, which is not a document. `validateServerMenu` refuses a duplicate group id, a blank or over-40-character group name, a stored group claiming the reserved id, and a `groupId` — the reserved one included — naming a group nothing defines.

The section draws pinned groups first, then the rest by `order`, then every ungrouped workflow at its own top level. That order is derived on each render, never stored as a list.

- **Create / rename** — an in-place input, the idiom "存为工作流" already established for naming a workflow, revealed from a hover icon button. A blank name abandons the edit; the field itself stops at the 40 characters the document refuses beyond, rather than letting a write travel to the route to be told.
- **Pin** — groups only. Pinning sorts a group ahead of every unpinned one without touching its `order`, so unpinning puts it back where it was. Pinning individual workflows is deliberately absent: it would contradict the manual drag order inside a group.
- **Delete** — the shortened group list and its members' cleared `groupId` travel in **one** patch. A document naming a group nothing defines is refused, so a patch carrying only the shortened group list would be rejected; the members land back at the top level.
- **Move** — drag a row onto another group's rows, onto its header, or onto the placeholder an empty group draws; the top level has no header, so it draws a placeholder of its own while a drag is in flight (only then — an empty top level is the ordinary state of a console whose workflows are all filed). Or use the row's 移动到… menu, which lists every lane but the one the row already sits in; a console with no group at all has a single lane and nowhere to send a row, and the control is left out rather than drawn over an empty list. That menu is not a convenience: HTML5 drag-and-drop has no touch equivalent, and the menu is the only path touch has. Every row and group-header control is revealed by a hover **or** by the focus being inside that row or header, so the always-drawn control each one starts with — a row's name button, a header's fold caret — brings the rest up and Tab walks them; a device with no hover at all matches neither condition, so on a coarse pointer they are drawn from the start instead. Tab stops at the 移动到… trigger: the list it opens is not keyboard-reachable (see Known Limitations).
- **Fold** — which groups are folded shut (the temporary section included) is a display preference remembered per browser under `dsh.server-sidebar.view.v1`, never in the deployment's own document. Reading and writing it are each contained: a browser that refuses site storage outright — where touching the global itself throws — falls back to everything expanded and keeps the click that asked. The map is pruned against the authoritative group list on every read of the document, so deleting a group does not leave its fold entry behind for the life of the browser profile.

A workflow whose `groupId` names no stored group is drawn at the top level rather than disappearing. The document's own constraint refuses such a reference, so it can only arise from a document edited outside the interface — and every workflow has to be reachable from somewhere.

### Temporary workflows

临时工作流 is every conversation this process can see that no other row in this shell already shows — the filter runs over the host's whole conversation directory with no identity predicate in it, and what makes that the same thing as "this person's own" is the deployment shape this console is built for: one visitor per process, per `$DSH_HOME` (see Known Limitations). It is derived on each render with nothing durable behind it; five predicates decide membership — not a subagent child, not archived, not the workbench's own conversation, not any workflow's `homeSessionId`, and not a blank draft unless it is the one on screen right now (otherwise every visit to the workbench would leave a nameless empty row behind). Rows sort by `updatedAt`, most recent first. This is where a displaced workbench draft now lands, instead of simply receding with nowhere to find it again.

- **A row shows the conversation's own durable title, or fixed copy** — never the session list's `displayTitle`, whose lower rungs are a directory basename and then a bare session id. Both are the vocabulary this console exists to keep off the screen, and a bare id is not something the banned-word check can catch.
- **Five rows, then 显示更多** — the shipped browser's own collapsed limit. Whether the rest was asked for is remembered alongside the fold state.
- **移出列表 archives, it does not delete** — it calls `ctx.workspaces.archiveSession`, and the session log survives on the host. Because a conversation taken off the list does not come back, the control asks for a second click in place before it commits — and the armed row is laid out so a second click cannot commit by accident: 确定移出 opens to the left, and the row's right edge, where the 移出列表 icon just was and where a double click's second press lands, becomes 取消. Escape disarms as well, from wherever the focus went, as does folding the section shut. Taking off the conversation that is open on screen lands the shell back on 工作台: this console always rests on a conversation, and the sidebar's own load-time landing is a one-shot that never fires a second time. A refused archive is reported inline in this section, in its own fixed copy ("移出失败，请稍后重试"), rather than as the workflow list's own save failure; the refusal's own text comes from the host runtime (`session archive failed: …`) and carries the vocabulary this console keeps off the screen, so it goes to the browser console only.
- **A saved workflow leaves this section by itself** — saving binds its `homeSessionId`, which is one of the five exclusions. No second bookkeeping mechanism.

By default the menu (`{workflows, groups, workbenchSessionId}`) is three volatile fields of this row's own Config, written through the settings service into the active profile's patch without remounting the row; the row turns off the generated settings page for them, since the sidebar is their editor. A menu an earlier release stored under the `server-sidebar` section of `settings.yaml` is imported once into the profile entry of the same id, so the row keeps that id. It is served over one same-origin route:

- `GET /server-menu/workflows` — the current document, `cache-control: no-store`.
- `POST /server-menu/workflows` — **merges** the posted patch (`{workflows?, groups?, workbenchSessionId?}`) into the current menu rather than replacing it wholesale, so a caller changing only one field never has to resend the others; each array it does carry is replaced whole. Every rule above (a duplicate workflow id, a pre-view `navSnapshot`, a group constraint) is checked against the merged menu and refused with 400 before the write; a write the settings service refuses (for example, one a higher configuration layer overrides) answers 500. The row checks the same rules at load, so a profile edited by hand into breaking one fails the row.

The browser cannot call `settings.*` RPC directly — it is a loopback-privileged method group, and a request arriving through a reverse proxy is refused with 403 by the shell's own trust fence rather than by any rule in the proxy's configuration — so this package's node half is an optional child that registers the route only when both `ctx.settings` and `ctx.webServer` are composed and the row was mounted by the Loader (the settings service writes into a profile entry); without them the sidebar itself still works (navigation is unaffected), just with nothing to show or persist under 我的工作流.

**With `perMember`, each console member's menu is kept apart.** One process then serves several members, so a menu in this row's Config would be one every member shares: one member's save would rewrite everybody's menu, and the shared `workbenchSessionId` would move between members on every load. The route keeps each member's menu in `ctx.consoleMembers.memberStore(<member>, 'server-sidebar')` instead and writes nothing through the settings service or into the profile patch, so it needs only `ctx.webServer` and no Loader entry; the row still turns off the generated settings page wherever `ctx.settings` is composed. The same two methods serve it with the same merge, and answer in this order: a method other than `GET`, `HEAD`, and `POST` is refused 405, a `POST` a browser labelled cross-site 403, and one not sent as JSON 415; then, before any body is read, 503 while no `consoleMembers` service is running and 401 when that service places the request with no member (`principalOfRequest`); a body past the bound is 413, one that is not a patch 400, and a merged menu that breaks a rule above 400. A member who has saved nothing reads the empty menu.

A save whose workflows or workbench name a conversation the directory's `principalOfSession` gives to another member is refused 400 by the path of each field that names one — `workflows[2].homeSessionId` by the workflow's index in the posted list, then `workbenchSessionId` — in its `error` text and again as the list `fields`, and the refusal names neither that member nor the conversation: otherwise a member could store another's conversation in their own menu and open it from there. A conversation the directory places with nobody, or does not know, is saved, because the menu holds weak references (see Workflows above). A saved copy that does not read as a menu answers 500 to both methods and logs one fixed line that carries neither the member nor the copy; it is never read as the empty menu, since a save merged onto that would replace whatever the member had saved. A write the store refuses answers 500 as well. One member's saves are applied one at a time, each reading what the one before it wrote, so two saves sent together both land; different members' saves do not wait on each other. A refused or failed save is reported in the 我的工作流 section in fixed copy, in either mode, and the refusal itself goes to the browser console: one refused 401 or 503 as 保存失败：请刷新页面后重试 (Failed to save: refresh the page and try again); a 400 that lists `fields` by the entries the page can name from the list it sent — each workflow by its name, the workbench as 工作台 — leaving out a path it cannot name, as 保存失败：「周报」指向别人的对话，请先把它移除再保存 (Failed to save: the chat behind “Weekly” is someone else’s; remove it, then save again) for one workflow, as 保存失败：「周报」、「日报」指向别人的对话，请先把它们移除再保存 (Failed to save: the chats behind “Weekly”, “Daily” are someone else’s; remove them, then save again) for more than one, and, where the workbench is among them, with no advice to remove anything, since the workbench is in no list, as 保存失败：「周报」、「工作台」指向别人的对话，这次修改没有保存 (Failed to save: the chats behind “Weekly”, “Workbench” are someone else’s; the change was not saved); any other 4xx, and such a 400 it can name nothing of, as 保存失败：这次修改没有被接受，请刷新页面后再改 (Failed to save: the change was not accepted; refresh the page and make it again); and a 5xx, a status below 400, a 2xx whose answer is no usable document, or a request that never reached the route as 保存失败：请稍后再试 (Failed to save: try again in a moment). A read is held to the same distinction in either mode: the browser half takes the empty menu only where nothing serves the route (404, or an answer that is no JSON object), and a read the route refuses — 401, 503, a member's copy that does not read (500) — or that never reaches it answers no document. On load the section then says 菜单没有读出来，请刷新页面后重试 (The menu could not be loaded; refresh the page and try again), and until the page is reloaded nothing saves the menu or opens, creates, or archives a conversation on its behalf: the workbench is not opened on load and its button does nothing, 我的工作流's controls and 存为工作流 save nothing, a workflow whose conversation is gone is not given a new one, a 导航 row shows nothing, since one clicked with no conversation on screen creates one first, and 移出列表 archives nothing, since an unknown menu leaves the member's workbench and workflow conversations in the 临时工作流 list. Each refused click is reported to the browser console. Once the menu has loaded, a read that fails on either path that reads the workflow list before writing it back — repointing a workflow whose conversation is gone, and saving a conversation as a workflow — writes nothing and reports 保存失败：请刷新页面后重试 rather than replacing the list with what it could not read.

<a id="selection-highlight"></a>
## Selection highlight

Exactly one row marks the current session, favoring specificity: a workflow whose `homeSessionId` equals `useSessions(state => state.current)` draws the highlight; the workbench draws it only when the current session is its own `workbenchSessionId` **and** no workflow already binds that session — a workflow's binding always wins over the workbench, so a session named by both never lights up two rows at once. Each row carries a boolean `data-active` attribute; `ServerSidebarRoot.module.css` styles the workbench's active state with an inset brand-colored ring (`.workbench[data-active='true']`) and `SidebarGroups.module.css` styles a workflow row's with the same `--dsw-alias-interactive-bg-active` fill `dsh-client-ui-trajectory` already uses for its own selected-row state, keeping this package's palette to tokens already established elsewhere in the product.

<a id="identity-and-sign-out"></a>
## Identity and sign-out

The footer names the person the deployment signed in, and offers the one control that undoes it. Neither half is model-visible: no session event carries the name, and nothing here reaches a model request.

**The name is a display copy, not authority.** `client/identity.ts` reads the deployment's access token out of `localStorage.accessToken`, drops the login page's `Bearer` scheme, decodes the payload without verifying anything, and shows the claim named by `Config.displayNameClaim` (`login_uname` for the sign-on this deployment runs). A token nobody can read, a claim that is absent or not a string, and a page with no token at all all render the anonymous placeholder ("用户" / "User") instead. Nothing is gated on this value — the party that verifies the token is the reverse proxy in front of this process, which has already decided who is on the other end by the time a page loads. The name follows a `storage` event, so a tab that signs a different person in moves it without a reload.

**Signing out runs five steps, in this order, every one of them attempted whatever the one before it did** (`client/sign-out.ts`).

1. **Stop the work in progress** — the open conversation, and every other one the session list reports as `running`, each through the same session-scoped `conversation.cancel()` the shipped stop button calls. The open one is stopped whether or not it carries that bit; an idle stop is a no-op the host answers. The wait is bounded at three seconds, so a cancel the host never answers costs the visitor that long rather than the four steps that actually drop the token.
2. **`POST /auth-gate/logout`**, so the process stops spending the token it holds. `keepalive`, because step 5's navigation would otherwise cancel a request the document owns — which is also why the sequence sends this request rather than waiting on it: a route held open until a proxy's read timeout would otherwise keep the visitor on a page whose work is already stopped and whose token is one step from being dropped.
3. **Remove the login page's own storage keys, and the shell's record of the conversation on screen, by name** — never `localStorage.clear()`, which would take the shell's other private keys and any other application served from this origin with it. The shell's record is `dsh.sessions.current`, the key `dsh-client-ui-workspace` persists its selection under; left in place, the next person to sign in on the same browser would open on the conversation the last one had on screen.
4. **Clear the mirror cookie**, under the exact `Path`, `Secure`, and `SameSite` auth-gate wrote it with — the `Path` being the deployment prefix this shell is served under, which both packages resolve the same way (the directory of `document.baseURI`).
5. **Leave for the login page**, carrying `?redirect=` and the address to come back to: the current one with the login page's own credential parameters (`token`, `token4a`) taken out of its query and its fragment alike, every other parameter left byte-for-byte as it arrived, and the fragment's own route kept — these pages are hash-routed, so the fragment is the address.

A refusal at any step is a `console.warn` and nothing more: the visitor is leaving either way, and a step that could not run is not a reason to leave the rest undone.

**Literal copies, not imports.** The `Bearer` strip, the JWT decode, `/auth-gate/settings`, `/auth-gate/logout`, the cookie line, and the return-address rule are copies of [`dsh-experimental-auth-gate`](../auth-gate/README.md)'s own, for the reason `client/nav-catalog.ts` copies the two catalog routes: a cross-package value import is not this repository's sanctioned way to couple two client-adjacent plugins, and this sidebar must also work in a composition that does not compose auth-gate at all. Both packages are fork-owned together and must keep these six agreements in step, including how each is addressed: both routes are requested document-relative, and the cookie is cleared at the same deployment prefix auth-gate wrote it under.

A press is consumed when the registry's accepted bindings are active, the press is neither consumed already nor composing, it lands in a region the command's owner runs it in (`page` and `editable` for `ui-workspace`'s six, `terminal` as well for `workspace.files` and `sidebar.right.toggle`, with Control+W and Control+R left to a terminal as the registry leaves them), and it is the exact combination of a withheld command's effective binding with no issue and no conflict. The guard reads the live catalog, so a key a visitor rebound a withheld command to is withheld as well, and a key another command took over still reaches that command. Input-method composition, dead keys, and AltGraph input pass through as the registry passes them; the one exception is Option+Command+N in a macOS browser, which the registry dispatches even when the browser reports it as a dead key, and which the guard consumes through the registry's own `consume`, so the press after it is not swallowed. **Rows:** `shell.overlay`'s cell is the entry id, so the console registers the reference's own entry `shortcuts` again at priority -1 with `ui-shortcuts`' own component, store, and `shortcuts` namespace, read off the slot ledger, and an inject face whose catalog leaves the eight out. It follows the ledger as that entry is registered, replaced, or removed. Its binding check, and its save, report a combination only a withheld command holds as reserved (此组合由系统或文本编辑操作保留。) rather than naming that command: the registry refuses to displace another command's binding, and its refusal would name a command the reference does not list. An entry whose component, store, namespace, or face hooks the console cannot read is replaced by one that draws nothing, reported once to the browser console, so the Settings row's 编辑快捷键 then opens nothing. The command ids and their regions, the entry id, and the namespace are literal copies, since no owner's `/client` entry exports a constant for them; `tests/console-shortcuts.client.spec.ts` checks them against the owners' source, including that `ui-shortcuts` registers at the default priority and that `ui-workspace` registers no command the console has not decided on, and the e2e scenario checks the open reference and presses each withheld key in a real browser.

The conversation header's expand button, which `ui-sidebar-right` draws in the header's corner (`conversation.session.header.corner`) while the right column is closed, is withheld with the toggle. The console's `index.ts` registers an entry that renders nothing in that single slot at priority -1; the slot's lowest-priority entry renders, so the button `ui-sidebar-right` registers at the default 0 never mounts, and the corner holds nothing but the slot's own anchor. The column's own collapse control stays, and a file a visitor clicks still opens the column through `ui-sidebar-right`'s `openResource`, which does not run the toggle command: the chip of a file referenced with `@`, or a file the conversation links. `tests/browser-plugin.client.spec.ts` pins the shadow and checks against `ui-sidebar-right`'s source that the button registers in that slot at the default priority; the e2e scenario checks that the header draws no expand button and its corner holds nothing, that the key leaves the column closed, and that the chip and a file link each open the column on the file's document tab.

Renaming a conversation has no place on the console, so its dialog is withheld rather than reworded; a conversation the console keeps is named by saving it as a workflow. `ui-workspace`'s rename dialog (the `shell.overlay` entry `workspace.session-rename`, titled 重命名会话) opens whenever `ui-workspace`'s rename request is set: by the `session.rename` shortcut, withheld above, and by two controls under `sidebar.workspaces`, a slot this shell never declares. `withheld-rename.ts` registers an entry under that id at priority -1 that draws nothing, so `ui-workspace`'s dialog never mounts, and settles every rename request as soon as it is set through the shadowed face's `settleSessionRename`, so none stays pending for `ui-workspace`'s dialog to show once the console unloads. A request raised by any path — a Desktop shell's native accelerator included — therefore shows nothing and renames nothing. The entry id and the face's members (`hooks.renameRequest`, `settleSessionRename`) are literal copies; `tests/withheld-rename.client.spec.ts` checks them against `ui-workspace`'s source, including that `ui-workspace` registers the dialog at the default priority. A face whose members the console cannot read leaves its request pending, and the dialog stays withheld.

## Brand and hero facade

Three more surfaces carry DeepSeek's own product identity or internal-status copy rather than banned vocabulary, and are replaced or removed for the same customer-form reason as De-terminology above:

- **Sidebar brand row.** `sidebar.brand.mark` renders with no fallback at all (previously a fish icon); `sidebar.brand.name`'s fallback is plain text — locale key `brand.name.fallback` ("工作台小助手" / "Workbench Assistant") — with no build-revision badge. `@deepseek-ai/dsh-client-ui-brand-official` (an official-build-only occupant of both slots, plus `conversation.hero.brand.mark`) is disabled outright in the console bundle; this package's own `client/index.ts` also takes over `conversation.hero.brand.mark` at priority -1 (the slot's shadowing rank — ascending, lowest renders — with an empty component), so a deployment that forgets to disable `ui-brand-official` still gets this package's no-icon hero mark rather than the official one.
- **Conversation hero chrome.** The blank-draft hero headline (`dsh-client-ui-conversation`'s `HeroShell`/`ConversationRoot`) carries a fish icon, a "PREVIEW" status pill, and a workspace-picker-plus-agent-preset row — none of it has a Config flag or a disable seat of its own, so `terminology-guard.ts` extends its CSS injection to also: hide the (now slot-empty) fish hitbox and the preview badge; collapse the headline text to `font-size: 0` and paint this package's own brand copy over it through a `::after` pseudo-element (the original headline text node stays in the DOM and the accessibility tree unchanged — see Known Limitations); and hide the workspace-picker row outright. That rule is load-bearing rather than belt-and-suspenders: `ui-workspace` is composed (see Composition below), so the chip carries a real Workspace title and opens a live picker menu — hiding the row is the only thing keeping both off a customer-form page, which is why an e2e scenario asserts the row is present **and** renders nothing, instead of trusting the selector: an element that stopped matching the rule is also an element that is not visible, so an invisibility assertion alone would pass on the one failure it exists to catch. `conversation.hero.agentPreset`, the same row's other seat, is emptied at the composition level instead: `ui-agent-preset` is disabled outright in the console bundle, which also removes its read-only session-header preset label and its Settings row — surfaces this row's own CSS rule could not reach.
- **Internal-testing notice.** `dsh-client-ui-settings-models` registers the "内测声明" dialog as a `settings.onboarding` step (shown once per acknowledgement version, `WELCOME_NOTICE_VERSION`), alongside the Models settings section and the DeepSeek credential onboarding step. A customer deployment fixes its model and credential at the deployment layer and never shows a DeepSeek-internal notice, so the console bundle disables the whole row rather than pre-acknowledging a version (product decision, 2026-09-06). With no step left, `SettingsRoot`'s onboarding list renders nothing.

<a id="composition"></a>
## Composition

The plugin is not part of any shipped bundle. The customer console composes it through [`@deepseek-ai/dsh-experimental-console-profile`](../console-profile/README.md), whose bundle layer disables `ui-layout`, `ui-sidebar`, `ui-agent-preset`, `ui-brand-official`, `ui-cordis`, `ui-trajectory`, `ui-model-selection`, `session-log-download`, `ui-settings-models`, and `ui-permission`, and inserts `server-layout`, `content-surface`, `content-column`, this package, and the `library-skills` row (an isolated `skill-filesystem` provider over `@deepseek-ai/dsh-experimental-library-skills`'s bundled `skills/`). This row must be composed in a bundle layer: the menu is volatile Config that the settings service saves into the profile patch, and config-editor refuses that write when a `--patch` overlay or the home patch inserts or configures the row, so a console assembled with `dsh --profile web --patch <overlay>` cannot save a workflow, a group, or the workbench session. With `perMember` the menu is not saved through the settings service, so a layer above the profile patch may configure the row: a deployment serving several members restates the whole row there with `perMember: true`, an empty menu, and no `workbenchSessionId`, which also keeps `settings/describe` from handing every member a menu an earlier single-person run left in the shared patch. Install the bundle with `dsh plugin --profile <name> add <path>`. The same package ships `permission-lock.patch.yml`, the rows a deployment applies above the profile patch. Its `permission` row restates the preset table with customer-facing names, because the shipped `workspace-write` name is what an access chip displays and the chip falls back to a host-supplied name verbatim whenever it differs from the built-in default; it names the `defaultPreset` a new session is pinned to (see De-terminology above); and it carries `isolate: { commands: true }`, which is what keeps `/permission` unregistered (see De-terminology above). The console package's `tests/profile.spec.ts` pins all three. Neither file inserts `content-frame` or `component-surface`: the deployment's own page catalog and view catalog go into the deployment's own bundle layer, since each carries deployment-specific configuration. Neither inserts [`auth-gate`](../auth-gate/README.md) either, and that row is what the footer's sign-out button needs: composed without it, the button still renders, but pressing it reports the missing login page to the console and stays put. The console bundle and `overlay/sidebar-menu.patch.yml` both carry this package's one required `config` field (see Config above); a row composed without it fails at load. `sidebar-menu.patch.yml` is the minimal composition — this row and the `ui-sidebar` disable row — and a composition that uses it also needs it in a bundle layer for the menu to save. Release bundles must not declare an experimental package. `dsh-experimental-library-skills` is named by a row's `bundledSkillDir` expression rather than by a row's plugin name, and it is no less required: a profile that cannot resolve it throws `MODULE_NOT_FOUND` while the row loads, the entry tree never settles, and **the console does not boot**. The console bundle lists it under `dependencies` for that reason.

## Known Limitations and Deferred Work

<a id="known-limitations-and-deferred-work"></a>

- **Literal 240px is not independently enforced.** This shell never fixes an inline pixel width; it renders at whatever `width` its owner (`dsh-experimental-server-layout`) hands it, and never toggles collapse. `server-layout`'s frozen 3:16:5 track ratio happens to equal exactly 240px at its own 1920px reference frame width (`1920 * 3/24 = 240`), but at any other frame width the column is proportional, not fixed. Making it literally fixed would require changing `server-layout`'s own frozen, deliberately non-configurable geometry, which is out of this change's scope.
- **Decision ③'s user-message check is a paged-window approximation.** Visibility of "存为工作流" reads `useSession(s => s.chat.legacy.nodes)`, the same paged conversation-snapshot window `StatsLine.tsx` reads from — a user message far enough back to have paged out of the window would not be found. A whole-log check would need a durable projection this v1 does not add.
- **The turns/steps status row, the permission-preset chip, and an untitled conversation's header crumb are hidden by coupled CSS selectors, not Config flags.** The first couples on DOM order, the other two on CSS-module class substrings; see De-terminology above for the exact fragility of each and what pins them.
- **Other places still show the working directory's name.** The header replacement covers the open conversation's own crumb. The session list's `displayTitle`, which for a conversation with no durable title is the working directory's basename, still reaches two places a console user can open: the session candidates of `ui-reference`'s `@` picker, and the hero's workspace chip, which `terminology-guard.ts` hides on screen but leaves in the DOM and the accessibility tree. A third place shows the whole path: the document tab (`ui-sidebar-documentpreview`) shows a file's absolute path on the Host, the working directory's name included, in its header and in the header's hover tooltip (`TextPreview.tsx` draws `displayPath`, which is `absolutePath ?? file.path`). The tab opens when a visitor clicks the chip of a file they referenced with `@`, or clicks a file in the conversation. A composition that keeps `ui-sidebar-files`, which the console bundle disables, also shows the whole working directory as the Files tab's label. A delegated conversation's breadcrumb names an untitled parent by `displayTitle`; the console's presets delegate nothing, so no console conversation has one.
- **A browser that showed the Files tab before the upgrade gets that tab back empty.** `ui-sidebar-right` keeps each conversation's column layout in the browser's `localStorage` under `dsh.sidebar-right.v1.<conversation>`. A conversation whose column held the Files tab before the console disabled `ui-sidebar-files` restores that tab, titled with the label the Files type had when it was opened (文件, or Files in English), over the line 这类内容还没有可用的查看方式。 (Nothing here can view this kind of content yet.), and with no path. An e2e scenario restores such a layout in a Chinese page and checks the title, the line, and that no directory path of the Host is on the page.
- **A workflow's untitled conversation reads 未命名对话 in the header.** A 我的工作流 row shows the workflow's name, but the header names an untitled conversation by the workbench entry or by the temporary rows' copy only. A workflow whose conversation is gone opens a fresh one, and while that conversation has no durable title its header reads 未命名对话 (Untitled chat).
- **A preset a visitor stored before the upgrade is dropped.** The lock overlay's `defaultPreset` sits in a layer above the profile patch, so the one-time import of `settings.yaml` refuses the stored `permission` section and leaves it in `settings.yaml.imported` — see De-terminology above.
- **Typing `/permission` still sends a message.** With no host descriptor and no client contribution under that name, the trigger's Enter adjudication resolves nothing and the composer's default sink submits the line as ordinary text: `/permission read-only` lands on the log as a `user/message` and opens a turn, the model reads those two words, and nothing else happens — no `permission/preset` event, and the access chip's `aria-label` still names the pinned preset. Closing that would need a refusal the command layer cannot express: a registry entry can only add a row, never claim a name it declines to serve.
- **`navSnapshot` captures only what the 导航 menu lists.** `captureNavSnapshot` keeps an entry only when the merged catalog carries its `{kind, entryId}`, so three things in an ordinary content column are dropped from the degraded re-creation: a chart the agent drew, a component the model showed on its own initiative with `show_component` (its id is free-form model output, not a configured view), and a page or view the deployment configured when the entry was shown but no longer configures at save time.
- **A stored view is replayed as it is configured today, not as it looked when saved.** `navSnapshot` records a view's id, not the spec behind it — replay runs `show-content-view`, which reads the deployment's current `views` config. A view the deployment has since edited comes back changed, and one it has since removed reports "没有这个视图。" and is skipped. The session log of the original conversation still carries the spec as the user saw it (that is what `content-component/shown` records); a workflow's snapshot is a list of stops, not a copy of what was at them.
- **The green-dot mechanism reuses `completionUnread` rather than new bookkeeping, and is unit-tested only.** It is an exact match for "stopped outside the main view and not yet opened," but proving it end to end would require a real agent-loop running→idle transition while unselected — the running bit is a host-frame push tied to actual execution, not something a log-only append can fake. This package's sidebar e2e scenarios issue no model calls (matching their established design), so the mechanism is pinned by `packages/experimental/server-sidebar`'s own unit tests instead.
- **Rename/remove use hover-revealed icon buttons, not a native context menu.** A v1 downgrade the task's own brief explicitly permitted ("若实现体量失控，降级为右键菜单「上移/下移」") for reordering too, until reordering moved to native HTML5 drag-and-drop; the context-menu downgrade for rename/remove remains, since a second interaction pattern for two occasional actions is still not justified on its own.
- **`ui-workspace` is composed, and only a CSS rule keeps its hero picker off the page.** It cannot be disabled: `dsh-client-ui-conversation` injects its `uiWorkspace` service, so a composition without it never activates the conversation column at all. Its `sidebar.workspaces` half is inert once this shell drops that slot (`ctx.slots.inject` just never fires — see Replacing the shipped sidebar above), but its `conversation.hero.workspace` registration lands, and `terminology-guard.ts`'s `heroWorkspaceRow` rule is what hides it — a class-substring coupling that breaks silently if that class is renamed. A zero-Workspace fresh install still leaves a page or workflow click a contained no-op (see Navigation above) — an existing, already-accepted edge case carried forward from the prior favorites-based design, not new here. The workbench's own load-time auto-open goes further and never even attempts in this case (see Workbench above), waiting indefinitely for a Workspace rather than firing once and warning.
- **With no Workspace connected, the composer names one.** `ConversationRoot` renders its inert composer under `placeholder.workspace` ("Choose a workspace to start"), banned vocabulary this package cannot reach. It is not chrome a CSS rule should hide — the composer is genuinely unusable in that state and the placeholder is the only thing saying so — and it is not renameable from a composition: it belongs to `dsh-client-ui-conversation`'s own locale namespace, and the locale registry rejects a second registration for a namespace/locale pair it already holds, so no plugin can shadow another's key. Closing it means either a deployment that always has a Workspace (the state the whole console already degrades to a no-op in — see Navigation above) or an override seam in the locale registry. An e2e scenario pins the conversation column's Workspace words to that one placeholder so a second one cannot appear unnoticed.
- **The English composer placeholders name sessions.** `dsh-client-ui-conversation`'s English `placeholder.default` ("Message or run a task, / commands, @ files or sessions") and `placeholder.hero` ("Describe what you want to build, / commands, @ files or sessions") say "sessions" where the Chinese copy says 对话. The console's lock holds `locale` at `{}`, so each browser shows its own language, and a visitor whose browser asks for English sees one of them in the composer. They belong to the same locale namespace as `placeholder.workspace`, so no plugin can rename them either.
- **The hero headline's original text node survives in the DOM and the accessibility tree.** `terminology-guard.ts`'s `::after` swap only changes what the headline paints (`font-size: 0` on the real text plus a pseudo-element carrying this package's own copy); a screen reader or any DOM-text query still finds `dsh-client-ui-conversation`'s own English/Chinese headline string, not this package's brand copy.
- **Signing out does not tell the deployment's own sign-on anything.** It drops the token everywhere this browser and this process hold it, and sends the visitor to the login page; the token itself stays valid on the issuer's side until it expires, because this package knows no revocation endpoint. A deployment that has one calls it from step 2 of the sequence above.
- **There is no confirmation step.** One click stops the work in progress and signs the visitor out. Stopping a turn preserves the conversation and its pending inbox work (that is what `cancel` means here), so the cost of a mis-click is a reopened login page, not lost work.
- **The displayed name is a non-authoritative copy.** It is decoded in the browser from an unverified token; anyone able to write `localStorage` on this origin can change what the footer says. Nothing is gated on it, so what that buys is a wrong name.
- **The mirror cookie's `Path` is resolved, not agreed.** Both packages narrow it to the deployment prefix by reading the same page fact rather than by sharing a value, so a proxy that serves the two halves under different prefixes would have the removal line write a second, empty cookie and leave the mirrored token in place. Nothing detects that; the pairing is proved by a unit test comparing this package's line against auth-gate's own.
- **The stop sweep trusts `SessionSummary.running`.** A conversation whose running bit has not arrived at this browser yet, and which is not the open one, is not stopped. The host-side turn keeps running until it finishes on its own.
- **The sign-out sequence has no browser-level evidence.** The Playwright scenario asserts that the control renders and that the footer band fits it, and stops there: this package's scenario composes no `auth-gate` row (that package gates the whole page on a token, which every other assertion in the scenario would then have to carry), so "click sign out, the cookie is gone, the login page is showing" is proved by unit coverage over the injected browser rather than end to end.
- **The settings entry renders as an icon, and its connection indicator goes with the label.** The footer band is one row, and the column it sits in is a share of the frame (`dsh-experimental-server-layout`'s `solveTracks` gives the session track 3 of 24 units), so the labeled trigger does not fit beside the signed-in name and the sign-out label: this shell asks the `sidebar.settings` occupant for its compact form (`wide: false`). `dsh-client-ui-settings-general` draws its connection indicator only in the labeled form, and that indicator is this console's only outage notice and its only reconnect button — a dropped socket now says nothing in the sidebar. Getting both back means a wider session column, which is that package's frozen track ratio rather than anything this one can change.
- **A per-member row configured only in the bundle layer keeps its menu fields writable.** The settings service still offers `workflows`, `groups`, and `workbenchSessionId` to a settings write, which saves them into the profile patch without remounting the row. Nothing reads them there, and the next start refuses the row at load, so a deployment serving several members restates the row in a layer above the profile patch (see Composition), where config-editor refuses that write.
- **Withheld keys still reach a Desktop shell's native accelerators.** The key guard consumes a key on the page. A Desktop shell on macOS or Windows delivers application keys as native menu accelerators, which do not pass through the page, so a console page loaded in such a shell would still run a withheld command; the rename dialog stays withheld there, and the archive confirmation and notices keep the console's words. The console is served to browsers.
- **A key a withheld command holds cannot be given to another command.** The shortcut reference reports it as reserved. A visitor who rebinds nothing keeps every default, and the withheld commands' defaults are combinations no kept command uses. A browser that stored a binding for a withheld command before the console withheld it keeps that binding: a kept command whose combination it overlaps is disabled as a conflict, 恢复默认 on that command reports the combination as reserved, and only 全部恢复默认 clears it. The reference's count of changed shortcuts counts that binding too.
- **Option+Command+N is consumed during input-method composition in a macOS browser.** The registry runs that combination even when the browser reports it as a dead key, and its input observer cannot tell that report from composition, so the guard consumes it in both cases. Composition with any other combination passes through.
- **The right column's collapse control still shows the withheld key.** Once a file has opened the column, its collapse button's tooltip and `aria-keyshortcuts` show ⌘⇧B (Control+Shift+B on Windows), which does nothing on the console: `ui-sidebar-right` reads them off the shortcut registry's own catalog (`SidebarRight.tsx`), not the console's. Taking the key off that button needs a change to `ui-sidebar-right`.
- **The right column's new-tab button opens an empty guide.** Once a file has opened the column, the `+` on its tab strip opens a Start tab (开始 on a Chinese page) whose guide lists nothing, since the console composes none of the tab kinds the guide offers; closing that tab is all it takes. Taking the button off needs a change to `ui-dockkit` (`TabPanel.tsx`) or `ui-sidebar-right`.
- **The header's corner keeps its spacing with nothing in it.** `ui-conversation` hides the corner with `.headerCorner:empty`, but every slot outlet draws a `display: contents` anchor (`ui-renderer`'s `SlotOutlet`), so the corner is never empty: with nothing in it, it keeps its 8px left margin and −16px right margin, the spacing the header has in any composition while an open column's expand button renders nothing. Taking the corner out of the layout needs a change to `ui-conversation` or `ui-renderer`.
- **A collapsed right column comes back only for a file.** A visitor who collapses a column a file opened has no button or key that opens it again; clicking a file — the same one or another — does. Whether the column is open is kept per conversation in the browser's `localStorage`, so a reload restores it as the visitor left it.
- **A save is refused for an old reference that has since become another member's.** The check covers every conversation id the saved fields name, including one the member saved while the directory placed it with nobody. Once the directory gives that conversation to another member — a root registered again, say — every save that sends the workflow list answers 400 naming that entry's field path, such as `workflows[2].homeSessionId`, and the section names that workflow and asks for it to be removed. The member clears it with that workflow's Remove (移除). A stored workbench reference blocks no save: the page sends a workbench id only for a workbench it has just created (`client/index.ts`), and the section's own saves carry only `groups` and `workflows`.
- **The settings route assumes an HTTP carrier.** The browser half fetches `/server-menu/workflows` — the route the node half registers, resolved against the page's deployment base. A transport that serves the shell without exposing the harness over HTTP would fail the row, the same way content-frame's settings route would.
- **An unclean-by-content draft is not actually displaced.** `isCleanWorkbenchDraft` refuses to reuse a draft whose content column shows anything but the home page, but the create path it falls through to resolves through `resolveOrCreateSession` → `connectWorkspace`, whose own reuse scan hands back the first blank session already in the Workspace — and a draft that has run no turn is one of those. It is normally the draft itself; a Workspace holding another blank session ahead of it in the session list hands that one back instead, and `workbenchSessionId` follows. Either way the visitor lands on the home page again on a conversation that already existed, with the page they had navigated to still in that draft's switcher strip. Minting a genuinely fresh conversation here would need a create path that bypasses that scan for this one caller, which also decides how many abandoned blank conversations a navigate-then-click cycle is allowed to leave behind — a product decision this slice does not take.
- **Cross-group movement has no keyboard path, and group order has no interface at all.** Both ways to move a workflow need a pointer or a touch: the drag, and the row's 移动到… menu, whose list `Menu` portals to the end of `document.body` without taking the focus, answering arrow keys, or holding Tab inside it — so its rows sit behind every other focusable element on the page. Tab reaches the trigger and stops. Closing that gap means a focus-managed dropdown of this package's own, or a change to the shared primitive; neither is in this slice, and the focus leaving the row at least closes the list rather than leaving it standing with its trigger hidden. Reordering the groups themselves is not reachable at all — a group takes its `order` at creation, and only pinning moves it after that.
- **The temporary section has no identity predicate.** Its five membership rules filter the whole conversation directory this process serves; none of them asks whose conversation a row is. What makes that "this person's own conversations" is the deployment shape — one visitor per process, per `$DSH_HOME` — and nothing in this package enforces it. A composition pointing two people at one process would show each of them the other's rows. With `perMember` this package still filters nothing by member: which conversations a member's page lists is the session list the Host serves that page.
- **移出列表 is one-way for the person using the console.** It archives, so nothing is lost on the host, but it raises no notice with an undo, and the shipped browser's unarchive control is not composed here; the `session.archive` shortcut, whose notice offers an undo, is withheld. A row taken off the list does not come back.
- **The temporary section derives over the whole session directory.** `session.list` returns everything (its v1 has no paging), so a very long history is filtered in the browser on every relevant change. The five-row cut shortens what is drawn, not what is computed.
- **A row's relative time does not tick.** It is computed at render, so "刚刚" stays until something else re-renders the section.
- **Not covered by an assembled snapshot.** The browser evidence is a Playwright scenario against a real composition; the snapshot lanes replay the shipped composition, which does not compose an experimental row.
