# @deepseek-ai/dsh-experimental-server-sidebar

English | [中文](README.zh.md)

## Summary

A fixed-width product-console sidebar: a drop-in replacement for the shipped [`dsh-client-ui-sidebar`](../../client/ui-sidebar/README.md) that removes session/workspace browsing entirely and replaces it with four sections — 工作台 (workbench, one persistent default conversation), 导航 (navigation, the pages and views the deployment configured), 我的工作流 (my workflows, a user's own named shortcuts back to conversations they taught the agent something in, filed under groups they name themselves), and 临时工作流 (everything none of those rows already shows). It replaces ui-sidebar in a composition rather than sitting beside it, because `sidebar` is a single slot and its child slots may be declared only once.

This package targets a "customer form" composition: an end customer using the product never needs to know a conversation is a durable, resumable object with a Workspace behind it. Every session/workspace management step (creating one, reconnecting one, choosing which one is "current") happens inside this package's own actions; the vocabulary itself — 会话/session, 工作区/workspace — is banned from every string this package's own dictionaries carry, and the composition disables the shipped controls that would otherwise leak it (see De-terminology below).

<a id="replacing-the-shipped-sidebar"></a>
## Replacing the shipped sidebar

- **Four child slots survive** — `sidebar.brand.mark`, `sidebar.brand.name`, `sidebar.settings`, and `sidebar.footer.action` keep the kinds and scopes `dsh-client-ui-sidebar` declared, reused by type import rather than restated, so ui-settings's existing registration keeps working unchanged (a brand package filling either identity slot is disabled in the customer composition instead — see Brand and hero facade below). `sidebar.workspaces` is dropped outright: this shell has no session-browsing region for it to seat in. `ui-workspace`'s `sidebar.workspaces` registration goes through `ctx.slots.inject`, which is declaration-gated (it waits for a declaration and simply never fires without one — `SlotRegistry.inject`'s own contract) rather than a hard requirement, so `ui-workspace` composes with that half of it permanently inert. It is composed, not disabled: `dsh-client-ui-conversation` requires its `uiWorkspace` service, so disabling it would leave the whole conversation column and every sibling that depends on it unactivated. Its other registration — `conversation.hero.workspace`, a slot `dsh-client-ui-conversation` always declares — therefore does land, and the hero row carrying it is hidden by `terminology-guard.ts` instead (see Brand and hero facade below).
- **The New Session button is gone.** There is no "start an ad-hoc conversation" affordance in this shell; every entry point (工作台, a 导航 page, a 我的工作流 row) resolves or creates its own session internally.
- **The 56px collapse rail is gone.** This shell never calls a collapse action and always renders its full content regardless of the `collapsed` owner prop — see the Known Limitations entry on the residual coupling this leaves with the surrounding shell's own track geometry.
- **The pointer-driven scrollbar behavior is unchanged** — the column's scrollbars draw while the pointer is inside it and for two seconds after it leaves, canceling a pending hide if the pointer returns, tracked geometrically rather than by DOM containment (so a portalled overlay that is a DOM descendant of the column, as ui-settings renders its panel, does not read as "the pointer left").

<a id="workbench"></a>
## Workbench

工作台 is the one persistent default conversation this shell lands on — but landing on it means something different depending on how you got there.

- **Loading** the sidebar with no session currently selected (`openWorkbenchOnLoad`) resolves the recorded `workbenchSessionId` and reopens it whenever it is still live, whatever content it already carries — continuity semantics: the page resumes exactly where it left off.
- **Clicking** it (`openWorkbenchOnClick`) always lands on a clean page instead — clean-draft semantics: it reopens the recorded session only when it is live and still *clean*, which is two conditions together (`isCleanWorkbenchDraft`): it has run no turn (`SessionSummary.blank`), and its content column carries nothing beyond the deployment's own configured automatic home. None recorded, a recorded one that is gone, one that has run a turn, and one whose content column shows anything else all take the create path instead: a session against the recent Workspace, with `workbenchSessionId` repointed at it. That path resolves through `connectWorkspace`, whose reuse scan hands back the first blank session the Workspace holds in the session list's own order — normally this same draft, and any other blank session of that Workspace when one comes first, with `workbenchSessionId` repointed at whichever it was (see Known Limitations); what the visitor gets there is the configured automatic home shown again, not a new conversation.

**`SessionSummary.blank` alone cannot answer a click.** That bit tracks conversation turns and nothing else — standalone events never lower it (see `sessionBlank` in `dsh-host-apiproxy`) — so a draft the visitor has already navigated somewhere in still reads as blank: one 导航 click, and the content column is showing a published report on a session the next workbench click would happily reuse, landing on that report instead of on a clean page. What the session already shows is therefore the second half of the judgment, read off the session list's own `projectionValues.contentSurface.entries` — the same feed, and the same defensive untyped read, `dsh-experimental-server-layout`'s `ShellFrame` uses for the content column's own empty check. The configured automatic home is the one entry that does not disqualify a draft, because the click path itself is what put it there (see below); counting it as content would leave every clean click unable to reuse the draft its own previous click had just populated.

Both share one open-or-create mechanism (`client/workflow-actions.ts`'s private `openOrCreateWorkbench`) and differ only in what qualifies the recorded session for reuse. `workbenchSessionId` is a weak reference for exactly the same reason a workflow's `homeSessionId` is (see below): nothing here owns session deletion, and a stale pointer degrades to a fresh conversation rather than corrupting the document that names it.

The load path's mount-time auto-open withholds its one-shot attempt rather than spending it against an unready Workspace baseline: reopening a live recorded session needs no Workspace at all, but creating one does, and `recentWorkspaceId` cannot distinguish "the Workspace baseline has not loaded yet" from "this deployment genuinely has none" — so the effect waits for either a live recorded session or a resolved Workspace before it tries, and gives up permanently the moment a session becomes current by any other means.

**A configured automatic home auto-shows on a clean click, never on the load path.** When the deployment configures one (content-frame's `homePage` or component-surface's `homeView` — see Navigation below), `onOpenWorkbench` runs that target's own command against the session `openWorkbenchOnClick` just resolved — the freshly created session on a create outcome, or the reused one on a reused-clean outcome — the instant after that resolution settles, so a new or clean-draft conversation opens onto a populated column instead of an empty one. A reused draft that already shows it skips the call (`hasShownHome`): that target is the only content a clean draft may carry, and repeating the command would append a second record for what is already on display. This runs only from the click handler: the load path's own continuity semantics (resume exactly where a live session left off) would be broken by forcing content onto a session that already carries something else, so `openWorkbenchOnLoad` never calls it. The auto-open command is an ordinary menu invocation — it appends the same session event and leaves the same durable log record a user's own click would.

<a id="navigation"></a>
## Navigation

导航 lists everything the deployment configured as one click away from the content column, merged from two catalogs (`client/nav-catalog.ts`): [`content-frame`](../content-frame/README.md)'s pages, read from `/content-frame/settings`, and [`component-surface`](../component-surface/README.md)'s composed views, read from `/component-surface/views`. Both reads happen once before this entry registers, over hardcoded route paths and locally validated JSON shapes rather than imported values or types — a cross-package value import is not this repository's sanctioned way to couple two client-adjacent plugins, and this package's own tests import each owning constant so the copies stay mechanically checkable. Every row carries which catalog it came from, because the two are opened by different commands and land as different content-surface entry kinds.

**Menu order is pages, then views, each in its own declaration order.** Navigation order follows deployment configuration and is never user-reordered (decision ⑤); a fixed source order keeps that true across the pair without a third configuration field to keep in step.

Clicking a row runs that row's own command against the current session (creating one first when none is open, through the same resolution the workbench and every workflow action share — see `client/session-resolution.ts`), through `ctx.remote.commands.execute` — the same command seam a session log can replay, not a direct service call. A page runs content-frame's `show-content-page`, whose handler appends `content/shown` with `by: 'user'`; a view runs component-surface's `show-content-view`, whose handler appends `content-component/shown` with `by: 'user'`.

**A row the deployment has since dropped answers differently by kind.** The navigation menu is built once at load, so a page or view removed from configuration after that is still a row until the next reload, and a workflow replay can name a stop the deployment no longer configures. A dead view row draws component-surface's own sentence, 没有这个视图。, in the chat where its command row sits; a dead page row draws nothing at all, because content-frame's command row is hidden unconditionally and its refusal is developer-register English no end user should read. Aligning the two is content-frame's change, not this package's; until then a page that vanishes vanishes silently.

**A composition with only one of the two packages is ordinary, not an error.** Each read is contained: an unreachable route, a non-200 answer, or an unusable document contributes no rows instead of taking the whole sidebar down, so a deployment that composes only content-frame gets a pages-only menu and one that composes neither gets the empty copy.

Each catalog also carries its own optional automatic home — content-frame's `homePage`, component-surface's `homeView` — read alongside its rows and consumed by the workbench's click handler above. A value naming nothing that same response configures is contained rather than thrown: unlike the node-side `Config` validation, which fails the whole load, this browser-side read reports it with `console.warn` and treats the field as absent, because a load-bearing shell surface should not go down over one misconfigured field on an otherwise-working deployment. **Configuring both is the one exception and fails at load**: the content column shows one thing at a time, so a deployment that named two has expressed an intent this shell cannot carry out, and honoring whichever route answered first would leave the other configured value doing nothing with nothing to say why.

<a id="my-workflows"></a>
## My Workflows

我的工作流 is a user's own named shortcuts, persisted per account (this deployment model's one-process-per-user shape — "per account" means "per `$DSH_HOME`"). One workflow binds exactly one conversation (v1 boundary; see Known Limitations): `{id, name, order, homeSessionId, navSnapshot, savedAt, groupId?}`.

- **Save** — the "存为工作流" (Save as workflow) action lives in the conversation's own session header (`conversation.session.header.actions`, order 30, after the subagent catalog and background jobs), not a sidebar "+" button: a regular seat for a session-scoped, occasional action already existed, and adding a second interaction pattern for the same kind of action was not justified. It is visible only once the current conversation carries at least one user-authored message (decision ③, checked via `chat.legacy.nodes` — see Known Limitations for the v1 approximation this implies), matching the intuition that a workflow is a shortcut back to a conversation the user actually started, not an empty one. Saving captures the current session id as `homeSessionId` and, as `navSnapshot`, the content column's currently-shown stops that the 导航 menu itself lists, oldest first — anything else the column carries is left out (see Known Limitations).
- **Open** — clicking a workflow reopens `homeSessionId` directly when it is still live. **Restoring only fills in what is missing** (decision ⑦): reopening a live session never touches its content, since there is nothing missing to fill.
- **Degrade** (decision ⑧) — when `homeSessionId` is gone, opening the workflow creates a fresh session against the recent Workspace, replays `navSnapshot` onto it in order (oldest first, so the last one replayed ends up on display, matching what was on display when the workflow was saved), and repoints `homeSessionId` at the new session. A fresh session starts empty, so "fill in what is missing" is trivially the whole snapshot.
- **Rename / remove** — hover-revealed icon buttons (the former favorites menu's own idiom), not a native right-click context menu; see Known Limitations.
- **Reorder** — native HTML5 drag-and-drop: every row is `draggable`, and dragging one over another row's top or bottom half previews an insertion line there (CSS-only); dropping commits through `reorderWithinGroup()` (`client/workflow-actions.ts`), which states the destination lane's complete next sequence and rewrites each named row's `order` field to its position in it (0..n-1) — a full rewrite, not a pairwise swap, so a drop anywhere always produces a clean, contiguous order regardless of what the previous values were. The same call re-files a row dragged in from another lane, so a within-lane reorder and a cross-lane move are one mechanism. This follows user drag order (decision ⑤).
- **Unread indicator** (decision ④) — a workflow whose `homeSessionId` has unseen output draws a green dot, reusing the session list's own `completed` bit ("finished while not selected and not yet opened") verbatim rather than a second last-seen bookkeeping mechanism the original brief suggested as a fallback: `completed` already means exactly this, and it already clears the instant `sessions.open` selects the session — see Known Limitations for why this is unit-tested only, not covered end to end.
- **Displaced sessions are not deleted.** A workbench click that lands on a fresh session (see Workbench above) does not delete the session it displaces: a workflow that already binds it keeps managing it through its own `homeSessionId` unaffected, and one bound by nothing simply stops being pointed at by anything. This composition has no session concept for a user to see or clean up (decision ②), so an unbound displaced session just recedes rather than requiring disposal.

### The navigation snapshot's stored form

`navSnapshot` is a list of `{kind, entryId}` pairs — `kind` is `page` or `view`, and `entryId` is that catalog's own id — because the two kinds are replayed through different commands and land as different content-surface entry kinds, so an id alone no longer says what to do with it. Only entries the 导航 menu lists are captured, since a stop is replayed by re-running its own command and both commands refuse an id the deployment does not configure (see Known Limitations).

**A document still storing the pre-view `string[]` form is refused at load, not reinterpreted.** Every stored id meant a page, so reading one as such would be exact — but a document the process silently reinterprets is one nothing ever converts, and this repository's pre-release stance rejects old on-disk formats outright. The refusal names the offending entry and the one-time converter that fixes it:

```sh
pnpm --filter @deepseek-ai/dsh-experimental-server-sidebar run convert-nav-snapshot ~/.dsh/settings.yaml --dry-run
pnpm --filter @deepseek-ai/dsh-experimental-server-sidebar run convert-nav-snapshot ~/.dsh/settings.yaml
```

The path is required rather than defaulted (a converter that guesses which document it is rewriting is one that can rewrite the wrong one); point it at the document the settings file provider serves, normally `$DSH_HOME/settings.yaml`. It rewrites each stored id to `{kind: 'page', entryId: id}`, writes the empty `groups` list the current format carries when the document has none, leaves an already-current document byte-identical, and writes nothing at all under `--dry-run`. The YAML path edits through `yaml`'s document model rather than a parse/serialize round trip, so an operator's own comments and key order survive.

### Groups

The durable format carries `groups` — `{id, name, pinned, order}` per group — and an optional `groupId` on each workflow naming the group it is filed under; a workflow naming none is ungrouped. `TEMPORARY_GROUP_ID` (`"temporary"`, deliberately not a UUID) is reserved for the conversations a user never named, and nothing durable carries it: that section derives its rows from the live session list and takes its title from the locale dictionary, so the id's one live use is as that section's key in the browser-local fold map, which is not a document. `validateServerMenu` refuses a duplicate group id, a blank or over-40-character group name, a stored group claiming the reserved id, and a `groupId` — the reserved one included — naming a group nothing defines.

The section draws pinned groups first, then the rest by `order`, then every ungrouped workflow at its own top level. That order is derived on each render, never stored as a list.

- **Create / rename** — an in-place input, the idiom "存为工作流" already established for naming a workflow, revealed from a hover icon button. A blank name abandons the edit; the field itself stops at the 40 characters the document refuses beyond, rather than letting a write travel to the route to be told.
- **Pin** — groups only. Pinning sorts a group ahead of every unpinned one without touching its `order`, so unpinning puts it back where it was. Pinning individual workflows is deliberately absent: it would contradict the manual drag order inside a group.
- **Delete** — the shortened group list and its members' cleared `groupId` travel in **one** patch. A document naming a group nothing defines is refused, so a patch carrying only the shortened group list would be rejected; the members land back at the top level.
- **Move** — drag a row onto another group's rows, onto its header, or onto the placeholder an empty group draws; the top level has no header, so it draws a placeholder of its own while a drag is in flight (only then — an empty top level is the ordinary state of a console whose workflows are all filed). Or use the row's 移动到… menu, which lists every lane but the one the row already sits in; a console with no group at all has a single lane and nowhere to send a row, and the control is left out rather than drawn over an empty list. That menu is not a convenience: HTML5 drag-and-drop has no touch equivalent, and the menu is the only path touch has. Every row and group-header control is revealed by a hover **or** by the focus being inside that row or header, so the always-drawn control each one starts with — a row's name button, a header's fold caret — brings the rest up and Tab walks them; a device with no hover at all matches neither condition, so on a coarse pointer they are drawn from the start instead. Tab stops at the 移动到… trigger: the list it opens is not keyboard-reachable (see Known Limitations).
- **Fold** — which groups are folded shut (the temporary section included) is a display preference remembered per browser under `dsh.server-sidebar.view.v1`, never in the deployment's own document. Reading and writing it are each contained: a browser that refuses site storage outright — where touching the global itself throws — falls back to everything expanded and keeps the click that asked. The map is pruned against the authoritative group list on every read of the document, so deleting a group does not leave its fold entry behind for the life of the browser profile.

A workflow whose `groupId` names no stored group is drawn at the top level rather than disappearing. The document's own constraint refuses such a reference, so it can only arise from a document edited outside the interface — and every workflow has to be reachable from somewhere.

### Temporary workflows

临时工作流 is every conversation this process can see that no other row in this shell already shows — the filter runs over the host's whole conversation directory with no identity predicate in it, and what makes that the same thing as "this person's own" is the deployment shape this console is built for: one visitor per process, per `$DSH_HOME` (see Known Limitations). It is derived on each render with nothing durable behind it; five predicates decide membership — not a subagent child, not archived, not the workbench's own conversation, not any workflow's `homeSessionId`, and not a blank draft unless it is the one on screen right now (otherwise every visit to the workbench would leave a nameless empty row behind). Rows sort by `updatedAt`, most recent first. This is where a displaced workbench draft now lands, instead of simply receding with nowhere to find it again.

- **A row shows the conversation's own durable title, or fixed copy** — never the session list's `displayTitle`, whose lower rungs are a directory basename and then a bare session id. Both are the vocabulary this console exists to keep off the screen, and a bare id is not something the banned-word check can catch.
- **Five rows, then 显示更多** — the shipped browser's own collapsed limit. Whether the rest was asked for is remembered alongside the fold state.
- **移出列表 archives, it does not delete** — it calls `ctx.workspaces.archiveSession`, and the session log survives on the host. Because this console offers no way back to an archived conversation, the control asks for a second click in place before it commits — and the armed row is laid out so a second click cannot commit by accident: 确定移出 opens to the left, and the row's right edge, where the 移出列表 icon just was and where a double click's second press lands, becomes 取消. Escape disarms as well, from wherever the focus went, as does folding the section shut. Taking off the conversation that is open on screen lands the shell back on 工作台: this console always rests on a conversation, and the sidebar's own load-time landing is a one-shot that never fires a second time. A refused archive is reported inline in this section, in its own fixed copy ("移出失败，请稍后重试"), rather than as the workflow list's own save failure; the refusal's own text comes from the host runtime (`session archive failed: …`) and carries the vocabulary this console keeps off the screen, so it goes to the browser console only.
- **A saved workflow leaves this section by itself** — saving binds its `homeSessionId`, which is one of the five exclusions. No second bookkeeping mechanism.

The durable document (`{workflows, groups, workbenchSessionId}`) lives in this package's own settings namespace and is served over one same-origin route:

- `GET /server-menu/workflows` — the current document, `cache-control: no-store`.
- `POST /server-menu/workflows` — **merges** the posted patch (`{workflows?, groups?, workbenchSessionId?}`) into the current document rather than replacing it wholesale, so a caller changing only one field never has to resend the others; each array it does carry is replaced whole. Every rule above (a duplicate workflow id, a pre-view `navSnapshot`, a group constraint) is refused before it commits, by the route's `validate` hook and this package's invariant.

The browser cannot call `settings.*` RPC directly — it is a loopback-privileged method group, and a request arriving through a reverse proxy is refused with 403 by the shell's own trust fence rather than by any rule in the proxy's configuration — so this package's node half is an optional child that registers the route only when both `ctx.settings` and `ctx.webServer` are composed; without them the sidebar itself still works (navigation is unaffected), just with nothing to show or persist under 我的工作流.

<a id="selection-highlight"></a>
## Selection highlight

Exactly one row marks the current session, favoring specificity: a workflow whose `homeSessionId` equals `useSessions(state => state.current)` draws the highlight; the workbench draws it only when the current session is its own `workbenchSessionId` **and** no workflow already binds that session — a workflow's binding always wins over the workbench, so a session named by both never lights up two rows at once. Each row carries a boolean `data-active` attribute; `ServerSidebarRoot.module.css` styles the workbench's active state with an inset brand-colored ring (`.workbench[data-active='true']`) and `SidebarGroups.module.css` styles a workflow row's with the same `--dsw-alias-interactive-bg-active` fill `dsh-client-ui-trajectory` already uses for its own selected-row state, keeping this package's palette to tokens already established elsewhere in the product.

<a id="identity-and-sign-out"></a>
## Identity and sign-out

The footer names the person the deployment signed in, and offers the one control that undoes it. Neither half is model-visible: no session event carries the name, and nothing here reaches a model request.

**The name is a display copy, not authority.** `client/identity.ts` reads the deployment's access token out of `localStorage.accessToken`, drops the login page's `Bearer` scheme, decodes the payload without verifying anything, and shows the claim named by `Config.displayNameClaim` (`login_uname` for the sign-on this deployment runs). A token nobody can read, a claim that is absent or not a string, and a page with no token at all all render the anonymous placeholder ("用户" / "User") instead. Nothing is gated on this value — the party that verifies the token is the reverse proxy in front of this process, which has already decided who is on the other end by the time a page loads. The name follows a `storage` event, so a tab that signs a different person in moves it without a reload.

**Signing out runs five steps, in this order, every one of them attempted whatever the one before it did** (`client/sign-out.ts`).

1. **Stop the work in progress** — the open conversation, and every other one the session list reports as `running`, each through the same session-scoped `conversation.cancel()` the shipped stop button calls. The open one is stopped whether or not it carries that bit; an idle stop is a no-op the host answers. The wait is bounded at three seconds, so a cancel the host never answers costs the visitor that long rather than the four steps that actually drop the token.
2. **`POST /auth-gate/logout`**, so the process stops spending the token it holds. `keepalive`, because step 5's navigation would otherwise cancel a request the document owns — which is also why the sequence sends this request rather than waiting on it: a route held open until a proxy's read timeout would otherwise keep the visitor on a page whose work is already stopped and whose token is one step from being dropped.
3. **Remove the login page's own storage keys, by name** — never `localStorage.clear()`, which would take the shell's private keys and any other application served from this origin with it.
4. **Clear the mirror cookie**, under the exact `Path`, `Secure`, and `SameSite` auth-gate wrote it with — the `Path` being the deployment prefix this shell is served under, which both packages resolve the same way (`resolveClientBase`).
5. **Leave for the login page**, carrying `?redirect=` and the address to come back to: the current one with the login page's own credential parameters (`token`, `token4a`) taken out of its query and its fragment alike, every other parameter left byte-for-byte as it arrived, and the fragment's own route kept — these pages are hash-routed, so the fragment is the address.

A refusal at any step is a `console.warn` and nothing more: the visitor is leaving either way, and a step that could not run is not a reason to leave the rest undone.

**Literal copies, not imports.** The `Bearer` strip, the JWT decode, `/auth-gate/settings`, `/auth-gate/logout`, the cookie line, and the return-address rule are copies of [`dsh-experimental-auth-gate`](../auth-gate/README.md)'s own, for the reason `client/nav-catalog.ts` copies the two catalog routes: a cross-package value import is not this repository's sanctioned way to couple two client-adjacent plugins, and this sidebar must also work in a composition that does not compose auth-gate at all. Both packages are fork-owned together and must keep these six agreements in step, including how each is addressed: both routes are requested through `clientUrl`, and the cookie is cleared at the same deployment prefix auth-gate wrote it under.

<a id="de-terminology"></a>
## De-terminology

Decision ② bans 会话/新会话/session/workspace from every user-visible string this composition renders, on top of the whole-shell restructure above. Seven more shipped surfaces name that vocabulary or hand an end user a permission switch this product does not offer: four go the same way ui-sidebar/ui-workspace do — by disabling the row in the customer overlay, never by patching the row's own copy — one is kept out of the composition by isolating the service it registers through, and the two with no channel of their own are hidden by a scoped CSS injection (see below):

| Surface | Row disabled | Note |
| --- | --- | --- |
| Chat/Trajectory tabs | `ui-trajectory` | The Trajectory tab is `ui-trajectory`'s own registration; removing it leaves a single-option tab switcher, which renders as no tab control at all. |
| Session log download button | `session-log-download` (`@deepseek-ai/dsh-session-log-export`) | The download dialog itself also carries "Session" copy; disabling the row removes both the trigger and the dialog. |
| Model selector | `ui-model-selection` | Also the composer's own "unselected model" block (`ConversationRoot.tsx`'s `useComposerBlock`) — with the row gone, no plugin ever arms that block, so the composer stays usable with no model picker at all. |
| Permission default in Settings → General | `ui-permission` (`@deepseek-ai/dsh-client-ui-permission-presets`) | The row writes `permission.defaultPreset` for later sessions, outranking the composed default through the Settings seam. That package's only other registration is the `/permission` popup decoration, which has no host command left to decorate. |
| Turns/steps status row | *(no disable row exists)* | `StatsLine` is a shipped `ui-conversation` component with no Config flag and no disable seat of its own — see below. |
| Permission preset chip | *(no disable row exists)* | `PermissionSelect` is `ui-conversation`'s own composer control, fed by the `permission-presets` projection the Host still serves; its "Workspace Write" label is title-cased from the preset's machine name, so no locale entry reaches it either — see below. |
| `/permission` | *(no disable row exists)* | `@deepseek-ai/dsh-permission-presets` registers the command under `ctx.inject(['commands'], …)`, and the registry itself has four other consumers this console composes, so the overlay isolates the name on that one row instead — see below. |

The turns/steps row has no official channel to remove, so this package falls back to a scoped CSS injection: a client-only effect (`terminology-guard.ts`) inserts `[data-composer-card] + * { display: none !important; }` into the document head. `data-composer-card` is the composer's own card wrapper (`InputBar.tsx`); its next sibling is the composer's footer/dock region, which in the shipped composition carries only `StatsLine` (`conversation.composer.dock`, order 0) — so this hides exactly the turns/steps row today, but it is a DOM-order-coupled selector, not a Config flag: a future plugin registering into `conversation.composer.dock`, or a DOM restructure of the composer's own markup, would silently change what this rule hides without either package's tests catching it from the other side. It is pinned by this package's own e2e scenario (`apps/web/tests/server-sidebar.e2e.ts`), which fails loud if the row becomes visible again.

The permission-preset chip has no channel either, and the preset itself is a Host row this composition keeps, so the same effect adds `[data-composer-card] [class*="modes"] [class*="trigger"] { display: none !important; }`. `PermissionSelect` seats in `InputBar.tsx`'s `modes` row the moment a conversation carries the `permissions` projection, labels itself off the preset's own machine name, and opens a menu offering every other preset including full access. The rule couples on two CSS-module class substrings, the only coupling `[hash]_[local]` emission leaves available: `modes` (`InputBar.module.css`) for the seat's own row — the scope that keeps the rule off the other `trigger`-named controls the same card carries, the trailing context meter and the input mirror's own chip/text-reference decorations — and `trigger` (`PermissionSelect.module.css`) for the chip button with its icon, label, and chevron. Renaming either class, or reseating the chip outside that row, un-hides it with no compile-time signal on either side; the e2e's whole-page banned-word screen is what catches that. The plan chip sharing the row keeps rendering — "Plan" is neither banned vocabulary nor internal status, and that chip is the only control that leaves plan mode — and the preset in force is untouched: the Host keeps whatever `permission-presets` row the deployment composes. Hiding the chip closes one permission surface of three; the overlay closes the other two, below.

A console offers an end user no permission switch of any kind (product decision, 2026-09-07), so the overlay closes the remaining two surfaces at the composition level. The Settings → General default row has a row of its own — `ui-permission`, disabled outright. `/permission` has neither a disable row nor a Config flag: `@deepseek-ai/dsh-permission-presets` registers it under `ctx.inject(['commands'], …)`, and dropping the `commands` registry is not available either, because the switcher strip's tab and close buttons, the sidebar's navigation rows, `show_component`'s press return path, and `SessionFace.command()` all inject it. The overlay writes `isolate: { commands: true }` on that one row instead: the loader mints an entry-local realm for the name, nothing implements `commands` there, the injected child never activates, and the command is never registered — so `commands.list` never names it and the slash menu has no row to filter. Isolation is per entry, so every other consumer keeps the registry the base bundle composes, and nothing else on the row is isolated: the preset table, the `permissions` projection, the Settings section the package installs, and enforcement itself are unchanged. With all three write paths gone the overlay states the effective preset rather than leaving it to be derived — `defaultPreset: workspace-write`, the preset the composed sandbox and approval defaults already resolved to, stamped onto every new session by the package's own `pinInitialPermission`.

That value is a floor, not a constant. `defaultPreset` reaches the service as the composition `base`, and settings resolve schema defaults, then `base`, then the user layer (`packages/settings/settings/src/index.ts:739`), so a `permission.defaultPreset` already stored in the deployment's settings document still outranks it and is what `pinInitialPermission` stamps. Disabling `ui-permission` closes the surface that wrote that key; it does not erase a value a visitor stored before the upgrade, and no UI is left to show or change it. A deployment clears it by deleting the section — a `permission:` key with an indented `defaultPreset: <name>` under it — from `<harness home>/settings.yaml`: `$DSH_HOME/settings.yaml`, else `~/.dsh/settings.yaml`, else whatever `path` the `settings-file` row configures (`packages/settings/settings-file/src/index.ts:23-24,51-57`). No composition key does it for them: `base` is the only layer a cordis.yml row supplies, and `SettingsScope.replace({})`, the reset, is an owner-side runtime call. The `remote.settings` write path also stays reachable from a browser — a property of a console that runs with no in-app auth, not something this overlay changes.

<a id="business-content-only"></a>
## Business content only

The conversation column shows what the visitor asked for and what came back, and nothing about how the run got there (product decision, 2026-09-07). `dsh-client-ui-chat` has no channel for that: its `transcriptView` setting is a closed `'normal' | 'compact'` union already sitting on its most-hiding value, `compact` folds process rows behind a disclosure rather than removing them, the fold reaches neither a running turn nor a session whose older history has not loaded (`ChatNodeSeat.tsx`'s `processWindowReady`), and no composition can pin the value — `ui-chat` supplies neither a `Config` nor a settings `base`. So these surfaces go the way the turns/steps row goes, through `terminology-guard.ts`'s stylesheet.

The kind rules are the cheapest and most stable couplings in the file: `data-chat-flow-kind` is a real attribute, not a class substring or a DOM position, so the only way to break one is an upstream kind rename. The e2e asserts each row is present **and** computed `display: none`, not merely invisible — `compact` already folds process rows behind `hidden="until-found"`, which reads as invisible too, so a present-and-invisible pair alone would pass with every rule here deleted. Command rows take three kinds because `ui-chat` splits one surface by how the command arrived: `manual-compaction` is `/compact` with its compaction transaction, `compaction` the automatic one, and `command` everything else — hiding only `command` would leave `/compact` on screen. Inside this composition these rules supersede [`content-frame`](../content-frame/README.md)'s and [`content-column`](../content-column/README.md)'s own narrower `:has([data-slot="conversation.chat.commandview"]:empty)` rules, which still carry every composition that does not install this guard. `context` and `model-retry` are the same judgment applied twice more: a `context` row is a `user/message` whose source is not the user, so it is machinery the run needed rather than something the visitor wrote, and a `model-retry` row is internal status — the retry either succeeds, in which case the answer is what the visitor reads, or it exhausts, in which case the kept `turn-error` row says so. `ChatNodeDataMap` is merge-extensible, so the union is open and a kind this table does not name would render unchanged: `command-input` and `workflow-run` are `dsh-client-ui-goal`'s and `dsh-client-ui-workflow-run`'s own contributions, both composed by the web bundle and disabled by no console overlay, and `unknown` is `ui-chat`'s registered fallback, which draws the raw JSON of an append-surface event no Definition claimed. The package's unit spec therefore lists every kind as hidden or kept and **fails to compile** if the composed union gains one that is in neither list.

What stays is the business record: the visitor's own messages, the assistant's text, `turn-error` and `turn-max-tokens` (notices a reader has to act on), the reply footer's own controls — copy, like/dislike, branch, and the end-of-turn clock — and its produced-files tail, `dsh-client-ui-deliverables`' list of what the run wrote. `content_read`'s card is the one deliberate loss inside a kept surface: the content column already shows the page that row would describe. Approval cards are out of reach of every rule here by construction — `dsh-client-ui-approval` registers into `conversation.composer`, so an approval takes the composer over and never becomes a flow row at all.

The footer rule takes the two metric pills and nothing else in that row, because copy, like/dislike, branch and the clock are the visitor's own affordances rather than process reporting. Neither pill carries a `data-*` attribute — `TurnUsagePanel.tsx` puts one on each opened dialog and none on either trigger — so the rule couples on `TurnUsagePanel.module.css`'s `.trigger`, the local name both panels give that button, and reaches the pill's wrapper through it with `:has(> …)`, so the pill leaves behind neither a flex slot nor the `.root + .root` margin rebate that hiding the button alone would. `aria-haspopup="dialog"` looked like the semantic handle and is not one: `dsh-client-ui-message-feedback`'s note-open button carries it too, in this same row, as part of the like/dislike affordance that stays. The class substring is therefore this rule's fragility, the same shape as the permission chip's; the e2e reads both halves — the pills gone, copy, branch and the clock still on screen — so either direction of that drift turns the gate red.

The composer placeholder is swapped through the same `::after` technique the hero headline uses, but it takes two rules, because `InputBar.tsx` renders one `[data-composer-placeholder]` element for every state of a placeholder ladder longer than it looks (`InputBar.tsx:467-476`: the owner prop first — hero copy, the inert composer's diagnostic, a raised block's reason — then `parentOffline`, then any other disabled state, then the steer-queue hint, then plan mode, then the default). The rules split it on what the composer can do. **Accepts input** reads 说说要做什么, the invitation. **Refuses input, with a session** reads 暂时无法输入 — that is where `placeholder.unavailable` (会话不可用 / "Session unavailable") and `placeholder.parentOffline` (父会话已离线…) land, banned session vocabulary decision ② reaches no other way since both belong to `ui-conversation`'s own locale namespace; the swap keeps what a visitor needs and drops the word. **The inert composer with no Workspace** is left alone: its placeholder is the only thing saying the composer is unusable and why (see Known Limitations). `data-phase` is `input?.phase ?? 'inert'` (`InputBar.tsx:533`) and `aria-disabled` is `editorDisabled` (`:534`), which every refusing state sets and the workspace-picker trigger deliberately does not — that asymmetry is what makes the three-way split expressible. The swapped copy carries `ui-conversation`'s own font-size token rather than a fixed pixel value, so it keeps following the Settings font-size preference. Nothing else was available: the `placeholder` prop of `conversation.composer.bar` is supplied by `ConversationRoot` alone, and the locale registry rejects a second registration for a namespace/locale pair it already holds. The sibling `[data-composer-input]`'s `data-placeholder` and `aria-label` are untouched — see Known Limitations.

The running-turn indicator stays on screen — a visitor must see that work is under way — but its copy and its paint were vendor identity rather than status: `chat.deepDiving` is 深度求索中..., the vendor's own Chinese brand name, painted through a `--dsw-static-deepseek-500/200` gradient clipped to the text. The rule re-texts it to 正在处理… and neutralises the gradient to the theme's ordinary label colour. It scopes as `[data-chat-flow] > [class*="turnStatus"]`: `ChatView.tsx` renders the indicator outside every `ChatNodeSeat`, which is both why no kind rule reaches it and why the direct-child combinator keeps the rule off the nested clock span, which sets its own size and colour and still appears after fifteen seconds.

Every rule is pinned twice. `packages/experimental/server-sidebar/tests/terminology-guard.client.spec.ts` asserts each as the literal selector it couples on, and `apps/web/tests/server-sidebar.e2e.ts`'s business-content scenario seeds one closed turn carrying every hidden row plus a produced file and a standalone command, then reads the assembled page: each hidden row present and `display: none`, the produced-files tail visible, an approval card visible with no `data-chat-flow-kind` anywhere inside it, the placeholder's rendered `::after` in both composer states, and the indicator visible, re-texted, and off the gradient.

## Brand and hero facade

Three more surfaces carry DeepSeek's own product identity or internal-status copy rather than banned vocabulary, and are replaced or removed for the same customer-form reason as De-terminology above:

- **Sidebar brand row.** `sidebar.brand.mark` renders with no fallback at all (previously a fish icon); `sidebar.brand.name`'s fallback is plain text — locale key `brand.name.fallback` ("工作台小助手" / "Workbench Assistant") — with no build-revision badge. `@deepseek-ai/dsh-client-ui-brand-official` (an official-build-only occupant of both slots, plus `conversation.hero.brand.mark`) is disabled outright in the customer overlay; this package's own `client/index.ts` also takes over `conversation.hero.brand.mark` at priority -1 (the slot's shadowing rank — ascending, lowest renders — with an empty component), so a deployment that forgets to disable `ui-brand-official` still gets this package's no-icon hero mark rather than the official one.
- **Conversation hero chrome.** The blank-draft hero headline (`dsh-client-ui-conversation`'s `HeroShell`/`ConversationRoot`) carries a fish icon, a "PREVIEW" status pill, and a workspace-picker-plus-agent-preset row — none of it has a Config flag or a disable seat of its own, so `terminology-guard.ts` extends its CSS injection to also: hide the (now slot-empty) fish hitbox and the preview badge; collapse the headline text to `font-size: 0` and paint this package's own brand copy over it through a `::after` pseudo-element (the original headline text node stays in the DOM and the accessibility tree unchanged — see Known Limitations); and hide the workspace-picker row outright. A customer deployment fixes its model and credential at the deployment layer and never shows a DeepSeek-internal notice, so the customer overlay disables the whole row rather than pre-acknowledging a version (product decision, 2026-09-06). With no step left, `SettingsRoot`'s onboarding list renders nothing.

<a id="composition"></a>
## Composition

The plugin is not part of any shipped bundle. `overlay/customer.patch.yml` is the full customer-form overlay: it disables `ui-layout`, `ui-sidebar`, `ui-agent-preset`, `ui-brand-official`, `ui-cordis`, `ui-trajectory`, `ui-model-selection`, `session-log-download`, `ui-settings-models`, and `ui-permission`, and inserts `server-layout`, `content-surface`, `content-column`, this package, and the `library-skills` row (an isolated `skill-filesystem` provider over `@deepseek-ai/dsh-experimental-library-skills`'s bundled `skills/`). It also reconfigures one shipped row rather than disabling it. The `permission` row does three things: it restates the preset table with customer-facing names, because the shipped `workspace-write` name is what the composer's access chip displays and the chip falls back to a host-supplied name verbatim whenever it differs from the built-in default; it names the `defaultPreset` a new session is pinned to when the settings document stores none (see De-terminology above); and it carries `isolate: { commands: true }`, which is what keeps `/permission` unregistered (see De-terminology above). `packages/experimental/server-sidebar/tests/customer-overlay.client.spec.ts` pins all three, and pins that the three console overlays under `apps/web/tests/` still carry the same row. It does not insert `content-frame` or `component-surface` — the deployment's own page catalog and view catalog are composed separately, alongside it, since each carries deployment-specific configuration this overlay cannot assume. It does not insert [`auth-gate`](../auth-gate/README.md) either, and that row is what the footer's sign-out button needs: composed without it, the button still renders, but pressing it reports the missing login page to the console and stays put. Both overlays carry this package's one required `config` field (see Config above); a row composed without it fails at load. Apply it with `dsh --profile <name> --patch <path>`; every package the overlay names must be resolvable from the profile directory, which for an out-of-tree plugin means `dsh plugin --profile <name> add <path>` or an equivalent link — release bundles must not declare an experimental package. Five packages have to be installed that way: `dsh-experimental-server-layout`, `dsh-experimental-content-surface`, `dsh-experimental-content-column`, this package, and `dsh-experimental-library-skills`. The last one is named by a row's `bundledSkillDir` expression rather than by a row's plugin name, and it is no less required: a profile missing it throws `MODULE_NOT_FOUND` while the row loads, the entry tree never settles, and **the console does not boot**.

## Known Limitations and Deferred Work

<a id="known-limitations-and-deferred-work"></a>

- **Literal 240px is not independently enforced.** This shell never fixes an inline pixel width; it renders at whatever `width` its owner (`dsh-experimental-server-layout`) hands it, and never toggles collapse. `server-layout`'s frozen 3:16:5 track ratio happens to equal exactly 240px at its own 1920px reference frame width (`1920 * 3/24 = 240`), but at any other frame width the column is proportional, not fixed. Making it literally fixed would require changing `server-layout`'s own frozen, deliberately non-configurable geometry, which is out of this change's scope.
- **Decision ③'s user-message check is a paged-window approximation.** Visibility of "存为工作流" reads `useSession(s => s.chat.legacy.nodes)`, the same paged conversation-snapshot window `StatsLine.tsx` reads from — a user message far enough back to have paged out of the window would not be found. A whole-log check would need a durable projection this v1 does not add.
- **The turns/steps status row and the permission-preset chip are hidden by coupled CSS selectors, not Config flags.** One couples on DOM order, the other on two CSS-module class substrings; see De-terminology above for the exact fragility of each and what pins them.
- **A stored `permission.defaultPreset` outranks the overlay's.** The overlay supplies the composition `base`, which settings resolve below the user layer (`packages/settings/settings/src/index.ts:739`). A console upgraded from a build whose Settings → General row was still live carries whatever preset a visitor picked there, with no UI left to show or change it; clearing it means editing the deployment's settings document — see De-terminology above.
- **Typing `/permission` still sends a message.** With no host descriptor and no client contribution under that name, the trigger's Enter adjudication resolves nothing and the composer's default sink submits the line as ordinary text: `/permission read-only` lands on the log as a `user/message` and opens a turn, the model reads those two words, and nothing else happens — no `permission/preset` event, and the access chip's `aria-label` still names the pinned preset. Closing that would need a refusal the command layer cannot express: a registry entry can only add a row, never claim a name it declines to serve.
- **`navSnapshot` captures only what the 导航 menu lists.** `captureNavSnapshot` keeps an entry only when the merged catalog carries its `{kind, entryId}`, so three things in an ordinary content column are dropped from the degraded re-creation: a chart the agent drew, a component the model showed on its own initiative with `show_component` (its id is free-form model output, not a configured view), and a page or view the deployment configured when the entry was shown but no longer configures at save time.
- **A stored view is replayed as it is configured today, not as it looked when saved.** `navSnapshot` records a view's id, not the spec behind it — replay runs `show-content-view`, which reads the deployment's current `views` config. A view the deployment has since edited comes back changed, and one it has since removed reports "没有这个视图。" and is skipped. The session log of the original conversation still carries the spec as the user saw it (that is what `content-component/shown` records); a workflow's snapshot is a list of stops, not a copy of what was at them.
- **The green-dot mechanism reuses `completed` rather than new bookkeeping, and is unit-tested only.** It is an exact match for "finished while not selected and not yet opened," but proving it end to end would require a real agent-loop running→idle transition while unselected — `SessionManager`'s `running` bit is a host-frame push tied to actual execution, not something a log-only append can fake. This scenario's own e2e suite issues no model calls (matching its established design), so the mechanism is pinned by `packages/experimental/server-sidebar`'s own unit tests instead.
- **Rename/remove use hover-revealed icon buttons, not a native context menu.** A v1 downgrade the task's own brief explicitly permitted ("若实现体量失控，降级为右键菜单「上移/下移」") for reordering too, until reordering moved to native HTML5 drag-and-drop; the context-menu downgrade for rename/remove remains, since a second interaction pattern for two occasional actions is still not justified on its own.
- **`ui-workspace` is composed, and only a CSS rule keeps its hero picker off the page.** It cannot be disabled: `dsh-client-ui-conversation` injects its `uiWorkspace` service, so a composition without it never activates the conversation column at all. Its `sidebar.workspaces` half is inert once this shell drops that slot (`ctx.slots.inject` just never fires — see Replacing the shipped sidebar above), but its `conversation.hero.workspace` registration lands, and `terminology-guard.ts`'s `heroWorkspaceRow` rule is what hides it — a class-substring coupling that breaks silently if that class is renamed. A zero-Workspace fresh install still leaves a page or workflow click a contained no-op (see Navigation above) — an existing, already-accepted edge case carried forward from the prior favorites-based design, not new here. The workbench's own load-time auto-open goes further and never even attempts in this case (see Workbench above), waiting indefinitely for a Workspace rather than firing once and warning.
- **With no Workspace connected, the composer names one.** `ConversationRoot` renders its inert composer under `placeholder.workspace` ("Choose a workspace to start"), the one piece of banned vocabulary this package cannot reach. It is not chrome a CSS rule should hide — the composer is genuinely unusable in that state and the placeholder is the only thing saying so — and it is not renameable from a composition: it belongs to `dsh-client-ui-conversation`'s own locale namespace, and the locale registry rejects a second registration for a namespace/locale pair it already holds, so no plugin can shadow another's key. Closing it means either a deployment that always has a Workspace (the state the whole console already degrades to a no-op in — see Navigation above) or an override seam in the locale registry. An e2e scenario pins the leak to that one placeholder so a second one cannot appear unnoticed, and a second assertion in the same scenario pins the other half: the Business content only placeholder swap deliberately does **not** reach this state, so what a visitor sees here is still this sentence and not an invitation to type.
- **The hero headline's original text node survives in the DOM and the accessibility tree.** `terminology-guard.ts`'s `::after` swap only changes what the headline paints (`font-size: 0` on the real text plus a pseudo-element carrying this package's own copy); a screen reader or any DOM-text query still finds `dsh-client-ui-conversation`'s own English/Chinese headline string, not this package's brand copy.
- **A hidden row contributes nothing to page text, which is both the point and the cost.** `display: none` takes a subtree out of `innerText`, out of the accessibility tree, and out of browser find-in-page, so a screen reader gets the same column a sighted visitor gets. But this package's two whole-page banned-word screens (`workspaceWordsInChat` and the landing-page `body.innerText()` scan in `apps/web/tests/server-sidebar.e2e.ts`) read rendered text, so every rule added under Business content only widens their blind spot by exactly what it hides: banned vocabulary that lands only inside a hidden process row would pass both.
- **The refusing composer's own reason is replaced, not translated.** `placeholder.unavailable` (会话不可用 / "Session unavailable") and `placeholder.parentOffline` are `dsh-client-ui-conversation`'s copy for a session whose input face is absent, removed, or whose continuable parent is offline. All three are reachable — the first on every conversation open and switch, in the window before the input face arrives — and all three carry decision ②'s banned vocabulary in a namespace no plugin may register into, so the guard swaps the rendered text to 暂时无法输入 rather than leaving the word on screen. What that costs is the distinction between them: a visitor sees the same sentence whichever state it is, and a raised composer block — dead in this composition, since `ui-model-selection` is disabled — would have its own reason masked the same way if a deployment brought it back. The upstream `data-placeholder` and `aria-label` still carry the original string, as with the invitation copy above.
- **The composer placeholder's accessible name is still the upstream string.** The `::after` swap changes only what the `aria-hidden` placeholder element paints; the sibling `[data-composer-input]` keeps `dsh-client-ui-conversation`'s own `data-placeholder` and `aria-label`, so a screen reader announces "Message or run a task... / commands, @ files or sessions" — banned vocabulary included — while the page reads 说说要做什么. Closing it needs the same locale override seam the hero headline entry above needs. Leaving the attribute in place is also what keeps every `[data-composer-input][data-placeholder=…]` locator under `apps/web/tests` working.
- **Signing out does not tell the deployment's own sign-on anything.** It drops the token everywhere this browser and this process hold it, and sends the visitor to the login page; the token itself stays valid on the issuer's side until it expires, because this package knows no revocation endpoint. A deployment that has one calls it from step 2 of the sequence above.
- **There is no confirmation step.** One click stops the work in progress and signs the visitor out. Stopping a turn preserves the conversation and its pending inbox work (that is what `cancel` means here), so the cost of a mis-click is a reopened login page, not lost work.
- **The displayed name is a non-authoritative copy.** It is decoded in the browser from an unverified token; anyone able to write `localStorage` on this origin can change what the footer says. Nothing is gated on it, so what that buys is a wrong name.
- **The mirror cookie's `Path` is resolved, not agreed.** Both packages narrow it to the deployment prefix by reading the same page fact rather than by sharing a value, so a proxy that serves the two halves under different prefixes would have the removal line write a second, empty cookie and leave the mirrored token in place. Nothing detects that; the pairing is proved by a unit test comparing this package's line against auth-gate's own.
- **The stop sweep trusts `SessionSummary.running`.** A conversation whose running bit has not arrived at this browser yet, and which is not the open one, is not stopped. The host-side turn keeps running until it finishes on its own.
- **The sign-out sequence has no browser-level evidence.** The Playwright scenario asserts that the control renders and that the footer band fits it, and stops there: this package's scenario composes no `auth-gate` row (that package gates the whole page on a token, which every other assertion in the scenario would then have to carry), so "click sign out, the cookie is gone, the login page is showing" is proved by unit coverage over the injected browser rather than end to end.
- **The settings route assumes an HTTP carrier.** The browser half fetches `/server-menu/workflows` — the route the node half registers, resolved against the page's deployment base. A transport that serves the shell without exposing the harness over HTTP would fail the row, the same way content-frame's settings route would.
- **An unclean-by-content draft is not actually displaced.** `isCleanWorkbenchDraft` refuses to reuse a draft whose content column shows anything but the home page, but the create path it falls through to resolves through `resolveOrCreateSession` → `connectWorkspace`, whose own reuse scan hands back the first blank session already in the Workspace — and a draft that has run no turn is one of those. It is normally the draft itself; a Workspace holding another blank session ahead of it in the session list hands that one back instead, and `workbenchSessionId` follows. Either way the visitor lands on the home page again on a conversation that already existed, with the page they had navigated to still in that draft's switcher strip. Minting a genuinely fresh conversation here would need a create path that bypasses that scan for this one caller, which also decides how many abandoned blank conversations a navigate-then-click cycle is allowed to leave behind — a product decision this slice does not take.
- **Cross-group movement has no keyboard path, and group order has no interface at all.** Both ways to move a workflow need a pointer or a touch: the drag, and the row's 移动到… menu, whose list `Menu` portals to the end of `document.body` without taking the focus, answering arrow keys, or holding Tab inside it — so its rows sit behind every other focusable element on the page. Tab reaches the trigger and stops. Closing that gap means a focus-managed dropdown of this package's own, or a change to the shared primitive; neither is in this slice, and the focus leaving the row at least closes the list rather than leaving it standing with its trigger hidden. Reordering the groups themselves is not reachable at all — a group takes its `order` at creation, and only pinning moves it after that.
- **The temporary section has no identity predicate.** Its five membership rules filter the whole conversation directory this process serves; none of them asks whose conversation a row is. What makes that "this person's own conversations" is the deployment shape — one visitor per process, per `$DSH_HOME` — and nothing in this package enforces it. A composition pointing two people at one process would show each of them the other's rows.
- **移出列表 is one-way for the person using the console.** It archives, so nothing is lost on the host, but this shell has no unarchive control and the shipped browser's own is not composed here. A row taken off the list does not come back.
- **The temporary section derives over the whole session directory.** `session.list` returns everything (its v1 has no paging), so a very long history is filtered in the browser on every relevant change. The five-row cut shortens what is drawn, not what is computed.
- **A row's relative time does not tick.** It is computed at render, so "刚刚" stays until something else re-renders the section.
- **Not covered by an assembled snapshot.** The browser evidence is a Playwright scenario against a real composition; the snapshot lanes replay the shipped composition, which does not compose an experimental row.
