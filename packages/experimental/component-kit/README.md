# @deepseek-ai/dsh-experimental-component-kit

English | [中文](README.zh.md)

## Summary

The component row behind the content panel's `component` kind: six components, each a host definition saying what a call may send it and what comes back, and the React renderer that draws it. It declares no slot and knows no layout. A placement package decides where a block is drawn; this row decides which blocks exist and what they look like.

Both halves register into [`component-surface`](../component-surface/README.md)'s catalog — the node half into `ctx.componentCatalog`, the browser half into `ctx.componentRenderers` — so a deployment that composes the placement row without this one offers no component at all and is offered no `show_component` tool. Neither registration requires the other row: each waits for the registry through `ctx.inject`, so composition order is free.

The node half also serves one route. It carries the single value the browser half cannot compute for itself — `bizBasePath`, the path prefix under which the `toy.data-page` component requests its table — and the row's `cordis.yml` entry is also what makes the browser bundle discoverable through `dsh.client`.

<a id="what-this-row-registers"></a>
## What this row registers

Two kinds of component live here. One is written in this repository as ordinary React and depends on nothing else. The other is a Vue 2 component compiled outside it, drawn through a bridge onto a Vue runtime another row owns. **How the originals get here**, below, records the whole of what that costs. One of those originals also requests its own data, and **The data page** records the whole of what *that* costs.

Six components, on both halves, as one contribution each. The node half hands `ctx.componentCatalog.register` the definitions and the package that wrote them, read from this package's own `package.json` rather than written down beside the call, so the catalog records which package contributed each component and a second package claiming one of these ids is refused by name. The browser half hands `ctx.componentRenderers.register` the same definitions paired with the React component that draws each, together with this row's own translate — the renderers keep their copy in this row's dictionary while the seat keeps its own.

The two halves read one list of definitions, so a component cannot arrive on one side and not the other. `componentKitRenderers()` pairs that list against the renderer table and refuses at registration when a definition has nothing to draw it, which is the check that used to be a `satisfies` against a derived id union: a catalog id is a runtime value now, and there is no literal union left to pin against.

Reaching the placement package's browser registry is a value import across packages, so this row declares `dsh.client.external: ['@deepseek-ai/dsh-experimental-component-surface/client']` and the loader answers the require from that row's own bundle.

<a id="what-a-renderer-receives"></a>
## What a renderer receives

Every component in the row takes the same six props (`ComponentRendererProps`, declared by the placement package and narrowed here to this row's translate): `nodeId`, the block's identity within one placement; `props`, the block's properties as the placement package's schema accepted them; `onAction(actionId, payload)`, where a user gesture goes, carrying the action's id and the properties that action declares; `onOutput(outputId, value)`, where the block's own current reading of itself goes, for the blocks beside it to take a property from; `state`, how far the gesture this block last reported got (`idle` / `sending` / `sent` / `queued` / `refused`); and `t`, this row's translate.

`onAction` and `onOutput` are different things and a component keeps them apart. A gesture is news: something the placement package records and the agent may read. An output is not — nothing is recorded, nothing reaches the agent, and a block that publishes one has still reported nothing. What a component publishes is republished on every change, including the change back to nothing, so a block fed by it can go back to waiting; every value must survive `JSON.stringify` and must be treated as read-only, because the placement package hands it straight to another block as a property. Which outputs a component publishes is the placement package's catalog to declare, exactly as for an action.

That is the whole contract. A renderer holds no ctx, subscribes to nothing, keeps no memory of its own gestures, and performs no navigation, no request, and no write — it draws what it was given, says what the user pressed, and is told what became of it. The placement package decides whether anything comes of that and where `state` is folded from.

`state` is one value for the whole block, so which of a component's gestures moves it is the placement package's decision rather than this row's. The console's placement moves it for the gesture a block was placed to receive and for no other, which is what lets a table keep taking ticks and sorts while an `operation` is still travelling, and a filter bar keep its submit button alive while the user types. A renderer that gates every one of its controls on `state` would be gating them on whatever that placement decided.

Properties arrive typed as `Record<string, unknown>` because one table type serves every component, so each renderer narrows the properties it declared. The narrowing is not a defense against the caller: the block was already checked against the catalog schema that admitted it.

<a id="copy"></a>
## Copy

The row owns one dictionary namespace, `componentKit`, and the placement package's seat declares it at its own registration rather than adding a second namespace — which components exist and what they publish is this row's fact, so the button row's accessible name, the sentence shown in place of a component this row does not have, and the line a block draws while it is still waiting on the block that feeds it all belong here. Everything else a block displays is the caller's text.

The data page has three lines of its own, under `dataPage.*`: what a block says while the address it will request under is still being read, what it says when that read failed, and what it says when the block names no table at all. They are the row's because the read is the row's — every other component draws without it. Each cause has its own line, because telling someone whose block named no table that an address is misconfigured names a cause that is not theirs.

The four sentences a block says about the gesture it last reported are the row's own `action.*`, drawn by one shared line under every interactive component: a renderer is told its state rather than remembering, so all of them say the same thing about the same state. `el.confirm-bar` keeps a second copy of those sentences under `confirmBar.*`, because a bar answers one question once and says so in its own words.

<a id="components"></a>
## Components

- **`el.confirm-bar`** — a short prompt over a row of buttons, for putting one decision in front of the user. Properties: `title`, `message`, and `buttons` (each `{ id, label, tone? }`, tone one of `primary` / `default` / `danger`). Pressing a button reports the `press` action, whose payload is the pressed button's `buttonId`.

A bar draws the `state` it is handed and refuses further presses in every state but `idle` and `refused`, saying which of them it is in: the gesture is on its way, the agent has it, it is waiting for the user's next message, or it reached nobody. What the placement package does with a press is a whole turn away, if it earns an answer at all, so a bar that looked untouched after a click would leave a recorded press and a lost one looking the same — and a bar remembering its own click would come back untouched anyway the first time the placement unmounts it. `refused` stays pressable, because reporting it again is the only thing left to try.

- **`toy.record`** (`TcFormDetailRenderer`) — a read-only record: label/value pairs laid out in columns. Properties: `dataList` (each `{ label, display }`), `labelWidth` (a number of pixels, turned into the CSS length the component wants), and `columnNum`. It reports nothing and publishes nothing, so the action sink, the output sink and the action state go unread. The component is `TcFormDetail` from the vendored tarball, which makes this block the one that exercises the whole Vue path.

A row whose `display` is the empty string keeps its place: the component draws the label with nothing beside it, which is what an attribute the record has but does not fill looks like. `0` and `false` are values too, and are drawn as their own text. A row is dropped only when it names nothing — no `label`, or a blank one — or when its `display` is not text at all, which a validated call cannot produce and a record written by another build can.

- **`toy.table`** (`TableDetailRenderer`) — rows in columns, with what the user picked, opened, sorted, or pressed reported back. Properties: `tableConfig.gridItems` (each `{ relatedMetaAttr, alias?, isShow?, isSortable?, relatedComponent?, relatedComponentObj? }`), `displayValueList`, `rawValueList`, `selectMode` (`checkbox` / `radio`), `isNameClick`, `tableSortable`, `customOperations` (each `{ key, label }`), and `operationColumnWidth`. Four actions come back: `select` carrying `rowIndexes`, `row-click` carrying `rowIndex`, `sort` carrying `prop` and `order` (`asc` / `desc` / `none`), and `operation` carrying `opId` and `rowIndex`. One output is published on every change of selection: `selectionDetail`, the first ticked row written out as the rows a record block draws — one entry per drawn column, under the heading the user is reading and skipping a column the row carries no value for. The ticked rows in the form the call wrote them are not published beside it, because no property the placement package declares takes rows.

Every row is named by its position in `displayValueList` and nothing about the data travels back, so the placement package reads the row a gesture names out of the call the model itself wrote. The component hands its selected rows back deep-cloned, so those positions are read off the mounted instance rather than out of the event. Three of its properties are written dead rather than offered: its own modify and delete buttons are removed, because they report through an event no action here carries; its translated-value links are turned off, because nothing supplies the values they resolve through, which is also what leaves `isNameClick` as the only thing that makes a row openable; and a table offers no selection column until the call asks for one. Both the name link and a row button sit inside a cell the table reports clicks on, so the cell click behind each of them is dropped rather than reported as a second gesture. A cell click of its own is reported as an opened row only where `isNameClick` is on, which is the property that decides whether a row opens at all: a table the call left with nothing to open reports no click, and one that asked for openable rows reports a click anywhere in the row, because the component offers no event narrower than its own cell click. `state` gates the row buttons and nothing else, and the placement package moves it for a pressed row button alone: ticking, opening and sorting are the user working rather than answering, and a table that stopped taking them because one of them had been reported would be a table that stops working when it is used.

- **`el.filter-bar`** (`TuQueryCondAdvRenderer`) — a row of query conditions the user edits and sends back, in the vocabulary the rest of that system speaks. Properties: `relatedMeta`, `metaConfig.attributes` (each `{ attributeEnName, alias, dataType? }`), `attrEqEnums` (each `{ value, label }`), and `confStyle` (`{ gutter?, showMatchMode? }`, the AND/OR choice off unless the block asks for it). Pressing the button beside it reports `submit` carrying `conditions`, each `{ key, op, value }`, and — where the block asked for the AND/OR choice — the `matchMode` the user picked; a press holding no complete condition reports nothing at all. Each committed edit reports `change` carrying the `count` of conditions that now stand: the editor commits one when the user picks an attribute, picks a strategy, or leaves the value box, not on each keystroke. A filter bar publishes nothing, so its output sink goes unread: no property the placement package declares takes a condition list, and what an edit reaches is the agent alone.

The component emits nothing at all, so what the user built is read off its mounted instance through `getData()`, and the button that sends it is this renderer's own — the component's own buttons add and remove condition rows, and none of them means "I am done". `metaConfig` is passed even when the block declares none, because without it the component fetches the attribute list itself and the vendored build answers that fetch by throwing. That list is read into the component when it is created and never watched, so a call carrying a different one remounts it rather than leaving the previous attributes on screen. An attribute's `alias` becomes the `attributeCnName` the component reads, and its `dataType` — which decides whether the value is typed into a text box, a date picker, or a number input — is passed with the flag the component needs before it consults it at all. The four column widths are this renderer's, not a block's: what they hold is two lists, one value control and the component's own add and remove buttons, and the component reads every field of that layout without a guard, so what a block leaves out is filled in here rather than left undefined. A condition's value is the user's own text and is reported as data; a value that is not text takes its condition with it.

- **`el.metric`** (`TcProcessBallRenderer`) — one number over a caption, drawn as a ball filled to that number. Properties: `process` (the number, and its fill level read as a percentage), `text`, `size` (diameter in pixels), `background`, `borderColor`, `pointColor`, and `isPointShow`. It reports nothing and publishes nothing, so the action sink, the output sink and the action state go unread.

- **`toy.data-page`** (`DataPageRenderer`) — the deployment's own full data page for one table: a query panel over a toolbar, a table of results, a pager, a side card and the add and modify panels, all of which the user works in themselves. Its properties come in two groups. What the page is opened on, which a `show_component` call may write: `relatedMeta` (the table), `conditions` (each `{ key, op, value }`, applied without being shown), `matchMode`, `querySort` (`{ asc }` or `{ desc }`), `selectMode`, `isInitQuery`, and `customOperations` (each `{ name, label }`, drawn as a row button). How the page is arranged and whether it can be written in, which only a written-down page may set: `regions`, `toolbarButtons` (`add`, `exp`, `gridexp`, `search`, `clear`), `rowOperations` (`modify`), `queryExpanded`, `pageSize`, `pageSizes`, `infoCardTabs`, and `readOnly`. Twelve actions come back: `denied` (which of the two judgements refused this table to this user's account), `auth-failed` (the answer this deployment refused the visitor's credential with), `load` (the table, the columns its query scheme draws, and the rights this deployment answered with), `query` (one answered query's three counts), `select` (how many rows are ticked and what the first five are called), `cell-click` and `operation` (one row's drawn cells), `card-open` and `card-close`, `added` and `modified` (that a record was saved, and the saved row's drawn cells), and `exported` (which of the two toolbar exports was submitted, and the file type the press named). It publishes nothing, so the output sink goes unread; the action state goes unread too, because none of the twelve is an answer the block was placed to collect.

Only the properties the block actually carries reach the page, so a block that arranged nothing gets the page's own defaults — every region drawn, every toolbar button kept, and `readOnly` on, which hides the add button, the two exports and the row's modify button and passes `isReadOnly` to the originals. A `show_component` call is refused by the placement package for writing any of the arrangement, so a page the model placed is always that page. A written-down view sets them and may open the page for writing with `readOnly: false`; which of the drawn entrances this visitor keeps is the host's verdict on their rights, described under [The data page](#the-data-page), and whether a press then succeeds is the deployment's own answer to the request the page makes with the user's credential. `metaLabel`, which both sources write, is the name on the approval card and stops at the placement package. The next section is the rest of what this one component costs.

<a id="the-data-page"></a>
## The data page

`toy.data-page` is the one component here that reaches a network. It fetches its scheme, its table's dictionary, every query's rows and every save straight from the browser, carrying the visitor's own credential, and nothing on the host reads any of it.

**Its address, and why the block waits.** `toy-core` — the request layer compiled into the tarball beside the page — reads `window.$toy_env.VUE_APP_BASE_URL` once, while its own module evaluates, and that module evaluates when this row's browser bundle does. There is no moment before it in which a host could write the value. The value is judged before either half uses it — root-absolute, and then resolved with the browser's own URL parser and refused unless the origin and the path come back exactly as written, because a backslash or a percent-encoded dot segment survives a hand-written reading and still sends every credentialed request somewhere else. So the node half serves the configured `bizBasePath` on `/component-kit/settings`; the browser half reads it once as it starts and hands it to the kit's `setBizBasePath`, which rewrites both the captured default and the live request instance; and `DataPageRenderer` mounts nothing until that read has settled. No request leaves under the kit's built-in default. A read that fails leaves this block drawing the line saying its address is not configured, with every other block on the panel drawing exactly as before.

The value is a path and nothing else — root-absolute, no origin, no query or fragment, no `.` or `..` segment — judged at load by the node half and again over the wire by the browser half, because it crossed a process. Being a path, it names the shell's own origin, so what carries a request to the deployment's backend is whatever reverse proxy the console runs behind and the request spends the visitor's own token the way any same-origin request does.

**Containment.** `toy-core` appends a full-screen loading overlay and an `nprogress` bar to `document.body`, and the page raises element-ui toasts the same way; left alone, all three would land on the console shell rather than in the block. `containCrud(box)` marks the block's own container, makes it the positioned ancestor, points `nprogress` at it, and moves body-level toasts into it. It does the same for the poppers element-ui appends to the body — a select's list, a date panel, a dropdown's menu, an icon's tooltip — moving each into the box and switching popper.js's `boundariesElement` from the viewport to the box, which has to happen together: adopted without the boundary the list is still placed against the viewport and the box's `overflow` then clips it, and the boundary without the adoption puts popper.js's two coordinate systems in different ancestors. It refuses in three cases, each leaving the popper where element-ui put it: no popper.js instance and options to read, a reference element belonging to another box, and a popper taller or wider than the box, because a clipped popper inside is worse than a whole one outside. The tarball ships its own copies of `toy-core`'s loading and message helpers, which render into the registered box, and the page's `$notify` is overridden per instance so a scheme failure draws inside the block. The effect that calls `containCrud` is declared before the bridge's mount effect, which is what puts the box in place before the page's first request; the release is a second effect declared after it, because React runs cleanups in declaration order and the page raises its last toasts while Vue is destroying it. Every CSS rule the tarball ships is prefixed at build under the box's own attribute selector, so none of its `.el-*` rules restyles the console; `theme-chalk` is not shipped a second time, because this row already installs element-ui, and loading the tarball leaves the shared runtime's `size` and `zIndex` defaults where the row set them. The box holds the console's own theme out of the page for the same reason it holds the page's rules out of the console: the page draws on white and sets no color on text standing directly on its panels — the refusal it draws when this account is not granted the table is one such text — so the box states element-ui's own text color rather than letting the dark theme's light one be inherited onto a white panel.

**Whether the page opens at all.** Before it fetches anything, the page reads this visitor's own profile through `toy-core`'s cached path and judges one thing, with two ways of answering no. Where the permissions that profile carries name tables at all and none of them is this block's, and where those permissions could not be obtained at all — the deployment answered the profile request with a refusal of its own, or with no permission table in it — the page fetches nothing, no scheme, no dictionary, no query, draws the deployment's own 无权限 inside the box, and raises `access-denied` once, naming which of the two it was. A profile naming no table at all is no restriction, because that is a deployment which never handed out a table list. A deployment that said nothing at all — no answer, a timed-out one, or one of its own failures — is neither: the page fetches nothing there too, but what it draws is a line saying it could not read the permissions, and it raises nothing, so this block reports nothing about it. No property of the block reaches that judgement: an arrangement, a `readOnly: false`, a hidden condition are all read after it, so nothing a call or a written-down page can write gets past it. The page does not read the per-button rights in that profile: it fixes the customer's own `useCloudPermission: false`, because the real backend answers `null` for `search`, `imp`, `exp` and `gridexp` on every account, administrators included, and reading them would hide the query button too. Which entrances a visitor keeps is decided by the host instead, as the next paragraph describes.

**Which entrances this visitor keeps.** The page takes one property no block carries: `abilities`, `{ create, update, delete, import, export }`, each `false` removing the entrances that operation opens — `create` the toolbar's 新增, `update` the row's modify icon, `export` both exports; `delete` and `import` open nothing this page draws and are passed for completeness. It can only remove what the arrangement drew and `readOnly` left, never add. `DataPageRenderer` fetches it from the node half's `/component-kit/abilities?meta=<table>`, where `ctx.bizBackend` reads this visitor's rights once and judges each of the five by the deployment's own rule table, the `bizOperationRules` of [`dsh-experimental-auth-gate`](../auth-gate/README.md); the browser receives only the five booleans, so no copy of the rules lives in the page. The verdict is spread onto the page's props after the block's own, so nothing a call or a view writes stands in for it, and the placement package's catalog declares no such property, so a spec carrying one is refused before anything is drawn. Until the verdict arrives, and whenever none can be obtained — no data backend composed and so no route, a refused or failed rights read, an answer that is not a complete table — every one of the five is `false`. When it arrives the page's entrances change in place: the same instance, no remount, no second query.

**A sign-in this deployment refused.** Separately from that judgement, and from the request layer rather than from the page, this deployment can answer any of the page's requests by refusing the visitor's credential. The vendored build goes nowhere on that answer — the customer's own sources replace the console's whole window with their login page there, and the tarball's patches replace that with a notification — so the page stays where it is, draws a line in its own box, and raises `auth-failed` once per mount, until a request of its own succeeds. The layer that judged the credential is not told which block asked, so every data page on screen is raised the same one and each reports its own: two pages on screen are two notes, one per block, and not two notes about one page. Within one block it is one note however many requests were refused, because the report is held exactly as a refusal and a load are, and the placement package replaces a block's own unclaimed note with that block's next one.

**What the page writes.** A page nobody arranged is read-only, and `readOnly` is the only thing that opens it: with it on, the write and export buttons are hidden and `isReadOnly` reaches the originals. Whatever the arrangement, the page writes an audit record. Every answered query calls `toy-core`'s `crudEventLog`, which POSTs `<bizBasePath>/nrms-resourcehistory/api/log/frontevent/` with the visitor's own token, carrying the console's own path as `app_enname`, 查询 as the event, the table's name, and the query's parameters — including the hidden `conditions` the model wrote — as the event data. It is the deployment's own front-end audit trail, written under the visitor's identity; the approval card does not mention it, and the patch the tarball carries for that endpoint only swallows its rejection. A deployment that does not want console queries in that trail has to replace `core/log`'s export before the page mounts. The page also leaves four keys in the browser's own storage, every one of them written by that same request layer rather than by anything here. `localStorage.userInfo` is the visitor's profile as `toy-core` fetched it and stored it back through its own `setUserInfo`, and it carries the bearer token verbatim in the record's `token` field. `new-task-uuid`, prefixed with the console's own path the way the two cache entries below are, holds the task each export was queued as, which the originals write for the deployment's own task list page to read; nothing here reads it and this console ships no such page. The other two are its localforage cache of one table: `localforage//console/_schemaall_<meta>` holds that table's query, add and modify schemes, and `localforage//console/_meta_<meta>` holds its attribute dictionary — the keys a jsdom probe of the vendored bundle recorded, prefixed with the console's own path; a real browser keeps the same two entries in IndexedDB instead. Signing out clears `userInfo`, which is on `server-sidebar`'s sign-out key list, and leaves the task number and the two cache entries where they are, so one table's schemes and dictionary outlive the session on a shared machine. Clearing the localforage database at sign-out is that package's sign-out to do and is not done here.

**What the agent learns, and what stays in the panel.** No result set is in any of the twelve readings. `denied` carries which of the two judgements refused the page and nothing else: the table it is about is the one the call itself wrote, and the profile the page judged against, along with the permissions in it, stays where it was read. `auth-failed` carries the answer this deployment refused the visitor's credential with and the business code beside it, and never the credential it presented. `load` names the table, the drawn columns of the page's query scheme, and the rights the page resolved — this deployment's own row for a page that may be written in, and the page's own read-only record otherwise, which is what it granted rather than what the page drew. `query` carries the matched total, how many rows are shown, and which page. `select` carries how many rows are ticked and what the first five are called, by their first drawn cell. `cell-click` and `operation` carry one row's drawn cells — the row the user pointed at, symmetric with what a `toy.table` selection reports. `card-open` names the row a side card opened on and `card-close` carries nothing. `added` and `modified` carry at most eight drawn cells of the saved row, read through the same columns a clicked row is: the save answers with the record, which carries the row's key and every attribute the scheme hides from the table, and what the agent is told is what the user can see of it rather than the form they filled in. `exported` carries which of the two toolbar exports the page submitted and the file type the press named, and neither the rows it covers nor the task the backend queued it as: each export is a task on the deployment's own backend, the file is collected from that deployment's own task list, and the task number the page hands over names a row of a page this console does not ship. A load or a query identical to the one this block last reported for the same call is not reported again, so a tab switch that drops and redraws the block does not tell the agent the same thing twice; a refusal and a refused sign-in are held the same way, because a redrawn block judges the same permissions again and presents the same credential again.

<a id="how-the-originals-get-here"></a>
## How the originals get here

Some of these components were not written here. `@sumomok/toy-surface-kit` is a build of Vue 2 components lifted out of three source libraries a customer maintains. It is compiled in a repository of its own and arrives as `vendor/sumomok-toy-surface-kit-0.3.1.tgz`, declared `"@sumomok/toy-surface-kit": "file:./vendor/sumomok-toy-surface-kit-0.3.1.tgz"`. Rewriting them in React was considered and rejected: 191 of those libraries' 354 single-file components address element-ui components directly and 153 rules reach into their markup, so a rewrite would restart a bug history the customer has already paid for.

**Two tarballs out of the same three libraries.** `@sumomok/toy-crud-kit` is the second build, carrying `Crud.vue`'s own sub-components and the request layer they run on, and it arrives as `vendor/sumomok-toy-crud-kit-0.4.5.tgz` under everything this section says about the first. Its `DataPage` export is those sub-components assembled into one page in `Crud.vue`'s own arrangement — not a rewrite of it: the query panel, the toolbar, the table, the pager, the side card and the add and modify panels are the originals, and what the tarball adds is one layout template, the data flow lifted out of `Crud.vue`'s own script, and a mapping from its layout options onto the originals' props. Three things about it differ. It vendors the real `toy-core` barrel rather than a shim, because that request layer is the thing being shipped. Its `toy-comp` shim is widened to the seven deep imports `Crud`'s closure reaches, which is what cuts the three `main.js` files whose module-time `Vue.use(Element, { size: 'small', zIndex: 2000 })` would move the shared runtime's defaults out from under every other block, and the duplicate `theme-chalk` import with them. And its rule about identity is scoped rather than absolute: components read no storage and no cookie, while credential use is confined to `toy-core`'s own request layer: it reads the visitor's stored token and no other credential, and writes back into that same storage the profile it fetched with it, which the data page's own section records above — which is the whole point of shipping it, and which its own README states. It carries nineteen patches rather than five: the surface kit's four, one dropping a `console.log` of the signed-in user, one attaching a `.catch` to a fire-and-forget event log whose rejection nothing consumed, one cutting the two branches that took a token out of the page's own address bar, three the assembled page needs mechanically — forwarding the selection-change event the middle layer swallowed, replacing an `eval` of a backend-supplied expression and giving the card a section filter, and turning the pager's hard-coded row counts into two props — two the exports need: the export panel raises an event instead of navigating to a task page this console has no router for, and the toolbar forwards that event up, because a Vue 2 `$emit` does not bubble — and seven that leave the console's own window alone, which is why the artifact writes no address at all: the four places the request layer and the router replaced this page with the deployment's login page now raise a notification the container turns into `auth-failed`, the profile read no longer swallows its own failure and clears the visitor's credential five seconds later, that read is marked silent so a deployment's 「用户没有资源权限!」 is a state rather than a toast, and the mobile branch's last navigation throws instead of navigating. And it is the one payload here that compiles third-party npm libraries into its own artifact — forty of them, axios and nprogress and localforage among them — so it ships a generated `BUNDLED.json` naming each with its version and terms, and a `THIRD-PARTY-LICENSES.txt` carrying their texts; `THIRD_PARTY_NOTICES.md` is generated from the first of those, because nothing in this repository's manifests or lockfile names that code. The two it leaves external instead, `lodash` and `dayjs`, are declared by the tarball's own manifest and disclosed in the same file's runtime tier, which is read off that manifest for the same reason.

**Every console downloads the page, offered or not.** The vendored bundle is 957 KB (242 KB gzipped), the `lodash` and `dayjs` it imports rather than compiles in add 553 KB (100 KB gzipped) on top, and all of it is imported statically, so it is part of this row's single browser bundle and reaches every viewer on every boot — including a deployment that leaves `dataPage: false`, which is the default. Deferring it is not available here: a plugin's client bundle is one closure-factory file the loader fetches by name (`tsdown.client.ts` wraps the whole output in `window.__ModuleLoader__.load`), so a dynamic `import()` has no second chunk to land in and nothing would fetch one if it did. Moving the page off the boot path needs a second fetchable artifact per plugin first, which is a loader change rather than a change here. **The trigger for making it is a deployment that runs the console with `dataPage: false` and measures the boot cost.**

**A snapshot, not a checkout.** Overwriting the tarball in place is silently ineffective: pnpm keys the install on the file path plus an integrity hash it does not re-read for an unchanged specifier, so the build keeps the previous bytes. Every rebuild bumps the version, lands under the new file name, and updates the specifier before `pnpm install`.

**Five patches.** The build is not a straight copy: five patches are applied to the sources and shipped inside the tarball under `patches/`, with the reason for each in its `SOURCES.md`. They drop a `cronstrue` dependency, drop a download column, fix a `toUpperCase` call, remove a token read from `localStorage`, and stop the metric ball's animation chain when its instance is destroyed — without the last one, a block that goes away leaves a `setTimeout` chain writing to a destroyed component until it counts out.

**One handle back the other way.** The bridge passes plain data and callbacks into Vue and nothing out, with one exception: a renderer may pass an `instanceRef`, which the bridge fills with the mounted component itself — `root.$children[0]`, not the root it owns — for as long as the block is mounted. It exists because two of the vendored components answer through instance methods rather than through an event: `TuQueryCondAdv` emits nothing at all and `getData()` is the only way to read what the user built, and `TableDetail` deep-clones the rows in its own selection event, so the identity a gesture is reported by has to be read back with `doGetSelection()`. Renderers use it to read.

**Six gates that run before the tarball exists.** The build repository refuses to publish one whose artifact still contains `from 'vue'`, `'element-ui'`, `'toy-core'`, or `'toy-comp'`; whose bytes include a `fontawesome-webfont`; or which fails a jsdom mount smoke test. The first four catch a barrel import dragging in module-load side effects, the fifth catches a 1.1 MB icon font, and the last catches what none of the text gates can see — a trimmed or inlined dependency that throws while its module is being evaluated.

**One Vue, requested rather than bundled.** Vue 2 reactivity does not cross runtime copies, so this row takes `Vue` from the row that owns the only one: `dsh.client.external` names `@deepseek-ai/dsh-experimental-vue2-echarts-poc/client`, `src/client/vue-shim.ts` re-exports what it supplies, and `tsdown.config.ts` aliases the bare specifier `vue` onto that file — for the browser bundle only, and only for the bare specifier. That is why no file under `src/` may import `vue` for itself, by any spelling — a `vue/dist/…` import would reach a copy of its own, which the alias does not cover — and `tests/source-vue-imports.client.spec.ts` fails if one starts to. What an inlined library asks for is not visible in the sources at all, so `tests/client-bundle-vue.client.spec.ts` counts Vue-runtime markers in the built `lib/client.js` and fails if a second copy landed there.

**element-ui, installed once, at 300.** `installElementUI()` holds the only `Vue.use(ElementUI)` there is, and the row's client plugin calls it when it starts. `Vue.use` has no counterpart, so it is a module-scoped guard rather than an effect: tearing the row down leaves the components registered. Both options are written dead — `size: 'small'`, and `zIndex: 300` because element-ui's own default of 2000 draws a dropdown over the harness chrome at 1100 and over the approval modal at 1000, which would let an open select cover the window asking the user to approve something. The browser half of a plugin receives no cordis config and this row has no host half, so making either option a setting means a placement package reads it and passes it in.

`src/client/element-ui.css` is a physical copy of element-ui's `theme-chalk/index.css` with one edit: the icon `@font-face` carries its woff inline as a `data:` URI and no longer offers the truetype alternative, because the client bundle injects the sheet as a `<style>` tag and a relative font URL would resolve against the page instead. Regenerate it the same way after a version bump.

**Three red lines.** No `window.Vue` on the page, ever — element-ui's UMD build installs itself onto whatever it finds there, which would register its components on a runtime this row does not own and stop reactivity with no error and no warning. No `el-dialog`, `el-message`, or `el-notification` in a block: their elements sit outside the host and nothing here can close them. The poppers that are allowed — a select's dropdown, a tooltip, a popover, a date picker's panel — are a closed table in the bridge, swept when a placement package says the block is off screen, and a component drawing a fifth kind of popper is added to that table in the same change. And every record handed to a Vue component goes through `freezeDeep` first, because Vue observes what it is given however deep — an observed array has its prototype swapped, which would reach back into data React owns. A component's listener map is the one thing that cannot be frozen: Vue rewrites the object it is given, installing an invoker over each handler, so the bridge hands it a copy and the caller's own map is left as it was written.

## Composition

This row is placed by [`component-surface`](../component-surface/README.md), whose overlay composes both. Neither is part of any shipped bundle. Composing the placement row without this one leaves its catalog empty, which is a deployment that offers the model no component and no tool.

One field. `bizBasePath` is the root-absolute path prefix the data page requests its table under, `/` by default; a composition that draws no data page can leave it alone. The route that serves it waits for `webServer` rather than requiring it, and the contribution waits for `componentCatalog` the same way, so a composition with neither still loads this row.

```yml
- id: component-kit
  name: '@deepseek-ai/dsh-experimental-component-kit'
  config:
    bizBasePath: /ini-server/
```

## Model Experience

None, as this row registers no tool, prompt, or result of its own and reaches a model only through the placement row's `show_component` description, which lists every registered component and whose token cost that row states.

#### KV Cache effect

None; this package neither assembles nor sends a provider request.

## Known Limitations and Deferred Work

- **The states are the placement package's to fold, and a wrong fold is invisible here** — this row draws `state` and decides nothing about it, so a placement that never advances a block past `sending`, or hands one block another's state, produces a bar that looks correct and says the wrong thing. Nothing in this row can tell.
- **The state table is closed, what a state means is not** — a bar draws one line per state it is handed, and the compiler catches a state this table has no line for. It cannot catch a placement whose new delivery grade folds into an existing state: an action a placement swallows without telling anyone, folded as `sent`, draws 已发送到对话 (`Sent to the conversation`) here. Whoever adds such a grade decides this line with it.
- **A placement's own sentences are not translated through this row** — this row localizes the lines a bar draws about its gesture, but whatever the placement package says about the same gesture elsewhere on screen carries whatever language that package wrote. The console's placement answers a press from its host, which is handed no browser locale, so `这个动作没能记下来。`, `内容太多了，少选几项或写短一些再试。` and `已记下，你下次发消息时对话会看到。` appear in the chat beside a bar reading `Sent to the conversation`. Nothing here can reach them; the fix belongs to whichever placement wants one interface language, and the trigger is the console offering an interface in any other language.
- **What a payload may carry is unenforced here** — a renderer is trusted to put only what the placement package's catalog declares for that action into `onAction`'s payload; nothing in this row checks it, and the placement package refuses the whole gesture rather than trimming it. A renderer that adds a field its action does not declare makes every press of that control reach nobody.
- **One catalog, two homes** — the ids in this table and the catalog that validates a block's properties are separate declarations in separate packages, tied together only by the consumer's `satisfies` check. That check covers the ids and nothing else: a renderer whose properties drift from the schema that admitted them compiles cleanly and draws the wrong thing.
- **A component publishes what it reads of itself and knows nothing of who reads it** — a component never names another block, never reads one, and cannot tell whether anything is bound to what it publishes. Which outputs exist, whether one can stand where a property is declared, and where the value ends up are the placement package's, and this row publishes on every change whether or not anyone is listening.
- **What an output may carry is unenforced here, exactly as a payload is** — a renderer is trusted to publish only what the placement package's catalog declares for that output and in the shape it declares. Nothing in this row checks it; the placement package leaves the fed block waiting rather than drawing something that does not fit, so the user sees a block that never arrives.
- **A published value must not be mutated afterwards** — the placement package hands it to another block as a property, and a publisher that goes on writing to it would change a property under a component nobody re-rendered. Nothing enforces it: the one component that publishes here hands over a list it builds for the occasion and does not keep.
- **A page that could not read the permissions at all reports nothing** — the deployment saying nothing to the profile request is the page's third answer, and the only one it raises no event for: it draws a line in the box saying it could not read the permissions, and this block has nothing to report because the page told it nothing. The agent is therefore told about a table refused to this account and about a credential this deployment refused, and not about a page that is empty because the deployment did not answer. Reporting it would mean this row deciding from the outside that a page which drew no columns and raised nothing had failed, which it cannot tell from a page still loading. The trigger is the vendored page raising an event of its own for that answer.
- **Removing an entrance is not refusing the request** — `abilities` hides what this visitor's rights do not allow, by the deployment's rule table, and nothing more: a request the page could still make is judged by the backend, and the ability route reads the rights the process holds, which describe whoever signed in last. Each data page mounted asks once, and nothing is cached, so rights changed while a page is open take effect when it is drawn again.
- **The tarball is a snapshot of libraries with no history** — the three source libraries have no git, no version numbers, and no change log. A customer edit cannot be diffed or even noticed, so the components here can drift from the ones the customer runs, and the only sync there is copying the sources again by hand and re-running the tarball's gates. This is a standing maintenance debt, not a warning that can be switched off.
- **The vendored components' own Chinese does not follow the interface language** — an empty table's 暂无数据 is compiled into element-ui, and 属性名, 匹配策略, 属性值, 条件关系, 并且, 或者, 增加 and a table's 操作 heading are compiled into the vendored components themselves. None of them reaches a dictionary of ours, so they stay Chinese in an English interface. Changing that means recompiling element-ui and rebuilding the tarball from edited sources, each its own piece of work.
- **A table's rows are named by position, and the narrowing can move them** — a gesture reports an index into `displayValueList` as this renderer built it, and it drops an item that is not a record at all, so a stored call written by another build can shift every index after the dropped row. A validated call cannot produce one.
- **A table is drawn at a fixed height and shows every row it is given** — there is no paging and no scroll-to-load, so a call carrying more rows than fit leaves the rest below the fold of the table's own scroll area. What bounds it is the catalog's row ceiling rather than anything here.
- **`isNameClick` only reaches a `display_default` column** — the component draws the openable name link from the column whose `relatedMetaAttr` is `zh_label`, and only when that column is drawn as plain text. A call that names a different column, or draws that one with a cell component, gets a table with no link on it at all whose rows still open on a click anywhere in them, because the property the call turned on is what this renderer reads.
- **A press with nothing complete in it draws nothing** — the condition editor starts holding one empty row, so the first press of a filter bar's button submits nothing and the placement package reports nothing; `state` never moves, and this row draws no line, because there is no gesture to draw one about. The user is left with a button that answers a press with no change on screen. Greying it out would mean drawing the button off how many complete conditions the editor holds, which this row learns only from the same `change` the placement package grades — the two would have to agree about when the button may move. The trigger is the first report of a press that seemed to do nothing.
- **A refused gesture has one line whatever refused it** — `action.refused` is 这个动作没能记下来，可以再试 for every refusal, because `ComponentActionState` carries one refused member and the placement's own reason does not reach this row. A placement whose refusal was about size says so elsewhere on screen — the console's says 内容太多了，少选几项或写短一些再试。 in the chat — and the block beside it says something else. Telling them apart here needs a further state in that union, agreed with whichever placement folds it, and a line for it in this dictionary.
- **The condition editor adds rows without a ceiling** — the vendored component's own add button appends a condition row for as long as it is pressed, and nothing here stops it. A placement package whose action declares a ceiling on how many conditions one submit carries therefore refuses the submit, and the user learns the ceiling from the placement's answer rather than from the editor. Capping it here would need that number on this side of the seam, and this row draws blocks for whoever places them: it cannot import a placement package to read one.
- **A filter bar's values are typed as text** — the vendored build replaced the seven value controls that fetch their own options with a disabled stand-in, so this renderer offers no way to select one and every attribute gets a plain text box. A date or an enumerated value is whatever the user types.
- **A metric's gradient degrades on a color keyword** — the component lightens `background` for the top of its gradient through a stand-in for a `toy-core` utility the tarball does not carry, and that stand-in converts `#rgb`, `#rrggbb`, `#rrggbbaa`, `rgb()` and `rgba()` and returns anything else unchanged. A color spelled as a keyword therefore draws a ball with no gradient rather than failing; the placement package's own tightening admits only the spellings that convert.
- **`TableDetail`'s function-shaped properties are not offered** — the component takes callbacks for per-row button visibility, per-row styling, and cloud permission checks. None of them can be expressed in a schema whose members are text, numbers, booleans and lists of those, and none is accepted here: a block decides what it offers by the data it carries.
- **`PopupManager.nextZIndex()` only ever counts up** — element-ui hands each new popper the next z-index from 300 and never resets the counter, so a session that opens roughly seven hundred of them climbs past the approval modal at 1000 and can cover it. Hiding a block closes the poppers it opened; nothing lowers the counter. The fix is the harness raising its own layers well above element-ui's range.
- **The data page navigates the whole window when it holds no token, or is answered 401** — `toy-core`'s request interceptor sends the browser to the deployment's login URL, and the console goes with it: the page is drawn inside the shell, not in a frame of its own. Recorded rather than fixed. It is acceptable in the same-origin deployment this component is for, where [`auth-gate`](../auth-gate/README.md) keeps a token fresh in front of every request; a deployment that composes `toy.data-page` without that gate gets a console that can navigate away from a conversation the user was in the middle of.
- **The overlay and the progress bar are module singletons** — `containCrud` points both at the box that registered last, so two data pages on screen at once draw one page's loading state inside the other's box. A single call may place only one page, which is the placement package's rule; two calls can still leave two entries in the column.
- **Toast containment assumes every element-ui toast on the page is this kit's** — the observer that moves body-level `.el-message` and `.el-notification` into the box does not ask who raised them, so a toast raised by some future row would be moved into a data page's box instead of drawn where that row meant it.
- **Seven of the data page's query controls are disabled stand-ins** — the value controls that resolve related records were replaced at build, exactly as in the surface kit, so a query cannot be narrowed by a related attribute and the control is drawn greyed out. The trigger for building them is the first user who needs one.
- **The data page's icons draw as empty boxes** — no icon font is shipped, so `TcAwesomeIcon` renders an `<i class="fa …">` with nothing inside it. None is visible in the read-only page; a write path would show them.
- **The data page offers no delete** — the tarball still compiles the delete confirmation dialog to an empty stub, so the row's delete icon would open nothing; `rowOperations` therefore admits `modify` alone and the catalog refuses `delete` by name. Restoring it means letting that dialog out of the stub table and auditing its batch endpoint, and the tarball's own README records what comes back with it.
- **The data page offers no import and no batch** — a press of either reaches nothing a person can act on: the import panel uploads a whole table's worth of rows and then navigates to a task page this console has no router for, so how it went and which row failed are nowhere on screen, and the two batch dialogs are empty stubs whose command writes one audit record. `toolbarButtons` therefore admits neither `imp` nor `batch`, and both the catalog and the page's own prop validator refuse them by name. Restoring them means the task-status panel inside the box for the first, and letting the two dialogs out of the stub table and auditing their endpoints for the second.
- **An export leaves as a task, and this page cannot show what became of it** — 模板导出 and 表格导出 each POST one export endpoint and the backend answers with a task number, which the originals write to `localStorage['new-task-uuid']` for the deployment's own task list page. This console ships no such page, so what the user sees is the page's own toast saying the task was created, and the file is collected in the deployment's own console. Showing it here means auditing the task-status subtree and its status endpoint into the tarball's closure; the file itself then downloads through a blob and an anchor, which a sandboxed frame refuses without `allow-downloads`.
- **模板导出 draws only where the table's scheme carries a modify template** — all three branches of the export panel read `templateConfig.modify`, so a table whose scheme carries none draws that button as a comment node however the view arranged it. It is the originals' behavior and the tarball does not change it; 表格导出 is drawn either way.
- **A page's toolbar order is the originals', and only which buttons appear is arrangeable** — `CrudAction.vue` writes the order into its template, so `toolbarButtons` is a list of which to keep rather than a list of where to put them, and a view that writes them in another order gets the original one.
- **Three of the side card's five sections are empty stubs** — `operation`, `related-stat` and `useage` were replaced at build, so `infoCardTabs` can only narrow the sections the scheme offers and two of the five are the only ones that draw anything.
- **A drop-down the block is too small to hold is still drawn outside it** — `containCrud` adopts a body-appended popper only when the box can hold the whole of it, because a popper moved into a clipping box loses whatever does not fit while one left on the body is at least entire. So a column shorter than the pager's seven-entry rows-per-page list, measured at 110×252 by the browser probe in the tarball's own repository, draws that list over whatever sits under the block, unclipped and not scrolled with it. Fixing it means passing `popper-append-to-body=false` to those controls, which is an edit to the originals; the trigger is a deployment whose content column is routinely shorter than a page's own drop-downs.
- **The data page tarball's types are hand-written** — `types/index.d.ts` inside it is written by hand against a JavaScript build, exactly as the surface kit's is, so a drift in the built component's own properties compiles cleanly here and fails when the block is drawn.
- **Not covered by an assembled snapshot** — the browser evidence is a Playwright scenario against a real composition; the snapshot lanes replay the shipped composition, which does not compose an experimental row.
- **The one-Vue assertion over the built bundle does not run on CI** — `tests/client-bundle-vue.client.spec.ts` reads `lib/client.js`; on a pull request the only job that runs `vitest` over this package is the coverage job, which does not build, so it skips there. The master lane, `linux-primary`, runs its gates serially with the build ordered after the coverage gate, so the artifact is absent there too. It runs locally and in any lane that builds first, and the repository has no gate that reads a built client bundle's text — the two other specs of this kind, in `client/ui-trajectory` and `session/session-persistence-sqlite`, skip on CI for the same reason. What CI does cover is the consequence: the Playwright scenario draws a vendored component against the shipped bundles. The trigger for moving all three onto a gate is the first one that reads a built client bundle.

**Runtime invariant:** No companion is published. This package is a renderer table: its node half serves one settings route and nothing else, it appends no session event, and what a block is allowed to draw is judged by the placement package that owns the catalog.
