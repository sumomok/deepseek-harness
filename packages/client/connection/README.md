# @deepseek-ai/dsh-client-connection

English | [中文](README.zh.md)

## Summary

The package carries browser-to-Host Remote calls, exact Fetch responses, and connection generations. The Client plugin mounts `ctx.connection` with current-page loopback state, generic RPC, the active generation and its Host facts, observable recovery state, an immediate reconnect command, and the registration point for one generation source. A generation becomes visible when its source reports ready; source completion, failure, withdrawal, or an explicit stop clears it before `ConnectionController` applies its retry policy.

<a id="use-this-package"></a>
## Use this package

A static desktop page can provide `__DSH_TRANSPORT__.streamBaseUrl` for the HTTP origin of its owned Host. The Gateway uses that origin for its WebSocket while HTTP transport remains independently selected. The desktop carrier owns authentication; setting the origin alone grants no access.

Unary RPC requests use JSON. A Host handler may return byte attachments that it has already separated from the JSON-compatible result value, with each attachment naming its result-relative path. Connection writes these values as multipart parts. The JSON `metadata` part contains the RPC response envelope with `null` placeholders and an attachment table recording each path, codec, and part identifier. Paths use string keys and numeric array indices; no business field name is reserved. The Client validates the envelope, `rpcId`, attachment table, and parts, then restores each byte value as an `ArrayBuffer`-backed view. Results without attachments, including base64 strings, and failures remain JSON. Logical RPC carriers return decoded native values directly. Connection does not discover binary fields or depend on Typert; the handler that owns a result protocol performs any type-directed or runtime projection before returning. Binary parameters, events, and streamed binary results are unsupported.

The browser uses HTTP POST for Remote unary calls. API Gateway owns the `/api/remote.mux` WebSocket and its logical streams; shell-owned compositions provide equivalent Remote streams, including a stream's uplink, through `connection.rpc.open` without opening a WebSocket. The browser plugin reads the page transport, recovery settings, and location, then delegates to `installConnection(ctx, options)`. A composition that owns its carrier may call the same installer directly; the whole-client test tier does so. Each invocation creates one Context-owned service, so several Client trees can use different carriers in one realm. The Host half always provides the carrier-neutral RPC and exact `GET`/`HEAD`/`POST` route registries. When a Web carrier is present it also owns the sole `/api` route, Fetch bridge, browser authentication, and Host/Origin checks; a shell-owned carrier dispatches the shared Fetch handler directly. Each exact route declares buffered or streaming request-body handling before the bridge reads any bytes. Typert Gateway claims generated Remote endpoints, feature packages register non-JSON responses such as Session-log downloads and raw file uploads, and unclaimed requests return 404. Loopback hostname classification remains package-internal to the browser-facing Client state. Browser raw-body transfer is provided by [`dsh-client-file-upload`](../file-upload/README.md).

<a id="browser-authentication-and-request-trust"></a>
## Browser authentication and request trust

Every Host RPC method and WebSocket stream requires one browser session; there is no method-specific loopback tier. Each process mints a random launch token. `dsh-web-app` prints and opens its application URL with `?token=...`, preserving the caller's authority and mount; `frontend-static` delegates root and index requests to `ctx.connection.authorizeIndex`, which accepts that token only on `GET /`, writes an authority-bound signed cookie, and redirects to clean `./`, which drops the token and keeps the request's directory. A missing, expired, malformed, or wrong-authority cookie returns 401 before RPC dispatch. Static assets remain public. The HTTP carrier accepts no query token outside the root exchange and no Authorization-header token.

The cookie signing secret is the owner-scoped `client-connection/browser-session` grant record in `ctx.credentials`. The local provider persists it in `$DSH_HOME/.credentials.yaml`; `BrowserAuth` loads or creates the record during Connection activation and retains the secret in memory, so request authentication is synchronous. Deleting or replacing the record takes effect on the next Connection activation. Cookies carry an absolute issue/expiry interval, defaulting to 30 days through `cookieMaxAgeDays`, and bind the normalized hostname plus port in both their deterministic name and signed payload. They are host-only, `Path=/`, `HttpOnly`, and `SameSite=Strict`; they deliberately omit `Secure` because the shipped server uses loopback HTTP.

Before authentication, every request still passes `src/api-request-trust.ts`. Its `Host` must be loopback or match a `trustedHosts` entry: exact on `host:port`, any port on port-less entries, both sides WHATWG-normalized. An attached `Origin` must equal that Host and `sec-fetch-site: cross-site` is refused. Malformed configured authorities fail plugin load. These checks defend DNS rebinding and cross-site browser requests; they never establish identity. A failed Host/Origin check returns 403, while a trusted but unauthenticated request returns 401. `dsh web --host 0.0.0.0` remains unsupported. Decision records: [browser request trust](../../../.agents/notes/implemented/architecture/2026-07-28-api-browser-trust-boundary.md) and [browser token authentication](../../../.agents/notes/implemented/architecture/2026-08-24-browser-token-authentication.md).

Every admitted request speaks for one Peer. `ctx.connection.operator` is the operator's `PeerScope`: its `ctx` is a Cordis scope that owns connection-lifetime registrations and is disposed with the Connection. `ctx.connection.admit(request)` runs the trust and authentication checks and answers with the rejection status or the admitted Peer; the `/api` route, dedicated RPC channels, and the Gateway's WebSocket upgrade admit through it, and every RPC handler, exact Fetch route, and stream receives the Peer of its call. Without an admitter every admitted request speaks for the operator, unless `requireAdmitter` is set. The shared Fetch handler and `bridge()` take the admitted Peer as an optional final argument; a shell-owned carrier that names none speaks for the operator. `OperatorPeer` is exported so a composition without Connection, such as the Gateway's in-process carrier, owns an operator scope with the same contract.

A deployment that serves several members from one Host installs one admitter with `ctx.connection.peers.admitWith(admitter)`. A second installation throws; disposing the registration, or the fiber that made it, restores admission without an admitter. The admitter runs synchronously, only after the Host/Origin checks and browser authentication have passed, and must give the same answer for the same headers. It returns a member Peer from `ctx.connection.peers.open()`, 401 or 403 to refuse, or `undefined`. `undefined`, a released Peer, or any Peer that `open()` did not return is refused with 401 and logged as an error, so with an admitter installed no HTTP request or WebSocket upgrade speaks for the operator. `requestRejection(request)` returns the same verdict to routes that use it as their only check. `peers.get(id)` and `peers.list()` return the member Peers whose `dispose()` has not been called. `connection/peer-opened` is emitted before `open()` returns, and `connection/peer-closed` once, after the first `dispose()` completes; unloading Connection disposes every open member Peer, and the operator emits neither event. A member Peer carries no identity: the plugin that installs the admitter keeps the mapping from its members to Peers. Connection checks the Peer again immediately before an exact route runs, a dedicated channel decodes its envelope, or the `/api` RPC interceptor decodes its request, with or without an admitter: a request whose Peer is neither `ctx.connection.operator` nor a member Peer from `peers.open()` whose `dispose()` has not been called reaches none of them and is answered 401 `unauthorized`. That covers a member Peer released since admission, such as while the bridge buffered its body or a `connection/request` or `connection/fetch` listener awaited, and a Peer an in-process carrier passes that Connection did not create. The operator is never checked again and is identified only by identity, `peer === ctx.connection.operator`; a member lookup that finds nothing, such as the admitter plugin's mapping for a released member Peer, does not identify the operator. `peers.memberAdmission` is `true` while an admitter is installed or `requireAdmitter` is true; each read reports the current state. Decision record: [one Host serving several members](../../../.agents/notes/implemented/architecture/2026-10-05-console-member-peers.md).

Set the Host Connection row's `config.requireAdmitter` to `true` to refuse with 401, while no admitter is installed, every HTTP request and WebSocket upgrade that passes the Host/Origin checks and browser authentication; `requestRejection` returns the same 401, and index authorization is unaffected. This closes the time before the admitter's plugin applies and while it restarts, when the default `false` admits such requests as the operator. With `requireAdmitter: true` and no admitter plugin in the composition, Connection refuses every such request; this fail-closed result is intended. `ctx.connection.peers.requireAdmitter` reports the resolved value, so a plugin that installs an admitter for a deployment that depends on default deny reads it at load and refuses to start when it is false, because a later configuration layer replaces the whole Connection row.

Authenticated shared HTTP requests pass through the `connection/request` waterfall before body transfer. A listener may refuse new requests or await `next()` through response completion; removing its owning fiber removes admission behavior. Desktop uses this hook to lock new API work during an approved installation without canceling already-admitted work. Client disconnection aborts the handler signal; the bridge stops socket writes and drains any remaining response chunks. WebSocket stream ownership remains with API Gateway.

Every request to an exact Fetch route, or to a dedicated channel registered with `rpc.handle`, passes through the `connection/fetch` waterfall after admission and the bridge's body handling, before the route runs or the channel decodes its envelope. A request an exact route does not own, including one to its path with a method it does not declare, continues through normal dispatch without the waterfall, and `/api` requests the RPC interceptor dispatches do not pass through it; the Gateway's `remote/invoke` waterfall covers those. A listener receives a `ConnectionFetchCall` — `kind` (`exact-route` or `channel`), `path` (the registered route path or channel prefix; the endpoint below a channel is on `request.url`), `method`, the Fetch `request`, and the admitted `peer`, which is the operator when a shell-owned carrier names none — and `next()`, which hands the request to the route or channel and resolves to its Response. A listener refuses by returning its own Response without calling `next()`. Every request below a channel prefix reaches the listener, including one the channel would answer with 404. A listener must not consume the request body, which the route still reads; it reads `request.clone()` instead, and reading the clone of a streaming request buffers the body for the route. After a listener consumes the body itself, the route can no longer read it: a route whose read throws answers as a throwing route does, 400 with an empty body and a warning; with `@deepseek-ai/dsh-attachment-local` as the attachment store, `/api/session/uploadFileBinary` stores no attachment and answers 200 with `ok: false`, error code `session/attachment-invalid`, and reason `ATTACHMENT_WRITE_FAILED`; and a channel answers 400 `body is not JSON`, although the body was JSON. A route that does not read the body, such as `GET /api/file`, is unaffected. An exact route whose registration is removed while a listener waits, such as when its plugin unloads, does not run: `next()` resolves to 404 `not found`, also when another route has been registered at the same path meanwhile.

Cordis hands every `connection/fetch` listener the same `next()`: each call runs the next listener that has not yet run, or the route when none remains. A listener therefore calls `next()` at most once; a second call, such as a retry after a later listener refused, skips every listener that has already run, so a listener's refusal holds only while every listener before it calls `next()` once. Connection cancels the body of every Response the route or channel produced for a `next()` called before the waterfall ended, unless the caller receives that Response or a Response that carries its body, such as one built over it to add headers. When the waterfall's result has no body, or its body is already locked, the cancel runs when the waterfall ends. Otherwise the caller's body may read a route body only as the caller reads it, as a listener's relay through `ReadableStream.from()`, an async generator, or a stream that takes its reader in `pull()` does, so the cancel waits until the caller has read its body to the end, cancelled it, or reading it failed. Connection then hands the caller a new Response with the listener's status, status text, and headers over a body that relays the listener's body; it does not keep the listener Response's `url`, `redirected`, or `type`, and its body is not a byte stream. The HTTP carrier always reads the body to the end, so over HTTP the cancel always runs; an in-process caller that leaves the body unread keeps the route body open. When every `next()` called before the waterfall ended has resolved to a Response that the caller receives, or whose body it receives, as without a listener or with a listener that returns `next()`'s Response, the caller receives the listener's Response object itself. Connection compares Responses and bodies by identity, so a Response that another copy of undici built follows the same rules. A Response still pending when the cancel runs is cancelled when it resolves, without delaying the caller. A cancel that fails, such as for a body a listener or the caller's body has locked, is ignored, and a route rejection no listener awaited is absorbed. The waterfall ends when Connection takes the outermost listener's result or failure, after any microtasks the listener queued before returning have run. Once it has ended, a `next()` call that reaches the route or channel dispatches nothing and rejects with an error saying that `next()` was called after the waterfall ended; a listener that has not yet run still runs first and may answer the call itself. A listener that discards that rejection leaves its own unhandled rejection. A listener that throws, or a `next()` whose route throws, rejects the Fetch handler as a throwing route does, and the HTTP carrier answers 400 with an empty body and logs a warning; a dedicated channel answers its own handler's throw with 500, so a listener's throw on a channel answers differently. While member admission is off, a request that finds no listener goes straight to its route or channel. While it is on, that is while `peers.memberAdmission` is true, such a request is answered 503 `service unavailable` and neither the route nor the channel runs; Connection looks for listeners when the waterfall would run, after the bridge has handled the body, so a buffered upload whose listener's plugin unloaded meanwhile is answered 503 as well, and so is a request a shell-owned carrier dispatches without naming a Peer. Connection resolves the listeners as Cordis's `waterfall()` does, emits `internal/dispatch` once per request, and passes every listener the same `next()` described above. An `internal/dispatch` listener instead receives the waterfall's first position: a call to it runs once the listeners are resolved and settles with the waterfall's own outcome, so it meets every listener's refusal and dispatches nothing the waterfall does not; when the request is answered 503 or an `internal/dispatch` listener throws, it dispatches nothing and rejects. The Response the step settles with is the waterfall's result itself, the object the caller receives or the one whose body the caller's Response relays, so an `internal/dispatch` listener must not read its body. `connection.fetch.list()` returns each exact route in effect with its methods, and `connection.rpc.channels()` each dedicated channel in effect, both sorted by path, so a gate test can require a classification for every one.

<a id="connection-generation"></a>
## Connection generation

API Gateway Client registers the internal `$events` logical stream as the sole generation source, independently of whether any `$on` listener exists. The Host attaches all incremental listeners in the API Remotes source factory, then sends one `{ type: 'ready', clientId, host: { home } }` item before events. `ConnectionController` publishes that generation and calls `onConnected` only after the ready item arrives, so baseline acquisition cannot race ahead of incremental observation.

An ended `$events` stream, a Remote stream error, a non-ready opening item, or a malformed event item invalidates the current generation. A pending handshake logs a slow-Host warning after 3 seconds and logs the readiness timeout and aborts after 15 seconds by default, including time spent waiting for the physical socket. The source must stop delivery, release resources, and settle after cancellation before a replacement starts; late readiness from a cancelled source cannot publish a generation. While the browser reports network availability, the controller publishes `connecting` and retries with 50%–100% jitter under caps of 500ms, 1s, 2s, 4s, 8s, and 10s, continuing at the final cap until recovery. Every retry asks Gateway to replace the physical WebSocket once and reopens `$events`.

`ctx.connection.reconnect()` interrupts active work, resets the sequence, and starts retry 1 immediately. Browser `offline` aborts active work, publishes `disconnected`, and suspends automatic attempts; the next `online` transition resets the sequence and starts at the 500ms tier. Only a ready item publishes `connected`. Gateway mux owns no independent retry schedule.

Set the Host Connection row's `config.recovery` to override retry caps, the growth factor, or handshake warning and cancellation times; the [configuration catalog](../../../docs/config-catalog.md#deepseek-aidsh-client-connection) lists accepted fields. The Host validates these values and injects them into each served page. The Client validates the bootstrap data before providing Connection and uses those defaults when Gateway starts its loop; explicit `start()` timing overrides take precedence. The growth factor must be finite and at least one. Readiness, failure, cancellation, or a hard deadline that occurs before the warning cancels that warning. Reload the page after changing Host recovery configuration.

## Known Limitations and Deferred Work

<a id="known-limitations-and-deferred-work"></a>

- **Buffered `/api` routes retain each request body in memory** — `maxRequestBodyBytes` (default 300 MiB, sized for the default 200 MiB aggregate image limit after base64 expansion plus envelope headroom) bounds ordinary image and RPC envelopes. Opt-in streaming routes receive backpressured chunks and bypass the aggregate cap; route implementations own persistence, cancellation, and any storage quota.
- **The browser cookie is not marked `Secure`** — loopback HTTP is the shipped transport, so exposing the same authority over plaintext networking can expose the bearer cookie in transit.
- **There is no logout operation** — clearing the browser cookie ends one browser session; deleting the owner credential record and restarting `dsh` revokes every session.
- **A relay that takes the route body's reader in `pull()` without a `cancel()` keeps the route body open** — when a `connection/fetch` listener returns a Response whose body obtains the route body's reader only inside its first `pull()` and defines no `cancel()`, and the caller cancels that body after that first `pull()` has run (on the caller's first read, or shortly after construction when the body's `highWaterMark` is above 0, which is the default), the reader still locks the route body, so Connection's cancel of it fails and the route body is not cancelled.
