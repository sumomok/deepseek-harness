# Agent Note: Answering an approval from the Windows toast

Status: implemented

[English](2026-09-06-desktop-toast-actions.md) | 中文

## Problem

桌面壳早就会告诉用户「某个会话在等一次工具批准」，点那条通知也会把窗口抬起来。但要拒绝这次请求，仍然得把窗口这一趟走完：还原窗口、找到会话、读那张卡、按按钮。而拒绝恰恰是唯一一个不需要这趟路的答案——没看清就拒掉，代价只是模型重试一次——于是最便宜、也最安全的那个答案，反倒是通知唯一送不出去的。

## Decision

Windows 上审批的 toast 带两个按钮，顺序固定：「拒绝」和「去看看」。

「拒绝」在 `$events/result` 上用 `{ kind: 'result', value: 'rejected' }` 答复这次 waterfall 投递，走的就是壳本来答 `next` 的那条已鉴权 HTTP 通道。任一客户端返回 `result` 就为所有客户端结算这次请求，于是 Host 会取消发给浏览器页面的那次投递，那张审批卡在按下按钮的同时消失——用户的动作落在用户看得见的地方。「去看看」调用的就是点通知本体所调用的那个 `reveal`；点本体的行为没有变化。

没有「批准」。toast 只说了某个会话请求执行哪个工具，别的什么都没说——没有命令、没有文件、没有将要写入的内容——而批准得当着它所批的那样东西给。

**一条 toast 的寿命，恰好等于这个壳还有资格答复它的那段时间。**Windows 几秒钟就把弹出的横幅收进操作中心，并把按钮一直留着可按；而壳自己的宽限在投递后一分钟答出 `next`，答出的同时它就被从这次投递的客户端里移除，此后它再发什么 Host 都会丢弃。这两段时间几乎不重叠，而 Windows 上宽限一定会武装——「最小化到托盘」用的是隐藏窗口而不是销毁窗口——于是用户回到操作中心按下「拒绝」，常态就是按在一个这个壳已经无权答复的按钮上。所以壳会在一条 toast 被人动过、或者它背后那件事已经结束的那一刻把它关掉：**按钮被按下了、自己的 `next` 发出了、`cancel` 帧到了，或者这一代被停掉了。**按「去看看」也在这张表上，尽管它什么都没答——投递原封不动，只是这条 toast 已经说完了它要说的；而「这一代被停掉」在表上，是因为一次 rebind 会在屏幕上留下一批按钮，它们点名的是一个这个壳已经离开的服务器上的投递。不带按钮的那些 toast 同样按这条规则走：一个已经在窗口里答完的提问，不该继续留在操作中心里问。

仍然落到某条壳已无权答复的 toast 上的一按，抬起来的是窗口而不是一次答复。抬窗不是安慰奖：这次请求通常还挂着，因为页面也是它的客户端，而 Host 只在最后一个客户端弃权时才按 `next` 结算，所以那张卡就在窗口里等着被答；而当它确实没了，它的消失本身就是「这一按发生了什么」的答案。无论哪一种，都留下一行日志。

**没能送达 Host 的那次拒绝会被重发，而且宁可弃权也不把请求吊着。**这次答复是一个可能失败的 POST，而 Host 会把没收到答复的投递重放一遍。给这次重放走普通宽限，就会在一分钟后答出 `next`，把用户的拒绝无声地丢掉——因为这个 id 已经报过一次，不会有第二条 toast 再来问。于是被拒绝的投递 id 一直被记到答复被接受为止，重放到同一个 id 时直接重发那次拒绝，而不是重新武装宽限；而 Host 在结算之前就把答复方移出了这次投递，所以送达了的那次拒绝只能在响应里自我清理，等不到一条不会来的 `cancel`。任何失败的答复都会重新领一次宽限，因为在听到答复之前 Host 一直把这个壳算作这次投递的客户端，其间别人的 `next` 也结算不了。于是连失败两次的拒绝，最终会变成它本来在跟其争的那次弃权——这里唯一做的一次取舍，而它输掉的那一半，是一个吊着不动的请求。

**已经没了的请求不再为它报消息，而这条投递仍然可以再报一次。**每次 waterfall 播报之前都要先走同一条 HTTP 通道去查会话标题，而这次往返飞行途中投递可能被结算，socket 也可能断掉。查名的后续会重新确认壳仍在等这条投递，然后才播报；于是被结算掉的审批不会以一条「带着两个可按按钮、却没人还持有这个请求」的 toast 形式到达。放弃播报的同时它也把这个 id 从「已报过」里删掉，因为丢了 socket 不等于请求结束了：Host 会把这条投递重放给下一个注册上来的客户端，而一次「发现 id 已报过」的重放会什么都不说，让这个请求永远没有通知。

`toastButtons` 只在 Windows 上画出这些按钮。Electron 同时为 macOS 声明了 `actions`，但 macOS 在这里根本走不到 `Notification`——壳在 macOS 上用 Dock 角标加一次弹跳来回应这类时刻——而 Linux 的 `Notification` 直接忽略 `actions`。

即便发错了词也是构造上安全的：`dsh-user-approval` 会把词汇表之外的任何答复归一成 `unavailable`，而它拒绝这次工具调用。答错的壳只可能多拒，绝不可能误批。

## Testing

`apps/desktop-shell/tests/notifications.spec.ts` 以纯函数的方式钉住按钮的顺序、文案和平台规则。`apps/desktop-shell/tests/toast-answer.spec.ts` 直接驱动这个模块——替身 `WebSocket` 全局投递 `ready` 与一次 `approval/request` waterfall，替身 `Notification` 接住那条 toast——并从环回服务器上读回答复：按下「拒绝」时 `$events/result` 的确切载荷、按下「去看看」时的抬窗、`cancel` 之后按下 / 按第二次 / 断线重连期间按下时的抬窗与日志行、被宽限 `next` 关掉的 toast、被 `cancel` 关掉的那条不带按钮的提问 toast、被停掉这一代关掉的 toast、查名途中被取消因而根本没弹出的那条 toast 以及断的是 socket 时在重放上补弹出来的那条，还有一次失败的拒绝在重放时被重发、被接受后被遗忘、连失败两次后转为弃权。

**「什么都没答」断言的是模块发出了什么，不是环回服务器收到了什么。**`fetch` 是被包了一层而不是被替换，于是任何一次答复在请求发出的那一刻就被记下；同一条断言若写成对着服务器收到的载荷去比，在「点 toast 本体也发一次拒绝」的变异下会通过，因为断言执行时那个 POST 还没落地。

Windows 的 toast 本身无法单测，验收在真 Windows 机上对着安装版进行——按钮依赖 NSIS 安装器写到开始菜单快捷方式上的 AUMID，而 `pnpm dev` 不会创建它。有五件事只有那台机器答得了：

1. 按下按钮是否会同时触发 toast 的 `click`，那样每次「拒绝」都会连带抬窗。
2. 两个按钮是否都画了出来、顺序是否如此，在正文这么长的一条 toast 上。
3. `close()` 对已经收进操作中心的横幅到底做了什么——Electron 只承诺「尝试」移除。
4. 应用退出后仍留在操作中心里的那条 toast，按下它的按钮会发生什么，会不会把应用拉起来。
5. toast 弹出一分钟以后再按下，落点在哪里——窗口起来了，审批卡还在上面，或者明显已经不在了。

## Alternatives considered

**「批准」也放上 toast。**否决，因为在 toast 上批准的是 toast 没有展示过的东西。正文只说了会话和工具名；真正让一次批准成其为决定的那些内容——命令、路径、差异——都在窗口里那张卡上。

**改用 `{ kind: 'rejected', error }` 而不是 `result` 答复。**否决，因为那个 outcome 是通道自己的失败通路：它让 Host 的待决 promise 被拒绝，而不是结算这次审批，审批服务读到被抛出的答复只会当成 `unavailable`。用户按了一个按钮，这是一个答案，不是一次传输失败。

**壳答不了的那一按只写日志、别的什么都不做。**否决。它看着整洁——反正 Host 也会丢弃迟到的答复——但它留下的是一个看着能按、按了却什么都不答的按钮，而这条 toast 到达用户手上时，多半正是壳已经交出答复资格之后。抬起窗口是唯一一个无论那次请求后来怎样都成立的回应。

**请求在别处被结算时，把那条 toast 留在操作中心里。**同理否决。把每条已弹出的 `Notification` 挂在 generation 上再关掉，代价是一张 map 和一次调用；换来的是 toast 绝不会活得比它所问的那件事更久——一旦壳自己的宽限答复也是「问完了」的方式之一，这就是正确性，不是整洁。

**接上 `Notification.handleActivation` 的冷启动通路。**没做。Electron 43 会把「按在一条内存里已无 `Notification` 的 toast 上」——包括跨过一次应用重启活下来的那条——路由到这个静态回调；但冷启动的壳没有 generation、没有客户端注册、也没有可以把这一按对上的投递，要让这一按有意义，得先让壳重开事件流、并确认那次请求仍然挂着。在那之前，按上一轮进程留下的 toast 够不到任何投递；至于 Windows 自己拿这一按去做什么——包括会不会把应用拉起来——是真机要回答的问题之一。

**用 `toastXml` 或 `electron-windows-notifications` 来承载 toast 上的按钮。**没有必要：Electron 43.4.0 在 Windows 上原生支持 `button` 类型的 `actions`，而这个应用早已设置了 Windows 要求 toast 发送方持有的那个 AUMID。

## Consequences

壳不再是一个只会弃权的客户端：它的流里有一种投递现在可以由它结算，模块里的 `answer` 也因此接收 outcome，而不是假定 `next`。它播报的其他事情——一轮跑完、一个问题、一份计划评审——依旧不带按钮；一个问题的答案不是二选一，需要另一种 action 类型。

从 toast 发出的拒绝抵达模型时就是普通的那次拒绝，所以 agent 的重试或改问，与从卡片上拒绝时完全一样。用户按下它不会失去任何东西，也不会获得任何他本来做不到的事——只是省掉了窗口这一趟。
