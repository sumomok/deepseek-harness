# Agent Note：让表自己决定画哪几列，空答复也要说清是空

Status: implemented

[English](2026-09-07-data-source-default-columns.md) | 中文

## 问题

[数据来源那条缝](../architecture/2026-09-06-content-component-library-v2c-data-source.zh.md)让模型可以从这套部署自己的后端往 `toy.table` 块里填行。拿它对着真实部署跑起来，暴露出两种那条泳道不可能显出来的失败——两者都要同时有活的模型和活的后端才看得见。

**模型被要求画一张表时会猜属性名，而其中一种猜法永远不会失败。** 第一次调用点的是表里没有的属性，被拒，拒绝里列出了真实的属性名，于是第二次成功——这个回路是有效的。回路救不了的是另一种猜法：在 `SpaceLayer` 上模型挑了 `layer_en_name` 与 `layer_type`，它们存在，而且行行为空。读取成功，表画出一列数据加两列空白，模型却告诉用户它画了三列数据。任何地方都没有相反的说法：拒绝路径根本没触发，结果行只报行数与属性名，模型和用户都没有被告知三列里有两列是空的。

**条件没匹配上任何行的读取，被报成了数据源坏了。** 对真实部署实测：匹配不到行的 `_search` 答的是 HTTP 200 加 `{ code: 0, msg: 'success', data: { rawValue: null, displayValue: null, page: { total: null, … } } }`——两份行列表都是 null，不是两份空列表。`readSearchData` 要求两者都是数组，于是这条缝把这种答复分类成 `unreachable`，detail 是 `the answer carried no rows to read`，模型读到的是「数据源联系不上」，而事实是一次普通的空结果。模型接下来要么重试要么告诉用户系统坏了；两者都不是真相，真相是它的筛选没匹配上。

第一条背后还有第三处缺口：`page` 说的是一页多大而不是第几页，所以想读第一页没够到的行的模型，只有「收紧条件」这一条路，没有翻页的办法。

## 决定

**不写 `tableConfig.gridItems`，就是这次调用在说「用这张表自己的列」。** 连 `tableConfig` 一起不写也可以。列于是来自这张表的默认查询方案——本部署自己的资源清单打开这个模型时用的那份存储方案——经新增的 `bizBackend.describeScheme(meta, signal)` 读来。方案藏起来的列被去掉，同一个属性被方案列了两次时只留第一次，其余保留方案的顺序、它的表头和它的可排序位。往下的一切都不变：同一道字典核对、同一次读取、同一条 `content-component/resolved`。

**这是工具的默认值，不是技能教的一步，因为它消掉的失败是模型看不见的那种。** 猜一个不存在的属性名，代价是一次拒绝，随后被拒绝里那份清单纠正——这个回路本来就有效，技能只能让它短一点。猜一个存在却行行为空的属性，产出的是一次成功的调用、一张画出来的表，和一句对用户说得很笃定的话；没有任何信号可供技能挂上一次纠正。唯一知道那张表值得画哪几列的一方是部署，而它已经为这件事存了一份方案。默认值触达每个模型的每一次调用，包括那些没人想起要加载技能的调用。

**在用户答之前，什么都不向后端请求，方案也一样。** 于是卡片说的是这次读取取的是这张表自己的默认列，一列都不点名——`取这张表默认显示的列`——因为具体是哪几列，由那份还没读的方案决定。这几列由哪一方挑，是这次读取里模型没有挑的那部分，也是人在回答之前有权知道的；而列名本身要花一次带凭据的请求，凭据恰恰就是这张卡片正在申请的东西。方案在读字典的地方读：答完之后，取行之前。

**方案让这张表画不出来，就拒掉这次调用，并用本工具自己的说法点名该改送的参数**：`Send tableConfig.gridItems on that block, naming the attributes to read.` 它不点名任何别的工具，因为哪个工具帮得上是模型自己的判断，不是这句拒绝的。四件事会在这里结束一次调用——这张表没有默认方案、方案请求本身失败、方案要从一个这张表字典里没有的属性上画列、方案展示的列比一张表画得下的还多——每一句都说清出的是哪一件，措辞点名的是方案。没有一句说调用点了什么，因为这次调用一列都没点名：一句「某列不对」说的会是模型从没写过的东西。后两件在问到任何一行之前就拒，因为画不出来的行，是白白花掉的一个人的数据。属于凭据而不属于这张表的失败（`unauthenticated`、`refused`、`rejected`）保留它们自己的句子。

**两份行列表都显式为 null，就是零行。** `search` 对这种信封答 `{ rawValue: [], displayValue: [], total: 0 }`——实测这个后端对匹配不到行的读取给的就是它。`unreachable` 留给载荷不是对象、行列表在场却不是由行对象组成的列表、以及两份行列表一个都不带这三种情况——它们才真的是这条缝读不懂的答复，包括谁都没见过这个后端发出来的那种信封。它上面那层工具的行为不动：零行仍然是 `"<table>" returned no rows for those conditions, so there is nothing to draw`，这才是模型能据以行动的句子。

**结果行加上读了第几页，和哪些属性空着回来。** 页号在属性清单之后单独成一句——后端报了总数时是 ` Page 3 of 5.`，没报时是 ` Page 3.`——因为写在那份清单里面，它读起来会像是多出来的一个属性。之后，这次读要的属性里只要有哪个在到达的每一行里都没有值，就加 ` No value in any read row: layer_en_name, layer_type.`。每个属性都在某一行有值时，什么也不多说——每次都出现的从句是模型会不再读的从句。空列被点名而不是从表里去掉：去掉等于在用户批准之后改掉他批准的那次读取。

**`page` 新增 `currentPage`**，1 或更大的整数，与既有的 `pageSize` 并列，不写时取 1。让它可用的正是结果行里的页号——分不清自己读的是第几页的模型，也就要不了下一页。

**会话日志的载荷不变。** `content-component/resolved` 的 `fetched` 各项仍然带 `nodeId`、`meta`、`rows`、`total` 与 `columns`。页号和空属性是从已经记下的东西里读回来的——spec 带着行，块带着列——所以把它们记下来等于在一份持久格式里存一个派生事实的第二份副本，`SESSION_FORMAT_VERSION` 于是原地不动。

### 闸门表——表自己的列，与一次空答复

| **3 — 做成缝还是写死** | **读做成缝，选哪几列写死。** `describeScheme` 是既有 Service Definition 上的第三个方法，换后端的部署在自己的 provider 里写它。默认列取自查询方案——而不是比如字典的前 N 个属性——是写死的，因为方案就是这个部署自己的页面打开这张表用的东西，而第二条规则需要第二套部署才立得住。复审触发器是一套资源清单不由存储方案驱动的后端。 |
| **4 — 每个方向一行** | *邻居*：多一个具名读，仍然没有写，也仍然没有调用方自己挑的路径。*契约*：答复之前什么都不请求，方案也一样；一张还不知道会取哪几列的卡片，能说的是这几列由哪一方挑。*诱惑*：不在调用之间缓存列清单，也不为自己点名了列的调用读方案。*红线*：问句在每一个请求之前，且只有 `allowed-once` 放行。*天花板*：卡片说的是一页多大而不是第几页，所以读第三页在用户那里用的是读第一页的措辞。 |

## 考虑过的替代

**改用技能来教默认列。** 按各自修的是哪种失败驳回。技能可以让模型先去查一张表有哪些列，加载了技能的模型也会照做；出问题的是没加载的那个模型，而它的调用成功、画出空白、报出三列数据。没有错误可供技能捕捉，也没有拒绝可供纠正。工具默认值作用在真正发出的那次调用上。

**在问之前先读方案，好让卡片点名它即将取的那几列。** 按三点驳回。凭据不在问之前花，而读一次方案就是在花它。一次调用最多点十二个块，于是模型可以对自己挑的十二张表发出十二次带凭据的请求，而没有任何人同意过其中任何一次——每一轮都可以，只要它还在继续调用。再有，方案请求自己的失败带着后端的状态码、错误码与消息，而它们会作为一次没人批准的请求的答复到达模型。

**拒掉不写 `gridItems` 的调用，叫模型自己去取列。** 驳回：那和模型现在因猜错属性名而损失的那次往返是同一次往返，前面还多加一次拒绝，而空列那种失败还留在原地。

**把空着回来的列在画之前去掉。** 驳回。用户批准的是读点名的那几列；一张悄悄少了两列的表，和卡片描述的那次读取不是同一次。改成告诉模型，由它决定。

**把页号与空属性加进 `content-component/resolved`。** 驳回：两者都能从那条事件已经带着的东西推出来，而持久格式不是放派生事实第二份副本的地方。

**把 `isShow` 读成「方案没说就是藏」。** 驳回——它是表格组件自己的字段，只在显式 `false` 时藏一列；同一个包里对同一个字段名有两种读法，是在等一个省略它的方案来出事。

## 后果

**买到了什么。** 不认识一张表的模型也能把它画出来，用的是部署自己给它展示的那几列；而当它要的某一列行行为空时，它会被告知。匹配不到行的筛选读起来就是匹配不到行。

**付出了什么。** 不写列的调用，每次多一次请求，发在答复之后、用这次答复放行的那份凭据。这些调用的卡片一列都不点名，所以想从卡片上核对即将读什么的人，只能读到这几列由哪一方挑。这张表画不出来的方案，要等用户答完之后才发现，而在它拒掉之前，读字典和读方案这两次请求已经花掉了。

## 已知限制与延后事项

- **卡片说的是一页多大，从不说第几页。** 读第三页被描述成 `取最多 200 条`，和第一页用的是同一句话。模型要的东西和用户被告知的东西，在「读的是哪些行」这一点上、也只在这一点上对不上；标识行和列清单不受影响。要说出来，需要为一个控制台别处都没展示过的概念，写一句用户自己语言的卡片文案。
- **「每一读到行里都为空」说的是到达的那些行，不是整张表。** 一列在第二页有值，被只读到第一页的那次读取报成空。句子写成 `in any read row` 就是这个缘故。
- **方案每次调用读一次，哪儿都不缓存。** 两次调用点同一张表，就读两遍。
- **`describeScheme` 未经真实部署验证**，与它旁边那两次读一样：它读的那几个响应字段——`grid.gridItems[].{relatedMetaAttr, alias, isShow, isSortable}`——取自部署自己的前端源码，而这些用例里的每一个后端都是假的。
