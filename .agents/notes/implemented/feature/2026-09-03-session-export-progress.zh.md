# Agent Note: Session export progress read from the archive stream

Status: implemented

[English](2026-09-03-session-export-progress.md) | 中文

## Problem

`dsh-session-log-export` 把导出 URL 交给浏览器后，立刻告诉用户下载已经开始。这个说法没有任何依据；在桌面客户端里，它在最要紧的意义上往往就是假的：页面根本不知道有没有字节真的动过、还剩多少、传输是否已经失败。路由以 `Transfer-Encoding: chunked` 流式发送归档且不带 `Content-Length`，因此即便由浏览器接管传输，也没有任何数据可以用来画进度条。失败比不可见更糟。子会话日志或附件读不出来时，Host 已经回了 `200`，只能在之后让流出错；而本包 README 把这类报告推给了「浏览器下载管理器」——DSH Desktop 外壳恰恰没有这个界面：它没有在主窗口注册 `will-download`，也没有自己的下载 UI。于是一个被撕裂的归档，到用户那里成了一条成功提示。

## Decision

Host 在归档字节之前先声明它的规模，页面则自己完成传输。

[`src/archive.ts`](../../../../packages/session-query/session-log-export/src/archive.ts) 中的 `measureSessionLogZip` 在流式传输前把这次导出遍历一遍，返回 `{ entries, bytes, estimatedWireBytes }`：ZIP 条目数、未压缩大小总和，以及响应体将要承载的字节数的估算值。日志大小是流将要推送的规范 JSONL 的精确 UTF-8 长度；媒体大小取自每个 `ImageAttachmentRef` 记录的 `bytes`，因此测量会重新读取每个子会话日志，但绝不重新读取已存储的图片。测量与条目流用的是同一个遍历函数 `sessionLogTextEntries`，但各跑一遍——一遍测量、一遍产出——因此两者对归档形状的认识一致，看到的却是两个不同时刻：在两遍之间追加了事件的活动子会话，会让声明的总数低于归档实际承载的量。线上估算值对日志条目施加标定系数 0.14——真实会话 JSONL 的压缩比落在 0.13 到 0.15 之间——对媒体按原值计，因为 PNG 与 JPEG 无法进一步压缩；在 `compressionLevel: 0` 下归档只存储不压缩，该值与真实体积之间只差它忽略掉的 ZIP 框架。路由把这三项作为 `X-Session-Export-Entries`、`X-Session-Export-Bytes` 与 `X-Session-Export-Estimated-Wire-Bytes` 同时发在 `GET` 与 `HEAD` 上；页面与路由同源，因此不涉及任何 CORS 暴露名单——只有连接载体保留的 null-origin 兜底路径例外，那时三个字段读不到，进度条退回不确定态。测量失败只会让这三个字段缺席，别无影响：测量能遇到的每一种失败——子会话日志缺失、句柄不可读、谱系读取出错——流式传输都会再遇到一次，由它对结果负责，仍然让流出错而不是发出被截断的归档。

浏览器半包通过 `fetch` 请求路由，并逐块读取 `response.body`。[`src/client/progress.ts`](../../../../packages/session-query/session-log-export/src/client/progress.ts) 是那个纯粹的模型：它累加已接收字节，并跨块边界统计 ZIP 局部文件头签名（`50 4B 03 04`），在块之间携带三个字节，使被切开的签名依然能匹配。两种度量都是下界，上报的比例取两者中较大者，并在传输期间被压在 1 以下。已接收字节除以的是线上估算值，而非未压缩总量：这里的种子样本压缩比为 7.6 倍，拿 103 KB 上线字节去除 780 KB 日志，只会爬到八分之一再猛跳——真机上验过，那读起来像传输卡住而不是正在推进。当归档压得比标定更狠时，条目计数会把估算值抬离下界；一个条目只有在下一个条目的头到达时才算完成，因为头总是先于它自己的数据，而条目计数又被封顶在声明的总数上，因此压缩数据里偶然出现的签名最多让进度条提前一个条目，绝不会越过终点。

没有子会话、没有附件的会话所导出的单条目归档，正是由这个估算值带动的——这里每一个种子样本都是，也正是条目计数毫无分辨率的场合。既然是标定值而非精确值，它有两种可见的偏差表现，但两种都仍读作「正在推进」：压得更狠的归档会在流结束前到达 0.99 天花板并停在那里，压得更松的则从约八成处直接完成。没有这些响应字段时比例为 `null`、进度条为不确定态，旧版 Host 也会落到这条路径上。

流结束后，控制器把各块拼成一个 `Blob`，点击指向其 object URL 的游离锚点（文件名读自 `Content-Disposition`），并在一个任务之后回收该 URL；`Content-Disposition` 先按 RFC 5987 的 `filename*` 读取，其次才是普通参数。下载状态存储按动画帧批处理，因此分成许多块的归档只会每帧重绘一次面板，而不是每块一次。面板新增了进度条、一行说明已到达多少的 `已导出 <大小>`、一个完成态，以及一个失败态：路由在流式传输前拒绝时说明 HTTP 状态码与 Host 的报错信息，连接失败或归档中途撕裂时则说明浏览器的传输错误。Host 无法描述在它的响应开始之后才发生的失败，因此被撕裂的归档到达页面时只是 `network error`：面板报告的是「导出撕裂了」——这正是原先那条提示从不曾做到的——而不是为什么。传输进行时，面板底部按钮用于取消——中止 `fetch` 并把该会话恢复为空闲；传输结束后它变为关闭。标题栏的关闭控件仍然只是收起而不取消，因此用户不再盯着看的导出照样会完成、照样会保存。`HEAD` 预检被移除：`fetch` 在响应头到达时就 resolve，`response.ok` 覆盖了预检原本覆盖的每一种流前失败，而读取响应体又补上了预检做不到的中途失败。

这必须是一个核心补丁，因为导出 UI 与导出路由属于同一个上游插件。fork 插件可以新增路由或槽位占位组件，却无法在保留 `session-log-download` 的 Host 半包的同时替换它的客户端半包：进度条需要路由算出的规模，而遍历归档的地方正是路由。

## Alternatives considered

**由外壳侧从 Electron 的 `DownloadItem` 取进度。** 桌面主进程可以监听 `will-download` 并按项上报 `receivedBytes`/`totalBytes`。它需要一条新的「外壳到页面」通道才能把这些数字送进 React 树，会让浏览器版本完全没有进度，而且它仍然无法在导出所在的地方把中途失败呈现出来——被撕裂的流传到 `DownloadItem` 只是外壳 UI 里一次中断的下载，页面看不见。页面本就握着响应，在那里读取不需要任何新通道，而且服务于每一种构建。

**为一次性下载再开一个进度上报端点。** 用一个以导出 id 为键的服务端推送通道，可以让锚点导航保持原样。它要新增一个端点、一份按导出维度的服务端身份，以及那份状态的生命周期，只为描述一次页面本可以自己完成的传输。它同样无法报告发生在页面并不拥有的那次下载内部的失败。

**改用 STORE（不压缩）归档，让字节总量精确。** 关掉压缩后，已接收字节就等于声明的未压缩总量，比例也就不需要第二种度量。代价是每次导出都显著变大，而条目度量本已覆盖了可压缩场景、进度条已经够准；并且它会为了展示层面的理由去覆盖已配置的 `compressionLevel`。

**在流式传输之前把整个归档压进一个计数器，从而声明压缩后的总量。** 这是让百分比对每一种归档（含单条目归档）都精确的唯一办法，而且能彻底删掉条目度量。代价是在本次改动已经付出的第二遍读取之上，再叠加一次对整个归档的完整 deflate，外加重新读取每一张已存储图片——媒体条目同样计入上线总量——于是一次导出的全部压缩开销都落在它的第一个字节之前。在实测规模下这只是毫秒级，但它会让「首字节时延」在所有部署上都变成归档总大小的函数，而本包存在的意义正是流式传输、绝不持有也绝不重做归档。

**在面板里显示条目计数。** 单条目归档在整个传输过程中显示的都是 `已导出 0/1 项`，而那正是常见的会话。该计数改为只作比例的下界继续存在——在那里它确实起作用，也不必假装自己在描述这次传输。

**从 `Content-Length` 推导总量而非使用自定义字段。** 归档是增量产出的，发送响应头时它的压缩后长度还不可知；为了得到这个长度而在 Host 侧缓冲整个归档，等于放弃本包赖以设计的有界内存流式传输。

## Consequences

页面在保存前把整个归档作为 `Blob` 驻留内存，且在数据块列表与 `Blob` 并存的瞬间会持有两份，因此导出受标签页内存限制，而非受可用磁盘空间限制。实践中会话归档是兆字节量级——这里最大的种子样本是 103 KB——数 GB 的会话树从此无法处理。Host 自身的流式传输仍然有界：它从不缓冲归档，只有浏览器这一侧会累积。

现在每次导出都在第一个字节之前多付一遍子会话日志的读取，且每个活动子会话会被 flush 两次——一次在测量读取它之前，一次在流读取它之前。第二次屏障已经没有任何东西需要落盘。因此首字节时延随子会话数量增长；没有子会话的导出只多付一次 `traceSession` 调用，完全不多读日志，因为根日志由路由读取一次并被两遍共用。

保存下来的文件来自应用自身源上的 `blob:` URL，而不再来自一次 HTTP 导航。Chromium 保存它的方式与它此前保存导航式下载一致，这一点由浏览器版本自己的端到端运行断言。Electron 外壳位于 `develop` 线、不在本代码树内：那里只有登录窗口与无头渲染窗口注册了 `will-download` 且都直接取消，主窗口没有处理器，因此两种 URL 形态都落到 Electron 的默认下载流程。

包内测试钉住了模型与两个半包：`progress.client.spec.ts` 覆盖响应字段解析、按线上估算缩放的单条目归档、被切开的签名计数、封顶、单调性与 0.99 天花板；`controller.client.spec.ts` 用返回分块 `ReadableStream` 的 mock `fetch` 驱动，断言进度序列、拼出的 `Blob`、两种 `Content-Disposition` 文件名形态，以及 HTTP、传输、缺失响应体、中途失败与取消各条路径；`archive.host.spec.ts` 断言在「一个子会话加两个附件」的会话树上，声明的总数等于归档真实的条目数与未压缩大小，断言 level 0 下估算值即精确值，并断言测量失败时这些字段缺席。整机装配在本代码树内由 `apps/web/tests/navigation-panes.e2e.ts` 覆盖，并随本次改动更新：它对着真实路由驱动 Session Header 按钮，断言 `GET` 带有三个规模字段，并解压页面保存下来的归档。

存储读不出来的附件不再撕裂归档：[读不出的媒体 Note](../bug-fix/2026-09-04-export-records-unreadable-media.zh.md)改为把那条条目记录进导出内部，因此面板的传输撕裂态如今覆盖的是连接失败、取消，或读不出来的子会话日志。

上游落地同等能力即退役：一次导出的进度与失败在页面里可见。
