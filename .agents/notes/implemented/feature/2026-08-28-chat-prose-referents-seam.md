# Agent Note: the `proseReferents` chat-prose scanning seam

Status: implemented

English | [中文](2026-08-28-chat-prose-referents-seam.zh.md)

## Problem

Inline-code file mentions (`chatFileMentions`/`MarkdownFileMentions`) already make a known-file token inside backticks clickable, but only inside code and only against a vocabulary of files the closing turn actually produced. Everything else in an Assistant message's prose — an absolute path written as plain text, a `~/…` shorthand, a bare URL, a UNC share — stays dead text with no interception point at all, even though the same `referent/open` seam (`packages/client/runtime/src/client/referent.ts`) already exists for exactly this purpose on file cards and the `openFile` chokepoint. A plugin that wants every clickable reference in a reply's prose — not just inline code, not just produced files — has no contract to implement.

## Decision

**A new optional service, `ProseReferents`** (`packages/client/ui-conversation/src/client/contract/slots.ts`), mirrors the `ChatFileMentions` convention exactly: `ctx.get('proseReferents')` is the only way in, a `declare module` merge adds `proseReferents` to `Context`, and an absent provider turns the whole surface off. Its one method, `scan(text, { cwd, home, inlineCode })`, is pure — no IO, no `stat` — and returns non-overlapping `ProseReferentSpan`s (`start`/`end`/`kind`/`target`/`raw`, the same fields `ReferentRef` itself carries minus `sessionId`/`source`/`provenance`).

**`render.tsx` (ui-primitives) stays detection-free.** `MarkdownRenderContext` gains one more optional field, `referents: MarkdownProseReferents | undefined`, holding a bound `scan(text, inlineCode)`/`open(span)` pair the renderer treats as fully opaque — its own `MarkdownProseSpan` type carries only `start`/`end`, never `kind`/`target`/`raw`. This keeps ui-primitives free of any dependency on `dsh-client-runtime`'s `ReferentKind`: the renderer slices `text.slice(span.start, span.end)` into a `css.fileMention`-styled `<button>` (the same always-visible mention token `fileMentions` already uses — no new style invented) and, on click, calls `referents.open(span)` with the exact object `scan` returned; the owner that built the bound pair is the only party that ever reads the fuller fields. `case 'text'` gained this scanning outright (it previously just returned the raw string); `case 'inlineCode'` runs it only after `fileMentions` declines the token, so a known-file mention still wins over the generic scanner. Both stay off inside `context.inLink` (no interactive element nests inside an anchor) and only ever run in `renderSettled`'s context — `StreamingRenderer`'s two frozen/tail contexts hard-code `referents: undefined`, the identical mechanism `fileMentions` already uses to keep a streaming message's cached elements from baking in handlers that could go stale.

**`apply.ts`'s `buildProseReferents(ctx, sessions, connection, sessionId)`** is the one place that turns the opaque render-facing pair into a real dispatch. `scan` reads the session's `cwd` (`sessions.list.getSnapshot()`, the same lazy read `openFile` already does) and the Host account `home` (`connection.hostDescription.getSnapshot()`, resolved via `ctx.get('connection') as ConnectionHandle` — this package has no ambient `ctx.connection` merge, unlike `ctx.sessions`/`ctx.workspaces`) fresh on every call, so composing the provider in or out takes effect on the next render with no re-registration. `open` builds its own `ReferentRef` — `source: 'chat-prose'`, `provenance: 'model-text'` — and dispatches it through `dispatchReferentOpen`, never through the `openFile` closure a few lines below (that would double-dispatch the click and mislabel its provenance `'structured'`). The default action, run only when nothing claims the click, mirrors the `openFile` chokepoint's own behavior: `url` → `window.open(target, '_blank', 'noopener,noreferrer')`, `file`/`dir` → `workspaces.openPath(target)`. `referents` threads down the exact path `fileMentions` already takes — `ChatViewInjected` → `ChatView.tsx` → `ChatNodeOwnerProps` (via `ChatNodeSeat`) → `AssistantNodeView` → `AssistantMarkdown` → `MarkdownText` — but as a plain per-session value rather than a per-turn-owner function, since prose scanning is not tied to one closing turn's produced-file vocabulary the way `fileMentions` is: it applies to every Assistant message equally.

## Alternatives considered

**Reusing the `openFile` closure for prose clicks.** Rejected: `openFile`'s `ReferentRef` is hard-coded `source: 'chat-view.openFile'`, `provenance: 'structured'` — correct for a tool-row/produced-file/mention click, wrong for model-authored prose. A listener that filters on `provenance` to treat structured and model-text opens differently would see every prose click misreported as structured, and the click would double-dispatch if both paths ever converged.

**Giving `render.tsx` the full `ProseReferentSpan` shape (`kind`/`target`/`raw`).** Rejected: nothing in the renderer needs to interpret those fields — it only ever slices `[start, end)` and hands the object back — so carrying them would add a real cross-package type dependency (`ui-primitives` → `dsh-client-runtime` for `ReferentKind`) purely to satisfy a type signature the renderer never reads. The opaque `MarkdownProseSpan` (`start`/`end` only) keeps the "renderer never guesses" boundary at the type level, not just in comments.

**Scoping `referents` like `fileMentions`, to `TurnTailOwnerProps` (closing-turn only).** Rejected: `fileMentions`'s vocabulary is genuinely turn-scoped — it answers "what files did this turn produce" — but a plain path or URL written in prose carries no such provenance; restricting scanning to only the last message in a conversation would leave every earlier Assistant reply's prose permanently dead even after composing a provider in.

**Detecting anything path- or URL-shaped inside core itself.** Rejected outright by the product's own line: core opens a generic seam and does zero classification; the plugin layer (`@haoran/dsh-clickable-refs`) owns every regex, OS-path-syntax, and refusal-list decision. This mirrors `chatFileMentions`'s own split (`MarkdownFileMentions.resolve` is a black box to the renderer) generalized to the same non-code case.

## Consequences

Absent a `proseReferents` provider, `ctx.get('proseReferents')` returns `undefined`, `buildProseReferents` returns `undefined`, and `MarkdownText` never receives a `referents` prop — `case 'text'` and `case 'inlineCode'` take the exact code paths they took before this seam existed, proven by every pre-existing `MarkdownText`/`AssistantMarkdown`/`ChatView` test passing unmodified plus a new explicit assertion (`apply-inject.client.spec.tsx`, `'referents (chat view face) is undefined with no proseReferents provider composed in'`). `packages/client/ui-primitives/src/markdown/render.tsx` and `MarkdownText.tsx` (not covered by the `ui-conversation/src/client/*` coverage exemption the prior file-attachment note empirically confirmed) carry 100% statement/branch/function/line coverage for every new arm: prose scanning, inline-code scanning after a declined mention, the `inLink` and streaming guards, adjacent zero-gap spans, and the absent-referents fast path (`markdown.client.spec.tsx`, `markdown-render-units.client.spec.tsx`). `packages/extensions/cordis-client-runner/src/client/slot-catalog.ts` (generated) picked up `ChatNodeOwnerProps.referents`/`ChatViewInjected.referents` via `pnpm run gen-client-catalog -- --write`; `api-catalog.ts` regenerated identical (no `ISession`/API-surface change). `SessionEventMap` is untouched — this is a pure client-rendering seam, no session log involvement, no `SESSION_FORMAT_VERSION` bump.

## Retirement

This seam is a temporary overlay for a capability upstream does not have yet: if upstream's own conversation UI scans Assistant prose (not just inline code against a produced-file vocabulary) for clickable references and exposes an equivalent scan/open contract, this patch is retired and the fork adapts to upstream's form.
