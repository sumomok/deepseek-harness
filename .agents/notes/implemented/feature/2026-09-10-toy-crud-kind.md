# Agent Note: the deployment's own data page, opened in the panel with the visitor's credential

Status: implemented

English | [中文](2026-09-10-toy-crud-kind.zh.md)

## Problem

The [data-source seam](../architecture/2026-09-06-content-component-library-v2c-data-source.md) fills a `toy.table` block from the deployment's own backend: the host reads rows with the visitor's credential, puts them in the block, and records the whole filled entry. Reading rows into the log is the right price for a table the agent assembled for one question. It is the wrong price for the thing users kept asking for next, which is the page they already use.

**A read is a snapshot; what people wanted was the page.** `toy.table` draws what one call read. To page it, the model calls again. To re-sort it, the model calls again. To narrow it, the user edits a filter bar, the submit reaches the agent, and the agent calls again — a turn per interaction, each one a fresh approval card and a fresh read of that person's data. The deployment already ships a page that does all of this in the browser with no turn at all, on the same tables, under the same credential; the console had no way to put it in front of anyone.

**And every row the host reads is a row in the session log.** A filled spec is up to 65536 bytes, once per live entry, carried in every checkpoint the content surface writes. Paging a wide table through `dataSource` writes that person's data into a durable log once per page, and signing out does not clean a log already written.

The spike that measured the alternative found the customer's `Crud.vue` mountable as-is, and found four defects in the original sources while doing it: `crudCloudPermission` calling an `axios.get` that does not exist on the vendored barrel, `getCustomMode` calling a `crudService.getCustomerMode` that is not there, an unhandled rejection whenever the fire-and-forget front-event log fails, and a `console.log` of the signed-in user's profile in `crudUtil`.

## Decision

**Mount `Crud.vue` as-is as the content-column kind `toy.crud`, and let it keep its own credentialed request layer.** Data goes browser → deployment with the visitor's own token; the host reads nothing for this kind, records no row, and is never on the request path. That is the whole point: the page the user already knows, doing in the browser what it already does, with none of it passing through a session log.

**It ships from a second kit package rather than by rewriting anything.** `@sumomok/toy-crud-kit` is built beside `@sumomok/toy-surface-kit` in the kit repository, out of the same three customer libraries, under the same rules: sources copied read-only, changes only as patch files. Two rules bend, and each bend is stated in that package's own README. Its `toy-comp` shim is widened to the seven deep imports `Crud`'s closure reaches — which is what cuts the three `main.js` files whose module-time `Vue.use(Element, { size: 'small', zIndex: 2000 })` would move the shared runtime's defaults out from under every other block on the panel, and the duplicate `theme-chalk` import with them. And "identity and tokens never enter the component layer" becomes "components never read storage or cookies themselves; credential use is confined to `toy-core`'s request layer", because that request layer is the thing being shipped. The gate that enforces it scans the component sources and freezes the eight `toy-core` files that legitimately read a credential as an allowlist.

**The first version is read-only, and read-only twice over.** The host spreads a frozen `CRUD_READ_ONLY_PROPS` after whatever the call wrote — every write, import and export key hidden, the menu and card subtrees off, `isReadOnly` on, `type` fixed, `urlConfig` null — and the kit's build compiles the six write dialogs to empty stubs, so no property opens one. Read-only is about the table's own data: what the page still writes is one audit record per query, which Known Limitations records. Eight properties are the model's: `relatedMeta`, `metaLabel`, `conditions`, `matchMode`, `querySort`, `selectMode`, `isExpandQuery`, `isInitQuery` — seven of which reach the page, because `metaLabel` is the name on the card and stops at the host. None may be read from another block, because every one of them is on the card the user answers and the card is drawn before anything another block could resolve exists.

**The user is asked once, at placement, through the seam the data-source path uses.** Same service, same `allowed-once`, same order — judge the whole call, then ask, then record, and only then draw:

```
用您的账号打开「图层配置」的完整数据页，可以在里面查询、翻页、排序；小助手看不到表里的内容，只会知道有哪些列、每次查到多少条，以及您点到的那一行。
数据表：SpaceLayer
```

The identifier is written on a line of its own and drawn on one: the panel draws the reason's line breaks rather than collapsing them, which is one line of CSS in `ui-approval` and fixes the read's card in the same place. Hidden conditions are counted on the first line and never shown, because a condition's value is the model's text and the page draws none of it. Where this path differs from the read is that **nothing is requested by anyone before the answer** — not by the host, which requests nothing for this kind ever, and not by the browser, because the block is not on screen yet. A refusal draws nothing at all. Queries the user then runs inside the page ask nothing further; the page is theirs once it is open, which is what the card promises.

**The call's own `tool/call` records no entry.** `recordsEntry` leaves a spec carrying a data page out of the extractor and out of the invariant companion alike, so the entry is the `content-component/resolved` the tool appends after the answer and nothing before it. Drawing the entry from the call would put the page on screen — and its first credentialed request on the wire — before the question was answered, and would leave it there after a refusal. For the same reason a view a deployment writes may not place one: a click on the sidebar asks nobody, so such a view is refused at load, by id.

**Feedback to the model is columns and counts, never rows.** Three readings leave the block through the existing content-component action path, all graded `context`, and no new session event type: `load` names the table and the first 20 drawn columns of the page's query scheme; `query` carries the matched total, the rows shown and the page number; `cell-click` carries the clicked column and that one row's drawn cells, symmetric with what a `toy.table` selection reports. A load or query identical to the one a block last reported for the same call is not reported again, so a tab switch that drops and redraws the block does not say the same thing twice. Every column header in those readings came off the deployment's own scheme, so both accounts of it — the notice and the placing call's result line — render it through one function that reads it back on a single line.

**A load the placing call is still waiting for goes into that call's result line and nowhere else.** The call waits up to `crudLoadTimeoutMs` for a browser to report; `PendingLoads` settles single-shot, and a report a waiting call takes is not also delivered as a notice, so the agent reads it exactly once. The table is keyed by session first and entry id second, because one plugin instance serves every session a console runs and an entry id is a string the model chose: `layers` in two conversations is the same string and two different pages, and a report belongs to the session whose seat sent it. Within one session a later call's waiter replaces an earlier one's under the same id, and each call removes only its own, so the call that replaced an entry still receives its page's report. The timeout sentence says what still comes — the columns and counts arrive as notices once the page loads — because a model told only that nothing was reported would place the page again and ask the user the same question twice.

**The base path is a validated `Config` field, applied before the page can request anything.** `toy-core` captures `window.$toy_env.VUE_APP_BASE_URL` once, while its own module evaluates, and that module evaluates when the component row's browser bundle does — there is no moment before it in which a host could write the value. So the row's node half serves `bizBasePath` on `/component-kit/settings`, its browser half reads that once at start and hands it to the kit's `setBizBasePath`, which rewrites both the captured default and the live request instance, and `CrudRenderer` mounts nothing until that read has settled. The value is a path and nothing else, judged at load by the node half and again over the wire by the browser half. Reading the string is not enough on its own: the browser's URL parser treats `\` as `/` under a special scheme, so `/\host/` names another origin, and it normalizes percent-encoded dot segments, so `/%2e%2e/api/` requests a path other than the one written. Both halves therefore resolve the normalized value against a probe origin with that same parser and refuse it unless the origin and the path come back exactly as spelled.

**Everything the page appends to `document.body` is confined to the block's own box.** `containCrud` marks the box, makes it the positioned ancestor, points `nprogress` at it, and moves body-level element-ui toasts into it; the kit ships its own copies of `toy-core`'s loading and message helpers, and `$notify` is overridden per instance so a scheme failure draws inside the block. Every CSS rule the tarball ships is prefixed at build under the box's own attribute selector, `theme-chalk` is not shipped a second time, and loading the package leaves `$ELEMENT` at `{ size: 'small', zIndex: 300 }`.

**Two of the spike's four defects are patched, two are recorded.** `0005` drops the `console.log` of the signed-in user; `0006` attaches a `.catch` to the front-event log, whose rejection nothing consumed. The `crudCloudPermission` and `getCustomMode` calls are dead in a read-only page — one needs `useCloudPermission`, the other has no call site — so they are recorded in the kit's README with their triggers rather than patched, on the standing rule that a patch is a maintenance obligation and an unreachable one buys nothing.

**The request layer takes no credential out of the address bar.** `0007` cuts the two branches in `toy-core`'s `getToken` and `getToken4a` that read `?token=` and `?token4a=` and write what they find into `accessToken` — the key `auth-gate` reads back as the signed-in visitor and mirrors into the cookie the proxy forwards. Those branches belong to the deployment's own login page handing a fresh token to the app it redirected to; the console is not that page, so a `token` in its address bar can only have come from a link someone sent, and a signed-in visitor who opened one would have had their stored credential replaced by this block's first request and every later request audited as the injected identity. Unlike the two dead defects, this one is on every mount's path, so it is patched rather than recorded, and the kit's eleventh gate now refuses a closure that reads a token out of a URL at all.

## Alternatives considered

**Rebuilding the page out of catalog blocks.** Rejected on what it costs and what it still would not be. The parts exist — a filter bar, a table, paging as repeated calls — but every interaction becomes a model turn, every turn a fresh card, and every page of rows a fresh copy of that person's data in a durable log. What the user would get is a slower, less capable imitation of a page they already know, and the console would own its bug history from scratch.

**Rewriting `Crud.vue` in React.** Rejected for the reason the surface kit records for its own components, at larger scale: the page addresses element-ui directly throughout and carries the request layer, the scheme reader and the query builder with it. A rewrite restarts a bug history the customer has already paid for, and it would have to be redone the next time their page changes.

**Letting the host proxy the page's requests, so the credential stayed server-side.** Rejected. It would put every cell of every query back through the host — the one cost this whole kind exists to avoid — and the host would then be the party that read them, which the card would have to say. Same-origin from the browser is what makes the promise on the card true.

**Asking per query rather than once at placement.** Rejected: the user is the one running the queries. A card per query would ask a person to approve their own typing, and the thing they actually agreed to — this page, this table, opened as them — is a placement-time fact.

**A new session event for the page's readings.** Rejected: the command registry already records each action document verbatim as `command/run`, which is exactly what the three readings are. A new event would be a second durable copy of a record that already exists, and `SESSION_FORMAT_VERSION` stays where it is.

**Writing `window.$toy_env` from the host before the kit module evaluates.** Rejected as impossible rather than undesirable — the kit module evaluates with the row's bundle, and there is no earlier moment in the browser half. Applying the path afterwards through `setBizBasePath` and gating the mount on it is what makes the ordering provable.

**Patching the two dead defects anyway.** Rejected: neither is reachable in a read-only page, and a patch file is a maintenance obligation that must be re-applied on every rebuild of the tarball. They are recorded with their triggers instead.

## Consequences

**Bought.** A user gets the deployment's own full page for a table, opened as themselves, and queries it without a model turn per interaction. The agent knows what the page is showing — the table, its columns, each query's count, the one cell the user clicked — and no page of rows enters the conversation or the session log. A query reports three counts; the only rows that leave the page at all are the drawn cells of a row the user clicked, one row per click, and those do reach the agent and the `command/run` record verbatim. The host makes no request for this kind at all.

**Paid.** A vendored 256 KB tarball with a hand-written `.d.ts` and no compile-time backing, whose sources have no upstream history to diff against, carrying forty third-party npm libraries compiled into it that no manifest or lockfile here names — so the tarball declares them itself and `THIRD_PARTY_NOTICES.md` is generated from that declaration, alongside the two it leaves external, which only the tarball's own manifest names. It is imported statically, so every console downloads the 878 KB page, and the 553 KB of `lodash` and `dayjs` under it, whether or not the deployment offers it. A page that can navigate the whole console away when its token is missing or rejected. A call that opens a page in a composition no browser attaches to pays the whole load deadline. Every query the user runs writes a durable audit record on the deployment's backend under their own identity, carrying the model's hidden conditions, which the card does not mention. And a second kit package to keep in step with the first.

## Known Limitations and Deferred Work

- **The page navigates the whole window when it holds no token or is answered 401.** `toy-core`'s request interceptor sends the browser to the deployment's login URL and the console goes with it — the page is drawn inside the shell, not in a frame of its own. Recorded rather than fixed, and acceptable only in the same-origin deployment this kind is for, where the auth gate keeps a token fresh in front of every request. A deployment that turns `crud` on without that gate accepts a console that can navigate away from a conversation.
- **The loading overlay and the progress bar are module singletons.** `containCrud` points both at the box that registered last, so two data pages on screen at once draw one page's loading state inside the other's box. One page per call is enforced; two calls can still leave two entries in the column.
- **Toast containment assumes every element-ui toast on the page is this kit's.** The observer that adopts body-level `.el-message` and `.el-notification` does not ask who raised them.
- **No selection reaches the agent.** The page can tick rows and emits nothing when the ticks change. Reading it would mean polling the mounted instance on a timer; v1 does not, and the trigger for revisiting is a user who needs the ticks to mean something.
- **Seven query controls are disabled stand-ins,** exactly as in the surface kit, so a query cannot be narrowed by a related attribute. **Icons draw as empty boxes,** since no icon font is shipped; none is visible in the read-only page.
- **`crudCloudPermission` and `getCustomMode` are left broken on purpose.** Both are unreachable in a read-only page — the first needs `useCloudPermission`, the second has no call site. The triggers are recorded in the kit's README, and reaching either without patching it first throws.
- **The kit's types are hand-written** against a JavaScript build, so a drift in the built component's own properties compiles cleanly and fails when the block is drawn.
- **A `load` naming a table other than the block's own is reported to nobody, and says so on screen.** A later call under the same entry id is a different table's page. It is not silence: the command answers the seat with 这个动作没能记下来。 and the chat row draws that refusal, for a gesture the user never made, about a page that is on screen and working. The window is small, and what it costs is one wrong-looking line rather than a wrong sentence to the agent.
- **Every answered query writes an audit record on the deployment's backend.** `Crud.vue` calls `toy-core`'s `crudEventLog` after each query, which POSTs `<bizBasePath>/nrms-resourcehistory/api/log/frontevent/` with the visitor's own token: the console's own path as `app_enname`, 查询 as the event, the table's name, and the query's parameters — the model's hidden `conditions` among them — as the event data. It is the deployment's own front-end audit trail, written under the visitor's identity, and neither the card nor the promise on it mentions it. Recorded rather than fixed: it is what the deployment's own page does with the same credential, and suppressing it would mean replacing `core/log`'s export before the page mounts. **The trigger is a deployment that does not want console queries in that trail.**
- **The page leaves three keys in the browser's own storage, and signing out clears one of them.** One mount and one query write `localStorage.userInfo` — the visitor's profile as `toy-core` fetched it and stored it back through its own `setUserInfo`, carrying the bearer token verbatim in the record's `token` field — and two localforage entries, `localforage//console/_schemaall_<meta>` holding the deployment's query, add and modify schemes for that table and `localforage//console/_meta_<meta>` holding its attribute dictionary. A jsdom probe of the vendored bundle recorded all three; a browser keeps the two localforage entries in IndexedDB rather than in `localStorage`. Every one of them is the page's own request layer writing, not host code. `userInfo` is already on `server-sidebar`'s sign-out key list and goes when the visitor signs out; the two localforage entries are not on it and stay, so one table's schemes and dictionary outlive the session on a shared machine. Recorded rather than fixed here: clearing the localforage database belongs to `server-sidebar`'s sign-out, beside the key list it already holds, and this change does not touch it. **The trigger is a console on a shared machine, where what one visitor's table looked like is the next visitor's to read.**
- **A page opened where no browser attaches costs the whole deadline,** once per such call. The ACP snapshot lane sets it to one second for exactly that reason.
- **Every console downloads the vendored page whether or not the deployment offers it.** 878 KB (222 KB gzipped) in this row's browser bundle, plus the 553 KB (100 KB gzipped) of `lodash` and `dayjs` the tarball imports rather than compiles in, on every boot, including the default `crud: false`. Recorded rather than fixed: a plugin's client bundle is one closure-factory file the loader fetches by name, so a dynamic `import()` has no second chunk to land in and nothing would fetch one if it did. Deferring the page needs a second fetchable artifact per plugin, which is a loader change. **The trigger is a deployment running the console with `crud: false` that measures the boot cost.**
- **The kit's build is not byte-reproducible.** Three builds of one tree gave two different bundles, differing only in the minifier's local symbol names; `FormItemComp.vue` imports `DisabledInputStub.vue` both statically and dynamically, which vite reports on every build. Nothing about behaviour changes, but re-running the build does not reproduce a given tarball's sha256, so the recorded hash is the hash of that one pack.
