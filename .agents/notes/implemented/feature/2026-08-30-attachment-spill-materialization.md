# Agent Note: Oversized text-file attachments lower via spill, not truncation

Status: implemented

English | [中文](2026-08-30-attachment-spill-materialization.zh.md)

## Problem

`@deepseek-ai/dsh-llm`'s `lowerFileBlockText` (added by the file-attachment wire/log/request series, `d56a5f7348`) truncates any text-file attachment's decoded content at a fixed `DEFAULT_MAX_LOWERED_FILE_CHARS` (16,000) before it enters a model request. A file past that cut loses everything beyond it — there is no way for the model to retrieve the remainder, unlike tool output, which already has a session-scoped spill path (`@deepseek-ai/dsh-spill-policy`) that keeps an oversized result on disk and lets the model `read`/`grep` it on demand instead of losing it. Attachments had no equivalent: large means truncated, silently and permanently.

## Decision

**Placement: stays at the existing per-adapter lowering call, not the `agent/request` waterfall.** Verified directly rather than assumed: `'agent/request'` (`packages/core/agent/src/runtime-types.ts:234-244`) is a route/config waterfall — its payload carries only `{ agent, turn, step, signal }`, no `messages` field at all, and it returns `LlmCallConfig` (`packages/llm/llm/src/call-config.ts:23`, provider/model/adapter defaults), never message content. Its own JSDoc states the constraint outright: "Model-visible content must use logged channels; this waterfall cannot mutate messages." Its dispatch site (`packages/core/agent-loop/src/agent.ts:457-460`) confirms the same: `proposedConfig` feeds `prepareCall`, never `buildRequest`. There is no mechanism here to rewrite file-block text, so the design falls to the spec's stated fallback — the same site the original truncation already used: each adapter's own `lowerFileBlocksFromStore` call, against its locally derived message copy, before `buildRequest`. This reaffirms the site the file-attachment-wire-log-request note already established for the same request-reconstruction-invariant reason (a lowering that ran centrally in `agent-loop` would desync `options.messages` from `session.deriveMessages()`); nothing about spilling changes that constraint, so nothing about placement changes either.

**A new package, not a new `dsh-llm` dependency on `dsh-spill`.** `dsh-spill` depends on `dsh-llm` for `CallId`, so `dsh-llm` cannot depend back on `dsh-spill` (or on `dsh-agent`, for `currentInitiator()`) without a cycle. `@deepseek-ai/dsh-attachment-spill` sits above all four (`dsh-agent`, `dsh-attachment`, `dsh-llm`, `dsh-spill`) and exports `AttachmentSpill` (`ctx.attachmentSpill`) plus `fileSpillOptionsFrom`, the one adapter-facing conversion into `dsh-llm`'s `FileSpillOptions`. `dsh-llm/src/file-lowering.ts` gained `FileSpillOptions`/`LoweredFileSpillRef`/`lowerSpilledFileBlockText` and an optional fourth `spill?` parameter on `lowerFileBlocksFromStore`; omitted, behavior is byte-identical to before (always truncate at the threshold). `LoweredFileSpillRef` is a structural type (`{ locator, retrievalHint }`) rather than an import of `dsh-spill`'s `SpillRef` — a real `SpillRef` satisfies it without `dsh-llm` naming the package.

**Idempotency is a process-local cache, not a storage-layer property — confirmed empirically, not assumed.** `saveTextFile` (`packages/spill/spill-local/src/store.ts:107-121`) writes to `join(dir, randomBytes(6).toString('hex') + '-' + safeName)` opened `'wx'` (exclusive create, fails on any existing path). A repeated call with the same `suggestedName` always lands on a fresh random path — there is no lookup-by-name and no content-hash dedup at this layer (the random prefix exists to defeat symlink planting in a shared root, not for idempotency). `lowerFileBlocksFromStore` runs once per request build, for the complete message history, on every step — an attachment referenced across N steps of a turn would call `resolveSpill` N times without a cache, materializing N distinct spill artifacts (N distinct locators, N distinct `attachment/materialized` events) for what is logically one attachment. `AttachmentSpill.resolveSpill` (`packages/attachment/attachment-spill/src/index.ts`) closes this with an in-process `Map<SessionId, Map<AttachmentId, SpillRef>>`: the first `resolveSpill` call for a (session, attachment id) pair in this process calls `store.saveText` and appends `attachment/materialized`; every subsequent call in the same process, same pair, returns the cached `SpillRef` without a second write or a second log append. Session ownership comes from `ctx.agents.currentInitiator().session.id`, read live rather than threaded as a parameter, so the id used to key the cache and the id the append targets can never disagree.

**Model-visible ⟺ logged, and what log replay reconstructs.** The locator string a spilled file's lowered text shows the model (`lowerSpilledFileBlockText`) is model-visible content; the `attachment/materialized` event is what makes it reconstructable from the session log, per the repository invariant. The event is appended synchronously, before `resolveSpill` returns the `SpillRef` that gets embedded in that same lowering call's output — so event order always matches request order: replaying the log up to any historical turn finds the locator that request actually carried. This does not promise a stable locator across process restarts: the cache is memory-only, so a session resumed in a new process re-runs `resolveSpill` on cache miss, `saveTextFile` mints a fresh random path, and a second `attachment/materialized` event is appended for the same attachment id with a different locator. Both events remain individually true records of what was model-visible in their own request; no request's lowered text ever shows a locator absent from the log. This is a deliberate scope line, not an oversight: making the artifact itself stable across process boundaries would require either a lookup-by-suggestedName primitive `dsh-spill` does not have (out of scope for this change — no other spill consumer needs one, since tool output is re-executed fresh rather than re-lowered from an immutable input) or content-addressing the artifact by the attachment id, which the local backend's exclusive-create-under-random-name design does not offer.

**Config, not a hardcoded tunable.** `AttachmentSpill.Config` (`packages/attachment/attachment-spill/src/index.ts`) is a schemastery `z.object` with two fields: `inlineWholeUnderChars` (default `DEFAULT_INLINE_WHOLE_UNDER_CHARS`, equal to the retired `DEFAULT_MAX_LOWERED_FILE_CHARS` from `dsh-llm` — one number until a deployment overrides it) and `previewChars` (default `DEFAULT_PREVIEW_CHARS`, 4,000 — how much of a spilled file's text still renders inline alongside its locator, so the model gets orientation without a mandatory extra tool call). Both are validated non-negative integers at load — once by the `z.object` schema (`ctx.plugin` parses `Config` before the constructor runs) and again by a manual `requireNonNegativeInteger` check in the constructor, defending direct construction that bypasses the schema parse, mirroring the same double-check already present in `attachment-local`'s `LocalAttachmentStore`. `DEFAULT_MAX_LOWERED_FILE_CHARS` itself is retired from its old role (an unconditional truncation cap) and repurposed as `dsh-attachment-spill`'s default inline threshold and as `lowerFileBlockText`'s fallback cap for the no-spill-options case — not deleted, since every caller that omits `spill` (a session-less LLM call, or a deployment without `dsh-attachment-spill` loaded) still needs a truncation bound.

## Alternatives considered

**Threading `resolveSpill` capability through the log at attachment-admission time**, so a `FileBlock` itself carries a spill decision the moment the file is saved, rather than lazily at each lowering call. Rejected: whether a file needs to spill depends on comparing its decoded length against a threshold that is deployment-configurable and can change between when a file was admitted and when it is later lowered (a session resumed under a different `dsh-attachment-spill` config); deciding at lowering time, the same site the original truncation already used, keeps that decision current and keeps the log holding only the durable attachment reference, never a request-time formatting choice.

**Cross-process durable idempotency via a lookup-by-suggestedName or content-hash primitive on `dsh-spill`.** Rejected for this change: it would require extending `dsh-spill`'s public seam for a need no other consumer has (tool-output spills are inherently fresh per tool invocation, never re-lowered from the same immutable input across steps), and `spill-local`'s exclusive-create-under-random-name design is deliberately built to defeat predictable paths, which a lookup-by-name would partially undermine. The process-local cache satisfies the immediate need (no duplicate spill within one process's handling of one session) without reopening that seam; cross-process locator stability is left as a known, documented limitation.

**Reaffirmed, not reconsidered: central lowering in `agent-loop`.** Already rejected by the file-attachment-wire-log-request note for the request-reconstruction-invariant reason; spilling introduces no new argument for revisiting it, since the same per-adapter site already exists and only needed an additional optional parameter.

## Consequences

`SessionEventMap` gains `'attachment/materialized'` (`packages/attachment/attachment-spill/src/types.ts`: `{ attachmentId: AttachmentId; locator: SpillLocator }`). `SESSION_FORMAT_VERSION` stays `0` — this is vocabulary growth in the merge-extensible event map, the same category as the file-attachment series' own `ContentBlockMap` addition, not a structural or envelope change. `packages/core/session/src/known-event-types.ts`, `docs/persistence-catalog.md`/`.zh.md`, `docs/config-catalog.md`/`.zh.md`, `docs/capability-seams.md`/`.zh.md`, `docs/subsystems/attachment.md`/`.zh.md`, `scripts/gen-cordis-catalog.ts`'s `SERVICE_PAGE`, and `scripts/gen-doc-graphs.ts`'s `SERVICE_ROLES` were all updated together with their generators re-run.

`packages/client/ui-conversation/src/client/locales.ts`'s `image.dropDesc` copy (both locales) changed from asserting text content "is sent as-is" to naming that text files are attached and read on demand — the prior wording became actively wrong once truncation stopped being the only outcome for a large file. `apps/web/tests/image-display.snapshot.ts` and `apps/web/tests/file-display.snapshot.ts` were updated/extended to match; the coordinator's initial pointer to `ui-attachment/src/client/labels.ts` for this copy was imprecise — that file only maps translation keys to label objects, the literal strings live in `ui-conversation/src/client/locales.ts`, confirmed via `grep -rln "dropDesc"` across the client packages.

Every touched package holds 100% per-file coverage on its changed source, scoped narrowly (`dsh-attachment-spill`'s full `src/**`, `dsh-llm`'s `file-lowering.ts` alone, both `llm-deepseek`/`llm-pi-ai` adapters), confirmed via scoped `vitest run --coverage --coverage.include=`. `pnpm run typecheck` (both `tsconfig.host.json` and `tsconfig.client.json` faces) and `pnpm run doc-sync` (28/28 gates) are clean. `pnpm run hygiene` required declaring `@deepseek-ai/dsh-attachment-spill` as a dependency of `packages/bundle/base` (consumed via `cordis.patch.yml`) and of `python/sdk-runtime` (reachable through `dsh-jsonrpc-agent-pkg → dsh-llm-deepseek`/`dsh-llm-pi-ai`), both added in the same change.

**A real model-turn snapshot proving a `grep`/`read` round-trip on the spill locator was not added to the keyless snapshot suite.** This harness's `test:snapshot` replays fixed model responses; scripting one that reads back a runtime-generated locator string would need `dsh-llm-replay`'s `{{fromRequest:<regex>}}` placeholder mechanism, which this change did not attempt (researched, not implemented, given the time and risk of a first hand-authored scenario of that shape). `apps/web/tests/file-display.snapshot.ts` instead gained a client-side round-trip regression test confirming an over-threshold file is never truncated in the composer/draft path, which is what that harness layer can assert. The actual spill-then-retrieve behavior was instead verified once, live, against the real DeepSeek API: `dsh web` booted from a scratch `$DSH_HOME` with a 95,562-byte Markdown attachment carrying a unique sentinel sentence as its last paragraph, sent through the same `session.prompt` wire call the browser composer itself makes. The session log recorded `attachment/materialized` with the artifact's locator, the model called `bash`/`grep`/`read` against that locator (a `read` at the tail offset landed exactly on the sentinel), and the final assistant message quoted it correctly — while `user/message`'s own `file` content part held only the durable `FileAttachmentRef` (id/name/bytes), never the 95 KB text, confirming the log stays small and the lowered text is reconstructable only through the separately logged locator. This is a real-API run, not a committed fixture, so it does not run in CI; closing that gap with a `dsh-llm-replay` scenario is left to a future change.

**Retirement.** This patch is a temporary overlay for a capability upstream does not have yet: if upstream adds an equivalent spill-on-lowering path for oversized file attachments — including resolving the same request-reconstruction-invariant-vs-lowering-placement question this note and the file-attachment-wire-log-request note both settled the same way — this patch retires and the fork adapts to upstream's form.
