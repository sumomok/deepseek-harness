# Agent Note: File attachments on the wire, in the log, and at request time

Status: implemented

English | [中文](2026-08-28-file-attachment-wire-log-request.zh.md)

## Problem

The prior commit gave `@deepseek-ai/dsh-attachment` a text-file storage seam (`saveFile`/`readFile`/`admitEncodedFiles`), but nothing calls it yet. A file still cannot reach a session: the prompt RPC has no content part for one, the session log has no block type for one, and no model request path knows how to represent one. This commit connects the seam end to end — client wire, session log, and model request — for text-only providers that accept no file part natively.

## Decision

**Wire and log.** `PromptContentPart` (`packages/host/apiproxy/src/api/sessions.ts`) gains `{ type: 'file'; name: string; text: string }`, with a matching zod branch in `promptContentPartSchema`. `ContentBlockMap` (`packages/llm/llm/src/types.ts`) gains `FileBlock { type: 'file'; attachment: FileAttachmentRef }`, mirroring `ImageBlock` exactly — a reference only, never inline text, so the log stays small and the referenced bytes stay independently verifiable. `durablePromptContent` in `api-proxy.ts` admits image and file parts in one `Promise.all([admitEncodedImages(...), admitEncodedFiles(...)])`, generalizing what was three image-specific helpers (`imageBlockIn`/`imageInEvent`/`referencedImage`) into generic `attachmentBlockIn<TRef>`/`attachmentInEvent<TRef>`/`referencedAttachment<TRef>`, with the image and file names surviving as thin wrappers. A new `session.file` RPC mirrors `session.attachment`: given a session and an attachment id referenced by that session's log, it returns the plain UTF-8 text (not base64 — a file has no binary transport ambiguity to canonicalize) for the bubble to render on expand.

**Session-shape validation and `SESSION_FORMAT_VERSION`.** `assertCurrentLlmShape`/`assertMessageEventShape` in `packages/core/session/src/index.ts` validate only `Array.isArray(content)`, with no per-block-type checks — confirmed by direct inspection, not changed. Per the session-log-version-mechanism note, a version bump gates *structural or envelope* changes; a new tag inside the already merge-extensible `ContentBlockMap` is vocabulary growth the mechanism is designed to absorb without one. `SESSION_FORMAT_VERSION` stays `0`.

**Request materialization: per adapter, not centralized in agent-loop.** The natural-looking design — lower every `FileBlock` to text once in `agent-loop`, before `buildRequest`, since no adapter accepts a file part natively — is wrong for this codebase and was caught by a real test failure, not by inspection: `packages/core/agent-loop/src/invariant.ts` installs a `llm/stream` waterfall listener that requires `JSON.stringify(options.messages) === JSON.stringify(session.deriveMessages())` on every loop-built request. A file lowered before `buildRequest` makes `options.messages` diverge from the log's own reconstruction by construction, and the dispatch fails loudly (`log-reconstruction desync`) on the very first request carrying a file block. This is not incidental: it is the same reason `ImageBlock` bytes are never materialized into `GenerateOptions.messages` either — each adapter already resolves image bytes into a *locally derived copy* (`requestMessages`/`requestOptions` in `llm-deepseek/src/adapter.ts`, `requestMessages`/`exactMessages` in `llm-pi-ai/src/context.ts`), never touching the frozen array the invariant checks.

`packages/llm/llm/src/file-lowering.ts` gains `contentHasFile` (exported, mirrors `contentHasImage`) and `lowerFileBlocksFromStore(messages, attachments, signal?)` — the read-decode-format composition (`attachments.readFile` → UTF-8 decode → `lowerFileBlockText`) both adapters share. Each adapter calls it once, at the very top of its own request construction, against its own locally derived message copy:
- `llm-deepseek/src/adapter.ts`: `streamWithConnection` gains a `hasFiles` gate parallel to `hasImages` (no model-capability check — the lowered form is plain text, which every model already accepts), resolving `attachments` and throwing `UNSUPPORTED_CONTENT` if unavailable, exactly like the existing image gate. `request()` lowers `requestMessages` into `fileLoweredMessages` before building `requestOptions`, so `serializeRequest`/`serializeRequestWithImages` see only `'text'` blocks and needed no changes.
- `llm-pi-ai/src/context.ts`: `textOnlyContext` (the synchronous, no-attachments path) gains a `contentHasFile` throw parallel to its existing `contentHasImage` throw. `toPiContextWithImages` lowers `options.messages` into `baseMessages` before `assertSupportedImageRoles`/`offloadRequestImagesWithPolicy` run, so the rest of the function is unchanged. `adapter.ts` resolves `attachments` whenever `containsImage || containsFile`, not only for images.

Every other content-part switch this change forced a decision at: `estimateContent` (`packages/llm/token-meter/src/estimate.ts`) prices a `'file'` block by its *lowered* size (`min(bytes, DEFAULT_MAX_LOWERED_FILE_CHARS)`), not the generic structural-JSON default, since the exact request-time text length is already known without a provider-specific formula. `blockText` (`packages/session-query/session-query/src/extraction.ts`) indexes a file's display name only, like a tool-call's name — full content needs an attachment-store read this synchronous walk cannot perform. `compaction-tool-result-pruner`'s `measureContent` needed no change: it counts only `'text'` blocks, so a `'file'` block is zero-cost and passes through unpruned, same as an `'image'` block today.

`DEFAULT_MAX_LOWERED_FILE_CHARS` (16,000) stays a code-level constant in `file-lowering.ts`, not a new `Config` field on any package: no deployment has asked to tune it, and threading a knob through three packages (`dsh-llm` and both adapters) before that need exists would be speculative ahead of the "no hardcoded tunables" rule's actual target — deployment-varying choices, not every constant.

## Alternatives considered

**Central lowering in `agent-loop`, upstream of `buildRequest`.** Implemented first, then reverted whole: it produces a `GenerateOptions.messages` that a fresh `session.deriveMessages()` cannot reconstruct, failing `agent-loop`'s own request-reconstruction invariant on the first request carrying a file block. Per-adapter lowering against a locally derived copy — the same pattern images already use — was the only design compatible with that invariant.

**Have a waterfall listener between the invariant check and the terminus substitute a lowered `options` for downstream listeners.** Rejected after reading the vendored `ctx.waterfall` implementation (`vendor/cordis/src/events.ts`): `next` is `() => cb(...args)` with `args` fixed at dispatch time, never re-suppliable by an intermediate listener. A listener can only wrap the *return value*, not the arguments seen further down the chain or by the terminus.

**Teach each adapter's own content-block switch (`contentParts` in `llm-deepseek/serialize.ts`, `userContent` in `llm-pi-ai/context.ts`) a `'file'` case.** Rejected: it would need the same read-decode-format logic duplicated at each of those switches, plus threading `AttachmentStore`/`signal` two layers deeper than they otherwise go. Lowering once at the top of each adapter's request construction keeps every existing block-type switch exhaustive over `text`/`image`/`tool-call`/`tool-result` exactly as it already was — a `'file'` block never reaches them.

## Consequences

`packages/host/apiproxy/src/api-proxy.ts` gained a `resolveAttachmentSession` helper and an `attachmentReadFailure` helper, extracted from the `attachment`/`file` RPC handlers once they were near-identical, to keep `jscpd` clean. Adding `fileLimits`/`validateFile`/`saveFile`/`readFile` to the abstract `AttachmentStore` (prior commit) and a required `file` method to `SessionsApi`/`IApiClient` (this commit) rippled into roughly fifteen test-only mock implementations across the repo, all mechanical.

Every touched package holds 100% per-file coverage (`file-lowering.ts`, both adapters' `adapter.ts`, `llm-pi-ai/context.ts`, `token-meter/estimate.ts`, `session-query/extraction.ts`, `host/apiproxy/api-proxy.ts`, `host/apiproxy/fetch/{client,handler}.ts`) verified via scoped `vitest run --coverage`; both repo-wide `tsc -b` aggregate faces, `oxlint`, and `jscpd` are clean on every touched path.

Running `pnpm run doc-sync` for the first time in this series (the prior commit's own verification did not include it) surfaced a classification gap the prior commit had left open: `scripts/gen-cordis-catalog.ts`'s `LINK_MAP` never listed `FileAttachmentRef`/`SaveFileAttachment`/`StoredFileAttachment`/`EncodedFileAttachment`, so the generated Cordis catalog (`docs/subsystems/attachment.md`, `packages/extensions/tool-cordis/src/api-catalog.ts`) could not render the `AttachmentStore` file methods the prior commit had already added. This commit closes that gap and documents the file-attachment type family (`docs/subsystems/attachment.md`'s new "Text file attachments" section) alongside adding `'file': FileBlock` to `docs/subsystems/llm-streaming.md`'s `ContentBlockMap` block — both regenerated/updated bilingually and reverified against `pnpm run doc-sync`'s full 28-gate suite.

**Retirement.** This patch is a temporary overlay for a capability upstream does not have yet: if upstream adds file-part support to its own prompt wire, session log, and request materialization — including resolving the same request-reconstruction-invariant-vs-file-lowering tension this note documents — this patch is retired and the fork adapts to upstream's form.
