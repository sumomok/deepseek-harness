# Agent Note: text files as composer draft attachments

Status: implemented

English | [中文](2026-08-28-file-attachment-composer-intake.zh.md)

## Problem

The wire, session log, and request-materialization seam for text-file attachments now exist (prior commit), but nothing in the browser composer can reach them: a dropped or pasted text file either falls through the image-only intake path's format check (rejected) or, via the separate `@sumomok/dsh-text-drop` plugin being retired alongside this series, gets spliced as raw text into the draft — bypassing the durable, content-addressed seam entirely. This commit makes the composer intake, draft state, and drop/paste surface treat a text file as a first-class draft attachment alongside an image, and fixes the mixed-drop papercut (a batch with one image and one text file used to reject the whole batch through the image path).

## Decision

**`ComposerAttachment` becomes a discriminated union.** `packages/client/ui-conversation/src/client/contract/slots.ts`: `ComposerImageAttachment { kind: 'image', id, file, previewUrl }` and `ComposerFileAttachment { kind: 'file', id, file }` (no `previewUrl` — a file chip shows name and size, never a thumbnail) replace the single `{kind:'image', ...}` shape the ui-attachment README had already flagged as the anticipated extension point. Both variants carry `file: File`, so kind-agnostic code (byte-size math, `.file.name`) needs no narrowing.

**The input machine is reused unchanged, not renamed.** `InputState.imageIds: readonly DraftAttachmentId[]` and the `addImages`/`removeImage`/`pruneImages` verbs already treat ids as fully opaque — never inspecting content kind — across `machine.ts`, `facade.ts`, `hub.ts`, and five dedicated test files that `contract.ts` itself calls a "frozen input-machine contract." A file draft rides the identical list and verbs; nothing there changes. This trades naming precision (the field is still literally `imageIds` while holding file ids too) for avoiding a large, risky touch surface across a contract explicitly marked frozen — a deliberate, documented scope call, not an oversight.

**Client-side sniff is a fresh, small, explicitly non-authoritative module, not a shared import.** `packages/attachment/attachment-local/src/sniff.ts`'s own JSDoc already anticipated "a client-side pre-sniff of a large File before it is fully read," but that package's main barrel imports `node:path`, `@deepseek-ai/dsh-home-paths`, and `sharp` — Node-only, unsafe for a browser bundle even via a `./src/*` subpath import, since it would add a Node/sharp-dependent package to a client package's dependency graph across the client/server boundary. `packages/client/ui-conversation/src/client/file-sniff.ts` duplicates just the two-line verdict (NUL byte, then strict `TextDecoder` decode) as `sniffIsText(file)` and `partitionDroppedFiles(files)`, documented as a UX-only pre-check: the durable attachment seam's own `NOT_TEXT_FILE` check is the only authoritative one.

**Two raw-file entry points, one partition function.** A document-level drop and a textarea paste are two independent DOM event sources reaching two different modules, so each partitions its own batch: `ComposerAttachments.tsx` (ui-attachment, which owns every document-level drag/drop listener) partitions a drop batch and calls `onAddImages`/`onAddFiles` separately with the split halves; `InputBar.tsx`'s paste handler routes through its own `intakeDrop` wrapper that partitions and calls `intakeImages`/`intakeFiles`. Both `onAddImages`/`onAddFiles` (the `ComposerAttachmentsOwnerProps` the slot owner supplies) receive an already-split, single-kind batch — the split itself is `partitionDroppedFiles`, exported from `ui-conversation`'s client barrel and imported by `ui-attachment`.

**A new `FileChipRow` component, not a widened `AttachmentRail`.** `AttachmentRailItem.previewUrl` is a required field and the rail's CSS is a fixed 64px square — unsuitable for a name+size chip with nothing to thumbnail. `packages/client/ui-attachment/src/FileChip.tsx` is a small sibling component (generic over its item type, mirroring `AttachmentRail<T extends AttachmentRailItem>`) rendering a wrapping row of chips beside the image rail; `ComposerAttachments.tsx` renders both, filtering `attachments` by `kind`.

**`image-labels.ts` renamed to `attachment-labels.ts`.** It now maps both image and file `AttachmentErrorCode` reasons to product copy (`attachmentErrorText` gained a `fileLimits` parameter alongside `limits`) and formats both kinds' byte sizes (`imageSizeText` renamed `attachmentSizeText`, exported from the client barrel for `ui-attachment`'s chip labels) — a two-kind module keeping an image-only name would be exactly the kind of unexplained asymmetry the repo's conventions flag.

**Overlay and toast copy** (`locales.ts`): `image.dropTitle` → "图片或文本文件拖到此处即可添加" / "Drag images or text files here to add them"; `image.dropDesc` keeps the image count/size line and appends the privacy reminder "文本内容会随消息发送，发送前留意其中的密码或密钥" / "text content is sent as-is — check for passwords or secrets before sending" (this is the only place the reminder lives now — no separate file-limits number in the overlay, since the task's approved copy states none). New `file.*` keys mirror every existing `image.*` limit/label key (`tooMany`/`fileTooLarge`/`totalTooLarge`/`notText`/`invalidName`/`pending`/`remove`/`label`/`sendFailed`). A fresh banned-words test (`attachment-labels.client.spec.tsx` plus a drop-copy assertion) checks the shipped `image.dropTitle`/`image.dropDesc` strings never contain 检测/发现/识别/detect/scan — freshly written against this surface's own required copy, not a literal port of the retired plugin's hint-strip test (different UI surface, different final strings).

**Slash-command file submission is explicitly out of scope.** `ConversationController.serializeDraftImages` (the slash-command image-submit path) still resolves every requested id — so its existing staleness check still covers a file id — then filters to image-kind before encoding. A file draft present at slash-command submit time is silently excluded from that command's image-only payload rather than rejecting the submission or serializing it some other way; no command surface accepts a file part today, and inventing one was out of this series' scope.

## Alternatives considered

**Import `sniffProbe`/`PROBE_BYTES` from `@deepseek-ai/dsh-attachment-local/src/sniff.ts` via its wildcard export.** Rejected: the package's `dependencies` include `sharp`, a native image library with no place in a browser bundle, and the `./src/*` export exists for the monorepo's own build tooling to resolve TypeScript project references, not as an invitation to import server-only source into a client package's dependency graph.

**Rename `InputState.imageIds` to a generic `attachmentIds`.** Rejected for this series: `contract.ts` documents the input-machine contract as frozen, and the rename would ripple through `machine.ts`, `facade.ts`, `hub.ts`, and five dedicated test files for a naming-precision gain with no behavior change. Flagged as a real, debatable trade-off rather than a settled non-issue.

**Widen `AttachmentRailItem.previewUrl` to optional and branch inside `AttachmentRail`.** Rejected: the rail's whole layout (`AttachmentRail.module.css`'s fixed 64px `.item`/`.thumbnail`) is sized for a thumbnail; a text chip needs a wider, wrapping row, not a conditional render inside a fixed square. A sibling component composes more simply than a rail that renders two visually unrelated shapes.

## Consequences

`packages/extensions/cordis-client-runner/src/client/slot-catalog.ts` (generated) picked up the widened `ComposerAttachmentsOwnerProps`/`ComposerAttachment` shapes via `pnpm run gen-client-catalog -- --write`. Three existing test files (`input-matrix.client.spec.tsx`, `input-scenarios.client.spec.tsx`, `skeleton.client.spec.tsx`) needed a mechanical `addFiles: () => null` addition to satisfy the newly required `ComposerBarInjected.addFiles` field. Two paste-fixture tests in `input-bar.client.spec.tsx` needed real PNG magic bytes (`Uint8Array.of(1, 2, 3)` decodes as valid UTF-8, indistinguishable from text once drops are content-sniffed) and `await`/`waitFor` around the now-async paste-to-intake path; one fake-timer toast test in the same file switched from a real paste to a direct `onAddImages` call to keep its subject (toast fade/re-announce timing) independent of the paste path's own async sniff, which real fake timers do not control (a native `File.arrayBuffer()` promise resolves via a genuine microtask, not vitest's mocked timers). `composer-attachments.client.spec.tsx` needed the same PNG-magic-bytes fix for its own drop fixtures plus `waitFor` around the drop handler's now-async partition.

`packages/client/ui-attachment/src/*` carries no coverage exemption and is fully covered (scoped `vitest run --coverage` confirmed clean after removing one dead defensive `items.length === 0` guard inside `FileChipRow` — the owner (`ComposerAttachments.tsx`) already renders it conditionally, matching `AttachmentRail`'s own pattern of no internal empty-guard). `packages/client/ui-conversation/src/client/*` (single-star glob) carries a pre-existing GUI-debt coverage exemption, but only for files directly under `client/` — `skeleton/InputBar.tsx` and `contract/slots.ts` are nested and remained fully gated; both confirmed clean by the same scoped coverage run. `service.ts`/`apply.ts`/`locales.ts`/`attachment-labels.ts`/`file-sniff.ts` fall under the exemption; they still carry real behavioral tests (`service-orchestration.client.spec.ts`, `apply-inject.client.spec.tsx`, `file-sniff.client.spec.ts`) verifying the new `createDraftFiles`/`sendSession` kind-dispatch/`serializeDraftImages` kind-filter/`releaseDraftImage` kind-guard/`addFiles` inject behavior, not relied on for the coverage gate.

**Retirement.** This composer-intake layer is a temporary overlay for a capability upstream does not have yet: if upstream's own composer accepts non-image attachments — generalizing its draft-attachment shape, drop/paste intake, and rail/chip presentation the way this patch does — this patch is retired and the fork adapts to upstream's form.
