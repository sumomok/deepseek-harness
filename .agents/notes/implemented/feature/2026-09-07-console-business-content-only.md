# Agent Note: the customer console's conversation column shows business content only

Status: implemented

English | [中文](2026-09-07-console-business-content-only.zh.md)

## Problem

The customer console rendered the harness's full developer transcript to an end customer.

A visitor who asked for a weekly report saw, between their question and the answer: a 系统提示词 disclosure holding the whole system prompt, a row per tool call (including `content_read`'s own result card, describing a page the content column was already showing beside it), a 思考 disclosure per reasoning block, a card per slash command, a "N 次工具调用 · M 条消息" fold row once the turn closed, and a reply footer whose action row carried 用量 33.7K tok · 用时 6 秒 next to copy, like/dislike, and branch. Two more surfaces spoke in the vendor's voice rather than the product's: the composer's placeholder is `dsh-client-ui-conversation`'s developer-register copy ("Describe what you want to build... / commands, @ files or sessions"), and the running-turn indicator says 深度求索中..., the vendor's Chinese brand name, painted through a DeepSeek-token gradient — the one piece of vendor identity the package's hero-facade rules never reached, because it is not a hero surface.

None of it is what a customer console is for. The product decision (2026-09-07) is that the conversation column shows what the visitor asked for and what came back, and nothing about how the run got there.

## Decision

**Every hide is one more rule in `packages/experimental/server-sidebar/src/client/terminology-guard.ts`**, the client-only stylesheet this package already injects for the turns/steps row, the permission chip, and the hero facade. No upstream package is touched, no new plugin, no composition row, no settings work.

**The process rows go by Chat Node kind.** `ChatNodeSeat.tsx` stamps `data-chat-flow-kind` on every flow row, so `[data-chat-flow-kind="system-prompt"]`, `"turn-process"`, `"tool-call"`, `"command"`, `"manual-compaction"`, and `"compaction"` are real attribute selectors — no class substring, no DOM position, and the only way to break one is an upstream kind rename. Reasoning is the exception: it renders inside the kept `assistant-step` seat rather than as a kind of its own, so its rule keys on `[data-variant="think"]`, which `ReasoningRow.tsx` sets unconditionally and no other `ToolRowVariant` member collides with. Command rows take three kinds because `ui-chat` splits one surface by how the command arrived — `manual-compaction` is `/compact` with its compaction transaction, `compaction` the automatic one, `command` everything else — and hiding only `command` would leave `/compact` on screen. `context` and `model-retry` are the same judgment applied twice more, and neither is on the Keep list's side of it: a `context` row is a `user/message` whose source is not the user (`messageDefinition` classifies it by exactly that), so it is machinery the run needed rather than something the visitor wrote; a `model-retry` row is internal status, since the retry either succeeds — and then the answer is what the visitor reads — or exhausts, and then the kept `turn-error` row says so. `command-input` and `workflow-run` are `dsh-client-ui-goal`'s and `dsh-client-ui-workflow-run`'s own contributions to the same map — both composed by `packages/bundle/web-app/cordis.patch.yml` and disabled by no console overlay, so `/goal` draws its own input row and a workflow tool run draws a lifecycle card — and `unknown` is `ui-chat`'s registered fallback, which renders the raw JSON of an append-surface event no Definition claimed. **The map is merge-extensible, so the union is open**: the package's unit spec lists every composed kind as hidden or kept and fails to compile when the union gains one that is in neither list, which is what keeps a kind from reaching a customer unreviewed.

**`content_read`'s result card is hidden with its row.** It is a keyed `tool.call.toolview` entry under the `tool-call` kind, so `:not(:has([data-tool="content_read"]))` would have kept it; the decision is that it should not be kept. The card says the agent looked at a page and names it — a fact the content column already carries by showing the page itself, so in a console the row restates in the transcript what is on screen beside it.

**The reply footer loses its two metric pills and keeps the rest of its row.** `[data-turn-tail]` has two children: `dsh-client-ui-deliverables`' `ProducedFiles` chain, which lists the files the run wrote, and `MessageIconActions`, which carries copy, like/dislike, branch, the two stat pills, and the end-of-turn clock. The files a run produced are the business result and the other controls are the visitor's own affordances; only 用量 and 用时 are process reporting, so only they go. Neither pill carries a `data-*` attribute — `TurnUsagePanel.tsx` puts one on each opened dialog and none on either trigger — so the rule couples on `TurnUsagePanel.module.css`'s `.trigger`, the local name both panels give that button, and reaches the pill's own wrapper through it: `[data-turn-tail] :has(> [class*="trigger"])` selects each panel's `span.root`, so the pill leaves behind neither a flex slot nor the `.root + .root` margin rebate that hiding the button alone would.

**The running indicator is re-texted, not hidden.** A visitor must see that work is under way, so `[data-chat-flow] > [class*="turnStatus"]` collapses the upstream text to `font-size: 0`, paints 正在处理… through `::after`, and neutralises the `--dsw-static-deepseek-500/200` background-clip-text shimmer to the theme's ordinary `--dsw-alias-label-primary`. The direct-child combinator is load-bearing twice over: `ChatView.tsx` renders `TurnStatus` outside every `ChatNodeSeat` (which is why no kind rule reaches it), and the combinator keeps the rule off the nested `turnStatusClock` span, which sets its own size and colour and still shows the elapsed clock after fifteen seconds.

**The composer placeholder reads 说说要做什么 where the composer accepts input, and only there.** `InputBar.tsx:545-549` renders one `[data-composer-placeholder]` element for every composer state, and `ConversationRoot.tsx` feeds it four different strings: the hero copy (`:343`), the established default, the inert composer's own diagnostic (`:334`, `placeholder.workspace` — "Choose a workspace to start"), and a raised block's reason (`:342`). The last two are not invitations to type, and painting one over them would invite a visitor to type into a composer that refuses input — which is also what the package README's Known Limitations says about that diagnostic being the only thing announcing the state. So the rule reaches the placeholder through its immediately preceding sibling, the composer input, and excludes both: `[data-composer-input]:not([data-phase='inert']):not([aria-disabled]) + [data-composer-placeholder]`. `data-phase` is `input?.phase ?? 'inert'` (`InputBar.tsx:533`), so the inert state is the one with no composer input face at all; `aria-disabled` is `editorDisabled` (`:534`), which a raised block sets and the workspace-picker trigger deliberately does not. The swapped copy carries `var(--dsh-content-font-size, 14px)`, the token the composer card itself sets, so it keeps following the Settings font-size preference instead of freezing at a pixel value the way the hero headline rule does. The element is already `aria-hidden`, and the sibling `[data-composer-input]`'s `data-placeholder` and `aria-label` are deliberately untouched.

## Alternatives considered

**`ui-chat.transcriptView`, the setting that looks like it exists for this.** It does not reach any of the targets. Its value union is exactly `'normal' | 'compact'` (`packages/client/ui-chat/src/chat-settings.ts:12`) and `'compact'` is already the default, so the console is at its most-hiding value today. `compact` folds rather than hides: members get `hidden="until-found"` and a browser find-in-page `beforematch` reopens the disclosure (`searchable-hidden.ts:21-28`). It never applies to a running turn — `ChatNodeSeat.tsx:63-69`'s `processWindowReady` requires `turnClosed` and a fully loaded history. And three of the rows this change hides are visible under `compact` by construction: `system-prompt`, `turn-process` and `turn-tail` are `TURN_PROCESS_INDEPENDENT_KINDS` (`contract/turn-process.ts:20-27`), which the fold never touches at all. A composition cannot pin it either: `SettingsRegisterOptions` offers only `base`, which loses to the user layer (`packages/settings/settings/src/index.ts:739-748`), and `ui-chat` registers its schema with no `base` and exposes no `Config`, so a cordis.yml row for it has no key to write.

**Register a console dictionary for the placeholder and the indicator copy.** `LocaleRuntime.register` throws on a duplicate namespace/locale pair (`packages/client/locale/src/client/index.ts:381-400`), and `dsh-client-ui-conversation` already owns `conversation` for `zh` and `en`, so a second registrant fails at apply time. A whole console language (`addLanguage` with a `zh` fallback, carrying only the overridden keys) is legal and would change `aria-label` too, but it hijacks language selection: the new language appears in the Settings → General Language row the console keeps, needs a durable `setLocale` write, needs an `en` sibling, and a visitor switching back to plain 中文 gets the upstream string. It also re-keys eleven `composer(page, …)` locators in `apps/web/tests/server-sidebar.e2e.ts` and one in `content-perception.e2e.ts`.

**Set the text from a client effect.** React clobbers both carriers: the placeholder is a React child of a component that re-renders on every keystroke-driven `empty` flip and every locale-revision tick, and `data-placeholder` is a React-controlled prop reconciled each render. It would need a MutationObserver loop.

**Edit `packages/client/ui-conversation/src/client/locales.ts`.** The fork forbids upstream edits where a composition- or plugin-level answer exists, and the blast radius is 46 committed goldens under `snapshots/**` plus 14 under `apps/web/tests/expected/**` carrying the established placeholder, plus two support helpers most web specs use.

**Take the whole action row, or reach the pills by `aria-haspopup="dialog"`.** The row-wide hide is the more stable selector — `[data-turn-tail] > [class*="actions"]`, an attribute-anchored direct child — but it takes copy, like/dislike, branch and the clock with the metrics, which the product keeps. `aria-haspopup="dialog"` looked like the semantic handle for the pills alone and is not one: `dsh-client-ui-message-feedback`'s note-open button (`MessageFeedbackActions.tsx:263-270`) carries it too, sits in this same row once a rating exists, and belongs to the like/dislike affordance that stays. That leaves the CSS-module class substring as the only isolator, which is why the e2e reads the keeps as well as the hide.

## Consequences

- Every new `display: none` widens the blind spot of this package's two whole-page banned-word screens: `workspaceWordsInChat` and the landing-page `body.innerText()` scan both read rendered text, so banned vocabulary landing only inside a hidden process row would pass both. The helpers are unchanged — narrowing them to raw DOM text would flag the upstream strings the guard hides on purpose, which is the very thing they were written to tolerate.
- Accessibility follows the hide exactly: `display: none` removes a subtree from the accessibility tree and from find-in-page as well as from `innerText`, so a screen reader gets the same column a sighted visitor gets. The one mismatch is the placeholder, where the swap is paint-only and `[data-composer-input]`'s `aria-label` still announces the upstream English string, banned vocabulary included. The package README's Known Limitations records both.
- Inside this composition the new command rule supersedes `content-frame`'s and `content-column`'s own `[data-chat-flow-kind="command"]:has([data-slot="conversation.chat.commandview"]:empty)` stylesheets. Those packages are unchanged: both compose without `server-sidebar` (`apps/web/tests/server-layout-content.overlay.yml`), where their narrower rule is still the only one.
- Intermediate assistant text still appears, by decision: it is `assistant-step`, the same kind as the answer, and the only attribute separating them (`data-turn-process-member`) exists solely on a closed turn with a fully loaded history. Hiding it would have meant hiding text the Keep list keeps.
- The reply footer keeps copy, like/dislike, branch and its clock, and the user message's own copy button and clock (`MessageItem`'s `MessageIconActions`, a different seat) were never in scope. Only the two stat pills are gone from either row.
- **Nothing model-visible changed.** This is browser CSS in a client plugin: no system prompt, no tool schema, no session event, no model request. `pnpm run test:snapshot snapshots/console` needs no update, and the web lane's aria goldens are unaffected because every golden-bearing spec runs under a composition that never inserts `server-sidebar` — `apps/web/tests/server-sidebar.e2e.ts` calls neither `captureStableAria` nor `compareOrRefreshGolden`.

## Testing

`packages/experimental/server-sidebar/tests/terminology-guard.client.spec.ts` asserts each new rule as the literal selector it couples on, the file's standing policy: the eight kind selectors, the `think` attribute, the footer's `:has(> [class*="trigger"])` pair — plus that neither the direct-child nor the descendant `actions` form appears, since either would take controls the decision keeps — the placeholder pair with its copy, and the indicator pair with its copy, its neutral fill colour, and the absence of 深度求索.

`apps/web/tests/server-sidebar.e2e.ts` adds a fourth describe that drives the assembled console with no model call. It seeds one closed turn carrying a `request/header`, an injected-context `user/message` under a plugin source, a scheduled `llm/retry`, a reasoning block, a `content_read` call, a `write` call, an intermediate step and a plain-text answer in a later step — which is what makes the turn foldable — then, after `turn/end`, a `feedback` command whose name no `conversation.chat.commandview` claims so `GenericCommandCard` actually draws, a `/goal` command run, a `tool-workflow` run, and both compaction rows: a replacement checkpoint alone for `compaction`, and a checkpoint correlated with a `/compact` run through `sourceCommandId` for `manual-compaction`, each shadowing one throwaway context message of its own because a surface `replace` names a real surface-node range and must cite it in `sourceEventSeqs`. Ten of the eleven hidden kinds are seeded that way. **`unknown` is the one that cannot be**: `isAppendSurfaceEvent` admits only `user/message`, `assistant/message` and `tool/result` (`packages/core/session/src/surface.ts:22-26`), and `ui-chat` registers a Definition matching all three unconditionally, so its own fallback never fires in this composition; it is pinned in the unit spec instead. The scenario then reads the page: each hidden row present and computed `display: none`; the `content_read` row hidden inside its seat; the two metric pills gone while copy, branch and the clock stay on screen; the produced-files tail and its file chip visible; the placeholder's rendered `::after` in both composer states while `composer(page, …)` still resolves by the untouched upstream attribute; an approval card visible with no `data-chat-flow-kind` inside it, driven by a direct `ctx.approval.request` against a turn the test opens and closes; and the indicator visible, re-texted, and off the gradient. The zero-Workspace describe pins the other half of the placeholder scoping: there the element keeps its own font size and renders no `::after` at all.

Several of those need the third half of the new `expectGuardHidesSelector` helper — present, invisible, **and** computed `display: none`. `compact` already folds tool and thinking rows behind `hidden="until-found"`, which reads as invisible, so a present-and-invisible pair alone would pass with every rule in this change deleted. Each new rule was checked against a deliberately broken build, with the client face rebuilt each time because the browser loads `lib/client.js` rather than source: without `[data-chat-flow-kind="tool-call"]` the seat's computed display comes back `block` while its `isVisible()` half still reports `false`; without `"context"` or `"model-retry"`, `block` likewise; without the footer rule the pill wrapper reports visible. Widening the footer rule back to the whole action row fails the pill assertion too — the wrapper's own display stays `inline-flex` under an ancestor hide — and adding a row-wide hide alongside the narrow rule fails the keeps instead, so both directions of drift are covered. The two rules added after review discriminate the same way (`command-input`, `workflow-run`, `compaction` and `manual-compaction` each fail their own kind assertion when removed), and dropping the placeholder rule's scope back to the bare `[data-composer-placeholder]` fails the zero-Workspace pin with `expected '0px' not to be '0px'`. The union's own exhaustiveness is a compile-time check rather than a runtime one: removing `workflow-run` from both lists in the spec fails `tsc -b tsconfig.client.json` with `Type 'true' is not assignable to type '"workflow-run"'`.

An approval card cannot be produced from the log alone, and neither can a running turn. The approval is asked for directly through `ApprovalService.request`, which reaches the browser over the composed `approval/request` waterfall exactly as a tool's ask would. The running bit is a Host push tied to real Agent execution (`api-session/status`, emitted from `agent/status` at `packages/api/session-controller/src/index.ts:175`), so the scenario emits that one declared remote event itself; everything downstream of it — the component, the stylesheet, the paint — is the real thing.
