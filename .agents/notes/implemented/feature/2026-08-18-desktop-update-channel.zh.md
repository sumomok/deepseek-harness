# Agent Note: 桌面客户端的静态更新源

Status: implemented

[English](2026-08-18-desktop-update-channel.md) | 中文

## Problem

[可安装客户端包](2026-08-18-installable-client-packages.md)出厂时没有更新通道。新构建只有靠人转告、再由对方手动下载重装才能到位,而已装好的那一份根本无从知道自己落后了。桌面客户端还没有用户时,这个 non-goal 是划算的;一旦有人拿到了不是自己构建的包,它就不再划算——此后每一个修复都卡在一个没人会执行的手动步骤后面。

## Decision

更新通道是**一个经 TLS 提供的静态目录**——即 electron-builder 的 `generic` provider——由两套按平台分化的行为读取,二者只在"能把用户送多远"上不同;其上再压一层强制更新。

### 更新源

`electron-builder.yml` 里每个平台各声明一个 `publish` 块,构建因此产出 provider 要读的清单:Windows 的 `latest.yml` 与 macOS 的 `latest-mac.yml`,各自列出该版本的产物及其 sha512 与大小,并与这些产物一起落在 `https://lhr.ink/dsh-updates/{win,mac}/` 下。Windows 那一块还会把 `app-update.yml` 写进打好的应用内部。

`channel: latest` 在两端都显式写出。默认行为会从运行版本的预发布段推导渠道名,于是 `0.1.0-rc.8` 构建会发布并寻找 `rc.yml`——渠道名会随发布周期的每个阶段自我改名,把客户端晾在一份再也没人写的清单上。本产品只有一个渠道。

这里没有更新服务。清单**本身**就是判断过程:客户端取回它、比对自己的版本,然后要么行动要么什么都不做。这就是服务端契约的全部,所以 nginx 发一个目录已经是它的完整实现。

### Windows:三段式,且安装从不静默发生

1. **检查**——静默。启动后 15 秒、此后每四小时,以及 **帮助 → 检查更新** 的手动入口。
2. **征询下载**——一个对话框,标题带版本号,releaseNotes 作为正文。此时一个字节都还没传,所以拒绝不花任何代价。同意则在后台下载,并配一个小进度窗(`src/progress-window.ts`)显示百分比、大小与速率;关掉这个窗口不会中断下载,任务栏进度两种情况下都在。下载期间手动检查会重新打开这个窗口,而不是在它上面再叠一个对话框。
3. **征询安装**——字节落盘后的一个对话框:「v… 已下载完毕,可以安装。现在重启安装吗?」,默认按钮是「暂不」,于是下意识的回车绝不会结束一次会话。

**没有用户的决定就不会发生安装,退出时或别的任何时候都一样。**`autoInstallOnAppQuit` 关闭,拆除路径是 `stopServerBounded()` → `app.exit(0)`;应用只在有人点了「重启安装」之后的几秒里替换自己,而那时内嵌服务器的进程树先落——安装程序要替换的正是这个服务器所运行的目录。被拒绝的安装留在盘上,此后只会再被提起两次:下次启动时缓存命中重新触发 `update-downloaded`,以及用户自己从菜单里问。没有角标,没有定时器,没有第二种提醒。

**那次点击之后的执行不再打断用户,这与"不问自装"正好相反。**这条规则禁的是用户没有决定过的安装;而那次点击**就是**决定,其后的一切只是把这个决定执行完。所以 `quitAndInstall(true, true)` 给安装程序传 `/S --force-run`。不给 `/S`,assisted(`oneClick: false`)安装器会把安装模式页、进度页、完成页再演一遍——问的正是那次点击已经回答过的东西,这也是这条通道的第一批用户反馈"这不像动态更新而像重新安装"的原因。这里的免打断不需要付代价:`$INSTDIR` 来自注册表 `InstallLocation`,在任何页面存在之前就已在 `.onInit` 里读好,所以静默执行落在应用本来就占着的那个目录里。而 `--force-run` 是必需而非可选,因为 assisted 安装器的自动启动分支是 `${if} ${isForceRun} ${andIf} ${Silent}`:`(true, false)` 会正确装好,然后把用户留在一片空白前面。

### 保持可安装:进程生命周期与提权

第一次真机 Windows 更新一口气撞出三种失败,值得记下来——因为单看更新代码,一种都看不出来。

**安装失败的原因是安装器从未被提权,而这台机器从不明说。**per-machine 安装要替换旧版本,就得拿旧卸载器去动 `HKLM` 与 Program Files,这需要管理员权限。electron-updater 从正在运行的应用里 spawn 安装器,而它没有提权,于是静默卸旧中止、返回退出码 2——呈现为「Failed to uninstall old application files: 2」,其中那个数字是**旧卸载器自己的退出码**(`handleUninstallResult` 打印 `$(uninstallFailed): $R0`;而"启动不了卸载器"是另一条只写详情日志、不弹框的路径)。全程用户没见到任何 UAC 弹窗,因为他的 UAC 滑块停在**从不通知**:在这一档,主动申请提权的进程被静默放行,不申请的进程则继续持受限令牌。更新器 spawn 的安装器从不申请。对同一个安装器用「以管理员身份运行」——显式授予完整令牌——一次就装成了。

修法是让更新器去申请。`perMachine: true` 给产品单一安装位置并去掉模式页;真正把 `isAdminRightsRequired: true` 写进清单的是 `packElevateHelper: true`,因为写出条件是 `updateInfo != null && isPerMachine && (oneClick || options.packElevateHelper)`(`NsisTarget.js`),而未设置的选项在这里是假值——提权助手无论如何都会被拷进去,所以漏掉这一行,等于发布一个**能**提权却从不告诉任何人的构建。之后更新器从下载文件的清单条目里读这个字段(`DownloadedUpdateHelper.js` 的 `fileInfo.info.isAdminRightsRequired === true`),传给 `doInstall`,并改用 `elevate.exe` 启动安装器而非直接启动(`NsisUpdater.js`)。在普通机器上这是每次安装一次 UAC 确认;在「从不通知」的机器上则是静默放行。

**正在死的应用和卡住的应用长得一模一样。**原先的拆除是:拦下退出、停服务器、再退出——而停这一步没有任何上界,于是一个永不落定的 stop 会把一个没有窗口的进程永久留在那里。安装器只给旧应用大约 7.6 秒消失(300 毫秒 + 1 秒,然后两轮 1 秒 + 2 秒,见 `_CHECK_APP_RUNNING`),超时就放弃并请用户手动关闭。`stopServerBounded` 现在给这段等待封了顶:Windows 上 4 秒,稳稳落在那个预算里;POSIX 上 10 秒,因为它要反过来长于服务器自己 8 秒的 SIGTERM→SIGKILL 升级窗口,否则这个上界会抢在升级之前触发,反而把它本想收掉的进程变成孤儿。

**杀掉应用并不会杀掉它的服务器。**服务器是安装目录下另一个独立的 `node.exe`,而安装器自带的清理够不到它:PowerShell 分支按 pid 停进程、不带子进程,回退分支则只按应用自己的映像名匹配。一个成了孤儿的服务器,握着卸载器正要删的那些文件。两道防御覆盖它。启动时,在新服务器起来之前,`sweepOrphanedServers` 杀掉可执行文件**恰好是**本安装那个内置 Node 的进程——比的是完整路径而非映像名,因为这台机器上其他任何 `node` 都属于别人。安装器一侧,`build/installer.nsh` 定义 `customInit`,由 app-builder-lib 从 buildResources 目录按名字取用;它先以 500 毫秒一轮、最多 10 秒等 `$INSTDIR` 下的进程自然退出——这覆盖了更新器刚请它退出、正在死的那个实例——之后才对残留连子进程一起杀。

### macOS:发现并交接

macOS 刻意**不用** electron-updater。Squirrel.Mac 只在运行中的应用已签名、且替换件满足同一签名要求时才会暂存更新;这些构建没有证书,所以原地安装再怎么努力也拿不到。与其发一条注定失败的路径,macOS 侧直接读 `latest-mac.yml` 比对版本,当更新源更新时用系统浏览器打开产物地址,并说明拿到之后怎么办——包括未签名应用首次运行时 Gatekeeper 要求的右键打开。

这个对话框被限制在启动与手动检查两处。会话中途的定时检查即使发现新版本也只写一行日志,因为正在进行的这次会话没有问过。

### 强制更新层

清单里带一个本产品自有的字段 `minimumVersion`:低于该版本的客户端必须更新才能继续使用。electron-updater 用 js-yaml 解析清单并把未知字段保留在 `updateInfo` 上,所以 Windows 从那里读,而自己解析文件的 macOS 直接读。判定只在 `isMandatory` 一个函数里、只由一个输入算出;字段缺席即没有红线,所以从不设置它的更新源,行为与这个字段存在之前完全一致。

| | Windows | macOS |
|---|---|---|
| **启动时** | 不展示 UI,内嵌服务端拆除。下载不经征询直接开始,走进度窗;完成后的对话框只有「重启安装」。下载失败则给出「重试」与「退出应用」两条路。 | 阻断对话框给「去下载」或「退出应用」;两者都以退出收尾,不进应用。 |
| **会话中** | 下载不经征询立即开始,并弹一次对话框告知。完成后「立即重启安装」与「稍后」并列——尊重正在进行的工作,下次启动才是这道闸不再可商量的地方。 | 提示一次并给出下载;下次启动会被阻断。 |

启动闸与服务器启动并发执行,所以在常规路径上它不占任何墙钟时间;它还带一个超时,而超时的结果是**放行**。连不上的更新源绝不能把人锁在自己的机器外面;红线留给下一次能读到它的启动去执行。

运维上,这条线由发布者设定、此后自行延续:`--minimum-version` 写入它,而此后每一次省略该参数的发布都会把更新源已在提供的值原样带上。忘记加参数不会悄悄丢掉一条红线。

### 发布是一次有序上传

`scripts/publish-update.ts` 接受 `--notes <文件>`、可选的 `--minimum-version` 与 `--dry-run`。清单与 `package.json` 对不上的 `dist-app` 它拒绝;上传前重算安装程序的 NSIS 启动 CRC;拒绝高于本次所发布版本的红线(那会把所有客户端卡死);并断言本地版本盖过更新源在提供的版本。

上传顺序就是原子性机制:**先全部产物、两端各自校验,清单最后。**因此正在轮询的客户端在发布途中读到的是旧清单指向旧产物,绝不会读到一份指着还在上传的文件的清单。NSIS CRC 校验移到了 `scripts/nsis-integrity.ts`,构建闸与上传闸因此是同一份代码。

清单还会被裁到真正发出去的那些产物。electron-builder 会列出它产出的每一个产物,于是 `latest-mac.yml` 在 zip 旁边还写着 dmg,而上传的只有 zip;脚本的做法是剔除上传集合之外的条目,而不是把上传集合撑大——dmg 是给手动安装用的方便件,更新路径里没有任何一环需要它。

真正难的地方是把字节送过去。到这台主机的链路掉得足够频繁,以至于 `scp`——断了就从零重来——连着三次都没能传完那个 145 MB 的安装程序,而服务器上没有 rsync,这台机器也不归本项目装包。于是上传改为只把服务器缺的那一段流进远端的 `cat >>`,每一轮用 `stat` 定位、用 `md5sum` 确认:每次尝试都保住已经拿下的地盘,所以有界重试能在一条不断掉线的链路上收敛。上传顺序也只保证单个渠道自洽——有一次正好死在两份清单之间,Windows 因此比 macOS 高了一个版本——所以发布最后会把两份清单都读回来,不一致就报错。

重发同一个版本是上传中断后的修复路径,也是唯一一个会覆盖线上清单已经背书过的产物的操作:字节被替换的那段时间里它们与已发布的 sha512 对不上,此时下载的客户端会校验失败并在下次检查时重试。这可恢复、窗口也短,但不该是误撞进去的,所以它需要显式的 `--republish`。

### 更新源放在哪

服务器是本项目既有的常开主机。它的 nginx(自定义前缀 `/data/third_party/nginx`,编译时 `--without-http_rewrite_module`,master 不归 systemd 管)只加了一个带 `alias` 的 `location /dsh-updates/`,追加进那个本来就在的 TLS server 块,并以 `nginx -s reload` 重载。更新源不套 BasicAuth,因为 electron-updater 不会带凭据,而这个目录里除了本产品的安装包什么都没有。

### 启动页显示阶段,不显示输出

同一次改动换掉了启动控制台。它原先实时滚动主进程的每一行预检和服务器打印的每一个字节——这对开发者是正确的诊断面,对正在等待的人却是错的:它把一堵文字墙摆成需要阅读的样子,而其中最常见的内容(一次被杀毒扫描拖慢的普通首启)看上去像正在发生的故障。

现在页面**一次只显示一个阶段**——`校验运行环境`、`启动 dsh 服务`、`连接界面` 里正在跑的那一个,秒数过三秒才出现,超过八秒再淡入一行说明首启会被扫描。还没开始的阶段根本不渲染:一份"尚未发生的事"的清单,只是一张让人猜哪里出错了的名单。几行叠在一个定高容器里做交叉淡入淡出,所以推进阶段不会让页面上任何别的东西移动。被阻断的启动复用那行提示说明自己为何停在这里。

页面上有字标(`从这里开始` 加一个闪烁光标;中文走真正的 CJK 字族,只有光标留在等宽里),底部是一行纯版本号。它**不再**带日志路径——启动页上的一条路径,只对已经知道自己需要它的人有用。取而代之的是菜单项 **帮助 → 查看日志**:打开该文件,打不开则回退到在文件管理器里定位它;它在"仅打包"分支之前构建,所以开发启动同样有。失败时正在跑的那个阶段转红,出现一行摘要,下面的指引点名那条菜单路径。

**文件 sink 完全没变**——每个字节仍然落进 `dsh-server.log`,只是不再上屏。诊断材料因此原封不动,只是从等待体验里移了出去。

启动页也不再是恒定的暗色。它带着两套色板,取自 web UI 自己的 token 表(`packages/client/ui-theme/src/styles/design-platform.css`)——背景、主文字、三级文字与那点蓝色强调——于是交接给应用是一次延续,而不是一次切换。painting 哪一套在窗口存在之前就定下:`backgroundColor` 决定页面加载期间显示什么,而晚定正是"闪一下另一个主题"的成因。这个选择会读 web UI 存的那份持久偏好(`~/.dsh/settings.yaml` 的 `ui-theme.preference`),遇到它的默认值 `system` 或任何读不出来的情况,再回落到 `nativeTheme.shouldUseDarkColors`;这就是为什么一个显式选了亮色的用户,在暗色系统上不会被塞一张暗色启动页。下载进度窗共用同一个模块。两种模式一视同仁——每一处背景与文字都是应用自己也在用的 token——所以留给启动页专有的是构图而非配色:字标、光标、点阵、暗角与那圈强调色辉光。

## Verification

macOS 构建从打包后的 `.app` 启动、走到它的 `dsh web:` 行、该 URL 返回 200,退出后无残留进程。Windows 安装程序过了 NSIS CRC 闸,`app-update.yml` 在打包资源里,`app.asar` 内含 `node_modules/electron-updater`。更新源路由在发布任何东西之前已从公网、对着真实证书链验证过,nginx 重载后也确认了原有的 `/flood/` 路由仍然回 `401`。

## Alternatives considered

**用 Squirrel.Windows 而非 NSIS + electron-updater。** 仓库已在 `pnpm-workspace.yaml` 里禁掉 `electron-winstaller` 的构建,而 Squirrel.Windows 会替换掉那个 NSIS 安装程序——它的完整性闸之所以存在,正是因为一台真实 Windows 机器拒绝过更早的构建。留在 NSIS 上意味着更新路径与安装路径是同一个产物,由同一个 CRC 校验把关。

**自建更新后端。** 更新 API 能做灰度、按用户分渠道、下载统计。这些都不想要,而清单**本身**已经是判断过程——加一个服务,换来的只是又一个要跑、要盯、要护的进程,而静态文件已经做到的事一样也没多。强制更新是通常需要买一个后端才有的那部分策略,结果它只是一个字段。

**macOS 走 electron-updater。** 这是被硬约束否掉的,不是偏好:Squirrel.Mac 拒绝为未签名应用暂存更新,所以那条代码路径存在的唯一作用就是失败。发现版本并打开下载,是一个未签名构建能诚实给出的上限。

**在服务器 IP 上走明文 HTTP。** 原定方案,依证据放弃:该主机入站 TCP/80 在防火墙处被丢弃,IP 加 80 端口的更新源每次检查都会超时。主机在 443 上应答,证书对得上解析到它的那个域名,于是 TLS 既是可用的那个选项也是更强的那个——它认证服务器,而 HTTP 做不到。

**退出时安装(`autoInstallOnAppQuit`)。** 很诱人:它省掉最后一次点击,而且更新是在用户不等待的时候落地的。否掉是因为它让应用在一个没人选择、也没人在看的时刻替换自己:退出不等于同意安装,而那时失败也没有任何可以汇报的面。代价是下载好的更新可能无限期不装;两次再提醒把"能隐形多久"框住了。

**保留滚动启动日志。** 启动失败时它确实是更好的面,失去它是这次重做的真实代价。失败态把它买了回来:点名日志文件并索要它。而这恰恰才是真正能把输出送到开发者手上的做法——屏幕上的一堵文字,人只会截图,不会发送。

## Consequences

装好的 Windows 客户端以三个显式步骤自更新;装好的 macOS 客户端会告知有新版本并把人送过去。一次 `publish-update.ts` 同时服务两端,而一个 `minimumVersion` 字段就能把二者中任意一个升级为强制,无需再发一版客户端。

更新源的安全性是诚实但不完整的:TLS 认证**服务器**,清单里的 sha512 把产物绑定到清单,所以没人能在传输途中做手脚——但产物仍未签名,于是对 `/var/www/dsh-updates` 的写权限就等于对每个客户端下一个安装程序的写权限,而两个操作系统都不会为下载到的东西背书。代码签名(Authenticode,以及 Developer ID 加公证)是补上这一环的升级,也正是能让 macOS 改为原地安装而非交接的那件事。

`minimumVersion` 是一把发布者持有、客户端服从的锁。红线若定在人们实际够不到的版本之上,会把每一份安装都变成砖,所以发布脚本拒绝写入高于本次发布版本的值——但没有任何机制能拦住一条对着装不上的产物发出的错误红线,所以它始终是一个刻意的、极少动用的动作。

这条通道给桌面应用添了 `electron-updater` 与 `js-yaml` 两个生产依赖,它们必须进到 `app.asar` 里,Windows 路径才谈得上能用——发布流程里的 asar 检查即为此而设。更新源地址现在同时出现在 `electron-builder.yml`(生成清单)与 `src/updater.ts`(运行时读取)中;迁移更新源要同时改这两处,README 记下了这个配对关系。
