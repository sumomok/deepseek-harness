# Agent Note: porting text-file composer draft attachments onto the 0.1.2 reorganization

Status: implemented

English | [中文](2026-08-31-file-attachment-composer-intake-port.zh.md)

## Problem

The original patch (`98020a23cd`, "text files as composer draft attachments") made the composer treat a dropped or pasted text file as a first-class draft attachment alongside an image: a discriminated `ComposerAttachment` union, a client-side content sniff splitting a mixed batch before it reaches the image- or file-intake path, a new `FileChipRow` beside the image rail, and `image-labels.ts` renamed `attachment-labels.ts` to carry both kinds' copy. That patch predates the upstream 0.1.2 package reorganization (`ui-conversation` split into `ui-conversation`/`ui-chat`/`ui-trajectory`; a `dsh.client` cross-package runtime-import gate tightened; an optimistic submission-echo system landed) and the rc.26 sync's own Family A (which added the `session.file` readback RPC and file-content-block wire plumbing this composer work assumes). Porting the original diff unchanged does not compile against the current tree: two of its target modules moved packages, its target shared-utility placement is now forbidden, and its target submission path already carries fields the original patch never had to touch.

## Decision

**Same discriminated union and reused input machine, ported verbatim.** `ComposerImageAttachment`/`ComposerFileAttachment`/`ComposerAttachment` in `packages/client/ui-conversation/src/client/contract/slots.ts` match the original patch exactly, as does reusing `InputState.imageIds`/`addImages`/`removeImage` unchanged for file ids — the frozen input-machine contract still never inspects content kind.

**`attachmentSizeText` and the file-sniff pair move to `ui-primitives`, not into `ui-conversation`'s client barrel.** The original patch re-exported both from `ui-conversation`'s barrel for `ui-attachment` to import as runtime values across the `ui-conversation` → `ui-attachment` package boundary; that boundary is legal in the pre-reorg tree but rejected today by `verify-client-packages`: a `dsh.client`-bearing ("dynamic") client package may not declare a runtime `external` naming another dynamic package's exports, only type-only imports survive. `packages/client/ui-primitives` carries no `dsh.client` field — it is a plain library package exempt from the dynamic-row check entirely, already the home of `IconCloseFill14`/`StateDot` that `ui-attachment` imports the same way. `byte-size.ts` (`attachmentSizeText`) and `file-sniff.ts` (`sniffIsText`/`partitionDroppedFiles`/`PartitionedFiles`) move there; `ui-conversation`'s own consumers (`attachment-labels.ts`, `InputBar.tsx`) and `ui-attachment`'s `ComposerAttachments.tsx` import both directly from `@deepseek-ai/dsh-client-ui-primitives`. This makes the original series' later build-purity fix (`59657e0132`, fixing a stale-import regression from exactly this cross-package pattern) moot in this port: the bug it fixed is never introduced, because the correct non-dynamic-package placement was used from the start. `59657e0132` is recorded SKIPPED in the ledger with this note as the reason, not silently dropped.

**The submission echo gains a `files` sibling to `images`, not a rename.** The original patch predates `beginSubmission`/`PendingSubmission`/`PendingSubmissionRetirement` (an upstream addition that inserts a synchronous local echo before the host round-trip settles); the current tree's `sendSession` already routes every image submission through it. Porting the file-draft path without threading it through the echo would silently regress: a file-carrying send would show no optimistic bubble and the composer would restore drafts on the wrong signal. `BeginSubmissionInput.files: readonly PendingSubmissionFile[]` (name + bytes, known synchronously — no async header probe like an image's dimensions), `PendingSubmissionRetirement`'s `observed` variant renamed `attachments` → `images` and gained a sibling `files: readonly FileAttachmentRef[]`, and `Session`'s internal `imageRefsIn` renamed `attachmentRefsIn` to scan both `'image'`- and `'file'`-typed content blocks. `ConversationController.sendSession` splits `imageAttachments`/`fileAttachments` from the resolved drafts, includes both in `beginSubmission`, and settles each kind on retirement through parallel `settleSubmittedImages`/`settleSubmittedFiles` methods (the file settler has nothing to revoke — no browser preview resource exists for a file draft). A new `fileLimits` session projection (mirroring the pre-existing `imageLimits`) is registered in `packages/api/session-controller/src/list.ts` alongside `imageLimits`, reading `ctx.attachments.fileLimits` — already present on the `AttachmentStore` abstraction Family A landed, requiring no further host-side attachment-service change.

**Everything else ports unchanged**: `FileChip.tsx`/`FileChip.module.css` (byte-identical to the original), `ComposerAttachments.tsx`'s partition-drop/render-both-rows logic, `attachment-labels.ts`'s `attachmentErrorText` file-reason cases, the `file.*` locale key set and the drop-copy privacy reminder, `InputBar.tsx`'s `intakeFiles`/`intakeDrop` kind-scoped pre-check pair (adapted only to route through the current tree's pre-existing `registerComposerKeymap` paste hook, a keymap abstraction the original patch's base tree did not have), and `ConversationController`'s `createDraftFiles`/`releaseDraftImage` kind-guard/`serializeDraftImages` kind-filter/`serializeAttachments` kind-dispatch/`encodeFile`.

**Scope boundary with the next port (B.1+B.2, original patch `fabc93555c`).** `fabc93555c` ("file-part bubble card and the referent/open seam") lands immediately after this one upstream and touches three of the same files this patch also touches: `AssistantBlock`'s `{kind:'file', ...}` variant (`contract/records.ts` and its Chat-side projection), `attachmentErrorText`'s `SUBAGENT_FILE_UNSUPPORTED` case and `file.subagentUnsupported`/`file.open`/`file.loading`/`file.loadFailed` locale keys, and `ISession.readFile`. All of that content was drafted alongside this patch during the port's development but is deliberately held out of this commit and deferred to the `fabc93555c` port: it belongs to the next patch's diff, not this one, and this note's own "one original patch, one commit" discipline would be violated by including it here even though nothing prevented it from compiling in place.

## Alternatives considered

**Keep the original's `ui-conversation` barrel re-export and grant `ui-attachment` an explicit `external`.** Rejected: this was tested directly (adding `"external": ["@deepseek-ai/dsh-client-ui-conversation/client"]` to `ui-attachment`'s `package.json` and running `verify-client-packages`), which fails with the gate's own error naming the violation. The gate postdates the original patch and is not a false positive to route around.

**Leave `PendingSubmissionRetirement.attachments` in place and add a parallel `fileAttachments` field instead of renaming to `images`.** Rejected for symmetry: an unexplained `attachments`/`fileAttachments` pair reads as though `attachments` still means "everything," when it has only ever carried image references. Renaming to `images`/`files` names both fields for what they hold, matching the CLAUDE.md convention against unexplained asymmetry between parallel values.

**Defer `fileLimits` to the `fabc93555c` port, since only its consumer (`InputBar.tsx`'s file-intake pre-check) is this-patch scope while the underlying `AttachmentStore.fileLimits` field is Family A's.** Rejected: the original patch's own `fileLimits` intake pre-check has no independent value without the projection that serves it, and registering the projection is a small, symmetric, self-contained addition next to the pre-existing `imageLimits` registration — holding it back would leave this patch shipping a pre-check that always defers to the host with no way to test the client-side limit path.

## Consequences

`packages/extensions/cordis-client-runner/src/client/slot-catalog.ts` (generated) picked up the widened `ComposerAttachmentsOwnerProps`/`ComposerBarInjected` shapes via `pnpm run gen-client-catalog`. `packages/client/ui-conversation/tests/input-matrix.client.spec.tsx`, `input-scenarios.client.spec.tsx`, and `skeleton.client.spec.tsx` needed the same mechanical `addFiles: () => null` addition the original patch made. `input-bar.client.spec.tsx` and `composer-attachments.client.spec.tsx` needed the same PNG-magic-bytes and `waitFor`-around-the-async-sniff fixes the original patch made, plus one further fix this port's own baseline required: the mixed-paste test's draft-commit assertion was already wrapped in `waitFor` in the current tree (an unrelated pre-existing timing fix the original patch's own base tree did not have), so the port keeps that wrapping instead of reverting to the original's synchronous check. `service-orchestration.client.spec.ts` gained the original's three new tests (file-draft creation/release, mixed image+file send, `serializeDraftImages` kind-filtering) adapted to route the mixed-send test through the current tree's echo-bench harness (`beginSubmission`/`onRetire`), which the original test predates; its three pre-existing echo tests needed their `onRetire({reason:'observed', attachments: [...]})` call sites updated to the renamed `images`/`files` shape, otherwise `ConversationController`'s `retirement.images[index]` read throws on `undefined`. `attachment-labels.client.spec.tsx` keeps only the `attachmentErrorText` coverage from the original file; the original file's `AssistantMarkdown` "assistant image slot handoff" describe block tested a component that the 0.1.2 reorganization already relocated to `ui-chat` before this port began, so it never belonged in this file's ported version. The byte-size unit test moved to a new `packages/client/ui-primitives/tests/byte-size.client.spec.ts` and the file-sniff unit tests to a new `packages/client/ui-primitives/tests/file-sniff.client.spec.ts`, following their source modules' relocation.

**Gap closed later (2026-09-01).** This port carried the composer's own half — draft state, intake, chip presentation — but not the fixture transport the assembled web scenarios run over. `packages/client/connection`'s `createFixtureConnection` knew only `text` and `image` prompt parts, so its prompt mapper read `block.data.length` off a file part that carries `name`/`text` instead, and every file send over the fixture failed with `session/prompt failed: Cannot read properties of undefined (reading 'length')` — the composer, the machine, and the durable seam were all correct. The fixture now mirrors the image side one-for-one: a `file` member on the prompt-part union matching the composer's `EncodedFileAttachment` wire form, a `fileAttachments` store keyed by the id the prompt mints, and a `file` route serving `{ attachment, text }` behind the same `logReferencesAttachment` authorization the `attachment` route already applies — the endpoint the host declares as `@Remote('file')`. `apps/web/tests/file-display.expected.e2e.ts` replays green on it.

**Retirement.** Unchanged from the original: this composer-intake layer is a temporary overlay for a capability upstream does not have yet. If upstream's own composer accepts non-image attachments, this patch (and this port) retires and the fork adapts to upstream's form.
