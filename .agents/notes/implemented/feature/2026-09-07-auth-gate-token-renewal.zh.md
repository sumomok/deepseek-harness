# Agent Note: 部署方公布了端点时，闸门就地续期它的 token

Status: implemented

[English](2026-09-07-auth-gate-token-renewal.md) | 中文

## Problem

[浏览器单点登录](../architecture/2026-08-28-browser-single-sign-on-and-mcp-token-injection.zh.md)的闸门在 token `exp` 之前 `refreshMarginSeconds` 时动作，而动作只有一种：交出 token，把访客送去登录页。这套部署里 token 只活两个钟头，于是有人正在其中干活的控制台每两个钟头就把他登出一次——活干到一半，屏幕上原本的一切换成一张登录表单。

部署方自己并不这样对待它自己的页面。它的前端是惰性续期的：`toy-core/api/axios.js` 的请求拦截器一旦发现 `isTokenRenewal()` 说存着的 token 比 `accessTokenRenewalTime` 分钟更老（默认 30，从 `accessTokenTime` 起算），就在任意一个请求上调用 `tokenRenewal()`，而 `tokenRenewal()` 从 `GET /nrms-auth/api/renewal` 里读出一枚新 token，用 `setToken` 存下。于是那个部署的每个页面只要开着就一直保持登录。挨着它们的控制台，是唯一不这样的那一面。

## Decision

**续期是两个 `Config` 字段，默认都不填，不填的部署行为与从前一模一样。** `renewalPath` 是那个端点，写成本页面自己源上的一条路径——标准安装是 `/<API 前缀>/nrms-auth/api/renewal`——`renewalIntervalSeconds` 是一枚 token 被持有多久之后闸门去要新的一枚。端点在哪里有两重的部署差异：API 前缀是前端自己的 `VUE_APP_BASE_URL`，而立在路径前缀反向代理后面的部署还要再带上那个前缀。两者只填一半都会被拒，加载即响：只有间隔没有路径，是一个自以为在续期、实则没有的部署；只有路径没有间隔，则按不存在的排期续期；间隔为零是一个请求循环；而不是根绝对的路径——包括协议相对的 `//host/path`——会把这位访客的凭据发出本部署之外。browser 半边在 settings 文档上把它们作为一个嵌套的 `renewal` 块收到，于是「要么都有要么都没有」是结构性的，而不是两个读者都得记住的一条规矩；收到后它把这三件事再查一遍，因为那份文档跨过了一个进程。

**两条排期都会去要，而对被拒作出反应的只有其中一条。** 两条都在一枚 token 被接受的那一刻装上，且每接受一枚就重排一次。周期性滴答在那一刻之后 `renewalIntervalSeconds` 触发，成败都不出声——部署方自己的规则是「手上那枚比间隔更老就续」，而这里是把那条规则做成计时器，而不是做成对一个本外壳根本不会发出的请求的检查。过期余量也会去要，而有去处的正是它：余量上没能续到，就交出 token 并前往登录页，也就是没有续期端点的部署一贯的做法。周期性尝试失败不改变屏幕上的任何东西，也不改变 node 半边的任何东西，因为手上那枚仍然可用，下一次滴答会再要一次。

**同一时刻只有一次交互，是共享而不是拒绝。** 余量遇上已经发出的周期性尝试时会等它的答复，而不是再发一次，也不是在第一次的答复还在路上时就离开。已经过了 `exp` 的 token 绝不送出：端点会拒掉一枚已死的，而那种情况在余量那里收场。

**答复只有把过期时间往后推才算数，而余量最多续一次。** 一枚续期只有在它的 `exp` 既晚于发出该请求时所用的那一枚、又晚于答复到达时存储里的那一枚时才被采纳。第一条规则拒掉把收到的那一枚原样答回来的端点：这样的答复什么也没续，被它满足的余量会以零延迟重排，两边就会在端点还肯答复的时间里一直往来——于是周期性滴答把它读作一次失败并保持沉默，余量把它读作一次失败并前往登录页。第二条规则不让一个标签页里慢到的答复盖掉另一个标签页已经存下的更新的一枚。被采纳、而自身已经落在余量之内的续期也不再从余量续第二次，理由同样是它自己的余量计时器是以零延迟排上的：对于 `renewalIntervalSeconds` 在 `refreshMarginSeconds` 之前不留余地的部署，这个闸门的答案是登录页。

**每一次余量只为它排上时的那一枚 token 作答。** 余量计时器带着那一枚，续期失败时也只交出那一枚——除非此刻手上的那一枚自身就落在余量之内，也就是上一条规则以登录页收场的那种情况。一次交互要花时间，而在它进行中到来的 token 会排上属于它自己的余量：另一个标签页续了、同源上被嵌入的部署页面续了、这位访客又登录了一次。没有这道检查，一次失败的续期就会吊销一枚距过期还有几个小时的凭据、清掉整个源都在读的那枚镜像，并把一个还在用的页面送去登录表单。

**比一个浏览器计时器拿得住的更长的延时会被拆成几段睡过去；而那么长的间隔仍然让这一行失败。** `setTimeout` 把延时放在一个 32 位有符号的毫秒字段里，更长的延时不会被等满，而是在下一次滴答就触发。于是 browser 半边的 `schedule` 先睡满 2147483647 毫秒，再为剩下的部分重排一次，而取消取消的是此刻挂着的那一段；两个计时器都走它，因此两个都容得下任意长的延时。真正需要这一点的是过期余量：它的延时就是部署方那枚 token 的 `exp`，而签发 30 天 token 的部署本来会在启动时就把访客登出——那个余量被浏览器放到下一次滴答就触发了。超过 2147483 的 `renewalIntervalSeconds` 在两个半边仍然让这一行失败，是拒绝而不是拆段，因为它是没有哪个部署会真心写下的数字：它说的是一条 24 天后才第一次触发的排期，而这个闸门接受的 token 没有一枚活得到那时候。

**浏览器拒掉的存储写入，算作一次什么也没产出的续期。** 配额已满会让 `localStorage.setItem` 抛错，浏览器压根不给配额的无痕窗口也一样。这个抛错被当成失败对待，与浏览器没留住的镜像 cookie 一样——周期性那条路保持沉默，余量以登录页收场——而不是让一个没人 await 的 promise 被拒，那会让页面一条排期都不剩。

**页面无论以哪种方式离开，闸门都先被释放掉。** 交出 token 这件事，会在登出请求发出之前先停掉存储订阅、两个计时器以及仍在途中的续期；换了个人登录时，在那次 reload 之前做的是同一件事。事件循环已经出队的回调之后照样会跑，已经发出去的答复也照样会到；采纳其中任何一个，都会把一枚 token 写回存储、写回镜像 cookie、也写回 node 半边——写给一个刚刚把它交出去的访客；而在换人那一路上，是把刚刚离开的那个账号写进即将载入的那份文档读取自己身份的那三处。

**请求就是部署方自己的客户端所发的那一个，写入就是它自己的 `setToken` 所做的那一次。** `GET <renewalPath>` 带着存储里那枚 token 原样（含 scheme）放在 `Authorization` 与 `CertificationToken` 两个头上；`localStorage.loginUserInfo` 存着的那些头放在它们之下；再在最上面盖一枚新的 `TINY-REQUEST-ID`——这个顺序就是 `api/axios.js` 组装它们的顺序。答复按 `tokenRenewal()` 的读法读：响应正文自己的 `token` 字段，也就是那个文件的响应拦截器把 `service.get` 解析成的东西。取回来的东西原样存在 `accessToken` 下，旁边写上 `accessTokenTime`，于是既有的「存储 → cookie → node 半边」那条路把新 token 送到 node 半边，也送到同源上任何一个被嵌入的部署页面。镜像 cookie 在写存储**之前**写入并读回，于是反向代理读到的那枚 cookie 与存储里的值从不互相矛盾；浏览器没留住的那次写入，会让页面继续用它本来就有的那枚。

**`accessTokenTime` 是 UTC 的 ISO 8601 时刻**，而不是 `dayjs().format()` 给同一时刻的本地偏移写法。那个部署里它唯一的读者 `isTokenRenewal` 会解析它并取差值，因此两种写法对它是可互换的，而这一种不会随浏览器所在时区而变。

**`GateBrowser` 多的是一道存储缝，而不是第二个 token 读者。** `readToken()` 没了，取而代之的是 `readStorage(key)` 与 `writeStorage(key, value)`；把登录页那个 `Bearer ` scheme 去掉这件事，发生在这道缝之上——每一处对存储值的解读本来就都在那里。另外两项新增是 `requestId()` 与 `requestJson(path, headers, signal)`，于是闸门本身依旧不需要 DOM 就能跑，每个续期测试驱动的都是一个假浏览器。那个 signal 就是闸门的 disposer：被释放的闸门会中止它发出的那个请求，之后再答复的东西一概不作数。

**node 半边不新增路由。** 一枚续来的 token 抵达它的方式与其他每一枚一样——闸门装上它，`push` 把它 POST 到 `/auth-gate/token`，闭包持有它。续期没有任何一处对模型可见：没有工具，没有 prompt 段落，没有 session 事件，因此也没有快照基线的变化。

## Alternatives considered

**像部署方那样，在下一个请求上惰性续期。** 因为根本没有那样一个请求而被否。控制台不通过 `toy-core` 的 axios 实例与部署方讲话——browser 半边只发它自己那三个请求，全都发给 node 半边——因此没有可以挂惰性续期的拦截器，而闸门手上唯一的时钟就是它自己的计时器。计时器是同一条规则，配上闸门真正拥有的那个触发点。

**让过期余量成为唯一的触发点。** 因为它要立在什么之上而被否。那会把一枚两小时 token 的全部续期押在它死前五分钟的一次尝试上，而一次请求失败的答案就是登录页；那还会让控制台存着的 token 比那个部署每个其他页面手上的都老上几个钟头。周期性地去要，让控制台与那些页面同步，而余量就从机制退成兜底。

**读 `accessTokenTime`，在存着的 token 比间隔更老时续期——逐字照搬 `isTokenRenewal`。** 被否：那会让排期依赖一个存下来的时间戳的格式，以及一套「这个值缺失、读不动、或在未来时怎么办」的政策，而这一切只是为了复现闸门本来就知道的一刻——它接受手上这枚 token 的那一刻。于是一个在旧 token 上打开的页面要等满一个间隔才去要；余量仍然管着那枚 token，而部署方自己的页面一被使用就会把它续掉。

**周期性尝试失败就退回登录页。** 被否：那一刻 token 仍然可用，于是一次瞬时失败就要让访客付出他正在其中干活的那个页面。失败真正意味着凭据快用完的地方是余量。

**新增一条 node 半边路由来接收续来的 token。** 作为通往同一个地方的第二条路而被否：闸门装上新 token 的方式，与它装上另一个标签页写下的那一枚一模一样，而 `push` 本来就把它 POST 到 token 路由。

**照搬部署方对 `Refresh-Authorization` 的处理。** 因为那不是一条续期通道而被否。响应拦截器的那个分支读的是 `response.config.headers['Refresh-Authorization']`——请求自己配置的头，而不是响应的头——因此它只对客户端本该自己发出的一个头触发，而没有谁在发它。

**选一个主标签页，只由它续。** 就本次改动而言被否：闸门没有可复用的选主或加锁概念，而加一个是比它要优化的这次续期更大的一块设计。相应的后果记在下面，而不是被藏起来。

## Consequences

**买到的。** 配好了自家部署续期端点的控制台，只要开着就一直保持登录，而它持有的 token 与那个部署每个其他页面持有的一样新。node 半边把续来的 token 花在 MCP 转发与数据后端上，而不必知道有「续期」这回事。

**付出的。** 每个间隔、每个打开的标签页一次 `GET`，把访客的凭据带去一个由部署方配置的端点。多两项 `GateBrowser` 操作，以及一次写入——闸门此前只读那块存储。不填这两个字段的部署与从前完全一样，也就是说它仍然每两个钟头把访客登出一次。

## Known Limitations and Deferred Work

- **本次改动所面向的那套部署不签发新 token，续期在那里因此是空转。** 它给出的每一份答复带回来的都是发出去的那一枚，包括在 `exp` 之前 2.3 分钟要的那一次；而那个 `exp` 之后 100 秒，端点与一次元数据读取都答 401：在那套部署上，JWT 的 `exp` 就是真正的过期时间。那两个字段因此在那个控制台上保持不配置，它保留本来就有的「余量→登录页」那条路，于是面对那套部署，本次改动买到的东西不比旧行为多。这些测试里每一个端点都是假的；要看到续期端到端地跑起来，需要的是一个端点会答更晚 `exp` 的部署。
- **设了 `isAuth` 的部署根本进不了这道闸。** `getLocalConfig().isAuth` 为真时，`toy-core` 的 `getToken`、`setToken` 与 `isTokenRenewal` 会把所有键换成 `accessTokenAuth` 与 `accessTokenTimeAuth`（`core/token.js`），而本包两个半边都只认默认的那两个键名。在这样的部署下，闸门读的是那个部署的登录页从不写入的键，于是访客被送去登录页、登录、再被送去一次。键名无从配置，这处不匹配也没有任何东西会报出来；真的有部署设了 `isAuth`，才是让那张表从常量变成配置的理由。
- **由余量触发的续期可能多花一个请求。** `arm` 会取消那个周期性计时器，但事件循环已经出队的回调照样会跑，于是与一次余量续期在同一轮到期的滴答会再问端点一次。上面那些规则对这份答复的采纳与拒绝跟对别的一样，因此代价就是部署方多看到的这一个请求；要关掉它，就得给 `arm` 加一个代次计数。
- **配额收下第一次写入、拒掉第二次时，会存下一枚这个闸门随后又放弃的续来 token。** `writeRenewal` 先写 `accessToken`、再写 `accessTokenTime`；收下 token 却在写时间时抛错的浏览器，会让整次续期被报成什么也没产出，于是余量交出凭据、前往登录页，而存储里放着的是那枚新 token 配上它前一枚的年龄，部署方自己的页面会把它读得比实际更老。这里没有任何东西把两次写入区分开——假浏览器两次都拒——要关掉它，就得把时间写在前面，或者把这一对存在同一个键下。
- **每个打开的标签页各续各的。** 没有选主，也没有锁：两个标签页各自每 `renewalIntervalSeconds` 要一次。它们最终会一致，因为没去要的那个会把另一个的写入当成同一个人的 `storage` 变化，走既有的那条路取走更新的一枚；但部署方看到的是每个标签页一次交互，而两份答复交错时以最后一次写入为准。
- **周期性续期失败什么也不说。** 一个续期端点已经拒了几个钟头的部署，看上去与没拒过的一模一样，直到余量到来。
- **在旧 token 上打开的页面要等满一个间隔。** 排期从闸门接受一枚 token 时开始，而不是从那枚 token 被签发时开始，因此在一枚 token 活了一个钟头后才打开的标签页，是一个间隔之后才去要，而不是立刻。
- **那两个续期字段是逐部署自选的。** 没有谁会从 `bizUpstream` 或从登录页推断出那个端点，因此一个有续期端点却没配的部署会保持旧行为，并且没有任何诊断说明这一点。
