# Agent Note: Desktop tray residency and task notifications

Status: implemented

[English](2026-08-19-desktop-tray-and-task-notifications.md) | 中文

## Problem

桌面客户端是一个跑着 agent 的窗口,而它的两端都不对。

Windows 上关窗即退出应用,退出会拆掉内嵌服务器——于是关闭按钮,这个在任何别的浏览器形态窗口里都只表示「我看完了」的东西,把 agent 正在做的事一并结束了。没有任何办法把客户端收起来而让活继续跑。

也从来没有东西叫用户回来。一个跑完了任务的 agent,或者一个停下来要批准、要回答的 agent,和一个还在干活的 agent 发出的是同一种沉默,于是想知道某个会话在等你,唯一的办法就是把窗口摆在前面盯着。这跟后台 agent 的意义正好相反,也正是第一个问题真正扎人的地方:一个你没法走开的客户端,不需要托盘。

## Decision

### 关窗只问一次,然后记住

Windows 上点关闭按钮弹一个对话框:「最小化到托盘」或「退出应用」,配一个「记住我的选择」勾选框。不勾选,答案只管这一次;勾选,`closeAction` 就写进 `desktop-state.json`,此后每次关闭都照它执行、不再问。托盘菜单的「关闭时询问」把它清回去。

最小化按钮原样不动——它就是普通的任务栏最小化,一个想留在任务栏上的窗口必须有办法这么说。

托盘图标在启动时创建,而不是第一次隐藏时才出现,这样「最小化到托盘」指的是屏幕上已经存在的东西,而 检查更新 / 退出 在窗口隐藏时仍然够得着。菜单是 打开 / 检查更新 / 关闭时询问 / 退出,和菜单栏一样按 `app.getLocale()` 本地化——两套文案现在都归 `src/menu-text.ts` 管,因为托盘菜单和它正上方的菜单栏说两种语言,是同一个产品在自相矛盾。

**每一次退出都走 `app.quit()`,因而都走 `before-quit` 那条停服务器的拆除链。**关闭处理器绝不自己销毁窗口:绕开那条链被销毁的窗口会留下整棵服务器进程树,而那正是 Windows 更新器装不过去的那种孤儿进程。`guardWindowClose` 在 `isQuitting()` 为真时整个让开,于是一次「退出中顺手关窗」的拆除,不会被它正在拆的东西拦下来。

**窗口进了托盘,对话框的性质就变了。**挂在隐藏 parent 上的 `dialog.showMessageBox` 是对一个没有任务栏按钮的窗口做窗口模态:既看不见也找不到。所有更新对话框都走 `ask()`,它现在先把窗口显示出来再挂上去,于是「发现新版本」和「重启安装」出现在用户答得了的地方。这跟当初无 parent 对话框是同一个毛病往前走了一步,而「没有用户的决定就不会发生安装」只在这个决定看得见的时候才成立。

### 状态文件长了一个字段

用户数据目录下的 `desktop-state.json` 现在装两样东西,都归 `src/desktop-state.ts` 管:

| 字段 | 含义 |
|---|---|
| `lastRunVersion` | 上次运行的构建版本,更新后的那次启动靠它决定要不要打出「已更新到 vX.Y.Z」。 |
| `closeAction` | `tray` 或 `quit`——记住的关窗答案。缺失表示要问。 |

读的时候容忍文件缺失或读不出来,写的时候容忍写失败,两个方向一致:这个文件是壳给自己留的方便,从来不是运行的前提。

### 壳订阅它自己启动的那个服务器

有两个时刻值得打扰:会话**跑完了**,以及会话**在等一个答复**。两者都从运行中的 `dsh web` 上读,走浏览器 UI 自己也在消费的那两条下行 WebSocket,连的就是 `startServer` 早已报出来的回环地址。**上游没有任何改动。**

- `/api/events.host` 送 `host/session-status`,它的 `running` 位是唯一真正的「agent 停了」边沿。持久日志事件 `turn/end` 不是这个边沿——一个 turn 后面可以紧跟另一个——而且工具等批准期间这一位仍然是 `running`,这正是让两种情况不重叠的原因。
- `/api/events.mux` 送 `approval/requested`、`question/requested` 及各自的 `resolved`,外加全部会话事件,其中只留 `session/title`:用作消息里那个名字。

两条流都是全会话、无订阅握手,而且都是**只下行**——客户端一发东西就被 1008 关掉,所以 `src/notifications.ts` 里没有任何地方往 socket 里写。

这两条流有三个承重性质,而且没有一个是显然的:

**SSE 不可用,是服务器自己的决定。**这两个路径上的 `GET` 在 fetch 处理器之前就被 connection 插件答成 `426 Upgrade Required`,它们背后的 SSE 分支只有进程内载体够得着。WebSocket 在这里不是更优的传输,而是唯一的传输。

**Node 客户端靠不发 `Origin` 通过信任闸。**这道闸要求 `Host` 是回环(满足),并接受 `Origin` 缺失,而一个不等于所服务 authority 的 `Origin` 会被裸 403 拒掉。所以这些 socket 上不设这个头,也不能设。

**重开一条流会重放仍然挂着的请求**,所以每个请求都按 id 记下,重复的丢掉而不是再报一次——批准按 `approvalId`,提问按会话 id,因为 `question/resolved` 用 rpc id 而不是当初问出去的那些 question id 来指认被回答的请求。

空闲边沿用同样的方式上膛:一个会话只有在这个壳看见它开始过,才会宣布它跑完了。否则一条打开时就面对若干已空闲会话的流,会去宣布历史。

Electron 43 的主进程是带全局 `WebSocket` 的 Node 24,所以以上这些不花一个依赖。

### 两个平台的告知方式不同

Windows 走系统 toast,点击把窗口抬起来。`app.setAppUserModelId` 设成 electron-builder.yml 里的 `appId`——也就是安装器写到快捷方式上的那个值——因为一个 AUMID 对不上已注册快捷方式的进程,它的 toast 会被静默丢弃。

macOS 走 Dock 角标加一次弹跳,完全不进通知中心。这是产品决定而不是平台限制:一个跑完十来个 turn 的 agent 会留下十来条要一一划掉的横幅,而角标只说有几条、在哪儿,并在窗口获得焦点的那一刻清零。

两个平台上,窗口有焦点时都不通知。

### 通知点不开它说的那个会话

**Web UI 没有 URL 路由。**没有路由库,没有 `history` 调用,整个客户端里唯一被读的查询参数是 `?fixture`;当前选中的会话是内存里的客户端状态。所以点击通知会显示并聚焦窗口,到此为止——那个在等你的会话此时在侧边栏里就差一次点击,而侧边栏本来就为这件事渲染了待交互圆点和已完成圆点。

深链不是桌面侧的缺口,也无法从桌面侧补上。它需要 web 客户端接受 URL 里的一个会话,到那时壳把它交给 `loadURL` 就够了,这里别的什么都不用改。通过 `executeJavaScript` 伸手进客户端内部这条路是有的,被否掉了:那会让壳依赖一棵 React 组件树的私有形状,而没有任何契约保证它稳定。

## Alternatives considered

**不问就隐藏到托盘,或者不问就退出。**两者各错在用户群的另一半,而且猜错的那个人无从挽回:静默隐藏坑了想让服务器停下的人,静默退出杀掉了想让它接着跑的人的活。问一次然后记住,代价是一次安装的生命周期里的一个对话框。

**macOS 上也加托盘。**那边关窗本来就把应用留在 Dock 里,`window-all-closed` 不退出,`activate` 重开窗口。菜单栏图标会成为 Dock 已经在表达的那个状态的第二套控件。macOS 保留自己的习惯;托盘只在 Windows。

**拿 `turn/end` 当「任务完成」事件。**它是那个名字对、意思不对的持久日志事件:turn 会接龙,于是一个多 turn 的任务会把自己宣布好几遍。`host/session-status` 是 agent 自身 `idle`/`running` 状态的桥接形态,每次停下只发一次。

**轮询 `session.list`。**能用、是一元调用、而且不对:它拿服务器已经提供的推送去换一个定时器,而这个定时器要么慢到没用、要么频繁到不诚实,并且照样看不见一个在两次轮询之间开了又关的批准提示。

**注入一个 `webserver.tapIndex` 变换或一个小的上游插件来暴露会话路由。**这能让深链真正成立,也是最终该给的答案,但它是上游改动,而本轮明确是桌面壳这一轮。记在这里,好让下一轮从这个结论出发,而不是重新发现一遍。

**macOS 上进通知中心。**因数量问题否掉,见上。

## Consequences

关闭按钮现在有了一个应用自己选择的含义,而不是窗口管理器强加的那个;内嵌服务器活得比启动它的那个窗口更久。代价是第一次关闭时的一个对话框,以及一个可能和用户今天的想法不一致的状态字段——托盘菜单存在就是为了改它。

通知让客户端在后台可用,那本来就是它被造出来的姿势,而此前它摆不出来。通知也把壳绑在了一份它并不拥有的线格式上:`MuxFrame` 与 `HostFrame` 是上游类型,在这里靠字段名经由防御式读取取用,而不是共享类型,因为桌面包刻意不带任何工作区依赖(它只发 `lib/`)。上游改了形状的帧退化成一条丢失的通知而不是崩溃——switch 落到一个有说明的 default,每一次字段读取都有保护——但仓库里没有任何东西会因此失败。这是从进程外订阅的诚实代价,而防它的闸就是这份笔记加上面那张帧表。

点击通知把用户送进应用,但送不进那个会话。在 web 客户端接受 URL 里的会话之前,侧边栏自己的待交互与已完成标记才是这段路的终点。

## Testing

在 macOS 上对着活的 `dsh web` 验证过:两条 socket 都接受不带 origin 的 Electron-Node 客户端,`host/session-status` 在下 prompt 时报 `running: true`、在取消时报 `running: false`,`session/title` 到两次(先 fallback 后 LLM provider)且后到的胜出。

随后按发布形态跑了通知器本身——真实 Electron 主进程里的 `lib/notifications.js`——对着一个说着已验证信封的桩服务器。它报出了批准、计划审阅和完成三条;对重放的 `approval/requested`、以及没有前置 `running: true` 的 `running: false` 保持沉默;窗口最小化期间 macOS Dock 角标读 `3`,窗口获得焦点后清空。

Windows 的托盘驻留、关闭对话框和 toast 投递结构上完整、未经真机验证:它们需要一台真的 Windows 机器,跟这个客户端发布的其他每一项 Windows 行为一样。
