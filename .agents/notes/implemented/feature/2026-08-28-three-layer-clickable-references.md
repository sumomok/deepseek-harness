# Agent Note: the three-layer clickable-reference architecture (nominate → verify → open)

Status: implemented

English | [中文](2026-08-28-three-layer-clickable-references.zh.md)

## Problem

The prior `proseReferents` seam (`ProseReferents.scan`) let a plugin mark prose spans clickable from syntax alone — an absolute path, a `~/…` shorthand, a bare URL — with no verification step. A 36-shot model self-marking experiment (`~/.claude/jobs/88ebf148/tmp/mark-exp/`) showed markdown-link nomination scores near-perfect on grounded cases and zero false positives on adversarial ones, but its one real weakness — a path authored from memory that no longer exists — reached exactly the class of failure "blue = openable" exists to prevent: a dead link a reader trusted enough to click. Nomination alone (regex/OS-path-syntax detection) cannot distinguish a real file from a plausible-looking one; only checking the filesystem, or a session's own recorded truth, can.

## Decision

**Three layers, strictly ordered: nominate → verify → open.** A span only ever reaches the renderer after verification — this is structural, not a policy a provider could accidentally skip, because `ProseReferents.scan`'s own contract (`packages/client/ui-conversation/src/client/contract/slots.ts`) now states explicitly that it returns **only already-verified** spans, and the render-facing mirror `MarkdownProseReferents` (`packages/client/ui-primitives/src/markdown/render.tsx`) carries the same contract with zero knowledge of what "verified" means — it is cordis-free and stays that way. Verification itself (a session truth index, then a host `stat` for the miss) is entirely a plugin-layer concern (`@haoran/dsh-clickable-refs` in `dsh-plugins`); core opens generic seams and does no classification, mirroring the split the original `proseReferents` seam already established for detection.

**A1 — `resolveLink`/`subscribe` on the contract.** Both new members are optional, so an old two-method provider (`{ scan, open }`) keeps compiling and behaving identically. `resolveLink(destination, displayText, ctx?)` lets a provider verify a *markdown link's* destination — a nomination channel `scan` never covered, since `scan` only sees rendered text/inline-code runs, never a link node's own `url`. `subscribe(listener)` is the missing notification hook for asynchronous verification: nothing before this patch could tell the renderer "a verification batch just finished, some previously-plain spans may now be clickable."

**A2 — markdown links route through `resolveLink`.** `render.tsx`'s `case 'link'` now decodes the destination (`decodeURIComponent`, best-effort) and, when it is shaped like a local path (`/`, `~/`, a drive letter, or a UNC `\\` share) and not an `http(s)`/`mailto` URL, offers it to `context.referents.resolveLink` instead of falling to the existing protocol allowlist. A verified span renders as a `css.fileMention` button (the same style `scan` hits already use); an unverified one renders as plain inline-code with the destination on `title` — deliberately *not* the pre-existing `text (destination)` trailing-text fallback, which would put a long absolute path back into visible prose exactly where this patch is trying to keep prose clean. Absent a provider, or a provider without `resolveLink`, this branch never engages — the destination falls through to the untouched allowlist path, byte-identical to before.

**A3 — the settle-rerender fix.** This is a genuine, independently-confirmed bug, not new scope creep: `MarkdownText`'s `useMemo` had no dependency that could change when an *asynchronous* verification batch completed after a message settled, so a message that settled before its paths finished verifying stayed dead text until the whole page reloaded (a fresh mount re-scans against an already-verified index). `useReferentsRevision` subscribes to `referents.subscribe` and folds an incrementing tick counter into the memo's dependency array — nothing else changes; the settle transition itself already re-renders correctly via the pre-existing `node.data.status` reactivity path (`AssistantNodeView` → `AssistantMarkdown` → `MarkdownText`, `streaming` prop flips `true`→`false` on genuinely new node data), which this patch verified rather than assumed.

**A4 — `probeTargets`, added only after confirming nothing reusable exists.** Recon covered `packages/api`, `packages/fs`, every `packages/client/*` directory-facing package, and `packages/host/*`: the only path-existence-adjacent client↔host RPC is `host.listDirectory`, which lists full directory contents (violates "stat only, no listing") and sits behind the `browse` capability, which most desktop installs (native picker, no RPC at all) don't have. The new `host.probeTargets(paths) → {results}` mirrors `listDirectory`'s exact plumbing pattern (schema → `RpcMethodMap` row → dispatcher → `IApiClient` → every test double), stats read-only with 8-way bounded concurrency, caps a single call at 64 paths (enforced by the zod request schema, so an oversized batch fails `bad-request` before the handler ever runs — never silently truncated), and carries no capability gate, unlike `listDirectory`/`pickDirectory`: it makes no filesystem *choice* a deployment would want to withhold, the same way `openPath`'s own pre-check `stat` is already unconditional.

**A5 — no core change; recon confirmed reuse.** `ctx.systemPrompt.section({ name, order, text })` (`packages/core/system-prompt/src/index.ts`) already lets any plugin append an ordered prompt section from its own `apply()`, with no new registration API needed — order 100-199 is the documented "tool guidance" band, exactly B1's use case. The model-visible ⟺ logged proof this architecture requires is *also* already satisfied: `request/header`'s `EpochHeader.system` field logs the full rendered system prompt text verbatim on every `'initial'`/`'resume'`/`'change'` header write (`packages/core/session/src/types.ts`), so a plugin's appended section text is reconstructable from the session log without any new `SessionEventMap` event.

## Alternatives considered

**Letting `scan` alone carry verification (no separate `resolveLink`).** Rejected: `scan` only ever sees a rendered text run — plain prose or inline code — never a link node's own `url`, which the renderer already decoded and normalized before `scan` could see it as a substring. A markdown link's destination needed its own nomination channel.

**A session-level or turn-level `SessionEventMap` event for the appended system-prompt section (A5).** Rejected once the `request/header` recon landed: the section text is already fully reconstructable from the existing `system` field on every header write, so a new event would duplicate data the log already carries, for no gain over grep-the-log verification.

**Gating `probeTargets` behind the `browse` capability, matching `listDirectory`/`pickDirectory` (A4).** Rejected: those two make an active *choice* about what filesystem interaction a deployment allows (browsing arbitrary directories, or invoking a native OS dialog) — a stat-only probe over paths the model/tool output already named makes no comparable choice, and `openPath`'s own pre-check already runs an unconditional `stat` with no gate.

## Consequences

Absent a `proseReferents` provider, or a provider on the old `{ scan, open }` shape, every new surface — `resolveLink`'s branch in `render.tsx`, `subscribe`'s tick in `MarkdownText.tsx` — is inert: no code path they open ever executes, proven by explicit tests (`packages/client/ui-primitives/tests/markdown.client.spec.tsx`'s no-provider and no-`resolveLink` cases) alongside every pre-existing test passing unmodified. `SESSION_FORMAT_VERSION` is untouched (client-rendering seam plus a stat-only RPC — no session log involvement). Every file this change touches — `render.tsx`, `MarkdownText.tsx`, `apply.ts`, `api-proxy.ts`, `host.schema.ts`, `fetch/client.ts`, `fetch/handler.ts`, `workspaces/service.ts`, `fixture.ts` — carries 100% statement/branch/function/line coverage for every new arm, verified against the *full* set of test files that exercise each (not just the file added alongside a given commit): `pnpm exec vitest run` across the touched packages plus `--coverage.include` scoped to each changed source file. The repository-wide `tsc -b tsconfig.host.json` + `tsc -b tsconfig.client.json` face (`pnpm run typecheck`) is clean, including every `IApiClient`/`HostApi`/`IWorkspaces` implementer this repository has (two `fake-api.client.ts` test doubles, `FixtureApiClient`, `TestWorkspaces`, and two host-contract unit-test scripted `ApiProxy`s) — a new required interface member breaks compilation everywhere it isn't yet implemented, by design.

## Retirement

Each of A1-A4 retires independently, on its own upstream-equivalent condition (recorded per-commit in `.claude/core-patches.md`): A1/A2/A3 retire together when upstream's own conversation UI grows an equivalent nominate/verify-layered clickable-reference capability over Assistant prose (same condition the original `proseReferents` seam already carries); A4 retires when upstream provides an equivalent read-only batch path-existence probe reachable from the client. A5 needed no patch and therefore has nothing to retire.
