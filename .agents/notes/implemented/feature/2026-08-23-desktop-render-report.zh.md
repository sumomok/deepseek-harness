# Agent Note: 每一次渲染都答一份报告,而一次越过的期限可以用像素来答

Status: implemented

[English](2026-08-23-desktop-render-report.md) | 中文

## Problem

[超时那一行](2026-08-22-render-timeout-diagnostics.zh.md)告诉模型渲染当时*在等什么*,然后就到此为止。同一个 Redmine 上的另外两次会话显示出它漏掉了什么。一个头像卡在 TCP 建连上的页面每一轮要花 21–22 秒,于是 25 秒的期限被越过;模型拿到一行 504,对一个除头像之外早已排好版的页面拿不到任何像素,也没有一个可以拧的旋钮。协议里没有任何东西让它要求更长的时间,也没有任何东西让它说「渲染这一页,但别去碰那个主机」。它转而花了 36 分钟去写自己的代理。

三个各自独立的缺口,而它们都在请求这一侧:回答没有结构,所以第一句之后的一切都得从英文里解析出来;失败把合成器早已拿到的像素扔掉;而每一个边界都属于壳或插件的部署配置,一个正在推理某一次调用的模型够不着它们。

## Decision

服务为每一次渲染答一份结构化的报告,请求持有自己的期限并说出一次越过的期限该产生什么,请求还可以点名它不想被访问的主机。

**这份报告就是那份 trace,取的是一张快照。**`RenderTrace.report(outcome, deadlineMs)` 返回一个 `RenderReport`——结果、阶段、已用时长对照期限、主文档(URL、状态码、是否重定向、标题)、load 事件有没有触发以及有没有画出过任何东西、请求计数、最旧的那些未结束请求、最先失败的那些、最糟的那些主机、控制台错误数与样本、主框架的加载失败、渲染进程的下场,以及这个回答所带像素的尺寸。窗口那一半把这一切都从主进程事件里喂进去——`did-navigate`、`did-redirect-navigation`、`page-title-updated`、`ready-to-show`、`did-fail-load`、`console-message`、`render-process-gone`、`unresponsive`——再加上 session 上那几个非阻塞的 `webRequest` 钩子。对一扇从不显示的窗口来说,`ready-to-show` 是 Electron 唯一的首次绘制信号,而它之所以会触发,只是因为设了 `paintWhenInitiallyHidden`。`onCompleted` 与 `onErrorOccurred` 现在把状态码与错误带进记录,而不再只是把请求关掉;把一个从未开始过的 id 判为结束仍是无操作,所以 `completed` 永远不可能超过 `total`。

**它走响应头,而不是响应体。**`x-dsh-render-report` 把 JSON 做百分号编码后带上,出现在 200、拒绝一次失败渲染的 500,以及 504 上——与 `x-dsh-render-landed-url` 同一套编码纪律,后者继续保留。最需要这份报告的那两个回答,响应体已经被占了:200 是 PNG 字节,504 是人、日志与冒烟测试都在读的那一行。放进响应体就意味着调用方要为成功再分一次支;放进响应头则意味着所有结果共用一个读取者,而既有的响应体一个字节都没变。一个根本没有开始渲染的拒绝——校验的 400 或 422、401、404、503——不带报告,因为没有什么可报告的。

**预算随请求走,壳只留一个天花板。**`timeoutMs` 按 `[1000, RENDER_LIMITS.maxTimeoutMs]`(120 秒)校验,越界即拒绝而不是夹进来:一个要了三分钟、却被默默给了两分钟的调用方,会按它发出去的那个数装好自己的 abort,并在答案到达之前先放弃。不给这个字段的请求拿到 `RENDER_LIMITS.timeoutMs`,仍是 25 秒,所以这个字段存在之前写的每一个调用方都不受影响。这也终结了[渲染服务那份记录](2026-08-22-desktop-render-service.zh.md)当年只能写成一条规矩的耦合——壳的期限必须小于插件那 30 秒的 fetch 预算,否则壳的回答一个也到不了模型手里。现在预算由插件发过来,而它把自己的 abort 装在 `timeoutMs + 5000` 上,于是这个先后关系由构造保证,而不再靠两个仓库里的两个常量彼此让着。下限与天花板是资源不变量,继续作为常量;真正随部署变化的那个数,是调用方发过来的那个。

**一次越过的期限可以用像素来答,而且只在请求要求时。**`onTimeout: 'capture'` 让期限那一刻对已经画出来的东西做一次 `capturePage()`,并以 200 回答,带着 `outcome: 'timeout'` 与 `capture.partial: true`。[超时诊断那份记录](2026-08-22-render-timeout-diagnostics.zh.md)当初把这件事推迟了,理由正是它改变了 200 的含义;把它做成逐请求可选,正是解决这一点的办法。没要它的调用方仍然可以把 200 读作「这就是那个页面」,而要了它的调用方,是在读取回答的同一次调用里选定了另一种含义——不需要壳的配置,也不需要版本协商。renderer 通过 `offerCapture` 把这次截图借给服务,因为窗口归它所有;服务在期限那一刻取用,上限是 `captureOnTimeoutMs`(3 秒),任何失败都被咽下,退回那个照旧的 504。

**期限那一刻的顺序是:取报告、放队列、截图、abort。**报告在最前面取,理由和 504 那一行原本的理由一样:abort 会销毁窗口,session 随后会把所有在飞行中的请求都报为失败,把这份报告本要点名的那份列表清空。接着放行队列——在截图之前而不是之后——于是一次永不 settle 的 `capturePage` 只扣住它自己那扇窗,正如一个永不 settle 的 renderer 早已如此。abort 放在最后,因为它要拿走截图正在读的那扇窗。代价是至多三秒内有一扇窗与下一次渲染并存,这是有界的,而且放弃竞速本来就允许这件事。

**`blockHosts` 就是报告点名的那个补救办法。**至多 32 条模式,每条要么是精确主机,要么是匹配该后缀的子域(不含后缀本身)的 `*.suffix`,命中的请求在 `onBeforeRequest` 里被取消并计入 `requests.blocked`。命中被渲染页面自己主机的模式是一个点名它的 400,因为一次把自己文档取消掉的渲染只会失败,且说不出任何理由。这是壳唯一注册的阻塞式 `webRequest` 钩子,而且只对真的带了这个字段的请求注册——让诊断钩子保持非阻塞的那条时序论证,对每一个没点名主机的渲染依然成立。`blockedByPattern` 从服务里导出,于是校验器据以拒绝的文法与窗口据以取消的文法是同一个函数。

**上界由构造给出,数的是响应头的字节。**每个列表都有上限(5 条 pending、5 条失败、5 个主机、3 条控制台样本),每个字符串都被截断——URL、主机与标题 96 字节,消息 160 字节,`net::ERR_…` 码 64 字节,资源类型与渲染进程消失原因 32 字节。这些上限数的是字符串在编码后的响应头里要花多少字节,而不是字符数,因为 JSON 转义与百分号编码可以让一个源字节花掉六个字节;对一个 URL 是中文的页面来说,按字符设的上限什么也框不住。所有列表都填满时,这个头是 4.3 KB,在 6 KB 的天花板之下。任何时候都不去截断已经成型的 JSON,那只会造出谁也解析不了的响应头。

**有界从句排在哪里,和那一行遵循同一条规矩。**[会话与输出那份记录](2026-08-22-screenshot-session-and-output.zh.md)把重试提示放在 pending 列表之前,因为它前面的一切都是有界的、而列表会随页面长大,于是尾部的截断落在列表里而不是落在建议上。报告以自己的形状保住了同一条排序纪律:调用方据以行动的定长字段——结果、已用时长对照期限、主文档、各项计数——都是任何页面都撑不大的单值,而唯一会随页面变长的是那四个有上限的列表。插件那段摘要文本也按同一个理由、同一个顺序拼装。

## Wire contract

| 字段 | 方向 | 含义 |
|---|---|---|
| `timeoutMs` | 请求 | 这次渲染从受理起算的期限,1000–120000;不给即 25000 |
| `onTimeout` | 请求 | `fail`(504)或 `capture`(用已经画出来的东西答 200) |
| `blockHosts` | 请求 | 至多 32 条 `host` 或 `*.suffix` 模式,在请求发出之前取消 |
| `x-dsh-render-report` | 响应,200/500/504 | 整份 `RenderReport`,百分号编码的 JSON,至多 6 KB |

`x-dsh-render-landed-url` 与两种失败响应体都没有变化,所以只读这些的调用方完全不受这一切影响。

## Alternatives considered

**把报告放进 JSON 响应体。**结构化数据最显然的形状,而它的代价是让最需要它的那两个回答失去各自既有的响应体:200 将不再是 PNG 字节,或者需要一种 multipart 格式;504 将不再带着冒烟测试与日志在读的那句话。否决:响应头是叠加的,所有既有读取者继续照常工作。

**让部分截图成为默认,或做成壳的一个设置。**两者都考虑过,而且坏在同一处。作为默认,它为所有调用方(包括老的)改变了 200 的含义,而这正是[超时诊断那份记录](2026-08-22-render-timeout-diagnostics.zh.md)当初推迟它的原因。作为壳的设置,它让一个回答的含义取决于调用方看不见的部署,于是插件不得不去协商它。逐请求之下,读取回答的那个调用方,就是选定含义的那个调用方。

**把 `timeoutMs` 夹到天花板而不是拒绝它。**错误更少,而一个被悄悄缩短的期限比一次拒绝更糟:调用方按它发出去的那个数装好了自己的 abort,于是它会在壳作答之前放弃,而它需要的那份诊断,正是它没等到的那个回答。

**让壳的期限继续说了算,插件自己配自己的。**这正是此前发布的做法,而它造出的耦合正是这次改动的起因:两个仓库里的两个常量必须维持一个不等式,而它们没维持住时,插件的 abort 先触发,壳为模型写下的每一个回答都被丢掉了。

**按 URL 模式或正则表达式来阻断。**表达力更强,而它让「拒绝命中主文档自己主机的模式」在一般情形下不可判定;它还会诱使调用方去阻断一个路径,再对页面仍然从别处取到它感到意外。主机才是这个字段存在的单位——报告点名的是主机,而调用方把它粘回来。

**统计对话框,以及提供 `waitUntil` 模式。**两者原本都在范围内,现在都不做。Electron 不给主进程任何关于「已被 `disableDialogs` 压掉的对话框」的信号,所以统计它们就意味着页面世界的代码——而在卡死的渲染进程上执行页面世界的 `executeJavaScript`,正是这个服务绕开的那个已知挂起点,不是再加一次调用的地方。`waitUntil: 'domcontentloaded'` 帮到的是与 `onTimeout: 'capture'` 同一批页面,却又给成功添了第二种含义,而且完全不说还差什么;部分截图满足同一个需求,并且说出了它落下了什么。

**在 abort 之后再取部分截图。**顺序更简单,而且不可能:abort 已经销毁了窗口,没有东西可截了。在截图之前放行队列,正是让这个顺序不给队列添任何代价的办法。

## Consequences

调用方现在可以对一次失败采取行动,而不只是复述它:报告点名那个主机,而 `blockHosts` 就是对它该做的事。一个卡在第三方主机上的页面,现在一次调用就同时给出像素与诊断;而它过去给出的是一句话,外加一小时写代理的工夫。

`Renderer` 类型变了两处:它返回 `Capture`(`{ png, width, height }`)而不是 `Buffer`,于是完整渲染与部分渲染以同一种方式报告自己的尺寸;它还多了一个 `offerCapture` 参数。任何实现这道缝的东西都随之更新——在这个仓库里就是 `renderInHiddenWindow` 与单元测试注入的那些 renderer。

`RenderTrace.requestSettled` 现在是 `requestCompleted(id, statusCode)` 与 `requestFailed(id, error)`,因为报告要分清「答了 503 的请求」与「根本没答的请求」。

一次渲染现在可能在自己的期限之后再多持有窗口最多三秒,用来取那张截图。队列不等它,窗口无论如何都会被销毁,所以这件事的代价至多是那段时间里同时活着两扇窗。

报告会到模型手里,而它点名页面自己请求过的第三方主机、页面的标题,以及它的控制台错误。这正是它的意义所在——它是「这个页面很慢」与「gravatar.com 在这个网络上不作答」之间的差别——同时值得明说的是:工具结果现在带上了被渲染页面所说内容中的这么多东西。

## Testing

`apps/desktop/tests/render-service.spec.ts` 用注入的 renderer 驱动真正的 `RenderTrace` 与真正的协议:200、500 与 504 上的报告;各项计数、有上限的列表、最糟主机的排序与失败列表;控制台的计数与采样;重定向、标题、绘制与渲染进程各字段;没有渲染发生过的拒绝不带报告;请求自己的 `timeoutMs` 会取代部署默认值,而越界的那个会被一条同时点名上下界的消息拒绝;直接测 `blockedByPattern` 的文法;每一种 `blockHosts` 拒绝,包括命中被渲染页面主机的那两种形态;`onTimeout: 'capture'` 以 200 作答并带 `outcome: 'timeout'` 与 `capture.partial`;一次抛错的截图、一次从未被提供的截图,以及一次永不 settle 的截图——最后这个断言的是两个并发请求被回答的先后顺序,这正是证明队列在截图进行期间已经往前走的地方。

有两个用例钉的是这个响应头的上界而不是它的内容:100 条 URL 长 2000 字符的 pending 请求、60 条失败与 50 条控制台错误,以及同样形状但写成中文的一份。两者都断言编码后的响应头至多是 `REPORT_HEADER_BYTES` 且仍能解析,而这正是按字符表达的上界会失败的地方。

`apps/desktop/scripts/render-smoke.mjs` 覆盖任何注入 renderer 都替代不了的部分。一个页面的唯一图片指向一个「接受连接却从不回答」的监听,它在真实 Chromium 上被渲染三次:在 2 秒预算加 `onTimeout: 'capture'` 之下,它答 200,PNG 解出来正好是请求的视口,报告里点着那个卡住的主机;带 `blockHosts: ['127.0.0.1']` 时,它在约 85 毫秒内完成,`requests.blocked` 为 1 且 load 事件已触发;什么都不加时就是那个 504,而它的报告点出的正是它那一行点出的同一张图。一个调用 `console.error` 的页面证明 `console-message` 与标题确实进到了报告里,而视口那个用例现在还断言报告里的 `capture` 尺寸与 `firstPaint`。
