# Agent Note: agent 对内容区知道些什么

Status: implemented

[English](2026-09-02-content-column-perception.md) | 中文

## Problem

内容区由浏览器绘制，在这次改动之前，agent 对里面的东西一无所知。有三件事从来到不了一次模型请求。用户从侧栏导航菜单打开一个页面，改变的是这场对话在谈什么，而 agent 是屋里唯一没注意到的一方。用户把另一个标签调到前面，是一次只活在某一个浏览器标签页组件状态里的决定，刷新即消失，因此无论是 agent 还是第二个控制台都无从知道用户正在看哪一条。而 frame 里的应用一直在自行路由——点一下它的菜单、登录后重定向、把表格换成详情页——这些都不碰这一栏记录下来的页面 id，于是 agent 对这一栏的印象在「屏幕上是哪个应用」这件事上是对的，在里面的一切上都是错的。

[页面读取通道那篇](2026-09-01-content-read-page-channel.zh.md) 交付的读取器把这个缺口放大而不是补上：一个能读用户眼前页面的模型，就是一个会被问到这个页面的模型，而它读的页面，地址它说不出、到达它没听说。它还是在工具调用落地的那一刻就读——对单页应用来说，那多半是页面正画到一半的时候。

## Decision

三件事，三条载体，各自按「这件事多久变一次、谁需要它」来选。

### 用户打开的页面是一条消息，调到前面的标签不是

`show-content-page` 在它的 `content/shown` 落库之后注入一句话——`The user opened the page "<title>" in the content column (内容区); it is in front now.`——作为一条来源为插件、`form: 'notice'` 的 `user/message`。`content-surface` 的 `dismiss-content-entry` 对关掉的标签做同样的事。`select-content-entry` 什么都不注入。

这条线划在哪里，取决于这个动作重复得多勤、以及 agent 会因此做什么不同的事。打开一个页面、关掉一个标签，改变的是对话在谈什么，一个会话里各发生几次；把标签调到前面是一次张望，用户四下看多少次就发生多少次，而听见了每一次的 agent 会读到一份主要由「用户在四下看」构成的对话记录。在前面的是哪一条改由内容区上下文送达模型，在那里它只占本来就会有的那一行上的一个标记。

用 `inject` 而不是 `queue`：打开一个页面不是一个问题。这条通告排给 agent 的下一个 pre-step，不唤醒任何驱动，因此闲着的 agent 在用户开口之前继续闲着。它从入队那一刻起就是持久的——收件箱的这次 splice 本身就是一条会话事件，整条消息都在里面——并在某个驱动认领它时进入模型可见面，成为一条 `user/message`。它之所以是 `user/message`，是因为那就是模型可见面：任何进入模型请求的东西都必须能从日志还原，而注入的上下文消息正是本仓库承载「用户没有键入的事实」的方式。

### 在前面的是哪一条是一次被记录的决定，较晚的事实赢

`content-surface/selected` 记录用户对标签的选择；`contentSurface` 的 fold 把最新的那次与记录一并保留，并发布 `front`。裁决它与流之间关系的规则只有一句：**一次选择输给任何在它之后被记录的 entry。** 用户点了一个标签、agent 过一会儿又展示了一个页面，两者都是真实意图，而这一栏跟着较晚的那个。

browser 半边对它仍然握着的那次点击——按钮与「这次点击的记录经 projection 抵达」之间的那一刻——套用完全相同的规则，这也是两边都按 `seq` 而不是按墙上时间或到达顺序比对的原因。`front` 指名的 entry 若已不在流里，就回落到最新的那条，因此关闭与重绘都不会让这一栏变空。

### 这一栏站在哪里是一段 prompt 上下文，绝不是 section

`content:column`（order 130）按由新到旧列出这一栏装着什么，标出在前面的那一项；frame 已经离开其配置地址的页面，还会给出它此刻所在的地址。它是 `ctx.systemPrompt.context` 而不是 section，理由与 `approval:policy` 相同：这个值随用户干活而变，而 context 在保留历史之后才被具化，因此挪动过的一栏不会改写供应商缓存的那段稳定 system-prompt 前缀。

里面没有任何时间戳。相对时间（「3 分钟前打开的」）在实跑与回放之间会不一样，那会让任何展示页面的场景录制都无法重放；而模型读到的对话本身已经带着事情发生的先后。

整段都是从该会话自己的 projection 折出来的——`contentSurface` 的 entry 与本包的 `contentPages` 状态——因此模型可见的这一半可以从日志还原。`contentPages` 记录每个页面是谁打开的、它的 frame 又去了哪里，且不带 `wire`：没有浏览器读它。

### ref 规则住在上下文里，不在工具描述里

`Refs like e12 are your handles for content_read's scope and after; when you answer the user, name what the page shows, never a ref.` 位于内容区上下文的收尾几行，只在部署配置了读取器时给出。

它管的是答复而不是调用。选中 `content_read` 的模型早已读过它的描述；它随后写给用户的那句话，是就着这次请求带着的东西写的，那时描述已经在很后面了。实测录制里出现过模型把 `e9` 引回给一个根本看不到它的用户——上下文是对话之前的最后一样东西，一条关于答复的规则就该在那里。

### 路由变化靠轮询，绝不打补丁

browser 半边盯住在前面的那个 frame 的 `load`、`hashchange` 与 `popstate`，并每隔 `navigationPollMs` 轮询它的 `location.href`。四路信号产出的一切都先过一个 300ms 的沉降窗口，再与该 frame 上一次报告过的地址比对，最后成为一条 `content/navigated`，带着页面 id、路径、文档标题与 `by: 'user'`。

轮询之所以存在，是因为这三条事件对 `history.pushState` 一个都不触发，而 history 模式下每个当代路由器都用它换路由——导航监视存在的理由，恰恰是那种没有任何事件通告的情况。替代方案见下文；轮询的代价是每个被监视的 frame 每个间隔一次同源属性读取，以及「移动之后就静止」这种情况最多晚一个间隔才被察觉。`navigationPollMs` 是 Config 字段而不是常量，因为这笔取舍是部署方的：一个应用一直在路由的控制台，想要的间隔比「点完几秒后就被问屏幕上是什么」的控制台更长。出厂值是一秒，短于用户说完一句话所需的时间，又远高于一次读取的代价。

这一片记录的每一次导航，`by` 都是 `'user'`，`'agent'` 被预留：这个字段存在，是为了让「手」那一片能记录 agent 自己点出来的一次点击，而不必新增一个事件类型。

### 一次读取会等页面画完

在加载等待与遍历之间，一次读取给 frame 的文档挂上 `MutationObserver`，一旦静止满 `settleQuietMs` 就作答，到 `readTimeoutMs × SETTLE_WAIT_SHARE` 就放弃。回报截止时间的两份份额——`LOAD_WAIT_SHARE` 给还在加载的页面，`SETTLE_WAIT_SHARE` 给还在绘制的页面——相加小于一，这一点由测试钉住，好让遍历与回程拿到剩下的部分。

两种结局都会到模型那里，而不是藏在一次重试里。始终没静下来的页面照读不误，列表表头如实说明，因为这份列表是那一瞬间的真实读取，而要不要再读一次由模型决定。`ReadOutcome` 带上 `settled: boolean`，在回报路由上与其他字段一样接受校验，因此这个事实是跨进程传过来的，而不是在宿主侧重新推断的。另外，页面上凡是可见且标了 `aria-busy="true"` 的，都会用表头里单独一行点名，至多三个，走引擎自己那套命名阶梯——一个说得出「哪块还在加载」的页面，等于把截图会说的话原样告诉了模型。

`role="progressbar"` 不被当作忙碌标记：页面可以把它当正文来画，一屏进度条并不是一个正在加载的页面。任何框架的 loading class 也一概不读，理由就是整个引擎写成那样的理由——[引擎那篇](2026-09-02-content-snapshot-engine.zh.md) 记录了这条规则。

`content/navigated` 不等。地址一变，frame 一沉降就报，等这个地址背后的页面画完是「读它」的事。与引擎自身 ref 失效之间的分工也是同一条界线：导航是关于这一栏的事实，ref 的存活期是关于一份文档的事实，而后者引擎早已拥有——frame `load` 时 ref 表被重置，元素已离开文档的 ref 解析为空，过期的 `scope` 或 `after` 被拒绝并告诉模型重新读一次。这一片什么都没动，`content/navigated` 也刻意不让 ref 失效：一次保住文档的 SPA 路由变化，保住的是那些仍然解析得到的 ref，而解析不到的那些早已被覆盖。

### 两条新事件都不是 `ignorable`

`content-surface/selected` 与 `content/navigated` 都是读取时必需的，和它们之前的 `content/shown`、`content-surface/dismissed` 一样。这不是「一个构建应当因为一次选择就拒绝整份日志」的判断——而是今天的 `Session.append` 根本没有办法设置这个标记，而加上它是对上游 core 的改动，这个 fork 不做。会话词汇表里没有这两个包的运行时会拒绝整份日志，而不是默默展示错的标签。本仓库的任何构建都认识这两个类型。

## Alternatives considered

**给 frame 里的 `history.pushState` 打补丁。** 完全不轮询就能看见路由变化的显而易见的做法：包住 frame 自己的 `history.pushState` 与 `replaceState`。因所有权被否。那份文档属于部署方而不是本包，而在补丁之后安装的路由器——每个框架都会自己包一层 `history`——会把它原样拆掉，留下一个什么都不报、也说不出为什么的监视。轮询读的是 frame 本来就暴露的属性，不需要页面配合任何事。

**让选择留在 UI 本地，维持原状。** 这一栏本来就把选中的标签放在组件状态里，留在那里不需要新增事件类型。因为上下文一旦点名「在前面的是哪一条」，它就违反「模型可见即须记录」这条规则而被否；它本身也是一个看得见的产品缺陷：刷新会把用户扔回最新那一条，而不是他正在读的那一条。

**用一条 system-prompt section 说明在前面的是哪一条。** section 注册起来更简单，读起来也一样。因 section 属于被缓存的前缀而被否：这一栏一个会话里要变好几次，每变一次都会让每个请求从那条 section 往后的前缀全部失效。context 之所以在保留历史之后才具化，正是为了让一个会变的值对它上游不产生任何代价。

**每次导航注入一条通告。** 与「打开页面」的通告对称，而且会把地址带进对话，让模型按顺序读到它。因量被否：应用在用户脚下一直在路由，一次路由变化一条消息会成为整份对话记录里最吵的东西，换来的新信息却最少。上下文只花一行就承载了 frame 在哪里，并且每个请求都免费刷新。

**把 ref 规则放进 `content_read` 的描述。** 它是一条关于 ref 的规则，而 ref 是这个工具的。因为工具描述是在模型选中工具时读的，而这条规则作用于它随后写下的那句话，那时描述已经在几千 token 之外而被否。两个位置都可用，只有一个紧挨着它所管辖的那段文本。

**报告「没静下来的页面」不如直接重试。** 落在绘制中间的一次读取可以丢掉重跑。因截止时间属于宿主而被否：在座位里重试，花掉的是模型的回报截止时间，而这个决定模型做得更好——它看得到列表，也看得到那句「这份可能不新」。

**等 `document.readyState` 或用「网络安静」的启发式，而不是等变更。** 两者都更便宜。因为它们描述的都不是要等的那件事而被否：单页应用什么都还没画的时候 `readyState` 早就 complete 了，而网络安静对一个用手上已有数据渲染的页面什么也说明不了。读取需要的是 DOM 停止移动，而这正是 `MutationObserver` 报告的东西。

## Consequences

拥有活的内容区的会话，此后每个请求都带着这段内容区上下文——每条 entry 一行，最多列十条，每个字段裁到 120 字符，再加两到三行收尾。这是 agent 知道屏幕上有什么的常驻成本，即使模型在这些请求里根本没问起这一栏，也照付。

用户打开一个页面要花掉对话里一句永久的话，关掉一个标签同样如此。把标签调到前面花掉一条会话事件，在对话记录里不花任何东西。

会话词汇表新增两条读取时必需的事件类型，`contentSurface` 的 fold 语义版本升到 3——两个理由都占：fold 多了一种情况，它存下的状态也从一串裸记录变成了 `{ records, selected }`，因此按旧形状写下的 checkpoint 会被丢弃而不是被重放。

每个被监视的 frame 每 `navigationPollMs` 花一次属性读取，而且只监视在前面的那个：被缓存、已隐藏的 frame 自行路由，要等它回到前面才被察觉。离开了 dsh 源的 frame 对每一次读取都以 `SecurityError` 作答，此时监视什么也不报，而不是让一次用户从没要过的读取失败。

对从不静止的页面的读取，此后每一份都带着那行说明。这是诚实的答案而不是缺陷：预算限的是等待，不是页面。

## Testing

单测钉住 fold 的 `front` 规则与两条命令的拒绝、两条新事件的载荷校验、每一段模型可见文本的逐字内容（`perception/text.ts`、`access/text.ts`）、jsdom 下用假定时器跑的沉降等待与忙碌命名、以及针对桩 frame 的导航监视——包括什么都不触发的 `pushState`、什么都不报的重复地址、以及什么都不说的跨域 frame——还有跑在真实 Loader 组合上的内容区上下文，那里命令真的执行、`assemble()` 真的带着这一段。

`apps/web/tests/content-perception.e2e.ts` 用真实浏览器、零模型调用把三件事全部走一遍：侧栏点页面与它注入的通告、切换条点击与挺过刷新的选择、活的 frame 里的一次 `history.pushState` 与它产出的 `content/navigated`，以及点名两个页面和 frame 自行路由到的地址的那段已装配上下文。`apps/web/tests/content-read.e2e.ts` 断言一个静止的固定页面两行表头都不带。

## Deferred

「断言模型最终答复里没有 `e<n>` ref」的 keyless snapshot 没有在这里加上：入库的 `content-read` fixture 录制于 ref 规则存在之前，它的答复引用了好几个 ref，因此这条断言只有对着重录的 fixture 才是诚实的。重录需要这一片并不持有的 API key。
