# Agent Note: The web profile's plugins stay synced to the desktop, and a defective one stays visible

Status: implemented

English | [中文](2026-08-25-desktop-web-profile-migration.zh.md)

## Problem

The desktop shell up to 0.1.0-rc.16 booted `bin.js web`, which is `--profile web` — the profile every CLI launch on that home composes. [rc.17 gave it a profile of its own](2026-08-21-desktop-builtin-plugins.md) and `apps/desktop/src/profile-seed.ts` creates it, for reasons that still hold: nothing but the desktop launches `desktop`, so no reference into the installed application is left in a profile a bare `dsh web` has to load.

Nothing carried the user's own plugins across that switch. A profile is user data, `initProfile` writes it once and never revisits an existing file, and the seed adds the built-ins this build ships and nothing else. Someone who had run `dsh plugin --profile web add <package>` — the only way a plugin reached a desktop install before rc.17, and still the way anything outside the seven built-ins reaches one — had those plugins composed on rc.16 and not composed on rc.17. The field case is an upgrade from rc.14 straight to rc.22: the desktop profile was created fresh with the seven built-ins, and the customer's own plugins stayed in `~/.dsh/profiles/web/`, still installed, still listed there, mounted by nothing the desktop runs.

Two constraints shape any answer. `loadProfile` resolves every `dsh.profile.bundles` entry and throws on one it cannot resolve, so a name added to that list and later unresolvable does not degrade the app — it ends the boot. And the machines this is for have no package manager: the premise of the desktop client is a person who does not have a terminal, so nothing in the shell may run an install.

**The admission check above was falsified in the field within hours of shipping.** `bundleDefect` at the time only checked whether a package existed and whether it declared `dsh.bundle`; it never checked whether the package's own entry file was actually on disk. A real customer had `@yuxianglin/dsh-bridge-browser` installed in their `web` profile — `package.json` present, `dsh.bundle` declared, `main: lib/index.js` — but the package was an unbuilt git install: only `src/*.ts` committed, no `lib/` at all, and no `prepare` script to build it on install. The check that was supposed to keep a boot-ending package out of `dsh.profile.bundles` passed it straight through, and `loadProfile` threw importing it on every subsequent boot: `Cannot find module '…\lib\index.js'`. The anti-brick pass this note originally shipped re-admitted the same broken package every launch, because nothing about it looked different from a healthy one — a permanent brick loop on a customer's machine, from a check written to prevent exactly that outcome.

The owner's response reframed the whole feature rather than patching the one check. A broken package must never abort startup, full stop — no admission check can be trusted to be complete, so the boot itself has to survive one it did not catch. And a plugin that cannot mount should stay **visible**, not silently vanish: disabled and repairable, not dropped where its owner would have no way to know it existed at all. That reframing is what turned a one-time migration with a pass/fail admission gate into the continuous, three-state system this note now describes.

## Decision

The shell keeps the `web` profile's user plugins in step with the desktop profile continuously, on every launch, and a plugin that cannot mount stays visible and repairable rather than being dropped.

**Sync, not a one-time migration.** `web-migration.json` in the desktop profile holds `{ from, migrated, defective, removed }`, and every launch reads it, revalidates every name it already tracks, and admits every name in the web profile's own `dsh.profile.bundles` it does not yet track. There is no absence-of-the-marker gate any more: gating a one-time run on the profile's creation reached only fresh installs, and gating it on the marker's absence reached those plus every machine already on rc.17 through rc.22 — but neither reaches a plugin the user installs into `web` **after** their first sync, which used to sit unmounted until nothing checked for it again. Continuous sync reaches all three. Only the very first sync a profile ever runs — the one that finds no marker at all — copies `cordis.patch.yml` and `pnpm-workspace.yaml` wholesale, exactly as the one-time migration used to; every later sync leaves both files untouched, which is what keeps this idempotent rather than clobbering an edit on every boot.

**What comes across.** Every name in the web profile's `dsh.profile.bundles` that is not one of the two in-box bundles the desktop template already lists, not in `BUILTIN_WEB_BUNDLES`, not in `WITHDRAWN_WEB_BUNDLES`, and not already in `migrated`, `defective`, or `removed`. A built-in, a withdrawn name, and a refusal are logged with the name and the reason, because this feature exists at all because a customer's `dsh-server.log` had to be read to work out where their plugins went. The two in-box bundles are the exception: they are in every web profile ever created, so a line about them would be on the first launch of every install and would say nothing about the profile being read.

**A link, never a copy and never an install** — for every name this sync tracks, defective ones included. `~/.dsh/profiles/desktop/node_modules/<name>` becomes a link to `~/.dsh/profiles/web/node_modules/<name>` — the web profile's path, not what that path currently resolves to. pnpm may hold the package anywhere and put a link of its own there; pointing past it would pin the desktop to today's copy, where the path keeps answering with whatever `dsh plugin --profile web add <package>@latest` installs next. The web profile stays the one place the package lives and the one place it is updated. `ensureLink` already makes the link, which is a junction on Windows and needs an absolute target, and already creates a scoped name's parent directory.

**A record that is gone is rebuilt rather than replayed.** A name already listed in `dsh.profile.bundles` whose link is the one this shell would have made is recovered into `migrated` (or `defective`, if `bundleDefect` now finds it so) without touching the manifest a second time — silently, with no `migrated <name> from the web profile` log line, because nothing new happened to log. Without that, a marker deleted by hand — or the vanishingly unlikely write that fails right after the manifest write succeeded — would leave entries pointing into the web profile that nothing re-checks. A name already listed whose link is not this shell's own is left alone with `<name>: already in the desktop profile`, because it is not this feature's to touch.

Only a **healthy** name gets the manifest write: appended to `dsh.profile.bundles`, with the version specifier the web manifest declared for it copied into `dependencies`, so a later `dsh plugin --profile desktop install` reconciles against the same version rather than dropping the name. This is the one thing in the seed that writes a dependency entry, and the module doc's promise that no dependency or other manifest field is ever touched now carries that carve-out explicitly.

**A defective name is disabled, not dropped and not silently refused.** `bundleDefect` is the one predicate every admission, every per-boot revalidation, and the plugin-admin service's own repair routes read, and it answers one of three kinds now, not two: `missing` (nothing installed — never recorded as defective, since there is nothing to show), `not-a-bundle` (the installed version declares no `dsh.bundle`), and `entry-missing` — the kind the field brick above added — the manifest's `exports` or `main` names an entry file that is not on disk, the shape an unbuilt git install leaves a package in. A name `bundleDefect` finds defective keeps its link (inspectable, repairable) but never reaches `dsh.profile.bundles`; its entry moves into the marker's `defective` list with the kind, a one-sentence `detail`, and `at` — first-detection time, held steady across boots that find the same defect again. The log line is `disabled migrated <name>: <reason>`, once per name per transition, not on every boot that finds it still defective. A defective entry is never auto-revalidated at boot: only the plugin-admin service's `/recheck` and `/repair` routes promote one back, by deliberate user action.

**Deleting the desktop-side link is a removal, not a loss.** A name whose `migrated` entry stops resolving through any of the three places `resolveBundleDir` looks, while the web profile's own copy is still there and healthy, moves into the marker's `removed` list instead of being dropped — `removed <name>: no longer linked in the desktop profile; still installed in the web profile, so it will not return on its own`. This is a tombstone: `removed` names are never re-admitted by the continuous sync above, only by the plugin-admin service's `/enable` route. A name whose web copy is gone too — both sides vanished — is the one case with nothing left to track, and is dropped from the marker outright, still logged as `dropped migrated <name>: no longer resolves in the web profile`.

**The patch layer is copied verbatim or not at all, and only on the very first sync.** If the desktop's `cordis.patch.yml` is still byte for byte the empty template the seed writes and the web profile's is not, the web file replaces it — bytes, so comments and `!!js` tags survive. An edited desktop copy is left alone and the log names the plugins whose rows to carry over by hand. `pnpm-workspace.yaml` follows the same rule. Nothing is merged: a patch layer is YAML the loader's own schema reads, and combining two of them means implementing that schema a second time, in an Electron main process that deliberately depends on no harness package.

**Every launch re-checks every name still in `migrated`, against the same three-way answer `bundleDefect` gives a fresh admission.** A healthy one is left alone. A defective one is disabled as above. One that resolves nowhere is checked against the web copy specifically to choose between `removed` (tombstone) and dropped outright, per the two paragraphs above. This is the withdrawn-built-in prune applied to the other class of entry the shell puts in a profile it does not own. A name the user has since taken over — a copy under the desktop profile's own `node_modules`, a link of their own at that path, or a package this build started shipping — still mounts, so it is left exactly as it is.

**A boot that still fails is quarantined and retried once, from `server.ts`/`main.ts`.** Admission and per-boot revalidation both read `bundleDefect`, but neither one can see every way the server's own loader can refuse an `import` — the field case's `entry-missing` kind is the fix for the one that was reachable *before* the boot; a name can still slip through and fail *at* the boot, in ways this repository does not model (a corrupt module, a native addon mismatch, anything short of "the file is missing"). So `startServerWithQuarantine` catches `ServerExitedBeforeUrl` — which now carries the boot's whole collected output, not just the message's own 15-line tail — and `quarantineLoadFailureFromOutput` scans it for the loader's own exact `failed to import loader entry <id> (<module>)` line; when `<module>` is a name in `migrated`, it moves to `defective` with kind `load-failed` and the loader's own message as `detail`, drops it from `dsh.profile.bundles`, and the server is started again, once, with that name no longer in the list. A module the output does not name, or a second failure, reaches the ordinary boot-failure page — the parse is deliberately exact, not a heuristic, so a message shaped differently is left for a person to read in the log rather than guessed at.

**Four loopback routes let Settings act on a defective or removed name**, each reading and writing the marker fresh from disk, never a cached copy: `/recheck` re-runs `bundleDefect` against the linked package and promotes a healthy one to `migrated`, or persists the freshest reason when it is still defective; `/repair` confirms with a native dialog, reinstalls at the web profile's own declared specifier (never a caller-supplied one), and — only if the package still names a missing entry file — runs the package's own `build` script in its real directory, found by `realpathSync` through the link, then deletes the `node_modules` and lockfile that build produced before re-checking; `/forget` deletes a defective or removed name's record and its link outright; `/enable` re-admits a `removed` name, landing it in `migrated` when its web copy is still healthy or back in `defective` when it is not. None of the four is auto-triggered — a name that a person has not acted on through one of these stays exactly where the last sync or the last route call left it.

**Peer versions are not this feature's problem.** A plugin installed under an older harness may not suit this one. Its unmet peers fall through to `$DSH_HOME/profiles/node_modules`, which the running installation heals, so it shares this build's cordis instead of resolving a second one — but whether its code matches this build's API is not a question a link can answer, and the runtime peer fallback does not validate it. Adding a check here would be guessing at a compatibility relation nothing in the repository models.

## Alternatives considered

**Tell the user instead of migrating.** A line in the log, or a notice in the window, naming the plugins that are in `web` and not in `desktop` and the command that would move them. Rejected on the audience: the desktop client's premise is a person without a terminal, and `dsh plugin --profile desktop add` is a terminal command against a registry on a machine that has no pnpm. A notice that cannot be acted on is the same outcome as silence, with more words.

**Copy the package directories instead of linking.** No dependence on a directory the user can delete, so no repair pass and no dangling entries. Rejected because it forks the package: the copy stops receiving `dsh plugin --profile web` updates and nothing in the shell would ever update it, so a plugin migrated once would be frozen at whatever version was installed on migration day, in a directory no tool the user has knows about. The repair pass costs one resolution per recorded name per launch and keeps one copy.

**Run `pnpm install` in the desktop profile from the web manifest's dependencies.** The outcome the profile system already models — real dependencies, resolved peers, `dsh plugin` reconciles them normally. Rejected outright: the shell may not run package installs. There is no pnpm on the machine, the profile's own `pnpm-workspace.yaml` disables `autoInstallPeers` for reasons the flat fallback depends on, and an install during a launch would put a network operation between the user and their window.

**Seed the desktop profile from the web profile at creation time only.** Much less code — one branch in `initDesktopProfile`, no record file, no repair. Rejected because it solves the case that is not the problem. The customer whose report started this had a desktop profile already; creation had happened three versions ago.

**Merge the two patch layers.** The complete answer to configuration rather than a first-file-wins rule: the user's desktop rows and their web rows both applying. Rejected because the merge is not textual — the layers are id-targeted patch entries where an id in both files means one row, not two — and doing it properly means parsing YAML with the loader's schema and re-emitting it with `!!js` tags and comments intact. That is `@deepseek-ai/dsh-app-boot`'s job, and this module deliberately reproduces the three templates rather than depend on it, because an Electron app that depends on a harness package packs the product closure into `app.asar` a second time. The refusal names the plugins to carry over, which is the honest version of what a merge would have to be reviewed for anyway.

**Keep the record outside the profile, in the app's userData.** It is the shell's own bookkeeping, not user data, and it would survive a user deleting the profile. Rejected because surviving that deletion is wrong: a deleted profile is a user asking for the seeded state again, and the record is only meaningful about entries in the profile it sits in. Two files that can disagree about one profile's contents is a bug waiting for the machine that has both.

**Patch the one predicate and keep dropping a defective name silently.** The minimal fix for the field brick: add the `entry-missing` check to `bundleDefect`, keep every other behavior — refuse at admission, drop at revalidation, no trace left for the user to find. Rejected because the same postmortem that found the gap also found the failure mode it was hiding: a customer had no way to know their plugin was ever there, and the only way anyone found out was reading a raw server log line by line. A predicate this repository does not yet know everything about (three kinds today; a fourth field case will find a fourth) must not decide alone whether a plugin disappears without a trace — the boot staying up is necessary but not sufficient, and visible-and-repairable is what makes the difference legible to the person it happened to.

**Auto-revalidate a `defective` entry on every boot, the way a `migrated` one already is.** Symmetric with the rest of the sync, and self-healing if the user fixes the package by hand outside the shell. Rejected: a name a person has not acted on should not silently start mounting again mid-session between two launches with no `/recheck` call — the plugin-admin routes exist so a person decides when a repaired-looking package is trusted enough to compose, not so the next boot decides for them. `/recheck` costs one `bundleDefect` call on demand; a boot-time sweep would cost one per defective name on every launch for a state the marker already answers.

## Consequences

A customer upgrading from any build before this one gets their plugins back on the first launch, with no action and no terminal. What they get is the composition they had on rc.16: the same packages, at the same installed versions, from the same directory — and a plugin they install into `web` afterward keeps arriving in `desktop` on the next launch, not only on the first one.

The desktop profile now holds entries whose package lives outside it, and the shell owns keeping them valid. That is a per-launch cost of one `resolvedBundleDir` walk per tracked name in `migrated`, plus one `bundleDefect` call per new arrival — a defective or removed name is not re-walked once it is tracked, so the cost does not grow with how long a broken plugin has sat there.

`dsh plugin --profile web add <package>@latest` updates a migrated plugin for both profiles, and the two ways that update can go wrong now land in different places: `dsh plugin --profile web remove <package>` — the web copy gone too — drops the desktop entry outright, while a version that is no longer a bundle disables it as `defective`, linked and visible, rather than dropping it. Deleting only the desktop-side link tombstones the name into `removed` rather than either. None of the three returns on its own; `/recheck`, `/repair`, and `/enable` are how a person brings one back.

A field case manifest-level admission cannot catch — the server's own loader throwing on `import` for a reason short of "the file is missing" — is caught one boot late, from that boot's own output, and costs exactly one retry rather than a second permanent brick.

A plugin that installed cleanly under an older harness and misbehaves under this one is not caught here, and a user who hits it disables its row in `cordis.patch.yml` or updates it in the `web` profile.

## Testing

`apps/desktop/tests/profile-seed.spec.ts` drives the whole feature against a staged `$DSH_HOME` with no Electron: the fresh-install sync, the rc.17-to-rc.22 field case with a desktop profile an earlier build created and no record, the second launch that changes nothing, each refusal with its logged reason, a link made at the web profile's path rather than at what that path resolves to, the dependency specifier copied and the one the desktop declared for itself left alone, the patch layer and the pnpm settings copied on the first sync only and refused once edited, a scoped name through the link and both manifest fields, the record rebuilt from its own links after being deleted by hand, a plugin admitted after an earlier sync already migrated a different one, and an old two-field marker read as if `defective` and `removed` were empty. A dedicated `bundleDefect` block drives every `exports`/`main` shape the entry-file check reads, including the verbatim field case (`main: 'lib/index.js'`, no file on disk). The revalidation block covers the package removed from the web profile, the web profile deleted wholesale, the package updated in place to one declaring no `dsh.bundle` (now disabled rather than dropped), a bundle version restored afterwards and deliberately not re-enabled, the desktop-side link removed while the web copy stays healthy (tombstoned into `removed`, never re-synced), the second launch after either outcome, and the three ways a name still mounts — the profile's own copy, a link the user re-pointed, and a package this build started shipping.

`apps/desktop/tests/server.spec.ts` drives `startServer` and `startServerWithQuarantine` against a real short-lived scripted child process (no `dsh` server, no Electron): `ServerExitedBeforeUrl` carrying the boot's whole output beyond the message's own 15-line tail, one retry when an injected `quarantine` finds a name to blame, no retry when it finds nothing, no retry for a failure that is not an exit-before-URL at all, and the retry's own failure propagating when it fails again. `apps/desktop/tests/plugin-admin-repair.spec.ts` covers `/recheck`, `/repair`, `/forget`, and `/enable`: each route's 422 outside its own marker list, `/recheck` promoting a repaired-by-hand package and persisting an updated reason when it is still broken, `/repair`'s confirmation dialog text, its reinstall-at-the-declared-specifier for both a semver range and a git spec, its build-script ladder running in the package's real directory through a `realpathSync`'d link and cleaning up the `node_modules` and lockfile that produces, and its two named failure reasons (no build script, no declared version to reinstall), `/forget` deleting a defective and a removed record's link, and `/enable` re-linking a removed name into either `migrated` or `defective` depending on whether its web copy is still healthy.

Two of those cases assert the property the whole feature is bounded by rather than the report: every name the desktop manifest lists resolves through `resolveBundleDir` from `@deepseek-ai/dsh-app-boot`, which is the call `loadProfile` makes for each of them and the one that ends the boot when it throws.
