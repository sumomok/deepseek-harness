# Agent Note: 页面上的一张图，作为模型直接看的像素

Status: implemented

[English](2026-09-04-content-read-image.md) | 中文

## Problem

五件内容读取答的都是关于页面的文字，而控制台画出来的东西，没有任何关于它的文字描述得了。一个配对二维码是一个既无 alt、又无 title、也无名字的 `img`：清单为它什么都不打印，`content_read_dom` 打印 `img#pairing {class: code}`，`content_read_attrs` 打印 `src="/pairing?ts=1788…"`，`content_read_dom_content` 打印一个空答案。这些都是对「页面写成什么样」的正确读法，而没有一个说出页面显示的是什么。验证码、画进 `canvas` 的图表、以 `svg` 路径而非字符画成的图标，同理。

[sign-in Note](2026-09-04-sign-in-pages-are-read.zh.md) 记下了这条路的尽头。用户要人帮忙处理一个控制台的登录页——画着二维码和验证码的那种——他要的正是 agent 对页面所显示内容的解读。当各件读取只答得出页面的写法时，模型伸手去调 `bash screencapture` 截了整个显示器，再用 `read_image` 读回那张 PNG：那一刻屏幕上的一切都以像素抵达，经由一件对其中任何东西都没有规则的工具，分辨率是显示器碰巧多少就多少。删掉页面级拒绝，去掉的是模型离开这条通道的理由；它并没有让这条通道具备回答模型那个问题的能力。

## Decision

再加一件读取 `content_read_image`，一个必填参数：前一次对本页的读取印出的一个 `ref`。它答出那个元素自己渲染出来的像素——在浏览器座位里导出、由宿主存下、作为一个 image 块挂到工具结果上让模型直接看——旁边配一行关于「导出的是什么」的事实。

四种标签自己带像素，这一读取的就是它们的全部。`img` 与 `canvas` 导出自己存着的那份栅格；`picture` 导出它实际渲染的那个 `img`，标签仍记外层那个；`svg` 没有存着的栅格，按它的布局盒栅格化。其余标签在画任何东西之前，就按标签被拒。

这不是截屏。它取的是一个元素，从不是一块区域、一棵子树、一整栏或一个显示器，所以它能答出来的东西，被页面自己画进那一个盒子里的东西框住——而 `ref` 只能由本次会话自己那一栏里对页面的一次读取铸出。

读取不需要审批，而这件是读取。它能携带的，就是一个元素画出来的东西：对一个 `img` 的截图不可能装着某个密码框里的值，因为那个值不是那个 `img` 的任何一个像素。[sign-in Note](2026-09-04-sign-in-pages-are-read.zh.md) 立的那条扣留规则——密码控件的值永远不到达模型——不受影响，这里也不需要为它新增一条分支。

### The gate

#### 工具本身与它的两道闸

- **新增面。** 一件工具、一个必填参数、一种 wire 请求 kind、一个 `ReadOutcome` 分支（`status: 'image'`）、一份输出 schema、一段描述。不新增 `ReadKind`：这个分支是一次读取的第三种结局，不是第四种读法。
- **边界。** 工具对像素不做任何决定。它核 `ref` 的写法、核本次会话的路由、在五件文字读取已经在等的那条通道上等，再把落定的那个分支变成两个面向模型的块。
- **契约。** 两道闸都在等待窗口打开之前跑，且按这个顺序，因为存下来的图是永久的：注定不成的调用必须在座位导出任何东西之前失败。`isConcurrencySafe` 为真——这一读不往页面写任何东西，而存像素是内容寻址的。
- **诱惑。** 拿这张图去替代一次读取。`ref` 只能来自已经跑过的一次读取，所以页面必须先被读过，这件工具才点得到它上面的任何东西；描述写的是那个元素必须是什么，而不是什么时候该优先用它。
- **红线。** 路上不从这张图里读出任何东西。工具不解码、不配文、不 OCR、不分类：它显示的是什么，由模型自己说；那行标题只写尺寸、格式和字节数。

#### 座位里的导出

- **新增面。** 两个模块：[`capture.ts`](../../../../packages/experimental/content-frame/src/client/access/capture.ts) 持有一次导出所做的全部决定，[`export-pixels.ts`](../../../../packages/experimental/content-frame/src/client/access/export-pixels.ts) 持有做出一次导出的那四个浏览器调用。
- **边界。** 这条切分线画在「没有 canvas 的 DOM 实现跑不了什么」上。那些决定——哪种标签、可见否、加载完否、非零否、按什么尺寸、什么媒体类型、多少字节——是纯的、被测的；绘制原语注入进座位，是测试唯一够不到的那一件。
- **契约。** 各项检查按固定顺序跑，第一个不过的就是那句拒绝：不是图、不可见、没加载完、零像素、被污染、格式不在集合内、字节太多。可见性用的是每次读取本来就在用的那个 `isSkipped`，所以一次读取会略过的元素，这里也不会导出。
- **诱惑。** 为了让绘制可测，引入一个 DOM 转 canvas 的库，或者一个原生 `canvas` 包。两者都为一个全部内容只是 `createElement`、`getContext`、`drawImage`、`toBlob` 的函数，往本包里塞进一个依赖，其中一个还是整套构建工具链。
- **红线。** 跨源像素永不导出。被污染的画布在浏览器里抛错，这个抛错被转成一句写明理由的拒绝；没有任何东西去试 `crossorigin`、试代理抓取，或者在服务端把 `src` 再抓一次。

#### 图片路由

- **新增面。** 一条路由 `POST /content-frame/image`，带一道自己的字节上限。
- **边界。** 它把 base64 装进 JSON，走认领与回报两条路由同一道 same-site、`application/json` 的围栏。`/content-frame/report` 原样不动。
- **契约。** 它的上限按一次导出可携带的东西算出（`IMAGE_REPORT_BYTES` = `MAX_EXPORT_BYTES` 的 base64 加上信封），而不是按部署的 `outlineChars`。读图的失败也走这条路由，因此同一个 call id 永远不会被两条路由抢。
- **诱惑。** 让字节走回报路由——它已经存在，也已经会解析一个 outcome。那等于为一份文字读取根本不产出的载荷，把每一次文字读取的字节上限一起抬高。
- **红线。** 路由解析它收到的东西：载荷先按 base64 字母表、长度和上限核过，媒体类型先按一个封闭集合核过，然后才谈解码或存储。

#### 宿主半边：先存，后落定

- **新增面。** [`image-report.ts`](../../../../packages/experimental/content-frame/src/access/image-report.ts)，以及本包 inject 清单里的 `attachments` 服务。
- **边界。** 它是唯一把投递来的字节变成一个持久引用的地方。座位投字节、从不投引用，因为它没有仓库；落定的调用带引用、从不带字节，因为工具结果要写进一份比这次请求活得更久的日志。
- **契约。** 像素在 `pending.report` 被调用之前就已提交，于是会话日志记下的那个引用，指向的是一个已经在磁盘上的对象。仓库拒收时，调用带着仓库自己给的理由落定，而不是抛错——抛错会让这次调用为一个这边早已知道的失败，白等满整条截止时间。
- **诱惑。** 先落定、再后台存，读起来更快，却把一个指向虚无的引用放进了一份持久日志。
- **红线。** 没有仓库，就没有这件工具。注册写在 `ctx.inject(['tools', 'attachments'], …)` 里，所以没有附件仓库的部署拿到的是五件文字工具，这一件不存在，它那条路由也不挂载。

#### 导出常量

- **新增面。** [`wire.ts`](../../../../packages/experimental/content-frame/src/access/wire.ts) 里四个协议常量，零个 `Config` 字段。
- **边界。** 每一个都锚在本包之外的东西上：PNG，因为它无损，也因为它正是 canvas 对任何不支持的类型所退回的格式；`IMAGE_PIXEL_BUDGET` = 640,000，即附件层自己的 `DEFAULT_REQUEST_IMAGE_PIXEL_BUDGET`；`SVG_RASTER_MIN_PIXELS` = 384 × 384，即供应商在 [`image-tokens.ts`](../../../../packages/llm/llm-deepseek/src/image-tokens.ts) 里的 `MIN_PIXELS` 下限；`MAX_EXPORT_BYTES` = 2 MiB，是供应商单图请求预算的两倍，正是无损所需要的余量。
- **契约。** 位图从不放大，矢量一定放大：放大位图，是在一道反正会把它放大的下限之前，只多出字节、不多出细节；而按 24 像素的布局盒栅格化矢量，扔掉的恰恰是那道下限马上要问的细节。两者随后都被附件层投射请求图片所用的同一套几何压进像素预算。
- **诱惑。** 把其中任何一个做成 `Config` 字段。它们都不随部署变化：它们是供应商的计价和附件层的投射，改了其中一个的部署，付的是任何请求都不携带的像素。
- **红线。** 超限的导出带着它的大小被拒，绝不压低质量重编码。一次有损重试，等于用一张已经解不出来的图，去回答一个关于二维码的问题。

## Alternatives considered

**给内容栏截屏。** 最顺手的形状，也正是模型拿 `screencapture` 干过的事。它需要 `getDisplayMedia`（每次会话一次用户手势加一次操作系统级授权弹窗），或者宿主上的一个无头浏览器（把一个状态活在用户浏览器里的页面再渲染一遍）。两者答出来的都是这一帧里的所有东西——包括页面画的其余一切——而问题问的是一个元素；两者也都产不出一张模型能凭 `ref` 指回去的图。

**把任意子树栅格化。** 用一个 `scope` 参数取代一个元素，于是任意区域都能导出。浏览器没有这样的原语：把标记栅格化，意味着把一棵子树连同它的计算样式序列化进一个 SVG foreignObject，或者引入一个 DOM 转 canvas 的库。两者都把页面按第二种方式再渲染一遍，都会以谁也审不了的方式与用户看到的东西不一致，也都把一张图的正确性塞进本包。一个自己就有像素的元素，是答得准的。

**引入 `canvas` npm 包，让导出跑在 Node 里。** 这能让绘制原语可测，也能让一条宿主侧路径成立。它同时把一整套原生构建工具链，塞进一个全部导出只是四个浏览器调用的包；而且它照样拿不到页面：像素在用户的浏览器里，不在宿主上。

**新增一个 `ReadKind`。** 三件原文读取是同一份快照的三个 `ReadKind`，所以第四个看上去很对称。但 `ReadKind` 命名的是「把页面渲染成文字进 `ReadSnapshot`」的一种方式，而这个答案不是文字，也没有快照。`ReadOutcome` 的第三个分支说的才是它本身：一次以图而非清单收尾的读取。它同时把 [`isActOutcome`](../../../../packages/experimental/content-frame/src/access/wire.ts) 逼回了肯定式写法——它原本写成「不是读取」，那会把任何新增的读取分支悄悄归成动手结局。

**不设模态闸，图照挂，让请求自己丢。** 更简单，也错得没法回头：路由丢掉那个块时像素已经在磁盘上，仓库会长期保留，而模型手里只剩一行描述着一张它从没见过的图的标题。一句点名模型的拒绝，花掉的是一次调用，存下的是零。

**在这里把位图放大到供应商的下限。** 供应商在计价前本来就会把小图放大，所以 240 × 240 的图标两种做法都按 384 × 384 计价。在这里做，只会给投递、给磁盘、给请求各多出一些字节，换不来模型本来就没有的细节。

**在会话卡片里渲染这张图。** 上游的 `tool.call.images` 子槽是 `kind: 'single'`，且已经有一个声明者（[`read-image-row.tsx`](../../../../packages/client/ui-tool/src/client/tool/toolviews/read-image-row.tsx)）；第二份声明会在 [`ui-slots`](../../../../packages/client/ui-slots/src/index.ts) 加载时抛错。在这里注册 toolview，要么把这个槽从内置的读图那里抢走，要么直接让控制台起不来，所以本包一个都不注册，落定后的卡片退回通用卡片。

## Consequences

模型能回答页面画了什么，走的是同一条通道、用的是与其他读取同一批 `ref`；而 [sign-in Note](2026-09-04-sign-in-pages-are-read.zh.md) 记下的那条 `screencapture` 路径，现在有了一个有界的替代：一个元素而不是一整个显示器，按元素自己的尺寸而不是屏幕的尺寸。

卡片显示的是那行标题，不是那张图，理由见上面那个槽。读记录的用户看得到导出的是哪个元素、多大、什么格式、多少字节——想看 agent 看到的是什么，得自己打开页面。

每一张导出的图都是永久的。附件仓库对交给它的东西一律保留、从不回收，因此每一次读取都在 `$DSH_HOME/attachments/` 里留下一张 PNG，活到那个 home 的尽头，并随会话日志的任何一次导出一起走。读过一次的登录二维码，就是永久留着的登录二维码。

图作为一条合成的 `user` 消息，紧跟在产出它的那条工具结果之后进入请求，因此从第一次读图起请求后缀就变了，而它前面的前缀仍然成立。一张图在供应商下限及以下花 117 tokens，占满整个像素预算花 349，对着供应商 384 tokens 的上限。

跑在纯文字路由上的部署，拿到的是这件工具加一句点名它那个模型的拒绝；没有附件仓库的部署，工具和路由都拿不到。两者都在用到的那一刻才显形，而不是在加载时，因为两者都是会话与组合的属性，不是那个配置块的属性。

## Testing

`tests/content-image-capture.client.spec.ts` 拿注入的绘制原语，对着真实文档驱动每一项导出决定——四种标签与对其余标签的拒绝、可见性/加载完/零像素/污染四句拒绝、媒体类型集合、字节上限，以及一次缩小和一次 SVG 放大各自产出的确切导出尺寸。`tests/content-read-image-tool.client.spec.ts` 对着真实工具运行时逐字符钉住描述、参数表与那行标题，并驱动模态闸的两个分支、失败分支、误报分支，以及 image 块里的附件引用。`tests/content-image-report.client.spec.ts` 管宿主半边：解码后的确切字节到达仓库、存下的名字跟着页面与元素走、落定的调用带引用不带字节、拒收的仓库以它自己的理由让调用落定，以及像素在问表之前就已提交。`tests/content-read-wire.client.spec.ts` 覆盖新解析器与路由的字节算术，`tests/content-read-routes.client.spec.ts` 覆盖路由本身，`tests/self-contained-copy.client.spec.ts` 走遍第七件工具定义与十段新文案。`src/` 保持按文件 100% 覆盖。

一个 Web 场景为它兜底：`apps/web/tests/content-read-image.e2e.ts`，对着原文场景用的同一个 `tests/fixtures/markup-app`，那个应用新增了一个没有 alt 的配对二维码、一个画着固定八柱图表的 `canvas`，以及一个内联 `svg` 星形。它有自己的一层补丁 [`content-read-image.overlay.yml`](../../../../apps/web/tests/content-read-image.overlay.yml)，写明这套组合里新建会话起手在哪条路由上；随后 spec 通过 `sessionController.selectModel`——也就是编辑器里模型选择器发的那个调用——把这条路由选到那个被 seed 的会话上。光靠这层补丁路由不了这个会话，也不可能路由得了：已经记过一次 request header 的会话，按自己的日志推导路由，组合的默认值只对一次都没记过的会话生效（[`selectionFor`](../../../../packages/api/session-controller/src/agent.ts)）。这些场景重放的那份 seed 记过。spec 在驱动提示之前就断言选中的路由及其声明的图片输入，于是路由错了的会话在那里就失败，而不是在这一轮里变成三句拒绝。

这个会话还由它自己的一份 preset 组合而成——[`tests/fixtures/presets/content-column`](../../../../apps/web/tests/fixtures/presets/content-column/agent.cordis.yml)，一件工具都不挂：给模型一个二维码再给它一个 shell，它会联网装 OpenCV，从存下来的附件里把载荷解出来，而那种记录没有任何一次回放能复现。Web profile 提供的每一件模型工具都来自 preset——profile 把自己全部 `tool-*` 行禁掉，`standard` 再把它们挂回来——所以补丁层拿不走任何一件；而一份不挂任何工具的 preset 剩下的，恰好就是内容栏那七件。spec 在驱动提示之前也把这份清单钉住。只钉住 `img` 那一路——一张入仓 PNG 解码后重编码，是唯一一条在录制机与回放机上产出相同字节的导出路径，而 canvas 与矢量由浏览器栅格化，字体与抗锯齿并不保证跨平台一致。带 key 录制：

```sh
DSH_SNAPSHOT=record pnpm exec vitest run --config vitest.web.config.ts apps/web/tests/content-read-image.e2e.ts
DSH_SNAPSHOT=refresh pnpm exec vitest run --config vitest.web.config.ts apps/web/tests/content-read-image.e2e.ts
```

那次 refresh 不需要 key，也不是可选的，理由与四个文字场景相同：录制带着实时供应商解析出来的东西，而一次回放跑永远不会产出它们。只要 `snapshots/web/content-read-image/` 还不存在，这个 spec 就自行跳过，于是场景与它的录制可以落在不同的改动里，而不会把一条无 key 的流水线搞红。
