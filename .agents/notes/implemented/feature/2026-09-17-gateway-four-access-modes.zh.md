# Agent Note: 四档访问方式，由围墙与审批策略折出

Status: implemented

[English](2026-09-17-gateway-four-access-modes.md) | 中文

> 本文推翻 [审查开关离开预设表](2026-09-06-gateway-review-switch.zh.md) 的两项决定：审查不再出厂即开，预设那一行改为以审查命名。那份记录里关于这道门坐在哪里、围墙覆盖什么、两条红线、越权应答器，以及那一行的 id 为何永不改动，仍然成立。

## Problem

`@haoran/dsh-llm-permission-gateway` 0.3.1 用自己的一项设置决定对一次调用做什么——一个出厂为 `auto`、在任何访问方式下都生效的开关——而访问方式只告诉它哪些工具已经有围墙。于是人选哪种访问方式与这道门行使多大权力是两个互不相干的选择，四种组合里有两种是错的，而这道门自己看不见。

在完全权限下，这道门提出的问题没有人收得到。`ApprovalService` 在 `approval: never` 下会在派发任何应答者之前就把每一次审批申请判成 `rejected`，所以它在那里提出的每一个 `ask`，到人那里是什么都没有，到模型那里是 `the user rejected tool "<name>"`。一位 Windows 客户遇到的就是这个：`browser_auth` 不弹窗也不报错。那种方式的全部含义就是什么都不拦、什么都不问，而这道门把它变成了对无人反对的调用的无声拒绝。

在仅可查看与工作区内修改下，审查出厂是开着的，而那里操作系统已经在拒绝审查会反对的那些文件副作用。审查在这两种方式下买到的，是对围墙够不着的每一次调用多一次模型往返——`run_code` 的程序体、一次离开这台机器的调用、一次带着登录态动作的调用——而这笔钱恰好收在人为了不被打断才选的那两种方式上。

插件贡献的那一行 `yolo-access` 当时叫关闭沙箱（不推荐），描述写的是它拿掉了什么。它恰恰是唯一一种审查并非可选的方式：它的 `{danger-full-access, ask}` 这对旋钮就是没有围墙加上人还答得到，这在构造上就是审查，而那个名字对此只字未提。

## Decision

桌面端换到 `@haoran/dsh-llm-permission-gateway` 0.4.3（tarball sha256 `cd7d6bd1ed97c673e6e2077e2f076927c25b82e4e7695fa7074d27e0418d382b`，194063 字节），替换掉 0.3.1 的 tarball。

**这道门对一次调用做什么，是从内核已有的两个旋钮折出来的，不看预设的名字。**两个旋钮都是逐次调用地读：操作系统管不管得住文件副作用，读的是 `ctx.sandboxPolicy.resolve({ session })` 与所挂载的 shell 执行器报告的 `sandboxMode`；会话的实际审批策略是什么，在注册了 `permissions` 会话投影的地方读它，否则读 `ApprovalService.overrideOf`，再退到部署默认值，最后退到 `ask`。一个把自己的预设改名或重排的部署，在这里什么都改不了。

| 围墙 | 审批策略 | 档位 | 这道门做什么 |
| --- | --- | --- | --- |
| `read-only`、`workspace-write` | 两者皆可 | `walled` | 只审围墙管不到的部分，且要它自己的开关打开才审 |
| 无 | `ask` | `auto-review` | 除本机读取之外的每一次调用都审；它自己的开关够不着这一档 |
| 无 | `never` | `full-access` | 什么都不做——不查红线、不走 `alwaysAsk`、不审查；每一次调用直接放行并记为 `unattended` |

**带围墙那一档的开关只覆盖那两种方式，而且出厂是关的。**`config.mode` 默认 `manual`，这推翻了 2026-09-06 记下的 `auto` 默认值。设置页的小节叫**审查设置**（英文 **Review settings**），输入框里的 `/review auto` 与 `/review manual` 是同一个开关，两者都点名自己够得着的那两种方式，而不是点名自己。把它打开，买到的是被围住的会话仍然发出的那些无墙调用的审查，每次一趟模型往返。

**那一行改名 `自动审查` 并声明在第三位。**这推翻了 2026-09-06 立下的「预设行不得点名审查」。那条规则写下时，审查是一个人可以独立于该行扳动的开关；在这里它不是——这一行的旋钮对本身就是把一次调用送进 `auto-review` 的那个东西，而带围墙那一档的开关够不着它。它的描述写的是这个名字压缩掉的同样三件事：不设操作系统围墙。每一步先交给审查模型看，拿不准的弹给你确认；动到审查功能自身文件、或一边读凭证一边外发，一律直接拒绝。声明顺序即菜单顺序，这张表现在读作有墙、没墙但还问你、没墙也不问。id 仍是 `yolo-access`，旋钮对仍是 `{danger-full-access, ask}`，理由是 2026-09-06 那份记录所拥有的、关于已存 `defaultPreset` 的那一条。

**没有人能答复的问题，由这道门自己署名拒掉。**当发起调用的那个会话自身的实际策略是 `never` 时，会提出 `ask` 的那五步——`alwaysAsk`、超长调用、`onFailure: ask` 下的审查失败、`ask` 判决，以及被降级的 `deny`——仍然先走完 `tools/pre-execute` 瀑布的其余部分，然后以 `{kind: 'deny'}` 收尾，带上该步自己的那句话，再加一句说没有人可以答复。链上更靠后的 `deny` 或更具体的 `ask` 依然优先。记录里带 `delegated` 与 `humanReachable`。

**被委派的调用由委派它的那个会话来管。**`@deepseek-ai/dsh-subagent` 在编排了审批能力的地方把每个进程内子代理钉在 `approval: never`，并在旁边种下父会话的沙箱覆盖，所以一个无墙会话的子代理带的是 `full-access` 那对旋钮，无论人实际选的是哪种方式；没有这条读法，一次 `delegate` 就会让子代理的每一次调用绕过审查、绕过 `alwaysAsk`、绕过两条红线。判据是 `header.origin === 'subagent'`，除此之外什么都不是——`parentSession` 是一个对话被 **fork** 出来时带的那个字段——档位则是沿 `session.header.parentSession` 用 `ctx.agents.get()` 往上爬，只要脚下这个会话本身还是子代理孩子就继续爬。爬不通的谱系按「问得到人」折档，所以立着的围墙仍然是围墙。

**两条红线在这道门决定一次调用的地方一律成立**，包括审查关着的那两种带围墙的方式；而在 `full-access` 下这个插件一行都不跑。自我修改那条现在只比绝对路径，相对参数交给它列出的那些字面拼法——因为拿本进程的工作目录去解析相对参数，会让 `dsh` 从受保护目录里启动时，每一个带分隔符的参数都命中。决策记录文件被刻意留在受保护集合之外：护住它要读 `verdictLog`，而一条 `Config` 字段能双向挪动的红线不是红线。

**桌面端的编排层没动。**`apps/desktop-app/cordis.patch.yml` 里的 `llm-permission-gateway` 行仍然只重述 `provider` 与 `model`，因为这仍是该插件 `Config` 里仅有的两个必填项、也仍是它自己 patch 层只写的两个键，而插件出厂的路由仍是那一行存在就是为了改道的、已退役的 `deepseek-v4-flash`。

### 退役

这一行、带围墙那一档的审查开关，以及判官路由设置，存在的理由是内核没有出厂的受审访问方式。上游 0.1.6-alpha.1 已经带着一个实验性的——`AUTO_PRESET` / `registerAuto`，id 为 `auto`，还没进默认组合。一旦它进入默认组合或桌面载荷，`git grep -n "AUTO_PRESET\|registerAuto" upstream/master -- packages/bundle/base packages/interaction/permission-presets` 与 base 预设表里出现的 `auto` 行都会报出来，这三样一并退役、改为适配它。同样这条判据写在插件自己的 `cordis.patch.yml` 里，所以它随这一行一起走。

## Alternatives considered

**在完全权限下照旧发问。**这是把每种方式一视同仁的那种读法。`ApprovalService` 在 `never` 下会在任何应答者看到之前就把审批申请判成 `rejected`，所以那种方式下产生的问题根本不是问题：人什么都没看到，模型被告知人拒绝了。改为由这道门自己署名答复，则会在唯一一种其明文含义就是「什么都不拒绝」的方式里产生拒绝。

**把开关默认成 `auto`**，也就是 2026-09-06 的决定，让升级不改变任何行为。否决的依据是这个默认值在它生效的地方要付什么代价：有围墙时操作系统已经在拒绝审查会反对的那些文件副作用，所以这个默认值买来的审查，恰好收在人为了不被打断才挑的那两种方式上。2026-09-06 支持 `auto` 的那条理由——挂载这个 bundle 本来就是一次刻意的动作——依然成立，但不再具有决定性，因为一个会话跑在哪种方式下是第二次刻意的动作，而那个开关此前对它视而不见。

**保留关闭沙箱（不推荐）这个名字**，这既是 2026-09-06 的决定，也是唯一用过这个功能的那台机器所认的名字。否决的理由是前提变了：那个名字是在「选中它买到的是模型提得出却执行不了的审批提示、而审查在其余每种方式下也都有」的前提下挑的。如今开关够不着这一行，所以审查在它里面不是一个选项——它就是这一行本身。

**在预设表里加第五行表示「审查开着」。**这仍然是人会去找它的地方，也仍然因 2026-09-06 记下的理由被否决：`PermissionPresetService` 靠把一个预设的 `(sandbox, approval)` 组合在表里查一遍来解析它，所以与别人共用组合的一行会让两行都解析成 `custom`，谁都选不中。「围墙已经立着的地方也审」是一个覆盖两行的是非题，不是自己的一行。

**从 `header.parentSession` 读委派关系。**0.4.1 发过并在 0.4.2 撤回：header 对该字段的定义是「本会话是从哪个会话 fork 出来的」，而 fork 命令为一个人打开并正坐在里面的会话写下它。于是 fork 一个对话之后，每一次本该问他的调用都答「这一步没有人可以答复」；fork 一个还活着的对话，则会覆盖他在里面设定的访问方式。

**既然上游自己的 `auto` 就要来了，现在就把 `yolo-access` 这一行删掉。**在那一行真正进入默认组合或载荷之前，这是被否决的：`permission.defaultPreset` 存在一个对这张表里的名字做闭合联合的 schema 下，而 `SettingsProvider.register` 面对 schema 不再接纳的已存小节是拒绝安装，所以删掉这个 id 会让存过它的人整个 `permission` 设置小节装不上。

**用自我修改红线护住决策记录**，也就是 0.4.0 的做法。0.4.1 撤回：护住它要读 `verdictLog`，于是一条 `Config` 字段决定了一条无条件拒绝覆盖多大范围——记录写进 harness home 里就护住了整个 home，每一个点名会话日志的调用都被拒；而 `verdictLog: false` 什么都不护。

## Consequences

访问方式控件读作仅可查看 / 工作区内修改 / 自动审查 / 完全权限，`apps/desktop-shell/README.{md,zh.md}` 用两种语言写明这四档各买到什么。新会话被钉住的仍是编排出来的默认值 `workspace-write` 加 `ask`，而现在它在人开口之前什么都不审。

完全权限每次调用少一趟模型往返，也没有多藏什么：放行被记为 `unattended`，而在那种方式下，决策记录是关于跑过什么的唯一一份账。

子代理由委派它的那个会话的访问方式来管，那里拿不准的判决以这道门署名的拒绝收场，而不是以一次记在一个什么都没看到的人头上的拒绝收场。围墙立着但方式不问任何人的会话里，人读到的是同一句话。

`apps/desktop-shell/tests/builtin-permission-gateway.spec.ts` 从提交进来的那个 tarball 里读出预设表，所以四行的顺序被钉成一张字面表，那一行被读作 `自动审查` / `不设操作系统围墙`，而「不得把审查卖成沙箱的替代品」这条承诺，是靠钉住描述里划定它主张边界的那三处措辞来守住的——墙没了、拿不准的弹给你确认、两类直接拒绝。三处都对着各自的 0.3.1 取值做过变异验证。

`packages/client/ui-settings-general/tests/settings-root.client.spec.tsx` 里带的网关小节标签只是某个注册方自有文案的替身；它现在写作 `Review settings`，免得夹具替产品保留一个已经弃用的名字。

## Deferred

有两件事等 rc.34。按上面那条退役判据，一旦上游 `registerAuto` 的座位进了默认组合，这一行就挪到那个座位上。另一件是把这个开关在本地回答的那个问题——带围墙的方式要不要也审——拿去和上游谈，因为若要让上游的受审方式覆盖同样的地面，一个挨着 `registerAuto` 的审批旋钮才是它该待的地方。
