# Agent Note: the gate renews its token in place, where the deployment publishes an endpoint

Status: implemented

English | [中文](2026-09-07-auth-gate-token-renewal.zh.md)

## Problem

The [browser single sign-on](../architecture/2026-08-28-browser-single-sign-on-and-mcp-token-injection.md) gate acts `refreshMarginSeconds` before a token's `exp`, and acting meant one thing: give the token up and send the visitor to the login page. Tokens in this deployment last two hours, so a console somebody is working in signs them out every two hours — mid-task, with whatever was on screen replaced by a login form.

The deployment itself does not do this to its own pages. Its frontend renews lazily: the request interceptor in `toy-core/api/axios.js` calls `tokenRenewal()` on any request once `isTokenRenewal()` says the stored token is older than `accessTokenRenewalTime` minutes (30 by default, measured from `accessTokenTime`), and `tokenRenewal()` reads a new token out of `GET /nrms-auth/api/renewal` and stores it with `setToken`. Every page of that deployment therefore stays signed in for as long as it is open. The console beside them was the one surface that did not.

## Decision

**Renewal is two `Config` fields, both absent by default, and a deployment that leaves them out behaves exactly as before.** `renewalPath` is the endpoint as a path on the page's own origin — `/<the API prefix>/nrms-auth/api/renewal` for a standard install — and `renewalIntervalSeconds` is how long a token is held before the gate asks for a new one. Where the endpoint lives is deployment-varying twice over: the API prefix is the frontend's own `VUE_APP_BASE_URL`, and a deployment behind a path-prefixed reverse proxy carries that prefix as well. Both are refused in halves and the load fails loud: an interval with no path is a deployment that believes it renews and does not, a path with no interval renews on no schedule, an interval of zero is a request loop, and a path that is not root-absolute — a protocol-relative `//host/path` included — would send this visitor's credential off the deployment. The browser half receives them as one nested `renewal` block on the settings document, so "both or neither" is structural rather than a rule two readers have to remember, and it re-checks all three on arrival because that document crossed a process.

**Two schedules ask, and only one of them acts on a refusal.** Both are armed the moment a token is accepted and re-armed every time one is. The periodic tick fires `renewalIntervalSeconds` after that moment and is silent either way — the deployment's own rule is "renew when the token in hand is older than the interval", and this is that rule as a timer rather than as a check on a request this shell never makes. The expiry margin asks too, and it is the one that ends somewhere: a margin no renewal answered gives the token up and leaves for the login page, which is what a deployment with no renewal endpoint always does. A periodic attempt that fails changes nothing on screen and nothing in the node half, because the token in hand is still usable and the next tick asks again.

**One exchange at a time, shared rather than refused.** A margin arriving while a periodic attempt is out waits for that attempt's answer instead of starting a second one, and instead of leaving while an answer to the first is still coming. A token already past `exp` is never sent: the endpoint refuses a dead one, and that case ends at the margin.

**An answer counts only where it moves the expiry forward, and the margin renews at most once.** A renewal is taken only when its `exp` is later than the token the request was sent with and later than whatever storage holds when the answer arrives. The first rule refuses an endpoint that answers with the token it was given: such an answer renews nothing, the margin it satisfied re-arms with no delay, and the two would exchange requests for as long as the endpoint kept answering — so a periodic tick reads it as a failure and stays silent, and a margin reads it as a failure and leaves for the login page. The second rule keeps a slow answer in one tab from replacing the newer token another tab has already stored. A renewal that is taken and is itself already inside the margin is not renewed from the margin again either, for the same reason its own margin timer is armed with no delay: the login page is this gate's answer to a deployment whose `renewalIntervalSeconds` leaves no room ahead of its `refreshMarginSeconds`.

**A margin answers for the token it was armed with.** The margin timer carries that token, and a failed renewal gives it up only where the page is still running on it — or where the token now in hand is itself inside the margin, the case the rule above ends at the login page. An exchange takes time, and a token that arrives while one is out arms a margin of its own: another tab renewing, an embedded deployment page renewing, this visitor signing in again. Without the check, a failed renewal would revoke a credential hours from its expiry, clear the mirror the whole origin reads, and send a working page to the login form.

**A delay longer than one browser timer holds is slept in links, and an interval that long still fails the row.** `setTimeout` keeps its delay in a signed 32-bit field of milliseconds, and a browser fires a longer one on the next tick rather than waiting it out. The browser half's `schedule` therefore sleeps 2147483647 ms and re-arms for the remainder, and cancelling cancels the link armed now; both timers go through it, so both tolerate a delay of any length. The expiry margin is the one that needs it: its delay is whatever `exp` the deployment's token carries, and a deployment issuing a 30-day token would otherwise have signed the visitor out at boot, on a margin the browser fired on the next tick. `renewalIntervalSeconds` above 2147483 still fails the row on both halves, refused rather than slept, because it is a number no deployment means: it names a schedule first firing 24 days out, which no token this gate accepts lives to reach.

**A storage write the browser refuses is a renewal that produced nothing.** A full quota throws on `localStorage.setItem`, and so does a private window a browser gives no quota at all. The throw is taken as a failure the way a mirror cookie the browser did not keep already is — the periodic path stays silent, the margin ends at the login page — rather than rejecting a promise nothing awaits, which would leave the page with no schedule armed at all.

**Leaving the page releases the gate, whichever way it leaves.** Giving the token up stops the storage subscription, both timers, and any renewal still out, before the sign-out request goes anywhere, and the account switch does the same before its reload. A callback the event loop had already dequeued still runs afterwards, and an answer already on the wire still arrives; taking either one would write a token back into storage, into the mirror cookie, and into the node half — for a visitor who has just given it up, or, on the switch, for the account that just left, into the three places the document coming up reads its identity from.

**The request is the one the deployment's own client sends, and the write is the one its own `setToken` makes.** `GET <renewalPath>` carries the stored token verbatim, scheme included, on both `Authorization` and `CertificationToken`; the headers `localStorage.loginUserInfo` holds under them; and a fresh `TINY-REQUEST-ID` over all of it, in that order, which is the order `api/axios.js` assembles them in. The answer is read as `tokenRenewal()` reads it — the response body's own `token` field, which is what that file's response interceptor resolves `service.get` to. What comes back is stored under `accessToken` exactly as it arrived, with `accessTokenTime` beside it, so the existing storage-to-cookie-to-node-half path carries the new token to the node half and to any deployment page embedded on the same origin. The mirror cookie is written and read back **before** storage, so the cookie the reverse proxy reads and the value in storage never disagree; a write the browser did not keep leaves the page on the token it already had.

**`accessTokenTime` is an ISO 8601 instant in UTC**, not the local-offset rendering `dayjs().format()` gives the same instant. Its only reader in that deployment, `isTokenRenewal`, parses it and takes a difference, so the two renderings are interchangeable to it, and this one does not change with the timezone the browser happens to be in.

**`GateBrowser` gains one storage seam rather than a second token reader.** `readToken()` is gone; `readStorage(key)` and `writeStorage(key, value)` take its place, and dropping the login page's `Bearer ` scheme happens above the seam where every other reading of a stored value already happens. `requestId()` and `requestJson(path, headers, signal)` are the other two additions, so the gate itself still runs without a DOM and every renewal test drives a fake browser. The signal is the gate's disposer: a released gate aborts the request it has out and acts on nothing that answers afterwards.

**The node half gains no route.** A renewed token reaches it the way every other token does — the gate arms it, `push` posts it to `/auth-gate/token`, and the closure holds it. Nothing about renewal is model-visible: no tool, no prompt section, no session event, and therefore no snapshot fixture changes.

## Alternatives considered

**Renewing lazily on the next request, the way the deployment does.** Rejected because there is no such request. The console does not talk to the deployment through `toy-core`'s axios instance — the browser half makes exactly three requests of its own, all to the node half — so there is no interceptor to hang a lazy renewal on, and the only clock the gate has is its own timers. The timer is the same rule with the trigger the gate actually has.

**Making the expiry margin the only trigger.** Rejected on what it would rest on. It would put a two-hour token's entire renewal on one attempt five minutes before it dies, with the login page as the answer to a single failed request, and it would leave the console's stored token hours staler than the token every other page of the deployment is holding. A periodic ask keeps the console in step with those pages, and the margin becomes the fallback rather than the mechanism.

**Reading `accessTokenTime` and renewing when the stored token is older than the interval — `isTokenRenewal` verbatim.** Rejected: it makes the schedule depend on a stored timestamp's format and on a policy for what to do when that value is missing, unparseable, or in the future, all to reproduce a moment the gate already knows — when it accepted the token it is holding. A page opened on an already-old token therefore waits a full interval before it asks; the margin still covers that token, and the deployment's own pages renew it as soon as they are used.

**Falling back to the login page on a failed periodic attempt.** Rejected: the token is still usable at that moment, so one transient failure would cost the visitor the page they are working in. The margin is where a failure means the credential is actually running out.

**A new node-half route to take the renewed token.** Rejected as a second path to the same place: the gate arms the new token exactly as it arms one another tab wrote, and `push` already posts it to the token route.

**Mirroring the deployment's `Refresh-Authorization` handling.** Rejected because it is not a renewal channel. That branch of the response interceptor reads `response.config.headers['Refresh-Authorization']` — the request's own configured headers, not the response's — so it fires for a header the client would have had to send itself, which nothing does.

**A leader tab, so only one renews.** Rejected for this change: the gate has no leader or lock notion to reuse, and adding one is a larger piece of design than the renewal it would optimize. The consequence is recorded below rather than hidden.

## Consequences

**Bought.** A console configured with its deployment's renewal endpoint stays signed in for as long as it is open, and the token it holds stays as fresh as the one every other page of that deployment holds. The node half spends the renewed token on the MCP forwards and the data backend without knowing renewal exists.

**Paid.** One `GET` per interval per open tab, carrying the visitor's credential to an endpoint the deployment configured. Two more `GateBrowser` operations and a storage write where the gate previously only read. A deployment that leaves the fields out is exactly where it was, which is to say it still signs its visitors out every two hours.

## Known Limitations and Deferred Work

- **The deployment this was written for issues no fresh token, which leaves the renewal inert there.** Every answer it gave carried back the token that had been sent, the one asked for 2.3 minutes before `exp` included, and 100 seconds after that `exp` both the endpoint and a metadata read answered 401: on that deployment the JWT's `exp` is the real expiry. The two fields therefore stay unconfigured on that console, which keeps the margin-to-login path it already had, so against that deployment this change buys nothing the old behavior did not. Every endpoint in these tests is a fake; a deployment whose endpoint answers with a later `exp` is what would show the renewal working end to end.
- **A deployment that sets `isAuth` is not gated at all.** `toy-core`'s `getToken`, `setToken`, and `isTokenRenewal` switch every key to `accessTokenAuth` and `accessTokenTimeAuth` when `getLocalConfig().isAuth` is set (`core/token.js`), and both halves of this package name the default keys only. Under such a deployment the gate reads a key that deployment's login page never writes, so a visitor is sent to the login page, signed in, and sent there again. Nothing configures the key names, and nothing reports the mismatch; a deployment that actually sets `isAuth` is what would make that table configuration rather than a constant.
- **A margin-driven renewal can cost one extra request.** `arm` cancels the periodic timer, but a callback the event loop has already dequeued still runs, so a tick that came due in the same turn as a margin renewal asks the endpoint once more. The rules above accept or refuse that answer like any other, so the cost is the one request the deployment sees; a generation counter on `arm` is what would close it.
- **A storage quota that takes one write and refuses the next stores a renewed token this gate then abandons.** `writeRenewal` writes `accessToken` and then `accessTokenTime`; a browser that admits the token and throws on the time reports the whole renewal as one that produced nothing, so the margin gives the credential up and leaves for the login page while storage holds the fresh token beside the age of the one before it, which the deployment's own pages read as older than it is. Nothing here distinguishes the two writes — the fake browser refuses both — and writing the time first, or storing the pair under one key, is what would close it.
- **Every open tab renews on its own.** No leader election, no lock: two tabs each ask every `renewalIntervalSeconds`. They converge, because the tab that did not ask sees the other's write as a same-person `storage` change and takes the newer token through the path that already existed, but the deployment sees one exchange per tab and the last write wins where two answers cross.
- **A failed periodic renewal says nothing.** A deployment whose renewal endpoint has been refusing for hours looks exactly like one that has not, until the margin arrives.
- **A page opened on an old token waits a full interval.** The schedule starts when the gate accepts a token, not when that token was issued, so a tab opened an hour into a token's life asks an interval later rather than immediately.
- **The two renewal fields are per-deployment opt-in.** Nothing infers the endpoint from `bizUpstream` or from the login page, so a deployment that has a renewal endpoint and does not configure one keeps the old behavior with no diagnostic saying so.
