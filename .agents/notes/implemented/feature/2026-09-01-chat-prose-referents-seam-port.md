# Agent Note: porting the chat-prose proseReferents seam onto the 0.1.2 reorganization

Status: implemented

English | [中文](2026-09-01-chat-prose-referents-seam-port.zh.md)

## Problem

The original patch (`ae19472402`, "a proseReferents seam for chat prose") gives Assistant prose a second optional-service seam alongside the existing inline-code-only `chatFileMentions`: `MarkdownRenderContext` (`ui-primitives`' `render.tsx`) gains `referents`, an opaque `scan(text, inlineCode)`/`open(span)` pair whose `MarkdownProseSpan` carries only `start`/`end` so the renderer never learns `kind`/`target`/`raw`, keeping `ui-primitives` free of any dependency on the runtime's `ReferentKind`. A hit renders as the same always-visible `css.fileMention` button token file mentions already use, in both plain text (previously returned as a bare string) and inline code left unclaimed by `fileMentions`; both stay off inside `inLink` and apply only to `renderSettled`'s context, mirroring `fileMentions`' own streaming gate exactly. `contract/slots.ts` adds the full `ProseReferentSpan` (`kind`/`target`/`raw` included) and the `ProseReferents` optional service (`ctx.get('proseReferents')`), mirroring `ChatFileMentions`' convention; `apply.ts`'s `buildProseReferents` binds `cwd` (session snapshot) and Host `home` fresh per call and dispatches its own `ReferentRef` (`source: 'chat-prose'`, `provenance: 'model-text'`) through `dispatchReferentOpen` — never through the `openFile` closure a few lines below, which would double-dispatch and mislabel provenance `'structured'`.

This is the first of a six-patch connected series (`ae19472402` + `0c9b669a3c` + `6e7045d8cf` + `1d8e975c1a` + `f495eefd50` + `83eb0e3ddb`), each a sequential, independently reviewable design increment on top of the previous, so — unlike the `4b7d225e25` squash — this port lands the six as six separate commits, this one first, referencing this same design decision set where later patches only extend it. It predates the same package reorganization every other patch in this sync predates: `ui-conversation`'s `chat/` subtree (and this patch's own target files) moved to a new `ui-chat` package, and it depends on `fabc93555c`'s `referent/open`/`dispatchReferentOpen` seam (ported as `0b32bd30ad`) and `88129b7b44`'s `probeTargets` RPC (already landed in Family A as `35ca000207`), both of which this port already has in place. An earlier attempt at this series (recorded in the ledger) reset a documentation-only Agent Note commit as SKIPPED because it described this architecture as already implemented when it was not; this port makes that description accurate for `ae19472402` specifically, five patches still to follow.

## Decision

**`ProseReferents`/`ProseReferentSpan` land in `packages/client/ui-chat/src/client/contract/slots.ts`, not `ui-conversation`'s.** The original patch's target package, `ui-conversation`, no longer owns the `chat/*.tsx` render call sites or `apply.ts`'s wiring — both relocated to `ui-chat` during the reorganization, carrying `ChatNodeOwnerProps`/`ChatViewInjected`/`ChatFileMentions` with them (established by the `fabc93555c` and `98020a23cd` ports before this one). `ProseReferents` follows the exact same precedent: it plugs into the identical `ChatViewInjected` → `ChatView` → `ChatNodeOwnerProps` → chat node renderers → `AssistantMarkdown` → `MarkdownText` chain `chatFileMentions` already threads through, so it lives beside `chatFileMentions`'s own `Context` merge block in the same file.

**`Host home` is read as `connection.generation.getSnapshot()?.host.home`, not `connection.hostDescription.getSnapshot()?.home`.** The original patch's `ConnectionHandle` had a `hostDescription` field directly; the current tree's `ConnectionHandle` (`packages/client/connection/src/client/index.ts`) has no such field — `home` now nests under `ConnectionGeneration.host: ConnectionHostInfo`, reached through `connection.generation.getSnapshot()?.host.home`. The resolution mechanism itself is unchanged: no ambient `ctx.connection` `Context` merge exists in either tree, so `apply.ts` still resolves it with `ctx.get('connection') as ConnectionHandle`, matching the identical cast already used by `packages/api/gateway/src/client/index.ts` and `packages/client/ui-settings-general/src/client/index.ts` — both of which also declare `'connection'` in their own `inject` array despite the untyped cast, the same convention this port follows by adding `'connection'` as the first entry of `ui-chat`'s `apply.ts` `inject` array.

**The default open action calls `ctx.remote.session.openWorkspacePath({ path })`, not `ctx.workspaces.openPath(target)`.** `ctx.workspaces` and its `openPath` method do not exist anywhere in the reorganized tree — the original patch's base predates whatever later removed that service. The pre-existing `openFile` closure a few lines below `buildProseReferents` in the same `apply.ts` already resolves an unclaimed workspace path through an RPC call, `ctx.remote.session.openWorkspacePath({ path })`, checking `.ok` and throwing on failure; `buildProseReferents`'s own default action adopts the identical call for behavioral and stylistic consistency with its neighbor, rather than inventing a second mechanism for the same operation.

**Adding `'connection'` to `ui-chat`'s required `inject` array is a real, package-visible dependency addition, not an internal-only detail.** `ui-chat/package.json`'s `dsh.client.inject` array and `devDependencies` both gained `@deepseek-ai/dsh-client-connection`, matching the existing convention that every cordis service key named in a plugin's `inject` array has a corresponding workspace package declared in both places (enforced by `verify-package-dependencies`). Every `SlotTestRuntime` bench that mounts `ui-chat`'s `apply` now must `ctx.provide('connection', ...)` before mounting, since `SlotTestRuntime.mount()` fails loud — `"mount would suspend: missing service(s) connection"` — for any declared `inject` entry left unprovided; `chat-apply.client.spec.tsx` and `apply-inject.client.spec.tsx` both gained a minimal stub providing only the `generation.getSnapshot()?.host.home` shape the code under test actually reads, matching the minimal-stub convention already established in `ui-settings-general`'s own apply test.

**The `ui-conversation/README.md` (now `ui-chat/README.md`) prose paragraph is not ported.** The original patch added a paragraph describing "every Assistant message's prose... a second, independent off switch..." to `ui-conversation/README.md`, immediately after its existing `chatFileMentions`/closing-turn-prose paragraph. Neither paragraph exists in `ui-chat/README.md` in the reorganized tree — the entire `chatFileMentions`/`TurnTailOwnerProps` discussion this addition depended on was already trimmed during the reorganization (`ui-chat/README.md` is a much shorter document, confirmed by direct inspection), matching the same pattern the `fabc93555c` and `98020a23cd` ports found for their own README additions. Adding a standalone paragraph with nothing to attach to would misrepresent the surrounding document's own scope.

## Alternatives considered

**Keep `ProseReferents` in `ui-conversation`'s `contract/slots.ts`, matching the original patch's file path literally.** Rejected: `ui-conversation` no longer owns any of this seam's actual consumers (`AssistantMarkdown.tsx`, `ChatNodeSeat.tsx`, `ChatView.tsx`, `apply.ts`) — they all moved to `ui-chat` in a prior port. Placing the contract in a package that cannot wire it would split one capability seam across two packages for no reason other than matching the original patch's now-stale path.

**Add a compatibility shim reintroducing `ctx.workspaces.openPath` so the original call site needs no edit.** Rejected: no owning service for `ctx.workspaces` exists anywhere in the reorganized tree to back such a shim: `ctx.remote.session.openWorkspacePath` is the tree's actual, already-tested replacement functionality, not a renamed alias for the same thing. Reintroducing a dead service interface would add an unbacked shape purely to avoid a two-line change already established as the correct pattern by the neighboring `openFile` closure.

## Consequences

`packages/client/ui-primitives/tests/markdown.client.spec.tsx` gained seven new tests covering prose scanning, inline-code scanning after `fileMentions` declines, adjacent-span rendering, the `inLink` gate, the streaming gate, and the absent-service default; `markdown-render-units.client.spec.tsx` gained a `referents: undefined` context field. `packages/client/ui-chat/tests/chat-view.client.spec.tsx` and `packages/client/ui-workflow-run/tests/workflow-run.client.spec.tsx` gained `referents: undefined` on their `ChatNodeOwnerProps`/`ChatViewInjected` fixtures. `packages/client/ui-chat/tests/apply-inject.client.spec.tsx` gained five new tests exercising `referents` on the injected Chat View face (absent-provider default, `scan` argument forwarding, `chat-prose`-provenance dispatch, and both default-action fallbacks — `openWorkspacePath` for a file/dir span, `window.open` for a url span — adapted from the original's `workspaces.openPath` assertion to this tree's RPC spy). Both this file and `chat-apply.client.spec.tsx` needed a `runtime.ctx.provide('connection', ...)` stub added to their `bench()` for the new required inject. `packages/extensions/cordis-client-runner/src/client/slot-catalog.ts` picked up the widened `ChatNodeOwnerProps` shape and shifted several unrelated `source:` line-number references via `pnpm run gen-client-catalog` (mechanical); `scripts/gen-cordis-catalog.ts`'s `SERVICE_WALK_EXEMPTIONS` gained a `proseReferents` entry alongside `chatFileMentions`, documented at `packages/client/ui-chat/README.md` per that table's convention even though the README prose itself is not being added (the exemption documents the client-side accessor's existence and ownership, not a specific paragraph).

The out-of-repo verification index this seam exists to support (the nominate → verify → open architecture's actual nominate/verify layer) still does not land in this repository — it belongs to an out-of-repo plugin, matching the capability-seam philosophy this port's core-only Service Definition/Consumer split already follows. The five remaining connected patches in this series (`0c9b669a3c`, `6e7045d8cf`, `1d8e975c1a`, `f495eefd50`, `83eb0e3ddb`) build on the `referents` seam this patch establishes and land as separate follow-on commits, all six now landed (`43d944b8fd`, `21c8b07bd5`, `bf2537030f`, `bfd732dd65`, `16ad7f6cd8`, `a8cc98f350`).

## Follow-on: 13cead33dd (not-found race degrade)

A seventh, related patch lands in the same series of work: `13cead33dd` ("degrade a prose referent's not-found race to the composer's own notice") fixes a real field-confirmed gap — a `referents.scan`-verified span can still name a path deleted between that verification and the click, and `buildProseReferents.open` had no user-visible feedback for that race, only a `console.error`. The terminal card already degrades the identical race through its own `ClickOutcome`/inline-notice machinery; prose has no per-span click state to degrade into, so this reuses the session's composer notice channel instead.

**The cross-package notice wiring uses `sessions.scope(id)` + `actx.get('conversation')`, not the original's same-file `InputHub` instance.** The original patch's base tree had `buildProseReferents` and its `InputHub` class instance in the same file (`ui-conversation/src/client/apply.ts`); this port's `buildProseReferents` lives in `ui-chat/src/client/apply.ts`, while `InputHub` stayed in `ui-conversation`, exposed as `ctx.conversation.input`. Reaching it from a different package uses the exact pattern `packages/client/ui-commands/src/client/service.ts`'s own `noticeFor()` already establishes: `sessions.scope(id)` resolves the session-scoped `Context`, then `actx.get('conversation')` (never `actx.conversation` — a first attempt at direct property access failed at runtime with `"cannot get property conversation without inject"`, since `actx` is a scope this plugin's own `inject` array does not cover; `.get()` is cordis's cross-scope-safe dynamic lookup, unlike the inject-guarded direct-property accessor). `'conversation'` joins `ui-chat`'s required `inject` array alongside the pre-existing `'uiConversation'`, both from the same providing plugin.

**Not-found classification uses `remoteErrorOf(error)`, not `instanceof PathOpenError`.** The original patch's `PathOpenError` class (with `.rpcError.code === 'not-found'`) has no equivalent in this tree: `openWorkspacePath` returns `{ok: false, error: RemoteError}` rather than throwing a wrapper exception, and the actual failure code for a deleted path is `'session/path-not-found'` (declared in `packages/api/session-controller/src/types.ts`'s `RemoteErrorDetailsMap`), not `'not-found'`. `buildProseReferents`'s `onDefault` now rethrows the raw `result.error` (a real `RemoteError`, preserving `.code`) instead of flattening it to a message-only `Error` as the neighboring `openFile` closure still does (that closure has no dedicated failure UI to route to, so flattening loses nothing there); the `.catch` classifies with `remoteErrorOf(error)?.code === 'session/path-not-found'`, following this tree's own documented convention — `packages/typert/protocol/src/remote-error.ts`'s own comment: "structural, not instanceof: an Error thrown in another realm... fails instanceof Error here." `@deepseek-ai/dsh-typert-protocol` joins `ui-chat`'s `devDependencies` for `remoteErrorOf` — a plain utility import, not a cordis service, so no `dsh.client.inject` entry is needed, matching several other `packages/client/*` packages that already depend on it the same way.

**A latent test gap from `ae19472402` surfaced and was fixed in the same commit.** Running this patch's own broader affected-test sweep (`ui-chat`, `ui-tool`, plus the earlier four) revealed that three `ui-tool` test benches (`chat-code-subcalls`, `assembly-surfaces`, `toolview-slot`) mount `applyChat` but were never given a `'connection'` stub when `ae19472402` (`43d944b8fd`) added that inject requirement — that commit's own gate sweep scoped to `ui-chat`/`ui-workflow-run`/`ui-primitives`/`ui-conversation` only, missing `ui-tool` entirely. This is a real gap in that earlier commit's own verification, not a new requirement `13cead33dd` introduces on its own; it is fixed in `13cead33dd`'s commit rather than as an isolated fix commit, because isolating it would require temporarily reverting `ae19472402`'s already-merged `apply.ts` change to give the fix commit something to test against — more churn than the entanglement it would resolve.

**Retirement.** Unchanged from the original: `proseReferents` is a fork-only interception seam for a capability upstream's own conversation UI does not yet expose. If upstream's own session UI natively scans and dispatches clickable references in Assistant prose, this patch (and this port) retires and the fork adapts to upstream's form.
