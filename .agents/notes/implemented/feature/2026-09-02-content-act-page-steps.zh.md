# Agent Note: content_act —— agent 在内容区那个页面上的手

Status: implemented

[English](2026-09-02-content-act-page-steps.md) | 中文

## Problem

`content_read` 给了 agent 一双看着用户正在看的那个页面的眼睛，却没有给它任何能对看见的东西做的事。控制台用户说「把这个点位改个名」「筛一下」「把这张表填了保存」，要的正是 agent 现在能完整描述、却碰不到的那件事。绕开的办法是 agent 把页面念给用户听、用户自己去点——而这一栏存在的意义，就是终结这种安排。

动手同样不是宿主的能力，理由和读取当初一样：文档活在某个人浏览器里的 iframe 中，跑在应用自己的事件处理器底下，宿主既没有 DOM，也没有指名那个浏览器的办法。它还是本包做的第一件用户移开视线也撤不回的事——点在「删除」上就是点在「删除」上——所以读取需要一条通道，而动手需要一条通道加一次决定。

## Decision

`content_act({ steps, dialogs? })` 最多跑 `maxSteps` 步、五个动作——`click`、`fill`、`select`、`press`、`wait`——按顺序作用在这一栏最前面的页面上，首个失败即停。它骑在读取那条通道上：同一张待办表、同一次认领、同一条回报路由，没有页面可动手时也是同样那四种结局。不同的只有回传的那份文档，以及它前面的那道审批。

### 一次调用就是一次审批请求，且只由参数生成

一个 `tools/pre-execute` 监听器把这个工具的每一次调用都升格成 `{ kind: 'ask' }`。监听器先委派，所以本来会拒掉这次调用的策略、hook 或 guard 照样拒得掉，用户也不会被问一件已经被拒的事；被放行的才升格成请求，而不是被直接放过。没有组合审批服务的部署一步都不会跑——这是内核对「问了却没人接」自己的降级。

这份请求写在任何东西够到浏览器之前。没有座位认领过这次调用，没有页面被读过，宿主对这一栏的全部认识只是一份它没有画过的 id 与标题的 projection。所以请求按用户看见的样子称呼这一栏最前面的那一项——在「当前展示的这一项」上：填「名称」为「东风」；点「查询」——而不是一个宿主只能猜的页面标题。这也是每一步都必须带 `label` 的第二个理由：要告诉用户将要点什么、填什么，而这些名字只可能来自调用本身。

### 页面自己的确认框是另一次同意

`dialogs: 'accept'` 让座位用「确定」去答页面弹出的 `confirm()`。一次覆盖「点删除」的审批，并不覆盖紧跟其后的那次确认，所以只要请求里带了那句话，监听器就记下它问过的这个 call id；而工具体在肯用「取消」以外的任何答案作答之前，先花掉这条记录。任何绕过用户读到的那份请求而到达工具体的路径——长期放行、从不发问的策略、重放、同一次调用的重试——因此都会取消页面的对话框。记录用一次即消，表最多记 64 个 id；越界丢最旧的那个，在这个方向上正是安全的答案。

### 动手之前先拿 label 与页面核对

除 `wait` 外每一步都两次点名它的元素：一次是某次读取给出的 ref，一次是那次读取印出的可及名称。座位解析 ref、重新算一遍名字，两者不同就拒掉这一步。整套设计正是围着这个失败搭起来的：上次读取之后重绘过表格的页面，同样的 ref 指的已是别的行，而只信 ref 的一步会去按此刻占着那个位置的东西——这是事后再读一次也撤不回的那一个错。另有三种结局会让某一步停下：页面上已经没有的元素、被页面挡在用户面前的对话框后面的元素、页面已经禁用掉的元素。

这道核对不是身份。两行里都叫「编辑」的按钮能过关，而一个同时改编号又改名字的页面，就是必须重新读一次的页面。它以每步一次可及名称计算的代价，抓住了常见的那一种——页面变了。

### 事件是用户会产生的那一套

一次 click 是 `pointerdown`、`mousedown`、`pointerup`、`mouseup`、`click`，因为只听 `mousedown` 的框架永远看不见一个光秃秃的 `click`。一次 fill 走原型上的 value setter，再发 `input` 与 `change`，因为 React 和 Vue 都在元素上记着自己上一次写进去的值，直接赋 `el.value` 是它们下一次渲染就会撤销的改动。一次按键是 `keydown`、`keypress`、`keyup`，背后不提交任何表单，因为 Enter 是什么意思由页面决定。`select` 要么是平台自己的 `<select>`，要么是一个自绘选择器需要的两次点击：点开、等选项出现、点文字对上的那一个。

步与步之间给页面 `settleQuietMs` 静下来，每步以 `settleMaxMs` 封顶，好让「点开一个对话框」这一步在「填对话框里那个框」这一步解析 ref 之前真的把它打开了。是每步封顶而不是整轮封顶：一个永远停不下来的页面每步付一次上限，而步骤照跑。

### 页面自己做了什么，随答案一起回来

一步是往一个元素上派一个事件；应用为此做的一切都发生在之后。来了又走的 toast 不给收尾快照留下任何东西，没人作答的 `confirm()` 会卡住 frame 的事件循环直到截止，而在控制台背后开出来的窗口没人会去看。所以在这次调用期间——且仅在这期间——座位盯着文档里出现又消失的文字、监听路由变化并比对地址，并给 `confirm`、`alert`、`prompt` 与 `window.open` 各派一个替身。会开新窗口的链接被拦下并同样上报。

这两个替身是本包对同源 frame 的唯一注入，而且放在 `finally` 里还原：一个留着本包的 `confirm` 的 frame，是一个它自己的对话框再也弹不出来的 frame，而产品里没有任何东西会报告这件事。测试对「还原」钉得和对「拦截」一样死。

### 三段，永远是三段，顺序固定

跑了什么、或哪一步让调用停了下来；页面自己做了什么、或一行说它什么都没做；以及一份按部署自己的预算重新读的整页。第三段正是让下一次调用不必再读一遍的东西，因为它点名的 ref 是当下的——一次改动了页面的调用，花费大致等于读它一次，而模型不必付两遍。一段只是有时才出现的东西，会变成模型不再去看的一段，所以「什么都没有」那一行是写出来的，不是省掉的。

某一步失败是返回值，不是异常。模型需要在「哪一步停下了」这同一份答案里拿到页面的新状态，而这恰恰是异常带不了的东西。只有什么都没跑的结局才抛：参数被拒、没有归属会话、没有控制台。既不属于这两类的只有一种——控制台认领了却没了动静：步骤可能全跑完了、跑了一部分、也可能一步没跑，所以它答 `status: 'unverified'`，附上那句「决定重试之前先读一次页面」。

### 不新增会话事件，也不新增字节

调用与结果是 `tool/call` 与 `tool/result`，审批是 `approval/asked` 与 `approval/decided`。拦截器替页面答了什么，写在结果自己的第二段里，所以模型可见的那一半整个可以从日志重建，既不新增词汇，也不触碰 `SESSION_FORMAT_VERSION` 的问题。回放绝不重跑任何一步：结果就在日志里。

回报路由的信封没有变。一份「跑了哪些步骤」的回报带两个页面名字、文档标题、以预算为界的正文、以及一份步骤清单，而完全不花地址、其中两个表头字段、cursor，以及一份列表的失败臂可能占掉的四个名字里的两个——留下 11,968 字节没花。在这份余量里，步骤清单花掉失败那一步的 message，也就是失败臂本来就被界住的那 2000 字符，而解析器只允许一步失败；再加每步约 35 字节的标点。`MAX_ACT_STEPS = 100` 正是把这些标点留在余量之内的那道界，而 `maxSteps` 超过它会在加载时被拒。

## Alternatives considered

**一个动作一个工具。** `content_click`、`content_fill`，诸如此类。因审批而否决：一张表单五个工具就是五次审批请求，而一次读一句的用户看不出自己在同意什么。「把该在一起的步骤放进一次调用」也是唯一一种能让「首个失败即停」有意义的形状。

**只信 ref。** 更简单、更快，而且恰恰在这套东西要服务的那些页面上是错的：一张按筛选重绘的控制台表格，ref 指着的行已经挪了位置。名字核对的代价是每步一次可及名称计算，换来的是把一次点错变成一次拒绝。

**与被托管应用之间的 `postMessage` 协议。** 因为和读取当初否决它同样的理由被否决：那要求每个被托管的应用都实现点什么，而整件事的要点恰恰是 agent 能对着部署方已有的那个应用干活。

**把每一次 DOM 变化都记成页面事件。** 因不可读而否决：重绘一个列表的应用会加进几百个节点，而模型需要知道的是「弹了一个提示」，不是去读应用的渲染流水账。上报的只是出现又消失的文字，每次调用至多八条、每条 200 字符。

**让 `dialogs: 'accept'` 骑在工具本来那道审批上。** 否决：那样一来，对 `content_act` 的长期放行就顺带确认了页面弹出的每一个对话框，而这不是一个同意了「点保存」的用户所同意的事。由被问过的那次调用花掉的那条记录，正是把两次决定分开的东西。

## Consequences

配了 `pageAccess` 的部署现在提供两个工具而不是一个，而第二个会改动用户的页面。三个新 `Config` 字段承载这件事的代价——`actTimeoutMs`、`maxSteps`、`settleMaxMs`——全部在加载时校验，截止时间的算术自足于这一个块内。

审批是 `content_act` 能用的硬依赖，不是软依赖：没有审批服务的组合照样提供这个工具，并拒掉它的每一次调用。这是刻意的，也是内核本来的行为；想要这个工具的部署，就去组合一条审批通道。

`PendingReads` 现在叫 `PendingCalls`，它的单次调用截止时间叫 `answerTimeoutMs`，因为两个工具在同一张表上以不同的截止时间等待。`contentAccess` projection 的状态成了两种请求的联合，`stateVersion` 走到 2。

同一个会话上开着的两个控制台只跑一份步骤，靠的正是那道让两个控制台不会轮流答读取的认领。「删除」不会被这条通道点两次。

## Follow-ups

- 没有手势：没有拖拽、滚动、悬停、文件上传或右键，也没有办法作用在一次读取没有编号过的东西上。
- 沉降等待与 `wait` 步都读 frame 自己的文档，所以往嵌套同源 frame 里画东西的应用，只会被收尾快照读到，不会被等。
- 没有装配级快照覆盖：浏览器侧的证据是一条跑在真实组合上的 Playwright 场景，而快照泳道回放的是出厂组合，那里没有任何 experimental 行。
