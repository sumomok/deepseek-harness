# Agent Note: 一批已放行的页面步骤由谁来定

Status: implemented

[English](2026-09-06-content-act-judged.md) | 中文

## Problem

服务线控制台在每一次工具调用前都挂着 `@haoran/dsh-llm-permission-gateway`，而在[归类那篇](../architecture/2026-09-06-content-tools-review-gate-classification.zh.md)所写的那份部署里，`content_act` 是留给它审查的。瀑布上的两个事实，让这份审查没能落到用户身上。

**审查方判放行，也拦不住本包自己那张卡。** 闸的放行分支返回的是 `next()`（`src/index.ts:541`），而 `next()` 的返回值就是链路余下部分的裁决——cordis 的 waterfall 返回最外层监听器的返回值，`next()` 逐个 shift（`vendor/cordis/src/events.ts:234-243`）。闸以 `prepend: true` 注册（`src/index.ts:509`），所以不论挂载先后它都在队首；本包的监听器裸注册，排在队尾，而它对每一次已放行的调用都返回 `{kind: 'ask'}`。于是一批审查方已经判过安全的步骤，仍旧要摆一张卡到人面前。两道闸判一次调用——这是机制给的，不是配置错的。

**审查方判 ask 时，本包的监听器根本没跑到。** 闸的 ask 分支不调 `next()` 直接返回（`src/index.ts:542`），于是 `approvals.ask(exec.callId)` 从未执行。用户在那张卡上点了同意之后进入工具体，`approvals.confirmed(exec.callId)` 读到 `false`，调用被 `DIALOGS_UNAPPROVED_REFUSAL` 拒掉。**这一半是闸自己的活，正在闸那边为 0.3.0 做**——已发布的 0.2.0 那一版，ask 分支仍旧不委托就返回；做法是让那个分支也委托下去。写在这里，是因为它是本包监听器与审查方对不上的另一个原因，也因为下面那条例外正是让这一侧无论闸修没修都成立的东西。

## Decision

**`pageAccess.actApproval: 'always' | 'judged'`，默认 `always`。** `always` 与这一行一贯的行为逐字节相同：每一次已放行的调用都变成一次请求，用用户自己的话逐条念出每个步骤。`judged` 则把瀑布余下部分的裁决原样返回——下游的 `deny` 仍作为本包自己的裁决返回，其余每一种裁决都原封不动地穿过。

**由你在 2026-09-06 拍板，不是这份 Note 定的。** 由审查方来判 `content_act`、只有危险的页面动作才把卡摆到人面前、这个开关只有两个值而不是三个、写了 `judged` 却没有审查方时必须向失败一侧倒——这四条都是你的裁定。这篇 Note 拥有的是它们被落成什么形状。

**`dialogs: "accept"` 在两种设置下都由本包发问。** 不是因为它更危险，而是因为这里组装出来的那次请求本身就是机制：`DialogApprovals.ask()` 与 `.confirmed()` 成对，把用户读过的那句话和「工具体去回答页面自己弹出的确认框」绑在一起，`src/access/dialog-approvals.ts` 把这条配对写成了模块的契约。`judged` 下若把这条子句交出去，工具体就没有记录可花，页面的对话框会被取消；而若允许上游监听器把这次 `ask` 改写成放行，工具体就会拿到一条谁都没读过那句话的记录。只有一个实例，就写死，不抽象成一张「哪些步骤形状要问」的表。

**`judged` 必须写 `judgedBy`，而查找是每次调用做一遍。** `judged` 是关于组合的一句断言，而本包唯一查得动的只有一个名字：`judgedBy` 是审查方的 cordis 插件名——对已发布的那道闸就是 `llm-permission-gateway`，即它模块导出的 `name`。监听器每次调用都读一遍 `ctx.registry.values()`，只要没有任何 runtime 带着这个名字，就拒掉这批步骤。名字为空、或因为那一行只写了一个光秃秃的 `judgedBy:` 键而缺席时，改在加载时就拒：空串正是 cordis 给每一个内联 `ctx.inject` 回调记下的 runtime 名字，所以拿到空串的守卫会在任何组合里都「找到」审查方。做成每次调用而不是加载时一次，是因为这一行与审查方那一行的挂载先后没有任何东西固定：加载时检查会拒掉一份审查方稍后才到的组合，也会一路放行一份审查方已被卸载的组合。runtime 记录会随它最后一个 fiber 释放而被删（`vendor/cordis/src/fiber.ts`），所以在那里找到的记录背后确有活着的 fiber。这条拒绝不经委托直接返回：会判这次调用的审查方排在本监听器之前，不在其后。这样跳过的不止是它后面那些监听器的裁决——一个同时还要记账的监听器，比如 hook 桥，对这次调用什么都看不到——而这是「不让排在本监听器之后的某个监听器，为一次必须被拒的调用把请求摆到人面前」所付的代价。`Config` 的 JSDoc 直说了：它查的是名字，不是那个插件真的审了什么。

**组合由部署自己写，写在它本来就拥有的那层 overlay 里。** `overlay/content-column.patch.yml` 保持默认，因为部署完全可以在没有任何审查方的情况下组合这一栏。`overlay/permission-gateway.patch.yml` 只在头部注释里补上这条说明，而不是加第二行：patch 是整体替换目标行完整的 `config`（`vendor/include/src/index.ts:121-124`），所以一行指向本包的 patch 就得把 `root`、`pages` 以及那个部署配过的其余一切，在一个对它们一无所知的文件里全部重写一遍。

## Alternatives considered

以下每一条都在拍板之前的调研里量过；一句话，加它输在哪里。

**由闸在这次执行上打标记，走共享 `WeakMap` 或全局 `Symbol`。** `ToolExecution` 没有任何自由字段，两个包又分属两个仓，唯一的路是一条无类型的全局协议——在算代价之前就被「Explicit > implicit at package boundaries」否掉。

**由本包去读闸的 settings namespace。** 机制上可行，代价是把一个私有第三方插件的名字与 settings schema 硬编码进一个将来要并回 `develop` 的包；而且它答的不是被问的问题：`mode: auto` 说的是「审查方在跑」，不是「这一次被判过」。

**给闸新开一张 `judgedTools` 表，用来压住下游的卡。** 它把「谁的卡可以被吃掉」这个判断，交给了不拥有那张卡的一方；而且不靠下面那条改写根本做不成。

**让闸把下游的 `ask` 改写成放行。** 结构性拒绝：它破坏上面那条对话框记录，反转闸自己写下的承诺——放行即委托，只增拒绝、绝不撤销别的插件的——并让「谁能问人」变成注册顺序说了算。

## Decision gate

**0. 已定原则里哪一条替你说了 no？** 没有，而且有两条说 yes。「No hardcoded tunables in plugins」要的正是这个形状：随部署而变的选择，做成可校验的 `Config` 字段。「Explicit > implicit at package boundaries」由「两个字段在加载时解析成一个值」满足，而不是在监听器里 `?? default`。唯一被蹭到的是「Misconfiguration fails loud」，而那道守卫正是把它补上的东西：只答了一半的行在加载时炸，断言不成立则在调用上炸，而不是默默把步骤跑掉。

**1. 碰几个新东西？两个，** 都是同一个既有块上的 `Config` 字段。新工具 0、工具参数 0、路由 0、会话事件 0、projection 0、依赖 0、系统提示词行 0、审批闸 0——这次改动是在一条路径上减掉一张卡，不是加一张。`SESSION_FORMAT_VERSION` 与 `contentAccess` 的 `stateVersion` 都没动，浏览器半边读的那份 settings 文档也没变，因为这是宿主侧的决定，seat 根本看不见。

**2. 能验证它对不对的最小版本。** 就是这两个值，`judged` 的含义是「除对话框子句外一律委托」。控制台上一行 overlay 就能验：浏览页面——点标签页、填搜索框——从每次一张卡变成零张，而审查方拦下来的删除或提交仍旧走到人跟前。

**3. 缝，还是写死？切了一道很窄的缝。** 开关是缝；对话框子句写死。三处近期真会不同的具体东西：控制台线现在就要 `judged`；桌面线组合的是同一道闸但内容区不同，答案不会一样；自动化回放需要第三种答案，而这两个值都不是。对话框子句只有一个实例，就保持一个。

**4. 边界。**

| 方向 | 线 | 它防的具名失败 | 期限 |
|---|---|---|---|
| 邻居 | 本包只拥有一位——问，还是委托——其余归部署。它不读任何审查方的 settings、不引任何审查方的类型，只把审查方当作某一行写下的一个名字 | 一个将来要并回 `develop` 的包，依赖上一个私有的、只以 tarball 形式存在的第三方插件 | 永久 |
| 契约 | 两种设置下 `presentCall` 都渲染完整步骤清单；`dialogs: "accept"` 只对用户读过其请求的那次调用为真；默认值永远是 `always`，所以什么都没写的行照旧发问 | 页面自己的确认框在无人读过那句话的情况下被点掉；新部署因为漏配而静默放开 | 永久 |
| 诱惑 | 把 `actApproval` 长成一张「哪些步骤形状要问」的表——label 关键词、按 action 分档、正则 | 两套互相漂移的启发式，一套在这里一套在审查方；以及「引擎不再加页面语义启发式」那条被从侧面绕过 | 永久 |
| 红线 | 任何监听器都不得把本包的 `ask` 改写成放行；任何跨包通道都不得在类型系统之外携带「已审过」 | 「谁能问人」变成注册顺序说了算 | 永久 |
| 天花板 | `judged` 只承诺把裁决交出去。它不承诺审查方判得对，不承诺卡的次数，而那道守卫证明的是「有一个名字挂着」，不是「有东西被审过」 | 把这个开关读成一条安全性论证；或者为了达成某个卡次指标去调审查方的口味 | 永久 |
| 假设 | `judged` 的价值，成立在「组合里确有一个更靠前的监听器真的在审 `content_act`」这个前提上。守卫查的是这件事最弱的可观测形式——一个名字 | 一份写了 `judged` 的行，静默地把每一次页面动作都跑掉，模型与页面之间空无一物 | 永久；守卫正是让它成为永久的那件东西 |

## Consequences

- 取默认值的部署看不到任何变化：同一张卡、同一句话、同一个顺序。
- `judged` 下，瀑布放行的一批步骤不弹卡就跑；链路上任何位置给出的 `deny` 仍旧拒掉它。两种情况下步骤清单都在调用卡上，因为 `presentCall` 没动。
- 审查方自己的 `ask` 给用户看什么，取决于闸的版本。已发布的 0.2.0 下它在这里什么都不显示，因为那一版的 ask 分支不委托就返回，本监听器根本没跑到。等 0.3.0 那处改动落地，审查方的 `ask` 会以审查方自己的措辞到达用户——除了 `dialogs: "accept"` 那一支，那里由例外换成这里组装的那句话，也正是那条记录所对应的那句话。
- `judged` 而审查方不在时，`content_act` 的每一次调用都被拒。这是设计中的失败，并且在模型自己的记录里是响的。
- 在控制台的「完全放开」预设下，审查方的 `ask` 仍旧在任何 answerer 跑起来之前被自动判拒：`ApprovalService.decide()` 在派发之前就把 `never` 判成 `'rejected'`（`packages/interaction/user-approval/src/index.ts` 的 `decide()`），那里的注释也写明了为什么任何监听器形态的闸都插不到它前面。`judged` 够不着这一格；同样理由，那个预设下的 `dialogs: "accept"` 也是拒。控制台最终发哪几个预设、那一个是否还保留 `approval: never`，是你在单独定的另一个问题。
- 闸 0.3.0 的那处改动——ask 分支也委托——才是让审查方的 `ask` 能走到本监听器的前提。在它落地之前，`judged` 部署里凡是审查方判 ask 的 `dialogs: "accept"` 调用，都会被工具体拒掉。那条例外无论如何都是对的；另一半在闸那边修。

## Testing

`packages/experimental/content-frame/tests/content-act-tool.client.spec.ts` 每一条分支都经由真的工具注册表驱动，而不是对监听器做断言：`always` 发问（原本就有的那些用例）；`judged` 配普通步骤时返回瀑布的放行、且不写对话框记录；下游的 `deny` 与下游的 `ask` 各自原样穿过；`dialogs: "accept"` 仍用本包的措辞发问、且调用成功——成功本身就是那条记录写进去了；审查方缺席时拒掉调用且不留记录；读不懂的参数与超过 `maxSteps` 的调用仍旧走到工具自己的拒绝话术。用例里的审查方是一个真的、以那个名字挂着的 cordis 插件，并像部署里的那个一样以 `prepend: true` 注册；还有一例在组合运行中途把它卸掉——那正是每次调用查一遍的理由。那条拒绝话术与其余每一句一起，被 `tests/self-contained-copy.client.spec.ts` 走了一遍。`tests/content-read-routes.client.spec.ts` 把两条加载期失败与那对能起来的组合都钉住。逐文件覆盖率保持 100%。

那道守卫是用「拆掉它」证明的：跳过注册表检查后，审查方缺席那一例失败，调用走到了工具体，并因为「没有控制台」而不是「没有审查方」被拒——这正是它要堵的那个失败。

**没有新增快照场景，理由是这个仓库跑不了一个。** 语料要的是经由真实可运行示例的无密钥回放，而 `judged` 只有在 `tools/pre-execute` 上确有一个审查方时才有意义；本仓库里没有任何插件是审查方，而已发布的那一道闸是仓外的、只以 tarball 存在的插件，web 场景装不上。要搭出这份组合，意味着：一个新的、会放行每一次调用的 test-support 发布包；第二份把第一份整体重写一遍的 column overlay（脚手架只收一层 patch）；`content-act` 场景 spec 的第二份拷贝；以及一次需要密钥的录制——换来的却是一份与已录制的 `content-act` 场景唯一差别只在「少了一次审批往返」的记录，而对面那个审查方什么也不审。默认路径没动，所以六个已录制的 web 场景逐字节照回。真正证明部署那一半的是控制台现场，做法与[归类那篇](../architecture/2026-09-06-content-tools-review-gate-classification.zh.md)为闸记下的一样。
