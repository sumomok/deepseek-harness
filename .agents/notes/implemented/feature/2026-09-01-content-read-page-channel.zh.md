# Agent Note: content_read 与它背后的浏览器通道

Status: implemented

[English](2026-09-01-content-read-page-channel.md) | 中文

## Problem

内容区把一个页面推到用户眼前，而推它上去的 agent 看不见它。它对那个页面知道的一切都来自部署方自己的配置——一个 id、一个标题、一行描述——因此一段关于「用户正在看什么」的对话跑在 agent 的想象上。让用户描述屏幕是这种缺席逼出来的变通，而这恰恰是坐在屏幕旁边的 agent 最不该做的事。

读取页面不是宿主的能力。文档活在某个人浏览器里的一个 iframe 中，由真实引擎带着真实布局渲染，而宿主既没有那份 DOM，也没有办法指名持有它的那个浏览器。回答这个问题的东西必须跑在 page 座位里，并把答案送回一次仍在等待的工具调用中。

## Decision

`content_read` 是一个工具体不做任何计算的工具。它校验参数，以 `exec.callId` 为键登记一次等待，并把这次调用发布到该会话自己的 `contentAccess` projection 上。正在展示该会话的 page 座位通过 `POST /content-frame/claim` 认领这次调用，用 `src/client/access/` 里已有的结构化读取器遍历 frame 的文档，再把列表 `POST /content-frame/report` 回来，结算那次等待。因此模型关于一个页面被告知的一切，都来自一个真的在看着它的浏览器。

整个切片就是 `Config.pageAccess`，而缺席是默认：没有工具、没有路由、没有 projection 单元、settings 文档里没有 `pageAccess` 字段、浏览器里也不安装读取器。只展示页面的部署不必为一项没要过的能力付账；开关是一个块而不是每块拼图一个标志位，因为这些拼图分开毫无用处。

### 两个阶段，而不是一个

一次读取要等两次。`claimTimeoutMs` 界定第一阶段，答的是「没有控制台在展示这个会话的内容区」；`readTimeoutMs` 界定第二阶段，答的是「控制台认领了这次读取却没有回报」。这个区分正是「认领」这次往返存在的全部理由：模型的下一步不同——打开一个控制台，还是重试一次——而单一截止时间会把两者压成一个无从行动的超时。

两道截止时间都属于宿主，座位两道都拿得到，才待得进去。它重新出价的上限用的是认领窗而不是回报截止时间，因为调用真正等在里面的正是那道窗；它在还没加载完的页面上最多花掉回报截止时间的一半，因为宿主从授予认领那一刻就开始计时。没有这个份额，「页面还没加载完」这句话就永远到不了模型面前——每一次都是宿主先应答。在这些界限之内，没能送达的认领或回报会再试一次而不是就此放弃：否则用户眼前摆着控制台，却由一次丢包去告诉模型这里没有控制台。

### 同一会话的读取黏在同一个标签页上

ref（`e12`）指的是某一个浏览器里某一份文档中的元素。同一会话上开着两个控制台、轮流应答读取，会把在下一次读取抵达的那份文档里指不到任何东西的 ref 交给模型。因此这张表把上次应答的标签页钉住 `pinMs`，并把别的标签页的认领挂起固定的 250 毫秒，好让被钉住的那个先拿——足够让一个活着的控制台赢下这场竞速，短到一个已关闭的控制台只花掉四分之一秒。

### callId 就是那把能力钥匙

两条路由带着外壳 `/api` 用的同一道 `sec-fetch-site` 与 `application/json` 栅栏，没有 Host 白名单，因为 webserver 本来就没有，而 `trustedHosts` 只守 `/api`。顶替它位置的是 callId：认领或应答一次读取，都需要一个由宿主铸出、且只发布进该会话自己 projection 流里的 id，而针对未知 id 的认领与回报什么都不改变。这与 `show_chart` 的回报路由所依赖的论证同构，后果更大——页面文本会进入模型——结论相同，因为这个 id 猜不出来，而错误的 id 是惰性的。

这条论证底下的前提，因为没有任何东西强制它，所以写在这里：熵是 LLM 供应商的，不是本包的。DeepSeek 的 callId 是 `call_00_` 加 24 位字母数字（末四位为数字），`code-mode` 的子调用是同一个 id 再加 `:code:<n>`，两者都约合 130 bit。本包既不检查这个格式，也不为它增加任何东西。换一家把调用编成 `call_1`、`call_2` 的供应商，这两条路由就成了任何能打到宿主的页面都能用的通道：其中一半——先认领、再回报一份伪造的列表——就能把攻击者选定的文本摆到模型面前。跑在不可信网络上的部署无论如何都要在反向代理上设栅栏，但换供应商的部署要检查的正是这一条。

### 被拒绝的 body 不是被读过的 body

两条路由都把 POST 上来的 body 卡在一道字节界上——认领是 1 KB，回报是座位自己的渲染预算按每字符四个 UTF-8 字节再加一层 JSON 信封——而这道界是对到达的分块做累计，不是对声明的 `content-length` 做检查。只看头部就拒绝，路由里一个字节没读，进程里却读了全部：响应结束时，node 会把没人消费过的 body 从线路上全部排空丢弃，于是一个因为过大而被拒的请求照样要付它自己的大小。读到界上就停、并随拒绝关闭连接，才能把一次 8 MB 的 POST 压到套接字里已经缓冲的那点——本机回环上是 131,072 字节，而同一个请求被排空时是 8,388,742 字节。代价是：仍在写入若干 MB 的客户端可能抢不到自己那份拒绝；而真实座位可能产出的 body 只超界几 KB，收得到。

这份拒绝是 413，而不是格式错误或形状不对的 body 收到的 400，因为二者是不同的错：一个 body 从未被读过，另一个被读完了、只是不是这条路由要的那份文档。

### 每一种结局都是一句话，每一次失败都抛出

这个工具只为一种结局返回值：一份列表。其余全部——没有控制台、没有应答、内容区为空、在前面的是别的 kind、失效的 ref、读不到的 frame、登录表单——都抛出，并带一句写明下一步的话。失败文本是模型在决定下一步时唯一会读的工具文本，因此一个以 `status: 'empty'` 形式返回的结局会被读过去而不被处理。登录这一种最尖锐：列表存在，但被扣住不发，因为密码表单是 agent 把键盘交还回去的地方，而不是绕着叙述的地方。

### 读取器住在 page 座位里

`content.surface.kind` 是 root 作用域，因此框架不给它 `useProjection`，也不给会话 id；这个座位从每个 root 槽都能拿到的会话列表快照上读自己会话的值（`useSessions(state => state.byId[id]?.projectionValues?…)`），与这一栏自己的路由器已有的做法一样。但这个座位仍是唯一可能的位置：它是唯一持有 iframe 元素的组件，而没有元素的读取就是没有文档的读取。它同时持有每个 frame 的 ref 编号，并在该 frame 的 `load` 时作废它，因为一个 ref 指的是刚刚离开的那份文档里的元素。

## Alternatives considered

**转发 cordis 事件，像 `cordis/inspect-query` 那样向浏览器提问。** 这套机制在形状上比 HTTP 更贴合这个问题——宿主 emit，浏览器通过 Typert `@Remote` 应答，第一个有效答案获胜，且校验归属。它是因归属而非优劣被否决的：转发事件白名单是 `@deepseek-ai/dsh-api-remotes` 里的一个字面数组，加一项就意味着改一个本 fork 不修改的上游包。HTTP 通道完全在本包内部，代价是两条路由。

**只用一道截止时间。** 表更简单，一个计时器，一句拒绝。否决的理由是这两种失败并非同一条指示：没有控制台打开的会话需要用户去打开一个，而失联的控制台需要重试。把它们压在一起产生的是一句模型只能靠猜的话。

**谁先认领谁应答，不设首选标签页。** 否决的理由是：同一会话上一旦开着两个控制台，ref 就不再意味着任何东西——模型会从一份文档读到 `e12`，却在另一份文档里指着它。这个钉住机制最多每次读取多挂起一次认领，而且只在未被钉住的标签页先出价时才发生。

**把失败作为普通返回值。** 一个 `{ status: 'empty' }` 的值让这个工具永不「失败」，也让模型可以按判别式分支。否决的理由是：模型不会按一个没人告诉过它的判别式分支，而真正改变下一次调用的是那句失败文本——它点名 `content_show`，或点名该去掉的那个参数。这正是 cookbook 那条「在失败文本里点名能修复它的参数」的规则。

**把读取器放进 `shell.overlay` 而不是 page 座位。** 一个全局 overlay 行始终挂载，且与这一栏展示什么无关。否决的理由是它够不到 iframe 元素，除非走 `document.querySelector`，那会把读取器耦合到座位的 DOM 属性而不是它自己的状态，并让按 frame 分的 ref 表无处安放。

**在浏览器里拼好整句模型可见的话。** 座位知道一次读取为什么失败，所以它可以直接发送成品文本。为宿主能说得更好的那两种情况否决：内容区为空与在前面的不是页面，都是关于会话的事实，它们的句子点名 `content_show`——那是宿主自己的工具。座位为这两种只发一句简短原因，只有 frame 失败才发成品句子，因为那是没有任何宿主能描述的一种。

## Consequences

agent 能读到它推到用户眼前的那个页面，每次读取以 `outlineChars` 为界，每次调用受两道截止时间约束。不想要这一切的部署什么都不写，也就什么都不会得到。

这条通道是把浏览器依赖放进了工具结果里。没有控制台打开时、标签页不可见时、控制台停在另一个会话上时，一次读取都没有答案——这三种情况都被明说而不是近似，但没有一种能从宿主侧绕开，而 headless 组合永远无法成功调用这个工具。这是正确的行为，也是这个工具适用范围上一条真实的限制。

`content-frame` 现在为聊天行的槽声明依赖 `@deepseek-ai/dsh-client-ui-tool`——只是一个类型导入，但它是一条此前不存在的清单与 tsconfig 边。

浏览器车道是唯一能演练真实路径的地方：jsdom 没有布局，也永远不会加载指向真实路由的 frame，因此本包自己的测试读的是手工挂载的文档，而 `apps/web/tests/content-read.e2e.ts` 覆盖装配起来的组合。

结构化读取器本身未被这次改动触及。它的拒绝文案逐字传到模型，因此改动那里的措辞就是改动模型读到的东西，而本切片里没有任何测试钉住它。
