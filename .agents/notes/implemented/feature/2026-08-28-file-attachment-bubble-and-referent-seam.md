# Agent Note: file-part bubble rendering and the `referent/open` seam

Status: implemented

English | [中文](2026-08-28-file-attachment-bubble-and-referent-seam.zh.md)

## Problem

Prior commits in this series got a text file onto the wire, into the session log as `{kind:'file', attachment: FileAttachmentRef}`, into request materialization, and into the composer as a first-class draft attachment — but a sent file part still renders nowhere in the message bubble, and there is no way for a plugin to intercept a click on a file/dir reference the way it can intercept nothing today: `apply.ts`'s injected `openFile` closure always asks the Host to open the path directly. Both gaps block the same use case: a plugin that wants to preview a referenced file, dir, or URL inline instead of shelling out to the Host/OS opener has no seam to hook, and a user has no way to see or re-open the text they just sent.

## Decision

**A direct, inline `FileCard`, not a new slot architecture.** `MessageItem.tsx`'s content-part walk (for user bubbles) and `AssistantMarkdown.tsx`'s block switch (for Assistant blocks) each render a `{kind:'file'}` part as `packages/client/ui-conversation/src/client/chat/FileCard.tsx` directly, mirroring `renderMessageImages`'s call site placement but not its slot indirection. The existing image gallery is a slot because it is a swappable *presentation* extension point (`ui-attachment` owns the renderer); nothing in this series asked for that pluggability for the file card, and a slot would have added a new `RenderMessageFiles` type, a new `ui-attachment` component, and a new `apply.ts` registration for no requested benefit.

**The `referent/open` seam** (`packages/client/runtime/src/client/referent.ts`): one ROOT-scope cordis waterfall event, declaration-merged into `Events`, dispatched through `dispatchReferentOpen(ctx, ref, onDefault)`. `ReferentRef` carries a reference only — `kind` (merge-extensible via `ReferentKindMap`, seeded `file`/`dir`/`url`), `target`, `raw`, optional `attachment`/`sessionId`, `source`, `provenance` (`'structured' | 'model-text' | 'tool-output' | 'user-text'`) — never content. A listener claims a click by returning without calling `next()`; calling `next()` (or throwing/rejecting, which is caught, logged, and treated as an implicit `next()`) delegates onward, terminating at the caller's default. Dispatch sites are user-gesture handlers only, by design and by test — never automatic delivery — since a claim is trusted to run side effects.

**Wired at the one existing chokepoint.** `apply.ts`'s `openFile` closure (`packages/client/ui-conversation/src/client/apply.ts`) now dispatches `referent/open` first (`kind: path === '.' ? 'dir' : 'file'`, reusing `ChatView.tsx`'s existing `isFolderOpenPath`-style heuristic since no richer file/dir signal reaches this closure; `provenance: 'structured'`; `source: 'chat-view.openFile'`), with the existing `workspaces.openPath(target)` call as the waterfall's terminus. This makes produced-file chips, Tool rows, and mentions interceptable in one move with zero behavior change when no listener is registered — proved by re-running the pre-existing `apply-inject.client.spec.tsx` suite unchanged (11/11 pass, including both the success- and failure-propagation paths). `FileCard`'s own click dispatches the same seam independently (`kind: 'file'`, `source: 'message-file-card'`, carrying the block's `FileAttachmentRef`), falling back to its own default: toggle an inline expand/collapse viewer.

**`loadFile`/`ISession.readFile` mirror `loadImage`/`ISession.readAttachment`.** `packages/client/ui-conversation/src/client/service.ts` gained `resolveFile(sessionId, attachment)`, caching the pending/settled text per `${sessionId}:${attachmentId}` and clearing on session-scope release, structurally identical to `resolveImage`'s cache. `readFile` on `ISession`/`Session` mirrors `readAttachment`, returning `{attachment, text}` (plain UTF-8, no base64 — the file already carries this shape end to end). `FileCard` fetches lazily on first expand only and never re-fetches on a later collapse/expand of the same mount.

**Subagent continuation blocks a file part the same way it blocks an image.** `Session.prompt()` (`packages/client/runtime/src/client/sessions/session.ts`) previously silently dropped a `'file'` content part reaching a continuable subagent (the `flatMap` only keeps `'text'`), unlike the loud `SUBAGENT_IMAGE_UNSUPPORTED` rejection an image part gets. Silent content loss on send violates the "model-visible ⟺ logged" invariant this repo enforces elsewhere and the general symmetry convention. A file part now gets the same treatment: rejected before any transport call with `{code: 'attachment-error', details: {reason: 'SUBAGENT_FILE_UNSUPPORTED'}}`, mapped to `file.subagentUnsupported` product copy in `attachment-labels.ts`, mirroring `image.subagentUnsupported` exactly.

## Alternatives considered

**A boolean `ran` guard in `dispatchReferentOpen`.** Rejected after a real, pre-existing test failure exposed the bug: `let ran = false; guardedDefault = async () => { if (ran) return; ran = true; await onDefault() }` cannot distinguish "the default already ran and is now the thing failing" from "a listener threw before ever delegating." With zero listeners registered, `apply-inject.client.spec.tsx`'s `'openFile rejects when the Host cannot open the path'` test mocks `workspaces.openPath` to reject; the rejection propagates into the catch block, which then calls `guardedDefault()` again — a silent no-op since `ran` was already `true` — so `dispatchReferentOpen` resolved to `undefined` instead of propagating the real failure. Replaced with a memoized `settled: Promise<void> | undefined`: `guardedDefault = () => { settled ??= Promise.resolve().then(onDefault); return settled }`; the catch block re-awaits and re-throws `settled` when it is already set (a genuine default failure) and only falls back fresh when a listener threw before ever delegating.

**A slot for the file card's presentation.** Rejected: no requirement in this series asked for a swappable file-card renderer, and the existing image slot exists specifically because `ui-attachment` owns that presentation independently — adding one here would be unrequested architecture for a card whose current design (name + size + inline expand) has exactly one implementation.

**A richer file/dir signal at the `openFile` wrap point.** Rejected: `apply.ts`'s closure receives only a `path: string`; inventing a new signal to distinguish file from dir more precisely than the existing `path === '.'` heuristic (already used by `ChatView.tsx` for the same purpose) was out of scope for this seam and would touch call sites this series does not otherwise need to change.

## Consequences

`packages/extensions/cordis-client-runner/src/client/{api-catalog.ts,slot-catalog.ts}` (generated) picked up `ISession.readFile`, the widened `AssistantBlock`, and `ChatNodeOwnerProps.{loadFile,openReferent}` via `pnpm run gen-client-catalog -- --write` / `pnpm run gen-cordis-inspect-catalog`. Six existing test files (`chat-branch-tails`, `attachment-labels`, `chat-view`, `coverage-tails`, `gate-branch-tails`, `reasoning-row` — all `ui-conversation` — plus `ui-workflow-run`'s `workflow-run.client.spec.tsx`) needed a mechanical `loadFile`/`openReferent` stub addition to satisfy the newly required `ChatNodeOwnerProps`/`AssistantMarkdownProps` fields.

**Coverage exemption, verified empirically rather than assumed.** `packages/client/ui-conversation/src/client/*`'s exclude glob, and `packages/client/runtime/src/**/!(settings-scope).ts`'s, and `packages/client/ui-trajectory/src/*`'s, exempt their **entire nested subtree** from the 100%-per-file coverage gate in this vitest version, not only direct children of the named directory — confirmed by running scoped `vitest run --coverage` and observing zero coverage rows for deeply-nested, heavily-exercised files (e.g. `skeleton/InputBar.tsx`, `contract/slots.ts`, `chat/FileCard.tsx`), even isolated to a single test file that indisputably imports and exercises them. This differs from an assumption recorded in the prior commit's own Agent Note and ledger entry, which is left uncorrected here (out of scope for this commit; noted for the record). Practically: every `ui-conversation`, `ui-trajectory`, and `runtime` file this commit touches is exempt, so none needed dedicated coverage-closing work; `packages/test-support/client-runtime/src/sessions.ts` is **not** exempt and did need one (`readFile`'s fail-loud stub throw was uncovered until `runtime.client.spec.tsx` gained a matching assertion, mirroring the existing `readAttachment` one).

`packages/client/runtime/tests/referent.client.spec.ts` (10 tests: default-runs, claim-suppresses, next()-delegates, registration order, prepend, `ctx.effect` disposer, throw/reject-falls-back-and-logs (both), no-double-run-after-successful-delegation, unrecognized-kind documented no-op) and `packages/client/ui-conversation/tests/file-card.client.spec.tsx` (6 tests: default expand + lazy fetch, loading state, error state, collapse without re-fetch, a claiming listener suppresses the default entirely, the dispatched `ReferentRef` shape) are new. `packages/client/runtime/tests/session.client.spec.ts` gained one test covering both the pre-existing (previously untested at this layer) image block and the new file block for a continuable subagent.

## Retirement

This bubble-rendering and referent-interception layer is a temporary overlay for capabilities upstream does not have yet: if upstream's own conversation UI renders a file content part natively and exposes an equivalent open/reference-interception seam, this patch is retired and the fork adapts to upstream's form.
