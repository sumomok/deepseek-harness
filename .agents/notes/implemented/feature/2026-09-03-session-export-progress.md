# Agent Note: Session export progress read from the archive stream

Status: implemented

English | [中文](2026-09-03-session-export-progress.zh.md)

## Problem

`dsh-session-log-export` handed the export URL to the browser and immediately told the user the download had started. The claim was unverified and, in the desktop shell, often untrue in the way that matters: the page had no idea whether a byte had moved, how much was left, or whether the transfer had failed. The route streams the archive with `Transfer-Encoding: chunked` and no `Content-Length`, so even a browser that owned the transfer had nothing to draw a bar from. Failures were worse than invisible. The Host answers `200` and only then errors the stream when a descendant log or an attachment cannot be read, and the package README delegated that report to "the browser download manager" — a surface the DSH Desktop shell does not have, since it registers no `will-download` handler on the main window and shows no download UI of its own. A torn archive therefore reached the user as a success toast.

## Decision

The Host announces the archive's extent before its bytes, and the page performs the transfer itself.

`measureSessionLogZip` in [`src/archive.ts`](../../../../packages/session-query/session-log-export/src/archive.ts) walks the export once before streaming and returns `{ entries, bytes, estimatedWireBytes }`: the ZIP entry count, the summed uncompressed size, and an estimate of the bytes the response body will carry. Log sizes are the exact UTF-8 length of the canonical JSONL the stream will push; media sizes are each `ImageAttachmentRef`'s recorded `bytes`, so measuring re-reads each descendant log but never re-reads a stored image. The measurement and the entry stream share one traversal, `sessionLogTextEntries`, so the two cannot disagree about what an export contains. The wire estimate scales the log entries by a calibrated 0.14 — real session JSONL deflates into the 0.13-0.15 band — takes media at face value because PNG and JPEG do not deflate further, and is exact at `compressionLevel: 0`, where the archive stores. The route sends all three as `X-Session-Export-Entries`, `X-Session-Export-Bytes` and `X-Session-Export-Estimated-Wire-Bytes` on both `GET` and `HEAD`; the page and the route share one origin, so no CORS exposure list is involved. A measurement failure drops the three fields and nothing else: every failure the measurement can reach — a missing descendant log, an unreadable handle, a lineage error — is reached again by the streaming pass, which owns the outcome and still errors the stream rather than shipping a truncated archive.

The browser half `GET`s the route through `fetch` and reads `response.body` chunk by chunk. [`src/client/progress.ts`](../../../../packages/session-query/session-log-export/src/client/progress.ts) is the pure model: it accumulates received bytes and counts ZIP local file header signatures (`50 4B 03 04`) across chunk boundaries, carrying three bytes between chunks so a split signature still matches. Both measures are lower bounds and the reported fraction is the larger of them, clamped below 1 while streaming. Received bytes are divided by the wire estimate, not by the uncompressed total: the seeded fixtures compress 7.6-fold, so dividing 103 KB of wire by 780 KB of log crawls to an eighth and then snaps, which the real app showed reads as a stalled transfer rather than a progressing one. The entry count raises the estimate off its floor when an archive compresses harder than the calibration; an entry counts as finished only when the next entry's header arrives, since a header precedes its own data, and the count is capped at the announced total, so a chance signature inside compressed data moves the bar at most one entry early and never past the end.

The estimate is what carries the single-entry archive a Session with no sub-Sessions and no attachments exports — every seeded fixture here, and the case where the entry count has no resolution at all. Being calibrated rather than exact, it has two visible failure modes, both of which still read as progress: an archive that compresses harder reaches the 0.99 ceiling before the stream ends and waits there, and one that compresses softer completes from around four fifths. Without the headers the fraction is `null` and the bar is indeterminate, which is also what an older Host produces.

When the stream ends the controller assembles the chunks into a `Blob`, clicks a detached anchor at its object URL with the filename read from `Content-Disposition`, and revokes the URL one task later; `Content-Disposition` is read as RFC 5987 `filename*` first and the plain parameter second. The download store is frame-batched, so an archive of many chunks repaints the panel once per animation frame rather than once per chunk. The panel gained the bar, an `Exported <size>` line naming what has arrived, a completion state, and a failure state that names the HTTP status and the Host's message when the route refuses before streaming, or the browser's transport error when the connection fails or the archive tears mid-stream. A Host cannot describe a failure after its response has begun, so a torn archive reaches the page as `network error`: the panel reports that the export tore, which is what the toast never did, not why. Its footer action cancels the transfer while it runs — aborting the `fetch` and returning the Session to idle — and closes the panel once it has settled; the header close control still dismisses without cancelling, so an export the user stops watching still completes and still saves. The `HEAD` preflight is gone: `fetch` resolves on headers, so `response.ok` catches every pre-stream failure the preflight caught, and the body read now catches the mid-stream failures it could not.

This is a core patch because the export UI and the export route are the same upstream plugin. A fork plugin can add a route or a slot occupant, but it cannot replace the client half of `session-log-download` while leaving its Host half mounted: the progress bar needs the extent the route computes, and the route is where the archive is walked.

## Alternatives considered

**Shell-side progress from Electron's `DownloadItem`.** The desktop main process can observe `will-download` and report `receivedBytes`/`totalBytes` per item. It needs a new shell-to-page channel to get those numbers into the React tree, it leaves the browser build with no progress at all, and it still cannot surface a mid-stream failure where the export lives — a torn stream reaches `DownloadItem` as an interrupted download in a shell UI the page cannot see. The page already holds the response; reading it there costs no new channel and serves every build.

**A second endpoint that reports progress for a one-shot download.** A server-sent progress channel keyed by an export id would let the anchor navigation stay. It adds an endpoint, a per-export server-side identity, and a lifetime for that state, all to describe a transfer the page could simply perform. It also cannot report a failure that happens inside the download the page does not own.

**A STORE-only archive so the byte total is exact.** With compression off, received bytes equal the announced uncompressed total and the fraction needs no second measure. It makes every export substantially larger for a bar that is already accurate enough once the entry measure covers the compressible case, and it would override a configured `compressionLevel` for a presentational reason.

**Announcing the compressed total, by compressing the whole archive into a counter before streaming it.** This is the only way to a percentage that is exact for every archive, single-entry ones included, and it would delete the entry measure entirely. It costs a second full pass — every log read and deflated twice, and every stored image read and deflated twice, since media entries count toward the wire total — so an export's whole cost lands before its first byte. At the observed sizes that is milliseconds, but it turns time-to-first-byte into a function of total archive size for every deployment, and the package exists to stream without ever holding or redoing the archive.

**Reporting the entry count in the panel.** `Exported 0/1 entries` is what a single-entry archive shows for its whole transfer, and that is the common Session. The count survives as the fraction's lower bound, where it earns its keep without claiming to describe the transfer.

**Deriving the total from `Content-Length` instead of custom fields.** The archive is produced incrementally and its compressed length is unknown when the headers are sent; buffering it on the Host to learn that length would give up the bounded-memory streaming the package was built around.

## Consequences

The page holds the whole archive in memory as a `Blob` before saving it, and briefly holds it twice while the chunk list and the `Blob` coexist, so an export is bounded by the tab's memory rather than free disk space. Session archives are megabyte-scale in practice — the largest seeded fixture here is 103 KB — and a multi-gigabyte tree is now out of reach. The Host's own streaming stays bounded: it never buffers the archive, and the browser is the only side that accumulates.

Every export now costs one extra read pass over the descendant logs before its first byte, and each live descendant is flushed twice — once before the measurement reads it, once before the stream reads it. The second barrier has nothing left to make durable. Time-to-first-byte therefore grows with the number of sub-Sessions; an export with none costs one extra `traceSession` call and no extra log read at all, because the root log is read once by the route and shared by both passes.

The saved file arrives from a `blob:` URL on the app's own origin rather than from an HTTP navigation. Chromium saves it as it saved the navigation download, which the browser build's own end-to-end run asserts. The Electron shell lives on the `develop` line, outside this tree: there `will-download` is registered only on the login and headless-render windows, both of which cancel, so the main window falls to Electron's default download flow for either URL form.

Package tests pin the model and both halves: `progress.client.spec.ts` covers the header parsing, the wire-scaled single-entry archive, the split-signature count, the cap, monotonicity and the 0.99 ceiling; `controller.client.spec.ts` drives a mocked `fetch` returning a chunked `ReadableStream` and asserts the progress sequence, the assembled `Blob`, both `Content-Disposition` filename forms, and the HTTP, transport, missing-body, mid-stream and cancellation paths; `archive.host.spec.ts` asserts the announced totals equal the archive's real entry count and uncompressed sizes for a tree with a child session and two attachments, that the estimate is exact at level 0, and that the fields are absent when measurement fails. The assembled application is covered in this tree by `apps/web/tests/navigation-panes.e2e.ts`, updated with this change: it drives the Session Header button against the real route, asserts the `GET` carries the three extent fields, and unzips the archive the page saved.

Retire when upstream lands the equivalent: an export whose progress and failures are visible in the page.
