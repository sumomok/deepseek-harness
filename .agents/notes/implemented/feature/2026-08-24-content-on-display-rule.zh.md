# Agent Note：让后续请求落到已经展示出来的那份内容上

Status: implemented

[English](2026-08-24-content-on-display-rule.md) | 中文

## Problem

一位用户面对屏幕上的图表，引用了它的标题，要求在折线旁再加一条柱状序列。模型另铸了一个图表 id，在用户所指的那张图旁边又画了一张。[`show_chart` 的 Agent Note](2026-08-24-show-chart-supersede-and-inspection.zh.md) 记录了这个发现和第一层修复：`id` 参数描述现在点出了触发条件，而不再只是提供复用这一选项。

那次修复只覆盖一个工具。这个失败并不属于图表——它属于内容 surface 路由的每一个生产者。一个页面若以新身份重新展示，同样会多开一条 content 栏 entry；下一个 kind 到来时也会带着同样的缺口。参数描述也不是陈述「对所有工具都成立的事」的地方：它是在模型已经决定调用某工具、正在挑参数时被读到的，而对一个还在判断「这到底是不是一份新内容」的模型完全不可见。

## Decision

分两层，因为实测结论就是两层。参数从句原封不动保留，同一条规则的另一份、与 kind 无关的表述由 `dsh-experimental-content-surface` 注册为一个系统提示词 section——这一行本来就拥有「内容条目」这个与工具无关的概念。

section 文本不指名图表、页面、工具或参数：

```markdown
# Working with content already on display

When the user refers to something you have already produced and put on display — quoting it, naming its title, or otherwise pointing at it — and asks for a change, update that same piece of content in place through the tool that produced it, reusing its identity, rather than producing a new one beside it.
```

日后注册的 kind 无需改动此处即可继承它，而各工具的 schema 继续各自交代自己哪个参数承载身份。

### 实测了什么

对那次失败的会话做日志重放，每个候选修复一条臂，每臂十个样本。每个样本的判定是机械的：响应是否复用了用户所引用那张图的 `id: "gold-7d"`，还是另铸了一个？

| 臂 | 复用了该 id |
| --- | --- |
| 修复前 | 1/10 |
| 仅 `id` 描述从句 | 5/10 |
| 仅通用规则，置于系统提示词末尾，零图表词汇 | 8/10 |
| 双层 | 10/10 |

由此得出三点。通用规则单独作用胜过参数从句单独作用，因此看上去更省的单层方案恰恰是更弱的那个。两者并不冗余——合在一起补上的缺口，任何一方单独都补不上。而 8/10 那一臂是把规则放在提示词**末尾**测的，这使位置成为被实测内容的一部分，而不是搭臂时的偶然细节。

### section 落在哪里

`content:on-display`，order 为 `200`，位于文档记载的 `100–199` 工具指引区间之后。这条规则是对照各工具刚说过的参数说明被读到的，因此它该排在全部工具之后；而今天整个仓库里没有任何 section 取更高的 order——最高是 `190`。Web e2e 会对着真实组合断言组装出的这段尾巴，而不是相信这套算术。

core 的区间文档不动。一个实验性行取用了区间之后的第一个 order，还不足以成为值得写进 `dsh-system-prompt` 的约定。

### 可选，且无条件

section 通过 `ctx.inject(['systemPrompt'], …)` 注册，与它旁边的 projection 子节点一致：没有提示词注册表的组合保留 extractor 表、不贡献任何指引。没有系统提示词并不是本行的配置错误——那是一个里面根本没有模型的组合——而改为必选会让 `ctx.contentSurface` 本身对本包早已支持的「只有 projection」的装配不可用。

它不查阅 extractor 表。这条规则描述的是用户在做什么，而不是某个 kind 能画什么，因此以「已注册某个 kind」为闸会把一个模型可见的提示词绑到热加载时机上——本 registry 在表每次变化时都重新注册，而 kind 行可能在会话中途到来——换来的却是任何真实组合都省不到的字数，因为这个路由器从来不会在没有 kind 的情况下被组合。

### 不新增任何记录

「模型可见 ⟺ 已记录」本来就已满足。组装出的系统提示词经由唯一的渲染路径抵达模型，并被记录在已路由的请求 header 里，那正是重放与 `ctx.tokenMeter` 所读的东西；一个提示词 section 无需自己的会话事件即可从日志重建。本包依然不追加任何会话事件。

## Alternatives considered

**只把规则留在 `id` 描述里。** 这就是已经发布过的那一臂：5/10，而且它无法为尚不存在的 kind 一次说清。

**只发通用规则，去掉参数从句。** 8/10 对双层的 10/10。何况那条从句还做了通用规则做不到的事：它交代了那个具体工具的哪个参数承载身份。

**把 section 放进 `vue2-echarts-tool-poc`。** 否决：那样一个工具就拥有了一条关于所有工具的规则，而第二个内容工具要么重复它——同名 section 会抛错——要么与它矛盾。surface 才拥有那个与 kind 无关的概念，这也正是这条规则能不带图表词汇写出来的原因。

**放进 `dsh-system-prompt` 或部署 persona。** 否决：没有内容 surface 的组合什么也没展示，却要为一条无所指的规则付账。这些字应由制造出这种局面的那一行来欠。

**以「至少注册了一个 extractor」为闸。** 上文已否决：热加载时机会变得模型可见，换来的节省没有任何部署能兑现。

**取 `100–199` 区间内的 order。** 否决：被实测的那一臂把规则放在末尾，而区间内的任何取值都会让它与工具指引争夺最后一位，胜负由注册顺序决定——`dsh-system-prompt` 自己已把这一点列为已知限制的插件加载产物。

**在 core 里预留一个记入文档的「末位」区间。** 暂时否决：一个消费者还构不成约定，实验性行也不该为了给自己安座位而挪动核心契约。

## Consequences

在包含本行的组合里，约 70 个词随每个 agent 的每一轮的每次请求携带，无论该会话是否曾展示过任何东西。文本是静态的，因此开销不随 entry 流增长，提示词只是多了一段恒定的尾巴，其前缀不受扰动。

这个位置是约定，不是不变量。任何注册在 order `200` 之上的 section 都会无声地把它挤离末尾，而支撑这套措辞的实测正是在末尾做的。Web e2e 是绊线；包 README 记下了这个缺口。

这些数字来自一次录下的会话和一条判定规则。它们足以在四个候选修复之间做出选择，但不足以成为关于提示词位置的普适论断；换一个失败应当重新实测，而不是从这张表里推演。

被 surface 路由的每一个内容工具，现在都继承了一条自己没写过的复用规则，包括来自本仓库之外的工具。这正是目的，也是风险：某个身份确实不该被复用的工具，必须在自己的描述里对着一条说「该复用」的通用规则把话说清楚。

## Testing

`tests/prompt-section.spec.ts` 把期望文本作为自己的字面量持有——导入那个常量什么也钉不住——并断言该 section 是组装结果的最后一段、渲染出的提示词以它结尾、在没有注册任何 extractor 时也会贡献它、卸载本行的 fiber 会撤走它（HMR 安全），以及在没有组合提示词注册表时 registry 依然能挂载。

`apps/web/tests/content-surface.e2e.ts` 回答单元测试回答不了的问题：它启动出厂 Web 形态加上 surface 的 overlay，断言该组合组装出的提示词最后一段正是这一段，逐字相符。这条断言不驱动模型，也不打开页面。
