# Agent Note：`show_chart` —— 跨调用的同一张图，以及一张模型真会去看的截图

Status: implemented

[English](2026-08-24-show-chart-supersede-and-inspection.md) | 中文

## Problem

[`show_chart`](2026-08-24-show-chart-tool-chat-view.zh.md) 在机制上闭了环：浏览器画出来，判定回到工具结果，`screenshot: true` 时还捎上一张 PNG。一次开着截图的真实会话表明，这个环在模型脑子里并没有闭上。

结果文本写着 `Rendered: … — 2 series, 14 points`，PNG 也附上了。模型的下一个念头是图表渲染成功、该去总结了。它根本没看那张图。判定行已经宣布了成功，而结果里没有任何东西再要求它做别的——同一个模型被明确要求时，看图是很仔细的。

第二次调用回答了 `Shown; not verified (no client reported within 8s)`，原因是浏览器标签页在后台，`requestAnimationFrame` 被节流，于是截止前没有 `finished` 事件。模型把它读成失败，原样重发了同一张图，用户便在一张已经在屏幕上的图下面多了一行重复的。

这两件都是文本问题。第三件是结构性的：模型是经 Code Mode 调到这个工具的，日志里因此是 `tool/code-dispatch-start` / `tool/code-dispatch`，带 `name`、已解码的 `arguments`、以及形如 `<root>:code:1` 的 `subCallId`——完全没有顶层 `tool/call`。任何要从日志里折出图表调用的东西，都必须同时认得这两种形态，否则对这样的会话什么也看不见。

第四件小一些：有用户要一张雷达图，第一层如实拒绝了，并列出 `bar, line, pie`。

## Decision

### 结果文本要说清下一步

截图现在带一句话到达：检查图例、标签或坐标轴有没有互相压住、文字有没有被裁掉；如果有，用同一个 id 再调一次 `show_chart`，给出改好的 option。它作为**第二个文本块**发出，而不是拼在判定行后面，这样按第一个文本块取标题的结算卡片仍是短短一行。

未确认那一行保留原来的第一句，并新增第二句：图表就在会话记录里，用户看到它时就会画出来，所以不要因此重发。`Shown; not verified` 本来就不是错误；缺的是由此该得出的那条指令。

描述里现在写明图表落进的那块表面有多大——大约 500×340 CSS 像素——并要求把图例放在底部、把排版交给 ECharts，而不是写绝对的 `grid` 偏移。模型自己给的 `grid` 偏移，正是那句检查提示所针对的排版问题的常见成因。

### `id` 命名一张图；较新的调用取代较早那一行

`show_chart` 接受可选的 `id`：去掉首尾空白后非空，至多 64 个字符。复用先前那张图的 id 意味着这次调用取代那张图。没有声明 id 的调用是它自己那张图，以自己的 call id 为键，取代不了任何东西。

两次调用都留在会话记录里——日志就是发生过的事，也没有哪一行去改另一行。较早那一行收缩成一行本地化提示：没有 canvas、没有 ECharts 实例、也不上报判定，因为它本要回答的那次调用早就结算了。

机制本身不会让模型去用它。一次实际会话里，屏幕上已经有一张图，用户引用了它的标题、要求在折线旁边再加一条柱状；模型在既有的 `gold-7d` 之外新起了 `gold-7d-change`，又画了一张新图，而用户预期的是自己指着的那张原地改掉。同一次会话里，截图指令要求它复用 id 时，同一个模型主动照做了——所以机制是够得着的，缺的只是触发条件。`id` 的描述现在把这个触发条件写明：要求改动、扩充或修正一张已经画出来的图——被引用、被叫出标题、或以别的方式被指着——就带上那张图自己的 id，因为换一个新 id 只会在旧图旁边再画一张。只有真正的新图才用新 id。

### `showCharts` 投影补上一行自己看不见的东西

一行渲染的是一次调用的切片。要判断后来的调用是否接手了它的图表 id，就得读到自己之后的调用，而没有哪一行做得到。改由宿主半边经 session-projection 缝投影：`showCharts` 把日志折成 `entries`——每一次记录在案的图表调用一条 `{ chartId, callId, title, seq }`，按日志顺序——view 再派生出 `latest`，即每个图表 id 当前归属的那次调用。

这个折叠读两种日志形态：`tool/call`（原始 JSON 的 `arguments`、`callId`）与 `tool/code-dispatch-start`（已解码的 `arguments`、`subCallId`）。两个半边都画不出图的参数不贡献任何东西——这也正是参数解析只有一个模块的原因：`src/chart-call.ts`，宿主折叠和浏览器那一行都 import 它。投影数进去、那一行却画不出的调用，会把用户还在看的图抹掉；那一行画得出、投影却没数进去的调用，则永远不会被取代。

浏览器那一行经 `useProjection` 读这个值，那是框架的第五个标准 hook 座位，交付给每一个 session 作用域的槽位组件——`tool.call.toolview` 正是其中之一。没有订阅、没有 store、没有第二张表。值缺席不等于这一行被取代了：投影比日志晚一帧，而没有组合投影注册表的组合根本不发布任何值。

`entries` 刻意比「取代」这件事需要的更多。将来列出一个 session 全部图表的 content 表面读的就是这个值；`latest` 只是取代恰好需要的那个派生视图。

### radar

`SUPPORTED_SERIES_TYPES` 加上 `radar`，它的图表模块进入加键的 `SERIES_MODULES` 表，`RadarComponent` 也加进共享组件表——radar 系列画在一套它的图表模块并不携带的坐标系上。工具描述和每一条拒绝文案都从那一个常量取集合，所以它们自动跟上了。

### 看得清，也放得下

截图按 `pixelRatio: 2` 读取。在这条栏目的 CSS 尺寸下，一比一的栅格会让坐标轴标签和图例条目无法辨认，那么「去看这张图」的指令也就没有意义。路由的正文上限本就由 attachment 存储自己的 `maxImageBytes` 推导，因此更大的 PNG 早已被容纳。舞台从 280 px 长到 340 px，也就是描述里许诺的那个高度。

## Alternatives considered

**改写较早那一行的参数，或删掉它的事件。** 否决：session log 就是发生过的事，每一个投影、回放和 SDK 消费方都读它。取代是一个只追加日志之上的渲染决定，每次回放都重新算。

**较早那一行什么都不给——渲染成空的，或者藏起来。** 否决：用户看过那张图并就它提过问；凭空消失的一行会被读成 bug。那行提示点名了这张图，并说明它已被更新。

**调大 `verdictTimeoutMs`，而不是写那句话。** 否决：后台标签页被无限期节流，任何有限的截止时间都救不了；而调大它会让每一次真正未确认的调用都阻塞更久。截止时间约束的是等待，等待之后模型该做什么是文本的活。

**让模型自己从参数判断这张图值不值得展示。** 否决，理由和当初「揭示时机」那条一样：模型除了自己刚写的 option 之外无从判断。截图是「究竟画出了什么」的唯一证据，所以那句指令指向的正是它。

**让那一行自己去读 session 窗口、找出后来的调用。** 否决：那会把一次业务折叠塞进展示组件、按行重复执行，而且窗口并不保证装着整份日志。投影才是被认可的计算位置，而且每个 session 只折一次。

**在浏览器侧再建一张图表 id 表。** 否决：投影值本身就是那张表，客户端副本要自带失效逻辑，而且会和回放对不上。

## Consequences

这个投影是 content 表面的前一半。`entries` 携带的正是一份图表清单需要的东西——id、标题、日志顺序——因此将来的功能读的是一个已经在被驱动的值，而不是对同一批事件再折一遍。

本包因此依赖 session-projection 缝，但只是可选的：`ctx.inject(['sessionProjections'], …)` 意味着没有注册表的组合保留工具、路由和每一行，每张图就是画出它的那次调用。

投影随本 session 的图表调用数增长，且逐字携带每条标题。两者都只受日志本身约束；今天没有任何截断，包 README 记下了这一点。

模型永远不会被告知某张图被取代了。较早那次调用的结果仍是它结算时的样子，没有任何东西会回头改它——取代是渲染决定，回头去改一个已结算的结果，会让同一次调用出现第二个真相来源。

组件行的 bundle 因 `radar` 变大：原始 1.50 MB、gzip 后 342 kB，此前是 1.47 MB / 337 kB。工具 bundle 是原始 16 kB、gzip 后 6 kB，依旧既不带 Vue 也不带 ECharts。

## Testing

`show-charts-projection.client.spec.ts` 在真实注册表和真实 session 上驱动这个单元：两种日志形态、显式 id 与 call id 回退、首尾空白归一到同一张图、跨形态的最后一次调用胜出、每条条目携带的日志 seq、每一种必须不贡献任何东西的参数形态、别的工具的调用、以及 fiber 销毁时的移除。`show-chart-routes.client.spec.ts` 经真实 Loader 把这个单元和路由、工具一起启动，并从一个它追加过事件的 session 上读出投影值。

`show-chart-tool.client.spec.ts` 逐字锁定每一条模型可见文本：含栏目尺寸的描述、带 `id` 及其复用触发条件的参数 schema、两条 id 拒绝文案以及把 id 故障排在前面的顺序、加长后的未确认行、以及作为独立文本块的截图指令——只在真的存了截图时出现，且从不进入结算卡片的标题。`validate.client.spec.ts` 锁定长度上限两侧的 id 规则，以及现在含 radar 的支持集合。

`show-chart-row.client.spec.tsx` 在录制版图表和打桩的投影座位上驱动那一行：被取代的一行渲染提示、不挂载图表、也不上报；当前归属的那次调用照画；值缺席、无关的图表 id、以及以自身为图表的调用也都照画。`echarts-option.client.spec.tsx` 锁定截图的 `pixelRatio: 2`，并让假引擎画一份 radar option。

`apps/web/tests/show-chart.e2e.ts` 往真实组合里注入四次已结算的调用——两次不带 id，随后两次共用 `id: 'demo'` 且 option 不同——并在已发布布局和服务线外壳两种组合下断言：较早那个 `demo` 行显示提示且内部没有任何 canvas，较新那个画出有尺寸的 canvas。较新那个是雷达图，于是真实 bundle 的模块注册被同一条断言覆盖。
