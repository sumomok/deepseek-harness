# Agent Note: 浏览器单点登录与 MCP token 注入

Status: implemented

[English](2026-08-28-browser-single-sign-on-and-mcp-token-injection.md) | 中文

## Problem

一个立在组织自有单点登录之后的 dsh Web surface 有三个缺口，而现有的缝一个也补不上。

外壳没有「已登录的人」这个概念。`dsh-client-connection` 按可达性给 `/api` 设栅栏——回环、已声明的 host、Fetch-Metadata 标记——它自己的 README 就写着：「这道栅栏是可达性策略，而不是认证；Web 载体不提供认证层。」于是，一个「前面放反向代理、把每位登录用户路由到各自的 dsh 进程」的部署，就有了一个已认证的边界和一个未认证的内部，中间没有任何东西把身份带过去。

代理需要每一次请求都带上 token，包括浏览器在完全没有脚本参与时发出的那些——首次导航、图片、iframe、下载。这些只带 cookie，别无其他。而组织的登录页签发的 token 住在 `localStorage` 里，上述请求一个也碰不到它。

立在同一套单点登录之后的 MCP 服务器需要访客的 bearer token，而 `dsh-mcp-client` 在它那一行加载时把 `headers` 配置解析一次。「启动之后才到达、且随登录者而不同」的凭据在那里根本无法表达：`headers: { Authorization: !!js ... }` 是在加载时、针对进程环境、在任何浏览器连上之前求值的。

## Decision

一个实验性包 `packages/experimental/auth-gate`，两个半边都在里面。

browser 半边是一个 boot 模块，没有 slot、没有组件、没有文案。每次页面加载时，它从 node 半边的设置路由读配置，读 `localStorage.accessToken`，然后走三条路之一：没有可用 token 就离开，前往 `<loginUrl>?redirect=<编码后的当前 URL>`；有可用 token 但 cookie 里不是它，就镜像进那个 cookie 并重新加载页面；有可用 token 且 cookie 里已经是它，就让页面跑起来并把它投递给 node 半边。

node 半边提供那份设置，把投递来的 token 收进一个闭包，并为每个配置的 MCP 上游认领一条转发路由。一次转发在两个方向按字节中继，并用 `Authorization: Bearer <持有的 token>` 替换调用方发来的那一枚。

### token 仅凭形状被接受

两个半边都不验签。有能力验签的是反向代理，它验签 token 以决定请求进入哪个 dsh 进程——因此请求抵达时，「这是谁」这个问题已经由一个持有密钥的东西回答过了。进程内部再查一次，等于拿别人递来的密钥去校验别人递来的声明。

token 在进程内能买到的东西也被相应地限定：它能触及本部署配置的那些 MCP 服务器，身份就是代理已经把请求路由到这里的那个人。没有任何路由能把 token 读回来，它也不会写进会话事件、设置文档、日志行或诊断。各种拒绝只点名字段、绝不点名值：一条引用了「差一点就对」的凭据的消息，会把它存放到任何读这份响应的地方。

### 镜像 cookie 不是 `HttpOnly`，而这不付出任何代价

token 本来就住在 `localStorage` 里，是登录页放进去的，页面上任何脚本都读得到。一个页面自己的脚本读不到的 cookie 并不能收窄任何攻击面——被注入的脚本直接读原件——却会让镜像无法与之保持一致。`Secure` 与 `SameSite=Lax` 仍然生效。

### 镜像不可能成环

决定要镜像的那次启动以一次 reload 收尾；而那次 reload 若又决定要镜像，标签页就会一直转下去。守卫是结构性的而不是计数器：镜像写 cookie、读回来，只有读回来确实是那枚 token 时才 reload。没写进去的情况——明文 HTTP、cookie 被禁——会让这一行失败，诊断里点名那个 cookie，且不重载任何东西。由于守卫是状态的性质而不是计数的性质，它在跨标签页、跨恢复、以及 token 在写入与 reload 之间被替换时同样成立。

### 过期是一次导航，配一处具名的缝

在 `exp` 之前 `refreshMarginSeconds` 时，闸门动作，而动作意味着把访客送回登录页——这是每个部署都有的那一条续期路径。`src/client/run.ts` 里的 `handleTokenExpiring` 是这项决定唯一被做出的地方，也是那个余量唯一的读者。若某个部署的单点登录多了一个续期端点，就替换这个函数的函数体；闸门的其余部分都不依赖 token 是怎么续的。不带 `exp` 的 token 会被拒绝而不是当作永不过期，因为整套排期正是建立在这项声明之上。

### 转发骑在 dsh webserver 上

`WebServer.register` 明文写着路由 handler「拥有完整的响应生命周期（可以挂住响应，例如 SSE）」，且该服务从不代 handler 读取请求正文。这恰恰就是一个 MCP 客户端做的 streamable-HTTP 交换：一次 POST 以 JSON 文档或一条挂住的事件流作答，一次 GET 为服务器到客户端的流长期挂住，一次 DELETE 结束会话。两个方向中继 `node:http` 流让答复保持增量，这一点 `apps/web/tests/auth-gate.e2e.ts` 与本包的路由套件都观察到了。

自管第二个监听什么也买不到，却要付好几笔：`Config` 与部署方代理表里多一个端口、多一条要绑到 fiber 上的生命周期、同站栅栏要多覆盖一个面——而 token 无论如何都还住在这个进程里。

转发替换 `Authorization` 而不是透传，因此没有东西能把凭据夹带过闸；并丢弃 `Cookie`，因为镜像携带的正是同一枚 token，而上游没有理由收到浏览器的 jar。

## Alternatives considered

**在 node 半边验签 JWT。** 那需要把签发方的密钥作为配置、处理密钥轮换、定一套时钟偏移策略——只为重新推导一个代理早一跳就用同一把密钥做过的决定。它也丝毫不改变 token 在这里能做什么，因为能抵达这个进程本身就已经要求通过了代理。以「重复的权威」为由否决。

**把 token 放进 `dsh-mcp-client` 而不是做代理。** 最自然的形态——一个逐请求求值的 `headers` 值——是为一个实验性部署去改一个已发布包的配置约定，而且它还得跨包去取一枚 `dsh-mcp-client` 根本没有缝去接收的凭据。本地转发路由把整套机制留在本包内部，让 `dsh-mcp-client` 保持它文档里已有的配置方式，只是 `url` 恰好指向本地。

**为转发自管一个 `node:http` 监听。** 曾被考虑，因为它不依赖 webserver 支持什么。在发现 `WebRoute` 约定本就承诺了唯一重要的那条性质——handler 拥有一个挂住的响应——之后被否决：那样监听就只剩代价了，一个要配的端口、部署方代理表里的第二条、同一个异步面的第二个生命周期所有者，以及一道要复制的栅栏。

**`HttpOnly` 的镜像 cookie。** 按上面那笔账否决：任何能读到该 cookie 的东西同样能从 `localStorage` 读到 token，因此 `HttpOnly` 没从攻击者手里拿走任何能力，却拿走了闸门让两者保持一致的能力。

**用 reload 计数器，或一个 `sessionStorage` 的「已试过」标记做防环守卫。** 两者都把守卫变成计数的性质而不是状态的性质，因此在恢复之后、在第二个标签页里、在 token 于写入与 reload 之间被替换时都是错的——而且两者都会让一次真正失败的 cookie 写入先 reload 一遍才放弃。把 cookie 读回来测的正是下一次启动会测的那个条件。

**在余量处静默续期。** 以 v1 阶段的臆测为由否决：没有任何续期端点可调，因此那段代码会是一个没有消费者的形状。那处具名的缝记下了它该在哪。

**把这道闸做成 `packages/client/*` 包。** 否决：它是与某个组织的单点登录做的、部署相关的集成，不是已发布 web 栈的一部分，而 `packages/experimental` 正是这类行在被某个部署验证之前该待的地方。

## Consequences

装了这一行的 dsh 进程，对着它的浏览器有了身份；立在同一套单点登录之后的 MCP 服务器也能以这个身份触达——这两件事此前都无法表达。

这道闸不会先于外壳其余部分运行。浏览器侧的行是一起创建的、各自等自己的服务，因此未登录的访客可能在跳转发生前先看到外壳画出来。`dsh.client.immediately` 让这一行的 bundle 在第一梯队被预取，缩短了这个窗口，却不排序激活；要关掉它需要 client runtime 里一道并不存在的启动阶段缝。

整个进程共用一枚 token——任何浏览器投递过的最新一枚。这与本包面向的部署形态相符，而对于多人共用一个进程的场景则是错的：那时最后加载页面的那个浏览器会决定每一次 MCP 调用花谁的凭据。也没有任何东西吊销它：浏览器登出后，进程仍持有它最后投递的那一枚。

这一行是实验性的、不在任何已发布 bundle 中，因此没有任何发布组合改变，其他 e2e 场景也看不到它。它自己的覆盖是本包三个测试套件，加上 `apps/web/tests/auth-gate.e2e.ts`——后者驱动整条回路：跳转、桩登录页、回跳、镜像、那一次 reload，以及一次带着浏览器 token 抵达 fixture 上游的 MCP 请求。
