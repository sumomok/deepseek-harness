# Agent Note：server-sidebar——只在工作台草稿仍然干净时才复用它

Status: implemented

[English](2026-09-04-server-sidebar-clean-workbench-draft.md) | 中文

## 问题

产品外壳的工作台在一次点击上只承诺一件事：你落到一张干净的纸上。已记录的那段对话只有在仍然够格时才被复用，其余一切情况都落到创建路径上。

而「仍然够格」的判据，原本只有 `SessionSummary.blank` 一项——这段对话跑过一轮没有。这一位是有意收窄的：独立事件从不把它降下来（`dsh-host-apiproxy` 里的 `sessionBlank`），而展示一个内容页恰恰就是这样一个事件。于是一份访客已经导航过的草稿读出来仍然是空白的，于是被复用：点一下「导航」，内容列上就摆着一份已发布的报表，而下一次工作台点击会把访客送回那份报表上，而不是送到一张干净的纸上。除了被查的那一位之外，这份草稿身上没有任何东西是干净的。

配置好的首页从另一侧把同一个问题磨得更锋利。当 content-frame 的 `homePage` 指名了一个页面时，点击路径自己会把它展示到它刚刚解析出的那份草稿上——于是复用判断如今要去看一个正是这条路径自己填充起来的内容列，并且绝不能把自己的产物读成访客的内容。

## 决定

**干净是两个条件，不是一个：没有跑过任何一轮，并且内容列除了本部署配置的首页之外什么都没有携带。** `client/workflow-actions.ts` 把两者都写成纯谓词——复用判断用 `isCleanWorkbenchDraft`，自动展示判断用 `hasShownHomePage`——于是这项判断是对着字面的条目列表断言的，而不是穿过一棵渲染出来的树；而 `openWorkbenchOnClick` 也仍然只接收一个已经拍好的 `reuse` 输入，不必自己长出一次会话列表读取。

**配置好的首页是唯一一个不会让草稿失去资格的条目，因为正是点击路径把它放上去的。** 若把它算作内容，这套机制会自我击败：第一次点击填充了草稿，于是此后每一次点击都会发现内容并新开一段对话，永远如此。这条例外是刻意收窄的——它同时匹配首页 id 与 `page` 这个 kind，所以 agent 画出的一张图、另一个页面、或与首页条目并列的第二个条目，都仍然让草稿失去资格。

**条目读自会话列表自己的 `projectionValues.contentSurface.entries`，且在读取点保持无类型。** 这与 `dsh-experimental-server-layout` 的 `ShellFrame` 为内容列空判断所做的，是同一条数据源、同一种防御式读法。这次读取保持无类型而不去导入 content-surface 的投影类型：跨包类型导入不是本仓库认可的、耦合两个贴近客户端的插件的方式（`packages/client/AGENTS.md` 的导出纪律），而一个从不组合 content-surface 的组合——或者一个还什么都没展示过的会话——必须降级成一个空列表，而不是在渲染中途抛出。被比较的字段只有两个，这正是 `ContentSurfaceEntryLike` 所指名的。

**一份已经在展示首页的复用草稿会跳过那次重复的 `show-content-page`。** `content/shown` 是一条持久日志记录；为已经摆在眼前的那个页面再发一次命令，只会追加一条什么变化都不描述的记录。而新建出来的那个结果无论这条提示为何都一定会收到这次调用，因为 `homePageAlreadyShown` 描述的是这次点击走开的那份已记录草稿，不是这次调用解析出来的那个会话——浏览器侧测试直接把这处区别钉住了。

**这项判断在会话快照本来就在的地方计算。** `ServerSidebarRoot` 持有 `useSessions` 订阅，因此由它算出两个布尔值并经注入动作传下去；被注入的那一侧仍然是其参数的纯函数。这让侧边栏对会话列表的那一次响应式读取留在原处，而不是在一个动作内部另开一次——那样这个动作就得有一棵会话树才能测。

## 被否决的替代

**展示首页但不追加 `content/shown`。** 否决：内容列是模型可见的，而模型可见 ⟺ 已记录。一个摆在眼前却没有任何事件记录的页面，无法从日志重建，同时也会让内容列自己的回放失去依据。[`content/shown` 写入方判别式](2026-08-29-content-shown-writer-discriminant.zh.md)已经拍定：用户触发的展示记为 `by: 'user'`；这条路径正是其中之一。

**让内容展示把 `SessionSummary.blank` 降下来。** 否决：`blank` 是一个还有其他消费者的核心事实——首屏占位文案、会话列表——对它们所有人而言它的含义都是「没有跑过任何一轮」。为了回答一个 fork 自有插件提出的问题，就把它放宽成「有任何独立事件」，会在上游核心里改动一批与这个外壳毫无关系的界面。

**复用时清空草稿的内容，而不是去判断它。** 否决：那些条目是访客有意放上去的，而本包对「恢复一段对话」的规矩是只补齐缺失的部分（决策 ⑦）。一次静默丢弃持久记录的点击才是更令人意外的行为，而不是更干净的行为。

**让侧边栏自己记住它有没有展示过首页。** 否决：这是在会话日志已经携带的事实之上再立一套账，而且一旦访客刷新页面或开第二个标签页，这套账就是错的。决策 ④ 的未读圆点之所以沿用会话列表自己的 `completed` 位，理由完全相同。

**在 `openWorkbenchOnClick` 内部读取会话列表。** 否决：这会复制一份组件已经持有的订阅，并让一个纯粹的「开或建」动作变成非有一棵活的会话树不可测。

## 后果

在没有配置 `homePage` 时，任何一个 content-surface 条目都会让草稿失去资格。这是有意的读法而非疏漏：没有配置页面，就没有任何条目可能是这条路径自己的产物，因此每一个条目都是访客的。

**拒绝复用，还不等于顶替掉。** 一份被拒绝的草稿落下去的那条创建路径，经由 `resolveOrCreateSession` → `connectWorkspace` 解析，而这个函数自己的复用扫描会按会话列表自身的顺序交回工作区里已经持有的第一个空白会话——一份仅仅因为内容而被拒绝的草稿，仍然没有跑过任何一轮，因此它符合条件；除非该工作区里另有一个空白会话排在它前面——那时交回的是那一个，`workbenchSessionId` 也随之改指过去——否则交回的就是它。于是这项判断的「内容」那一半今天真正产出的，是在一段本就存在的对话上把配置好的首页再展示一次，而访客先前导航到的那个页面仍然坐在那份草稿的切换条里；真正把行为改掉的是去重那一半。要让这次拒绝真的顶替掉草稿，需要一条为这一个调用方绕开那次扫描的创建路径，而拍下它同时也就拍下了一次「导航再点工作台」的循环允许留下多少段被抛弃的空白对话——这是一个产品决定，所以它被记为「已知限制」，而不是在这里拍掉。

`apps/web` 场景的首页那一段现在端到端地承载了这项判断的两半：第二次点击复用了它自己第一次点击填充好的那份草稿，既没有多出一个会话，也没有第二条 `content/shown` 记录；而一份被导航到别处的草稿，在 `SessionSummary.blank` 仍然读作真时未能通过「内容」那一半，于是这次点击把首页又展示了一遍——并且仍然落回同一段对话，也就是把上一段所说的事实断言了下来，而不是假定它成立。
