# Agent Note：用访客自己的凭据，读这套部署自己的数据

状态：已实现

[English](2026-09-06-content-component-library-v2c-data-source.md) | 中文

## 问题

到目前为止，内容列画过的每一块界面，行都是模型或部署自己写出来的。一张三个站点的表，就是模型敲出来的三行。对一个服务线控制台来说这是错的形状：客户想看的行在那套部署自己的数据后端里，控制台已经以这位客户的身份登录着它，而让模型把听说来的行重打一遍，既白费一次回合，又是编造的风险敞口。

这次读需要的东西，进程里全都有，只是彼此没接上。

- **凭据只在一个地方被持有、也只花在一个地方。** `auth-gate` 存着访客的 access token，把它塞进 MCP 转发路由。别处够不着它，也不该有任何地方能把它当成一个裸字符串拿到手。
- **工具没有办法说「这一块从那边取」。** `show_component` 的表格属性 `displayValueList` 是必填且至少一行，所以「把行读进来」这个意思根本表达不出来。
- **没有任何东西可供重放。** 内容列是从循环写下的 `tool/call` 里折出条目的。不在那次调用里的行，日志里哪儿都没有，靠它们建起来的条目在下一次折叠时就消失了。
- **没人被问过。** 花一个人的凭据去读这个人的数据，不是模型可以自己决定的事。

## 决定

**一条只有三个具名读操作的能力，绝不是通用 `fetch`。** `ctx.bizBackend` 提供 `search(request, signal)`、`describe(meta, signal)` 与 `describeScheme(meta, signal)`，除此之外够不着任何东西。同一个前缀下还挂着 `PUT /api/resources/{model}/{id}`、`DELETE /api/resources/{model}/{id}` 和 `POST /api/batchresources/delete/{model}`；一条 `fetch(path, init)` 服务等于把访客的凭据连同这些端点一起发给同进程的每一个插件，而本 fork 自己的审计已经实证：第三方插件默认不声明任何审批闸。模型名在进入 URL 之前先判过是不是一个光秃秃的路径段，所以一个带 `/` 或 `..` 的名字没法把一条带凭据的请求引到隔壁端点去。

**基址配在持有 token 的那个包上。** `bizUpstream` 是 `auth-gate` 的字段，不是 `component-surface` 的。它是唯一能在类型上说出「这枚凭据只去这个源站」的形状：消费方点的是表名，永远不是地址。它没有默认值——不写就压根不注册服务，消费它的行会明确挂起并点名缺的是哪个服务。这个值必须带上部署自己的 API 前缀，因为那个前缀就是前端的 `VUE_APP_BASE_URL`，一套部署一个样：标准安装发布在 `/ini-server/`，没配这一项编译出来的安装发布在源站根上。拼接用的是部署客户端自己的 `combineURLs`，不是 `new URL(relative, base)`——后者会把这段前缀整个丢掉，让每一条请求都落到服务器根上。

**Service Definition 单独住在一个纯 Host 包里。** `dsh-experimental-biz-backend` 持有 `ctx.bizBackend`、它的提供方和它的失败联合；`auth-gate` 用它校验过的基址和它手里的 token 把它构造出来，`component-surface` 消费它。这次拆分是被逼的，而这股力值得记下来：只要一个包的 Host 导出所能到达的文件里声明了 Cordis 面，Typert 分析器就把这个包选进 Host face，然后拿这个包整份 tsconfig 文件清单当 Host 程序的根文件。`auth-gate` 是注册在 Client 聚合上、带 `src/client` 半边的包，所以在它的 `src/index.ts` 里声明 `Context.bizBackend`，就把 `src/client`——以及经由它的 `@deepseek-ai/dsh-client-runtime/client`——拽进了 Host 程序，与 `packages/core/agent` 并排，而两者都声明了 `agent` 这个 Typert 上下文键；目录生成器于是以 `duplicate TypertContextMap key agent` 停下。`component-surface` 处境完全一样。纯 Host 包没有客户端半边可拽，于是这个服务被分析到、被发布进 `docs/subsystems/biz-backend.md` 上生成的 Cordis 目录，而凭据依旧没有离开 `auth-gate` 的闭包。

**两个头都写 `Bearer <token>`。** 部署的页面存的是 `"Bearer <jwt>"`，并把存储原值逐字塞进 `Authorization` 与 `CertificationToken`；而这道闸手里是裸 JWT——浏览器半边在存储值入口处把 scheme 剥掉了一次——所以这里把 scheme 加回去，线上的字节就与页面一致。`CertificationToken` 是这个后端读 token 的方式，不是第二枚凭据。

**失败是值，是一个闭合联合，且没有任何一个成员携带凭据。** `unauthenticated`、`refused`、`rejected`、`unreachable`。消费方按标签 switch，以 `assertNever` 收口。后端回来的任何自由文本，都先按名字把本次呈上的凭据抹掉、再截长度——只截长度守不住这条承诺，因为后端把 token 说在前一百个字符里就会通过。

**`dataSource` 是这次调用的顶层参数，不是那一块的属性。** `displayValueList` 是 `required: true` 加 `minItems: 1`，而 `PropsSchema.required` 是逐字段的布尔值，表达不了「除非另一个参数在场，否则必填」。这些属性所在的目录还与浏览器座位共用，那边不该带任何只有宿主用得上的字段。做成顶层参数，目录、座位和既有的判据这一趟全都不用动，行代入之后摆到它们面前的就是一份普通的 spec。

**顺序是：判整次调用、看手上有没有凭据、问、读字典、取数、再判一次。** 一切不花任何东西就能判的先判掉，而且判的是整次调用而不只是取数那一半：拿手写调用走的那道 `validateComponentCall`，去判一份每张待填的表里放了一行占位行的副本，于是标题过长、第十三块、这套部署没有的组件、第三十一列，都在问任何人之前就被拒。被取数填的块既不能送 `displayValueList` 也不能送 `rawValueList`：存储那一份正是被上报的手势用来作答的东西，调用自己写它，等于把自己的值放在卡片上说「读来的」那些行背后。接着从网关读一下手上到底有没有凭据，这一步不花钱也不碰网络——不该为一次本进程做不到的取数去问人答不答应。然后问用户，一次调用问一次——`allowed-once` 是审批服务唯一的放行值，所以「一次调用一个问题」本来就是这条缝给的。然后读这张表的字典，把这次取数点到的每一个属性都核一遍——每一列、每一条筛选的键、以及排序用的那个属性——调用没写表头的列也在这里补上一个。否则一条点到表里没有的属性的筛选就交给后端自行解释，而把它直接忽略掉的后端，会把用户批的那次「筛过的」取数答成一直取到页大小为止。一列都没点名的块，它的列在读字典与取数之间定下来，取自[默认列那条笔记](../feature/2026-09-07-data-source-default-columns.zh.md)新增的查询方案。然后取行，一张表接一张表。然后代入后的 spec 再走一遍那道判定，判的是只有行才能决定的两件事：到了多少行，填好之后有多少字节。字典放在问之后而不是问之前读，是因为读它就要花凭据，而凭据不在问之前花。

**审批卡片不印任何这套部署平时不给人看的标识符。** 卡片正文里的表名是模型写的那个，后端给它的名字单独一行小字。列按调用自己写的表头点名，没写表头就只计数；筛选在被筛的列全都有表头时按表头加算子写，否则整句改成计数——因为在字典读到之前，它剩下的唯一名字就是后端用来存这一列的属性名，那是个标识符。筛选的值一概不出现：一个条件里可能是别人的身份信息。最后一句是固定的、永不参与截断：您在表里勾选的行，会作为您的选择告诉小助手——勾中的行确实会离开面板到达模型，所以一张说反话的卡片许诺的就是本条路径并不做的事。

**一次读取只留它所取的那些列。** 后端答回来的是它自己挑的属性，而不是请求点名的那些——本部署的客户端会往每一份 `source` 前面插它自己的 `int_id`，后端也就不管问没问都把它答回来——所以两份行列表在画出来、记下来之前，都先被收到这次读取所取的那些列上——那是这一块自己声明的列，或者它的默认方案定下来的列。少了这一步，卡片上那句「只取 N 列」就是面板和会话日志双双违背的承诺，而多出来的那一列是这套部署平时不给任何人看的标识符。

**模型写的任何东西都画不出卡片上的一行。** `metaLabel` 与每一个列表头都必须是平铺的一行——不带换行、不带其他控制或格式字符、不带 Unicode 行/段分隔符、不带 `「」`——而表头受的是与代入后调用同一条四十字符的限，于是一个长到画不出来的表头在提问之前就被拒，而不是等凭据花完之后。随后每张表的描述会先按它在三百字符正文预算里分到的那一份被裁掉，**之后**才接上那张表的「数据表」行和结尾的承诺，于是这两样都推不掉。少了这两条规矩，一次调用就能把自己那行「数据表」写进标签里，或者把表头撑长到把真的那行顶出去，卡片上唯一可核对的事实就变成了又一句模型说的话。

**取数成功会 append 一条 `content-component/resolved`，带着整份代入后的 spec。** 内容列的读取器是逐事件、同步、纯的：它没法把一条记录里的基础 spec 和另一条里的行拼起来，而同一条目 id 的后一条记录会把前一条整条替换掉。记录而不是重放还有另一层理由——重放意味着在没人要求的时刻再读一次这个人的数据，而且可能读到不一样的答案。

**任何一步出错都不 append。** 顶层参数这个做法，把「正在取数」这个中间态在它能出现之前就消掉了：一次取数调用自己的 `tool/call` 里，被点名的块没有行，过不了抽取器的判据，压根不产生条目。等待期间用户看到的就是审批卡片本身。所以失败 = 给模型一句话，内容列一动不动。

**HTTP 401、或者失败状态码带上结果码 2 或 3，会交出 token；HTTP 200 上的同一个码不会，单独一个 HTTP 403 也不会。** 这套部署自己的客户端只在错误拦截器里对这两个码丢掉存着的 token——它的成功拦截器在 HTTP 200 上遇到非零码只报错、token 照留——那个 switch 之外，它只对 HTTP 401 再丢一次。403 只走到它那句 `拒绝访问`，存着的 token 一动不动，所以这里的 403 和别的失败状态一样按信封分类。严格照抄它，才不会因为一次普通的业务拒绝、或者一个这位访客够不着的端点，丢掉一枚还活着的凭据，连带停掉这个进程里的每一条 MCP 转发。

## 考虑过的替代

**通用的 `authGateFetch(path, init)`。** 因为上面那张端点表被否：审计面从两个读扩到整个 base URL——包括删除——而且是对进程里每一个插件。

**就在凭据所在的 `auth-gate` 上声明 `ctx.bizBackend`。** 被 Typert 分析器否掉，不是被口味否掉的：那会让 Host 程序同时看见 Host 与 Client 两份 `agent` 上下文声明，直接拒绝构建。把 `auth-gate` 的编译面拆成两份同样可行，也一并被否——`docs/development.md` 只允许 `api/remotes` 用这个形状，并明写不要照抄。

**把数据后端塞进 `mcpUpstreams`。** 两重理由被否。每个条目会认领一条 `/auth-gate/mcp/<name>` 路由，而那条路由只挡跨站，于是任何同源页面——包括内容列里的业务 iframe——都能以已登录访客的身份打到后端，自己一枚 token 都不用出。而且那条路是字节管道：它读不了信封的 `code`，会把一次拒绝当数据送出去。

**结果太大就截断。** 被否。一张悄悄少了尾巴的表，用户会当成完整的读。拒绝会写出行数和字节数，并让模型少要一些。

**给没有登录凭据的会话配一个服务账号兜底。** 被否。兜底账号存在的那天就会在生产里被用上，而它会让卡片开头那三个字——用您的账号——对那个账号所代表的人变成假话。没有凭据的会话就是被拒，访客去登录。

**在问之前先读表的字典，好让卡片带上后端自己给这张表和这些列的名字。** 被否：读它就要花凭据，而凭据不在问之前花。代价已记录在案——卡片上的表名是模型的说法，调用没给表头的列只计数不点名。

**在记录的事件上加一个 `failure` 成员，好让失败的取数在面板上说出来。** 被否：顶层参数这个做法意味着取数调用在行到位之前不产生条目，所以没有一个「正在进行」的条目供失败去落定。这与调研稿的结论相反——那份稿子假定条目从调用那一刻就存在。

**不管 HTTP 状态码，只要结果码是 3 就交出凭据。** 读过部署客户端的两个拦截器之后被否：只有它的错误分支会对这个码丢 token。猜反了就会因为一次普通的业务拒绝交出一枚还活着的凭据，连带交出每一条 MCP 转发。

## 后果

**买到的。** 模型可以把这套部署当下的真实数据摆到它的主人面前，而且是先问过这个人的，全程没有一行数据经过模型请求。一次读最多就是三个具名操作，变不成别的。座位、目录和组件库一个字节都没动。

**付出的。** 一份最大 65536 字节的代入后 spec，会随内容面写的每一个检查点走一遍，每条活着的条目一份。`content-component/resolved` 是本仓每一个构建都必须认识的会话事件。一次被后端拒的读会停掉整个进程的 MCP 转发，因为 token 是进程范围的。而且这条取数路径又多了一样「只有访客登录着才成立」的东西。

快照那条线缺一样东西：一个场景没有任何办法去够到它刚启动的那套组合的路由，而在有人 post 之前这道闸手里没有 token。`Scenario.afterSpawn` 就是这个钩子——它在子进程 spawn 之后、第一步输入之前跑——取数场景用它把访客的 token 按那位访客的浏览器会用的方式 post 上去。

## 已知限制与延后事项

- **行级裁剪是后端的事，而本次改动证明不了它真的发生。** 这套部署自己的前端有一遍行/列权限判据，而它在拿不到登录用户信息时是提前返回、把数据放开而不是收紧，所以它根本不是一条边界。如果后端不按收到的 token 裁行，一次取数就可能把某人不该看到的行画上这个人的屏幕、并写进这个人的会话日志——而退出并不会清洗已经写下的日志。要闭掉它，需要那个后端的负责人给一个答复。**在这个答复出现之前，这条路径不该对真实用户开放。**
- **本次改动没有任何一处跑过真机部署。** 这里的每一个后端都是照着 2026-09-05 那次抓包的形态写的假件。第一次真读，就是抓包与线上系统之间的差异会显形的地方。
- **一次被后端拒的读也会停掉 MCP 转发。** HTTP 401，或者失败状态码带上码 2 或 3，都会让进程交出 token——那是登出路由的同一个终态——于是每条转发路由都答 503，直到某个浏览器 post 一枚新的。一次读的失败因此是进程范围的。
- **进程随后知道了页面不知道的事。** node 半边是第一个知道 token 被拒的地方，而它没有任何通道告诉浏览器，那个页面照旧跑到自己的过期计划触发为止。最便宜的闭法是：凭据因被拒而丢掉之后，token 路由答 409——那也会是 `HeldCredential.drop` 的 `reason` 的第一个读者。
- **HTTP 200 上的 `code 3` 是 rejected 而不是 refused。** 一个这样报过期 token 的后端会一直被呈上它，直到浏览器的过期计划出手。
- **`Bearer ` 是加回去的**，前提是这套部署的登录页存的就是它。存裸 JWT 的部署会收到一个比它自己页面多一个 scheme 的头。
- **组合里每一行都能调 `ctx.bizBackend`。** 这三个方法的窄就是边界的全部；谁可以调是组合层的决定。token 本身仍关在闭包里、不作为服务发布。
- **卡片上的表名是模型的说法**，调用没给表头的列只计数不点名——两者都是「字典在问之后才读」的后果。它下面那行「数据表」既伪造不了、也顶不掉，所以读它的人有机会看出对不上；对不读它的人，一个看起来合理的错标签照样过关。
- **卡片说的是一页多大，从不说第几页。** 自[默认列那条笔记](../feature/2026-09-07-data-source-default-columns.zh.md)起 `page` 带上了 `currentPage`，而卡片仍然用读第一页的措辞描述每一次读取。
- **配置出来的视图读不到自己的行。** `dataSource` 是一次调用的参数，所以部署自己的首页视图带的只有人手敲进 `cordis.yml` 的行。要让视图自己取数，就得把问题挪到用户点开它的那一刻去问——配置出来的视图没有一次模型回合可以挂这个问题。下一片。
- **取数失败时屏上留着的是上一次的表，没有任何地方说它是旧的。**
- **本行向后端要的列比这套部署自己的页面少** —— 组件库把方案里的每一列（含隐藏列）都要过去，而这里的调用只送它声明过的那几列，或者自[默认列那条笔记](../feature/2026-09-07-data-source-default-columns.zh.md)起，送那份方案里展示出来的那几列。这是有意的收紧，写下来免得日后被当成 bug「修」回去。
- **不复刻这套部署前端的按模型覆盖地址机制。** 配了这种覆盖的模型会被读到默认地址上。触发器是第一次取数结果与页面对不上。
- **行进日志就是检查点的重量** —— 最大 65536 字节的代入后 spec，每条活着的条目一份，随内容面写的每一个检查点走一遍。
- **`content-component/resolved` 是 required on read**，与本包另一个事件同理：`Session.append` 没有给追加方设置信封 `ignorable` 标记的途径。
- **审批面板把卡片画成一整段连排文字。** 理由里是带换行的——那行小字「数据表」本该单独一行——而面板把换行渲染成了空格。读得懂，但不是写下来的样子。修法在面板那一侧。
