# Agent Note：一条工作流绑定的会话 id 是弱引用，在渲染时才即时解析

Status: implemented

[English](2026-08-29-favorites-weak-session-reference.md) | 中文

## Problem

`@deepseek-ai/dsh-experimental-server-sidebar` 的工作流菜单以会话 id 在一份比任何单个会话都长寿的文档里指名一个对话：一条工作流的 `homeSessionId` 持久保存在 `settings` 能力的持久文档里（[按账号，一个用户一个 `$DSH_HOME`](../../../../packages/settings/settings-file/README.zh.md)），而它所指名的会话可以在任何时候，被同一个用户，通过普通的 Workspace 机制删除，两个功能之间没有任何协调。本包里没有任何东西监听会话删除——拥有删除权的工作区域没有理由知道别处的某份 settings 文档可能引用了它刚刚删掉的 id，为这一个功能的记账去打通这条通知，会把两个原本独立的能力耦合在一起。因此工作流文档终将指名一个已经不存在的会话——这是预期中的正常情况，不是一种失败。

## Decision

**一个绑定的会话 id 是弱引用，在渲染或动作发生时才即时解析，从不在写入时校验。** `ServerMenuWorkflow` 携带一个裸的 `homeSessionId: string`（`ServerMenuSettings` 也携带一个裸的 `workbenchSessionId?: string` 给持久工作台对话用，遵循完全相同的规则），整条写入路径上没有任何存在性校验——`POST /server-menu/workflows` 路由的 schema 校验里没有，settings 命名空间的 `validate` 钩子里没有，本包的 invariant 里也没有。这三处各自把关的唯一关系是文档内部的关系（不得有两条工作流共享同一个 id）；一个被指名的会话当下是否存在，是这份文档不能也无法承诺的事实，因为它可能在写入成功的下一秒就变得过时。

**失效判定是浏览器侧、按动作发生时计算的，不是一个持久标记，而且它会去降级、而不只是展示。** `ServerSidebarRoot` 在每次渲染时都从标准的 `useSessions` 快照里派生 `liveSessionIds`（用 `useMemo` 依赖 `byId`），并拿一条工作流的 `homeSessionId`（或工作台的 `workbenchSessionId`）与这份实时集合比对。打开一条其会话已经消失的工作流，不会渲染一行禁用的记录留给用户以后去注意和处理——它会立刻创建一个全新对话，把这条工作流保存的导航快照重放到上面，再把 `homeSessionId` 重新指向这个新会话（决策⑧，[`2026-08-30-server-sidebar-product-console-retrofit.md`](2026-08-30-server-sidebar-product-console-retrofit.zh.md)），因此发现失效的那次点击，就是解决失效的那次点击。一条工作流从不会因为绑定已经失效就被从列表里过滤掉，不管是悄悄地还是别的方式——对它降级，恰恰是让它继续留在列表里、以自己的名字继续可打开的方式。

## Alternatives considered

**在写入时（`POST` 或 `settings/updated`）对照存活会话列表校验 `homeSessionId`。** 拒绝：这只能防止*新增*一条绑定到尚不存在的会话的工作流——对更常见的情况（保存工作流时会话确实存在，之后才被删除）毫无帮助。文档会在下一次删除时照样过时，这个校验只在一个很窄的窗口里换来了正确性，对真正要紧的那种情况却毫无帮助，同时还给 settings 写入路径加上了一个对实时会话列表的依赖（这在 node 半边的进程里并不总是以同样的方式存在，在没有加载会话运行时的组合里甚至可能根本不存在）。

**让删除顺带清理任何指名了被删会话的工作流。** 拒绝：这需要工作区/会话删除路径知道本包的 settings 命名空间，颠倒了本仓库能力接缝约定所要求的所有权方向（一个能力的提供方不应该在每次操作时都伸手去碰一个不相关消费者的持久数据）。这样做还会把用户自己命名的快捷方式彻底删掉，而不是让它在重新指向一个新会话之后继续可用。

**为一个失效引用渲染一行禁用的、带标签的记录，而不是在打开时透明地对它降级。** 这是本笔记最初为本包出厂时的收藏菜单做出的决定——一行灰显、不可跳转的记录，带有明确的「会话已删除」标签，保持可见、可移除以便手工清理，绝不悄悄从列表里丢弃。产品外壳改造替换了这个做法：决策⑧要求打开一条失效的工作流,要立刻把用户带进一个可用的对话（一个全新的、重放了导航快照的对话），而不是一个需要用户自己注意到、再手工清理的死胡同。两种做法共享上文同一个弱引用前提；不同的只是呈现方式——一个留给用户处理的可见失效状态，对比同一次点击就完成的修复。

**在保存时存一份会话标题的冗余快照，即便失效也照样展示。** 拒绝：一条工作流的 `name` 本来就是一个独立于会话自身标题的、用户自选的名字（工作流快捷方式的意义正在于一个用户自己挑的名字，而不是会话本身的标题），因此第二份冗余标题回答的是一个没人会问的问题。

## Consequences

工作流 schema 保持接近最小——`{id, name, order, homeSessionId, navSnapshot, savedAt}`——没有状态字段，也没有「最后核实时间」；`navSnapshot` 是唯一一个超出弱引用文档严格需要的新增字段，携带它是因为决策⑧的降级路径需要知道该重放什么，而不是弱引用机制本身要求它。代价是每次渲染都要做一次 `O(工作流数 × 存活会话数)` 的成员检查（每条工作流一次 `Set` 查找，用的是这个组件本来就要为「当前会话」派生而读取的那份快照），在「一手几个对话」的真实工作流列表规模下可以忽略不计。

这个决定完全不要求工作流文档最终必然与存活会话列表完全一致，也没有任何机制去追求这一点——一个失效的 `homeSessionId` 会一直留着，直到它的工作流下一次被打开，届时它会自行重新指向。这正是弱引用本该有的形状：正确性永远活在读取（或动作发生）的那一刻，而不是在每一次写入时被苦苦追赶。
