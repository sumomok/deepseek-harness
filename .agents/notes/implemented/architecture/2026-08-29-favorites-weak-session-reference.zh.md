# Agent Note: a favorite is a weak reference to a session id, never silently dropped

Status: implemented

[English](2026-08-29-favorites-weak-session-reference.md) | 中文

## Problem

`@deepseek-ai/dsh-experimental-server-sidebar` 的收藏菜单以 id 在一份比任何单个会话都长寿的文档里指名会话：一条收藏持久保存在 `settings` 能力的持久文档里（[按账号，一个用户一个 `$DSH_HOME`](../../../../packages/settings/settings-file/README.zh.md)），而它所指名的会话可以在任何时候，被同一个用户，通过普通的工作区 UI 删除，两个功能之间没有任何协调。本包里没有任何东西监听会话删除——拥有删除权的工作区域没有理由知道别处的某份 settings 文档可能引用了它刚刚删掉的 id，为这一个功能的记账去打通这条通知，会把两个原本独立的能力耦合在一起。因此收藏文档终将指名一个已经不存在的会话——这是预期中的正常情况，不是一种失败。

## Decision

**一条收藏是弱引用，在渲染时即时解析，从不在写入时校验。** `ServerMenuFavorite` 携带一个裸的 `sessionId: string`，整条写入路径上没有任何存在性校验——`POST /server-menu/favorites` 路由的 schema 校验里没有，settings 命名空间的 `validate` 钩子里没有，本包的 invariant 里也没有。这三处各自把关的唯一关系是文档内部的关系（不得有两条收藏指名同一个会话）；一个被指名的会话当下是否存在，是这份文档不能也无法承诺的事实，因为它可能在写入成功的下一秒就变得过时。

**失效判定是浏览器侧、按渲染计算的，不是一个持久标记。** `ServerSidebarRoot` 在每次渲染时都从标准的 `useSessions` 快照里派生 `liveSessionIds`（用 `useMemo` 依赖 `byId`），菜单在展示时把每条收藏与这份实时集合逐一比对。一条会话已被删除的收藏会渲染成一行灰显、不可跳转的记录，带有明确的「会话已删除」标签，其重命名操作被隐藏（已经没有可以重命名到的地方去），移除操作依旧保留——这一行始终可见、可清理，绝不会从列表里被悄悄过滤掉。这是一项刻意的产品要求，不是实现上顺手选的默认值：一条被悄悄丢弃的收藏，在保存过它、之后却找不到的用户看来，与数据丢失没有区别，也没有办法分辨这两者。

## Alternatives considered

**在写入时（`POST` 或 `settings/updated`）对照存活会话列表校验 `sessionId`。** 拒绝：这只能防止*新增*一条指向尚不存在的会话的收藏——对更常见的情况（收藏时会话确实存在，之后才被删除）毫无帮助。文档会在下一次删除时照样过时，这个校验只在一个很窄的窗口里换来了正确性，对真正要紧的那种情况却毫无帮助，同时还给 settings 写入路径加上了一个对实时会话列表的依赖（这在 node 半边的进程里并不总是以同样的方式存在，在没有加载会话运行时的组合里甚至可能根本不存在）。

**让删除顺带清理任何指名了被删会话的收藏。** 拒绝：这需要工作区/会话删除路径知道本包的 settings 命名空间，颠倒了本仓库能力接缝约定所要求的所有权方向（一个能力的提供方不应该在每次操作时都伸手去碰一个不相关消费者的持久数据）。这样做还会悄悄删掉用户自己命名的书签——正是渲染时方案要避免的那种「无声丢弃、无迹可寻」的结果，只是把它从读取时刻挪到了写入时刻。

**把失效的收藏从渲染列表里悄悄过滤掉。** 拒绝，这正是本决定要拒绝的字面意思：一个收藏过某个会话、之后（有意或无意）被删除、随后在列表里找不到这条收藏的用户，完全无法判断它当初是否真的被保存过。一行灰显、带标签、可移除的记录，把一个隐形的数据完整性问题，变成了一个可见、一键可解决的 UI 状态。

**在收藏时存一份会话标题的冗余快照，即便失效也照样展示。** 拒绝：这条收藏的 `label` 本来就是一个独立于会话自身标题的、用户自选的名字（收藏的意义正在于一个用户自己挑的名字，而不是会话本身的标题），因此第二份冗余标题回答的是一个没人会问的问题。失效状态的标签（「会话已删除」）已经把这一行被禁用的操作原本会告诉用户的一切都说清楚了。

## Consequences

收藏的 schema 保持最小——`{ sessionId, label, order }`——没有状态字段，没有快照，也没有「最后核实时间」。代价是每次渲染都要做一次 `O(收藏数 × 存活会话数)` 的成员检查（每条收藏一次 `Set` 查找，用的是这个组件本来就要为「当前会话」派生而读取的那份快照），在「一手几个会话」的真实收藏列表规模下可以忽略不计。

这个决定完全不要求收藏文档最终必然与存活会话列表完全一致，也没有任何机制去追求这一点——一条失效的收藏会一直留着，直到它的所有者亲手移除。这正是弱引用本该有的形状：正确性永远活在读取的那一刻，而不是在每一次写入时被苦苦追赶。
