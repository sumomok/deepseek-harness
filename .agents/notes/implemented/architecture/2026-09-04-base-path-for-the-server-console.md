# Agent Note: serving the console under a deployment path prefix, with the prefix known only to the browser

Status: implemented

English | [中文](2026-09-04-base-path-for-the-server-console.zh.md)

## Problem

The server line publishes one shell per user behind a shared nginx, and the only address space that scales is a path prefix — `https://host/console/` rather than a subdomain per process. The harness cannot be served that way. A `dsh` process learns nothing about a prefix: `WebServer`'s `Config` carries only `host` and `port`, nothing in `packages/`, `apps/`, or `examples/` reads `x-forwarded-prefix` or any spelling of `basePath`, and every route is registered root-absolute (`/api`, `/plugins`, `/manifest.webmanifest`, plus the seven this repository's own plugins claim). Behind `location /console/ { proxy_pass http://…/; }` the process therefore sees exactly the paths it registered, and answers them correctly.

The browser is the half that breaks, in three separate ways, none of which any existing test could see.

- The built shell addresses the origin root. Vite had no `base`, so `dist/index.html` carried `/assets/…`, `/favicon.svg`, and `/manifest.webmanifest`; under a prefix those are four 404s and a blank page before a line of application code runs.
- Everything the page builds at run time resolves against `location.origin`. Three separate copies of the same `resolveBase()` — in `client/connection/src/client/rpc.ts`, `host/apiproxy/src/fetch/client.ts`, and `session-log-export/src/client/controller.ts`, each with its own `INTERNAL_BASE` literal — plus the two WebSocket downlinks, the HMR `EventSource`, and the settings routes four of this repository's own plugins fetch.
- The plugin bundles are named root-absolute in the boot manifest, and two of them are requested before any script runs: `client-modules` contributes `client-modules` and `client-runtime` as parser-blocking `<script src>` rows, which no run-time hook can reach.

The verification surface had the matching gap. `apps/web/tests/assembled-boot.ts` pinned the page address to `'/'`, so no assembled scenario could tell a root-absolute URL from a prefix-relative one; and `auth-gate.e2e.ts` counted shell loads with `location.pathname === '/'`, which under a prefix would have turned "the mirror reloaded exactly once" into "the shell never loaded" without failing anywhere a reader would look.

## Decision

**The prefix lives in one plugin's `Config` and reaches the browser as two index rows.** `@deepseek-ai/dsh-experimental-server-base` validates `basePath` at load — leading slash, trailing slash, no query, no fragment, no empty segment, and only characters a URL path segment admits — then contributes `<base href="<basePath>">` and a `{ kind: 'global', name: '__DSH_BASE__' }` row through `webserver/index-inject`, both with `{ prepend: true }`. The character set is what makes the `<base>` row safe to write by interpolation: `"`, `<`, `>`, and `&` are outside it, so no escaping step stands between the configuration and the served markup. `prepend` is load-bearing rather than stylistic — head rows render in table order, and `<base>` governs only the URLs after it, so a row contributed by an earlier-registered listener (the two parser-blocking bundle tags among them) would resolve against the document URL instead.

**Route constants stay root-absolute everywhere; `clientUrl` is the only supported way to turn one into a URL the browser may request.** `packages/client/connection/src/client/base.ts` exports `INTERNAL_BASE`, `resolveClientBase()`, and `clientUrl(path)`, and `@deepseek-ai/dsh-client-connection/client` re-exports all three. `clientUrl` drops every leading slash before resolving, because a root-absolute path would replace the prefix rather than extend it. The three duplicate `resolveBase()` implementations collapse into it, `API_PATH` and the six route constants this repository's own plugins own keep their root-absolute spelling, and no package gains a second, segment-shaped copy of a path it already has — the node half registers the constant and the browser half resolves the same constant.

`resolveClientBase()` takes its authority from `location.origin` always, and lets `__DSH_BASE__` and `document.baseURI` contribute only a path. That is narrower than "prefer `document.baseURI`": a `<base href>` naming another origin cannot redirect Host traffic, and a document whose URL cannot be a base (`about:blank`, a sandboxed frame) does not throw on the way to the fallback.

**The bundle URL is relativized at its one composition point.** `graphRow` in `client/modules/src/index.ts` mints `plugins/<id>/client.js?rev=<rev>`, and both consumers — the parser preloads and the module system's `el.src` — then resolve it through the document base. `client/system.ts` deliberately does not add a base of its own; the two are alternatives, and doing both would prefix twice.

**The mirror cookie is scoped to the prefix.** `mirrorCookieLine`/`clearCookieLine` in auth-gate take a `path`, and `windowGateBrowser` computes it once as `new URL(resolveClientBase()).pathname` so the write and the clear repeat it verbatim — a browser matches a removal by name, path, and domain, so a mismatch writes a second, empty cookie and leaves the token in place. `server-sidebar`'s sign-out clears that same cookie from its own copy of the line, so `windowSignOutBrowser` resolves the prefix the same way; a unit test compares the two lines rather than trusting the copy.

**`apps/web/vite.config.ts` sets `base: './'`, not the prefix.** One built `dist` then serves under any prefix, which the one-process-per-user topology requires; `base: '/console/'` would bake one prefix into the artifact.

## Alternatives considered

**Replicate the transport through `__DSH_TRANSPORT__`.** Rejected. It is a documented whole-transport seam — `createApiClient`, `fetch`, `loadBundle` — and it would have kept the letter of "no upstream edits". But it does not cover the two parser-blocking `<script src>` preloads, which are emitted before any script runs, and it does not cover the built shell's own assets, so the build config had to change regardless. The price of the letter would have been a second implementation of three transport channels in this repository, against six small same-shaped edits upstream that the degradation clause retires the day upstream grows a `basePath` of its own.

**Let the process learn its prefix and register routes under it.** Rejected. The prefix would then have to be honored in four places that each match paths independently — the `WebServer` route table, `rpc-host.ts`'s `endpointFromPath`, `apiproxy/fetch/handler.ts`'s three `/api/` string tests, and the privileged-method fence in `connection/src/index.ts` — and a change that reached only the first would produce 404s whose symptom points at routing rather than at the prefix. nginx already strips prefixes for a living; the process keeps one set of paths.

**`base: '/console/'` in the Vite config.** Rejected: it moves the prefix from a validated run-time value into a build artifact, so a deployment could not run two prefixes off one build, and the value would exist in two places with no mechanism keeping them equal.

**`sub_filter` in nginx.** Rejected: it can only rewrite literals in a text response body, and almost every broken URL here is assembled at run time (`new URL(path, origin)`, `new WebSocket(url)`, `el.src = url`), so those strings never appear in a body in the form it would match. It also requires disabling upstream compression, and the module is not compiled into the nginx this deployment runs.

**Add `resolveClientBase()` to `apiproxy`'s `AbstractApiClient` directly.** Rejected as a dependency cycle: `client/connection` already depends on `host/apiproxy` in both its package manifest and its project references, so the reverse import would close a cycle npm and `tsc -b` both refuse. Instead `resolveBase()` — already a `protected` platform seam — is overridden in the browser subclass `WebApiClient`, and `apiproxy` gains only a private `carrierUrl` that drops leading slashes. No base-resolution logic is duplicated; the `INTERNAL_BASE` literal is.

**Give `content-frame`'s `pages[].url` a `clientUrl` treatment.** Rejected: `pages.ts` requires those values to start with a single `/` at load, and deployments already write the full browser-side path there. Resolving them again would prefix twice. The same reasoning applies to auth-gate's `loginUrl`, which the browser assigns to `location.href` verbatim. Both are deployment data that carry the prefix; the note that distinguishes them from the process-side route constants is now in their JSDoc and READMEs.

**Turn route constants into prefix-free segments (`api`, `plugins/events`, `auth-gate/settings`).** Rejected: the node half registers from the same constants, so a segment spelling would leave the two halves unable to share one source of truth for a path. Dropping the leading slash inside `clientUrl` achieves the same resolution with one constant.

## Consequences

Two test-harness changes had to land before the product change, because without them a regression would have passed. `assembled-boot.ts` grew `installDeploymentBase(basePath, search)`, which reproduces all three things the plugin injects, and the new `apps/web/tests/base-path-boot.snapshot.ts` asserts that no boot URL — 41 manifest rows plus the 2 preloads — resolves outside the prefix; against the root-absolute manifest all 43 did. `auth-gate.e2e.ts`'s load counter now compares against a named `SHELL_PATH` instead of a literal `'/'`.

`apps/web/tests/base-path.e2e.ts` runs the whole flow through `prefix-proxy.ts`, a forty-line stand-in for the deployment's nginx that strips the prefix, forwards upgrades, and answers 404 for anything it was not asked to strip. It observes 44 bundle responses under `/console/plugins/`, exactly two relative preloads and no root-absolute one in `<head>`, both downlinks on `/console/api/events.{mux,host}`, the export controller's HEAD on `/console/api/session.export`, a mirror cookie with `Path=/console/`, and no request at all to a prefix-free `/api`, `/plugins`, or `/auth-gate`. Its last case is the negative one: through an identity proxy the same harness answers 404 for the document, 405 for the RPC uplink, and destroys the WebSocket upgrade, which is what makes "strip the prefix whole" mechanically observable rather than a line in a deployment guide.

The `apps/desktop` packaging check had to follow the manifest: `verifyClientModules` scanned the served index for `/plugins/…client.js` and would have found none, failing the package run with "staged boot served an index naming no client modules". It now accepts either spelling and normalizes to the relative one.

Two browser bundles that never had a runtime dependency on `client-connection` now have one (`session-log-export` and `client-hmr`), as do three experimental packages here; each declares it as `dsh.client.external` plus a peer and dev dependency, which is what `verify-client-packages` requires. `packages/client/hmr/tsconfig.json` moved from the Host base config to the Client one: it is a `packages/client/*` package built by the client aggregate, and only a Client-face config may reference `connection`'s client leaf.

The privileged-method fence in `connection/src/index.ts` is unchanged. Its route is registered `kind: 'prefix'` at `/api`, which matches `/api` and `/api/<anything>` and nothing else, so a path still carrying a deployment prefix never reaches that handler; the only path that does reach it without a readable method name is the bare `/api`, which the downstream gateway already answers 404. Tightening the guard would have edited an upstream file for no behavior change, against keeping the upstream edits minimal and same-shaped.

### Known limitations

- **Origin-scoped storage is not prefix-scoped.** `localStorage` (`dsh.workspace.view.v5`, `dsh.conversation.chat`, and the gate's `accessToken`) and CacheStorage are isolated by origin, never by path. Two prefixes on one host share all of it: workspace view, conversation drafts, and the token key. A same-host multi-prefix deployment needs one subdomain per process, or keys carrying the prefix.
- **PWA is not supported under a prefix.** `apps/pwa` is not composed on the server line and was left untouched: a Service Worker's scope is fixed by its script URL, and the offline cache name and its `'/'` key are origin-global, so two prefixed deployments would overwrite each other's offline shell. `apps/web/public/manifest.webmanifest` keeps its root-absolute `id`, `start_url`, and `scope` for the same reason: relativizing them would move the installed application's identity under the prefix without moving the worker or the caches, which is the half of PWA support that cannot be reached from here. The shell's own `<link rel="manifest">` is relative, so the file is still fetched under the prefix.
- **`<base>` changes what a bare fragment link means.** With a base in the document, `href="#x"` resolves against the base rather than against the current address. The shell ships no such link today; one added later would navigate to `/console/#x` from any route.
- **The prefix is a browser-side fact only.** Nothing in the process validates that the proxy strips what `basePath` says it does. A mismatch shows up as 404s and refused upgrades, which the negative e2e case pins but no runtime check reports.
- **Addresses that leave the page are configuration, not resolution.** auth-gate's `loginUrl` and content-frame's `pages[].url` must be written with the prefix already in them; they are assigned or requested verbatim.
