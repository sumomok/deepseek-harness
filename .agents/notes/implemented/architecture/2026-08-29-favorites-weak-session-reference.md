# Agent Note: a workflow's bound session id is a weak reference, resolved fresh at render time

Status: implemented

English | [中文](2026-08-29-favorites-weak-session-reference.zh.md)

## Problem

`@deepseek-ai/dsh-experimental-server-sidebar`'s workflow menu names a conversation by session id in a document that outlives any one session: a workflow's `homeSessionId` persists in the `settings` capability's durable document ([per-account, one `$DSH_HOME` per user](../../../../packages/settings/settings-file/README.md)), while the session it names can be deleted through the ordinary Workspace machinery at any time, by the same user, with no coordination between the two features. Nothing in this package observes session deletion — the workspace domain that owns deletion has no reason to know a settings document elsewhere might reference an id it just removed, and wiring that notification would couple two otherwise-independent capabilities for one feature's bookkeeping. The workflow document therefore *will* end up naming a session that no longer exists, as an ordinary and expected occurrence, not a failure.

## Decision

**A bound session id is a weak reference, resolved fresh at render or action time, never validated at write time.** `ServerMenuWorkflow` carries a bare `homeSessionId: string` (and `ServerMenuSettings` a bare `workbenchSessionId?: string` for the persistent workbench conversation, following the identical rule) with no existence check anywhere in the write path — not in the `POST /server-menu/workflows` route's schema validation, not in the settings namespace's `validate` hook, not in the package's invariant. The one relation those three enforce is internal to the document itself (no two workflows may share an id); whether a named session currently exists is a fact the document does not and cannot promise, because it can go stale the instant after a successful write.

**Staleness is a browser-side, per-action computation, not a durable flag, and it degrades rather than merely displays.** `ServerSidebarRoot` derives `liveSessionIds` from the standard `useSessions` snapshot on every render (`useMemo` keyed on `byId`), and checks a workflow's `homeSessionId` (or the workbench's `workbenchSessionId`) against that live set. Opening a workflow whose session is gone does not render a disabled row for the user to notice and act on later — it creates a fresh conversation immediately, replays the workflow's captured navigation snapshot onto it, and repoints `homeSessionId` at the new session (decision ⑧, [`2026-08-30-server-sidebar-product-console-retrofit.md`](2026-08-30-server-sidebar-product-console-retrofit.md)), so the click that discovers the staleness is the same click that resolves it. A workflow is never filtered out of the list for having a dead reference, silently or otherwise — degrading it is exactly what keeps it in the list, still openable, under its own name.

## Alternatives considered

**Validate `homeSessionId` against the live session list at write time (`POST` or `settings/updated`).** Rejected: it only prevents *adding* a workflow bound to a session that doesn't exist yet — it does nothing for the far more common case, a session that existed when the workflow was saved and was deleted afterward. The document would still go stale on the very next deletion, so the check buys correctness for a narrow window and none for the case that actually matters, while adding a dependency from the settings write path to the live session list (which does not exist in the node half's process the same way, and may not exist at all in a composition without the sessions runtime loaded).

**Have deletion clean up any workflow naming the deleted session.** Rejected: it requires the workspace/session deletion path to know about this package's settings namespace, inverting the ownership this repository's capability-seam conventions ask for (a capability's provider does not reach into an unrelated consumer's durable data on every operation). It would also silently remove a user's own named shortcut, discarding it entirely rather than keeping it usable under a repointed session.

**Render a disabled, labeled row for a stale reference instead of degrading it transparently on open.** This was this note's own original decision for the favorites menu this package shipped with — a grayed-out, non-navigable row carrying an explicit "session deleted" label, kept visible and removable for manual cleanup, never silently dropped from the list. The product-console retrofit replaced it: decision ⑧ requires opening a stale workflow to land the user in a working conversation immediately (a fresh one, with its navigation snapshot replayed), not a dead end they have to notice and clear by hand. Both approaches share the same weak-reference premise above; only the surfacing differs — a visible dead state for the user to act on, versus a same-click repair.

**Store a denormalized snapshot of the session's title at save time, shown even when stale.** Rejected: a workflow's `name` is already a user-chosen name independent of the session's own title (the whole point of a workflow shortcut is a name the user picked, not the session's own), so a second denormalized title would answer a question nobody asks.

## Consequences

The workflow schema stays close to minimal — `{id, name, order, homeSessionId, navSnapshot, savedAt}` — with no status field and no last-verified timestamp; `navSnapshot` is the one addition beyond what a weak-reference document strictly needs, carried because decision ⑧'s degrade path has to know what to replay, not because the weak-reference mechanism itself requires it. The cost is a repeated `O(workflows × liveSessionIds)` membership check on every render (a `Set` lookup per workflow, over a snapshot already read for the "current session" derivation this same component needs), which is negligible at the "handful of conversations" scale a real workflow list has.

Nothing about this decision requires the workflow document to ever fully agree with the live session list, and nothing enforces that it eventually would — a stale `homeSessionId` persists until the next time its workflow is opened, at which point it repoints itself. That is the intended shape of a weak reference: correctness lives at read (or action) time, forever, rather than being chased at every point of write.
