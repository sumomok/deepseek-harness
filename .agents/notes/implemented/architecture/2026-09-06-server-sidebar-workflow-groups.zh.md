# Agent Note: server-sidebar — workflow groups and the temporary section

Status: implemented

[English](2026-09-06-server-sidebar-workflow-groups.md) | 中文

## Problem

[v2b 那一片](2026-09-06-content-component-library-v2b-vendor-views.zh.md)把 `groups` 落进了持久的 server-menu 文档，却一点都没画出来：控制台仍然只显示一条扁平的 我的工作流 列表，`groupId` 不改变任何绘制结果，POST 路由也只收 `workflows` 和 `workbenchSessionId`。那份记录把界面明确留给了下一片。

它旁边还有第二个缺口。控制台自己的每一个入口——工作台、一条 导航 行、一条已保存的工作流——都在内部解析或创建自己的对话，而工作台点击会刻意顶掉一份它已经不能复用的草稿（[干净稿规则](2026-09-04-server-sidebar-clean-workbench-draft.zh.md)）。被顶掉的草稿此后无处可寻：这里没有组合任何会话浏览器，而只有已保存的工作流才有自己的一行。访客真正做过的活儿就这样退场，没有任何回去的路。

出厂的 `dsh-client-ui-workspace` 浏览器表面上解决的是类似问题，实际上不是同一个：它按会话所属的工作区目录分组，而那恰恰是本控制台要移除的词汇；而且它只导出插件入口，树算法是私有的。

## Decision

**分组以车道的形式在每次渲染时现算，从不作为一份列表存储。** 置顶分组在前，其余按 `order`，再是每一条未分组工作流所在的控制台顶层。`client/workflow-actions.ts` 把每条车道写成对两个数组的纯变换（`pinnedGroups`、`otherGroups`、`workflowsInGroup`、`ungroupedWorkflows`），因此这套组合是对着数组断言的，而不是穿过一棵渲染树，并且每条工作流恰好出现在一条车道里。车道是这一段唯一的一层层级，而屏幕上只有缩进在表达它，因此每条车道带 `role="group"` 并由自己的标题行命名（`aria-labelledby`），折叠箭头则指名它折起的那份列表（`aria-controls`）；没有标题行的顶层就是这一段本身，它自己的小标题已经命名了它。

**置顶是分组级的事实，仅此而已。** 一个置顶分组排在所有未置顶分组之前，且不动它的 `order`，因此取消置顶会把它放回原位。刻意不做单条工作流的置顶：车道内的行已经带着手工拖拽的顺序，逐行置顶会与它冲突。

**一次用户动作一个补丁，因为删除分组本身不可拆。** 删除一个分组要把缩短后的分组表和成员被清空的 `groupId` 放进同一次 POST：文档拒绝指名了不存在分组的 `groupId`，所以任何一半单独提交都是会被路由拒收的文档。因此侧边栏注入的席位是 `onSaveMenu(patch)`——一次调用收 `{workflows, groups, workbenchSessionId}` 的任意子集——而不是每张表一个回调。路由的 `readPatch` 接受同样的三键子集，settings 写入仍是合并，因此一次只带 `groups` 的补丁从不重发工作流列表。

**跨组移动有两条路，两条都需要指针或触摸。** 一行可以拖到另一条车道的行上、拖到它的标题行上、或拖到空车道画出的占位文字上——顶层没有标题行，它只在拖拽进行中才画出一条，因为工作流都已归档到分组的控制台，顶层为空正是常态。行上的 移动到… 菜单会列出除它自己所在之外的每一条车道；一个分组都还没有的控制台只有一条车道、没有别处可去，这个控件就不画出来，而不是画一个打开后空无一行的菜单。HTML5 拖放没有触摸的等价物，所以这个菜单不是便利品——它是触摸唯一的路，这也让「控件如何被唤出」成了承重规则：`:focus-within` 挂在行和车道标题行上，绝不挂在被隐藏的容器自己身上，因为 `display: none` 的子树里没有任何可聚焦的东西，永远匹配不上；而一台没有悬停的设备两个条件都不满足，因此在 `@media (hover: none)` 下这些控件从一开始就画出来。每一行、每一条标题行都以一个常驻绘制的控件开头（名字按钮、折叠箭头），聚焦它就唤出其余控件，Tab 随即走进去。`apps/web/tests/server-sidebar.e2e.ts` 会按下那一次 Tab。键盘的可达范围到此为止：`Menu` 把它的列表 portal 到 `document.body` 末尾，既不接管焦点也不响应方向键，那些去处因此排在页面上其余全部可聚焦元素之后。要补上这条路，需要本包自绘一个自己管理焦点的下拉，或者改共享原件，本片两者都不做——它只让焦点离开该行时关掉列表，使一张 portal 出去的列表不会比「被唤出规则随即隐藏掉的触发按钮」活得更久。两条路都通过同一个变换提交：`reorderWithinGroup(workflows, groupId, ids)`，它表达的是「这条车道接下来就是这些行、这个顺序」，在改写 `order` 的同时把每一个被点名的行归入该车道；同组重排与跨组搬运是同一次调用。

**临时工作流由存活的会话目录现算，背后没有任何持久数据。** 五条谓词决定成员资格（`temporarySessions`）：不是子代理的孩子、没有被归档、不是工作台的那个对话、不是任一工作流的 `homeSessionId`、以及——除非它正是屏幕上的那一个——不是空白草稿。最后一条谓词挡住的是「每次去一趟工作台就攒下一条无名空行」；第四条是「保存成工作流之后它自己就离开这一段」的原因，不需要第二套记账机制。行按 `updatedAt` 倒序，段内先显示五条，再给 显示更多。五条谓词里没有一条追问某一行是谁的对话：过滤跑在本进程所服务的整份对话目录上，它之所以读起来像「本人的对话」，靠的是部署形态——一个访客一个进程、一份 `$DSH_HOME`。本包不强制这一点，两份 README 都把它记为限制。

**临时行只显示对话自己的持久标题，否则用固定文案——绝不用 `displayTitle`。** 那个字段的下层回落是目录 basename，再下层是裸的会话 id：前者正是本控制台存在的意义所要移除的词汇，后者则不是禁词断言抓得住的东西，因为裸 id 不匹配任何词。`ServerSidebarRoot` 的 `temporaryRow` 在组件看到之前就把一个会话归约成 `{title | undefined}`，因此那条回落链是渲染树够不到，而不只是没被用到。

**移出列表是归档，问两次，而且第二次点不可能是误触。** 它调用 `ctx.workspaces.archiveSession`：日志与记账位都留在宿主上，这里没有任何东西删除一个对话。但本外壳没有组合任何取消归档的控件，出厂浏览器自己的那个也没有组合进来，所以对使用控制台的人而言这个动作是单向的——控件在提交前会变成第二个、明确的 确定移出 按钮。承担这份重量的是位置而不是计时器：确定移出 向左展开，行的右缘——移出列表 图标原本的落位、也是双击第二下的落点——变成 取消。因此双击是解除而不是提交。Escape 同样解除（监听在 document 上：点击把这一行武装起来时，焦点并没有留在组件自己拥有的任何地方），把这一段折起也解除。

**移出屏幕上那个对话之后，外壳落回工作台。** 归档会连带把当前选中清空（工作区投影自己的清扫），而侧栏载入时的那次落位是一个一次性的 ref，不会再触发第二次，于是控制台会停在一个输入框只读、无话可说的空壳上。因此这次点击成功之后会走一遍工作台落位的同一条路（`landOnWorkbench`——载入时自动落位用的就是它，含新建对话时把 `workbenchSessionId` 写回文档），席位为此多收工作台的两项事实：记录的 id，以及它是否还活着，与点击工作台时收的是同两项。「它是不是屏幕上那一个」必须在归档之前读：归档之后已经没有可比的东西了。归档被拒绝时这一段报的是一句固定文案（「移出失败，请稍后重试」），存的是一个标志位而不是消息：被拒绝的原文出自 host 运行时（`session archive failed: …`），带着本控制台要挡掉的词汇，因此只进浏览器控制台。

**折叠状态与 显示更多 存在浏览器里，不进部署自己的文档。** 落在 `localStorage` 的 `dsh.server-sidebar.view.v1` 下，由那两个视图动作手写读写，而不是走 `defineStore` 的 `persist`：那套机制存取的是整份 state，会让一份过期的工作流列表在每次页面加载时盖掉这个 store 赖以初始化的、从服务端读回的文档。读与写各自被兜住——连 `typeof localStorage` 这道守卫也在 `try` 里面而不是在它前面，因为一个禁用站点数据的浏览器会在那个全局变量自己的 getter 上抛，守卫本身就是会失败的那条语句。没有 `localStorage`、彻底拒绝它、配额写满、或文本读不出来的浏览器，一律回落成全部展开，并且当时那次点击照常生效。这张表在这个 store 见到的两份文档上都按权威分组列表裁剪——加载时的那一份，以及每次保存后答复回来的那一份——因为一台只读不写的浏览器否则会把一个已删分组的折叠记录永远留着；折叠记录是这里唯一一件会随浏览器档案的寿命不断累积的东西。

**invariant 伴生插件对已提交的文档重跑 `validateServerMenu`。** v2b 曾以「没有任何界面能产出违反这些约束的文档」为由，把分组约束从伴生插件里豁免掉。这一片正是那个界面，所以豁免随之撤销：伴生插件调用与路由 `validate` 钩子同一个函数，而不是重述它的规则。

### 本次改动逼出的两条构建事实

**`TEMPORARY_GROUP_ID` 与 `MAX_GROUP_NAME_LENGTH` 迁到 `src/menu-constants.ts`——一个什么都不 import 的模块。** 浏览器半边把这两个都当值读：保留的分组 id 是临时段在自己折叠表里的键，长度上限则给命名输入框自己封顶，让一次注定被拒的写入根本不必跑到路由。折叠表是这个保留 id 唯一的实际用途：任何持久数据都不携带它，`validateServerMenu` 既拒绝占用它的存储分组，也拒绝归在它名下的工作流。而 `src/workflows.ts` 为了持久 schema 引入了 `@deepseek-ai/dsh-settings` 与 `@deepseek-ai/schemastery`，从客户端树对该模块做值导入会把这两个都拽进浏览器 bundle，客户端 bundle 纯度门禁会拒绝。`src/route.ts` 早就出于同样的理由收着本包的 HTTP 路径。

**本包的两个 Node 入口改为各自独立成包。** 伴生插件一旦重跑 `validateServerMenu`，`lib/types/index.js` 与 `lib/types/invariant.js` 就都会走到 `src/workflows.ts`，原来的单次双入口构建会把它提升成一个哈希命名的共享 chunk，而本包精确的 `files` 列表发布不了它——publint 与 `verify-built-package-invariants` 都会拒绝那份产物。`tsdown.config.ts` 现在把 invariant 入口作为 companion 配置传入，`packages/core/agent` 出于同样的理由早已这么做；`clientLibraryConfig` 从 `packages/client/tsdown.client.ts` 导出，因此这次拆分没有重述任何依赖规则。

## Alternatives considered

**复用 `dsh-client-ui-workspace` 的树。** 否决，改为只借它的形状。那个包只导出三个插件入口、`tree.ts` 是私有的，因此根本没有可 import 的东西；把这个包本身组合进来，又正是本控制台一开始就移除掉的（[替换决定](2026-08-29-server-sidebar-replaces-ui-sidebar.zh.md)），而且它的分组键是工作区目录——控制台禁掉的那套词汇。真正带过来的是四个已被解决的问题的形状：三条谓词的可见性过滤、带稳定并列打破的最近性比较器、零或五的折叠（而不是分页）、以及带版本键、并按存活键裁剪的浏览器本地视图账。四者都按本控制台自己的事实重写了一遍。

**逐条工作流置顶。** 否决。出厂客户端没有可对齐的做法——更早的一版按活动置顶的设计被整条否掉了——而逐行置顶会和车道内已有的手工拖拽顺序打架。分组级置顶是本片新造的，两份 README 都如实这么写，而不是暗示继承来的行为。

**删除一个临时对话。** 否决。`ctx.workspaces` 提供的是归档而不是删除，而本控制台没有权限销毁一份部署方可能正在记账的日志。归档加就地二次确认给出的是可见的结果（「它从我的列表上下去了」），而不是破坏性的那个，代价是从本外壳内部看它是单向的——如实记为限制，而不是藏起来。

**两个回调，`onSaveWorkflows` 与 `onSaveGroups`。** 否决。单看每一次写入都合法，但把一次删除分组拆成两次往返，中间那一刻就是一份路由会拒收的文档；而两次之间被打断，留下的就是一个空分组或一个孤儿 `groupId`。一个补丁把原子性变成席位自身的性质，而不是调用方的自觉。

**把折叠状态存进 server-menu 文档。** 否决。谁折了哪条车道是每浏览器的显示偏好，不是关于这个部署的事实；放进文档会让一个浏览器的视图状态变成所有其他浏览器都得读的一次写入，还会为一件清一次缓存就该忘掉的事去动持久格式。

**让分组约束继续留在 invariant 伴生插件之外。** 连同它所依赖的前提一起否决。v2b 的理由是没有界面能产出违反这些约束的文档；这一片就是那个界面。

## Consequences

控制台画的是四段而不是三段，被顶掉的草稿重新有了自己的一行。`groups` 变得可打补丁，因此 v2b 点名的那条限制关闭。临时段在每一次相关变化上都对整份会话目录现算（`session.list` 的 v1 没有分页），所以五行的裁剪缩短的是画出来的东西，不是算出来的东西；一段很长的历史是在浏览器里被过滤的。

两项代价摊开写。分组之间的顺序完全没有界面——一个分组在创建时拿到 `order`，此后只有置顶能动它；持久字段在那里，而会改写它的那个变换不在，因为没有任何东西调用它。以及，移出列表 在本控制台内无法撤销。

`ServerSidebarInjected` 换了形状：`onSaveWorkflows` 变成 `onSaveMenu`，`onOpenTemporary`/`onDismissTemporary` 加入其中，后者还收工作台的那两项事实。归档失败与保存失败一样就地上报，因为组件对两者都不 await——但它走自己的 store 标志位（`temporaryFailed`）和自己那句固定文案，落在发生点击的那一段里，而不是跑到 我的工作流 下面说保存失败。

## Testing

包内单测在 `src` 上逐文件 100%：车道变换与五条成员谓词对着数组测、两个组件对着渲染树测、路由的三键补丁（含一次只带 `groups`、且会让某个 `groupId` 变孤儿的补丁被整份拒收）、以及伴生插件对着五份被破坏的已提交文档。`apps/web/tests/server-sidebar.e2e.ts` 承担真实组合上的浏览器证据——新建分组、把一条工作流移进去、置顶、折叠后刷新、然后在 临时工作流 里找到一段未保存的对话并把它移出列表——它的禁词断言覆盖本包字典这次新增的每一条字符串。其中三步守的是代码本身证明不了的承诺：从一行自己的名字按钮按一次 Tab 落在 移动到… 上——键盘的可达范围就到这里，README 的 Known Limitations 有记——对 移出列表 的一次真实双击之后那一行还在原处，以及把屏幕上打开的那一行移出之后页面落在工作台、整页文字不匹配任何一条禁词。
