# Agent Note: 技能包的视图进得了内容列，而摆数据页的视图先问一句

Status: implemented

[English](2026-09-18-skill-pack-views-and-consent.md) | 中文

## Problem

[判定器那篇](2026-09-18-skill-pack-reconciler.zh.md)与[组件目录注册表那篇](2026-09-18-component-catalog-registry.zh.md)落地之后，这两个包之间还缺三样东西。

第一样是它们之间那根线。`ctx.skillPackParts` 是一个没人提供的服务键，于是每一个点名了部件的技能包在每一套部署上都未激活——fail-closed 的正确答案，也是一个没用的答案。

第二样是视图。技能包发的是视图文件，`ctx.skillPacks.activeViews()` 答得出它们，而没有东西去读这个答案：`component-surface` 的视图索引只从自己的 `Config` 里建，别处一概不取，于是技能包的视图是一个躺在盘上、任何侧栏都不会列出来的文件。让它列出来，就会逼出一个配置来源从来不必回答的问题——第三方的视图写错了，这套部署该怎么办。配置里写错的视图让这一行失败，因为部署自己的 `cordis.yml` 是这套部署自己能改的文件；对技能包也这么干，等于让一份发放过来的技能包里一个坏视图文件把整条内容列拖下水。

第三样是数据页。摆 `toy.crud` 的视图在加载时就按 id 被拒，理由写得很明白：工具那条路在画那个页面之前会问用户，而点侧栏一行谁也没问。这条拒绝保住了部署的安全，也把技能包最想发的那个视图彻底挡在了侧栏之外。

## Decision

**一行适配器把这两个包连起来，而且这条边只在这一处双向跑。** `@deepseek-ai/dsh-experimental-skill-pack-components` 注入 `componentCatalog`、`componentViews` 与 `skillPacks`；它提供 `ctx.skillPackParts`，并把激活技能包的视图注册进去。两个包谁也不依赖谁，只组合了其中一个的部署拿到的仍是各自本来就有的 fail-closed 答案。做成微包而不是 `component-surface` 里的一个入口：那个包必须能在一套完全没有技能包的部署里被组合，且不该为此背上一个指向 `skill-pack` 的 type-only import，反过来对 `skill-pack` 也一样——把适配器放进任何一个里面，都是判定器那篇的边界已经拒过的一条依赖边。

**部件是这套部署**交出来**的组件，不是它注册过的组件。** `ComponentCatalogRegistry` 在构造时收一份 `withheld` 表，并在 `components` 之外答一个 `offered`；`component-surface` 传进去的是 `withheldComponents(options)`，也就是早已决定了 `crud: false` 的部署把哪些组件挡在工具之外的那一个函数。没人摆得出来的组件就画不出来，所以需要它的技能包保持未激活。

**`ctx.componentViews` 就是视图索引，它从两个地方收视图。** 做成服务而不是工具行上的一个 `registerViews` 方法：侧栏路由、命令、适配器的判定，三个读者都得按名字拿到这个索引，而谁也伸不进那一行的闭包。部署自己的 `Config.views` 是这个注册表的构造选项；其余每个贡献者调 `register({ owner, views })` 并拿回一个 disposer。这个注册表是在 `ctx.inject(['componentCatalog'])` 的回调里用 `new ComponentViewRegistry(ctx, options)` 建的，不走 `ctx.plugin`，这样它才早于这一行第一次组件贡献存在，并且在这一行自己的名字下打日志。

**两个来源由同一道判定过，只是后果不同。** `judgeView` 先做参数替换，再走 `validateComponentCall`，再走数据页那条规则，配置视图与贡献视图一视同仁。被拒的**配置**视图让这一行失败，失败前先打一条点明代价的 error 行。被拒的**贡献**视图被丢掉：这一行照常加载，其余每个视图照常在，每个已注册的组件照常注册着，而这次丢弃在这一行自己的名字下以 error 级别说一次。实际上技能包的视图走不到那次丢弃，因为技能包是在被交出去之前就判过的——`PartsSource.judgeView(view, claimed)` 问的正是同一个注册表，一次拒绝让这个技能包带着一条 `view-refused` 未激活，那条记录带着文件、文件里的路径，以及组件表面自己说的那句话。`GET /skill-pack/status` 三样都带；而那份扣下报告，在点到被拒视图时写 error 级别，其余写 info：等插件的技能包会在那一行被组合时自己激活，视图被拒的技能包永远不会。

**id 撞车由判定顺序决定，不走回馈路。** 技能包按技能名顺序判定；激活的技能包为排在它之后判定的技能包占下自己的视图 id，而技能包最先对上的是 `ctx.componentViews.configuredIds`，所以部署自己的视图永远赢。这道检查是技能包集合与配置 id 的纯函数——一个拒掉注册、再把这件事回头告诉技能包根目录的注册表，是一个会来回震荡的环。

**`params` 在视图被加载时替换。** 视图在 spec 里写 `{"$param": "table"}`，旁边列 `params: { table: sys_layer }`；替换发生在校验之前，于是目录判的就是将要被画出来的那份文档，一次拒绝点的也是这份文档里的路径。不认识的参数名、非标量的值、以及被当成列表项用的 `$param`，都各自点名路径拒掉。`$from` 原样不动——那是目录自己在块与块之间的绑定，画的时候才解，而技能包的参数由写这个技能包的人定死。

**视图可以摆数据页，而那一下点击就是那句问话——它是界面上的一次同意，不是对小助手的一次审批。** 加载期那条拒绝在两个来源上都撤了。`ctx.approval` 完全不参与：那个服务是为了在模型跑到一半时打断它而存在的，而且拒绝在没有一个回合能包住它那对审计记录时发问——而侧栏点击恰恰就发生在那种状态里。点下去的那个人就是被问的那个人，也并没有任何工具调用悬着，所以这个问题去的是这条命令自己的答案本来就会画出来的地方：对话里的那一行。

**它要点两下，而第二下带着一枚 nonce。** 第一下回以一个 `ConsentQuestion`——视图 id、一字不差的 `crudApprovalReason(page)`，外加一个一次性值——编码进这条命令唯一的那个文本字段里，前面带一个标记，于是普通的拒绝句永远不会被读成一张卡片。什么都不追加，也不向任何后端要任何东西。对话里那一行用自己的词典画出这张卡片和允许／拒绝；拒绝画 `没有打开。` 并且什么都不发，允许跑 `/show-content-view <view> <nonce>`。用 nonce 而不是标志位，因为标志位是第一下点击本来也写得出来的东西：它只会因为这一行画过一张卡片而被铸出来，绑着登录摘要（没有 `auth-gate` 时绑会话），绑着视图和那张表，第一次被交出来就作废，过了 `crudViewConsentTtlSeconds` 就死。它能失败的每一种方式——不认识、过期、用过、收件人不对——回的都是一张新卡片，而不是一张报错页。

**这同样是把模型挡在外面的那件事。** 跑这条命令的模型拿到的是一张卡片和一个它用不了的值，因为卡片是画给人看的，而那枚 nonce 点名了一个模型根本没有的登录。这条拒绝是在做出这个决定的那个操作里执行的：没有一枚兑掉的票，`judgeDataPage` 什么也不摆。

**一次回答按登录记住，只在本进程里，而且两张表都自己清自己。** `ctx.loginIdentity.current()` 用 `auth-gate` 所持 token 的 SHA-256 摘要给访客起名；回答记在视图 id 和这个页面打开的那张表下面。`crudViewConsent` 在 `'per-login'`（默认）与 `'every-time'` 之间选。没有 auth-gate 那一行就没有名字，于是每次点击都问一遍，也什么都不记。这份记忆只装一个人的回答：摘要一旦不是它上次被问到的那个，前一个人的回答就被丢掉——因为一个进程只服务一位访客，而一次续期、一次重新登录、一次退出再进来，都是同一个座位上的另一个人。票表在每次读时把过期的全扫掉，于是它装着的就是「画出来又没在期限内被回答」的卡片，一张一条。两张表都不持有任何 token，进程没了它们就没了。

**点击追加的仍是 `content-component/shown`。** `content-component/resolved` 要一个 `ToolCallId`，而一次点击没有；会话折叠对这两者一视同仁，invariant 的 `APPENDED_EVENTS` 本来就把两个都点了名，所以无论从哪条路摆进去，内容列、抽取器和一次重放看到的都是同一条记录。

## Testing

单元用例钉住参数替换及它拒绝的每一条路、注册表的两个来源与它们的顺序、id 撞车规则与两条日志行、贡献视图在目录变动之下的判定、这个问题的编码对上「能从持久日志里抵达它的每一种坏文档」、记忆的淘汰与票表的一次性和清扫，以及判定器的 `view-refused` 上报与它那份被占 id 的累积。

一份真实 Loader 组合把 `component-surface` 与 `auth-gate` 一起启起来，并在**没有开着的回合**的会话里点那个命令——侧栏点击就发生在那儿：它从结算好的命令里把卡片读回来，断言它等于 `crudApprovalReason(node)` 且带那行数据表，断言第一下什么都不画也什么都不记，断言回答的那一下摆出记录并追加点名了视图与那张表的 `content-component/shown`，断言同一枚 token 下再点一次不问任何人，断言退出登录、换一枚 token、用过的值、没人铸过的值、来自另一个登录的值、来自另一个会话的值、以及过期的值，每一种都会再问一次且什么都不摆，断言 `'every-time'` 一次也不跳过，断言不摆数据页的视图第一下就打开。对话行自己的用例把两个按钮都按一遍，钉住每个按钮发什么、画什么；浏览器插件那条用例钉住被注入的那条投递。

每一个改动过的 `src` 文件的逐文件覆盖率都是 100%。

## Alternatives considered

**把适配器做成 `component-surface` 里的一个小入口。** 拒了。那会让一个必须能在完全没有技能包的部署里被组合的包背上一个指向 `skill-pack` 的 type-only import，而判定器那篇画下的那条边界——两个包谁也不伸进谁——就只能靠 `import type` 的恩典站着。微包的代价是一份 `package.json`、三处 tsconfig 注册和两张生成目录里的两行，换来的是这条边成为一套部署去组合的东西，而不是一直都在的东西。

**在工具行上加 `registerViews(source)`，而不是做一个 `ctx.componentViews` 服务。** 拒了。有三个读者要按名字拿到这个索引——侧栏路由、命令，和适配器的 `judgeView`——而行上的一个方法一个也够不着。服务还给撞车规则一个家：`configuredIds` 是适配器在技能包被交出去之前要问的一个问题，闭包答不了。

**让被拒的技能包视图也像配置视图那样让这一行失败。** 拒了。发放过来的技能包不是这套部署自己的文件。一个技能包里的一个坏视图，会把内容列、工具和每一个组件一起拖下水，而这套部署自己的配置是对的。

**丢掉被拒的那个视图，让技能包在没有它的情况下激活。** 按判定器那篇已经给出的理由拒了：技能包的正文讲的是整个技能包，模型照着它走进一个被悄悄丢掉的视图，产出的正是整包规则要防的那个画到一半的页面。

**在视图被展示时才替换 `params`。** 拒了。那样目录判的就不是将要画出来的那份文档，一次拒绝点到的会是用户从没写过的一份 spec 里的路径，而一套部署要到第一次点击时才知道参数写坏了，而不是在加载时。

**让这次点击走 `ctx.approval.request`，和工具那条路一样。** 上线之后拿它对着它所服务的那个产品量了一遍，然后拒了。审批服务拒绝在没有开着的回合时发问——它那对 `approval/asked` + `approval/decided` 审计记录必须被一个回合包住——而命令处理器是在用户点的地方跑的，对侧栏条目来说那几乎总是在两个回合之间。于是它本该交付的那件事——*装个技能包、点一下条目、页面就开*——几乎每点一次都答 `没有打开。`。这个问题被放错了类型也是一层：那个服务是为了就一次工具调用在模型跑到一半时打断它而存在的，而这里既没有工具调用，被问的人就是刚点下去的那个人。围着命令处理器开一个回合，或者教审批服务在没有回合时也能发问，两者都是 `packages/interaction` 里的改动，而这一行并不拥有它。

**让同意变成第一下点击本来也能写出来的第二个词，比如 `--consent`。** 拒了。命令行既是别人的也是模型的，而标志位是调用方直接给得出来的值。nonce 之所以存在，只是因为这一行为它画过一张卡片——这正是把「有人看过这张卡片」变成一个前置条件、而不是一种指望的东西。

**把这次同意、或这次拒绝，记成一条会话事件。** 拒了。拒绝就是一个没被打开的页面，关于它没有任何持久的话可说；而同意本来就有它跑的那条命令可供回读：第二条 `command/run` 点名了视图与那枚 nonce，旁边的 `content-component/shown` 点名了视图与那张表。新加一个事件等于往日志里放一份长期授权，而日后读日志的人会把它当成一份长期授权。

**按进程问一次，或按会话问一次，而不是按登录。** 拒了。按进程是一份活得比当初给出它的那次登录还久的授权——一个进程重启过但页面没重载，第二位访客就继承了第一位的回答。按会话则每开一个新对话就再问一次，等于一个下午问十几遍，是让这句问话没人看的最快办法。

**用 token 的 `sub` claim 给登录起名。** 拒了。`auth-gate` 什么都不验签——它整个部署形态说的就是立在它前面的代理已经验过了——所以去读一个 claim，等于这个包断言一个它没查过的身份。摘要是它唯一能诚实给出的名字，代价也记下了：续期一次就是一次新登录。

**把 token 存下来，或存一个用它派生出的带盐值，好让续期之后回答还在。** 拒了。token 只活在一个闭包里、只到两个花它的地方；第三个读者就是第三个可能漏出去的地方，而一份能挺过续期的授权，也就是一份能挺过一次部署方或许有理由要求的重新认证的授权。

**让点击追加 `content-component/resolved`。** 拒了：它要一个 `ToolCallId`，而点击没有。伪造一个等于往日志里放一个不指向任何工具调用的 id，而折叠本来就对 `shown` 与 `resolved` 一视同仁，所以内容列、抽取器和一次重放看到的已经是同一条记录。

## Consequences

一套部署可以把一个技能和这个技能所讲的那个页面，当成一个技能包一起发出去，而用户可以点开那个页面。技能包的视图在它激活时出现、不激活时离开，全程不重启；而视图画不出来的技能包是未激活的，在状态路由里被点名并带着文件与那个值，并以 error 级别写进进程日志——在此之前，它要么根本看不见，要么把控制台一起拖下水。

代价是数据页要过的那句问话，而且是两下点击而不是一下。它和工具那条路展示的是同一张卡，所以用户看到的是一样东西而不是两样，而且它在小助手闲着时也管用——侧栏条目实际上就是在那时候被点的。它换来的代价是卡片留在对话记录里：往回翻到一次旧点击，卡片会连按钮一起再画一遍，按下去的人会被重新问一遍，而不会被告知哪里不对。README 把它和「两张卡片」那条都记成了 Known Limitation。

续期过的 token 就是一次新登录，所以配了 `renewalIntervalSeconds` 的部署每续一次就再问一次。这是「用一枚这里没人验签的 token 的字节给访客起名」的必然结果，而错也是往这个方向错的。
