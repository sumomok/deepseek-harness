# Agent Note: the shared content channel's seam and what it costs

Status: implemented

English | [中文](2026-10-09-content-channel-seam-and-duplication.zh.md)

## Problem

Two content domains deliver calls to the browser tab a session is shown in. `content-frame`'s page tools read and drive the page in the frame; `component-surface`'s `act_component` runs steps inside a drawn component entry in the column, and its `read_component` reports what that entry shows in the same vocabulary. Both domains need the same apparatus — a waiting table on the host, a claim and a report route, a seat that bids for a call and answers it — and neither needs the other's vocabulary: the tools are different, their arguments are different, and what a report means is different.

The client bundle carries a second, unrelated constraint. `packages/client/tsdown.client.ts`'s `dsh-client-bundle-purity` plugin refuses a value import of a package that is not in the bundle's module request list, because such an import either inlines a duplicate runtime (two `ContentChannel` classes, two tab identities) or requires a specifier the module table cannot answer. Type-only imports are erased and stay legal. So a domain in another package can share the channel's *types* but not its *values*.

## Decision

**The apparatus is a Cordis service, and a domain joins it.** `ContentChannel` is provided as `ctx.contentChannel` by the row that composes the content column; a domain registers a `ChannelMember` — its name, its widest report in bytes, and the reader that parses one. The two routes belong to the service and are claimed when the first member registers, so a composition serving no calls keeps 404 on both paths. A waiting call records the member that opened it, and a posted report is read by that member alone; a report for an already-settled call names no member, and every registered member is offered the body in turn, which is how a one-domain channel read one. Each domain publishes its own pending projection under its own key (`contentAccess`, `componentAccess`) because the arms of such a list are that domain's own vocabulary; the fold and the view check are shared in `src/access/channel.ts`.

**The browser half is the same split, provided as `ctx.contentTabChannel`.** The channel owns the tab identity, the hidden-tab grace, the bidding loop, the report retry and the pruning of calls a seat gave up on; a domain joins with a name, a readiness answer and the function that answers one claimed call, and answers either with a document it weighed itself or with an outcome the channel composes the call id and tab into. The outcome form is what lets a domain that has nothing to weigh know no route constant at all. One channel instance per page load is the point rather than an implementation detail: the tab id it mints is what the host pins a session's calls to, so `ContentFrame`'s page seat reads its identity off the instance it is handed rather than minting one, and every domain in the page is the same reader. Before this change the page seat posted its report under a module-level tab id of its own while claiming under the service instance's, which the host reads as two different tabs.

**The seam lives in `content-frame`, and the consequence is stated rather than papered over.** A deployment composing `component-surface` without `content-frame` has no channel, so its `installComponentAccess` injection never fires and neither of its two channel tools is offered at all — the model sees the tools not existing rather than tools that time out on every call. Both READMEs record that prerequisite. Moving the seam into a package of its own, or onto the `content-surface` layer both domains already share, is a pure move and is deferred; nothing in this decision's shape depends on where the files sit.

**Two pure functions stay duplicated, because the seam cannot host them as values.** `component-surface`'s `act-component-projection.ts` folds its own pending list and `act-component-tool.ts` tests its own settled outcome with four-line functions that `content-frame` also has. Importing them as values would be legal for the host half alone — there is no purity gate on a host bundle — but `content-frame` is a peer dependency, and tsdown's host rule (`neverBundle` is the production-dependency set, `alwaysBundle` everything else) inlines a non-production dependency, so the import would ship a second copy of the channel's wire layer inside this package's host artifact. The client half cannot do it at all. The alternative inside the seam — the service exposing `foldCalls` and `isActOutcome` as methods — was weighed and lost: it widens the channel's public surface, and the values it would expose are the channel's internal wire vocabulary rather than anything a domain asks it to do. The duplicates carry comments saying why, and this note is the record.

**`act_component` stays out of the review gate's read-only list, and `read_component` joins it.** `act_component` drives what the user is looking at, so `@haoran/dsh-llm-permission-gateway` judges every call; `read_component` writes nothing and reads the model's own drawing, so it is listed beside the five page reads and `content_show`. The classification file this repository owns, `content-frame`'s `overlay/permission-gateway.patch.yml`, names the five page reads, `content_show` and `read_component`, and leaves both act tools out; `component-surface`'s `tests/act-component-gate.client.spec.ts` holds the shipped file to both dispositions, the way `content-frame`'s own overlay test holds out `content_act`.

**A second tool of a domain is a second arm of its one member, not a second domain.** `read_component` shares the component member, the `componentAccess` pending list and the seat with `act_component`: the list's arm carries the tool's name and its own arguments, the member's reader takes either tool's report (each reading refuses the other's document by its discriminant), and the browser domain answers a claimed call by which of the two it was offered. What is genuinely new on the wire is the reading's arm, `status: 'read'`, declared in `content-frame`'s `access/wire.ts` beside the page documents because that module is the home of every report that crosses the two routes — the page member refuses it, as it refuses a report of steps. The reading itself is produced through the same target resolution the step executor runs through (`component-surface`'s `client/targets.ts`, extracted for this), because a reading that found a control by its own rules would be an addressing vocabulary that drifts from the one a step acts by; the two call vocabularies share the log-shape readers in `act-component-call.ts` for the same reason.

## Alternatives considered

**Move the seam into a neutral package now.** The cleanest end state: neither content row owns the apparatus both consume. It lost on cost and ordering, not on shape — the move re-homes two 300-line modules and their tests, and every fact the seam owns would have to be re-established under a new package's composition tests before the second domain could be trusted on it. The decision above is deliberately written so that the move is mechanical: members, domains and the two route paths are the whole interface.

**Put the channel on `content-surface`, the layer both rows already depend on.** `content-surface` is the host-side entry stream; it has no client face and no `./client` export, so the browser half would have to grow one, and every deployment composing the router without a column would start carrying the channel. Possible, larger, and not obviously better than a package of its own.

**Expose the shared pure functions as service methods.** `ctx.contentChannel.foldPending(opened, settled)` would remove the duplicates without any new package, and the projection unit already has the service in hand at registration. It lost because it makes the channel's wire vocabulary part of its API for the benefit of one caller, and because the browser-half test's own copy of `isActOutcome` (the client bundle can never take a value from another plugin) would stay duplicated either way — so the seam would grow for half the duplication.

**Share one pending projection for both domains.** The arms of the list would become a union of both domains' tool names and arguments, and the browser seat would have to narrow them again. It replaces two small, independent folds with one generic arm that every content tool then depends on, which is a behavior risk to the page domain for no gain in reach.

## Consequences

- The page domain's behavior is unchanged: its mask, cross-origin, `isTrusted` and ref-table rules, its projection key, its schema and its log sentences are byte-for-byte what they were, and its two executor suites and the route suite were not edited to make room for the seam.
- A domain that joins the channel gets the bid loop, the hidden-tab grace, the report retry and the call memory without writing them; what it writes is what answering one of its own calls means.
- The channel is now the one place a tab identity exists. A second instance in one page would make the same seats bid against each other and would settle a report under an identity its claim did not carry, which is why the page-load channel is a single instance and the page seat reads its identity from it.
- A channel tool's existence is a function of the composition: `act_component` and `read_component` both require `tools`, `contentChannel` and `sessionProjections`, and are absent when any is missing. That is loud in the model's own transcript — the tools are not in the request — rather than silent at call time.
- Every content call in a deployment now rides two routes owned by one service, so a composition that serves one domain is on the same code path as one that serves two. The per-`perMember` admission, the same-site fence and the body bounds moved with the routes without changing.
- A future third domain costs a member, a domain and a projection key rather than another copy of the apparatus.

## Testing

`component-surface/tests/act-component-chain.client.spec.tsx` boots the real composition — webserver, tools, sessions, projections, content-surface, content-frame with `pageAccess`, this row — points the browser half's `fetch` at the served origin, and drives one call of either tool from the log event through the projection, the claim, the work in a real document, the report and the model-visible value. It also pins the two refusals, the step ceiling, an unclaimed call, a claimed call that never reports, and that a page-domain seat and the component domain bid under one tab id. `content-frame/tests/content-channel.client.spec.ts` holds the service's side: two members on one route pair, and the session lookup both routes read; its wire suite holds the page member to refusing the component reading's arm. Per-file coverage is 100% on both packages' `src`.
