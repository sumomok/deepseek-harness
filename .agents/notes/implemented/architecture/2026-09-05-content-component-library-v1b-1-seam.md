# Agent Note: drawing a customer's own Vue component in the content column — the vendoring seam

Status: implemented

English | [中文](2026-09-05-content-component-library-v1b-1-seam.zh.md)

## Problem

[The component library's first slice](2026-09-04-content-component-library-v0.md) built the whole path — a tool, a catalog, a judged spec, a seat, a renderer table — over one confirmation bar written here as ordinary React. The library it is meant to become is not written here. Three source libraries a customer maintains hold 354 Vue 2 single-file components; 191 of them address element-ui components directly and 153 CSS rules reach into their markup. That is the material, and the question this slice had to answer is what it costs to draw one of them in the console.

Everything about that material is hostile to the surface it has to land on.

- **It is Vue 2 and the shell is React 18.** Vue 2 has no standalone `render(vnode, container)`, makes what a component receives reactive by rewriting it, and its reactivity does not cross runtime copies — a component built against a second copy stops updating with no error and no warning.
- **It needs element-ui, which is process-wide state.** `Vue.use(ElementUI)` registers roughly eighty components on a runtime's prototype, stamps `$ELEMENT` onto it, and starts a monotonic z-index counter at 2000 — over the harness's own chrome at 1100 and over the approval modal at 1000.
- **It has no git history this repository can consume.** The sources live in a build repository that has no version control worth the name, and the components reach npm through nobody: there is no registry to install them from.

And the console's own rules were already in the way. The repository ships one aggregate compiler face per package with `rootDir: src` and a source plane that never mixes with the artifact plane; `publint` refuses a `file:` dependency; the third-party notice generator refuses a package whose license field is `UNLICENSED`.

## Decision

**The originals come through a seam, not a rewrite.** `@sumomok/toy-surface-kit` is a build of those components, compiled in the repository that owns their sources and vendored here as `packages/experimental/component-kit/vendor/sumomok-toy-surface-kit-0.3.1.tgz`. This slice packages one of the four it exports — `TcFormDetail`, a read-only record — as the catalog entry `toy.record`, because it is the smallest thing that tree carries and therefore the one that proves the whole path with the least of its own behavior in the way: plain data in, nothing emitted, nothing fetched.

**The tarball is a snapshot, and the trap is silent.** pnpm keys the install on the file path plus an integrity hash it does not re-read for an unchanged specifier, so overwriting the tarball in place leaves the build on the previous bytes with no diagnostic. Every rebuild bumps the version, lands under a new file name, and updates the specifier before `pnpm install`.

**Four patches and six gates live in the build repository, not here.** The patches — dropping a `cronstrue` dependency, dropping a download column, fixing a `toUpperCase` call, removing a token read out of `localStorage` — ship inside the tarball under `patches/` with their reasons in its `SOURCES.md`. The gates refuse to publish an artifact that still contains `from 'vue'`, `'element-ui'`, `'toy-core'` or `'toy-comp'`; whose bytes carry a `fontawesome-webfont`; or which fails a jsdom mount smoke. The four text gates catch a barrel import dragging module-load side effects in behind it, the fifth catches a 1.1 MB icon font, and the smoke catches what no text gate can see — a trimmed dependency that throws while its own module evaluates. They are there rather than here because they are conditions on *building* the artifact, and a gate that can only fail after the bytes are committed is a gate that fails too late.

**One Vue on the page, requested rather than bundled.** `dsh.client.external` names `@deepseek-ai/dsh-experimental-vue2-echarts-poc/client`, the row that owns the page's only Vue 2.7; `src/client/vue-shim.ts` re-exports what that row supplies; and `tsdown.config.ts` aliases the bare specifier `vue` onto that file for the browser bundle only. The alias is what makes it hold for code this repository did not write: element-ui is the one inlined library that `require`s `vue` internally, and without the alias it would have pulled a runtime of its own into the bundle. The vendored tarball names neither package — its compiled components run on whatever runtime renders them and resolve their `el-*` tags through the global registration `installElementUI()` performs, which is what makes that function load-bearing. Two consequences are load-bearing and both are gated: **no file under `src/` may import `vue`, by any spelling** — an import there would be aliased back onto the shim and close a cycle, and a subpath import would reach a second copy instead, because the alias maps the bare specifier and nothing else (`tests/source-vue-imports.client.spec.ts`) — and what an inlined library asks for, which no source gate can see, is measured on the artifact: `tests/client-bundle-vue.client.spec.ts` counts `_isVue`, `__patch__` and `defineReactive` in the built `lib/client.js` and fails on a second runtime. (A fourth candidate marker, `initGlobalAPI`, was measured and dropped: it reads zero either way, because the bundler renames a plain function.)

**The alias target is a source file, and that is a deliberate exception to the source/artifact plane rule.** It points at the absolute path of `src/client/vue-shim.ts`, not at `lib/types/client/vue-shim.js`. Rolldown resolves `resolve.alias` before any plugin's `resolveId`, and hard-fails when the target is absent; at bundle time the Client face's `tsc` has not emitted that file yet. The path is absolute because tsdown runs with the repository root as `process.cwd()` in a workspace build. This is the one place in the row where a build config names a `src` path, and it is written into `tsdown.config.ts`'s own module documentation as well as here.

**element-ui is installed exactly once, from one place, with both options written dead.** `installElementUI()` holds the only `Vue.use(ElementUI, { size: 'small', zIndex: 300 })` there is, guarded by a module-scoped boolean; the row's client plugin calls it when it starts. It is not a `ctx.effect`, because `Vue.use` has no counterpart — tearing the row down leaves the components registered on a runtime other rows also hold, so idempotence rather than reversibility is what makes a reload safe. `300` is the number because element-ui's counter only ever climbs: starting at its own 2000 would let an open dropdown cover the window asking the user to approve something, and starting at 300 puts every popper under both the chrome and the modal. Neither option is a `Config` field: the browser half of a plugin receives no cordis configuration and this row has no host half, so making one configurable means a placement package reads the setting and passes it to this function — a change at the call site, not here.

**`vue` and `element-ui` are `dependencies` of the row.** They are its own build inputs rather than something a composing application supplies: element-ui is inlined into the client bundle, and `vue` is present so the row's tests and its type resolution have a runtime to resolve against. What guarantees there is only one Vue at runtime is the bundle alias and the external request, not the package manager — but the two agree anyway, because pnpm resolves this row's `vue` and `vue2-echarts-poc`'s to the same store entry. `element-ui` is pinned to an exact version rather than a range, because its stylesheet is copied into this repository by hand and a range would let the copy and the code drift.

**The stylesheet is a physical copy with one edit.** `src/client/element-ui.css` is `theme-chalk/index.css` with the icon `@font-face` carrying its woff inline as a `data:` URI and the truetype alternative removed: the client bundle injects the sheet as a `<style>` tag, so a relative font URL would resolve against the page rather than against the package.

**Three red lines, each guarding a failure that is invisible when it happens.** No `window.Vue`, ever — element-ui's UMD build installs itself onto whatever it finds there, registering its components on a runtime this row does not own. No `el-dialog`, `el-message`, or `el-notification` in a block — their elements sit outside the host and nothing here can close them; the three popper-bearing components that *are* allowed are a closed table in the bridge, swept when a placement package says the block is off screen. And no data reaches a Vue component unfrozen. The listener map is the measured exception rather than an oversight: Vue's `updateListeners` writes an invoker back into the object it is given, so freezing that map throws where a frozen record is merely skipped — the bridge hands Vue a copy of it, and the caller's own map is left as it was written.

**Freezing happens inside the tightening pass, not beside it.** `sanitizeNodeProps` already rebuilds a block's whole property tree — it walks the schema rather than the record — so every record and list it answers with was built by that walk, and freezing each one as it is returned costs no second traversal and takes nothing away from a caller. Because validation is the one call site of that pass, every reader of an accepted node gets the same guarantee: the tool, the fold over the log, and the browser seat. What it buys is the thing Vue would otherwise do silently — observing a record React still holds, swapping a nested array's prototype, and leaving the two frameworks disagreeing about what changed.

**`toy.record` enters the catalog and the renderer table in the same change, because the pin between them requires it.** `CatalogId` is derived from `COMPONENT_CATALOG` and the seat's `satisfies Record<CatalogId, ComponentRenderer>` fails to compile the day the catalog names a component the row cannot draw. One consequence of the row's new contents: `renderer-coverage.client.spec.ts`, whose whole subject is that compile-time claim, now declares `@vitest-environment jsdom` — the barrel it imports reaches element-ui, whose own module reads `document` as it evaluates.

**What the model sends is a number of pixels; the CSS length is the renderer's.** `labelWidth` is declared `{ kind: 'number', min: 40, max: 240 }` and `TcFormDetailRenderer` turns it into `96px`. The schema union deliberately has no member that can express a CSS value, and this keeps it that way: a length the layout can carry is a measurement, and the unit is added by the code that knows which component wants it. `columnNum` is an enumeration of `1, 2, 3` rather than a range for the same kind of reason — a range would also admit `1.7`.

**A composition that draws a block now composes the Vue runtime row too.** `component-kit` requests `@deepseek-ai/dsh-experimental-vue2-echarts-poc/client` through the loader's module table, and a request nothing provides does not degrade to a blank block — it takes the page's whole client bundle with it. Both overlays that compose this row insert `vue2-echarts-poc` ahead of it, for its runtime alone, and the web scenario links it as a resolvable row.

**Two repository gates get a narrow, documented exemption each.** `publint` reports a `file:` dependency as an error because a user installing from a registry cannot resolve it; nothing under `packages/experimental/` is published, so the check has nothing left to protect and `scripts/publint-all.ts` drops exactly that one message for exactly that area. The third-party notice generator lists `@sumomok/toy-surface-kit` as first party: it is built from sources the same owner supplies, in a sibling repository, and its `UNLICENSED` field is the absence of a public license rather than a restrictive one — naming it there is a statement about who owns it, not a license claim about the sources it compiles, whose terms live in that repository's `SOURCES.md`. `element-ui` additionally gets a repository-URL override, because its manifest declares an scp-style ssh remote (`git@github.com:…`) that is not a URL and that the generator's normalizer would otherwise turn into a dead link.

**The workspace holds two Vue majors, and the documentation site has to say which one it wants.** `vitepress-plugin-mermaid@2.0.17` imports `vue` inside its own `Mermaid.vue` and declares no dependency on it, so its resolution falls to pnpm's hoisted fallback — the slot this workspace now fills with element-ui's Vue 2 — and VitePress's SSR entry fails on `vue/server-renderer`. `pnpm-workspace.yaml` declares the missing peer through `packageExtensions`, which pins the plugin to Vue 3 by resolution rather than by hoisting order.

## Alternatives considered

**Rewriting the components in React.** Rejected on a count rather than a preference: 191 of the 354 single-file components address element-ui components directly and 153 CSS rules reach into their markup, so a rewrite restarts a bug history the customer has already paid for — and would have to be redone for each of the three source libraries. What the seam costs instead is a second framework in the page and everything the two gate tables above are about; that trade is the whole subject of this note.

**Putting element-ui into `vue2-echarts-poc`, beside the Vue runtime it owns.** Rejected: that row is a chart row, and element-ui is roughly eighty components and a 200 KB stylesheet that no chart needs. It would make every composition drawing a chart pay for a component library it does not use, and it would put the decision about `zIndex` and `size` in a package that has no components to configure. The runtime is shared because Vue's identity is process-wide; element-ui is not shared, because it is a library one row happens to use.

**Linking the component tarball with `link:` instead of `file:`.** Rejected on the same ground as the desktop's own vendoring rule: a link resolves to a working tree that can change under the build, so what is committed here would no longer determine what ships. `file:` copies the bytes into the store under an integrity hash, which is what makes the tarball a snapshot. The cost is the silent-overwrite trap, answered by the version bump.

**Publishing the components to a registry and depending on a version.** Rejected as out of scope rather than wrong: it needs a registry, an owner, and a release process for a customer's private components, none of which exist. The `file:` specifier is what the absence of those looks like; it is also why `publint`'s objection is answerable — the package carrying it is not published either.

**Aliasing `vue` to the shim's built output rather than its source.** Tried first and rejected by rolldown: `resolve.alias` runs before any plugin's `resolveId` and hard-fails on an absent target, and the Client face's `tsc` has not emitted `lib/types/client/vue-shim.js` at the moment the bundle is built. The source path is the only target that exists when the alias is consulted.

**Freezing in the browser seat, with `freezeDeep` imported from the component row.** Rejected once the coupling was visible: the seat's only runtime import from the row today is `COMPONENT_RENDERERS`, and a second named import widens what an older row has to export — the exact mismatch `component-surface-mismatch.client.spec.tsx` exists to keep survivable, where a missing renderer costs one block and a missing export costs the page. A copy of the function in the placement package was the other option and was rejected as the same function twice. Freezing inside the tightening pass needs neither.

**Giving the renderer a `visible` prop the seat sets.** Rejected as dead plumbing: the column hands this seat an entry only while the seat is the one on display, so the value would be a constant `true` and its false branch unreachable — and unreachable code is what the per-file coverage gate is for. The bridge's `visible: false` path stays, because it is for a placement package that hides blocks rather than dropping them; this one drops them, and element-ui's own `beforeDestroy` removes the poppers when it does.

**A repository-wide `publint` exemption, or a general fix to the notice generator's repository normalizer.** Both rejected as wider than the fact. The `file:` exemption is scoped to `packages/experimental/`, the one tier that is never published, and drops one message code rather than silencing a package. The scp-style remote is answered by the generator's own documented override table rather than by teaching the normalizer a second URL grammar it has one instance of.

**Reusing `vue2-echarts-poc`'s bridge, or folding the two into one.** Rejected for this slice, with the difference written down rather than left to be discovered: the chart row's bridge freezes shallowly (`Object.freeze({ ...props })`), which is enough for the flat option record a chart is handed and not for a block's nested rows; it carries no listener map and no popper sweep. Converging them means the chart row's bridge grows both and its freeze deepens — a change to a row this slice does not otherwise touch, whose own tests would have to come along in the same PR. The two mount sequences are close enough that the duplication is real and small enough that jscpd does not report it. The review trigger is a third caller, or the first change that has to be made twice. The chart row's shallow freeze is a known gap in that row rather than a decision — the nested values of an echarts option are observed there today — and it is registered as that row's, with a review trigger of its own: a third Vue 2 package joining the page, or the first defect in the chart row that traces to an observed option, an `__ob__` on a value its caller still holds. Neither has happened, and deepening that freeze is a change to a row this slice does not otherwise touch.

**What the repository pays.** The row's client bundle is 2.9 MB raw and 557 KB gzipped, almost all of it element-ui and its stylesheet; before this slice it was a few kilobytes of React. That is the price of the seam, and it is paid by every composition that draws a block — which is why the row is experimental and part of no shipped bundle. The `component-kit` package also gains a Project Reference on `vue2-echarts-poc`, which is what makes the Client compiler face resolve the shared runtime's types rather than pulling its sources into this package's own program.

**What the review of this slice changed.**

- **The bridge copied the listener map on every React commit**, which reassigned a reactive root property and re-rendered the whole Vue tree for commits that changed nothing. The copy is still made — Vue rewrites the object it is given — but only when the caller's map is a different object, remembered in a ref beside the root. The prop record needed nothing: it is frozen in place rather than copied, so Vue's own setter drops a reassignment of the same object. `TcFormDetailRenderer`'s memo over the block's properties is what makes that hold for a record, and the bridge spec now pins it by counting renders rather than by inspecting the DOM, which a root that re-rendered for nothing leaves unchanged.
- **An empty value now keeps its row.** `readDisplay` dropped the empty string as if it were an absent value, which took the label with it and hid from the user that the record has the attribute at all. It is a value: the row is kept and the component's own `v-if` draws the label with nothing beside it. Only a row that names nothing, or whose value is not text, is dropped.
- **The description now states each component's properties**, one derived line under its identity line. It previously told the model that a block carries "the properties its component declares above" while the catalog lines declared none, so the first call for a component the model had not used before was a refusal spent on finding out. The line comes from `propsSchema`, so a component whose schema grows a property offers it in the same edit; the bounds a refusal already states are left out, because the description is paid for on every request.
- **The `publint` exemption has its counterexamples.** Both halves of its condition — the message code, and the `packages/experimental/` prefix — are now asserted by a case that must still fail.
- **The one-Vue assertion over the built bundle is registered as not running on CI**, in the spec's own module doc and in `component-kit`'s Known Limitations. It skips because no CI job that runs this package's `vitest` has built first: the pull-request coverage job does not build, and the master `linux-primary` lane orders its build after its coverage gate. No gate was added for it: the repository has none that reads a built client bundle's text, and the two other specs of this kind, both belonging to shipped rows, skip on CI for the same reason. Giving an experimental row a gate script of its own while those go without would be the asymmetry rather than the fix. The trigger for moving all three is the first gate that reads a built client bundle.
- **`visible` is unconnected here**, and stays so. The bridge's popper sweep runs only when a placement package passes `visible: false`; this column unmounts the blocks instead, so the seat passes nothing and the sweep's path is unused in this composition. It is kept because it is the correct behavior for a placement that hides rather than drops, and it is tested against probe components rather than against this seat.

**Known Limitations, carried in the READMEs.**

- The tarball is a snapshot of a source tree with no version history of its own, so "which sources produced these bytes" is answerable only from the build repository's `SOURCES.md`.
- element-ui ships its own Chinese strings for the copy it owns (a date picker's month names, a table's empty-state line), and they do not follow the interface language.
- `PopupManager.nextZIndex()` only climbs. A session that opens roughly seven hundred poppers eventually passes the approval modal again.
- Three of the four components the tarball exports have no catalog entry and no renderer.
- Nothing a user types into a block survives the column drawing another entry: the seat unmounts the blocks, and the Vue root goes with them.
- A record row whose value is empty shows its label and nothing beside it, which is the component's own reading of an unfilled attribute.
- The built bundle's one-Vue assertion does not execute on CI, for the reason above.
