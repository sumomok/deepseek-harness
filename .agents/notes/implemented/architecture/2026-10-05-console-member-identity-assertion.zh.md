# Agent Note: 控制台的登录闸用一枚签名断言告诉 dsh 请求来自哪位成员

Status: implemented

[English](2026-10-05-console-member-identity-assertion.md) | 中文

## Problem

一个控制台进程要同时服务多个客户账号，而每一项按成员的判断——一个请求能碰哪些会话、一次取数花谁的客户 token、一条审批发给谁的浏览器——都从「这个请求是哪位成员发的」开始。dsh 宿主自己弄不清这件事。客户 token 是一枚 HS512 JWT，签名密钥只在客户系统手里，宿主从里面读出的 claim 都没有经过校验。dsh 浏览器 cookie 是对固定载荷做的 HMAC（`packages/client/connection/src/browser-auth.ts`），不指向任何人；托管控制台的代理又给每位访客同一套启动 token 交换，所以每位访客手里的 cookie 都有效。真正核验登录的是 dsh 前面那道闸——托管控制台上是 `packages/experimental/server-base/deploy/proxy.mjs`，别处是 nginx `auth_request`——它的核验方式是去问客户系统，而不是持有密钥。[浏览器单点登录 Note](2026-08-28-browser-single-sign-on-and-mcp-token-injection.zh.md) 假定每位登录者一个 dsh 进程，登录者的 id 只在代理内部用来挑选那个进程，从不送进 dsh。一个进程服务多位成员之后，那条规则所服务的路由就不存在了。

## Decision

**登录闸是成员身份的唯一来源，并以签名断言的形式把身份送进来。** 客户系统对一枚 token 答 2xx 后，闸门取这枚 token 载荷里的 `login_uid` 作为成员。按续期核验时，还要求答复里的 `token` 与提交的那枚有相同的 `login_uid` 和 `jti`；载荷里没有 `login_uid` 的一律拒绝。闸门核验过并转给 dsh 的每个请求、每次这样的 WebSocket 升级，都带一枚现签的 `x-dsh-member: v1.<载荷>.<签名>`：载荷是 `{"p": <字符串形式的 login_uid>, "aud": <部署 id>, "exp": <签发时间 + 120 秒>}` 的 base64url，签名是对 `v1.<载荷>` 的 Ed25519 签名。格式写在 server-base 的 README 里，宿主侧的核验方照它实现。

**每条路径都删掉客户端自带的头。** 代理的 `forwardHeaders` 在 HTTP 请求和升级上、在 dsh 路径、豁免路径和远端应用路径上一律删掉 `x-dsh-member`，只用现签的值设置它。nginx 样例里，`/console/` 块用核验器答复里的值设置这个头，于是 nginx 不会转发客户端的值；豁免 location 继承一个空值，什么也不转发。nginx 不缓存鉴权子请求，所以一个 200 和它的断言永远不会被重放。

**一个文件服务两种部署，签名可选。** `proxy.mjs` 既可以作为同源代理运行，也可以在 `PROXY_MODE=verify` 下作为 nginx 询问的核验器运行。没有 `MEMBER_ASSERTION_KEY_FILE` 时它只删头，单人部署不受影响。有私钥而没有 `MEMBER_ASSERTION_DEPLOYMENT_ID`、有部署 id 而没有私钥、有私钥而登录闸关闭，三种情况都在启动时让进程停下。

**私钥放在 dsh 宿主读不到的地方。** 环境变量里只放私钥文件的路径，从不放私钥本身；这个文件必须对 dsh 宿主的 OS 用户不可读，也就是闸门以单独的 OS 用户或在单独的容器里运行。托管控制台眼下让闸门和 dsh 以同一个用户跑在同一个容器里；两者分开之前，那里的防伪造只靠 dsh 在容器内只监听 `127.0.0.1`。

**宿主里还没有任何东西读这个头。** dsh 忽略 `x-dsh-member`；让它起作用的，是一个用部署公钥核验断言、并准入它所指成员的宿主侧组件。

### 数字 claim 保留每一位

`login_uid` 是 19 位数字，超出了 JavaScript 数字能精确表示的范围；claim 若是 JSON 数字，两位成员可能被并成同一个 id。闸门的 JSON reviver 把每个数字保留为源文本，`p` 总是这段文本；`JSON.parse` 不给 reviver 源文本的运行时上，闸门拒绝启动。

### 续期答复要与提交的 token 对上

续期端点对一枚有效 token 的回答就是这同一枚 token，所以 `token` 指向另一个 `login_uid` 或 `jti` 的 2xx 说的不是提交的那枚 token，按拒绝处理。`AUTH_CHECK_REPLY=status` 只看状态码，用于不回传 token 的核验路径。

## Alternatives considered

**明文的成员 id 头。** 任何连得上 dsh 端口的进程都能自称任何成员，这个头除了发送方所在的网络位置之外什么也证明不了。签名断言还通过 `aud` 把成员绑定到一个部署上，并在签发两分钟后过期。

**用共享密钥的 HMAC 代替 Ed25519。** 宿主为了验签必须持有密钥，而以宿主用户运行的代码——agent 的文件工具、能读出宿主可读的任意路径（`/proc/<pid>/environ` 也在内）的 `/api/file`——都能读到它，进而替任何成员签名。用 Ed25519，宿主只持有公钥。

**在宿主内校验客户 JWT。** HS512 需要客户系统的签名密钥，宿主持有它，就意味着任何能读宿主文件的东西都能铸造客户 token；闸门去问客户系统也是这个原因。

**用 dsh 浏览器 cookie 当身份。** 它标识的是闸门放行过的一次浏览器会话，签的是固定载荷，而托管闸门给每位访客同一套交换，所以它不指向任何成员。

**保留 nginx 对鉴权子请求的缓存。** 它会在 30 秒窗口内重放同一枚签名断言，还会把 token 写进缓存文件的键里；核验器的内存缓存与请求合并取代了它。

**两份代理副本继续留在仓库外。** 验收站那份已经和托管那份分叉：没有登录闸、分类前不做路径规范化、也没有防止异步处理函数拒绝的保护。身份注入依赖这个文件，所以它进了仓库并带上测试；每一处差异要么成为一个环境变量，要么（两张路由表）取两份清单的并集。

## Consequences

每个核验过的请求现在都以宿主能核验、却无法伪造的形式指明自己的成员——前提是私钥已经隔离、宿主侧核验方已经存在；截获的头在签发两分钟后失效。nginx 样例不把任何 token 写到磁盘上。

与它取代的托管副本相比，闸门会拒绝没有 `login_uid` 的 token，也会拒绝答复里的 token 与提交的不同的续期答复，而那份副本对这两种情况只要是 2xx 就放行；闸门还会读取最多 64 KiB 的答复体。`REMOTE_HOST` 与 `REMOTE_PORT` 没有默认值，每个部署都要写明自己的远端应用。在宿主侧核验方出现、且私钥文件对 dsh 宿主的 OS 用户不可读之前，这个头分不开任何成员。宿主怎样按成员持有客户 token 是另一项决定，本 Note 不涉及。

## Testing

`packages/experimental/server-base/tests/deploy-proxy.spec.ts` 在一个替身 dsh 和一个替身客户系统之间运行两种模式。它覆盖：伪造的 `x-dsh-member` 在 HTTP、升级、豁免和远端应用路径上都被删掉；豁免和远端路径上没有断言；核验过的升级带一枚新断言；续期答复带着另一个 `login_uid` 或 `jti` 时拒绝；claims 核对；启动时的各项拒绝；日志行里既没有成员 id，也没有 token 和断言。测试里照文档格式写的核验方接受一枚新断言，拒绝过期、被篡改、改了 `aud`、或由别的私钥签出的断言。
