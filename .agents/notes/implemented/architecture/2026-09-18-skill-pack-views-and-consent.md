# Agent Note: A skill pack's views reach the content column, and a view that opens a data page asks first

Status: implemented

English | [中文](2026-09-18-skill-pack-views-and-consent.zh.md)

## Problem

Three things were missing between the two packages [the reconciler note](2026-09-18-skill-pack-reconciler.md) and [the catalog-registry note](2026-09-18-component-catalog-registry.md) landed.

The first is the wire between them. `ctx.skillPackParts` was a service key nothing provided, so every pack naming a part stayed inactive on every deployment — the correct fail-closed answer and a useless one.

The second is the views. A pack ships view files, `ctx.skillPacks.activeViews()` answers them, and nothing read that answer: `component-surface` built its view index from its own `Config` and from nothing else, so a pack's view was a file on disk that no sidebar ever listed. Making it list one raises a question the configured case never had to answer — what a deployment does when a third party's view is wrong. A refused configured view fails the row, because a deployment's own `cordis.yml` is a file that deployment can fix; doing the same to a pack would let one bad view file in a delivered pack take down the whole content column.

The third is the data page. A view placing `toy.crud` was refused at load, by id, for a stated reason: the tool path asks the user before that page is drawn, and a click on a sidebar row asked nobody. That refusal kept the deployment safe and kept the one view a pack most wants to ship out of the sidebar altogether.

## Decision

**One adapter row connects the two packages, and it is the only place the edge runs in both directions.** `@deepseek-ai/dsh-experimental-skill-pack-components` injects `componentCatalog`, `componentViews` and `skillPacks`; it provides `ctx.skillPackParts` and it registers the active packs' views. Neither package depends on the other, and a deployment that composes one without the other gets the fail-closed answer each already had. A micro-package rather than an entry inside `component-surface`: that package must be composable in a deployment with no skill packs at all and must not carry a type-only import of `skill-pack` to do it, and the reverse holds for `skill-pack` — an adapter inside either one is a dependency edge the reconciler note's boundary already refused.

**The parts are the components the deployment *offers*, not the ones it registered.** `ComponentCatalogRegistry` takes a `withheld` list at construction and answers `offered` beside `components`; `component-surface` passes `withheldComponents(options)`, the one function that already decided which components a deployment's `crud: false` keeps out of the tool. A component nobody can place cannot be drawn, so a pack requiring it stays inactive.

**`ctx.componentViews` is the view index, and it takes views from two places.** A service rather than a `registerViews` method on the tool row: the index is read by the sidebar route, by the command and by the adapter's judgement, all of which need it by name and none of which can reach the row's closure. The deployment's own `Config.views` are the registry's construction options; every other contributor calls `register({ owner, views })` and gets a disposer. The registry is built with `new ComponentViewRegistry(ctx, options)` inside the `ctx.inject(['componentCatalog'])` callback rather than through `ctx.plugin`, so that it exists before the row's first component contribution and logs under the row's own name.

**Both sources are judged by one pass, and only the consequences differ.** `judgeView` runs parameter substitution, then `validateComponentCall`, then the data-page rule, on a configured view and a contributed view alike. A refused **configured** view fails the row, after an error line naming what that costs. A refused **contributed** view is dropped: the row loads, every other view stands, every registered component stays registered, and the drop is stated once at error level under this row's name. A pack's view never reaches that drop in practice, because the pack is judged before it is offered — `PartsSource.judgeView(view, claimed)` asks the same registry, and a refusal makes the pack inactive with a `view-refused` entry carrying the file, the path inside it and the surface's own sentence. `GET /skill-pack/status` carries all three, and the withholding report is written at error level when it names one, at info level otherwise: a pack waiting for a plugin activates by itself when that row is composed, and a pack with a refused view never does.

**Id collisions are decided by reconcile order, not by a feedback path.** Packs are judged in skill-name order; an active pack claims its view ids for the packs judged after it, and `ctx.componentViews.configuredIds` is what a pack is checked against first, so the deployment's own views always win. The check is a pure function of the pack set and the configured ids — a registry that refused a registration and told the pack root about it would be a loop that oscillates.

**`params` are substituted when the view is loaded.** A view writes `{"$param": "table"}` in its spec and lists `params: { table: sys_layer }` beside it; substitution happens before validation, so what the catalog judges is the document that will be drawn and a refusal names a path in it. An unknown parameter name, a non-scalar value and a `$param` used as a list item are each refused naming the path. `$from` is untouched — it is the catalog's own binding between blocks, resolved at draw time, and a pack's parameters are fixed by whoever wrote the pack.

**A view may place the data page, and the click is the question.** The load-time refusal is gone from both sources. `/show-content-view` on a view carrying a `toy.crud` block puts it through `ctx.approval.request` with `crudApprovalReason(page)` — the same builder, so the same card, the 数据表 line included — before anything is appended or drawn. A refusal, a cancellation, an approval service that is not composed, and a click made outside an open turn all reach one sentence, `没有打开。`

**An answer is remembered per login, in this process only.** `ctx.loginIdentity.current()` names the visitor as the SHA-256 digest of the token `auth-gate` holds; the key is that digest, the view id and the table the page opens. `crudViewConsent` chooses `'per-login'` (the default) or `'every-time'`. No auth-gate row means no name, which means every click is asked about — the fail-closed answer. The memory is a `Set` in the row, holds no token, and is gone with the process.

**The click still appends `content-component/shown`.** `content-component/resolved` requires a `ToolCallId` and a click has none; the session fold reads the two identically and the invariant's `APPENDED_EVENTS` already names both, so the column, the extractor and a replay see one entry either way.

## The decision gate

| Gate | Answer |
|---|---|
| 0. Which standing principle already decides this? | **A capability seam is complete, never one role** puts the second view source behind a registry with a Service Definition, a provider and consumers rather than a callback on the tool row. **Registrations are effects** decides that `register()` answers a disposer and that the adapter holds exactly one. **Model-visible ⟺ logged** decides that a click writes its own session event, because nothing else in the log would explain the entry. **Misconfiguration fails loud** decides that a deployment's own broken view fails the row — and its converse, that a third party's broken view is *not* the deployment's misconfiguration, is why a pack's is dropped instead. **Explicit > implicit at package boundaries** decides that `crudViewConsent` is a validated `Config` field rather than a constant, and that `offered` is a construction-time `withheld` list rather than a rule the catalog infers. |
| 1. How many new permanent surfaces? (count, then list) | **8.** One npm package and plugin row (`@deepseek-ai/dsh-experimental-skill-pack-components`); one Cordis service (`ctx.componentViews`, with `index`, `configuredIds`, `judge`, `register`, `onChange`); one Cordis service (`ctx.loginIdentity`, with `current()`); one method on the already-declared `ctx.skillPackParts` interface (`judgeView`); one member of the closed `PackMissing` union (`view-refused`, carrying `view`, `path` and `reason`, visible at `GET /skill-pack/status`); one on-disk view-file element (`params`, and the `{"$param": "<name>"}` reference inside a spec); one config field (`component-surface.crudViewConsent`); one config field (the catalog registry's `withheld`). No new tool, no new session event, no new route, no new approval gate — the data page's question is the one the tool already asks. |
| 2. Smallest version that proves it right | The second source alone: `ctx.componentViews.register(source)` fed from `activeViews()`, with the sidebar route and the command rebuilt on change. That is the whole claim — a pack can put a page in the column and take it back out, with no restart. The rest is what the claim costs once a pack's view is a real view: the `view-refused` kind, because a judged view that fails must not take the pack's components down with it; `params`, because one pack file ships to deployments that name their table differently; and the remembered answer, because the question the data page now goes through would otherwise be asked on every click and stop being read. |
| 3. Seam or hardcode? | **One seam, named:** `ComponentViewSource` — two real contributors exist today, the deployment's own `cordis.yml` block and this adapter's reading of `activeViews()`, and the sidebar cannot tell them apart. **One config field, justified by two real deployments:** `crudViewConsent` — the console one person works in all day (`per-login`) and a screen several people walk up to (`every-time`) want different answers, and neither is a default the other can live with. **Everything else is hardcoded:** the two refusal sentences, the three parts of the consent key and its separator, configured views winning a collision, substitution happening at load rather than at show time, and the digest being SHA-256. `ctx.loginIdentity` is deliberately **not** a seam — one provider exists and one can exist, because the token lives in exactly one closure; what it is is the narrowest possible read of state that was already there. |
| 4. Boundaries | See below. |

### Boundaries

| Direction | The line | The failure it prevents | Term |
|---|---|---|---|
| Red line | A view that places a data page asks at least once per login. No configuration removes the question; `crudViewConsent` only chooses between once and every time, and a composition that cannot ask draws nothing. | A sidebar click reading a person's data with nobody told. | 永久 |
| Neighbour | `component-surface` judges every view, whoever wrote it; `skill-pack` carries a view file through and reads neither its spec nor its params; `auth-gate` names the login and says nothing about what an answer to a question means. | Three packages each holding part of the judgement, so a view is accepted where it is written and refused where it is drawn. | 永久 |
| Contract | A refused contributed view costs its contributor, not the console: the row loads, every other view stands, and every registered component stays registered. A refused configured view still fails the row. | A deployment losing its whole content column — components, views and the tool — to a typo in a delivered pack, and, in the other direction, a deployment's own broken view being swallowed. | 永久 |
| Temptation | The remembered answer is a `Set` of keys in this process: a digest, a view id and a table name. Nothing is written to disk, to the session log or to a settings document, and the token is never one of the three. | A grant store nobody can see the inside of, outliving the sign-in it was given under. | 暂缓 — 复查触发器: a durable grant is asked for, at which point it needs an owner, a revocation surface and a format version rather than a `Set`. |
| Ceiling | A click made while no turn is open is not asked and draws nothing. The approval service refuses to ask without a turn to enclose its audit pair, and a command handler runs wherever the user clicked. | A question recorded nowhere: an approval whose audit pair has no turn to belong to. | 暂缓 — 复查触发器: an approval path that does not require an open turn, or a command runner that opens one around a handler. |
| Assumption | One visitor per process, named by the digest of the token that process holds, and one pack root offering one set of views. | Inventing a per-user identity this deployment shape does not have, and a view index whose contents depend on who is asking. | 暂缓 — 复查触发器: the multi-user decision. |

## Testing

Unit suites pin parameter substitution and every path it refuses, the registry's two sources and their ordering, the id-collision rule and both log lines, the judgement of a contributed view against a catalog that changes under it, the consent key and both `crudViewConsent` modes, and the reconciler's `view-refused` reporting with its claimed-id accumulation. A real Loader composition boots `component-surface`, `user-approval` and `auth-gate` together and clicks the command: it reads the card back off `approval/asked` and asserts it equals `crudApprovalReason(node)` and carries the 数据表 line, that a grant draws the entry and a refusal draws nothing, that a second click on the same view under the same token asks nobody, that posting a different token asks again, that `'every-time'` asks every time, and that a composition with no approval service draws nothing. The adapter's own composition specs assert the part list, the forwarded subscription and its disposer, and the views appearing and disappearing as packs activate. Per-file coverage of every changed `src` file is 100%.

## Alternatives considered

**Put the adapter inside `component-surface` as a small entry.** Rejected. It would give a package that must compose in a deployment with no skill packs a type-only import of `skill-pack`, and the boundary the reconciler note drew — neither package reaches into the other — would hold only by the grace of `import type`. The micro-package costs a `package.json`, three tsconfig registrations and two rows in the generated catalogs, and it makes the edge a thing a deployment composes rather than a thing that is always there.

**Add `registerViews(source)` to the tool row instead of a `ctx.componentViews` service.** Rejected. Three readers need the index by name — the sidebar route, the command and the adapter's `judgeView` — and a method on the row reaches none of them. A service also gives the collision rule one home: `configuredIds` is a question the adapter asks before a pack is offered, and a closure cannot answer it.

**Let a refused pack view fail the row, the way a refused configured view does.** Rejected. A delivered pack is not the deployment's own file. One bad view in one pack would take down the content column, the tool and every component with it, for a deployment whose own configuration is correct.

**Drop the refused view and activate the pack without it.** Rejected for the reason the reconciler note already gives: the pack's instructions describe the whole pack, and a model following them into a view that was silently dropped produces the half-drawn page the whole-pack rule exists to prevent.

**Substitute `params` when the view is shown.** Rejected. The catalog would then judge a document that is not the one drawn, a refusal would name a path in a spec the user never wrote, and a deployment would learn about a bad parameter on the first click rather than at load.

**Ask the user once per process, or once per session, instead of per login.** Rejected. Per process is a grant that outlives the sign-in it was given under — a second visitor on a restarted-but-not-reloaded process inherits the first one's answer. Per session asks again on every new conversation, which is the same question a dozen times an afternoon and the surest way to make it unread.

**Name the login by the token's `sub` claim.** Rejected. `auth-gate` verifies nothing — its whole deployment shape says the proxy in front of it already did — so reading a claim would be this package asserting an identity it has not checked. The digest is the only honest name it can give, and the cost is recorded: a renewal is a new login.

**Store the token, or a keyed derivation of it, so a renewal keeps the answer.** Rejected. The token is held in one closure and reaches two spenders; a third reader is a third place it can leak from, and a grant that survives a renewal is a grant that survives a re-authentication the deployment may have had a reason to demand.

**Append `content-component/resolved` from the click.** Rejected: it requires a `ToolCallId` and a click has none. Fabricating one would put an id in the log that names no tool call, and the fold reads `shown` and `resolved` identically, so the column, the extractor and a replay already see the same entry.

## Consequences

A deployment can ship a skill and the page that skill talks about as one pack, and a user can click that page open. The pack's views appear when the pack activates and leave when it does not, with no restart, and a pack whose view the surface will not draw is inactive, named in the status route with the file and the value, and written to the process log at error level — where before it would either have been invisible or have taken the console down with it.

The question the data page goes through is the cost. It is the same card the tool path shows, so a user sees one thing rather than two, but it is a question in a place where a click used to be enough — and a click made while the agent is idle is answered with `没有打开。` and nothing else, which reads like a broken row to a user who does not know an approval needs an open turn. The README records it as a Known Limitation, and the honest fix is in the approval service rather than here.

A renewed token is a new login, so a deployment with `renewalIntervalSeconds` set asks again on every renewal. That follows from naming the visitor by the bytes of a token nobody here verifies, and it is the direction the error falls in.
