# Agent Note：助手读本部署自己的业务系统

Status: implemented

[English](2026-09-20-system-map-v0.md) | 中文

## 问题

控制台助手叫不出本部署数据模型的名字。有人用自己的话问起「图层配置」，它只能猜一个英文表名，或者提议一个那个人根本按不动的按钮，而组合里没有任何东西能纠正它。

链条断在第一步。`ctx.bizBackend` 已经能读一个模型的属性、一个模型的默认查询方案、和它的一页行，但这三个都要求调用方事先就知道模型的英文名。没有任何一个读能列出有哪些模型，也没有任何一个读能说出当前登录者可以对一个模型做什么。

目录也大到不能整份交出去。2026-09-20 在真实后端上实测：`GET /nrms-schema-manage/api/meta/resclassname?resClassCnName=&resClassType=1` 一次答回 **103 个专业下的 1219 个模型**，每个模型的完整描述都挂在上面；`GET /nrms-schema-manage/api/meta/resclass/{model}` 对一个 61 属性的模型约 70 KB；`GET /nrms-schema-manage/api/schema/schema?metaEnName={model}` 约 230 KB，含四个默认方案、新增与修改表单各 49 个表单项、其中 27 个带最多十项的字典。同一个端点不带 `metaEnName` 时答回 1129 个方案、34 MB。`GET /nrms-auth/api/auth/userinfo` 带着 1403 行权限 —— 以及紧挨着它们的那个人的账号、工号、手机号与邮箱。

## 决定

**三个工具，分层，且不做常驻上下文。** `system_map_domains` 列出 103 个专业并各带模型计数；`system_map_domain_models` 列出一个专业下的模型，带英文名、给人看的名字、存储表、本部署自己的说明，以及当前登录者对每个模型可以做什么；`system_map_model` 把一个模型整个读下来 —— 每个属性的存储类型、长度、可否为空、是否行标识、缺省值、表单分组、固定取值、取哪个模型的行，与四个默认方案中哪些画它、哪些不填不让存、会不会让这个人改它合并，再加上这个人的权限行。分层是实测逼出来的：103 个专业常驻付得起，1219 个模型的目录付不起，而这两者之中该让谁常驻，要靠首次调用的实测成本来回答。那份实测现在写在 README 里；常驻块不做。

**感知不问任何人。** 三个读都不写、不问、不看屏幕，所以不声明审批，也不注册 `tools/pre-execute` 升级器 —— 与 `content-frame` 的五个读同形。

**读是具名的，并且在读的那一刻就归约。** `biz-backend` 新增 `listModels()`、`describeSchemes()`、`userRights()`，并把 `describe()` 拓宽到发布模型描述本来就写明的那些属性事实。路径不做 `Config`：它们是本部署前端自己的外部规范。`userRights()` 只用权限子树构造答案，一点都不拷贝旁边的个人资料，于是账号、工号、手机号、邮箱都到不了模型请求、会话日志或失败文案。权限行是逐键读的而不是照一张固定操作表读，因为这个部署是靠加键来扩这张表的。三个读拿它做什么——只列出、只描述登录者可以查看的模型，并按一张规则表判出、用七个操作码写出 `may`——归[权限那份 note](2026-09-24-console-rights-judged-once.zh.md)。

**什么都不缓存。** 每次调用都重读目录。进程级缓存需要一条这边校验不了的过期规则，而且本部署自己的前端本来就是先给缓存再后台回源，配置从一开始就不是强一致的。

**每个答案一个字符预算，而不是一个条目计数。** `listingChars` 限住一份清单的各行；`valuesPerAttribute` 与 `noteChars` 限住一行里那两个本身能无限长的值。条目数由预算加游标自然落出来，于是每一样会长大的东西各有一个上限，而不是同一样东西有两个。

**排序按码位。** 专业按编码，模型与属性按英文名；操作按后端列出其操作码的顺序。按区域设置比较会让同一个答案在两台机器上排出两种顺序，而依那个顺序建出的游标会在两次调用之间跳过或重复行。

## 架构决策闸

**0. 已定的原则里，哪条已经替你说了 no？**

| 原则 | 它说了什么 | 结论 |
|---|---|---|
| `biz-backend` 的「capability, not a pipe」（`src/index.ts:15-20`） | 不许有通用 `fetch(path, init)`；路径是外部规范不是部署选择 | **砍掉**「加一个 Config 放行路径前缀」。只能加具名读。 |
| 实测否决系统提示常驻（[笔记](../../archived/feature/2026-07-30-current-sandbox-policy-context.md)） | 一次首见的权限切换让 cache read 掉到 256 token，约 14.7k input token 全部 miss | **砍掉** `ctx.systemPrompt.section()`。 |
| 审查网关分类笔记的「诱惑」栏（[笔记](2026-09-06-content-tools-review-gate-classification.zh.md)） | 把真的离开本机的调用划成只读是已暂缓项，须逐个单独论证 | **砍掉** v0 顺手进 `readOnlyTools`。 |
| `gen-cordis-catalog.ts` 的双向 fail-closed `SERVICE_PAGE`（`:56-64`） | 新 `ctx.<key>` ⇒ 必须新增 subsystem 三件套 | **砍掉** 注册服务。 |
| 「per-user 可见性不存在」（`skill-pack/README.md:260`） | 结构性不存在，等多用户决策 | **砍掉** per-user 知识层。 |
| `packages/AGENTS.md:11`「Require a current owner and need」 | 每个抽象都要有当前消费方 | **砍掉** 为第二个后端预留的 provider 缝，也砍掉经验包的并入 —— 两者都没有真实实例。 |

六条原则在闸的其余部分开跑之前就砍掉了六个候选。

**1. 碰几个新东西？COUNT = 8，全部永久。**

1. 一个新包 `@deepseek-ai/dsh-experimental-system-map`，含 tsconfig、README 三件套、两处根配置登记。
2. 三个模型可见的工具：`system_map_domains`、`system_map_domain_models`、`system_map_model`。
3. 五个工具参数：`after`；`domain` 与 `after`；`model` 与 `after`。
4. 三个 `Config` 字段：`listingChars`、`valuesPerAttribute`、`noteChars`。
5. `ctx.bizBackend` 上三个新公开方法：`listModels`、`describeSchemes`、`userRights`，外加把 `BizMetaAttribute` 拓宽的七个可选字段。
6. 新触达的客户端点三个：模型目录、全方案读、登录权限读。
7. 一份 overlay 文件，任何出厂 profile 都不组合它。
8. 一个快照场景及其夹具，以及给控制台泳道假后端加的三个端点。

**不新增：** 服务键、会话事件、`SessionEventMap` 成员、`MessageSourceMap` 变体、审批闸、路由或 RPC、系统提示分节、`./invariant` 伴生件、subsystem 页、`agent/pre-step` 监听器、缓存、工作区之外的依赖。`SESSION_FORMAT_VERSION` 原样不动。

**2. 能验证它对不对的最小版本是什么？** 就是它。桌上那个更小的一档 —— 索引做成工具而不是常驻上下文 —— 正是这次取的那一档，因为它把唯一没量过的问题变成了一次测量：一次会话的首次调用到底值多少钱。现在的答案是：全部 103 个专业 3466 个字符、约 1163 token；一个典型专业下 12 个模型 2332 个字符、约 856 token；61 属性的参考模型整个读下来 8047 个字符、约 2733 token。这三个数字在手，「其中哪一份该常驻」就回答得了，而在此之前回答不了。

**3. 缝，还是写死？**

| 决策点 | 结论 | 理由 |
|---|---|---|
| 从哪里读后端 | **写死**走 `ctx.bizBackend` | 只有一个真实后端；provider 缝会只有一个消费方、没有第二个实例。 |
| 索引投放在哪 | **写死**成工具结果 | 系统提示那条已被实测否决，而两条尾部消息缝都需要一个刷新触发器，那等于第二套机制。 |
| 那些上限 | **`Config`** | 一份清单值多少钱取决于一个部署有多少模型，而两个部署之间能差一个数量级。 |
| 专业与表单的词表 | **写死** —— `UNFILED`，以及 `query`/`grid`/`add`/`modify`/`card` | 四类方案是 schema 服务自己的编号，属外部规范；`UNFILED` 是模型从一个答案里读出来再传进下一个调用的值，部署改动它等于改动一个协议词。 |
| 前置工程师的经验笔记 | **写死为没有** | 能想出两种形态，但一个真实实例都还没有；Rule of Three 说别切这道缝。 |

**4. 边界（六向）。**

| 方向 | 线 | 它防的具名失败 | 期限 |
|---|---|---|---|
| 邻居 | 本包不发 HTTP、不持凭据；一切后端读经 `ctx.bizBackend` | 出现第二个持访客 token 的地方，那会作废 `auth-gate`「凭据只有两个持有者」的立场，并让 token 出现在本包的日志、错误与夹具里 | 永久 |
| 契约 | 答案是带具名字段的规范 JSON，散文是它上面的 `output.render`；计数、游标、权限都是字段，绝不是要读者从句子里反解出来的东西 | 侧栏或审计去正则匹配模型读的那份清单 —— 这正是 `SkillCatalogSource` 当初被设计成那样要避免的 | 永久 |
| 诱惑 | 有人会想把 `ctx.bizBackend.search()` 接进来，「顺手把行也给模型」 | 推翻 `component-surface` 对用户的承诺「取回来的数据画成表格放在右边，小助手看不到表里的内容」。这一行只读配置与权限，永不读行 | 永久 |
| 红线 | ① `auth.*` 旁边的个人资料永不离开 `userRights()`；② 这三个工具不进网关 `readOnlyTools`；③ 不新增 `SessionEventMap` 成员 | ① 手机号进模型请求与会话日志，而登出并不清洗已写的日志；② 把三个真的离开本机的调用划成只读；③ 逼动 `SESSION_FORMAT_VERSION`，进而让旧 build 拒读日志 | ①③ 永久；② 暂缓，触发器＝实测判官成本超预算，并按分类笔记要求逐个工具单独论证 |
| 天花板 | 一个答案是本部署存下的配置，不是屏幕，也不是服务端会照此执行的保证：本部署自己的权限层在找不到档案时是放开而不是收紧，所以 `may=` 是界面会给出的东西 | 模型拿元数据去断言此刻摆在谁面前的画面 —— 与 `content-frame` 那些读的职责冲突，它自己的文案就写着「这些东西是什么意思该由一个关于这个应用的技能来说」 —— 或者把 `may=` 读成服务端保证 | 永久 |
| 假设 | 一个 dsh 进程 = 一个登录者，所以这里报的权限属于进程而不属于某一次请求 | 一个进程服务多个人时，把 A 的权限当成 B 的呈上去 | 暂缓，触发器＝多用户 token 架构落地；届时这些答案必须改为按会话而不是按进程重算 |

## 备选方案

**靠 `agent/pre-step` 让专业常驻。** 这道缝是对的 —— 追加式、异步、带一个非模型读者用得上的具名 `source` —— 而且一旦测量说该常驻，就是走它。没做是因为测量当时还不存在：103 个专业约 1163 token，付得起，但一次从不问业务系统的会话该不该付这笔钱，是关于真实会话的问题，而工具版正是产生那些会话的东西。以后迁过去很便宜，两边产出同一段文本。

**系统提示分节。** 依本仓自己的真实 provider 实测否决，不是按原则否决。

**虚拟技能，一个模型一条。** `ctx.skills` 从不碰文件系统，技术上收得下；但技能目录既没有条目数上限也没有正文上限，1219 条会把它整个淹掉，而且模型被教育的是「技能是一套要遵循的指令」而不是「一张可读的表」，再加上 `skill` 工具只有一个参数，而这里需要三个。

**一个工具加 `include` 参数。** 对一个模型做更窄的投影 —— 只要属性、只要权限 —— 能压低单次读的开销。为压住面数把它砍了：字符预算与游标已经限住了答案，而一个唯一作用是把本已受限的答案再变小的参数，只是又多一样让模型弄错的东西。加回它的触发器是「实测一次模型读大部分被丢弃」。

**拓宽 `describeScheme` 而不是新增 `describeSchemes`。** 现有那个方法在线上就把请求收窄到一类方案，约 60 KB；新的那个取全部四类，约 230 KB。拓宽现有方法会让 `component-surface` 的每一次数据源调用都为它用不上的事实付那笔更大的读。

**按进程缓存目录。** 暂缓而不是否决。它需要一条过期规则，而诚实的那条 —— 本部署自己的前端就是先给缓存再后台回源 —— 说明配置本来就不是强一致的。触发器是实测单次调用成本超预算。

## 影响

- 在客户 overlay 之外再叠 `overlay/system-map.patch.yml` 的控制台会拿到三个读；其余任何组合一个都拿不到，因为这一行注入 `bizBackend`，没有它就一直 pending。任何出厂 profile 都不组合它。
- 每次调用都把当前登录访客的凭据花在客户后端上。在跑审查网关的控制台上，每次调用还要付一次判官往返，因为这三个是刻意不划成只读的。
- `ctx.bizBackend` 从三个读长到六个。`docs/subsystems/biz-backend.md` 与两份 README 随之更新。
- `describe()` 现在每个属性多发布七个字段。`component-surface` 只读其中两个，不受影响；那条曾断言其余字段被丢弃的用例随行为一起更新。
- 控制台快照泳道钉住的 `tool-schemas.expected.json` 多出三个工具，它的假后端多答三个端点。`snapshots/console/system-map-turn` 钉住一个回合：先读一个专业，再读一个模型 —— 并钉住一处缺席：夹具的权限答案里带着账号、工号、手机号与邮箱，而它们在整份记录里一个都找不到。

## 暂缓

四件事，各带触发器：专业常驻块，等真实会话说出首次调用值多少钱；进程级目录缓存，等实测单次调用成本超预算；划成只读，等实测判官成本超预算并逐个工具单独论证；以及把答案改为按会话而不是按进程重算，等一个进程服务不止一个登录者。

## 测试

`packages/experimental/system-map/tests/`，逐文件 100%：对给定答案的归约、文案与渲染 —— 包含那两条关于缺席的规则，即没有描述点名别的工具、没有拒绝点名补救用的工具 —— 三个工具经真实注册表跑在桩后端上，以及一份经 vendor 里 Loader 启动的 REAL 组合，验提供了什么、描述以什么形态抵达模型、以及一个写不出清单的预算会在装载期失败。处置在同一个注册表上断言：销毁 fiber，三个提供在下一次请求里全都消失。`packages/experimental/biz-backend/tests/biz-backend.spec.ts` 以逐文件 100% 覆盖三个新读，并对权限读断言：五个个人字段值在它发布的内容里一个都找不到。`snapshots/console/system-map-turn` 是成套的免密钥证据。
