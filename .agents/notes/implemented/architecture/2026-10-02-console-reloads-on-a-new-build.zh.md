# Agent Note：控制台在出现新构建时刷新已打开的页面，而不是热替换客户端插件

Status: implemented

[English](2026-10-02-console-reloads-on-a-new-build.md) | 中文

## Problem

控制台服务端升级并重启后，已经打开的页面不会重新加载，而它也没法在自己加载的那份客户端上继续工作。

**插件热替换会把页面弄坏。** `dsh-web-app` 组合了 `dsh-client-hmr`，它把宿主有变化的插件包加载进已打开的页面。2026-10-02 在一个隔离站点上，一个从 0.2.0-rc.2 合并之前的控制台构建加载的页面保持打开，站点重启到 0.2.0-rc.2 构建。页面没有导航。重连之后，`client-hmr` 按新的修订号拉取有变化的插件包，并把它们替换进页面已经加载的那个外壳，随后页面接连报错：`SlotAssemblyError: scope 'session-maybe' rendered without an installed adapter`、`conversation.input: sessions service unavailable`、一个未知会话的绑定错误，以及 `ctx.remote.dynamicCordisRunner.syncInspectManifest is not a function`。React 根组件崩溃，页面变白。整页重新加载（加载新外壳）后恢复。

**旧客户端配新服务端本身也不能用。** 同样的升级、但站点组合里禁用了 `client-hmr` 时，页面画得出来，侧栏也正常，但页面一重连，对话列就崩溃了：`conversation.view` 里报 `TypeError: Cannot read properties of undefined (reading 'foldCompletedTurns')`。0.2.0-rc.2 把 `ui-chat` 的 `transcriptView` 设置的默认值从服务端挪到了客户端，于是旧客户端从新服务端读到 `undefined`，找不到对应的策略。所以只关热替换不够：升级之后页面必须重新加载。

**重启到同一个构建时不能刷新。** 站点重启到页面本来运行的那个构建时，页面留在原地：连接重试、重连，页面照常工作。这时刷新只会白白让访客丢掉页面状态。

**上游从不刷新页面。** 在重连和插件变化中保持页面存活是上游的设计，由它自己的测试钉住：`packages/client/modules/tests/entries.client.spec.ts` 把需要新代码的引导模块报告为「需要整页重新加载」的失败，并保留每个 fiber；`apps/web/tests/client-plugin-live.e2e.ts` 断言导航次数为零。

## Decision

控制台组合关掉插件热替换，并在页面所来自的服务端带着另一个构建回来时，让已打开的页面刷新一次。

**`dsh-experimental-console-profile` 禁用 `client-hmr`。** bundle 层带着 `- id: client-hmr` 和 `disabled: true`，所以已打开的控制台页面永远不会把新的插件包换进正在运行的外壳。

**`dsh-experimental-page-refresh` 检查构建并刷新。** 控制台 bundle 层插入它。一个构建，是所服务首页赋给 `__DSH_BOOT__` 的启动图——插件 id 及其修订号，按集合比较——再加上首页基准目录下各模块脚本的 URL，它们带着 web 外壳的构建哈希；来自别处的模块脚本，例如浏览器扩展加进来的脚本，不属于任何构建。页面在插件启动时记下自己的构建，只记一次。每次连接建立（`connection/reset`，API gateway 的客户端在每次连上时发出）以及页面在连接状态下每次回到前台时，页面请求它被服务时的地址，不用缓存、不跟随重定向，读出那份首页带的构建。只有带着完全一致的启动图标记、且启动图列出本插件的 `200` HTML 应答才算证据；其他任何应答都不改变什么。不含本插件的启动图是仍在组合插件的宿主会服务的，刷新到它上面会留下一个再也不检查的页面。构建不同时，在本标签页的会话存储里记下它，默认立即刷新；之后某次检查又遇到记下的那个构建，或标签页没有可用的会话存储时，改为在横幅里提供刷新。构建相同则清掉记录。宿主在组合完插件之前就服务首页，但 API gateway 要等启动器报告应用就绪、全部插件组合完之后才接受连接；所以检查只从组合完的宿主读首页。插件修订号由包文件的 stat 得出，所以组合完的宿主仍服务同样的文件就是同一个构建，什么都不刷新。完整行为与配置以[包 README](../../../../packages/experimental/page-refresh/README.zh.md) 为准。

**一条横幅承载页面的提示。** 同一个包把刷新提议和连接提示——断开、已重新连接、连不上服务并带刷新按钮——画成一个 `shell.overlay` 条目，由 `dsh-experimental-server-layout` 在它的整框浮层里渲染。控制台此前没有任何连接提示：设置面板的指示只在宽布局里画，而控制台侧栏不是宽布局。

## Why fork code and not a core patch

这项行为反转了上游的一个设计选择，而上游自己的测试钉住了那个选择。改 `dsh-client-hmr` 或 gateway 就成了每次同步都要重新打上的 core-patch，而且会改变出厂的 Web 与桌面产品里的每一种组合，而不只是控制台。在新构建时刷新，是关于一个组合的决定，所以它放在那个组合里：一个 fork 自有的插件加一行禁用，删掉这两行就退役。

## Why the index and not a route

控制台部署的反向代理只把外壳自己的精确路径——`/`、`/index.html` 以及外壳服务的其他文件——转给 dsh 进程，其余全部转给客户自己的后端。新增一条路由（比如构建版本端点）就要在每个部署上改那个代理。文档被服务时的那份首页本来就会被转发，宿主也本来就把启动图渲染进去，所以检查直接读它，node 半边只把自己的设置作为首页全局变量发布出去。请求文档 URL 本身——导航条目的那个——让请求留在代理会转发的路径上，无论页面是在哪个前缀下加载的。

## Testing

本包的测试钉住比较、刷新防护、新触发取代进行中的检查、前台检查等待连接、应答到来前已释放、连接提示和横幅；一个真实 Loader 组合钉住 web 服务器渲染出的设置全局变量。`apps/web/tests/page-refresh.e2e.ts` 拿着一个真实页面，在它底下改变启动图：重连到同一个构建什么都不变；实时组合进又一个客户端插件之后的那次重连让页面恰好刷新一次；刷新后的页面在下一次重连时不再导航；浏览器扩展会加的那种模块脚本不触发刷新。`apps/web/tests/server-sidebar.e2e.ts` 检查控制台组合服务本插件而不带 `client-hmr`，并检查连接被拒的页面在 `server-layout` 的覆盖层里画出连接断开提示，且不压住输入框。`packages/experimental/console-profile/tests/profile.spec.ts` 钉住 bundle 层里的这两行。两个真实构建之间的升级没有在仓库里复现；它在隔离站点上手动验收。

## Alternatives considered

**保留 `client-hmr`，让它在外壳变化时刷新。** 否决：这是针对一个设计上从不导航的上游包的 core-patch；而且上面的证据表明，即使没有热替换，旧客户端配新服务端也会失败，所以每个新构建都必须刷新，而不只是外壳变化时。

**只禁用 `client-hmr`。** 被上面的站点实测否决：页面不再全白，但对话列在新服务端的设置下崩溃。

**每次重连都刷新。** 否决：重启到同一个构建时靠重连就能恢复，刷新会丢掉页面状态；连接反复断开时还会反复刷新。

**比较启动图自己的 `rev`。** 否决：它对条目和批次按宿主列出的顺序做哈希，没有任何东西保证同一个构建两次启动时顺序一致，所以同构建重启可能被读成新构建。按集合比较插件 id 与修订号，从构造上就是稳定的。

**用专门的路由提供构建标识。** 因上面的代理原因否决；它也会把首页已经说明的事再说一遍。

**由服务端通知已打开的页面刷新。** 否决：重启期间页面是断开的，新服务端也不知道每个页面在跑哪个构建。页面自己知道，所以由页面在重连时检查。

**只提供刷新，从不自动刷新。** 否决：发现新构建的页面可能已经画不出来，访客得在坏掉的页面上找按钮。提供刷新只是刷新防护或会话存储排除自动刷新时的后备。

**输入框有未发送草稿时推迟刷新。** 未采用：输入框在每次编辑时把文字草稿写进本地存储，刷新后的页面随所选对话把它恢复，所以文字不会丢。未发送的图片和文件附件是浏览器对象，会丢失；为它们推迟刷新，等于让访客留在一个配不上新服务端的客户端上。

**发布一个宿主已组合完插件的标志，或在不算证据的应答之后再请求一次首页。** 未采用：API gateway 要等启动器报告应用就绪、全部插件组合完之后才注册它的 WebSocket 升级，所以由连接触发的检查不会读到还在组合的宿主，前台检查也要等有连接时才跑。标志只是在首页里把这个先后关系再说一遍，重复请求则会把一个不算证据的应答变成再问一次的理由。

## Consequences

**得到的。** 升级不再让已打开的控制台页面变白或只剩一半能用：重连到新构建的第一次就会刷新它。重启到同一个构建时的表现和以前一样。任何部署的反向代理都不需要改。控制台多了它之前没有的连接提示，包括带刷新按钮的连不上服务状态。

**付出的。** `pnpm run dev:web` 重新构建的插件包在宿主重启之前不会到达任何控制台页面，无论是已打开的还是新加载的，因为向宿主报告插件包重新构建的正是 `client-hmr`。每次连接和连接状态下每次回到前台都多一次首页请求。未发送的附件会在自动刷新时丢失。首页请求被拒绝（浏览器会话过期时答 `401`）或被重定向的页面，会停在它的客户端上，直到访客手动刷新。内容不变的重新构建也算新构建，因为修订号来自文件 stat。这个组合上线之前就打开的页面不带检查，需要手动刷新一次；部署去掉这一行、或某个构建给本包改了名时，已打开的页面也一样，因为检查找的是页面客户端构建时的那个包名。在运行中宿主所服务的目录树里、于重启之前构建（例如 `pnpm run dev:web` 的重新构建），会让下一次检查把页面刷新到新外壳加运行中宿主启动时加载的插件包上，重启时又会再刷新一次；在单独的目录树里构建、重启时再切换，就不会出现这种混合页面。
