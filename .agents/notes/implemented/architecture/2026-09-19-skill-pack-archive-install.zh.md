# Agent Note: 一套技能包集合从一个打好的包安装进来

Status: implemented

[English](2026-09-19-skill-pack-archive-install.md) | 中文

## Problem

[技能包判定那条记录](2026-09-18-skill-pack-reconciler.zh.md)只给了发放侧一条替换部署手里技能包的路：拿一个发放方早就放到机器上的目录去调 `syncPackRoot`。这只是半份发放。一个已经把一套技能包做好的控制台手里拿着的是一个文件，不是别人主机上的一个目录；而收下它的那套部署那边，是一个运维拷一样东西进去、然后指望一步就发生一件事。

有两个方向没被测过，其中一个根本没有答案。装一个打好的包就是缺掉的那个方向；另一个是这个打好的包换成另一套集合时会发生什么——加了一个技能包、改了一个技能包、退役了一个技能包，以及一个 `requires` 在这套部署上已经不满足的技能包。

打好的包还是从外面来的。机器上的目录本来就是运维放进去的那个样子；而一个走过网络的文件带来了两个问题：它完不完整，以及它是不是它自称的那套集合。技能包那几条规则——不带代码、不走出目录、不带链接——必须对着一个谁都没看着它被写出来的文件仍然成立。

## Decision

**发放包是第三种发放方式，不是第二个安装器。** `PackDelivery` 多了 `{ kind: 'archive', name, bytes, limits }`，而 `syncPackRoot` 把它读成目录会读出的那同一套发放集，用同一套技能包规则卡它——包括[视图检查那篇](2026-09-19-skill-pack-view-checks.zh.md)加在暂存树上的清单、视图格式与视图文件那几项——落到同一个同级暂存目录里，再用同一次 rename 换进来。根目录最后等于发放集，重复的发放不写任何东西，失败留下的旧根目录逐字节不变——因为这些都是那唯一一条安装路的性质，不是发放包的性质。

**清单说了算，而且在任何东西落到暂存目录之前就整份核对完。** 发放包根部的 `pack-delivery.json` 写着 `format`、这套集合的 `id` 和 `version`，以及每个文件一条 SHA-256；每个技能包文件放在 `packs/<pack>/` 下面。发放包会因为以下情形被拒：格式版本不认识、清单不成其为清单、清单没声明的条目、清单声明了而发放包里没有的文件、对不上的摘要、点不出技能包目录的路径、被发放了两遍的条目名或清单路径，以及超过它被读时那些上限的大小或条目数。`PackInstallRefusal` 把每一条作为封闭联合的成员带出来，和目录发放本来就有的 `code-file`、`path-escape`、`symlink`、`not-a-pack` 并排。

**容器里的元数据什么也决定不了。** 每个被声明的文件都按普通文件写下去，所以别的工具标成符号链接、硬链接或设备的条目装不成它本身：它要么没被声明、按「清单没声明的条目」被拒，要么就当作一个装着那堆字节的普通文件写下去。安装器不读 unix 权限位、也不读条目类型，所以它压根不需要一条关于这些的规则。

**`buildPackArchive(source, set)` 写出安装器要读的那个文件。** 条目按路径排序，一个固定的修改时间——写成本地时间字符串，好让 DOS 日期字段在任何时区都一样——以及一个固定的压缩级别：同一批技能包在同一个身份下产出同样的字节。ZIP 由 `fflate` 读写，它本来就是这个工作区的依赖、本来就在 `THIRD_PARTY_NOTICES.md` 里，于是这里没有一个字节的容器解析是自己拥有的。

**被监视的发放目录就是部署侧的入口。** `deliveries.directory` 加三个经过校验的上限；这个目录说的就是这份发放。恰好一个 `*.dshpack` 文件就是这套部署手里的那套集合，一个也没有就让技能包根目录原样不动，超过一个则直接拒绝而不去裁决。这里不往那个目录里写任何东西：它属于往里拷东西的人。大小在字节之前先被读，所以超限的发放包在这套部署还没把它拿在手里的时候就被拒掉。

**集合的身份只被带着，不被拿来比。** `set.id` 和 `set.version` 和「装了什么、退役了什么」一起记进日志。降级就是一次普通的发放。

**装上或退役一个技能包，改的是这套部署交出什么，绝不是一个用户被允许做什么。** 哪个用户被交出哪个技能包，那是按用户的组合期过滤，它还不存在，要等多用户那个决定；而用户能不能借技能包的页面动手，是客户自己的后端和它前面那张审批卡说了算。一次发放两者都碰不到。

## The decision gate

| Gate | Answer |
|---|---|
| 0. 哪条既有原则已经把这件事定了？ | **优先用维护中的依赖，而不是自己手搓**定了容器：`fflate` 本来就是这个工作区的依赖、也已经有 notices 条目，于是 ZIP 由它读写，这里不拥有一个字节的容器解析。**插件里不写死可调项**定了那三个大小是经过校验的 `Config` 字段而不是常量。**配错要响亮地失败**定了相对路径的 `deliveries.directory` 在加载时就被拒，以及每一次发放包拒绝都是一个点名条目的类型化错误。**包边界上显式胜过隐式**定了那些上限只从 schema 解析一次再交给安装器，而安装器自己没有任何默认值。入口由部署约束定：`dsh` 自己没有鉴权，前面隔着一层对它的特权方法答 403 的代理，所以一条不鉴权的上传路由是红线，而一个宿主本来就管着的目录不是。 |
| 1. 新增多少个永久面？（先数，再列） | **6 个。** 一种落盘的发放包格式（`*.dshpack`：一个带着 `pack-delivery.json` 和 `packs/<pack>/…` 的 ZIP，里面有 `format`、`set` 和每文件 `sha256`）；`PackDelivery` 上的一种发放方式，加上结果带回来的那个 `set`；一个导出的写入函数 `buildPackArchive`；`PackInstallRefusal` 上的七个成员（`duplicate-entry`、`archive-unreadable`、`archive-format`、`archive-manifest`、`archive-entry`、`archive-digest`、`archive-oversize`）；一块 `Config`，即带四个字段的 `deliveries`；一个被监视的目录和它的两条日志。没有新路由、没有新服务、没有新工具、没有新会话事件、没有新审批闸，也没有新依赖。 |
| 2. 能证明它对的最小版本 | 带发放包这种发放方式的 `syncPackRoot`，再加上产出一个发放包的 `buildPackArchive`：一次结果与目录安装逐字节相等的来回。这正是「一个打好的包装得上」的证明，而发放控制台调的也正是这两个。被监视的目录是让运维不必自备一个应用就能用上它的最小东西——读一个目录，没有路由，不新增任何权限。 |
| 3. 做缝还是写死？ | **写死**，因为缝已经在了：`PackDelivery` 就是每个入口都要走的那个联合，所以第二种收发放包的方式加的是一个调用方，不是一层抽象。格式固定的理由和技能包扩展名集合固定的理由一样：条目前缀、清单名、压缩级别和修改时间正是让两次运行产出同一个文件的东西，而一套能改动它们的部署，就是一套它的发放包彼此无法对比的部署。 |
| 4. 边界 | 见下。 |

### Boundaries

| Direction | The line | The failure it prevents | Term |
|---|---|---|---|
| 邻居 | 这一行只往自己的技能包根目录里装技能包，并读那个发放目录。它从不往发放目录里写、从不装插件、也从不运行发放包里带来的任何东西。 | 一套把运维交给它的文件消费掉或改了名的部署；以及一个变成往机器上放可执行文件的路的技能包根目录。 | 永久 |
| 契约 | 装什么由清单说了算；发放包自己条目的元数据什么也不说。每个被声明的文件都按普通文件写下去。 | 一个标成符号链接、硬链接或设备的条目在盘上真的成了那个东西；以及一个在两个同名条目里悄悄留下读取器恰好返回的那一个的安装器。 | 永久 |
| 诱惑 | 一条直接从控制台收下发放包的 HTTP 路由。 | 往这套部署装技能包的那个目录里开一个不鉴权的写入口：`dsh` 自己没有鉴权，而它前面那层代理是拒掉它的特权方法，不是替它鉴权。 | 暂缓 —— 触发条件：发放控制台有了一个可鉴权的身份（多用户 token 那条线），到那时这条路由就鉴权在别的特权方法本来就鉴权的那个地方。 |
| 红线 | 发放包带来的东西一律不执行，它点名的东西一律不写到技能包根目录之外。每一次拒绝都是响亮的、类型化的，并且点名那个条目。 | 发放这条路变成技能包规则本来要堵死的那条装代码的路。 | 永久 |
| 天花板 | 一个发放包是整个读进内存的，由 `maxArchiveBytes` 框住，而那个目录恰好只说一份发放。没有流式、没有续传、没有队列。 | 装了一半的发放；以及一条谁也说不清的、在好几个发放包之间排序的规则。 | 暂缓 —— 触发条件：一套装不进部署愿意给的那点内存的集合；今天这是一次响亮的拒绝，而不是一台被榨干的主机。 |
| 假设 | 宿主允许谁写那个发放目录，谁就决定这套部署交出什么。那个目录带的是宿主自己的访问控制，自己不带任何一条。 | 在一个插件里自造一套权限模型；以及让一个根本没有用户概念的包去回答按用户的问题。 | 暂缓 —— 触发条件：多用户那个决定，它同时也决定哪个用户被交出哪个技能包。 |

## Testing

单元用例两个方向都钉住了发放包：一次经 `buildPackArchive` 再经读取器的来回、同一批技能包无论按什么顺序进来都产出逐字节相同的输出、一个从目录打出来的发放包其条目是清单在前再按路径排序，以及每一条拒绝——读不了的字节、没有清单、不是 JSON 的清单和不是对象的清单、不认识的和缺失的格式版本、格式不允许的清单字段、不成其为摘要的摘要和对不上的字节、没被声明的条目（包括一个 ZIP 目录条目）、清单声明了而发放包里没有的文件、清单里重复的路径、用 `fflate` 流式写入拼出来的重复条目名、点不出技能包目录的声明路径，以及那三个上限各一次。

安装用例把发放包对着它必须等同的那次目录安装来测：两个根目录出来的摘要完全一样、同一个发放包装第二遍不写任何东西、升级会加会换、降级会退役、被改过的发放包让旧根目录逐字节不变且不留下暂存同级目录，以及一个声明了代码文件或走出目录路径的发放包在根目录还没出现前就被拒。

发放目录既被直接测——不存在的目录、空目录、一个发放包、同一个发放包再来一次、两个发放包、超过大小上限的发放包、核对不通过的发放包，以及一份说明、一个点开头的文件和一个目录就摆在真发放包旁边——也在真实组合里被测：一份由 Loader 启动的 `cordis.yml`，它的技能包根目录一开始是空的，把拷进发放目录的那套集合装上，把发放过来但没人注册其部件的那个技能包扣着（带 `plugin-absent` 和 `part-absent`，它的视图一个人也不交），直到部件来源出现；随后升级、降级、拒绝一个放着两个发放包的目录、拒绝一个字节和清单对不上的发放包、拒绝一个超过配置大小的发放包，并在自己的 fiber 被销毁后不再安装任何东西。`src` 的逐文件覆盖率是 100%。

## Alternatives considered

**用 tar 容器而不是 ZIP。** 否决。它的条目类型能让安装器在拒绝里点名一个符号链接条目，而这也是它买到的全部；代价是在一个已经带着 `fflate` 的工作区里再加一个依赖，而真正要紧的那条性质——链接装不成链接——来自把每个被声明的文件都当文件写下去，不来自读一个类型字段。

**边暂存边核对。** 否决。每写一个文件就查一次摘要，意味着装了一半的树是失败安装的常态，而那个暂存目录就得按失败情形一种一种地去想。先把整个发放包核对完，把失败留在一个点上。

**让清单可选，直接读 ZIP 自己的条目表。** 否决。没有清单，发放包说不出自己是什么，被截断的文件和一套小集合分不出来，而读取器自己对重复条目名的取舍就成了决定一套部署手里有什么的东西。

**现在就做一条鉴权的上传路由。** 在这次改动里否决。`dsh` 自己没有鉴权；它前面那层反向代理是对它的特权方法答 403，而不是替它鉴权，所以这条路由要么到不了，要么不鉴权。重新考虑的触发条件记在上面。

**装完就把文件消费掉——删掉，或者改名成 `.applied`。** 否决。那会让一套部署往运维拥有的目录里写东西，并且用「改它」而不是「读它」来回答「哪个发放包才是这份发放」。把文件留在那儿，这个目录就是一句「这套部署手里有什么」的陈述，而重启、重新部署和第二行读到的是同一句。

**在好几个发放包里挑最新的那个。** 否决。按名字最新是一条排序规则，按 mtime 最新是拷贝工具的副产物，按 `set.version` 最新则让降级做不了。拒绝两个发放包是运维唯一能预判的规则。

## Consequences

发放控制台可以把一个文件交给一套部署，而运维把它拷进一个目录就完成了安装。之后这套部署手里有的，正是那个文件带来的东西，包括它退役掉的技能包，以及它加进来、但这套部署暂时还交不出的技能包——那些会装上、保持未激活，并在状态路由上说出自己在等哪个插件或哪个部件。不是在等、而是坏了的技能包是另一回事，[视图检查那篇](2026-09-19-skill-pack-view-checks.zh.md)会拒掉带着它的那份发放。

代价是：发放目录的可信程度就等于宿主在它上面的写权限；以及一套躲在代理后面的部署，仍然没有让控制台经网络发过来的路。两者上面都记了什么会改变它们。

格式从此是一个兼容面：`format: 1` 是这个构建读的那一版，而碰到更晚版本的构建会点名拒掉这个发放包，不去猜。发放包自己的字节对这个包的同一个构建是可复现的；跨压缩器变更还能认出一套集合的，是它清单里的那些摘要。
