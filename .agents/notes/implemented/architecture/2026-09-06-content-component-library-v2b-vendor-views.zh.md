# Agent Note：部署自己写的视图，以及一个菜单读两份目录

Status: implemented

[English](2026-09-06-content-component-library-v2b-vendor-views.md) | 中文

## 问题

内容列里能出现的东西，今天全得由模型摆上去。对一条服务线的控制台来说这个默认是反的：客户每天早上打开的那个排布——站点列表在上、选中的站点详情在下——是部署这套东西的人写死一次、之后不再变的；让模型每次按请求重画，是花掉一个回合去产出一个固定答案，而且每次还不太一样。

控制台已经有「点一下就打开一个固定东西」的那块界面：`content-frame` 提供配置好的页面，侧栏的导航菜单把它们列出来。一块拼装好的视图是同一个手势、换一种内容。缺的东西同时落在三处。

- **部署写不出一块视图。** `show_component` 收的是模型给的 spec。没有办法把同一份 spec 写进 `cordis.yml`，也没有任何保证说写在那儿的东西是工具会接受的 spec——部署要等到用户点下去，才知道这块视图是坏的。
- **菜单只读一份目录。** `readContentPages` 去取 `content-frame` 的 settings，再无其他；`openPage` 跑 `show-content-page`，因为一行能是的东西只有页面。
- **工作流的快照说不清自己抓到了什么。** `navSnapshot` 是 `string[]`：页面 id，回放时对每个跑一遍 `show-content-page`。数组里一个视图停靠点会被当成页面 id 回放，然后悄无声息地什么都不做。

## 决定

**部署配的视图和模型的调用是同一份 spec，过同一道判定。** `Config.views` 收 `{id, title, spec}` 条目，每条都过 `validateComponentCall`——工具体自己跑的那个函数，连 id 和 title 一起判，不是一道更松的「只给配置用」的检查。视图里点了目录没有的组件、或者绑了组件要回读的属性，加载期就失败，报的是模型本来会拿到的那句话。被否掉的替代是给配置视图另写一个校验器：那是两套要保持同步的规则，也是两边第一次对「什么算合法 spec」产生分歧的入口。

**视图经命令进入内容列，命令自己写记录。** `show-content-view <id>` 追加 `content-component/shown`，带 `{entryId, title, spec, by: 'user'}`——视图的 id 就是条目 id，只按内容列分键用的那个名字记一次；折叠 `tool/call` 的那个 `component` 抽取器，把它折进同一种条目。这次点击就是侧栏对着一个会话跑一条命令，跟 `show-content-page` 已经在做的一模一样，所以 `command/run`/`command/done` 这对持久配对是白拿的，内容列也能只靠日志回放。

**记的是整份 spec，不是视图 id。** 一条条目要自足，就像一次调用的参数那样。部署之后改了或删了这块视图，回放出来的仍然是用户当时真正看到的东西，读日志的人也不必拿着一份自己没有的 `cordis.yml` 去解析。

**这个事件读取时必需，不是 ignorable。** `Session.append` 根本没有设置信封 `ignorable` 标记的入口——那个标记由 `dsh-session` 自己的校验读取，而插件够不着的任何东西都写不了它——所以这个事件和 `content/shown`、`content-surface/dismissed` 一样，是运行时必须认识的。本次改动把它登记进 `KNOWN_SESSION_EVENT_TYPES` 和 `docs/persistence-catalog.md`，并把这条限制写进包 README：一个单独构建、排除了本包的运行时，遇到带该事件的日志会整份拒绝而不是跳过。要让它真的可忽略，得改 `dsh-session` 的 append 签名——那是上游，不在这条线能碰的范围内。

**spec 绝不走路由。** `GET /component-surface/views` 答的是 `{views: [{id, title}], homeView?}`，再无其他。点击往内容列里放什么，是在宿主侧、从这条路由列出的同一份索引里追加的，所以页面要不到部署没配过的视图，spec 也只有一条进入通道。这条路由之所以存在，是因为浏览器那半边收不到 cordis 配置——启动清单带的是插件名，不是它们的 `config` 块。

**菜单合并两份目录，按 kind 分派。** `readContentPages` 和 `readContentViews` 各读各家的路由，每一行都带 `kind`；`mergeNavCatalogs` 先接页面、再接视图，各自按自己声明的顺序。没有加 `order` 配置字段：导航顺序跟随部署配置、绝不由用户重排，而固定的来源顺序就能让这件事在两份目录之间继续成立，不必再引入第三个需要同步的字段。路由不可达、非 200、或者文档不可用时，那一份贡献零行，而不是把整个侧栏带下去——只组合两个属主包中的一个，是完全正常的部署形态。

**两个自动首页会在加载期报错。** 内容列一次只显示一样东西，所以同时配了 `homePage` 和 `homeView` 的部署，表达的是这个外壳执行不了的意图。`mergeNavCatalogs` 抛错，位置在 `apply()` 里、任何注册之前；而不是默默采用先读到的那一个，把另一个配置值晾在那里什么都不做、也没有任何地方说明为什么。

**`navSnapshot` 换形状，并拒绝旧形状。** 它现在是 `{kind, entryId}[]`。存着的 `string[]` 被点名拒绝——在 settings 的 `validate` 钩子、路由的 400、以及浏览器侧的 wire 读取三处——而不是被重新解读成页面 id（存下来的每一个当时确实都是这个意思）。本仓库的预发布立场明确拒绝旧的落盘格式，而一份进程会默默重新解读的文档，是永远不会真被转换的那一份。拒绝文案点名 `pnpm --filter @deepseek-ai/dsh-experimental-server-sidebar run convert-nav-snapshot <settings file> [--dry-run]`，转换器随本次改动一起交付，落在 `src/bin.ts` 上、逻辑在 `src/nav-snapshot-migration.ts`：把每个存下的 id 改写成 `page` 停靠点、补一个空 `groups` 列表、通过 `yaml` 的文档模型保留键顺序与被改写值以外的全部注释（挂在被改写的 `navSnapshot` 值上的注释，会随被替换的节点一起消失），并且幂等。

**捕获只留菜单列出的东西。** `captureNavSnapshot` 接过合并目录，把目录里查不到的条目全部丢掉。content 栏里装的不只是导航：agent 画的图表、模型自己用 `show_component` 展示的组件（它的 id 是模型自由写下的，不是一份配置好的视图），以及部署已经不再配置的页面或视图。快照靠重跑每个落点自己的命令来回放，而两条命令都会拒绝部署未配置的 id，所以把这三样中的任何一样记下来，都只会存下一个回放时只能报警告的落点。只按条目 kind 过滤不够：`show_component` 落地成的正是菜单点击落地成的那个 `component` kind。

**转换器放 `src/bin.ts`，不放 `scripts/`。** `packages/*/*/src/bin.ts` 是仓库既有约定：它在包自己 tsconfig 的 `include` 里、被 vitest 覆盖率排除、并且通过跑它的 package script 成为 knip 的 entry。`packages/*/*/scripts/**` 不在任何 compiler face 的 include 中，也不是 knip 的 entry——放那儿的转换器两边都管不着。

**分组只落数据，不做界面。** `ServerMenuSettings` 加 `groups: ServerMenuGroup[]`，工作流加 `groupId?`，`TEMPORARY_GROUP_ID` 被保留：恒可解析、从不入库、被存储分组占用则拒绝。没有任何东西渲染分组。这次格式变更比读它的界面早一片落地，是因为它搭的是 `navSnapshot` 那次变更已经强制发生的同一次拒绝——运维只转换一次，不是两次。

**侧栏躲不掉的改动落在两个文件上。** `session-resolution.ts` 零改动：两种 kind 解析会话的方式完全相同，它们之间的全部差别就是 `open-nav.ts` 里的一张分派表。`nav-snapshot.ts` 成为侧栏跨越的那一处翻译的唯一住所——导航 kind（`page`/`view`）到 content-surface 条目 kind（`page`/`component`）——因为把投影折成快照本来就是它的活儿。反向表由正向表派生，所以两者不可能漂移；`workflow-actions.ts` 的干净稿判断也从同一个函数取，而不是再写一遍 `'component'` 字面量。

## 考虑过的替代

**在目录路由上下发 spec，让浏览器自己追加。** 之所以诱人，是因为这样侧栏根本不需要命令——它手里已经有会话 id，可以自己写记录。否掉的原因是这把 spec 放进了页面：一条会发 spec 的路由，就是页面上任何东西都能读到一份 spec 的路由；而在浏览器里拼出来的追加，是一条宿主从未判定过的记录。命令保住了「只有一条进入通道」，而且用的就是 `show-content-page` 已经在用的那条。

**给视图另写一个只管配置的校验器。** 考虑过，因为部署写的 spec 没有模型可以对话，工具那些面向模型的拒绝文案在启动时读起来别扭。否掉的原因是：这个功能的要点就是「部署能写模型能写的东西」；两个校验器就是对「这份 spec 合不合法」的两个答案，它们第一次不一致的时候，要么一块能启动的视图是工具会拒绝的，要么反过来。加载期文案语气别扭，比这个代价小，而且那句话仍然点名了出问题的路径。

**把存着的 `string[]` `navSnapshot` 读成页面 id。** 存下来的每一个当时确实都是这个意思，所以今天这么读是对的，而且免费。按预发布立场否掉：一份进程在读取时默默升级的文档，是永远不会真被转换的那一份，于是那个兼容分支就成了永久的；而第一个视图停靠点会让这个猜测出错，并且没有任何地方会报。这次拒绝是对运维的一次性代价，而且我们把修它的命令一起递到了他手上。

**让侧栏直接 import `component-surface` 的路由路径和命令名。** 按 `nav-catalog.ts` 与 `http.ts` 已经记下的理由否掉：跨包的值 import 不是本仓库耦合两个 client-adjacent 插件的正规做法。替代它的是「一份副本加一道机械校验」——侧栏的测试 import 属主常量来比对，于是漂移会挂掉一个测试，而不是悄悄让菜单少一行。

**部署同时配了两个首页时择一。** 否掉，因为两种顺序都讲得通，而且哪一种都发现不了：部署写了两个值，其中一个什么都不做，也没有任何地方说是哪一个、为什么。

**分组连界面一起发，或者先发界面。** 两个方向都否掉。先发界面意味着同一个运维要为同一件事经历第二次存储格式变更和第二次转换。两个一起发意味着这一片要扛一次它根本没有验收标准的导航改版。持久形状搭 `navSnapshot` 那次变更已经强制发生的拒绝，界面随后跟上。

## 后果

**买到的。** 部署能写下客户每天早上打开的那个排布，不花模型回合，而且每次结果相同。两份目录是一个菜单、一条合并规则。工作流能回放页面与视图混合的序列。配坏的视图会拦住启动，而不是拦住某一次点击。

**付出的。** `content-component/shown` 是本仓库每个构建都必须认识的会话事件；一个不含本包组装出来的运行时，会拒绝带该事件的日志。`navSnapshot` 的格式变更是一次硬断裂，附带一次性的运维步骤。目录路由，以及 `show-content-page`/`show-content-view` 这两个名字，在两个包里各有一份字面副本，靠测试而不是靠编译器绑在一起。

**证据。**

- `pnpm run build`、`pnpm run typecheck`、`pnpm run doc-sync`（28/28）全绿；`pnpm run lint` 与 `pnpm run hygiene` 停在既有的 `apps/desktop` 基线上；`pnpm run duplication` 停在既有的三处克隆上。
- `pnpm vitest run packages/experimental`：113 个文件、1553 个测试。`component-surface`、`component-kit`、`server-sidebar`、`content-column` 四个包的语句、分支、函数、行覆盖率逐文件 100%。
- `pnpm run test:snapshot examples/content-console`：14 个场景不变。配一块视图不改变任何模型可见的东西——`show-content-view` 是命令，而这条泳道说的 ACP 协议没有调用命令的方法——所以固定产物不需要重录；这条泳道证明的是「带 `views` 的组合真的能起来」，而这正是一份坏 spec 会拦住它的地方。
- `pnpm run test:web:built server-sidebar`：20 个场景，含一条新的、同时组合两份目录的组合（`server-sidebar-views.overlay.yml`），驱动合并后的菜单、点击、排布、绑定，以及存下来的 `{kind: 'view'}` 停靠点。截图在 `.artifacts/web-e2e-server-sidebar-views-{open,binding,workflow}.png`。
- 转换器对着一份真实的 settings 文档跑过 `--dry-run` 与写入两种模式：注释与键顺序保留，第二次跑是空操作。

## 已知限制与推迟事项

- **拼装好的视图不能在控制台里编辑。** 部署改 `cordis.yml` 然后重启。没有创作界面，复核触发点是第一个想要它的部署——到那时，「一块视图的持久住所在哪」就是这一片刻意没有回答的那个问题。
- **没有视图就没有路由。** 目录路由只在 `views` 非空时注册，所以读它的侧栏分辨不出「这一行组合了但什么都没配」和「这一行根本不在」——两者都由 web 服务器的 SPA 兜底作答。两种情况下侧栏都退化成只有页面的菜单，这对两者都是正确行为，但诊断分不出它们。
- **分组存下来了，但不画。** `groups` 目前也不能通过 server-menu 路由的 POST 补丁写入，那个补丁只收 `workflows` 和 `workbenchSessionId`。画分组的那一片要在同一次改动里把它加进白名单。
- **视图停靠点按 id 回放。** 一个在原对话消失后被重建的工作流，是拿当前配置去跑 `show-content-view <id>`，所以部署之后改过的视图，回放出来是它现在的样子、不是当时的样子。原对话里存下的 `content-component/shown` 记录仍然带着用户当时真正看到的东西；退化重建做不到，因为那是一个全新的会话，没有这样一条记录可抄。
- **一个工作流仍然只绑一次对话**，agent 画的图表仍然不进快照。两者都是前几片记下的 v1 边界，这里没有改动。
