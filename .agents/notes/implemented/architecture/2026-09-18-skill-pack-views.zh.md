# Agent Note: 技能包的视图进得了内容列，而视图在用户点下的那一刻打开

Status: implemented

[English](2026-09-18-skill-pack-views.md) | 中文

## Problem

[判定器那篇](2026-09-18-skill-pack-reconciler.zh.md)与[组件目录注册表那篇](2026-09-18-component-catalog-registry.zh.md)落地之后，这两个包之间还缺三样东西。

第一样是它们之间那根线。`ctx.skillPackParts` 是一个没人提供的服务键，于是每一个点名了部件的技能包在每一套部署上都未激活——fail-closed 的正确答案，也是一个没用的答案。

第二样是视图。技能包发的是视图文件，`ctx.skillPacks.activeViews()` 答得出它们，而没有东西去读这个答案：`component-surface` 的视图索引只从自己的 `Config` 里建，别处一概不取，于是技能包的视图是一个躺在盘上、任何侧栏都不会列出来的文件。让它列出来，就会逼出一个配置来源从来不必回答的问题——第三方的视图写错了，这套部署该怎么办。配置里写错的视图让这一行失败，因为部署自己的 `cordis.yml` 是这套部署自己能改的文件；对技能包也这么干，等于让一份发放过来的技能包里一个坏视图文件把整条内容列拖下水。

第三样是数据页。摆 `toy.data-page` 的视图在加载时就按 id 被拒，理由写得很明白：工具那条路在画那个页面之前会问用户，而点侧栏一行谁也没问。这条拒绝把技能包最想发的那个视图——这套部署自己那张表的那块屏——彻底挡在了侧栏之外。

## Decision

**一行适配器把这两个包连起来，而且这条边只在这一处双向跑。** `@deepseek-ai/dsh-experimental-skill-pack-components` 注入 `componentCatalog`、`componentViews` 与 `skillPacks`；它提供 `ctx.skillPackParts`，并把激活技能包的视图注册进去。两个包谁也不依赖谁，只组合了其中一个的部署拿到的仍是各自本来就有的 fail-closed 答案。做成微包而不是 `component-surface` 里的一个入口：那个包必须能在一套完全没有技能包的部署里被组合，且不该为此背上一个指向 `skill-pack` 的 type-only import，反过来对 `skill-pack` 也一样——把适配器放进任何一个里面，都是判定器那篇的边界已经拒过的一条依赖边。

**部件是这套部署**交出来**的组件，不是它注册过的组件。** `ComponentCatalogRegistry` 在构造时收一份 `withheld` 表，并在 `components` 之外答一个 `offered`；`component-surface` 传进去的是 `withheldComponents(options)`，也就是早已决定了 `dataPage: false` 的部署把哪些组件挡在工具之外的那一个函数。没人摆得出来的组件就画不出来，所以需要它的技能包保持未激活。

**`ctx.componentViews` 就是视图索引，它从两个地方收视图。** 做成服务而不是工具行上的一个 `registerViews` 方法：侧栏路由、命令、适配器的判定，三个读者都得按名字拿到这个索引，而谁也伸不进那一行的闭包。部署自己的 `Config.views` 是这个注册表的构造选项；其余每个贡献者调 `register({ owner, views })` 并拿回一个 disposer。这个注册表是在 `ctx.inject(['componentCatalog'])` 的回调里用 `new ComponentViewRegistry(ctx, options)` 建的，不走 `ctx.plugin`，这样它才早于这一行第一次组件贡献存在，并且在这一行自己的名字下打日志。

**两个来源由同一道判定过，只是后果不同。** `judgeView` 先做参数替换，再走 `validateComponentCall`，再走数据页那几条规则，配置视图与贡献视图一视同仁。被拒的**配置**视图让这一行失败，失败前先打一条点明代价的 error 行。被拒的**贡献**视图被丢掉：这一行照常加载，其余每个视图照常在，每个已注册的组件照常注册着，而这次丢弃在这一行自己的名字下以 error 级别说一次。实际上技能包的视图走不到那次丢弃，因为技能包是在被交出去之前就判过的——`PartsSource.judgeView(view)` 问的正是同一个注册表，一次拒绝让这个技能包带着一条 `view-refused` 未激活，那条记录带着文件、文件里的路径，以及组件表面自己说的那句话。`GET /skill-pack/status` 三样都带；而那份扣下报告，在点到被拒视图时写 error 级别，其余写 info：等插件的技能包会在那一行被组合时自己激活，视图被拒的技能包永远不会。

**id 撞车由这些 id 决定，不走回馈路。** 技能包最先对上的是 `ctx.componentViews.configuredIds`，所以部署自己的视图永远赢。两个技能包之间那种撞车由[视图检查那篇](2026-09-19-skill-pack-view-checks.zh.md)定：两个都扣下。两道检查都是技能包集合与配置 id 的纯函数——一个拒掉注册、再把这件事回头告诉技能包根目录的注册表，是一个会来回震荡的环。

**`params` 在视图被加载时替换。** 视图在 spec 里写 `{"$param": "table"}`，旁边列 `params: { table: sys_layer }`，并处在[视图检查那篇](2026-09-19-skill-pack-view-checks.zh.md)加的那个按技能包写一次的 `metadata.pack.viewFormat` 版本之下；替换发生在校验之前，于是目录判的就是将要被画出来的那份文档，一次拒绝点的也是这份文档里的路径。不认识的参数名、非标量的值、以及被当成列表项用的 `$param`，都各自点名路径拒掉。`$from` 原样不动——那是目录自己在块与块之间的绑定，画的时候才解，而技能包的参数由写这个技能包的人定死。

**视图可以摆数据页，而用户点下的那一刻它就打开了。** 加载期那条拒绝在两个来源上都撤了，而且没有任何东西顶上它的位置：没有卡片，没有审批请求，也不铸任何值。有四件事让这就是全部。点击前面再加一张卡片，只是把同一个按钮再按一遍——这个页面画在控制台自己的同源里，旁边就是同一个部署的 [`content-frame`](../../../../packages/experimental/content-frame/README.zh.md) 页面，那些页面点一下就开、什么都不问，所以为人刚刚按下的那一下再讨一句确认，拦不住谁。模型跑不了这条命令：`CommandInvocation` 不带来源，`CommandSourceMap` 只有 `user` 一个成员，并由一条类型断言钉住——哪天多出第二个生产方，那一行就编译不过。模型自己通往那个页面的路——摆 `toy.data-page` 的 `show_component` 调用——仍然走 `ctx.approval` 和它那张卡片，一字未改，因为那里做决定的是模型，而人是在回合中途被打断的。决定权也仍然在部署手上：`dataPage: false` 会把这个组件扣下，而摆它的视图就会在加载时被点名拒掉。至于这句问话本来会住在哪儿，外壳已经替我们答了：`dsh-client-ui-conversation` 对一个从未跑过回合的会话根本不画对话记录，而侧栏旁边那张空白草稿，正是这些点击几乎每一次发生的地方——于是一句摆在命令行上、要人回答的问话，会被造出来、被记进日志，而永远不在屏幕上。

**点击追加的仍是 `content-component/shown`。** `content-component/resolved` 要一个 `ToolCallId`，而一次点击没有；会话折叠对这两者一视同仁，所以无论从哪条路摆进去，内容列、抽取器和一次重放看到的都是同一条记录。

## Testing

单元用例钉住参数替换及它拒绝的每一条路、注册表的两个来源与它们的顺序、id 撞车规则与两条日志行、贡献视图在目录变动之下的判定、视图所过的那几条数据页规则，以及判定器的 `view-refused` 上报与它那份被占 id 的累积。

一份真实 Loader 组合把 `component-surface` 连同命令注册表、会话存储与内容表面路由器一起启起来，并在**没有开着的回合**的会话里点那个命令——侧栏点击就发生在那儿：它断言摆数据页的视图就在那一下里打开，结算是一个不带文案的成功；断言旁边那条 `content-component/shown` 点名了视图、并带着点名那张表的 spec；断言再点一次会再追加一条；断言不摆数据页的视图打开的方式一模一样；断言点名不到配置视图的那一下挣到 `没有这个视图。`，而且什么都不打开。对话行自己的用例钉住它唯一会画的那句话，以及它什么都不画的那些结算。

每一个改动过的 `src` 文件的逐文件覆盖率都是 100%。

## Alternatives considered

**把适配器塞进 `component-surface`，做成一个小入口。** 拒绝。那会让一个「必须能在没有技能包的部署里被组合」的包背上一个指向 `skill-pack` 的 type-only import，而判定器那篇画的边界——两个包谁也不伸进谁——就只能靠 `import type` 的恩典站着。微包的代价是一份 `package.json`、三处 tsconfig 注册和生成目录里的两行，换来的是这条边成为一套部署去组合的东西，而不是永远都在那儿的东西。

**在工具行上加 `registerViews(source)`，而不是做一个 `ctx.componentViews` 服务。** 拒绝。有三个读者需要按名字拿到这个索引——侧栏路由、命令、适配器的 `judgeView`——而行上的一个方法谁也够不着。服务还给撞车规则一个归属：`configuredIds` 是适配器在技能包被交出去之前要问的问题，而闭包答不了它。

**让被拒的技能包视图也像被拒的配置视图那样让这一行失败。** 拒绝。发放过来的技能包不是这套部署自己的文件。一个技能包里一个坏视图，会把内容列、工具和每一个组件全带走——而这套部署自己的配置是对的。

**丢掉被拒的那个视图，让技能包照常激活。** 拒绝，理由判定器那篇已经给过：技能包的说明写的是整个技能包，而一个照着说明走进「被悄悄丢掉的视图」的模型，产出的正是整包规则要防的那种画一半的页面。

**在视图被展示时才替换 `params`。** 拒绝。那样目录判的就不是将要被画出来的那份文档，一次拒绝点的会是用户根本没写过的 spec 里的路径，而且部署会在用户第一次点击时、而不是在加载时，才知道参数写错了。

**让用户确认这次点击——走 `ctx.approval`，或者本包自己画一张卡片。** 拒绝。`ctx.approval` 在没有一个回合能包住它那对审计记录（`approval/asked` + `approval/decided`）时拒绝发问，而侧栏点击就发生在回合之间，所以那条路在几乎每一次点击上回的都是 `没有打开。`，而不是问了什么。本包自己的卡片确实能在回合之间画出来，也确实画过，而它正是上面那四件事排除掉的东西：点击就是那个决定，同一套部署旁边那些屏不问就开，模型够不着这条命令，而这张卡片和它要守的那个页面住在同一个 DOM 里。

**把那张卡片画在这条命令自己的对话行上。** 在上面那条之上再拒一次。外壳对一个从未跑过回合的会话不画对话记录（`ConversationSession` 在会话空白时什么也不渲染，而对话目标对一份只装着命令行的记录报告「没有活动」），而空白草稿正是这套控制台的入口状态，于是那张卡片被造出来、被记进日志，却从没上过屏。本包提出的任何一句要人回答的问话，都得住在对话在每一种状态下都会画的地方。

**从点击追加 `content-component/resolved`。** 拒绝：它要一个 `ToolCallId`，而一次点击没有。伪造一个等于往日志里塞一个谁也不指的 id，而折叠对 `shown` 与 `resolved` 一视同仁，所以内容列、抽取器与一次重放本来看到的就是同一条记录。

## Consequences

一套部署可以把一份技能和这份技能谈论的那个页面作为一个技能包一起发出去，而用户点一下就能把那个页面打开。技能包的视图在它激活时出现、在它不激活时离开，不用重启；而视图画不出来的技能包处于未激活，在状态路由里被点名连同文件与那个值，并以 error 级别写进进程日志——在这之前，它要么根本不可见，要么把整个控制台一起带走。

数据页点一下就开，这正是那条侧栏行存在的意义。换来的代价是部署没法逐次改主意：`dataPage` 一旦打开，每一个摆这个页面的配置视图与贡献视图都会把它打开，剩下的唯一控制就是组件表本身。那和工具拿到的是同一种控制，也是部署真正推得动的那一种。

这条命令唯一会画的那句话仍留在它的对话行上，而空白草稿不显示它。那是一句谁也没法据以行动的拒绝——下一次加载那一行就从菜单里没了——所以没有为了让它可见而挪动任何东西，本篇与包 README 的 Known Limitations 都把它记着。
