# Agent Note：桌面服务端闭包以收敛并封包的形态发布

Status: implemented

[English](2026-08-19-self-contained-desktop-closure.md) | 中文

## 问题

一次 Windows 安装的时间几乎完全花在文件数上。[用真安装器测得](../testing/2026-08-19-windows-install-cost.md)，把载荷的 500.9 MB 以 12453 个文件搬运要 5.67 秒，而同样的字节以 10 个文件搬运只要 0.12 秒：拷贝里 98% 是每文件开销，创建一个 0.446 毫秒。安装器要付两遍这个数量，一遍解压进 `%TEMP%`、一遍拷进安装目录，而这就是 NVMe 上一次全新安装 53.56 秒的主体。机械盘上每文件那项涨两个数量级、每字节那项只涨一个，所以同一个测量说明文件数在那里更重要而不是更不重要。

包里 12452 个文件中有 12426 个是内嵌的服务端闭包——Electron、内置 Node 运行时和应用可执行文件都是少数几个大文件，对文件数毫无贡献。闭包内部，319 个第三方包占 11008 个文件；本仓库自己的 199 个包占 1417 个，tsdown 已经把每个打成一个入口加一个 invariant 模块。

有两条约束决定了能怎么办。运行时是 Cordis：`@deepseek-ai/cordis-plugin-loader` 在启动时读配置、**按包名解析插件**，所以一个静态单包里没有任何东西能让配置里写的名字解析到。而 219 个 workspace 包全部可发布——没有一个是 `private`——所以在构建时把第三方代码内联进它们，会改变 npm 消费者收到的东西。

## 决定

两处改动，只作用于为安装器铺出的那份副本，别处一律不碰。

**第三方树被收敛进 import 它们的包里。** `scripts/bundle-closure.ts` 跑在派生出的载荷上，从每个 `@deepseek-ai/*` 包自己的入口打包，把依赖内联进去。我们的包彼此保持 external，所以加载器仍然按名解析 `@deepseek-ai/dsh-agent-loop`，仍然找到一个同名目录和其中的入口；变的只是那个入口里装着什么。随后，凡是没有任何可达之处再 import 的第三方目录都被删掉。

**剩下的第三方作为一个归档travel。** `scripts/after-pack.cjs` 把它们封进 `resources/server-deps.7z`，由 `customInstall`（`build/installer.nsh`）用模板本来就带着的 `Nsis7z` 插件解开。一个归档在安装器的两遍里都只是一个文件，于是那些文件被创建一次而不是两次。

两者之间的切分依据是**变化频率**，而这正是更新源保持廉价的原因。本仓库的包每次发版都变，因此保持散装。更新源的差量下载建立在一个非固实、1 MB 字典的 7z 之上，其用意正是让一个文件的改动只作废约一个字典份量的块；把每次发版都变的东西封进一个归档，会让改动点之后的每个块都偏移，那就白费了。

跑在派生之后而不是构建面里，是 219 个可发布产物一个字节都没动的原因——这里没有任何东西写进 workspace 里某个包的 `lib/`。它也是唯一能把事情做对的位置：判断哪个第三方目录仍然需要，靠的是组装好的闭包，而包构建拿不到那个视图。

## 哪些保持散装，以及为什么

**原生模块。** `node-pty`、`koffi`、带 `libvips-42.dll` 的 `sharp`、`@vscode/ripgrep`，以及 `node-addon-require-builtin`。它们的 JavaScript 是拼路径去找旁边的 `.node` 或 `.exe` 的，内联之后加载器就找不到它要的文件。

**浏览器产物。** client 构建面产出的那 40 个 `client.js`，它们在页面求值时通过 `window.__ModuleLoader__.load` 自注册。判据是内容而不是 `./client` 这个导出键：一个文件叫什么，不决定它是不是跑在浏览器里。

**本仓库自己的包，作为目录。** 加载器按名字找它们。

## 验证

`verifyStagedBoot` 启动派生出的载荷、拉取首页，然后把首页里点名的每个 `/plugins/<id>/client.js` 都拉一遍，断言它仍然通过 `__ModuleLoader__` 自注册、且没有 `node:` 前缀的 import。正常构建上 38 个模块通过；把引出这条检查的那个 bug 临时放回去，构建当场失败并指名 `/plugins/@deepseek-ai/dsh-typert-registry/client.js`——正是当初报障的那一个。

封包与解包的往返被直接测过：进去 5443 个文件，发布 1289 个，出来 5443 个，重建后的闭包启动正常，首页与原版同样是 12076 字节。

差量下载是量出来的而不是假设的，`scripts/measure/diff-download.mjs` 用 electron-updater 自己的算法比对两份 blockmap：

| 改动 | 下载量 | 占 136 MB |
|---|---|---|
| 我们自己的包，散装 | 192 KB | 0.14% |
| 一个依赖，落在归档内部 | 5.2 MB | 4% |

第二个数字是把一个担心撤销掉，而不是确认它：原以为归档内一处改动会让其后所有块偏移、逼出整包下载，实测只作废约 30% 的归档块——blockmap 的分块在偏移之后能重新对齐。

已在报障的那台机器上安装运行，也在别处的机械盘上装过，那边的评价是「稍稍有些慢，基本在可接受范围内」。

## 备选方案

**`DSH_BUILD_FACE deploy` 构建面。** 最初的提案：在 `host` 与 `client` 之外，由包构建产出自包含产物。真正动手之后被否决。它必须写进每个包的 `lib/`，而那正是 npm 发布的东西，所以要保住发布物不变就得为每个包维护两套产物。而且它根本做不了后半件事：哪个第三方目录仍然可达，是组装好的闭包的性质，不是任何单个包构建的性质。

**把整个服务端入口打成一个文件。** 可能得到的最小闭包，也是 Cordis 加载器唯一无法配合的形态，因为配置点名的插件必须在运行时作为可解析的包存在。

**把整个闭包封起来，而不只是第三方。** 更简单，文件数还能更低。基于差量下载否决：我们的包每次发版都变，把它们封起来会让一次常规更新从 192 KB 变成整个载荷。

**就地打包每个第三方包。** 逐包改写铺好的闭包，而不是从我们自己的入口打包。否决：第三方的 `exports` 映射是任意的，消费者会 import 子路径，要为 319 个别人写的包保住每一条可达子路径，其暴露面远大于打包一张属于我们自己的 import 图。

**裁得更狠。** 流水线已经按后缀、平台和文档边车裁掉了 19469 个文件。剩下的是服务端真正会加载的运行时 JavaScript。

## 影响

载荷从 12452 个文件降到发布 1289 个、解开后 5443 个。安装器 132.9 MB，对比原来的 144.2 MB；闭包 106 MB，对比 135 MB——打包靠 tree-shaking 拿掉的比内联重复放进去的多，这与事先对它的预期相反。

最深相对路径 166 个字符，对比原来的 190，因为 `@earendil-works/pi-ai` 的嵌套树没有了。安装器的解压预算原本只剩四个字符余量，现在约有二十八个，于是 [MAX_PATH 那道悬崖](../bug-fix/2026-08-19-windows-update-max-path-uninstall-loop.md)不再近在咫尺。

有两个包打不了包——`@deepseek-ai/dsh-client-ui-primitives` 与 `@deepseek-ai/schemastery`——它们保留原有全部文件。代价只是文件数，而且由流水线报告出来，不是静默的。

三个坑值得带走，因为每一个都花了一次诊断：

`node-addon-require-builtin` 是个名字看不出来的原生插件。加载器通过它够到 Node 自己的模块图来设置 `loader.internal`，把它内联掉之后，启动会在一个插件之后失败于 `--expose-internals is required`，指向一个从来不相干的 flag。

删除第三方目录要的是可达集，不是一轮扫描。`@babel/code-frame` 因为还有人 import 而存活，而它需要的 `picocolors` 没有别处点名；单轮扫描会把它刚保留下来的那个包的依赖删掉。

浏览器产物不能按 Node 重打。这么做会在四十个 client bundle 顶上加一句 `import ... from 'node:module'`：注册代码还在每个文件里，而页面永远够不着，同时服务端一侧的每一项检查都是绿的。正是那次失败，让启动闸门现在把手伸进了渲染进程。
