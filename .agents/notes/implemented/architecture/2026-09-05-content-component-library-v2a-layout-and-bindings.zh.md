# Agent Note：安排一次调用里的多个块，并让一个块喂给另一个

Status: implemented

[English](2026-09-05-content-component-library-v2a-layout-and-bindings.md) | 中文

## 问题

一次调用摆下若干块，内容列按书写顺序竖排。对一个块够用，对两个块就不对了，而两个块正是每个业务控制台最先要的：上面一张记录表，下面是用户挑中的那条记录。缺两样东西，而且现有调用里都表达不出来。

- **块摆在哪。** 顺序只说谁在前，从不说谁挨着谁。被表格喂的记录块，只有和表格同屏时才有价值；而把两者竖排进一个需要滚动的面板，就是一对永远不会同时出现的块。
- **下面那个块显示什么。** 今天模型只能问：先摆表格，等用户勾，读回执，再发第二次调用带上那一行的字段。四步，外加为一个页面早已知道答案的手势跑一次模型请求，中途条目还要闪一次替换。而用户那边勾完一行，要一直等到某处的模型跑完一轮才看得见反应。

第二件更难，因为显而易见的办法会破坏整个界面赖以成立的一条规矩。若用户勾中的行经由模型到达下面的块，那每一次勾选都是模型可见输入，`Model-visible ⟺ logged` 就要求每勾一次写一条会话事件。若它走别的路到达，那就是页面上有东西在决定一个块显示什么，而 host 判定了一个它从未见过的值。

## 决定

**不新增条目 kind，也不新增工具。** `show_component` 在 `nodes` 旁多一个可选的 `layout`，并接受绑定作为某个属性的整个值。一个视图就是一次调用，折叠成一条 `contentSurface` 记录，和单块调用完全一样，因此切换器条、关闭事件、投影、以及同 id 相替的规则都原样不动。另一条路——为组合视图立第二个 kind——要付出第二个抽取器、第二次渲染器认领、第二套折叠和第二份上述规则，换来一个用户根本分不出与旁边有何不同的条目。

**布局原语只有一个：`stack`。** 它带方向、三档命名间距、是否换行、以及子节点；子节点要么是另一个 stack、要么是一块，两者都可以带 `flex`——切分一行的是它的孩子，不论哪一种。唯独最外层那个 stack 不可以：它本来就占满整条条目，写在它身上的份额切不到任何东西，两遍读都这么说——宿主点名拒掉 `spec.layout.flex`，座位则把这棵树当成读不懂的树，退回竖排。没有栅格、没有标签页、没有宽度。栅格属于「画 N 个同类东西」的组件内部，而这一行包的组件本来就在干这件事。标签页就是内容列本身：一条目一页签，条目内部再来一层，等于同一个面板上有两个切换器。宽度是模型算不出的数：列自身的宽度是运行时对着用户拖动的对话栏解出来的——`flex` 是「现有空间里占几份」，说的是同一件事而不必猜。

**绑定记法只有一个：`{"$from": "node:<id>.<输出名>[<索引>]"}`，且必须是某个属性的整个值。** 没有表达式、没有条件、没有默认值、没有兜底、一个值里不能有第二个引用。这套记法是故意小到不能拿来算的：一旦绑定能写出 `a ?? b` 或 `rows.length > 0`，页面就在跑模型写的程序，而出错时要模型自己隔着一个什么都不报的界面去调。剩下的就是一个引用，而引用要么解得开，要么解不开。

**组件的输出由目录声明，相容性静态判定。** `ComponentCatalogEntry` 新增必填的 `outputs: readonly ComponentOutput[]`——不可读的组件填空数组，与 `actions` 对称——每个输出带的是属性同款的 `PropsFieldSchema`。于是 `acceptsOutput(source, target)` 在调用被接受之前就判定：一个块报出来的东西，能不能站在另一个块声明属性的位置上——种类相同，且来源的每一道上限都在目标之内。它只比上限、不比下限，因为输出是「用户做到哪一步」：声明了 `minItems: 1` 的属性照样接受绑到勾选上的写法，免得为了一行用户还没勾的数据，回头拒绝模型一小时前发的那次调用。下限归座位、对着真正解出来的值算——一份空勾选装不进那个属性，被它喂的块画等待行。

**宿主要回读的属性不许绑定，理由由组件自己说。** `PropsField` 新增可选的 `unbindable`，装的是给模型看的那句理由；数据表的 `displayValueList` 与 `rawValueList` 各带一句。回程手势指认的东西——被勾中的那一行、被排序的那个表头——宿主是从写下这些行的那次调用里读出来的，而解析出来的值不在任何调用里：一张由别的块喂行的表格，会把里面发生的每一次手势报给没有人，而且悄无声息，因为一条说不出发生了什么的通知等于没有通知。这条规则是通用的，不是给表格打的补丁：宿主要回读的属性，就是别的块不许写入的属性。

**于是值只朝一个方向流，也就没有谁去找环。** 凡是会上报东西的组件都要回读自己的属性，所以「会上报的块」就是「没人能喂的块」，绑定链闭不上环。当年走链找环、拒绝成环的那一遍，随着最后一份能写出环的 spec 一起没了；守住目录的是一条测试：把每个会上报的组件的每个输出，绑进每个会上报的组件的每个属性，逐条要求被拒。一个既会上报又能被喂的组件会在那里挂掉——那也正是运行时那一遍该回来的地方。

**被绑的值从不进日志、不进 payload、不进模型请求。** 引用是模型写下的、也是日志承载的；它所代表的值在页面里解出来，只活一次渲染，随即丢弃。这正是「被喂的块」仍满足 `Model-visible ⟺ logged` 的原因：模型能看见的东西一点没变，因为模型看见的是引用。用户勾一行、旁边的记录块跟着变，这是页面在重画自己，会话日志一个字节都不花——而这正是这套记法存在、而不是走一趟往返的全部理由。

**等着被喂的块画一行字，不是报错。** 当组件必填的某个属性绑到了还没有人发布过的输出上时，座位把这个块排除在判定之外，在它的位置上画「请先选择要看的内容」；这次调用的其它块照常画。画空记录等于说这条记录没有字段；整条拒绝则是为一个只是还没勾选的用户把条目变白。

**解析出来的值要过判定，而判定失败只由被喂的块承担。** 这个值出自页面里的组件，host 只查过它声明的形状能不能站在那儿——从没查过它会装什么。所以座位把解析后的值代入属性，再对结果跑同一份 `validateComponentSpec`，这是一趟判定，不是两套规则。当这趟判定被拒时，座位丢掉全部绑定块、判定其余的：用户正在操作的表格留在屏幕上，而每一个被别的块喂过的块都退回等待行——包括那些手里的值本来完全没问题的，因为被拒的那一趟已经丢掉，剩下的东西说不出是哪一块坏的事。

**块的身份是 `[entryId, seq, nodeId]`，绑定节点再加上它的引用解出来的东西。** 渲染器按属性做记忆化，而 Vue 表格拿到一个新的行数组时，会读成「行被整体换掉了」——它清空选中。所以若因为**旁边**那个块被喂了新东西就重读 payload，用户自己的勾选会在第一次勾选时就被扔掉。于是引用解出来没变的块沿用它已有的对象（`holdSteady`），只有真正被交了新东西的块才拿到新的。已发布的值按调用作用域隔离：同一 entry id 的后一次调用从零开始，因为把上一次调用的勾选带进新表格，等于拿一张已经不存在的表格的行去喂记录块。

**上限。** `MAX_NODES` 由 8 提到 12，布局最多嵌 4 层 stack，一个 stack 最多 `MAX_NODES` 个子节点，`flex` 取 1–12，且布局要把每个节点恰好摆一次。host 只查形状与上限，别的一概不查：它并不知道「表格在记录上方比在旁边更好读」，而一个对此有主张的 host，就是把某一家的审美编译进去的布局引擎。

## 否决的替代方案

**把标签页或折叠面板作为第二个布局原语。** 否决，因为内容列本身就是标签页：一条目一页签，切换器用户已经会用。在条目内部再来一个，等于同一个面板上出现两个规则不同的切换器，用户还得学清楚哪个关掉的是什么。折叠面板是同一条反对意见，只是把页签竖过来。

**带行、列、跨度的栅格。** 否决，因为归属搞错了。真正需要栅格的地方，栅格是覆在「N 个同类东西」之上的——N 个指标、N 张卡片——而那是一个组件，由知道「一格是什么」的东西来画。任意块之间的栅格需要每块一个跨度、每个断点一个列数，那还是猜宽度，只是多了些算术：模型要去给一个用户正在拖动的列定尺寸。

**在绑定里写表达式——`a ?? b`、`rows.length`、一次筛选、一个格式串。** 否决的理由是出错时的样子，不是实现的代价。一个写错的表达式产出的是「显示了错东西的块」，且无从读起：没有路径被点名，因为路径本来就没错；而 host 要判定表达式的结果就得先求值，那等于在 host 里跑模型的代码。到目前为止提出的每个运算符，都可以改由组件来回答——一张对缺失字段不画东西的记录、一张自带空状态的表格——在那里失败看得见、代码有测试。

**条件渲染——勾中东西时才画某个块。** 否决，因为等待行已经是它诚实的版本。让块消失又出现，会在每次勾选时把面板从用户的光标底下挪走；而人真正需要分清的两种状态是「还没挑」和「挑了，就是这个」，一行字加一个填好的块把这两件事说清楚了，且什么都没动。

**跨条目绑定——一个条目的表格喂另一个条目的记录。** 否决，因为屏幕上只有一个条目。被喂的块会对着用户看不见的表格解析，而用户切到别的页签时它的值还会变。把已发布的值按调用作用域隔离，也正是替换调用能干净重来的原因。

**把一个块沿列表重复。** 否决，理由与栅格相同，这是组件的活：总得有东西决定「一项长什么样」，而那个决定就是一个组件。

**让座位复用 host 的布局读取器。** 考虑过，等 host 导出一个的时候就该去重。座位今天没法把 `layout` 交给 `validateComponentSpec`，因为判定节点的那一遍跑的是节点的**子集**——等着被喂的块被排除在那一遍之外——把全量的树交给那一遍会因为它手上少了一个节点而被拒，所以 `layout` 不进那一遍。读取器排的是另一个集合：全部的块，等待中的也在内，于是等着被喂的那一块占住自己的位置，而不是让栈合拢把它挤掉。两次读取面对的听众也不同：host 点名它拒绝的路径好让模型去改，而座位读不懂就退回竖排，好让另一个 build 写下的 payload 仍然画得出来。已写进两包 README，是一个 `readLayoutTree(value, ids)` 导出可以关掉的重复。

**为「值装不下」加第二句等待文案。** 本片否决并已登记。「还没勾选」和「交过来的东西装不下」画同一行字，而只有前者是用户能处理的。要把两者分开，座位得在丢掉那次失败的判定之前知道自己撞的是哪一种，而换来的第二句话用户照样处理不了。

**浏览器发现、而本片不修的东西。** 那个厂商表格把勾中行的方框画成和未勾中一样的白底：`getComputedStyle` 两边都读出 `rgb(255, 255, 255)`，本条目如此，早于这一切就已发布的 `sites` 条目同样如此。组件本身把勾选记对了——报出的位置、被喂的记录、`is-checked` 这个类都对——所以错的是这一行包的样式，不是本片的主题。它被记在浏览器泳道里、紧挨着那条读这个类的断言，好让下一个打开这个文件的人先遇到测量结果、而不是先遇到意外。

## 已知限制与推迟事项

- **同一 kind 的两个条目共用一个座位，来回切换会丢掉用户做过的事。** 已发布的值按 `[entryId, seq]` 隔离，因此切回一个条目时，它的块会在「什么都没发布过」的状态下重画，每个被喂的块回到等待行——而表格自己的勾选早已随卸载消失。日志里有的东西一样没丢；丢的是用户搭起来的工作状态。要关掉它，需要内容列为每个条目保留一个已挂载的座位，那是内容列的设计，不是这一行包的。
- **组合视图存不下来。** 没有办法把一次调用的排布与绑定存起来、以后（本会话或另一个会话）再摆回去，而那正是工作流想要的。那是 `v2b`，连同厂商自己存好的视图与 `/show-content-view`，并且需要给「视图」在单次会话日志之外找一个家。
- **厂商自己的视图不在这里。** 已经在自家系统里定义好视图的部署，没法把它们提供给模型；每个视图都是模型逐次调用现搭的。同样是 `v2b`。
- **输出等收得下它的那个组件出现再声明。** 目录里只声明了一个输出——`toy.table` 的 `selectionDetail`，喂给记录块的 `dataList`，正是这个功能存在的理由那一对。调用当初写下的那些勾中行、以及 `el.filter-bar` 的条件，都没有声明：这里没有任何属性收得下它们，而没人收得下的输出，等于先给模型一条绑定再拒掉它——一条只会产出拒绝的目录行，比没有这一行更差。等到出现把行或条件当输入吃进去的组件、或者 `v2c` 的数据来源时再各自声明：一行目录，加上渲染器里的一次 `publish`，因为现在两个渲染器都不发它们。
- **host 与座位把布局读了两遍。** 一套文法两个读取器，理由见上；从 `validate.ts` 导出一个 `readLayoutTree(value, ids)` 就能把 host 的读取器给座位，让这条规则只有一个家。
- **等待中的块说不出自己在等哪一种。** 一行字同时覆盖「还没有人发布过」和「发布出来的装不下」，而只有前者是用户能处理的。
