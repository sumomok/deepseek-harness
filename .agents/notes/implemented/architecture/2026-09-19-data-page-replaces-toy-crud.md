# Agent Note: the data page replaces the read-only block, and a view file is where it is arranged

Status: implemented

English | [中文](2026-09-19-data-page-replaces-toy-crud.zh.md)

## Problem

The block the console drew for one table was `toy.crud`, and it was read-only by construction, twice over: the placement package spread a frozen record of write-suppressing properties over whatever the call wrote, and the vendored build compiled the six write dialogs to empty stubs. That settled the question the first version asked — can the deployment's own page go in front of a person with the host never on the request path — and it settled nothing about the page a person actually works in. The console this page comes from draws that table with 新增 on the toolbar, a modify button on every row, a side card that narrows the table, and full-page add and modify panels. None of it could be drawn here, and no property could ask for it, because the host's answer to every write property was to overwrite it.

Two more things were wrong with the shape rather than with the settings.

The eight declared properties were one group. "Which table, narrowed how, sorted how" and "which regions are drawn, which buttons are kept" were judged by one rule and offered to the model as one list, so a model placing a page was handed a layout choice it has no way to make well — and the first property anybody added for the page a person works in would have been one more thing a call could ask for.

And the block sat in the content column at its own height. The page is a query panel over a table over a pager, sized `height: 100%`; a cell that carries no share of the column's height leaves that `100%` resolving against a box the size of whatever happened to be in it, with the rest of the column empty underneath.

## Decision

**`toy.crud` is retired, and `toy.data-page` is not a version of it.** The component id, the renderer, the placement package's module, its two `Config` fields, the three dictionary keys, the snapshot lane and the web scenario are renamed in one change, and nothing is left behind that answers to the old name: no alias, no compatibility path, no second entry in the catalog. The vendored tarball is `@sumomok/toy-crud-kit` 0.4.4, where it was 0.2.3, and its `DataPage` export is `Crud.vue`'s own sub-components assembled in `Crud.vue`'s own arrangement rather than a rewrite of them. A session log holding a spec that names `toy.crud` degrades through the path the content column already has for a spec this build's catalog did not write — the same path a log from any other build reaches — which is why the retirement needs no format version and no migration.

**Whether a button exists is layout data; whether a press succeeds is the backend's answer.** The placement package holds no list of buttons a user may have, no check of what this visitor may do, and no sentence that branches on it. A view file says which regions the page holds and which buttons it keeps; `readOnly: false` says the page may be written in at all; and from there every add, every edit and every operation is a request the page makes with the visitor's own credential, which the deployment's own backend answers. The host is not a second opinion about a right, because a second opinion is one that can disagree with the one that counts. The page itself holds to the same line from the other side: it fixes the customer's own `useCloudPermission: false`, so the per-button rights this deployment answers with hide no button either — a button the backend would refuse is drawn, and the refusal arrives when it is pressed. The one thing those permissions decide before a request is whether the page opens at all: where the visitor's own profile names tables and none of them is this block's, the page fetches nothing, draws the deployment's own 无权限 and reports `denied`. That check is drawn from a profile the browser holds, so it spares a person a page of failures rather than protecting the table; the table is protected by the backend refusing the requests that are never made.

**One declaration decides both halves of the model/view split.** `PropsField` gained `viewOnly`, a sentence rather than a flag. A property carrying it is filtered out of the description the model reads, and the same sentence is what a call writing that property is refused with — so the model is neither offered the property nor told something different when it sends one anyway. The refusal names the path (`spec.nodes[0].props.regions`), states what settles it and what the page will be instead, and names no other tool and no way round. A view is judged by the same pass with `written` true, because the arrangement in a view file is the arrangement of whoever wrote that file.

**The two lists belong to the vendored page, and the host's copies are pinned to them.** The page exports `DATA_PAGE_MODEL_SETTABLE_PROPS` and `DATA_PAGE_LAYOUT_PROPS`, seven names each. The placement package cannot import a browser package, so it declares `DATA_PAGE_MODEL_PROP_NAMES` and `DATA_PAGE_VIEW_PROP_NAMES` — the same seven plus `metaLabel`, which is the name on the approval card and stops in this package, and plus `readOnly`, which is settled in the file the layout is settled in — and `component-kit`, which can import both, asserts the equality. A property the page grows and the host does not is a failing test rather than a page that quietly ignores what a view wrote.

**Twelve gestures leave the page, every one of them counts and names.** The three the read-only block reported are unchanged in kind and two are wider: `load` names the table, the first twenty drawn columns and the rights this deployment answered for this visitor, and `query` and `cell-click` carry what they carried. Seven are new: `select` reports how many rows are ticked and names them the way `toy.table` names a selection, `card-open` and `card-close` report the row the side card was opened on and that it closed, `added` and `modified` report that a record was saved and the saved row's drawn cells — at most eight, read through the same columns a clicked row is, never the form the user filled in — `operation` reports which added row operation was pressed, on which row, and `exported` reports which of the two toolbar exports was submitted and the file type the press named. The eleventh, `denied`, is what arrives instead of a load: it carries one closed-set `reason` and nothing more, because the table it is about is the `relatedMeta` the call itself wrote and the profile the page judged against belongs to the visitor. The reason is carried because the page's two ways of refusing are two different things to say: `no-row` is that this table is not among the permissions this deployment holds for this user, and `no-rights-table` is that those permissions could not be obtained at all, which holds for every table rather than this one. A reason neither the reading nor the catalog knows is reported as absent rather than passed through, so a page that starts naming a third still reports the refusal. The twelfth, `auth-failed`, is not a judgement of this page at all: this deployment refused the visitor's credential on one of the page's requests, and what is carried is the answer code it refused with — zero where the page had none to present — and the business code beside it, never the credential. The page goes nowhere on it, which is what the tarball's own patches buy: the customer's sources replace the console's whole window with their login page there. The request layer is not told which block asked, so every data page on screen raises the same one and each reports its own; the placement package's same-key supersede makes that one note per block. All three sentences name the fact and no remedy and no other tool. The one answer that reports nothing is the deployment saying nothing at all to the profile request: the page draws a line and raises no event, so this row has nothing to carry, and the package README records it as a limitation rather than inventing a gesture for it. An export is a task queued on the deployment's own backend, and the task number it answers with is left out of the report: it names a row of that deployment's own task list, which is where the file is collected and which this console neither ships nor can reach, so a report carrying it would put an identifier in front of the agent that nothing it can do resolves. All twelve are graded `context` and travel the content-component action path the catalog already declares, so there is no new session event type and `SESSION_FORMAT_VERSION` stays where it is. `load`'s rights list is capped at sixteen keys of twenty-four characters because the whole document is measured against the action payload ceiling beside twenty columns at their widest, which a test measures rather than assumes.

**The page fills the column because three cells give it a definite height.** The seat's scroll viewport is a flex column, the outermost stack takes `flex: 1 0 auto`, and the renderer's own section is a flex column whose box takes `flex: 1` with a `32rem` floor. A view then writes `flex: 1` on the cell holding the block, and the page's `height: 100%` resolves against the column. Nothing here measures anything: the height is CSS all the way down, which is what makes it survive a column that is resized, split or scrolled.

**The example is layout data.** `examples/space-data-page` reproduces the page this deployment's own console shows for its layer table — query panel collapsed to one row, 新增 beside the query buttons, a modify button on each row, the side card, the add and modify panels — entirely in `views/space-layer.yml`, with `readOnly: false`, with `{"$param": …}` for the table and its name, and with a `SKILL.md` body that is still a placeholder because the instructions are the pack author's to write. There is no code in the example, and there is nothing in the placement package that knows this table exists.

## Testing

Unit suites pin the whole judgement and the whole reading. On the placement side: the model/view split from both directions — a call writing any one of the eight arrangement properties is refused by path with the catalog's own sentence, a view writing all eight is accepted, and the `WRITTEN_PROPS` table the view case walks is asserted equal to `DATA_PAGE_VIEW_PROP_NAMES`, so a property added to one and not the other fails rather than silently going untested; the description the model reads, which carries the model properties and none of the arranged ones; the refusals a page still earns (not offered, a second page, both sort directions, beside a `dataSource`); the approval card's wording, its counted-not-shown conditions and its own-line identifier; and `PendingLoads`, which settles single-shot, per session and per entry id. On the drawing side: each of the twelve gestures, including the ones with nothing to report, the once-only memory that keeps a redraw from saying the same thing twice, which holds a refusal and a refused sign-in as it holds a load; a block opened on a table the profile does not grant and one whose permission table the deployment would not answer with, both of which draw the deployment's own 无权限, request nothing under that table's name and name which judgement refused them; a deployment refusing the credential outright, which leaves the console's own address unchanged and reports the answer code and the business code beside it; the properties that reach the page and the ones that may not, the mount that waits for the base path, and the box that is still a box while Vue is destroying the page. `component-kit` asserts the host's four lists — the two of properties, and the toolbar buttons and row operations a view may keep — equal to the vendored page's four exports.

A real Loader composition boots the row with the view registry and the content-surface router and opens the view with a click, asserting the spec the column receives carries the arrangement the file wrote. The snapshot lane `snapshots/console/show-data-page-turn` carries the whole turn a model sees — the offer in the tool schema, the card, the grant, the record and the result line — and `apps/web/tests/component-surface-data-page.e2e.ts` drives the built bundles against a stub backend.

Per-file coverage of every changed `src` file is 100%: 80 files, 1174 tests over `component-kit`, `component-surface`, `skill-pack` and `skill-pack-components`.

## Alternatives considered

**Keep `toy.crud` and add the writable page beside it.** Rejected. Two catalog ids for one vendored page means two renderers, two entries in every description a model reads, two lanes in the snapshot tree and a rule about which one a view should use — bought in exchange for logs from one pre-release build continuing to draw. The pre-release stance settles it: the old spec degrades through the path that already exists for a spec this catalog did not write.

**Alias `toy.crud` to `toy.data-page`.** Rejected for what the alias would have to mean. A `toy.crud` spec carries `isExpandQuery` and carries no arrangement, so the alias is not a rename but a translation with its own rules, tested and maintained, for documents that only a pre-release log holds.

**Let the host decide which buttons a visitor may have.** Rejected, and it is the boundary the whole change is built on. The host would have to learn the deployment's permission model to do it, from a `rights` list the page happens to report; it would then be a second answer to a question the backend answers on every request; and the first time the two disagreed, the user would be looking at a button the host drew and the backend refuses, or at a missing button they are entitled to press. Whether a button exists is layout; whether a press succeeds is the backend's.

**Make the eight arrangement properties a `Config` allow-list, so a deployment picks which of them a call may write.** Rejected. It is a tunable with no deployment asking for it, and the choice it offers is one nobody can make well: a model that may write `regions` for one deployment and not another has to be told which, and the description is the same text for both.

**Report the load's rights list to the model as "buttons you can press".** Rejected on measurement. A jsdom probe of the vendored bundle shows a read-only page still answering `search`, `exp` and `searchSetting`, so the phrase would be false in exactly the case it mattered. What the reading carries is the deployment's own answer, under the deployment's own word: the rights it granted this visitor.

**Report the saved record as the endpoint answered it.** Rejected, and this is the one reading that was built that way and corrected. The endpoint answers with the record, which is the row's key and every attribute the scheme holds — including the ones it hides from the table — so reporting the answer puts in front of the agent what nobody on screen can see. Every other row-bearing reading already goes through the drawn columns the page's own `load` remembered; the save goes through them too, at its own ceiling of eight. A save whose answer holds no drawn cell is still reported, with an empty record, because that a record was saved is the fact the agent needs.

**Give the block a measured height, from a resize observer on the column.** Rejected. Three flex declarations do it in CSS, survive a resize, a split and a scroll with no JavaScript on the path, and cannot be out of date by a frame. The `32rem` floor is what keeps a column too short to be worth drawing into from collapsing the page onto itself.

**Write the example's arrangement into the component's defaults.** Rejected: the defaults are the vendored page's, and a page a call places has to open with them. An example that needs different ones is what a view file is for — which is the claim the example exists to make.

## Consequences

**Bought.** The console can draw the deployment's own page as that deployment's own console draws it, writable, arranged by a file a person wrote, with the placement package holding nothing about the table and nothing about a right. A view ships that arrangement as data, so the next table is another `.yml` rather than another renderer. The model's path is unchanged in what it may do and narrower in what it may ask for: it names a table and how to narrow it, and the page it opens is read-only with its own arrangement.

**Paid.** Twelve gesture ids and their ceilings, where there were three — every one of them a thing the catalog declares, the seat builds and a test measures against the action payload ceiling. A vendored tarball that grew from 0.2.3 to 0.4.4, with nineteen patches against the customer's sources rather than five, five of them mechanical repairs the assembled page needs and seven of them the price of a build that writes no address at all. A model/view split that lives in one declaration and would have to be re-expressed the day a second component needs one. And a `readOnly: false` in a view file that reads like a permission and is not one — recorded here, and in the package README, as the assumption whose review trigger is a backend that does not check.

The original decision to mount this page at all — the credential that never leaves the browser, the host that is never on the request path, the card at placement, the containment and the base path settled before the first request — is unchanged and is stated in present tense by [`@deepseek-ai/dsh-experimental-component-kit`](../../../../packages/experimental/component-kit/README.md) and [`@deepseek-ai/dsh-experimental-component-surface`](../../../../packages/experimental/component-surface/README.md). Its original rationale, and the alternatives it beat, are the archived [the deployment's own data page, opened in the panel with the visitor's credential](../../archived/feature/2026-09-10-toy-crud-kind.md).
