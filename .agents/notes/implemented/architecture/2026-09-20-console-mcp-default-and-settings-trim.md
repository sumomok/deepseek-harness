# Agent Note: the console mounts MCP by default, and its settings page stops naming plugins and configuration files

Status: implemented

English | [中文](2026-09-20-console-mcp-default-and-settings-trim.zh.md)

## Problem

Two unrelated things were wrong with what a console deployment is, and both were visible from the same page.

**MCP reached the console only through material that lives outside this repository.** The deployed console gets it from a vendored `@haoran/dsh-mcp-servers` tarball, listed in the deployment's `Dockerfile` and added to the profile with `dsh plugin --profile web add`. That package is a good desktop answer and the wrong console answer: its entire surface is a **Settings page** where someone types a server in, ticks the tools it may offer, and re-confirms when the server changes them. A console's end users are business staff who must not be able to add a server at all. So the console was carrying a settings UI it had to hide, in order to get a capability it could not otherwise have — and "does this deployment have MCP" was answered by which tarball the image happened to be built with.

The in-repo bridge, `dsh-mcp-client`, is the opposite shape and closer to right: one composition row per server, no UI. But it takes exactly one server per row and requires a `serverName`, so a composition reaching no server states no row — and "the capability is absent" and "the capability is present with nothing configured" become the same file. A console cannot promise MCP is mounted if the promise disappears whenever nobody has chosen a server yet. Its credential story is the other half: `headers` is a string table, so a composition reaches a secret through `!!js process.env.X`, an expression whose failure mode is a request header quietly carrying nothing.

**The settings page showed a customer two surfaces written for a maintainer.** A **Plugins** section with cards named after host-plane subsystems and a read-only Cordis Loader inventory listing rows by package name; and an **Open configuration file** button that opens the Host's settings document in a native editor. The second is the sharper one, because it looks like it only affects a developer's own machine and does not: it is guarded by `ctx.remote.$host.isLoopback`, and the console makes that true for a remote visitor on purpose — `server-base`'s `ownsHost` declares the deployment's own login gate as the thing deciding who reaches the page, and every visitor it admits then gets the operator surface. On the deployed console, that button is in front of the customer.

## Decision

**The console composition carries the MCP capability, and a deployment carries only the list.** A new row, `@deepseek-ai/dsh-experimental-console-mcp`, is mounted by [`customer.patch.yml`](../../../../packages/experimental/server-sidebar/overlay/customer.patch.yml) with `servers: []`. It takes one list and mounts one `dsh-mcp-client` bridge per entry. An empty list is the delivered state and is idle in the strong sense: the row loads, opens no connection, registers no tool, and adds nothing to any model request. Stating `servers: []` in the overlay rather than leaving it to a schema default is deliberate — a deployment's own list is then an edit to a value it can already see.

**A server is named, never carried.** Each entry is an endpoint plus the *name* of a credential, resolved through `ctx.credentials`. The value never enters a composition file, and a reference nothing has stored a value for fails the row while it loads, naming the reference and not the value. This is what the `!!js process.env.X` form could not do: a missing environment variable produced a header carrying nothing, and the first symptom was a tool call refused by the server.

**The out-of-repo plugin is not needed and is not vendored.** Everything the console wants is the in-repo bridge plus a list. What `@haoran/dsh-mcp-servers` adds beyond it — a settings document of servers, a settings section to edit them, a stored per-tool opt-in, and a re-confirmation when a server changes what it offers — is all machinery for putting the decision in front of a person at runtime, which is exactly the thing a console must not do. Its per-tool gate is real value this row does not reproduce; that is recorded as a limitation rather than copied, because reproducing it means reproducing the page that answers it.

**Streamable HTTP only.** A stdio server is a local program the host starts, outside every sandbox this product applies, under the account running the host. That is a genuine deployment decision, and it is not one a console makes by adding a line to a server list. A deployment that needs it composes `dsh-mcp-client` directly and owns the choice explicitly.

**The two plugin settings rows are disabled; the settings shell is not.** `ui-settings-plugins` owns the one Plugins navigation entry, the `configurable` tab, and its four cards; `ui-settings-plugin-inventory` contributes the inventory tab into that same section. Neither registers anything outside it, so two `disabled: true` rows remove the section and nothing else. The inventory row is disabled as well rather than left to wait on a slot that will never be declared, because a composition carrying a plugin whose only contribution can never land misstates what it runs.

**The open-configuration-file action is hidden in CSS, because nothing else can reach it.** It is registered by `ui-settings-general` — the settings shell itself, which also draws the panel, the navigation and the General section, so its row cannot be disabled. There is no `Config` field gating the action, and a list slot admits no withdrawal by another plugin: `ctx.slots.register()` hands its disposer to the registrant. So the console's existing de-terminology stylesheet gains a fourth rule, the same mechanism and the same pinning discipline the three before it use. The one clean composition-level alternative — composing no file-backed settings provider, so the Host reports `hasDocument: false` and the action renders null — was rejected because it takes durable user settings with it.

## What the console's approval settings do and do not cover here

Factual, and unchanged by this slice.

A bridged MCP tool declares **no approval gate**. `createDefinition` in `mcp-client/src/tools.ts` builds a `ToolDefinition` with `name`, `description`, `parameters`, `output`, `execute` and `finalizeContent`, and nothing else; the registry asks the approval seam only when a `tools/pre-execute` listener returns a `PreToolDecision` of kind `ask`. Nothing returns one for these tools, so an MCP tool call runs without a question, under every access preset the console offers — including 只读 ("read-only"), whose `sandbox: read-only` governs the filesystem and shell seams, not network egress to a configured MCP server.

So the console's rule — follow the original system's own confirmations — does not cover this. That rule is about a page the user is looking at, where the deployment's own frontend asks before it writes. An MCP tool call is a request this process makes to another machine, with no page in front of it, and under the identity of whatever the row's `auth` names: **the deployment's service credential, the same for every person using the console**, not the signed-in user. A record written through it is attributable to the deployment and not to the person who asked for it, and the deployment's own backend has no way to tell the two apart.

The composition-level mitigation that already exists is `auth-gate`'s `mcpUpstreams` forward: the MCP row points at a local route, and the gate replaces `Authorization` with the token the browser posted, so the request lands under the visitor. It is documented in both READMEs as the other of two ways, and it is the deployment's choice rather than this row's default. Out of scope and reported rather than changed: whether a console MCP tool should declare an approval gate at all, and what the out-of-repo permission gateway (`@haoran/dsh-llm-permission-gateway`, which the ECS image carries) does with a tool that declares none.

## Testing

`packages/experimental/console-mcp` carries 23 tests at 100% per-file coverage of its two `src` files. `tests/servers.spec.ts` pins every self-contained refusal — the id grammar, two entries claiming one id, a url that is not absolute `http(s)`, a url carrying user information, a url carrying a fragment, a header name that is not one, a credential reference outside the reference grammar — plus the case that matters most for the refusal wording: a url the parser could not read is *not* quoted back, asserted as a negative. `tests/apply.spec.ts` mounts the row over a real `ToolRuntime` with the MCP SDK mocked and a credentials double, and pins the four lifecycle claims: an empty list opens no transport and registers no tool; two servers register under their own namespaces; a named credential lands on the configured header behind its scheme; and a missing one rejects by reference name with nothing registered. The list-level refusal is pinned by its consequence — a list whose second entry repeats an id mounts *no* transport, not one.

`packages/experimental/server-sidebar/tests/customer-overlay.client.spec.ts` gains the composition assertions: the two disable rows by id and package name, the same two rows still composed and not disabled in `packages/bundle/web-app/cordis.patch.yml` (so the console's disable is the console's, and a row retired upstream fails here rather than silently becoming dead configuration), the settings shell deliberately *not* disabled, and the MCP row with `config` equal to `{ servers: [] }`. The three console e2e overlay copies are asserted to carry all of it verbatim, the way that file already treats the permission row.

`terminology-guard.client.spec.ts` pins the new rule twice: as the literal selector, and structurally — the selector is run against the element tree `SettingsRoot.tsx` renders and must match exactly the header's action row, while a section element that also names a class `actions` must not match. That second half is what keeps the rule from widening onto a control it has no business hiding.

`snapshots/console/cordis.yml` composes the row with `servers: []`, and all nineteen recorded scenarios pass unchanged — the lane boots the row through the real Loader over the shipped `acp` profile, so it is simultaneously the idle proof and the composition proof, and it needs no key.

Not covered by an automated lane, and verified by hand in a browser instead: the rendered settings page before and after. Screenshots are in the slice's scratch directory; the Plugins navigation entry is present before and absent after, and the open-configuration-file button is present before and renders nothing after.

## Alternatives considered

**Vendor `@haoran/dsh-mcp-servers` into the console.** Rejected on what it is, not on how it is delivered. Its value is a runtime page for choosing servers and ticking tools; the console's requirement is that no such page exists. Vendoring it would mean shipping a settings section in order to hide it, and hiding it would disable the only thing it does.

**Put the server list in user settings instead of the composition.** Rejected. Settings are what a user edits, and the console's users must not add servers; the settings Remote takes any namespace, so anything already admitted to `/api` could write it. The composition is the layer whose author is the deployment, which is exactly whose decision this is.

**Extend `dsh-mcp-client` with credential references and an empty-server mode.** Rejected under the fork's upstream-zero-change rule. That package is upstream; the console's needs are a composition concern, and a wrapper leaves the bridge free to move.

**Let a `cordis:group` with an empty child list stand in for "capability present".** Rejected as a word game. It would load and do nothing, and a deployment would still have to know to add `dsh-mcp-client` rows itself — which is the state this change exists to end.

**Disable `ui-settings-general` to remove the open-configuration-file action.** Rejected: it is the settings shell, and disabling it removes the panel, the navigation and the General section with it.

**Compose no file-backed settings provider, so `hasDocument` is false and the action renders null.** Rejected although it is the only true composition-level removal available: it takes durable user settings — theme, language, transcript mode — with it.

**A core patch adding a `Config` switch to `ui-settings-general`.** Not taken in this slice, and recorded as the smallest upstream change that would do this properly: one boolean that gates the `settings.action` registration, or a slot-withdrawal API on `ctx.slots`. Either would retire the CSS rule. It needs registration in `.claude/core-patches.md` and the owner's decision, so it is reported rather than made.

## Consequences

**Bought.** A console deployment now states what it reaches in the same file that states everything else it composes, and states it by naming rather than by carrying: an endpoint and a credential's name, with the value left where the credential seam keeps it. "Does this deployment have MCP" stopped being a property of which tarball the image was built with. A server whose credential is missing now fails the boot with the reference named, instead of coming up and refusing every call. And the settings page stopped offering a customer two things written for a maintainer — a plugin administration section, and a button that opens the Host's configuration file on a deployment whose `ownsHost` makes that button real for every visitor it admits.

**Paid.** There is one more package in `packages/experimental`, and it exists to hold a list. The console line now carries a fourth CSS rule coupled to an upstream package's rendered structure — the weakest mechanism used here, taken because `ui-settings-general` is the settings shell and offers neither a `Config` field nor a slot withdrawal; it is pinned by a structural test rather than trusted, and it retires the day upstream grows either. Per-tool opt-in, which the out-of-repo desktop plugin does have, is not reproduced: every tool a configured server advertises is offered to the model, and a deployment that needs less has to name a server that advertises less. A credential is still read once per process, because that is the only thing `dsh-mcp-client`'s string header table can express, so rotating a secret needs a reload.

**Unchanged, and worth stating.** A bridged MCP tool still declares no approval gate, so it runs without asking, under every access preset — including 只读. This slice did not change that, and the section above records exactly what it means for a console: the request leaves under the deployment's service credential, with no page in front of it, unless the deployment points the row at the auth-gate forward instead.
