# Agent Note：控制台侧栏——身份行的「组织」入口，以及组织告知卡片

Status: implemented

[English](2026-10-05-console-identity-org-entry-and-notice.md) | 中文

## 问题

部署加入组织的客户控制台，会在 [`@deepseek-ai/dsh-experimental-server-sidebar`](../../../../packages/experimental/server-sidebar/README.zh.md) 旁边组合组织插件 `@sumomok/dsh-org`。这时有两样东西要经侧栏所在的页面送到每一位成员面前，而且在没有这个插件的控制台里两样都不能出现。

- 从登录者通往组织的设置分区 `sumomok-org` 的入口。这个分区完整展示组织告知、成员自己的状态，以及插件暂时做不了的事。控制台在身份行（[身份显示与退出](2026-09-04-server-sidebar-identity-and-sign-out.zh.md)）上写明登录者是谁，而这一行原本只有「退出登录」。
- 组织告知：组织替部署确认之后每位成员看一次，每出一个新版本再看一次；组织设为 `member` 确认方式时，由成员自己确认。它告知、也征求同意，但不能拦住成员本来要进行的对话。

谁该看哪一版，页面判断不了。`organization` 确认方式下，作数的是组织的 owner 为这个部署确认的版本，只有后台有这个值，而页面只拿得到当前版本的告知正文。成员看过哪一版是按成员记的，而控制台由全体成员共用。

## 决策

**入口经 fork 的 `settings.trigger.action` 席位打开设置。** 上游只把 `openSection(id)` 交给 `settings.onboarding` 当前的那一步；`settings.launcher` 拿到的是 `openSettings` 与 `openOnboarding`，设置外壳的 store 建在 `dsh-client-ui-settings-general` 的注册里，不导出。fork 的核心补丁 `settings-trigger-action-seat`（[它的 Agent Note](../feature/2026-09-11-settings-trigger-action-slot.zh.md)）声明了 `settings.trigger.action`，其 owner props 带 `openSection`。侧栏在其中注册 `server-sidebar.settings-opener`：一个什么都不画的席位，挂载期间把 opener 发布到一个源里，侧栏经 inject face 的 `hooks.settingsOpener` 读取（`client/settings-opener.ts`）。控制台以紧凑形态渲染设置触发器，这个形态用 CSS 隐藏这个列表、但保持其占据者挂载，因此 opener 恰好在设置外壳存在期间存在。这件事不改任何上游文件；侧栏成为这个席位的第二个占据者。

**入口跟着分区走，读的是 `settings.section` 的胜者。** 当 `settings.section` 的某个胜者带着 `sumomok-org`、并且 opener 已发布时，菜单才提供「组织」（`client/org-section.ts`）。部署方停用的行、或被兼容检查停掉的行，不提供浏览器 bundle，因此分区、连同这个入口，都随这一行是否运行而定。胜者就是设置页画出的那些行，所以别的条目用同一 id 遮住这个分区时，按遮住它的条目算。没有菜单项时，身份行的标记与没有组织插件的控制台完全相同，那样的控制台什么都不变。「退出登录」在任何组合里都留在这一行上。

**插件判断成员该看什么；页面只显示，并回报成员做了什么。** 组织插件的浏览器半边挂载 Remote 命名空间 `sumomokOrgNotice`，宿主半边按调用的那位成员回答每个方法：`due()` 答没有、等待、一次性告知或待确认的告知；`markSeen(version)` 与 `confirm(version)` 答结果或 `stale`。谁看哪一版的规则只在插件里写一次，写在它需要的数据旁边。页面重述应答类型，并在 wire 边界校验每个应答：不读的字段忽略，不认识的 `kind` 按「没有要显示的」处理，因为插件的应答结构只做加法。只有命名空间存在时卡片才注册（`client/org-notice-remote.ts`）；这个命名空间不在侧栏的 `inject` 列表里，所以没有组织插件的控制台照常启动，也不出现卡片。

**页面只记得本页收起过哪些卡片。** 成员看过、同意过哪一版由插件保存。控制台上，浏览器发起的设置写入对每位成员都被拒绝，而且设置会写进全体成员共用的 profile 补丁；浏览器存储则由用同一个浏览器的所有人共用，退出登录也不清它。成员收起的卡片，在本页一直不再出现，直到插件答出另一个版本；「稍后」就只是这样，所以下次加载时会再次征求这位成员的同意。

**卡片是 `shell.overlay` 里的非模态条目。** `Modal` 会抢走焦点、接管 Tab 与 Escape 直到关闭，等于拦住输入框；`settings.onboarding` 的步骤会关掉已打开的设置面板，而且在侧栏的树里。`shell.overlay` 是整框浮层，只有其中的条目接收指针事件，server-layout 一直渲染它。卡片不抢焦点、没有关闭按钮，放在既不盖输入框、也不盖身份行和它的设置按钮的位置：宽框时在侧栏这一列之内、底部区域上方，位置取自侧栏测得的整列与底部区域的方框（`client/foot-placement.ts`）；窄框时在抽屉按钮下方，底边止于空对话输入框开始的那条线之上。它处在窄框的抽屉与遮罩之下，抽屉打开时像盖住页面其余部分一样盖住它。

## 备选方案

**向上游要一个 opener，或者打开设置停在第一行。** 上游没有这样的 opener；停在第一行，成员就得自己到「账户与用量」下找「组织」。上游一旦有了 opener，就由它替换这个席位。

**按插件的服务是否存在、或按侧栏的一个 `Config` 字段决定是否提供入口。** 服务存在不等于设置页上有这个分区；`Config` 字段则是对「组织这一行是否运行」的第二份表述，会与这一行的实际状态不一致，浏览器半边不另开一条路由还读不到它。

**由页面根据告知正文和存下的「已看过」版本自行判断。** 页面拿得到当前正文，拿不到组织 owner 确认的版本；存在设置或浏览器存储里的「已看过」会在成员之间串用。

**把「退出登录」移进菜单。** 那样这一行就有两种布局：有组织插件时退出在菜单里，没有时在行上；而在共用的机器上，退出是必须一眼可见、一次点击的动作。

**把卡片放在左下角，固定 360px 宽。** 常见宽度下侧栏这一列只有 180px 宽，空对话的输入框大约再往右 180px 就开始了，360px 的卡片放在那里会盖住输入框。

## 后果

控制台从身份行提供组织分区、并显示组织告知，除了 fork 已有的席位之外不改任何上游文件；没有组织插件的控制台画出的和以前完全一样。`apps/web/tests/server-sidebar.e2e.ts` 在真实浏览器里检查这两种组合，组织那一种借助一个夹具插件，它在内存里实现 `sumomokOrgNotice` Remote。侧栏成为 `settings-trigger-action-seat` 的第二个使用方，因此退役这个补丁，现在还需要控制台有另一种打开设置分区的方式；席位拿不到 opener 时，身份菜单场景会失败。

页面依赖插件挂载 `sumomokOrgNotice`：只注册分区、不挂载这个命名空间的插件版本会让成员看不到告知，而页面察觉不到，这一点由插件自己的测试钉住。插件不提供流，新版本在页面下一次询问时出现（挂载、重新连接、页面重新可见，或 `pending` 应答给出的延时到期）。宽框下卡片与侧栏这一列同宽，在最小的宽框上是 164px，较长的告知要在卡内滚动；窄框下它只在输入框上方那半屏里展开。
