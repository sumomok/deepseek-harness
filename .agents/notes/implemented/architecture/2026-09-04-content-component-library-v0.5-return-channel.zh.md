# Agent Note: 回程通道 —— 用户在一块界面里做的事到得了智能体

Status: implemented

[English](2026-09-04-content-component-library-v0.5-return-channel.md) | 中文

## Problem

[上一片](2026-09-04-content-component-library-v0.zh.md)把一块界面摆进了内容栏，并且在工具描述里明说：用户对它做了什么不会回到模型这里。正是这句话让那块界面不如旁边的对话值钱——智能体可以摆出一个确认条，然后还得在聊天里把同一个问题再问一遍，因为按下什么也到不了。

把一次按下送回去不是一个决定，而是六个，其中多数是插件容易悄悄做错的那种。

- **一次按下是模型可见的输入，所以必须先进日志。**本仓的规矩是：任何进入模型请求的东西都必须能从会话日志还原。一条通道如果把一句谁也没记下的话交给智能体，那这个会话就重放不出来。
- **每次按下都开一轮就是一个循环。**用户在按钮上连点会无止境地串起新轮次，而最显然的护栏——预算——本身是个陷阱：没有回补的预算只花一次，之后每一次按下都永久降级成静默，而且任何地方都不会说明为什么。
- **座位是一个页面，页面会撒谎。**浏览器送上来的一切都是文本。如果智能体读到的通知是用这些文本拼出来的，那么一个被篡改的、甚至只是写错的渲染器就能把「取消」报成「删除」，而智能体会照做。
- **动作声明的档位，不等于通知最后落在哪里。**智能体正忙时、以及超出预算时，`wake` 都会降级进收件箱；于是一条对每次按下都同一句话的回程，会告诉一部分用户「对话已经拿到你的答案了」，而事实上在他们下次开口之前什么都不会发生。
- **用户一去看别的东西，这一块就被卸载。**内容栏按种类各留一个座位，只把被选中的那条条目交给它，所以一块自己记住的任何东西，在用户挑另一个标签的那一刻就没了——包括它是不是已经被回答过。
- **命令的输入在任何 handler 跑起来之前就已落库。**`commands` 在 `index.ts:341-345` 就把原始输入逐字写进 `command/run`，而 handler 在 `:389` 才进入。因此任何「payload 里能放什么」的规则，都是在 payload 已经持久化**之后**才被应用的。

## Decision

**通道是一条命令，并且不新增任何会话事件。**座位执行 `/component-action <json>`，其全部输入是一个 JSON 对象：`entryId`、`componentId`、`actionId`、`nodeId`，以及一个只带该动作声明属性的 `payload`。`recordInput` 保持默认值，于是 `command/run` 逐字承载这份动作文档、只进日志不进模型；而 handler 造出的通知，会作为智能体认领它时由循环写下的那条 `user/message` 进入日志。本包的两个方向现在都从运行时本来就会写的记录里重放，`SESSION_FORMAT_VERSION` 依旧不动。

**座位送上来的东西没有一样是按原样显示的。**除 `payload` 外的每个字段都是拿去和日志比对的标识符：条目必须存在于 `contentSurface` 折叠结果里，节点必须是这条条目的 spec 画出来的，组件必须是那个节点点名的那一个，动作必须是那个组件声明过的，payload 必须通过该动作的 `payloadSchema`。智能体与用户随后读到的那些词——条目标题、组件名称、按下的按钮名——都是从目录里、从**模型自己写下的那份 spec** 里读回来的。按下一个这条确认条并没有画出来的按钮，什么也报不出去。

**存下来的 spec 是重新判定的，不是直接采信的。**handler 读到的记录是一个持久化检查点可能种下的折叠单元格，所以它声明的类型只是一种主张；`validateComponentSpec` 会对它再跑一遍，而正是这次判定，给了那个节点用于组装通知的那些属性。

**三档，写在目录里，没有 Config 覆盖。**`silent` 就地吞掉，`context` 在智能体的收件箱里等，`wake` 当场开一轮。档位是动作的属性而不是部署的属性，因为它说的是这个手势**意味着什么**——改个排序不算新闻，按下的确认就是智能体停下来在等的那个答案——一个部署如果挪动它，改变的是智能体被告知发生了什么。`el.confirm-bar` 的 `press` 是 `wake`。档位上刻意不做 Config 覆盖表；复查触发器是「某个客户真的要求改一个档位」，那时这是一次目录修改加一次发版，而不是一个配置字段。

**唤醒预算是 3，且只由人的输入回补。**`agent/inbox/claimed` 在被认领消息的来源是 `user` 时删掉该智能体的计数，照抄 `tool-jobs`。回补与消耗共用一张以确切 `Agent` 为键的 `WeakMap`。超出预算时、以及智能体正忙时，`wake` 降级为 `context`——而正在跑的一轮读收件箱不需要自己的轮次边界。

**payload 白名单是座位的义务，宿主执行的是投递而不是准入。**因为 `command/run.args` 在 handler 之前就已持久化，没有任何宿主代码能把一份超量文档挡在日志之外。宿主仍在做的是拒绝**投递**它：超过 `MAX_ACTION_PAYLOAD_BYTES`（2048），或带了该动作没声明的属性，这个动作就完全到不了智能体。浏览器那一半在行还不存在时就量同一个字节上限，所以超量文档通常压根不会被写下来。两个半边都在本包里，这条限制如实记进 README，而不是被抹平。另一条路——本行自有的 Log-only 会话事件，让 handler 有地方决定存什么——推迟到引入数据源的那一片，那时才会有第二个理由去开这个事件。

**闸门留在它本来就在的地方。**本行不提供任何写工具，也不发起审批：命令 handler 可能在没有开着的轮次时运行，而 `approval.request()` 在那里会抛。真正的闸是部署自己的 `tools/pre-execute` 策略，作用在模型**在这次按下所开的那一轮里**伸手去拿的那个写工具上；而 `wake` 正是「被问到时确有一轮开着」的保证。

**宿主当场处理掉的按下不在聊天里留下自己的一行；它当场处理不了的那两种是例外。**`ui-conversation` 对没人注册的命令用它的 `GenericCommandCard` 兜底，那一行的标题就是光秃秃的命令名：`component-action · Completed`，英文，摆在刚刚亲手按下按钮的人面前。这条命令是为它写下的那条持久记录而发的，所以本行在命令名上注册了自己的聊天视图——就是 `content-column` 对 `dismiss-content-entry`、`content-frame` 对 `show-content-page` 用的那手空注册——它空出来的那一行由 `content-column` 本来就装着的样式表折叠掉，而本行按构成必然与它组合在一起。对话里关于一次智能体正在读的按下所显示的，仍然是智能体认领的那条通知。

这个视图之所以是个组件而不是一片空白，是因为有两种结局没有别的地方可去。一次谁也对不上的按下到不了智能体，于是通知、轮次、回答都永远不会来。智能体停下来等的那次按下如果只进了收件箱，它会被读到，但要等到用户下次开口，而对话里没有别的东西会说这件事。把这一行藏掉，这两种和「智能体正在读」在屏幕上就长得一模一样，而 handler 那两句面向终端用户的话正是为它们准备的。这一行画的就是这次结局带的那句话——`这个动作没能记下来。` 或 `已记下，你下次发消息时对话会看到。`——关于这条命令别的什么都不画；拒绝按失败的样子画，等待中的按下按普通一行画，而折叠规则两个都不碰，因为都不是空的。

**回答一次按下的是「投递到哪」，不是「声明的档位」。**智能体自己的回答隔着一整轮，而且可能永远不来，所以这次按下必须在按下的地方就被回答——而诚实的回答是通知实际落到了哪里，那与目录声明的档位并不一致：智能体正忙时、以及超出预算时，`wake` 都会降级进收件箱，而一条写着「已发送到对话」的条，配上「在用户下次开口之前什么都不会发生」的事实，就是屏幕亲口让用户白等。因此 `deliverAction` 报的是通知落到了哪里，而 handler 只对其中一种答一句面向终端用户的话：`queued`，也就是智能体停下来等的那个回答，而它在用户下次开口之前不会被读到。`none`、`opened`、`context` 都不带文案——最后那种是因为勾一行是用户在干活而不是在等，每勾一次回一句就是每勾一次在对话里多一行（见 [v1b-2](2026-09-05-content-component-library-v1b-2-originals.zh.md)）。这句回答本身也是持久的——它就是这次结算写下的 `command/done`——这正是它以后还能被读回来的原因。

**按下态从日志里折出来，任何一块都不自己记。**在这根内容栏里，块自己记按下态天生是错的：用户一挑别的条目，内容栏就把这个种类的 DOM 丢掉，于是一条「自己回答自己点击」的条再回来时干干净净，同一个决定会被上报两次；而投递失败时又会留下一个永远按不动、也没法重试的按钮。一次按下本来就写下的那两条记录已经足够说明它的下场，所以本行去折它们：`componentActions`，按 `(entryId, nodeId)` 一格，`command/run` 开格（它逐字的 `args` 用与 handler 同一个解析函数读），与之按 `commandId` 配对的 `command/done` 把它结算成 `sent`、`queued` 或 `refused`。浏览器就在内容栏读自己条目流的那个地方读这份值——同一条通道，不是新开一条——而 `ComponentRendererProps.state` 把各自那一格交给各自那一块。`refused` 仍然可按，因为再上报一次是唯一还能做的事。

一次手势只算给此刻在显示的那次调用：格里的 `seq` 是这次按下的日志位置，条目的 `seq` 是摆放它那次调用的位置，所以同一个 id 下后来的调用会把先前所有按下都甩在身后。块的 React 身份就是它那次在途按下所归属的那个键——会话、条目、摆放它的那次调用、节点——所以替换时照样重新挂载；而切换会话时座位是被重画而不是被卸载的，也绝不会把一个会话的等待交到另一个会话的块手上。变的是重新挂载不再是复位答案的那个东西。日志唯一盖不住的是这趟往返本身：一块等的是比它已经看得见的那个日志位置更晚的东西，在更晚的手势被记下来之前读作 `sending`。

**这份等待由整个页面兜着，不由那一块兜。**浏览器那半边在客户端插件的整个生命期里维护一张表，记着还没有记录的那些按下，键是会话、条目、摆放它的那次调用和块；每一块在按下离开时写下自己那一行，之后每次被重画都把它读回来。把它留在块里，留下的正是折叠本来要堵的那个洞，只是窗口更窄：按一下、切到别的标签页、再切回来，第一次上报还在路上，条却又可以答了，于是同一个决定会两次到达智能体。只有两件事会清掉一行，别的都不会——记录到了，以及派发回话说不会有记录了。

**压根没变成记录的那次按下会自己了结。**`postAction` 回答 `dispatched` 或 `failed`，座位等这个答案。`failed` 覆盖三种情形：浏览器自己拒掉的超量文档、传输层失败，以及被拒的调用——socket 关了、网关重启了、宿主已经不持有这个会话了。三种情形里浏览器都没看到 `command/run` 被写下，因此就页面所能知道的而言不会有结算到来，而还在等结算的那一块会钉在 `sending` 上、所有按钮全死，直到会话结束。所以这一块丢掉自己那一行、读作 `refused`——这也正是页面看得见的事实：这个动作没能记下来，而这个状态的文案本来说的就是这句。这个判断是本地的、暂时的，存法和那份等待一样——按这次按下所锚定的日志位置存着——所以宿主在传输断掉之前已经写下的记录，照样像任何别的结算那样把这一块结算掉，而不是在这次挂载的余下时间里被这一块自己的答案挡着。handler 拒掉动作则是相反的情形，算作 `dispatched`——它的两条记录都在日志里，这一块像读任何别的结算那样从折叠里读到这次拒绝。

**这条命令在斜杠菜单里的那一行只能是一句话，不能是一片空白。**`commands.register` 没有任何办法把一行挡在输入框的菜单之外——`CommandDescriptor` 带的是名字、描述和输入提示，客户端把宿主目录返回的东西照单列出。于是 `/component-action` 就摆在终端用户面前，混在一堆本该由人来打的行里，而本行唯一能左右的是它在那儿说什么：终端用户读的中文，点明是内容面板里的按钮、由页面自己发出。`commands.list` 是 `@Remote` 方法，所以没有任何模型读到这句话。真正的修法是描述符上加一个 `listed` 字段，那属于 `dsh-commands`，等第二个需要它的行出现时一起做。

**切换条上的种类角标删掉了。**`content-column` 里的一处删除同时覆盖 `page`、`chart`、`component` 以及将来所有种类，而内容栏保住了「它不认识任何具体种类」这条性质。标签页现在只说自己的标题。

## Alternatives considered

**本行自有的 Log-only 会话事件。**本片否决，依据是一条机械事实而非偏好：这种事件要在被卸载后仍然安全所需要的 `ignorable: true`，插件根本写不出来——`Session.append` 对非 surface 事件的选项元组是空的，而全仓没有任何生产代码写过这个标志。没有它，新的 `SessionEventMap` 成员就是必读的，不认识它的构建会拒绝日志。而 `command/run` 本来就逐字记录这份文档，并且文档里写明只进日志；`plan-mode` 是「插件按命令名过滤并读它的 `args`」的先例。推迟的代价正是这个事件唯一能买到的东西：一个决定存什么的地方——这也是白名单今天只能是客户端义务的原因。

**第四档 `answer`：把模型的回答返回给同一次工具调用。**否决：它需要一条 HTTP 路由、一张待回执表、一个模型可见的三值枚举和两个 Config 字段，而换来的唯一增量是答案落在一次工具调用内而不是新开一轮。在一个「对话是正门」的产品里，这是延迟上的便利，不是能力。复查触发器是实测证明多一轮不可接受。

**给 report 档位做一张 Config 覆盖表。**作为过早的抽象否决：见第 3 格。一个部署挪动档位，改变的是智能体被告知发生了什么，这是目录层面的决定。

**用座位送来的 label 组装通知。**否决：一个从 wire 上来的 `componentLabel` 字段，与「绝不采信客户端自由文本」这条规则直接矛盾。wire 只带标识符。

**从动作文档里去掉 `nodeId`。**否决：没有它，同一份 spec 里两个同类组件就无从区分，通知也说不出是哪一块在说话。

**「组合起来的那一轮」的证据落在浏览器泳道，而且不可能落在转录泳道。**一条驱动按下的 ACP 快照场景不可能存在：`/component-action` 只能经 `remote.commands` 到达宿主，ACP 协议没有命令方法。这条泳道仍然组合了命令注册表，因为它钉住的那段描述告诉模型按下会回来，提供这段描述的组合就得兑现得了；泳道做不到的是把这条命令发出去。同一堵墙在下一层也立着——包内的裁判测试同样起不了 `agent-loop`，因为 `component-surface` 注册在 Client 编译面而 `agent-loop` 是 Host 包，两个聚合在 `Context` 合并上会撞车。于是组合测试钉住交接之前的全部（命令存在、交出去的说法、留下的日志、本行不在这套组合的策略前面加自己的闸、卸载时的释放），而 `apps/web/tests/component-surface.e2e.ts` 钉住那一轮本身。`content-console` 泳道仍然钉住这次**确实改了**的模型可见半边：工具描述。

**Known Limitations，写在两个包的 README 里。**

- payload 白名单是界面那半边的承诺。命令注册表在任何 handler 跑起来之前就把命令输入逐字记下了，所以宿主拒绝它的时候，一份超量文档早已进了日志；宿主执行的是「不投递」。
- 折叠行写的是机制而不是那块界面。一条通知在对话里是一行折叠行，表头写着「上下文注入 · content-component」（英文界面是 `Context injection · content-component`），旁边那句一行摘要是个可伸缩的格子，控制台三栏布局的聊天列宽度会把它挤到零宽。两者都是 `ui-conversation` 的外壳，对所有产出方一视同仁；按产出方给显示名是那个包里的改动。
- 唤醒预算只在内存里。已花掉的唤醒记在一张以智能体对象为键的表里，所以重启之后每个智能体都重新拿到整份预算，恢复出来的会话也无从知道它的那些按下已经开过几轮。
- 模型仍然看不见内容栏里现在有什么。它知道自己发过哪些调用、回来了哪些手势——不知道用户正在看哪一条，也不知道任何一块此刻显示着什么。
- 渲染器一旦多放一个该动作没声明的属性，这个控件的每一次按下就都到不了任何地方：宿主是整条手势一起拒掉而不是做裁剪，而组件行在发送前不检查 payload。
- 这条命令列在终端用户的斜杠菜单里，还带着 `<json>` 提示，因为注册表没有藏起一行的办法。真在那里手打一行，答的是与丢掉的按下同一句拒绝，并且会把它点到的那一块重画成这句拒绝：手势折叠读的是一行里带的标识符，只有 handler 才拿它们去对当前在显示的条目。
- `silent` 档的动作会让那一块说对话已经收到。谁也没告诉的那次投递和开了一轮的那次投递结算成同一条不带文案的成功，折叠把两者都读成 `sent`。目录里今天没有任何动作声明 `silent`；第一个声明它的动作，要在同一次改动里定下它那一块画什么话。
- 展开那条折叠通知并不比不展开好：`notice` 画的是它给模型看的正文，也就是写给智能体的那句英文，句子里还带着条目与节点的标识符。它的复查触发器与「按产出方给显示名」那个 `develop` 线改动是同一个。
- 折叠按块而不按动作：一个声明了两个动作的组件，两个动作共用一格，所以条画出来的是它最后一次上报的状态，而不是「它最后一次上报**该动作**」的状态。目录里每个组件都只有一个动作，等真出现第二个的那天，格子的键跟着长一位。
- 日志开了却没合上的那次按下会一直读作「正在发送」。两条记录分别写在 handler 前后，宿主在两者之间停下就会留下一个没合上的格子——之后没有任何东西会去合上它，这一块要等后来的调用替换掉这条条目才恢复可按。压根没产生任何记录的那次按下是另一回事，它会自己了结。
- 两句结算文案在任何界面里都是中文。它们由 handler 写下，而 handler 拿不到浏览器的语言——命令结果就是一个字符串，日志又必须留下用户当时看到的那些字——于是非中文控制台把它们画在聊天里，紧挨着一条条上文案来自 `component-kit` 字典、已经本地化的条。解法是改成由客户端翻译的 key，或让命令结果带上语言；触发器是控制台开始提供中文以外的界面。
