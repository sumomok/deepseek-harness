# Agent Note：server-sidebar——在底部写明登录者是谁，以及撤销它的那一个控件

Status: implemented

[English](2026-09-04-server-sidebar-identity-and-sign-out.md) | 中文

## 问题

[`@deepseek-ai/dsh-experimental-auth-gate`](2026-09-04-auth-gate-bearer-scheme-and-sign-out-route.zh.md) 把访客的访问令牌送到 dsh 需要它的两处，并在令牌消失或过期时离开去登录页。它没有的，是一个人主动离开的入口：产品外壳的底部只有一个灰色圆圈和字面的「用户」，整套界面里没有任何东西能有意地把访客登出。在一台共用的机器上，这就是全部缺口——想不再是那个登录者，唯一的办法是关掉标签页，然后指望令牌自己过期。

另有两条约束塑造的是答案，而不是问题。

- 侧栏还必须能在压根不组合 auth-gate 的组合里工作。它是产品外壳的承重面；一个读不到名字的底部、一个没有登录页可回的按钮，都不能把它一起拖垮。
- 这里的一切都是一个人的身份。它们一律不得进入模型：名字不行，解码它所用的令牌不行，记录二者任一的会话事件也不行。

## 决策

**名字只是用于显示的副本，在浏览器里从一枚未经验证的令牌解码得来，不为任何事情充当权威。** `client/identity.ts` 读 `localStorage.accessToken`，剥掉登录页写入的 `Bearer` 前缀，不验签地解码 payload，取出 `Config.displayNameClaim` 指名的那个 claim。在这里验签，等于拿别人递来的密钥去核对别人递来的声明；有能力验证的是这套进程前面的反向代理，它早已用这枚令牌把请求路由到了这里。因此一枚伪造令牌买到的只是底部一个错误的名字——没有任何界面以这个值为门槛，它也到不了任何请求。它同样不进模型，且是仓库那条规则所追踪的严格意义上的不进：没有会话事件携带它，也没有任何东西去追加这样一条，README 的 Model Experience 保持 `None`。

**claim 名是 `Config`，通过第二条只读路由送达。** browser 半边收不到任何 cordis 配置——启动清单携带的是插件名，不是它们的 `config` 块——所以 `GET /server-menu/identity` 应答 `{ displayNameClaim }`，与 auth-gate 自己那条 settings 路由应答它那三个值的做法一致。这个字段必填，并在加载期拒绝空白值，因为它挡住的那种失败是无声的：claim 名写错的部署会把每一个登录者都显示成匿名，而页面上和日志里都没有任何线索说明原因。该路由只需要 `ctx.webServer`，不需要 `ctx.settings`：写明登录者是谁并不是持久状态，没有组合 settings 能力的部署照样应当有底部。

**与 auth-gate 之间的六项约定是逐字复制，不是导入。** `Bearer` 剥离、JWT payload 解码、`/auth-gate/settings`、`/auth-gate/logout`、那行删除 cookie 的指令，以及把登录页凭证参数从回跳地址里剔掉的那条规则，都在本包里重新写了一遍。跨包直接导入符号并非本仓库为两个客户端相邻插件设计的耦合方式（`packages/client/AGENTS.md` 的导出纪律一节），而且本包出于同样的理由已经有过一份这样的副本——`client/pages.ts` 复制 content-frame 的 settings 路由而不是导入它。改为发明一条共享缝（第三个包，或一个插件注册、另一个插件消费的 `ctx` 服务），会让 auth-gate 在每一种组合里都成为侧栏的硬依赖，包括那些什么也不设门槛的组合，而换来的只是省下六段本来就由两个同仓维护的包一起改动的短字面量。每一处复制点与两份 README 都写明了它是复制品，这才是 auth-gate 变动时能被找到的保证。

**退出按固定顺序跑五步，且无论前一步结果如何，每一步都会执行。** 停掉正在进行的工作；`POST /auth-gate/logout`；删除登录页的存储键；清掉镜像 cookie；跳转到登录页。这个顺序本身就是论证：

- 先停，是因为只有这一步的对象还活着。一个继续跑的回合，会以一个刚刚离开的人的身份继续花用部署方的凭据，而之后的每一步都让它更难被够到——它所依赖的令牌两步之后就被丢弃了。
- 先停，同时也是唯一一步被设了期限。它之后的四步才是真正把令牌丢掉的动作，而那四步只依赖这个浏览器；停止是唯一一步要等宿主的，因此最多等三秒。不设上限，就意味着一次始终不应答的取消——断掉的连接、卡在回合中间的宿主——能把访客连人带令牌一起扣在页面上，而这恰恰是整套流程存在的目的所要避免的结果。
- 令牌先于 cookie，因为那条登出请求正是被这枚 cookie 路由到本进程的；浏览器在 fetch 发起时附上 cookie，这才是这个顺序成立的原因（与 auth-gate 的 `leaveForLogin` 记录的是同一条推理）。
- 那条登出请求只发出、不等待。`keepalive` 是让它跨过跳转活下来的东西，同时也正是让「等它」既无意义又有害的东西：一条被代理挂到自己读超时才断的路由，会把访客扣在一个回合已经停下、令牌仍留在存储里、屏幕上又没有任何说明的页面上。
- 存储与 cookie 都先于跳转，因为已经离开的页面什么也清不了。
- 任何一步失败都只记一条 `console.warn`，离开阶段那三步也各自带着自己的守卫，理由正在于此：一个被设置为拦截本源站点数据的浏览器，会在删除存储键和写 cookie 时抛错，而这两者都不该让访客失去那次跳转。访客反正要离开；一步跑不通，不构成把其余几步一起放弃的理由。

**存储按枚举的键名清除，绝不用 `localStorage.clear()`。** 这些键是登录页自己的——令牌、它的时钟、它的加密标记、它的续期时钟、两份档案副本、一份应用权限表、它在查询参数里接受的那个备用凭据，以及它同样会写的 `…Auth` 拼法。一次性全清会把外壳自己的私有键一并带走；在同源上还提供其它应用的部署里，还会带走它们的——把访客从这个按钮从未承诺触碰的东西里一起登出。枚举的代价是一份必须与登录页保持同步的列表；这份列表带来的失败是残留一个键，而全清带来的失败是别人的会话。

**停止扫描向会话列表询问谁在跑，并且总是停掉当前打开的那个对话。** `SessionSummary.running` 是宿主推送、与真实执行绑定的那一位，因此它是访客没在看的每一个对话的判据。当前打开的那个不看这一位也照停：对空闲会话的停止是宿主直接应答的空操作，而对屏幕上这唯一一个对话去信任一个推送位，会让退出这件事先取决于某一帧是否已经到达。每一次停止都走出厂停止按钮所用的同一条按会话作用域取到的 `conversation.cancel()`，由 `dsh-client-ui-conversation` 自己那个 `scopedConversation` 的复制品解析得到（那个包并不导出这样一个 helper）。

**不向部署方自己的登录体系告知任何事。** 本包不知道任何吊销接口，令牌在签发方那一侧仍然有效直到过期——这一点写进 Known Limitation，而不是留作隐含事实，并写明有这样一个接口的部署该在哪一步（第 2 步）调用它。

**响应式的名字走 inject 的 `hooks` 隔间。** 另一个标签页写入令牌时底部的名字会变，所以它是一个注册方私有的响应式事实；`packages/client/AGENTS.md` 为这类事实只给了一条通道，而那条通道不是在组件里用 `useState` 去订阅存储。`createDisplayNameSource` 是一个裸的 `HostObservable`，由渲染器绑定为 `useDisplayName`，组件里没有任何订阅机制。这个源同样不保留名字的副本：`getSnapshot` 每次都重新读存储，每一次存储变化都通知每一个订阅者。留副本就得有刷新它的路径，而唯一的刷新路径是订阅——那会让名字在没有任何订阅存活的那段时间里过期（首次挂载之前，以及一次卸载与下一次挂载之间），还会让刷新恰好跑在哪个订阅者名下，就由它把其余订阅者应得的那次通知吃掉。名字是字符串，`useSyncExternalStore` 按值比较，因此重新读取只有在名字真的变了时才带来一次渲染。

## 备选方案

**由两个插件共同消费的一个身份服务。** 否决：那会让 auth-gate 成为外壳侧栏的硬依赖，而外壳自己的组合（`overlay/sidebar-menu.patch.yml`）刻意不组合它。这条缝还会为了一个底部之外没有任何读者的用途，把一份凭据搬过包边界。

**显示 `sub`，或者任何看起来像名字的 claim，而不是一个配置出来的 claim。** 否决：`sub` 是主体 id 而不是名字，而对 claim 名做启发式匹配，是一种本包无法对之失败得响亮的猜测。一个必填的 `Config` 字段在加载期把部署方的答案说清一次。

**`localStorage.clear()`。** 已在上文否决：它会把访客从这个 origin 上的每一个应用里登出，包括本外壳自己记住的状态。

**先二次确认。** 本片否决：`cancel` 会保留该对话及其待处理的排队内容，因此误点的代价是一次登录往返，没有任何持久损失。这一点写进 Known Limitation，好让「要不要加确认」的产品决策有当前行为可依。

**复用 auth-gate 自己的 `leaveForLogin`：侧栏只删令牌，其余交给那个包的存储监听。** 否决：那只在组合了 auth-gate 的组合里成立；它会让整套顺序依赖一个本标签页对自己的写入并不会收到的 `storage` 事件；而在一次主动退出里最要紧的那几步——停掉正在进行的工作、删除登录页的其它键——本来也不是那个函数的职责。

**只取消当前对话。** 否决：外壳会代访客创建会话（工作台、每一条工作流），所以「我正在看的那一个」并不等于以这个人的身份正在跑的回合集合。扫一遍列表，代价是一次快照读取，外加每个在跑的对话一次 `cancel`。

**把名字放进侧栏已有的工作流 store。** 否决：那个 store 承载的是 server-menu 文档，而针对它快照的每一条既有断言都得多长出一个与工作流毫无关系的字段。hooks 隔间才是客户端规则为「注册方私有的响应式事实」已经指定的通道。

## 后果

`@deepseek-ai/dsh-experimental-server-sidebar` 现在有一个必填 `Config`，因此每一个插入它的组合都要写明 `displayNameClaim`：两份包内 overlay、两份 `apps/web` 场景 overlay，以及 `workflow-route.client.spec.ts` 里的两处测试组合。缺了它的行会在加载期失败——对一个没有可辩护默认值的字段来说，这正是「配置错误要失败得响亮」应有的读法。

这个按钮没有浏览器级证据。本包的 Playwright 场景没有组合 auth-gate 行——那个包会以令牌为门槛拦住整个页面，于是场景里其余每一条断言都得先自带令牌——所以整套顺序改由针对注入式 `SignOutBrowser` 与真实会话树 cancel 面的单测覆盖来证明，这个缺口写进了 README。

底部如今是本组合里第二处从部署方令牌里读 claim 的界面。若出现第三处，该合并的就是 `client/identity.ts` 里的那几份复制——到那时，建缝的理由是三个读者，而不再是把两个本来就一起发布的包耦合起来。
