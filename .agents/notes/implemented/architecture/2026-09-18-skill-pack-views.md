# Agent Note: A skill pack's views reach the content column, and a view opens on the user's click

Status: implemented

English | [中文](2026-09-18-skill-pack-views.zh.md)

## Problem

Three things were missing between the two packages [the reconciler note](2026-09-18-skill-pack-reconciler.md) and [the catalog-registry note](2026-09-18-component-catalog-registry.md) landed.

The first is the wire between them. `ctx.skillPackParts` was a service key nothing provided, so every pack naming a part stayed inactive on every deployment — the correct fail-closed answer and a useless one.

The second is the views. A pack ships view files, `ctx.skillPacks.activeViews()` answers them, and nothing read that answer: `component-surface` built its view index from its own `Config` and from nothing else, so a pack's view was a file on disk that no sidebar ever listed. Making it list one raises a question the configured case never had to answer — what a deployment does when a third party's view is wrong. A refused configured view fails the row, because a deployment's own `cordis.yml` is a file that deployment can fix; doing the same to a pack would let one bad view file in a delivered pack take down the whole content column.

The third is the data page. A view placing `toy.data-page` was refused at load, by id, for a stated reason: the tool path asks the user before that page is drawn, and a click on a sidebar row asked nobody. That refusal kept the one view a pack most wants to ship — the deployment's own screen for one table — out of the sidebar altogether.

## Decision

**One adapter row connects the two packages, and it is the only place the edge runs in both directions.** `@deepseek-ai/dsh-experimental-skill-pack-components` injects `componentCatalog`, `componentViews` and `skillPacks`; it provides `ctx.skillPackParts` and it registers the active packs' views. Neither package depends on the other, and a deployment that composes one without the other gets the fail-closed answer each already had. A micro-package rather than an entry inside `component-surface`: that package must be composable in a deployment with no skill packs at all and must not carry a type-only import of `skill-pack` to do it, and the reverse holds for `skill-pack` — an adapter inside either one is a dependency edge the reconciler note's boundary already refused.

**The parts are the components the deployment *offers*, not the ones it registered.** `ComponentCatalogRegistry` takes a `withheld` list at construction and answers `offered` beside `components`; `component-surface` passes `withheldComponents(options)`, the one function that already decided which components a deployment's `dataPage: false` keeps out of the tool. A component nobody can place cannot be drawn, so a pack requiring it stays inactive.

**`ctx.componentViews` is the view index, and it takes views from two places.** A service rather than a `registerViews` method on the tool row: the index is read by the sidebar route, by the command and by the adapter's judgement, all of which need it by name and none of which can reach the row's closure. The deployment's own `Config.views` are the registry's construction options; every other contributor calls `register({ owner, views })` and gets a disposer. The registry is built with `new ComponentViewRegistry(ctx, options)` inside the `ctx.inject(['componentCatalog'])` callback rather than through `ctx.plugin`, so that it exists before the row's first component contribution and logs under the row's own name.

**Both sources are judged by one pass, and only the consequences differ.** `judgeView` runs parameter substitution, then `validateComponentCall`, then the data-page rules, on a configured view and a contributed view alike. A refused **configured** view fails the row, after an error line naming what that costs. A refused **contributed** view is dropped: the row loads, every other view stands, every registered component stays registered, and the drop is stated once at error level under this row's name. A pack's view never reaches that drop in practice, because the pack is judged before it is offered — `PartsSource.judgeView(view)` asks the same registry, and a refusal makes the pack inactive with a `view-refused` entry carrying the file, the path inside it and the surface's own sentence. `GET /skill-pack/status` carries all three, and the withholding report is written at error level when it names one, at info level otherwise: a pack waiting for a plugin activates by itself when that row is composed, and a pack with a refused view never does.

**Id collisions are decided by the ids, not by a feedback path.** `ctx.componentViews.configuredIds` is what a pack is checked against first, so the deployment's own views always win. Between two packs, [the view-checks note](2026-09-19-skill-pack-view-checks.md) settles it by withholding both. Either check is a pure function of the pack set and the configured ids — a registry that refused a registration and told the pack root about it would be a loop that oscillates.

**`params` are substituted when the view is loaded.** A view writes `{"$param": "table"}` in its spec and lists `params: { table: sys_layer }` beside it, under the pack-wide `metadata.pack.viewFormat` version [the view-checks note](2026-09-19-skill-pack-view-checks.md) added; substitution happens before validation, so what the catalog judges is the document that will be drawn and a refusal names a path in it. An unknown parameter name, a non-scalar value and a `$param` used as a list item are each refused naming the path. `$from` is untouched — it is the catalog's own binding between blocks, resolved at draw time, and a pack's parameters are fixed by whoever wrote the pack.

**A view may place the data page, and the user's click opens it.** The load-time refusal is gone from both sources and nothing stands in its place: no card, no approval request, nothing minted. Four facts are what make that the whole of it. A card in front of the click would be the same button twice — the page draws in the console's own origin, beside the [`content-frame`](../../../../packages/experimental/content-frame/README.md) screens of the same deployment, which open on a click and ask nothing, so confirming a press the person just made stops nobody. The model cannot run this command: `CommandInvocation` carries no source and `CommandSourceMap` has one member, `user`, pinned by a type-level assertion that stops compiling the day a second producer exists. The model's own way to that page — a `show_component` call placing `toy.data-page` — still goes through `ctx.approval` and its card, unchanged, because there the decision is the model's and the person is being interrupted mid-turn. And the deployment still decides: `dataPage: false` withholds the component, and a view placing one is then refused by name at load. The shell settles what would otherwise have been the question's home: `dsh-client-ui-conversation` draws no transcript at all for a session that has never run a turn, and a blank draft with the sidebar beside it is where nearly every one of these clicks is made — so a user-answerable question on a command row would have been built, logged and invisible.

**The click appends `content-component/shown`.** `content-component/resolved` requires a `ToolCallId` and a click has none; the session fold reads the two identically and the invariant's `APPENDED_EVENTS` already names both, so the column, the extractor and a replay see one entry either way.

## The decision gate

| Gate | Answer |
|---|---|
| 0. Which standing principle already decides this? | **A capability seam is complete, never one role** puts the second view source behind a registry with a Service Definition, a provider and consumers rather than a callback on the tool row. **Registrations are effects** decides that `register()` answers a disposer and that the adapter holds exactly one. **Model-visible ⟺ logged** decides that a click writes its own session event, because nothing else in the log would explain the entry. **Misconfiguration fails loud** decides that a deployment's own broken view fails the row — and its converse, that a third party's broken view is *not* the deployment's misconfiguration, is why a pack's is dropped instead. **Enforce a decision in the operation that makes it** decides where the data page is judged: in `judgeView`, against the components the deployment offers, rather than in a sentence asking somebody to be careful. **Explicit > implicit at package boundaries** decides that `offered` is a construction-time `withheld` list rather than a rule the catalog infers. |
| 1. How many new permanent surfaces? (count, then list) | **6.** One npm package and plugin row (`@deepseek-ai/dsh-experimental-skill-pack-components`); one Cordis service (`ctx.componentViews`, with `index`, `configuredIds`, `judge`, `register`, `onChange`); one method on the already-declared `ctx.skillPackParts` interface (`judgeView`); one member of the closed `PackMissing` union (`view-refused`, carrying `view`, `path` and `reason`, visible at `GET /skill-pack/status`); one on-disk view-file element (`params`, and the `{"$param": "<name>"}` reference inside a spec); one config field (the catalog registry's `withheld`). No new tool, no new session event, no new route, no new config field on the surface row, no new dictionary key, and no new approval gate. |
| 2. Smallest version that proves it right | The second source alone: `ctx.componentViews.register(source)` fed from `activeViews()`, with the sidebar route and the command rebuilt on change. That is the whole claim — a pack can put a page in the column and take it back out, with no restart. The rest is what the claim costs once a pack's view is a real view: the `view-refused` kind, because a judged view that fails must not take the pack's components down with it; and `params`, because one pack file ships to deployments that name their table differently. |
| 3. Seam or hardcode? | **One seam, named:** `ComponentViewSource` — two real contributors exist today, the deployment's own `cordis.yml` block and this adapter's reading of `activeViews()`, and the sidebar cannot tell them apart. **Everything else is hardcoded:** the refusal sentence a click naming no view earns, configured views winning a collision, substitution happening at load rather than at show time, and the data-page rules being the tool's own rather than a second set. **No new config field:** whether a view may place the data page is `dataPage`, the field the tool already reads, because a deployment that offers the page offers it to both ways in. |
| 4. Boundaries | See below. |

## Testing

Unit suites pin parameter substitution and every path it refuses, the registry's two sources and their ordering, the id-collision rule and both log lines, the judgement of a contributed view against a catalog that changes under it, the data-page rules a view is judged by, and the reconciler's `view-refused` reporting with its claimed-id accumulation.

A real Loader composition boots `component-surface` with the command registry, the session store and the content-surface router, and clicks the command in a session with **no turn open**, which is where a sidebar click is made: it asserts that a view placing the data page opens on that click with a textless success, that the `content-component/shown` beside it names the view and carries the spec that names the table, that a second click appends again, that a view placing no data page opens the same way, and that a click naming no configured view earns `没有这个视图。` and opens nothing. The chat row's own cases pin the one sentence it draws and the settlements it draws nothing for.

Per-file coverage of every changed `src` file is 100%.

## Alternatives considered

**Put the adapter inside `component-surface` as a small entry.** Rejected. It would give a package that must compose in a deployment with no skill packs a type-only import of `skill-pack`, and the boundary the reconciler note drew — neither package reaches into the other — would hold only by the grace of `import type`. The micro-package costs a `package.json`, three tsconfig registrations and two rows in the generated catalogs, and it makes the edge a thing a deployment composes rather than a thing that is always there.

**Add `registerViews(source)` to the tool row instead of a `ctx.componentViews` service.** Rejected. Three readers need the index by name — the sidebar route, the command and the adapter's `judgeView` — and a method on the row reaches none of them. A service also gives the collision rule one home: `configuredIds` is a question the adapter asks before a pack is offered, and a closure cannot answer it.

**Let a refused pack view fail the row, the way a refused configured view does.** Rejected. A delivered pack is not the deployment's own file. One bad view in one pack would take down the content column, the tool and every component with it, for a deployment whose own configuration is correct.

**Drop the refused view and activate the pack without it.** Rejected for the reason the reconciler note already gives: the pack's instructions describe the whole pack, and a model following them into a view that was silently dropped produces the half-drawn page the whole-pack rule exists to prevent.

**Substitute `params` when the view is shown.** Rejected. The catalog would then judge a document that is not the one drawn, a refusal would name a path in a spec the user never wrote, and a deployment would learn about a bad parameter on the first click rather than at load.

**Ask the user to confirm the click, through `ctx.approval` or through a card of this package's own.** Rejected. `ctx.approval` refuses to ask without an open turn — its `approval/asked` + `approval/decided` audit pair must be enclosed by one — and a sidebar click is made between turns, so that route answers `没有打开。` on nearly every click rather than asking anything. A card of this package's own can be drawn between turns, and it was, and it is what the four facts above rule out: the click is the decision, the neighbouring screens of the same deployment open without one, the model cannot reach the command, and the card lives in the same DOM as the page it is guarding.

**Draw that card on the command's own chat row.** Rejected on top of the above. The shell draws no transcript for a session that has never run a turn (`ConversationSession` renders nothing while the session is blank, and the chat target reports no activity for a transcript holding only command rows), and a blank draft is this console's entry state, so the card was built and logged and never on screen. Any user-answerable question this package raises has to live somewhere the conversation draws in every phase.

**Append `content-component/resolved` from the click.** Rejected: it requires a `ToolCallId` and a click has none. Fabricating one would put an id in the log that names no tool call, and the fold reads `shown` and `resolved` identically, so the column, the extractor and a replay already see the same entry.

## Consequences

A deployment can ship a skill and the page that skill talks about as one pack, and a user can click that page open. The pack's views appear when the pack activates and leave when it does not, with no restart, and a pack whose view the surface will not draw is inactive, named in the status route with the file and the value, and written to the process log at error level — where before it would either have been invisible or have taken the console down with it.

The data page opens on one click, which is what the sidebar row is for. What a deployment gives up in exchange is the chance to change its mind per click: once `dataPage` is on, every configured and contributed view that places the page opens it, and the only remaining control is the component list itself. That is the same control the tool has, and it is the one a deployment can actually reason about.

The one sentence this command can draw stays on its chat row, where a blank draft does not show it. It is a refusal nobody can act on — the row is gone from the menu on the next load — so nothing was moved to make it visible, and the Known Limitations of both this note and the package README record it.
