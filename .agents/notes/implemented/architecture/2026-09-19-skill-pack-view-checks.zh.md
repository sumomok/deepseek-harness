# Agent Note: 技能包的视图有版本、在安装时被检查，并且不共用 id

Status: implemented

[English](2026-09-19-skill-pack-view-checks.md) | 中文

## Problem

关于技能包视图的三件事，是由技能包以外的东西决定的。

**视图文件没有版本。** [技能包视图那篇](2026-09-18-skill-pack-views.zh.md)给一种对自己一言不发的文件格式加上了 `params` 和 `{"$param": …}` 引用。一个照着后来的格式写、却装在更早构建上的技能包，会被按为别的东西写的规则读：读取方拿走它认识的键、忽略它不认识的，于是这个技能包带着一张谁也没检查过的页面激活了。

**视图在安装时没有任何检查。** `syncPackRoot` 核对暂存树的文件名、扩展名、链接和路径，然后就换进来了。一份清单解析不了、声明的视图文件根本不在、或者视图这套部署画不出来的发放，会干干净净地装进去，并且只在 `GET /skill-pack/status` 上说这件事——那已经是把文件拷进来的运维走后几个小时。[发放包那篇](2026-09-19-skill-pack-archive-install.zh.md)核对的是一个归档*是不是它自称的那个*；没有任何东西核对它自称的那个东西，是不是一套这套部署交得出去的技能包根目录。

**两个技能包争同一个视图 id 时，是 `localeCompare` 把它们分开的。** 判定用 `left.skill.localeCompare(right.skill)` 给技能包排序，并让排在前面的那个留着被争的 id。`localeCompare` 的答案来自主机的 ICU 数据和默认区域设置，于是两台放着同样技能包的机器可能交出不同的东西——而输掉的那个技能包什么也没做错，只是在那台机器上排在了第二。同一个调用还决定着扫描技能包根目录的顺序，以及写归档文件时的条目顺序——在那里它决定的是归档的字节，而那篇 note 承诺这些字节是可复现的。

## Decision

**`metadata.pack.viewFormat` 是视图文件的格式版本，一个技能包只写一次。** 一个整数，声明了视图的技能包必须写，没声明视图的技能包写了也没有意义。`PACK_VIEW_FORMATS` 是这套构建读的版本——`[1]`——写了别的数字的技能包，以及声明了视图却什么都没写的技能包，会被扣下，并由新的封闭联合成员 `view-format` 带出这个技能包写的版本和这套构建读的版本。按技能包而不是按文件，因为一个技能包的视图文件是一起发放的，而技能包是整体交出去的；按文件的版本会让一个技能包有一半可读，而整体规则存在的意义正是不要这种状态。这项检查会盖住逐视图的那些原因：每份文件解析成了什么，是按错的规则读出来的，报出来等于报一份没人该信的读数。

**一份发放在成为技能包根目录之前，先按技能包根目录核对。** `verifyStaged` 用技能包根目录自己的读取器重读暂存树，并把里面每个技能包按四条规矩收：清单解析得了、声明视图的技能包写了这套构建读的格式、每份声明的视图文件都在并且确实是视图，以及——在调用方组合了表面时——那个表面画得出来。任何一项没过，**整份**发放被拒，抛出点名技能包、文件和原因的 `PackInstallRefusal`（`pack-manifest`、`pack-view-format`、`pack-view`、`pack-view-refused`）；暂存的同级目录被删掉，旧的根目录逐字节保持原样。整份而不是逐个技能包，因为一套发放集是关于「这套部署手里有什么」的一句话，而只装读得通的那一半，留下的根目录既不是旧的那份发放，也不是新的那份。

**这套部署眼下还满足不了的要求不算拒绝。** 一个点名了这里没有的插件、部件或平台版本的技能包会被装进去、判为未激活、在状态路由上说清楚它在等什么，并在那一行被组合进来时自己激活——这正是[发放包那篇](2026-09-19-skill-pack-archive-install.zh.md)发出去的行为，它的用例也钉着它。所以组件目录的判定只对其它要求已经满足的技能包问：`DEFERRED_REQUIREMENTS` 点名那四种意味着「在等」的种类，带着其中任何一种的状态不产生任何拒绝。这条线划的是「还会不会变」。插件可以到；写坏了的视图文件不会自己变好。

**组件目录的判定是一个参数，因为那是唯一诚实的落点。** `skill-pack` 不可以 import `component-surface`——[判定器那篇](2026-09-18-skill-pack-reconciler.zh.md)在两个方向上都划了这条界——而发放侧调用 `syncPackRoot` 的人根本没有目录。于是 `syncPackRoot(root, delivery, verify)` 收下 `VerifyStagedPacks`：它拿到每个已经读好的暂存技能包，答出第一条拒绝。`SkillPackRegistry` 用 `ctx.skillPackParts` 造一个传进去——那正是本来就在为判定回答这同一个问题的那道缝；没有组合任何表面的调用方什么也不传，那四项结构检查照样跑，组件目录的判定推迟到判定环节，和别人手工写进根目录的技能包完全一样。`$param` 的解析跟着这份判定走、而不是另起一份，因为 `applyViewParams` 是组件表面自己的，而在这里再实现一次就是判定器那篇拒绝过的、会漂移的第二个答案。

**两个技能包争同一个视图 id 时两个都扣下。** 这条规则在每个技能包各自判完之后、对整个根目录判：在这个根目录本来会交出去的那些技能包里，被认领超过一次的 id 会把每一个认领者都扣下，带上一条点名这个 id 和其余每个技能包的 `view-id-conflict`。因为别的原因未激活的技能包不占任何 id，所以一个谁也没被交出去的技能包扣不住一个本来会被交出去的。已提供的组织技能包持有的 id 归它，在这条规则之前就扣下根目录里声明它的技能包（[组织接收接缝那篇](2026-10-05-skill-pack-organization-intake.zh.md)）。因此 `PartsSource.judgeView` 去掉了 `claimed` 参数：部署自己的 `configuredIds` 仍然在那里被拒，因为部署自己的视图拥有自己的 id，而技能包对技能包这个问题，只有技能包根目录同时看得见两边。

**顺序按码元。** `compareCodeUnits` 替掉了这个包里的每一处 `localeCompare`——`statuses()` 的技能名顺序、技能包根目录扫描的目录名顺序，以及 `buildPackArchive` 写条目的路径顺序。两台放着同样技能包的主机现在答出同样的列表、写出同样的字节，无论它们带的是哪套 ICU 数据和默认区域设置。

**`buildPackArchive` 只按技能包文件的规矩收一套集合，一份也不读。** 它的承诺被收窄成这句话：名字、路径和扩展名在写归档的地方检查，而清单、视图格式和每份视图文件由装它的那套部署判，因为那一侧才有画这些视图的表面。

**技能包根目录的监视器在装好时重读一遍根目录，和发放目录的监视器本来就做的一样。** 一个落在监视器自己第一次列举与它的原生流开始供事件之间的技能包，两边都不在——那次列举被 `ignoreInitial` 忽略掉了，而那个流还没开始——所以在此之前它要等到根目录下一次发生别的变化才会被交出去。对这个工作区里的 `chokidar` 在 macOS 上做的实测显示，大约每四十次到达就有一次丢掉那第一个事件；装好时的那次读，正是让到达这件事本身、而不是后来某次变化，把这个技能包交出去的东西。

## The decision gate

| 0. Which standing principle already decides this? | **Misconfiguration fails loud** 在最早能定的那一点，决定了一份发放在换进来之前核对、而不是事后在路由上报——反过来也决定了一个在等插件的技能包不是配置错误，照装不误。**Enforce a decision in the operation that makes it** 把这项检查放进 `verifyStaged`——那是唯一一个把暂存树变成技能包根目录的操作——而不是放进一句请发放控制台小心点的话里。**Explicit > implicit at package boundaries** 决定了组件目录的判定是传进来的 `verify`，而不是一条部署可能有也可能没有的 `?? undefined` import；也决定了 `viewFormat` 是写出来的字段，而不是从一份文件碰巧带了哪些键里推出来的版本。**A capability seam is complete, never one role** 把这份判定留在 `ctx.skillPackParts` 上——它已经有 Service Definition、有 Provider、有 Consumer——而不是为同一个问题再开第二条问法。**Opaque cross-boundary values are stated, never guessed** 是一个不认识的 `viewFormat` 直接拒、而不是回退到这套构建知道的最新版本的原因。 |

## Testing

单元用例钉住格式（读得了的技能包、写了这套构建不读的版本的、什么都没写的、任何版本下都没声明视图的，以及各自得到的那句话）、两条路线（技能包路线与归档路线）上的安装检查（解析不了的清单、不认识的格式与没写格式、声明了而发放没带的文件、不是视图的文件，以及它们各自让根目录逐字节不变、不留暂存同级目录）、部件不在照装的技能包、每个调用方表面收到的那套暂存集合、点名技能包与文件与原因的表面拒绝、没变时那条快路径什么也不问那个表面，以及一个不带 `SKILL.md` 的发放目录按它本来就不是技能包的样子装进去。id 规则从四个方向钉住：两个都扣下且各自点名对方、无论技能包按什么顺序到来、名字排序像什么都答同一个、每个被争 id 的每个认领者都被点名，以及因别的原因被扣下的技能包不会把 id 从一个本来会被交出去的技能包那里扣走。顺序在判定器和技能包根目录扫描两处都用大小写混排与中日韩名字钉住。

被监视根目录那一例让它的技能包在每次轮询时连目录一起重新到达一次，而不是只到达一次。还在装的监视器会丢掉那一刻创建的目录的事件，此后对一个它从未登记过的目录什么也不报，所以一次到达就是对一个由操作系统掌握的事件的一次机会；这一例断言的是这个技能包在不重启的情况下到达目录，而这里的注册表目录不会被别的东西失效，所以一套监视器从不触发的组合照样失败。

真实 Loader 组合覆盖这道缝的两侧。`skill-pack` 自己的组合在挂着部件源的情况下往被监视的目录投一个归档：那个源拒掉的视图会被点名拒绝、根目录保持原样；而一个在等插件的技能包会被装进去，`plugin-absent`、`part-absent` 和 `view-refused` 三条都在路由上。`skill-pack-components` 把组件目录、技能包根目录和适配行一起启动，并经同一个目录发放：一份点名了这套部署不提供的组件的视图，和一份点名了未声明 `$param` 的视图，各自带着组件目录自己那句话被拒，而侧栏保留它原有的视图；一份这套部署画得出来的发放则到达侧栏。`skill-pack`、`skill-pack-components` 与 `component-surface` 的 `src` 逐文件覆盖率为 100%。

## Alternatives considered

**把版本放进每份视图文件。** 拒绝。一个技能包的视图文件是一起发放的、技能包是整体交出去的，所以按文件的版本买到的，是描述一种整体规则本来就不允许存在的状态——半个技能包可读——的能力。它还把这句兼容性声明放在技能包作者最容易复制粘贴的位置，并把一次格式升级要改的地方数量乘上视图份数。

**把没写的 `viewFormat` 默认成 1。** 拒绝。这个字段的意义在于，一套构建遇到一份文件时说得出自己认不认识它所依据的规则；而默认值对每个从没听说过这个字段的技能包都答「1」，包括那些将来由后续格式产出的。预发布立场定了这笔代价：现在采用这个字段的技能包只要改 frontmatter 的一行，比一句收不回来的沉默便宜。

**一个技能包所需的部件不在就拒掉安装。** 拒绝，而这是这篇 note 最小心的一条。发放包那篇是有意做出「发放比插件先到」这一场景的：一套装进去并等着的集合，正是运维把技能包提前放到它所需的行之前的做法，而拒掉它会让两个不相干操作的先后顺序变成承重的。判别标准是：后面来的东西会不会改变这个答案。

**只拒有问题的那个技能包，其余照装。** 拒绝。一套发放集是关于这套部署手里有什么的一句话；只装其中一部分，留下的根目录既不是旧集合也不是新集合，而结果里那份 `retired` 表会点名一些以没人记录过的理由退役掉的技能包。整份拒绝让「这套部署手里有什么」仍然由一个文件回答得了。

**把组件目录 import 进 `skill-pack`，直接在那里判视图。** 拒绝。那正是判定器那篇在两个方向上都拒过的依赖边，并且会让一个必须能在没有任何组件表面的情况下组合的包带上一个。参数的代价是三个导出类型，换来的是发放侧调用方也能传进自己的那份。

**在 `skill-pack` 里实现一份 `$param` 检查，好让结构检查在没有目录时也覆盖它。** 拒绝。这套记法的规矩——要么是整个值要么什么都不是、只能是标量、绝不能当列表项——是 `component-surface` 的；在这里复制一部分，会接受真正那一遍会拒的东西，并在拒的时候点出不同的路径。这份判定改为跟着组件目录走，而同一遍的其余部分本来就在那里。

**被争的视图 id 留给前面那个技能包，只扣下后面那个。** 拒绝。「后面」必须有个意思，而每个候选都是机器的属性而不是技能包的属性：文件系统的列举顺序、区域设置的排序，或者一份发放碰巧被写出来的顺序。两个都扣下是唯一一个在哪里都一样的答案，而且它把修正放在该放的地方——两个技能包里必须有一个改 id，而状态路由把两个都点名，好让拥有它们的人看得出是哪一个。

**用固定区域设置（比如 `en-US`）的 `localeCompare` 排序。** 拒绝。它仍然取决于主机那份 Node 编进去的 ICU 数据，对同样的字符串在不同版本间仍然答得不一样，而且买来的是一个没人读的阅读顺序：`statuses()` 是被一条路由和一个判定器消费的，不是被一个照着字母表扫的人。

**边暂存边核对，逐个文件，而不是重读暂存树。** 拒绝，理由和发放包那篇就摘要给过的一样：在每份文件写下时才检查，会让暂存到一半成为一次失败安装的常态。重读写完的那棵树还顺带检查了真正会成为根目录的那个东西，包括写这件事本身对它做了什么。

**在 `buildPackArchive` 里核对，好让发放控制台早点知道。** 这次拒绝。写入方把技能包放在内存里、读取方读的是一个目录，所以这些检查需要在一张文件映射上再实现一遍；而最要紧的那一项检查——这套部署画不画得出这个视图——只有在有目录的地方才答得出。README 记下了写入方承诺什么、不承诺什么。

## Consequences

**买到的。** 一份成不了可用技能包根目录的发放，在有人把它拷进来的那一刻就被拒，进程日志里带着技能包、文件和原因，而不是变成一个技能包在每份目录里都悄悄缺席的根目录。技能包的视图文件现在说得出自己依据的是哪套规则，于是后来的格式是一条点出两个数字的拒绝，而不是一次无声的半读。而技能包根目录交出什么，在每台放着它的主机上都一样：两个争同一个 id 的技能包都被扣下，按 id 而不是按区域设置；这个包产出的三种顺序也不再取决于 ICU。

**付出的。** 现在发放一个技能包比以前严：一个只有 `SKILL.md`、没有 `metadata` 块的目录，以前装得进技能包根目录，现在被拒——这是对的，它本来就一直被报成 `manifest-invalid` 并且谁也没被交给过——而这是每份 fixture 和每个发放控制台都得做的改动。每个声明视图的技能包多写一行 frontmatter。两个以前会悄悄按「前面那个赢」解决 id 冲突的技能包，现在两个都黑掉，这更响，而且在它发生的那天更打扰人：这是「答案不取决于机器」的价钱。还有，发放控制台没法预先检查这其中任何一项，因为做决定的那个表面是部署的；README 把这件事记成了它本来就是的那条限制。
