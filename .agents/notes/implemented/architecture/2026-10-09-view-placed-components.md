# Agent Note: components only a written-down view places, and the two outputs that wire them to a data page

Status: implemented

English | [中文](2026-10-09-view-placed-components.zh.md)

## Problem

The data page a person works in edits a record in a form and shows one record in a card, and both are drawn inside the page: the add and modify forms cover the table they edit, so a view cannot lay them out. The form page is a component of its own, so that a view lays the table, the form and the card out side by side.

The form is a write path. It saves with the visitor's own credential, and the one rule the data page already holds is that a page a model's call places opens read-only ([the data-page note](2026-09-19-data-page-replaces-toy-crud.md)). That rule is enforced by judging the data page node of a call, so a form page in a call is a writable block with no data page node to judge: placed on its own, or riding along a call that reads a `dataSource` — that path appends the whole spec as `content-component/resolved` once the user agreed to a read, and the extractor draws it. The approval card the user answered would have described a read.

The form and the card also need to know which record. Only the page knows, inside its own drawing: which button the user pressed, which name they clicked. The catalog had a way for one block to read what another reports — an output and a `$from` binding — but the data page declared no output, and every one of its properties refuses a binding.

## Decision

**Placement is a property of the component, read through one predicate.** `ComponentCatalogEntry` gains `placement?: 'view'`, read only by `placedOnlyByViews`, and `viewPlacedNodes` picks a spec's such blocks. It is enforced in the operation that makes each decision. The tool refuses a call carrying one before the user is asked anything or it appends a record of its own, on both of its paths — a call that writes its rows and a call that reads a `dataSource` — through `refuseViewPlaced`, in one sentence whether or not the deployment offers the component. It reads the spec as the call wrote it, before validation judges the block's properties, so the refusal never lists what the component accepts. The extractor's `recordsEntry` draws a spec carrying one only from `content-component/shown`, the event a click on a view writes; a `tool/call`, a `tool/ptc-dispatch-start` and a `content-component/resolved` carrying one record no entry, so a refused call's record never draws the block. `describeCatalog` and `offeredEntries` leave such a component out of the description and out of what makes the tool worth registering, and the view pass accepts it. `ComponentCatalogRegistry.offered` keeps it, because `skill-pack-components` answers a pack's `requires.parts` from what can be drawn here, and a view draws it. `dataPage: false` withholds the form page and the info card with the data page (`DATA_PAGE_GATED_IDS`), and `componentNotOffered` lists the components the setting does not govern.

**The page declares two outputs, and both are state.** `editing` is `{mode (add|modify), type, id?, name?}`, what the page's add button or a row's modify button is editing; `opened` is `{id, name?, type}`, the record a name or a relation link opened, whose `type` is the related table for a relation link. Neither carries a counter: pressing the same button again publishes the same value, and the seat hands the blocks reading it nothing new. The declaration fixes withdrawal as publishing `undefined`, as the seat's output contract states: `opened` when the page closes its card, is cleared or turns a page, and not on a query; either when the record it names is deleted. Both outputs carry `readers: 'view'`, because every property that accepts them is on a component only a view places, so the description leaves them out with those components; a catalog test holds the declaration to the properties that accept each output. A block a call may place that binds the data page finds neither output: the reference is looked up only among the outputs that block could read, which are none, so the refusal says the page reports nothing and states no field of either.

**The two blocks read only a binding, judged only where a view is judged.** `toy.form-page` takes `relatedMeta`, written out because the save is reported under it and compared with the page's, and `request`, which reads `editing`. `toy.info-card` takes `record`, which reads `opened`, and `infoCardTabs`. `PropsField.bindsFrom` names, for `request` and `record`, the one component, the one output and the reason a refusal states. Both properties are optional in the schema, so a block whose binding has nothing to stand for yet is handed its properties without it rather than drawn as the seat's waiting line; `judgeDataPageParts` requires them in a view, written as that binding. The rule is not in the shared pass because the browser seat runs that pass after it has put the resolved value where the binding was, so a binding-only rule there would refuse every resolved block. A call never reaches the property, because placement refused it first, and a catalog test holds every `bindsFrom` property to a component only a view places.

**The view rules reject a file whose pieces contradict each other, and decide nothing about the visitor.** `judgeDataPageParts` runs after the shared pass and the page's own judgement: every `bindsFrom` property is that binding to a `toy.data-page` block of the same view, whole; a form page is placed at most once, saves into the page's table, beside a page whose `readOnly` is `false` and whose own add and modify forms are switched off; a page with no form page beside it does not switch a form off while keeping the button that opens it; an info card is placed at most once, beside a page whose own side card is switched off. Each is a press that would open two forms, a click that would open two cards, a form that would save into a table the view did not name, or a button that would open nothing. Whether the visitor may add or modify is still the backend's, answered per request, and which entrances the page draws is still the host's verdict on the visitor's rights; no rule here reads either.

**Values travel one way, argued by outputs.** [The layout-and-bindings note](2026-09-05-content-component-library-v2a-layout-and-bindings.md) rests the one-way flow on the components that publish an output. The table and the data page publish one and refuse a binding on every property they declare; the form page and the info card report actions and accept a binding, and publish nothing. The test that binds every output into every property of every publishing component covers the data page.

**Declared before drawn.** The two entries are `COMPONENT_KIT_VIEW_ENTRIES`, kept apart from the six `COMPONENT_KIT_ENTRIES`, because `component-kit` registers an entry together with the renderer that draws it and draws neither; until it does, a view naming either is refused as naming no component of the deployment. The data page also declares `deleted` and `batch-modified`, under the ceilings its other actions already use: counts of records written and not written, the names of at most five, and for a batch edit the attribute names it changed, never a value.

**No session event, no format change.** The outputs never reach the log or a model request: a bound value is resolved in the page for one render, as every output is. The new actions travel the content-component action path the command registry already records. `ComponentSpec` and `ComponentNode` are unchanged, and the extractor's data version stays where it is: a build without these two entries refuses a spec naming them, so no record an older build stored carries one.

## Alternatives considered

**Wire the three blocks through the page's ticked rows.** Rejected. Ticking is multi-select by default and serves the batch and export entrances; a tick says which rows, not which button, and cannot say "new record" at all.

**Give the form page its own add button, with modify driven by the bound row.** Rejected: it moves 新增 out of the page's toolbar, which is where the deployment's own console puts it and where a view's `toolbarButtons` arranges it.

**Carry a counter in `editing`, so every press is news.** Rejected: an output would then be an event, the one exception the definition of an output would have to carry, and every press would hand the form a new value even where nothing changed. Without it, pressing modify on the same row again hands the form nothing new.

**Refresh the page after a save through a binding from the form page.** Rejected: it makes the data page bindable, which takes down the read-back reason its properties refuse a binding for and the one-way argument with it, and would close a chain between the two blocks.

**Keep the forms inside the data page and split out only the card.** Rejected: the layout a view writes could not then put the form beside the table.

**Judge binding-only in the shared pass, with the seat passing the set of properties it substituted.** Rejected: it changes the seat's judgement for a gain only against a forged session log, and whoever can forge the log can already change the host. Placement keeps every call away from these properties, and a catalog test keeps a call-placed component from declaring one.

**Leave the two outputs in the description.** Rejected: a model would be offered values it can bind into nothing it may place — the binding the catalog would offer and then refuse.

## Consequences

**Bought.** A view can lay a writable table, its form and its card side by side, wired by two declared bindings, and every way a model's call could put a form on screen is closed in the operation that would have done it. The description a model reads is unchanged, so no request prefix moves. A view whose pieces disagree fails at load, at the path that has to change.

**Paid.** Three declaration fields that every reader of the catalog has to respect, one of them (`bindsFrom`) judged in a different pass from the rest of a property. Two entries that exist in the catalog before anything draws them, so a deployment cannot use them until the component row registers them with their renderers. And a publisher obligation — when to withdraw each output — that this package declares and cannot check, recorded above as the assumption to verify where the renderer is written.

## Testing

`npx vitest run packages/experimental/component-surface --maxWorkers=2` runs 31 files and 920 tests. They cover the predicate and the placement refusal on both of the tool's paths with and without the data page offered; the extractor drawing a view-placed spec from `content-component/shown` only; the description unchanged with and without the two blocks under every offer; the output declarations held to the properties that accept them, the cross-bound outputs refused, and a block a call places finding neither output, named or misspelt; every view rule accepted in the three-block view and refused at its path; withdrawal and same-value republishing in the seat; and the notices of the four new block actions and the two new data page actions with their ceilings. `tests/self-contained-copy.client.spec.ts` holds every sentence the package writes, the two new blocks' purposes and reasons included, to naming no tool but `show_component`. `npx vitest run packages/experimental/component-kit --maxWorkers=2` (247 passed, 2 skipped) and `npx vitest run packages/experimental/skill-pack-components --maxWorkers=2` (16 passed) run unchanged.
