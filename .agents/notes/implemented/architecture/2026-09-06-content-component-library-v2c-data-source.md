# Agent Note: reading the deployment's own data, with the visitor's own credential

Status: implemented

English | [中文](2026-09-06-content-component-library-v2c-data-source.zh.md)

## Problem

Every block the console has drawn so far was written by the model or by the deployment. A table of three sites is three rows a model typed out. That is the wrong shape for a service-line console: the rows a customer wants to see are in that deployment's own data backend, the console is already signed in to it as that customer, and a model retyping rows it was told about is both a waste of a turn and a fabrication risk.

Everything the read needs is already in the process and none of it is joined up.

- **The credential is held and spent in one place only.** `auth-gate` keeps the visitor's access token and puts it into the MCP forwarding routes. Nothing else can reach it, and nothing should be able to reach it as a bare string.
- **The tool has no way to say "fill this from over there".** `show_component`'s table property `displayValueList` is required with at least one row, so a call that means "read the rows" cannot be expressed at all.
- **There is nothing to replay from.** The content column folds an entry out of the `tool/call` the loop writes. Rows that were not in that call are nowhere in the log, so an entry built from them would vanish on the next fold.
- **Nobody has been asked.** Spending a person's credential to read that person's data is not something a model may decide alone.

## Decision

**A capability with three named reads, never a general `fetch`.** `ctx.bizBackend` offers `search(request, signal)`, `describe(meta, signal)` and `describeScheme(meta, signal)`, and can reach nothing else. The same URL prefix also carries `PUT /api/resources/{model}/{id}`, `DELETE /api/resources/{model}/{id}` and `POST /api/batchresources/delete/{model}`; a `fetch(path, init)` service would hand every plugin sharing this process the visitor's credential and those endpoints with it, and this fork's own audit found that third-party plugins declare no approval gate by default. The model name is checked to be one bare path segment before it reaches a URL, so a name holding `/` or `..` cannot steer a credentialed request at a neighbouring endpoint.

**The base URL is configured on the package that holds the token.** `bizUpstream` is `auth-gate`'s field, not `component-surface`'s. It is the only shape in which the type system can say "this credential goes to this origin and no other": the consumer names a table, never an address. It has no default — left out, no service is registered at all, and a row consuming it stays pending with the missing service named. The value must carry the deployment's API prefix, because that prefix is the frontend's own `VUE_APP_BASE_URL` and differs per install; a standard install publishes `/ini-server/` and an install built without one publishes at the origin root. The join is the deployment client's own `combineURLs`, not `new URL(relative, base)`, which would drop that prefix outright and land every request at the server root.

**The Service Definition lives in a Host-only package of its own.** `dsh-experimental-biz-backend` holds `ctx.bizBackend`, its provider and its failure union; `auth-gate` constructs it with the base it validated and the token it holds, and `component-surface` consumes it. The split is forced, and the force is worth recording: the Typert analyzer selects a package into the Host face as soon as a file reachable from that package's Host exports declares a Cordis surface, and it then takes that package's whole tsconfig file list as Host program roots. `auth-gate` is a Client-aggregate package with a `src/client` half, so declaring `Context.bizBackend` in its `src/index.ts` drags `src/client` — and through it `@deepseek-ai/dsh-client-runtime/client` — into the Host program beside `packages/core/agent`, where both declare the `agent` Typert context key; the catalog generators then stop with `duplicate TypertContextMap key agent`. `component-surface` sits in exactly the same position. A Host-only package has no client half to drag in, so the service is analyzed, published in the generated Cordis catalog on `docs/subsystems/biz-backend.md`, and the credential still never leaves `auth-gate`'s closure.

**Both headers carry `Bearer <token>`.** The deployment's page stores `"Bearer <jwt>"` and puts the stored value into `Authorization` and `CertificationToken` verbatim, while the gate holds the bare JWT — the browser half strips the scheme once, where a stored value enters — so the scheme is added back here and the bytes on the wire match the page's. `CertificationToken` is how this backend reads the token, not a second credential.

**Failures are values in a closed union, and no member carries the credential.** `unauthenticated`, `refused`, `rejected`, `unreachable`. A consumer switches on the tag and ends in `assertNever`. Whatever free text the backend sends back has the presented credential removed by name and is then cut to length — bounding alone would not keep the promise, since a backend saying the token inside its first hundred characters would pass.

**`dataSource` is a top-level parameter of the call, not a property of the block.** `displayValueList` is `required: true` with `minItems: 1`, and `PropsSchema.required` is a per-field boolean that cannot express "required unless another parameter is present". The catalog those properties live in is also shared with the browser seat, which must not carry host-only fields. As a top-level parameter the catalog, the seat and the existing judgement pass are all untouched, and what is put in front of them after the rows arrive is an ordinary spec.

**The order is: judge the whole call, check a credential is held, ask, describe, read, judge again.** Everything judgeable without spending anything is judged first, and that is the whole call rather than the data source alone: the `validateComponentCall` a hand-written call gets runs over a copy carrying one stand-in row per table to be filled, so a title too long, a thirteenth block, a component this deployment does not have and a thirty-first column are refused before anybody is asked about them. A block a data source fills may send neither `displayValueList` nor `rawValueList`: the stored list is what a reported gesture is answered from, so a call writing it would put its own values behind rows the card said were read. Whether a credential is held at all is then read off the gate, which spends nothing and reaches nothing — a person is not asked to allow a read this process could not have performed. Then the user is asked, once per call — `allowed-once` is the approval service's only grant, so a per-call question is what the seam already gives. Then the table's dictionary is read and every attribute the read names is checked against it — each column, each filter key, and the attribute sorted by — which is also where a column the call left a header off gets one. A filter naming an attribute the table does not have is otherwise the backend's to interpret, and a backend that ignores it answers a read the user allowed as a narrowed one with everything up to the page size. A block that named no columns at all has them settled between describe and read, out of the query scheme [the default-columns note](../feature/2026-09-07-data-source-default-columns.md) adds. Then the rows, one table after another. Then the filled spec goes through that same pass again, for what only the rows can decide: how many arrived, and how many bytes the filled call is. The dictionary is read after the question rather than before it because reading it spends the credential, and the credential is not spent before the question.

**The approval card prints no identifier the deployment does not otherwise show a person.** The table's name in the card's own sentence is the one the model wrote; the backend's name for it is on a line of its own beneath the prose, drawn at the same size as the prose. A column is named by the header the call wrote for it and counted otherwise, and a filter is named by header and strategy where every filtered column has a header and counted otherwise — because the only other name available before the dictionary is read is the attribute the backend keys the column by, which is an identifier. Filter values never appear at all: a condition can carry another person's identifier. The last sentence is fixed and never truncated: 您在表里勾选的行，会作为您的选择告诉小助手 — a ticked row does leave the panel and reach the model, so a card promising otherwise would promise something this path does not do.

**A read keeps only the columns it takes.** The backend answers with the attributes it chose rather than the ones the request named — the deployment's client puts its own `int_id` in front of every `source`, and the backend answers with it whether or not it was asked for — so both row lists are held to the columns the read takes — the ones the block declared, or the ones its default scheme settled — before anything is drawn or recorded. Without that the card's 只取 N 列 is a promise the panel and the session log both break, and the extra column is an identifier this deployment shows nobody.

**Nothing the model writes can draw a line of the card.** `metaLabel` and every column header must be one plain line — no line break, no other control or format character, no Unicode line or paragraph separator, no `「」` — and a header is held to the same forty characters the drawn call is held to, so one too long to draw is refused before the question rather than after the credential has been spent. Each table's description is then cut to its share of a three-hundred-character prose budget **before** that table's 数据表 line and the closing promise are appended, so neither can be pushed off the card. Without both rules a call could write its own 数据表 line inside the label, or pad a header until the real one fell off the end, and the card's one checkable fact would become another thing the model said.

**A successful read appends `content-component/resolved` carrying the whole filled spec.** The column's reader is per-event, synchronous and pure: it cannot join a base spec in one record to rows in another, and the later record for an entry id replaces the earlier one outright. Recording rather than replaying is the further point — replaying would mean reading a person's data again at a moment nobody asked for it, possibly to a different answer.

**Nothing is appended when anything fails.** The top-level-parameter design removed the "read in progress" state before it could exist: a reading call's own `tool/call` names blocks with no rows in them, fails the extractor's judgement, and produces no entry. What the user sees during the wait is the approval card itself. So a failure is one sentence to the model and a column that did not move.

**HTTP 401, or a failing status carrying result code 2 or 3, gives the token up; the same code on an HTTP 200 does not, and neither does an HTTP 403 on its own.** The deployment's own client drops its stored token on those two codes from its error interceptor only — its success interceptor reports a non-zero code on an HTTP 200 and keeps the token — and beside that switch it drops on HTTP 401 alone. A 403 reaches only its `拒绝访问` message, with the stored token untouched, so a 403 here is classified from its envelope like any other failing status. Following it exactly is what keeps an ordinary business refusal, and a single endpoint this visitor may not reach, from dropping a live credential and with it every MCP forward in the process.

## Alternatives considered

**A general `authGateFetch(path, init)`.** Rejected on the endpoint table above: the audit surface goes from two reads to the whole base URL, including deletes, for every plugin in the process.

**Declaring `ctx.bizBackend` on `auth-gate` itself, where the credential is.** Rejected by the Typert analyzer, not by taste: it turns the Host program into one that sees both the Host and the Client `agent` context declaration and refuses to build. Splitting `auth-gate`'s compiler faces would also have worked and was rejected too — `docs/development.md` allows that shape only for `api/remotes` and says in as many words not to copy it.

**Putting the data backend into `mcpUpstreams`.** Rejected twice over. Each entry claims a `/auth-gate/mcp/<name>` route that only fences cross-site requests, so any same-origin page — including a business iframe in the content column — could reach the backend as the signed-in visitor without presenting a token of its own. And that path is a byte pipe: it cannot read the envelope's `code`, so it would deliver a refusal as data.

**Truncating an over-large result.** Rejected. A table silently missing its tail is a table the user reads as complete. The refusal names the row count and the byte count and tells the model to ask for fewer.

**A service account for sessions with no signed-in credential.** Rejected. A fallback account would be reached for in production the day it exists, and it would make the card's first three characters — 用您的账号 — untrue for whoever that account turned out to be. A session with no credential is refused and the visitor signs in.

**Reading the table's dictionary before asking, so the card could carry the backend's own name for the table and its columns.** Rejected: reading it spends the credential, and the credential is not spent before the question. The cost is recorded — the table's name on the card is the model's word for it, and a column the call gave no header is counted rather than named.

**A `failure` member on the recorded event, so a failed read could say so on the panel.** Rejected: the top-level-parameter design means a reading call produces no entry until the rows are in, so there is no in-progress entry for a failure to settle. This reverses the research draft, which assumed the entry existed from the moment of the call.

**Dropping the credential on result code 3 whatever the HTTP status.** Rejected after reading the deployment client's two interceptors: only its error path drops on that code. Guessing otherwise would give up a live credential — and every MCP forward with it — on an ordinary business refusal.

## Consequences

**Bought.** A model can put this deployment's own current data in front of the person who owns it, having asked that person first, without any row passing through a model request. A read is at most three named operations and cannot become anything else. The seat, the catalog and the component library are untouched.

**Paid.** A filled spec of up to 65536 bytes rides every checkpoint the content surface writes, per live entry. `content-component/resolved` is a session event every build of this repository must know. A read the backend refuses stops MCP forwarding for the whole process, because the token is process-wide. And the reading path is one more thing that only works where the visitor is signed in.

## Known Limitations and Deferred Work

- **Row-level trimming is the backend's, and this change cannot prove it happens.** The deployment's own frontend has a row and column permission pass that returns early and opens the data up when it finds no signed-in profile, so it is not a boundary. If the backend does not trim rows against the token it was handed, one read can draw rows a person was not meant to see onto that person's screen and write them into that person's session log — and signing out does not clean a log already written. Closing it needs an answer from whoever owns that backend. **This path should not be opened to real users before that answer exists.**
- **Nothing here has run against the real deployment.** Every backend in this change is a fake that answers the shapes a 2026-09-05 capture recorded. The first real read is where a difference between that capture and the live system would show up.
- **A read the backend refuses stops MCP forwarding as well.** HTTP 401, or a failing status carrying code 2 or 3, makes the process give up the token — the sign-out route's terminal state — so every forwarding route answers 503 until some browser posts a new one. One read's failure is process-wide.
- **The process then knows something the page does not.** The node half is the first place to learn the token was refused and has no channel for telling the browser, which runs on until its own expiry schedule fires. The cheapest close is the token route answering 409 once a credential was dropped as refused, which is also the first reader `HeldCredential.drop`'s `reason` would have.
- **A `code 3` on an HTTP 200 is a rejection, not a refusal.** A backend reporting an expired token that way keeps being presented it until the browser's expiry schedule intervenes.
- **`Bearer ` is added back**, on the premise that the deployment's login page stores it. A deployment storing a bare JWT receives one scheme more than its own page sends.
- **Every row in the composition can call `ctx.bizBackend`.** The narrowness of the three methods is the whole boundary; who may call them is the composition's decision. The token itself stays in a closure and is published as no service.
- **The table's name on the card is the model's word for it**, and a column the call gave no header is counted rather than named — both consequences of reading the dictionary after the question. The 数据表 line beneath it cannot be forged or pushed off the card, so a person who reads it can notice a mismatch; a plausible wrong label on a person who does not read it still passes.
- **The card says the page size, never the page number.** `page` carries a `currentPage` since [the default-columns note](../feature/2026-09-07-data-source-default-columns.md), while the card describes every read in the words a first-page read gets.
- **A configured view cannot read its own rows.** `dataSource` is a parameter of a call, so a deployment's own home view carries only rows a person typed into `cordis.yml`. Giving a view its own read means asking the user at click time, since a configured view has no model turn to hang the question on. Next slice.
- **A read that fails leaves the previous table on screen with nothing saying it is stale.**
- **This row asks for fewer columns than the deployment's own page does** — the component library sends every column of a scheme, hidden ones included; a call here sends the columns it declared, or, since [the default-columns note](../feature/2026-09-07-data-source-default-columns.md), the shown columns of that scheme. A deliberate narrowing, recorded so it is not later "fixed".
- **The per-model address overrides the deployment's frontend keeps are not reproduced.** A model configured that way is read at the default address. The trigger is the first read whose rows disagree with the page.
- **Rows in the log are checkpoint weight** — a filled spec of up to 65536 bytes, once per live entry, in every checkpoint the content surface writes.
- **`content-component/resolved` is required on read**, like this package's other event and for the same reason: `Session.append` gives an appending plugin no way to set the envelope's `ignorable` marker.
