# Agent Note: The skill-pack row installs and judges an organization's skill packs through an intake

Status: implemented

English | [中文](2026-10-05-skill-pack-organization-intake.zh.md)

## Problem

The organization plugin, which lives outside this repository, delivers an organization's signed skills to a console and is their skill provider: it chooses which version of each skill a member is offered — the stable one or a trial one — reports that version to `ctx.skills`, and counts its use. Some of those skills are skill packs. Their views place component parts, they name plugins and a platform range, and a pack exported with element anchors states which anchor-file format it is written in. Such a skill may be offered only where its parts are registered, its views can be drawn and its anchor format can be read, and every one of those answers lives in this repository: the component catalog, the view judgement and the pack rules belong to the skill-pack row and the component surface beside it. The organization plugin cannot ask them, and it cannot hand the packs to the pack root either: `syncPackRoot` replaces a pack root wholesale, so a delivery and an organization would erase each other's packs, and the pack root's provider would report the skills a second time. Separately, the strict manifest refused `metadata.pack.anchorFormat`, so every pack the anchor exporter writes was withheld as `manifest-invalid`.

## Decision

**The skill-pack row provides `ctx.skillPackIntake` where `organizationRoot` is configured.** `replace(packs, { signal })` installs an organization's packs, `isActive(name, version)` answers synchronously whether one entry may be offered now, and `onChange(listener)` reports a change in that answer. The organization plugin stays the only skill provider of these skills and asks `isActive` which versions it may report; the row installs them, judges them, and hands the active entries' views to `ctx.skillPacks.activeViews()`, from where [`skill-pack-components`](../../../../packages/experimental/skill-pack-components/README.md) places them as it places a pack of the root. Without `organizationRoot` the key is not provided, and the organization plugin offers none of these skills.

**The organization root is a directory of its own, and nothing in it is reported to `ctx.skills`.** Each entry is installed under `<organizationRoot>/<name>@<version>`, where `version` is the organization manifest entry's version, so a stable and a trial version of one skill sit side by side; it is not compared with `metadata.pack.version`, which is shown and traced only. The root is this package's layout and enters no model-visible path: the organization plugin points each skill's `resourceBase` at its own skill cache. `organizationRoot` is refused at load when it is relative, and any two of `root`, `deliveries.directory` and `organizationRoot` are refused when they are one directory or one lies inside the other, because replacing one would write into the other; they are compared as the file system reads them, every symbolic link followed and, on macOS and Windows, letter case and Unicode normalization folded, and a directory reached through a symbolic link whose target does not exist is refused at load, because where it would be created cannot be compared. Only `replace` writes it, so it is not watched.

**Entries are judged one by one and written together.** Each entry is read from its files in memory through `observePack`, the reader the pack root is read with, which keeps a byte-order mark exactly as `readFile(path, 'utf8')` does, and is held to the pack rules, its frontmatter name, a directory-safe version, its manifest, its anchor and view formats, readable views and the composed surface's judgement of them. An entry breaking one is refused with a code from the open `IntakeRefusalCode` list and an English `detail` for an operator; every occurrence of a repeated `name@version` is refused, because nothing says which is meant. Two keys that differ only in letter case name one directory on macOS and Windows, and two that differ only in Unicode normalization name one on macOS; both count as one repeated key on every platform, so that one rule holds wherever the set is written. Keys and paths are compared after Unicode NFC, lower case, upper case, lower case again and NFC again, a fold wider than any one file system's that also makes one key of a few pairs a file system keeps apart, such as `ı` and `I`; two paths of one entry that fold to one refuse it as `pack-invalid`, as `validatePacks` refuses them in a delivery. The accepted entries go to `syncPackRoot` together, so the root holds all of them or none, and a set already on disk byte for byte is not written again. `replace([])` withdraws the set and empties the root. `IntakeResult` is closed: `ok` with the refusals, or `failed`.

**The offered set is held by the calling fiber.** Cordis hands every reader of a service a proxy bound to the context it was read from, and a Service method sees that context as `this.ctx`, so the fiber of the context the caller read the intake from — an `inject` callback's own fiber included — holds the set while it is loading or loaded. When that fiber stops the set is withdrawn and its files stay; a later `replace` of the same files writes nothing. A caller that stops before its write answers `failed`, and a call whose caller or row stops during its write answers `failed` with the root already holding the set. Calls run in arrival order, and when one answers `ok`, `isActive` already answers from the new set and every `onChange` listener has been called after it. Nothing is offered between a start and the first `replace`.

**An organization pack keeps a view id against the pack root.** A view id an active organization entry declares withholds a pack of the root declaring it, with `view-id-conflict` naming the organization pack under `origin: 'organization'`; the rule that withholds both of two root packs claiming one id, from [the reconciler note](2026-09-18-skill-pack-reconciler.md), holds inside the pack root only. Inside the organization set, a view id declared with files of identical bytes is one view; with different bytes, an id already held keeps its bytes and every entry changing them is refused, and an id nothing holds is refused to every entry declaring it. Neither rule reads the order the entries come in. While a set is offered, that set holds the ids; while none is — after a start, or once the fiber holding the last set stopped — the entries the last write left in the organization root do. Only a `replace` whose entries passed these rules writes that root, and a call whose caller or row stops while its set is written leaves there a set that was never offered, which later calls are judged against while no set is offered.

**The anchor formats a build reads are a constant.** The manifest reads `metadata.pack.anchorFormat` as an optional integer. `PACK_ANCHOR_FORMATS` is `[1]`, the list point-anchor's `ANCHOR_FORMATS_READ` holds, and a pack stating another number is withheld with `anchor-format`, or refused as `pack-anchor-format` in a delivery. The list is only ever added to: dropping a number is a breaking change for every pack that states it, and needs its own decision and upgrade guide. The requirement is not deferred, because nothing arriving later changes which formats a build reads.

**The status route lists the organization set and answers per member.** Each `PackStatus` carries `origin`; an organization entry also carries `entryVersion` and `channel`, and `version` stays `metadata.pack.version`. No trial identifier is published. With `perMember`, the route answers only a request `ctx.consoleMembers` places with a member — 503 without the service, 401 for nobody — and every placed member reads the same document.

## Alternatives considered

**Install organization packs into the pack root.** `syncPackRoot` replaces the root wholesale, so a delivery and an organization would erase each other's packs, and the pack root's provider would report every organization skill a second time beside the organization plugin's own entry.

**Make this row a second provider of organization skills.** The organization plugin chooses a version per member and ranks duplicate names; a second provider would list the same skill twice and make that choice twice.

**Offer the set read from disk at start.** The set would stay offered after the organization plugin was disabled, reloaded or failed, so its views would stay in the sidebar with nothing behind them. Holding the set on the caller's fiber withdraws it with the plugin, and an unchanged set costs no rewrite on the next `replace`.

**Reuse the pack root's judgement over the whole set.** It indexes active packs by skill name, so a stable and a trial version of one skill would overwrite each other, and its contested-id rule treats one name as one claimant.

**Refuse the later of two entries claiming one view id.** The answer would depend on the order the organization plugin lists its entries. Keeping what is held, and refusing every claimant where nothing holds the id, does not.

**Judge view ids against the offered set alone.** After a reload or a restart nothing is offered, so a set whose trial version changes a view its stable version holds would have both versions refused, and the stable version removed from the organization root, although the same set kept the stable version a moment before. The entries on disk are the set the last write judged, so a set handed over again is judged against what that write kept.

**Withhold both an organization pack and a pack of the root that claim one id.** The same export delivered both ways would withhold the version the deployment chose. The organization set is that choice, so it keeps the id.

**Make the readable anchor formats a Config field.** A deployment could then claim to read a format its build cannot, and a pack would be offered with anchors nothing reads correctly.

**Filter trial entries per member in this row.** It has no trial list, and the view index has no per-member views; filtering belongs to the organization plugin, and per-member views wait on the view index.

## Consequences

A console can take an organization's packs with views, requirements and anchors on the same terms as its own pack root: what cannot be drawn is not offered, what waits for a part activates without a restart, and the status route says which is which. The organization plugin decides who sees which version, and this row only answers whether that version can be offered at all.

The cost is a set held in memory by another plugin's fiber: between a start and the first `replace`, and while the organization plugin reloads, the organization's views are absent. A trial version's views are offered to the whole process, accepted because a trial manages roll-out rather than secrecy. Two rules about view ids coexist — root packs withhold each other, an organization pack wins — and the status route carries `origin` so a reader can tell which applied. Dropping an anchor format number is a breaking change by policy, so the constant can only grow.
