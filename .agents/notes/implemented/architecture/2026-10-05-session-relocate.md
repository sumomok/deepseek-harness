# Agent Note: A stored session moves to another cwd by rewriting its current header record

Status: implemented

English | [中文](2026-10-05-session-relocate.zh.md)

## Problem

Moving a workspace folder must keep its sessions: same id, same events, new cwd. The persistence seam offered `create`, `open`, `flush`, `stat`, and `list`, and the cwd lived in the immutable header. The JSONL backend stores each session in `sessionDir(root, cwd, id)`, so a new cwd means a new directory, and every reader checks that the highest generation's header cwd names the directory it sits in ([`assertStoredIdentity`](../../../../packages/session/session-persistence-jsonl/src/index.ts)). A plugin cannot move a session safely from outside: while the same id has canonical generations in two project directories, `findLog` and `listArtifacts` throw a plain `Error`, so `list()` fails for the whole root, and the workspace registry's startup `list()` keeps the Host from starting. A header whose cwd names another directory fails the same way.

## Decision

`SessionPersistence` gains an optional `relocate(id, cwd, options)` and the `@mode emit` event `session-persistence/relocated(id, previous, current)`. Callers test `typeof ctx.sessionPersistence.relocate === 'function'`. The method moves the session to the storage location of `cwd` and replaces the header cwd; id, `createdAt`, lineage, `isSeeded`, the inherited cut, events, and seqs stay unchanged. A stored cwd that already equals `cwd` (exact string comparison) changes nothing and emits nothing, so a caller that crashed repeats the call. A write handle in any process or a pending create refuses the move with `SessionAlreadyOwnedError`. Read handles stay open: while the session is absent between its two locations, an `open` or a handle read that consults storage rejects with `SessionPersistenceNotFoundError`, and an `open` or read that located the source just before it was hidden rejects with the filesystem's `ENOENT` error, as in builds without the patch when a log vanishes. The event fires once per successful move after the backend releases ownership, inside a `try`, because Cordis `emit` runs listeners synchronously and does not catch: a listener that throws stops the dispatch, the listeners after it miss the event, and the move still succeeds with a warning. No recovery emits it.

The JSONL backend rewrites only the current generation's header record. When the highest generation is historical, it first publishes the current successor through the same path a write open uses ([released-format migrations](2026-08-31-released-session-format-migrations.md) allow adding a version-named successor), then rewrites that successor. Prior generations move unchanged: a rename within one filesystem keeps their bytes and inodes. The only deleted bytes are the source copy of the current generation; its event records remain byte-identical in the target, except complete records recovered from a torn tail, which the move re-encodes exactly as the write path's first append would.

This is not a format migration: the format version, the header fields, the envelope, and `SessionEventMap` are unchanged. A moved session is the standard layout with a standard header, identical to a session created under the new cwd, so any runtime of the same format version reads it, including builds without this patch. The new cwd reaches the model through the system prompt, which is logged as `system/message`, and the header record in the log holds it as well.

## Disk protocol

Notation: `C` is the current-generation filename of the configured encoding, `P` the retained prior generations, `T` a staged copy named `<C>.relocate-<token>.tmp`, and `H(x)` the hidden name `<x>.relocating-<token>`. Neither suffix is canonical for either encoding, so discovery, the encoding check, and `scripts/migrate-sessions-to-v4.ts` ignore them. Three invariants hold at every instant, for every process, as long as no other writer stores a second session with the same id (see Consequences): at most one directory under the root holds canonical generations of the id (V1); in that directory the highest generation's header cwd names the directory (V2); once the target `C` exists, the source holds no canonical generation (V3). The only transition state is "neither directory holds one", from hiding the source to publishing the target, and it reads as absence: `stat` returns `undefined`, `list` omits the session, and `open` rejects with `SessionPersistenceNotFoundError`. A live move leaves that state after a few filesystem operations; a move that dies inside it leaves the session absent until a backend recovers its intent.

The backend takes the in-process write claim, the source directory's lock, re-resolves the session (see below), and publishes a historical successor when needed. It creates the target project and session directories durably, takes the target's lock, and refuses a target holding any canonical generation and a source and target on different filesystems (`stat().dev`) before writing the intent; a refusal removes the target session directory it created, while a target project directory it created stays. Then the runtime ([`relocation.ts`](../../../../packages/session/session-persistence-jsonl/src/relocation.ts)) runs: remove intent temporaries of this id that a process left when it died before publishing its intent; write the intent `root/.relocate.<sha256(id)>.json` without replacing an existing one (`link` on POSIX, `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING` on Windows), which records the committed length of the source `C` (its whole length unless its tail is torn); write `T` in the target as the new header record followed by the source's committed bytes after the old header and any records recovered from a torn tail, fsync, and verify it in a Worker Thread against the id, event count, and written digest; rename each `P` to the target as `H(P)`; rename the source `C` to `H(C)`; search every other project directory for a canonical generation of the id and stop when one exists; publish `T` as the target `C` without replacement (`link` on POSIX, `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING` on Windows) — the commit point; restore each `H(P)` to `P`; remove `T`, `H(C)`, the source lock file, and the source directory (a directory holding unrecognized files stays and is reported); delete the intent; release both locks and the claim; emit. Every cross-directory operation precedes the commit point, so a cross-device failure can still roll back.

When the target cwd's normalized project directory is the source's (`projectKey` is lossy: `/a/b` and `/a-b` share `--a-b--`), or the target spelling names the same physical directory (a case alias or a symlinked project directory, detected by `dev`/`ino`), the move rewrites in place: write the intent, stage `T` beside `C`, and replace `C` atomically (`rename` on POSIX, `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH` on Windows); prior generations stay. Renaming `C` away first would let a prior generation become the highest for a moment, and open read handles would report a shrunken log. An in-place intent names the source and target spellings; recovery rejects it when both exist as two physical directories and settles it when either spelling names no directory any more, because settling removes only the stage beside the source `C` and the intent. A cross-directory intent whose two spellings name one physical directory is rejected: its two locks would be one lock file, which the recovering process would contend with itself.

## Recovery

Startup recovery and in-call failures share one decision, made from disk facts alone: does the target `C` exist? If not, the move rolls back: `H(C)` returns to the source `C`, each `H(P)` returns to the source without replacing a file (an identical file counts as restored), `T` is removed, a target directory holding only its lock file is removed, and the intent is deleted. Restoring `C` before the priors keeps a historical generation from becoming the highest mid-rollback. A rollback that would make an empty source visible again first searches every other project directory for a canonical generation of the id, as the publish step does. If the target `C` exists and continues the moved log, the move completes from the prior-name restoration onward and never touches the target `C`, which another process may already have opened and appended to. A log only grows by appending and the move rewrites only the header record, so a continuing target `C` begins with `T` while `T` exists, and otherwise its header record matches that of `H(C)` in every field but cwd and its bytes after the header begin with the committed bytes of `H(C)` (the length the intent records) after its header. Whether `T` exists cannot tell a committed move from a same-id session stored at the target while the source was hidden: Windows consumes `T` when publishing, and a POSIX crash between removing `T` and `H(C)` leaves the same files. Deciding by the published target instead of by the intent or a step field keeps events another process appended to the source `C` before the source was hidden. Storage that contradicts the intent — both directories holding canonical generations, a target `C` that does not continue the moved log, a target generation without `C`, the source `C` and `H(C)` both missing, a hidden file whose canonical name holds different bytes, or a canonical generation of the id in another project directory while the source is hidden — leaves every file and the intent in place.

The backend's first operation (the lazily memoized root check, which a Host first reaches through the workspace registry's `list()`) recovers every intent before checking the root encoding, taking the lock of each intent directory that exists; a held lock, an invalid intent, a contradiction, or an I/O failure leaves the intent and logs a warning, and nothing rejects the memoized check. Intent temporaries stay, because one may belong to a relocation still writing it in another process; only a relocation of the same id removes them, while it holds the lock of the directory the session occupies, which every relocation of that id must hold to write one. Every recovery holds the locks of the directories an intent names (a directory that no longer exists needs none) and reads the intent again under them, acting only on an unchanged intent; the intent path is keyed by the id alone, so recovering from a stale read could delete another relocation's intent. A relocation of an id first takes the lock of the directory the session occupies and only then settles an intent left for the session, under that lock and the lock of the intent's other directory. Only a holder of that lock writes an intent for the session, so none appears before this relocation records its own; a relocation that died between this one's lookup and its lock is therefore settled, not overwritten, and an intent found at the path anyway refuses the move with `SessionPersistenceCorruptionError` naming it and stays. When locking fails because the session is absent or stored in two directories, the relocation settles a remaining intent under the locks of the directories it names and locks once more. Settling refuses with `SessionAlreadyOwnedError` while a directory is held or with `SessionPersistenceCorruptionError` naming the intent file; an intent another backend removes between being found and being read counts as settled. Inside a call, a failure before the commit point rolls back and rethrows (an `AggregateError` when the rollback also fails, keeping the intent); a failure after it completes the cleanup, and when the cleanup fails too the call still succeeds, emits, warns, and keeps the intent for the next recovery. Cancellation is observed only before the commit point.

## Lock re-resolution

A POSIX lock names an inode, not a path, so removing a live session's lock file forfeits exclusion. Relocation removes the source lock file it holds after the target is published. A writer that resolved the source before that could then recreate the directory through the lease's `mkdir`, lock a fresh file there, and read the session from the target — two writers. Every write open therefore resolves the session again after locking; when the session no longer lives in the locked directory, the open removes the directory it recreated while still holding its lock, releases, and retries once. A second mismatch rejects with `SessionAlreadyOwnedError`, or `SessionPersistenceNotFoundError` when the session vanished.

## Consumers

The workspace registry follows the event at runtime. Before any await, its listener replaces the session's indexed header and drops its indexed path, so the old workspace stops listing the session and an `attachSession` right after `relocate` validates against the new cwd. Its mutation queue then durably detaches the session from every workspace whose record lists it at another path: the `workspace/follow` baseline filters by indexed path, but its delta frames send the unfiltered stored `sessionIds`, and the registry bootstraps its index only once, so an in-memory change alone would keep the old workspace listing the session. When a workspace exists at the new canonical cwd, the queue attaches the session to it, so a move needs no restart. The event can still miss the registry: the registry is not running, recovery finishes the move, or a listener ahead of it throws. At its next start the registry therefore durably detaches every session whose canonical cwd is an existing directory other than the path of the workspace record listing it, for records whose stored path resolved at that start, and `attachSession` first detaches a validated session from every other workspace that lists it. Filtering alone would let the caller's attach account the session in two workspaces, which the next start rejects as an inconsistent domain. Callers still attach idempotently because recovery emits no event.

The projection cache keys each record by the session's lifecycle identity, which includes the cwd. Without re-keying, every moved session misses the cache, and the session list's cold rows, whose titles come from the cache, show no title until each session is opened once. The cache's listener therefore rewrites the cwd of a record whose `createdAt`, `cwd`, and `isSeeded` match the header before the move, at the current or a predecessor format generation, and keeps its rows, because a move changes no event.

## Alternatives considered

**A side record of the new cwd instead of rewriting the header.** Moving the directory and recording the new cwd beside the log leaves a header whose cwd names another directory; a build without the patch (upstream after this patch retires, or a downgrade) fails `assertStoredIdentity` with a plain `Error`, which `listArtifacts` does not catch, so `list()` fails for the whole root (the JSONL spec pins this as "list rejects a header whose cwd does not identify its physical log"). Leaving the directory in place silently restores the old cwd on such a build. Either form makes an older runtime read the log incorrectly, which the format-version rule in [`types.ts`](../../../../packages/core/session/src/types.ts) answers with a `SESSION_FORMAT_VERSION` bump the fork cannot claim. It also spreads into `decodeStoredLog`, the historical identity check, migration publication, and every revision call site.

**Write the new location first, then delete the old one.** Between the two steps both project directories hold canonical generations of the id, and every process — including builds without the patch and this process before recovery — fails `findLog` and `list()` for the whole root. Retiring the source before publishing the target replaces that window with a span of absence, which every reader already handles.

**An intent directory outside the root, chosen by configuration.** The backend does not know `DSH_HOME`, a rename across filesystems is not atomic, and a deployment-varying path would need a validated `Config` field for what is internal layout. Plain files directly under the root are never scanned: discovery lists only directories, and the migration script skips names without a log suffix.

**A `step` field in the intent.** Recovery that trusts a recorded step either rolls back after another process appended to a published target or completes over a source a writer reopened. Deciding by whether the target `C` exists has neither failure.

**Keeping the source copy of `C` under a non-canonical name.** No committed byte would be deleted, at the cost of twice the space per move and a separate cleanup mechanism; the target holds every event record byte-identically, so the copy is removed.

## Consequences

Retained prior generations keep their old header cwd. They are never read while `C` exists, and released predecessors promise neither fallback nor downgrade support; deleting `C` by hand selects a prior generation whose header names another directory, and `list()` then fails for the root. A move needs twice the session's space while `T` exists. Every move changes the current generation's inode, so its revision changes; `historicalCorpusRevision` hashes paths, so a move also changes every historical session's revision once, causing one round of re-observation, and a `list()` inside the absence window reports the session as removed until the next listing. A move of a subagent child invalidates a historical parent's memoized preparation: the parent's next read open retries automatically and its next write open rejects once with `JsonlGenerationSourceChangedError`.

A move that dies between hiding the source and publishing the target leaves the session absent in every process that already ran its recovery, until that process restarts or relocates the id. Session Controller's `createOrAdopt` creates a new session with the same id when the session query reports the stored one missing, and the agent loop's `restoreOrCreateConfigured` falls back to `create` on `SessionPersistenceNotFoundError`; either can store a second session with that id while the first is absent. The publish step and every rollback that would make the hidden source visible search the other project directories first; on a hit the move stops, the intent and hidden files stay, a warning names the intent, and relocating the id rejects with `SessionPersistenceCorruptionError` naming the intent, the same handling as both directories holding the session; recovery stops the same way for a same-id session stored at the target or at the source. The [package README](../../../../packages/session/session-persistence-jsonl/README.md#relocating-a-session) names the files that keep the original session and how to restore it by hand. The search narrows but cannot close the race: `create` checks the id when called and stores at its first append, so a create that saw the session absent and first appends after the search still leaves the id in two directories, and `list()` fails for the root — the same class as two processes creating one id under different cwds.

The post-lock re-resolution excludes writers only among builds that have it. A build without the patch that write-opens the session while a relocation runs can resolve the source, recreate it through the lease's `mkdir` after the relocation removed it, lock the fresh lock file, and append to the session at the target while a patched writer holds the target's lock; both then append the same seq. Every process that writes a root on which relocations run must therefore run a build with this patch.

Session Controller never disposes a resumed Agent, and a resumed Agent holds its write handle until the Host exits, so a session the Host has followed or prompted refuses relocation with `SessionAlreadyOwnedError`; callers move sessions before any client opens them. Recovery emits no event, so a crash after the commit point loses `session-persistence/relocated`; consumers that track sessions by cwd must attach idempotently after `relocate` returns, and the workspace registry repairs its membership at its next start. Until that start, after a listener ahead of the registry threw, the old workspace still lists the session and an attach at the new path is refused, because the registry's index keeps the header from before the move.

The crash matrix in [`relocation.spec.ts`](../../../../packages/session/session-persistence-jsonl/tests/relocation.spec.ts) stops the runtime after every step through an injected barrier, for both encodings and both namespace-operation platforms, asserts V1–V3 and the location of every non-canonical file at that instant, reads the root as the backend without this patch reads it (highest canonical generation by name, header identity, current-format event decoding) and requires the original events, then recovers with that platform's namespace operations and checks the result through a fresh backend; the same spec stores a same-id session in a backend that recovered before the crash and asserts that recovery leaves the move unsettled with V1 and V2 intact. [`relocation.two-process.e2e.ts`](../../../../packages/session/session-persistence-jsonl/tests/relocation.two-process.e2e.ts) recovers intents left on both sides of the commit point through the built backend in a plain-Node child and pins the refusal while another process holds the session.

This is a core patch registered in [`.claude/core-patches.md`](../../../../.claude/core-patches.md) as `session-relocate`. It retires when upstream `SessionPersistence` itself offers a way to move a session or change its cwd.
