# Agent Note: the return channel — what a user does inside a block reaches the agent

Status: implemented

English | [中文](2026-09-04-content-component-library-v0.5-return-channel.zh.md)

## Problem

The [first slice](2026-09-04-content-component-library-v0.md) put a block of interface in the content column and told the model, in as many words, that what the user does with it does not come back. That sentence is what made the block worth less than the conversation beside it: the agent could place a confirmation bar and then had to ask the same question again in chat, because a press reached nothing.

Carrying a press back is not one decision but six, and most of them are the sort a plugin gets wrong quietly.

- **A press is model-visible input, so it has to be in the log first.** The repository's rule is that anything reaching a model request must be reconstructable from the session log. A channel that hands the agent a sentence nobody recorded is a session that cannot be replayed.
- **A press that always opens a turn is a loop.** A user drumming on a button would chain turns without bound, and the obvious guard — a budget — is a trap of its own: a budget with no refill spends itself once and then degrades every later press to silence, permanently, with nothing anywhere saying why.
- **The seat is a page, and a page can lie.** Whatever the browser sends arrives as text. If the notice the agent reads is assembled from that text, a compromised or merely buggy renderer can report a press of "Cancel" as a press of "Delete", and the agent will act on it.
- **The grade an action declares is not where the notice lands.** A `wake` degrades to the inbox on a busy agent and past the budget, so a channel that answers every press the same way tells some users the conversation has their answer while nothing will happen until they write again.
- **A block is unmounted whenever the user looks at something else.** The column keeps one seat per kind and hands it only the selected entry, so whatever a block remembers about itself is gone the moment another tab is picked — including whether it has already been answered.
- **A command's input is recorded before any handler runs.** `commands` writes `command/run` with the raw input verbatim at `index.ts:341-345`, and the handler is entered at `:389`. Any rule about what a payload may contain is therefore applied *after* the payload is durable.

## Decision

**The channel is a command, and it introduces no session event.** The seat runs `/component-action <json>`, whose whole input is one JSON object: `entryId`, `componentId`, `actionId`, `nodeId`, and a `payload` carrying the properties that action declares. `recordInput` stays at its default, so `command/run` carries the action document verbatim, log-only, and the notice the handler builds is logged as the `user/message` the loop writes when the agent claims it. Both directions of this package now replay from records the runtime already wrote, and `SESSION_FORMAT_VERSION` still does not move.

**Nothing the seat sends is displayed as written.** Every field but `payload` is an identifier resolved against the log: the entry must exist in the `contentSurface` fold, the node must be one that entry's spec draws, the component must be the one that node names, the action must be one that component declares, and the payload must pass that action's `payloadSchema`. The words the agent and the user then read — the entry's title, the component's label, the pressed button's name — are read back out of the catalog and out of the spec *the model itself wrote*. A press of a button the drawn bar does not carry resolves to nothing at all.

**The stored spec is re-judged, not trusted.** The record the handler reads is a fold cell a persisted checkpoint may have seeded, so its declared type is a claim; `validateComponentSpec` runs again over it, and that judgement is what gives the node the properties the notice is built from.

**Three grades, declared in the catalog, with no `Config` override.** `silent` is swallowed where it happens, `context` waits in the agent's inbox, `wake` opens a turn. The grade is a property of the action rather than of a deployment, because it says what the gesture *means* — a sort order is not news, a pressed confirmation is the answer the agent stopped for — and a deployment that moved it would be changing what the agent is told happened. `el.confirm-bar`'s `press` is `wake`. A `Config` override table over the grades is deliberately not built; the review trigger is that a customer needs a grade changed, which is then a catalog edit and a release, not a configuration field.

**The wake budget is three, and it is refilled by human input only.** `agent/inbox/claimed` deletes the agent's count when the claimed message's source is `user`, following `tool-jobs`. The refill and the spending site share one `WeakMap` keyed by the exact `Agent`. Past the budget, and on an agent already working, a `wake` degrades to `context` — which a running turn reads without a turn boundary of its own.

**The payload whitelist is the seat's obligation, and the host's enforcement is delivery, not admission.** Because `command/run.args` is durable before the handler runs, no host code can keep an over-full document out of the log. What the host still does is refuse to *deliver* it: past `MAX_ACTION_PAYLOAD_BYTES` (2048), or carrying a property its action does not declare, the action reaches the agent not at all. The browser half applies the same byte ceiling before the line exists, so an oversized document is normally never written. Both halves ship in this package, and the limitation is recorded in the README rather than papered over. The alternative — a Log-only session event of this row's own, where the handler could shape what is stored — is deferred to the slice that introduces a data source, when there will be a second reason for one.

**The gate stays where it already is.** This row places no write tool and requests no approval: a command handler can run with no turn open, and `approval.request()` throws there. The deployment's `tools/pre-execute` policy over whatever write tool the model reaches for *in the turn the press opened* is the gate, and the `wake` is what guarantees a turn is open when it is consulted.

**A press the host acts on leaves no row of its own in the chat; the two it cannot act on now are the exception.** `ui-conversation` draws an unregistered command with its `GenericCommandCard` fallback, which would head the row with the bare command name: `component-action · Completed`, in English, in front of someone who just pressed the button themselves. The command is dispatched for the durable record it writes, so this row registers its own chat view at that name — the empty-registration move `content-column` makes for `dismiss-content-entry` and `content-frame` for `show-content-page` — and the row it leaves empty is collapsed by the stylesheet `content-column` already installs, which this row is composed with by construction. What the conversation shows of a press the agent is reading stays the notice the agent claims.

The view is a component rather than an absence because two settlements have nowhere else to go. A press that resolves against nothing reaches no agent, so no notice, no turn, and no answer ever follows it. A press that only reached the inbox will be read, but not until the user writes again, and nothing else in the conversation says so. Hiding the row would make either of them and a press the agent is reading identical on screen, which is exactly what the handler's own end-user sentences exist for. The row draws whichever sentence the settlement carries — `这个动作没能记下来。` or `已记下，你下次发消息时对话会看到。` — and nothing else about the command; a refusal reads as the failure it is and the waiting press as an ordinary line, and the collapsing rule ignores both because neither is empty.

**A press is answered by the delivery, not by the grade.** The agent's own answer is a whole turn away and may never come, so the press has to be answered where it was made — and the honest answer is where the notice actually landed, which is not what the catalog declared. `wake` degrades to the inbox on a busy agent and past the budget, and a bar saying "sent to the conversation" while nothing will happen until the user writes again is a user left waiting on a screen that told them to. `deliverAction` therefore reports `none`, `opened`, or `queued`, and the handler answers a `queued` delivery with one end-user sentence; the other two carry none. That answer is itself durable — it is the `command/done` the settlement writes — which is what makes it readable again later.

**The pressed state is folded out of the log; no block keeps one.** A block's own pressed flag is wrong in this column by construction: the column discards a kind's DOM whenever the user picks another entry, so a bar that answered its own click comes back untouched and lets one decision be reported twice, and a delivery that failed leaves a button disabled forever with no way to retry. The two records a press already writes are enough to say what became of it, so this row folds them: `componentActions`, one cell per `(entryId, nodeId)`, `command/run` opening it (its verbatim `args` read by the same parser the handler uses) and the `command/done` paired by `commandId` settling it into `sent`, `queued`, or `refused`. The browser reads that value off the session's projection values exactly where the column reads its entry stream — the same channel, not a new one — and `ComponentRendererProps.state` hands each block its own cell. `refused` stays pressable, because reporting it again is the only thing left to try.

A gesture counts for the call now on display and no other: the cell's `seq` is the press's log position and the entry's is its placing call's, so a later call under the same id leaves every earlier press behind it. A block's React identity is the very key its in-flight press is filed under — session, entry, placing call, node — so a replacement remounts rather than reuses, and a session switch, which redraws the seat instead of unmounting it, never hands one session's waiting to another session's block; what changed is that the remount is no longer what resets the answer. The one thing the log cannot cover is the round trip itself: a block waits past the log position it can already see and reads `sending` until a later gesture is recorded.

**The waiting is held for the page, not by the block.** The browser half keeps one table of presses that have no record yet — keyed by session, entry, placing call, and block — for the life of the client plugin, and each block writes its row when the press leaves and reads it back whenever it is drawn again. Keeping it in the block instead leaves the exact hole the fold was built to close, one window narrower: press, pick another tab, come back, and the bar is answerable again while the first report is still travelling, so one decision reaches the agent twice. Two things clear a row and nothing else does — the record arriving, and the dispatch answering that none is coming.

**A press that never became a record settles itself.** `postAction` answers `dispatched` or `failed` and the seat awaits it. `failed` covers the browser's own refusal of an oversized document, a transport-level failure, and a rejected call — a closed socket, a restarted gateway, a session the host no longer holds. In each of them the browser saw no `command/run` written, so as far as the page can tell no settlement is coming, and a block waiting for one sits at `sending` with every button dead for the rest of the session. The block therefore drops its row and reads `refused`, which is what the page can see happened: the gesture was not recorded, and the copy for that state already says so. That reading is local and provisional, and is held the same way the waiting is — as the log position the press was anchored to — so a record the host wrote before the transport dropped settles the block like any other, rather than staying hidden behind the block's own answer for the rest of the mount. A handler that refused the action is the opposite case and counts as `dispatched` — both its records are in the log, and the block reads that refusal off the fold like any other settlement.

**The command's slash-menu row is a sentence, because it cannot be an absence.** `commands.register` has no way to keep a row out of the composer's menu — `CommandDescriptor` carries a name, a description, and an input hint, and the client lists whatever the host catalog returns. So `/component-action` is in front of end users in a menu of things they are meant to type, and the only thing this row controls is what it says there: end-user Chinese naming the buttons in the content panel and stating that the page sends it. `commands.list` is a `@Remote` method, so no model reads that sentence. A `listed` field on the descriptor is the real fix and belongs to `dsh-commands`, with the second row that needs it.

**The kind badge is gone from the switcher strip.** One deletion in `content-column` covers `page`, `chart`, `component`, and every future kind at once, and the column keeps the property that it recognizes no specific kind. A tab now says its own title and nothing else.

### The gate table, as built

| Cell | Content |
|---|---|
| **0 — which settled principle already said no** | "Model-visible ⟺ logged" required the press to be in the log before the model may see it, which `command/run.args` satisfies. "The conversation is the front door" ruled out dressing a gesture as the user typing: `source.kind` is `plugin`. "Upstream zero-change" permitted the mechanism, because `agent.followup` is an existing public contract. **"`ignorable` has no plugin-facing API" ruled out a session event of this row's own**: `Session.append` accepts no such option for a non-surface event, so a new required-on-read member would break every build that does not know it. "A projection never reaches the model" ruled out "a new event plus a projection is enough to tell the model". |
| **1 — new things touched: 4** = 1 + 0 + 0 + 1 + 0 + 0 + 1 + 1 | data source **1** (what the user does inside a seat); UI surface **0** (the component's own buttons); tool or parameter **0**; route or RPC **1** (the `/component-action` command); `Config` field **0** (three grades declared in the catalog, ceilings and budget protocol constants — see below); event type **0** (`command/run` and `user/message` are reused, and the `componentActions` projection folds those same two records rather than adding one); approval gate **1** (a write action passes the deployment's `tools/pre-execute`); dependency **1** (`zod`, for the fold's checkpoint and wire schemas — what every projection unit in the repository carries). |
| **2 — smallest version that proves it** | An idle agent showing a confirmation bar; a user presses a button; the log carries `command/run` with the action document, a turn opens, the notice arrives as a plugin `user/message`, and the model's next words name the pressed button. |
| **3 — seam or hard-coded** | **Hard-coded.** A per-action `report` seam with a `Config` override table was rejected, against two near-term changes argued for it — a table's `select` dropping to `silent` once a data source exists, and a filter bar's `submit` dropping to `context` for a customer who does not want the conversation interrupted. Neither component exists yet, so both are suppositions rather than instances, and the rule says hard-code. The grades live beside their actions in `COMPONENT_CATALOG`; the review trigger is the first real request to move one. Also hard-coded: three grades and no fourth (an `answer` grade returning the model's reply is rejected below); the command name (a wire contract, read from one constant by both halves); and `source.form = 'notice'`. |
| **4 — one line per direction** | *Neighbours*: the handler reads the document, resolves it against the entry the log says is on display, builds the account from the catalog, and delivers it — it reaches no backend, calls no tool, and asks for no approval. Guards against the handler becoming a second agent loop, and against an `approval.request()` that would throw for want of an open turn. *Contract*: the notice's every word comes from the catalog and the logged spec. Guards against a page putting words in the user's mouth — the concrete precedent is a source-library component whose event payload carries the whole signed-in user record. *Temptation*: no `source.kind: 'user'`. Guards against a machine-authored message that quoting, editing, and history all treat as something the person said. *Red line*: a wake is budgeted **and** refilled. Guards against both an unbounded turn chain and a session that silently stops waking after three presses. *Ceiling*: only "what the user did" reaches the model, never "what the block currently shows" — the agent cannot answer "what is in row three". Deferred until a model starts asking. |

## Alternatives considered

**A Log-only session event of this row's own.** Rejected for this slice, on a mechanical fact rather than a preference: the `ignorable: true` flag such an event would need to be safe on uninstall cannot be written from a plugin at all — `Session.append`'s option tuple for a non-surface event is empty, and no production writer of that flag exists in the repository. Without it, a new `SessionEventMap` member is required-on-read, and a build that does not know it refuses the log. `command/run` already records the document verbatim and is documented as log-only, and `plan-mode` is the precedent for a plugin filtering commands by name and reading their `args`. What the deferral costs is the one thing the event would have bought: a place to shape what is stored, which is why the whitelist is a client obligation today.

**A fourth `answer` grade returning the model's reply to the same tool call.** Rejected: it needed an HTTP route, a pending-report table, a model-visible three-valued enumeration, and two `Config` fields, and the only thing it bought was that the answer landed inside one tool call rather than in a new turn. In a product where the conversation is the front door that is a latency convenience, not a capability. The review trigger is a measurement showing the extra turn is unacceptable.

**A `Config` override table for the report grades.** Rejected as premature: see cell 3. A deployment that moves a grade changes what the agent is told happened, which is a catalog decision.

**Building the notice from the label the seat sends.** Rejected: a `componentLabel` field arriving on the wire contradicts the rule that no client text is trusted, in the same breath as stating it. The wire carries identifiers only.

**Dropping `nodeId` from the action document.** Rejected: without it, two blocks of the same component in one spec are indistinguishable, and the notice cannot say which one spoke.

**The composed-turn evidence lives in the browser lane, and could not live in the transcript lane.** An ACP snapshot scenario driving a press cannot exist: `/component-action` reaches the host only through `remote.commands`, and the ACP protocol has no command method. The lane composes the command registry all the same, because the description it pins tells the model a press comes back and a composition offering that description has to be able to keep it; what the lane cannot do is invoke the command. The same wall stands one level down — a package-local judge test cannot boot `agent-loop` either, because `component-surface` is registered in the Client compiler aggregate and `agent-loop` is a Host package, and the two aggregates collide on the `Context` merge. So the composition spec pins everything up to the handover (the command exists, the account handed over, the log kept, no gate of this row's own in the way of the composition's policy, the row disposing), and `apps/web/tests/component-surface.e2e.ts` pins the turn itself. The `content-console` lane still pins the model-visible half that *did* change: the tool description.

**Known Limitations, carried in the READMEs.**

- The payload whitelist is the block's own promise. The command registry records a command's input verbatim before any handler runs, so an over-full document is already in the log when the host refuses it; what the host enforces is that it is not delivered.
- The transcript row names the mechanism, not the block. A notice arrives as a collapsed row headed `上下文注入 · content-component` (`Context injection · content-component` in English), and the one-line summary beside it is a flexible cell the console's three-column chat width squeezes to nothing. Both are `ui-conversation`'s chrome, drawn the same for every producer; a per-producer display name is a change in that package.
- The wake budget is memory. Spent wakes live in a table keyed by the agent object, so a restart hands every agent a full budget again and a resumed session cannot tell how many turns its presses had already opened.
- The model still cannot see what the column holds. It knows which calls it made and which gestures came back — not which entry the user is looking at, nor what any block currently shows.
- A renderer that adds a property its action does not declare makes every press of that control reach nobody: the host refuses the whole gesture rather than trimming it, and nothing in the component row checks the payload before it is sent.
- The command is listed in the end user's slash menu, with its `<json>` hint, because the registry has no way to hide a row. A line typed there by hand answers with the same refusal a lost press gets, and repaints the block it names with that refusal: the gesture fold reads a line's identifiers, and only the handler resolves them against the entry on display.
- A `silent` action's block would say the conversation has it. A delivery that reached nobody and one that opened a turn settle as the same textless success, so the fold reads both as `sent`. No catalog action declares `silent` today; the first one that does decides its block's line in the same change.
- Expanding the collapsed notice is no better than leaving it closed: a `notice` renders its model-facing text, which is the English sentence written for the agent with the entry and node identifiers inside it. Its review trigger is the same `develop`-line change that gives a producer its own display name.
- The fold is per block, not per action: a component declaring two actions has one cell for both, so the state a bar draws is whatever it last reported rather than what it last reported *of that action*. One action per component is all the catalog has, and the day a second one exists the cell key grows with it.
- A press the log opened and never closed reads as on its way forever. The two records are written either side of the handler, so a host that stops between them leaves a cell open — nothing closes it afterwards, and the block stays unpressable until a later call replaces the entry. A press that produced no record at all is the other case and settles itself.
- The two settlement sentences are Chinese in any interface. The handler writes them and is handed no browser locale — a command result is one string, and the log has to keep the words the user was shown — so a non-Chinese console draws them in the chat beside a bar whose own lines came from `component-kit`'s dictionary and are localized. A key the client translates, or a locale carried on the command result, is the fix; the trigger is the console offering an interface in any other language.
