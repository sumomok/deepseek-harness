# Agent Note: arranging the blocks of one call, and feeding one from another

Status: implemented

English | [中文](2026-09-05-content-component-library-v2a-layout-and-bindings.zh.md)

## Problem

A call places blocks and the column stacks them in the order they were written. That is enough for one block and wrong for two, and the two-block case is the one every service-line console asks for first: a table of records above, and the record the user picked below it. Two things are missing, and neither is expressible in what the call already carries.

- **Where the blocks go.** Ordering says which comes first, never which sits beside which. A record fed by a table is only worth having while both are on screen at once, and a column that stacks them top to bottom in a panel the user has to scroll is a pair that is never both visible.
- **What the lower block shows.** Today the model would have to ask: place the table, wait for a tick, read the notice, place a second call carrying that row's fields. Four steps and a model request for a gesture the page already knows the answer to, and the entry flickers through a replacement in the middle of it. The user meanwhile ticks a row and watches nothing happen until a model somewhere finishes a turn.

The second one is the harder problem, because the obvious answer breaks a rule the whole surface rests on. If what the user ticked reaches the lower block by way of the model, every tick is model-visible input and `Model-visible ⟺ logged` requires a session event per tick. If it reaches it any other way, then something on the page is deciding what a block shows, and the host has judged a value it never saw.

## Decision

**No new entry kind, and no new tool.** `show_component` gains an optional `layout` beside its `nodes` and accepts a binding as the whole value of a property. A view is a call, folded into one `contentSurface` record exactly as a single-block call is, so the switcher strip, the dismissal event, the projection, and the id-replaces-id rule are untouched. The alternative — a second kind for composed views — buys a second extractor, a second renderer claim, a second fold and a second set of the rules above, for an entry the user cannot tell apart from the one beside it.

**One layout primitive: `stack`.** It carries a direction, a gap from three named sizes, whether it wraps, and its children; a child is another stack or a block, and either kind may carry a `flex` — what divides a row is its children, whichever kind they are. The outermost stack is the one that may not: it fills the entry, so a share written on it divides nothing, and both readings say so — the host refuses `spec.layout.flex` by name, and the seat reads the tree as one it does not understand and draws the plain column. There is no grid, no tab strip, and no width. A grid belongs inside a component that draws N of one thing, and the components this row wraps already do. A tab strip is what the content column is: one entry per tab, and a second one inside an entry is two switchers over the same panel. A width is a number the model cannot know, because the column's own width is solved at runtime against a chat pane the user drags — `flex` is a share of what there is, which is the same statement without the guess.

**One binding notation: `{"$from": "node:<id>.<output>[<index>]"}`, as the whole value of one property.** No expression, no condition, no default, no fallback, no second reference in one value. The notation is deliberately too small to compute in: the moment a binding can express `a ?? b` or `rows.length > 0`, the page is running the model's program and the failure modes are the model's to debug through a surface that reports nothing. What is left is a reference, and a reference either resolves or does not.

**A component's outputs are declared in the catalog, and compatibility is decided statically.** `ComponentCatalogEntry` gains a required `outputs: readonly ComponentOutput[]` — empty for a component nothing can be read from, symmetric with `actions` — and each output carries the same `PropsFieldSchema` a property carries. `acceptsOutput(source, target)` then decides, before the call is accepted, whether what one block reports can stand where another declares a property: same kind, and every ceiling of the source within the target's. It compares upper bounds only, never lower ones, because an output is how far the user has got: a property declaring `minItems: 1` still accepts a binding to a tick list, so that the call the model made an hour ago is not refused for a row the user has yet to tick. The floor is the seat's to apply, against the value that actually resolves — an empty tick list does not fit that property, and the block it feeds draws the waiting line.

**A property the host reads back cannot be bound, and the component says why.** `PropsField` gains an optional `unbindable` carrying the model-facing reason, and a table's `displayValueList` and `rawValueList` carry one. What a reported gesture is named against — the row that was ticked, the header that was sorted — the host reads out of the call that wrote the rows, and a resolved value is in no call: a table fed its rows by another block would report every gesture in it to nobody, silently, because a notice that cannot name what happened is a notice nobody sends. The rule is general, not a patch on the table: a property the host reads back is a property no other block may write.

**Values therefore travel one way, and nothing looks for a loop.** Every component that reports something reads its own properties back, so a reporting block is one no other block can feed, and no chain of bindings can close. The pass that walked the chains and refused a cycle is gone with the last spec that could have written one; what holds the catalog to it is a test that binds every output of every reporting component into every property of every reporting component and expects each one refused. A component that both reports and can be fed fails there, which is where the runtime pass would have to come back.

**A bound value never enters the log, the payload, or a model request.** The reference is what the model wrote and what the log carries; the value it stands for is resolved in the page, for one render, and is thrown away. This is what keeps `Model-visible ⟺ logged` true of a fed block: nothing the model can see has changed, because the model sees the reference. A tick that feeds a record beside the table is a page redrawing itself, and it costs the session log nothing — which is the whole reason the notation exists rather than a round trip.

**A block waiting on a value draws a line, not an error.** When a property the component requires is bound to an output nothing has published yet, the seat leaves that block out of the judgement and draws `Pick something to show here` in its place; every other block of the call is drawn normally. An empty record would say the row has no fields; a refusal would blank an entry over a user who has simply not ticked anything yet.

**A resolved value is judged, and a judgement it fails costs only the fed blocks.** The value came out of a component in the page, and the host checked only that its declared shape could stand there — never what it would carry. So the seat substitutes resolved values into the properties and runs the same `validateComponentSpec` over the result, which is one pass, not two rules. When that pass refuses, the seat drops every bound block and judges the rest: the table the user is working in stays on screen, and every block fed by another falls back to the waiting line — the ones holding a perfectly good value included, because the refused pass is discarded and what is left does not say which block spoiled it.

**A block's identity is `[entryId, seq, nodeId]`, and a bound block adds what its references resolved to.** A renderer memoizes on its properties, and a Vue table handed a fresh row array reads it as a table whose rows have been replaced — it clears the selection. Re-reading the payload because the block *beside* it was fed something would therefore throw away the user's own ticks at the first tick. So a block whose references stand where they stood keeps the object it already had (`holdSteady`), and only a block actually handed something new gets a new one. The published values are scoped to one call: a later call under the same entry id starts from nothing, because carrying the previous call's ticks into a new table would feed a record the rows of a table that is gone.

**The ceilings.** `MAX_NODES` goes from 8 to 12, a layout nests at most 4 stacks deep, a stack holds at most `MAX_NODES` children, `flex` is 1–12, and a layout places every node exactly once. The host checks shape and ceilings and nothing else: it does not know that a table above a record reads better than beside it, and a host that had an opinion about that would be a layout engine with one deployment's taste compiled into it.

## Alternatives considered

**A tab strip or an accordion as a second layout primitive.** Rejected because the content column already is a tab strip, one entry per tab, with a switcher the user knows. A second one inside an entry gives the same panel two switchers with different rules, and the user has to learn which of the two closes what. An accordion is the same objection with the tabs stacked.

**A grid with rows, columns and spans.** Rejected as the wrong owner. Where a grid is genuinely wanted, it is over N of one thing — N metrics, N cards — and that is a component, drawn by something that knows what one cell is. A grid between arbitrary blocks needs a span per block and a column count per breakpoint, which is the width guess again with more arithmetic: the model would be sizing a column whose width the user is dragging.

**Expressions in a binding — `a ?? b`, `rows.length`, a filter, a format string.** Rejected on the failure mode rather than the effort. An expression that goes wrong produces a block showing the wrong thing with nothing to read: no path is named, because the path was fine, and the host cannot judge an expression's result without evaluating it, which means running the model's code in the host. Every proposed operator so far is answerable by the component instead — a record that draws nothing for an absent field, a table that draws its own empty state — where the failure is visible and the code is tested.

**Conditional rendering — a block drawn only when something is ticked.** Rejected because the waiting line already is the honest version of it. Making the block vanish and reappear moves the panel under the user's cursor at every tick, and the two states a person actually needs to tell apart are "nothing picked yet" and "picked, and here it is", which a line and a filled block say without moving anything.

**A binding across entries — one entry's table feeding another entry's record.** Rejected because only one entry is on screen. The fed block would resolve against a table the user cannot see, and its value would change when they switch tabs to something else entirely. Scoping the published values to one call is also what makes a replacement call start clean.

**Repeating a block over a list.** Rejected as a component's job for the same reason as the grid: something has to decide what one item looks like, and that decision is a component.

**Letting the seat reuse the host's layout reader.** Considered, and it is the deduplication to make when the host exports one. The seat cannot hand `layout` to `validateComponentSpec` today, because the pass that judges the nodes runs over a *subset* of them — a block waiting on what feeds it is left out of it — and a full tree handed to that pass is refused for placing a node the shortened list no longer has, so `layout` stays out of it. What the reader arranges is the other set: every block, the waiting ones included, so a block waiting on what feeds it holds its place instead of the stack closing over it. The two readings also answer to different audiences: the host names the path it refused so the model can fix it, and the seat falls back to a plain column so a payload another build wrote still draws. Recorded in both READMEs as the deduplication a `readLayoutTree(value, ids)` export would close.

**A second waiting line for a value that does not fit.** Rejected for this slice and recorded. "Nothing ticked yet" and "what was handed over does not fit here" draw the same line, and only the first is something the user can act on. Telling them apart needs the seat to know which of the two refusals it hit before it discards the failing pass, and a second sentence a user would still not be able to act on.

**What the integration found that neither half could.** The two halves were written against one agreed vocabulary and both passed their own tests, but three call sites in `component-kit`'s specs constructed a renderer's properties inline rather than through the shared helper, and so never gained the new `onOutput`. Vitest does not see it — a missing prop is `undefined` and nothing in those tests calls it — and `tsc -b` does, which is why the build gate is the one that caught it and why it is the first gate this integration runs.

**What the browser found and this slice does not fix.** The vendored table draws a ticked row's box with the same white fill as an unticked one: `getComputedStyle` reads `rgb(255, 255, 255)` for both, on this entry and equally on the `sites` entry that shipped before any of this. The component holds the tick correctly — the reported positions, the fed record, and the `is-checked` class are all right — so what is wrong is the row's styling, not this slice's subject. It is recorded in the browser lane beside the assertion that reads the class, so the next person to open that file meets the measurement rather than the surprise.

## Known Limitations and Deferred Work

- **Two entries of the same kind share one seat, and switching between them loses what the user did.** The published values are scoped to `[entryId, seq]`, so returning to an entry redraws its blocks with nothing published and every fed block back on its waiting line — and the table's own ticks are gone with the unmount, as they already were. Nothing is lost that the log holds; what is lost is a working state the user built. Closing it means the column keeping a mounted seat per entry, which is the column's design rather than this row's.
- **A composed view cannot be kept.** There is no way to save the arrangement and the bindings of a call and put it back later, in this session or another, which is what a workflow would want. That is `v2b`, with the vendor's own saved views and `/show-content-view`, and it needs a home for a view outside one session's log.
- **A vendor's own views are not here.** A deployment that already has views defined in its own system cannot offer them to the model; every view is one the model composes per call. Also `v2b`.
- **An output waits for the component that takes it.** The catalog declares one output — `toy.table`'s `selectionDetail`, into a record block's `dataList`, the pair the feature exists for. A table's ticked rows in the form the call wrote them and `el.filter-bar`'s conditions are not declared, because no property here accepts either: an output nothing accepts is a binding the model is offered and then refused, and a catalog line that only ever produces a refusal is worse than no line. Each is declared with the component that takes rows or conditions as an input, or with the data source of `v2c` — a catalog line plus the renderer's `publish` call, since neither renderer publishes one now.
- **The host and the seat read a layout twice.** Two readers of one grammar, for the reasons above; a `readLayoutTree(value, ids)` export from `validate.ts` would give the seat the host's reader and leave one home for the rule.
- **A waiting block cannot say which kind of waiting it is.** One line covers both "nothing published yet" and "what was published does not fit", and only the first is the user's to act on.
