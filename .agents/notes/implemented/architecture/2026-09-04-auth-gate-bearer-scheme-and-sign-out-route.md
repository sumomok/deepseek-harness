# Agent Note: auth-gate — one place to drop the login page's `Bearer` scheme, and a sign-out that reaches the mirror cookie and the held token

Status: implemented

English | [中文](2026-09-04-auth-gate-bearer-scheme-and-sign-out-route.zh.md)

## Problem

`@deepseek-ai/dsh-experimental-auth-gate` ([`2026-08-28-browser-single-sign-on-and-mcp-token-injection.md`](2026-08-28-browser-single-sign-on-and-mcp-token-injection.md)) was written against an assumed contract with the deployment's login page: `localStorage.accessToken` holds a bare three-segment JWT. The login page this deployment actually ships is a toy-core page, and it stores `"Bearer <jwt>"` — the value its own HTTP client puts into the `Authorization` header verbatim. Against that page the gate never gets past its first decision: `usableToken` calls `isJwtShaped`, which refuses anything but three base64url segments, so a freshly signed-in visitor reads as unauthenticated, is sent back to the login page, is signed in again, and returns to the same refusal. The tab never renders anything else.

Three further gaps surfaced with it, all on the path the gate takes when it gives up a token.

- The mirror cookie survives every decision to leave. The gate writes it so requests carrying no `Authorization` header still identify the visitor to the reverse proxy in front of the process; when the token behind it is gone or expired, the cookie goes on presenting a dead credential — on the navigation to the login page, and on every request the login page itself makes.
- The node half goes on holding the token. Its forwarding routes spend whatever was posted last, so a visitor who signed out or whose token expired leaves the process able to reach the deployment's MCP servers as them until the process ends.
- The return address carries the login page's own credential parameters back to it. toy-core reads a credential from `token` and `token4a` as well as from storage (`core/token.js:32,81`), and reads them out of the whole address rather than out of its query — `getUrlParam` parses everything past the first `?` in `location.href` (`utils/commonUtils.js:60`). So a page reached as `…?token=<jwt>`, or as `…#/board?token=<jwt>`, produces a `redirect` that hands the login page the very token the gate has just refused, and leaves it in the browser's history and in every referrer that page sends.

## Decision

**The scheme is dropped at the one point a stored value enters the gate, and nowhere else.** `storedToken(raw)` in `src/client/browser.ts` removes any leading whitespace, a case-insensitive `Bearer`, and the run of whitespace after it; `windowGateBrowser().readToken()` is its only caller. It is idempotent — a bare JWT and `null` come back unchanged — so a login page that later stores a bare token needs no second contract. `isJwtShaped` and `parseTokenPost` in `src/route.ts` are untouched: they fence a wire boundary the token crosses between processes, and everything downstream of `readToken` — the mirror cookie the proxy reads, the token route, the `Authorization` header `proxy.ts` builds by adding `Bearer ` itself — carries the bare JWT. Loosening the wire check to accept both forms would have put the choice of which form travels where into every consumer instead of into one function.

**Every decision to leave for the login page gives the token up first, in a fixed order.** `leaveForLogin` in `src/client/run.ts` is the single exit, reached from the boot decision, the storage-change decision, and `handleTokenExpiring`: it calls `revoke()`, then `browser.clearCookie(settings.cookieName)`, then navigates. The node half stops spending the credential before the mirror stops presenting it, and the page leaves last, so no step depends on a page that may already be gone. `clearCookieLine(name)` sits beside `mirrorCookieLine(name, value)` and repeats its `Path`, `Secure`, and `SameSite` verbatim — a browser matches a removal against an existing cookie by name, path, and domain, so a line differing in any of them writes a second, empty cookie and leaves the mirrored token in place.

**`POST /auth-gate/logout` is a route the browser half calls, not a control a person operates.** It sets the plugin closure's `held` back to `undefined` and answers 204, behind the whole `rejectMethod`/`rejectCrossSite`/`rejectNonJson` fence the token route carries and with no body read at all: it names no token, it drops whichever one is held, which is the token of the one visitor this process serves. Both halves of the fence are load-bearing, and for one reason: `rejectCrossSite` reads `sec-fetch-site`, so a request carrying that header at all is one a browser labelled, and a request carrying none passes. What withdraws a state-changing route from the set a cross-origin page can post to without a preflight is the content type, which is why the sign-out route requires `application/json` even though it reads nothing, and why the browser half declares it. The browser half posts it from `leaveForLogin`'s `revoke` callback with `keepalive: true`, because the navigation two steps later would otherwise cancel a request the document owns. Seating the call at the gate's three login decisions is what makes the guarantee hold without a product surface: the states that make a held token wrong — no token, a removed one, an expired one — are exactly the states the gate already detects.

**The return address is stripped of `token` and `token4a` before it is encoded, in the fragment as well as in the query.** `returnAddress` in `src/client/gate.ts` splices the remaining parameters textually rather than re-serializing them, so every parameter the page was asked for comes back encoded exactly as it arrived. The fragment gets the same treatment because the reader on the other end does not respect the divide: toy-core's `getUrlParam` parses everything past the first `?` in `location.href` (`utils/commonUtils.js:60`), and `getToken` feeds `token` from there straight into `localStorage.accessToken` (`core/token.js:75`). Stripping only the query would therefore make things worse than leaving both — it takes away the `?` that was keeping the fragment's copy out of that parser's reach. What survives is the fragment's own route and its other parameters, which is what a hash-routed return address is.

## Alternatives considered

**Accept both forms at the wire boundary — let `isJwtShaped` and `parseTokenPost` take a `Bearer`-prefixed value.** Rejected: the token route is the boundary between the browser and the process, and a boundary that accepts two spellings of the same credential makes every reader downstream responsible for knowing which one it got. `proxy.ts` builds `Bearer ${token}` itself, so a prefixed value reaching it produces `Bearer Bearer <jwt>` — a header an upstream refuses with no diagnostic pointing back here. Dropping the scheme where the value enters keeps exactly one representation inside the package.

**Strip the scheme inside `usableToken` or `decideGate` instead.** Rejected: those are the decision table, defined over the token as a value, and `run.ts` carries `decision.accepted.token` straight into the mirror cookie and the push to the node half. A strip there would have to be repeated for the cookie read-back comparison, and a second stripping point is a second contract to keep in step.

**Clear the token out of `localStorage` too, alongside the cookie.** Rejected for this slice: the gate has no storage write in `GateBrowser`, the login page overwrites the key on the way back in, and a gate that cleared storage would race another tab that is mid-sign-in on the same origin. The product decision this slice implements is "no token or a 401 sends you to the login page"; a sign-out control that clears storage and interrupts the running turn is a separate surface, recorded as a Known Limitation in the package README.

**Have the node half expire the held token on its own, from the `exp` claim.** Rejected: the node half deliberately reads nothing out of the token — it holds an opaque credential and never decodes it, which is why the package can state that it authenticates nobody. Adding a claim reader there to answer a question the browser half already answers on a schedule would put a second, weaker expiry policy in the process.

**Re-serialize the return address through `URLSearchParams`.** Rejected: it rewrites the parameters it keeps (a literal space becomes `+`, reserved characters are re-encoded), so a return address would come back subtly different from the one the visitor asked for. The textual splice keeps every kept parameter byte-for-byte.

**Strip the query's credential parameters and leave the fragment alone.** Rejected: the fragment does not leave the browser, but neither does `localStorage`, and the login page reads both. Because that page's parser starts at the first `?` in the whole address, the query's copy shadows the fragment's; removing only the query's is the one change that turns a credential the page could not reach into one it takes. Either strip both or strip neither, and stripping neither is what the gate is here to stop.

**Name the token to drop in the sign-out request, and clear `held` only when it matches.** Deferred, and recorded as a Known Limitation in the package README rather than left implicit. It would close a real ordering hazard — a `keepalive` sign-out that arrives after the next page load has already posted a fresh token drops that fresh one — but it does not fit the decision that has to work first: the boot that finds no usable token has no token to name, so the route would need "drop whichever is held" semantics anyway, and a route with two modes is a route whose fence has to be reasoned about twice. The recovery half of the same gap, re-posting the current token when a page is shown again, is the other shape it could take.

## Consequences

A deployment whose login page stores a bare JWT is unaffected: `storedToken` returns such a value unchanged, and the e2e scenario in `apps/web/tests/auth-gate.e2e.ts` now stores the `Bearer`-prefixed form while still asserting the bare token in the mirror cookie and in the forwarded `Authorization` header, which is what makes the removal observable end to end rather than as a unit fact. That scenario also has a sign-out phase: a second tab in the same context removes the stored token, which is the only way a `storage` event is delivered at all, and the three effects are read off the browser — the mirror cookie gone from the context, the tab settled on the login page, and the forwarding route back to 503.

`storedToken` accepts any whitespace around the scheme rather than the one space the login page writes, because the alternative failure is the one this note exists to remove: a value it declines to strip fails `isJwtShaped` and sends a signed-in visitor back to the login page. Nothing else is stripped — a repeated scheme survives and is refused the same way — since a JWT carries no whitespace, so what the tolerance widens is the set of values the gate reads correctly, not the set it accepts.

The node half's memory of the token is no longer "for the process lifetime": `held` is now cleared by a route, so the package README's Known Limitation about revocation is replaced by the route's contract and by what still has no sign-out — a visitor who closes the tab, and the agent loop, which this slice does not interrupt.

`runGate` takes a fourth argument. It is a browser-half signature with two callers, the client plugin body and its own spec, so the cost is confined to this package; the alternative — a `GateBrowser` method — would have put a route call inside the interface whose whole purpose is to be the gate's only contact with the browser's globals.
