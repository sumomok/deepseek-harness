# Agent Note: the views a deployment writes, and one navigation menu over two catalogs

Status: implemented

English | [中文](2026-09-06-content-component-library-v2b-vendor-views.zh.md)

## Problem

Everything the content column can show, a model has to place. That is the wrong default for a service-line console: the arrangement a customer opens every morning — the site list above the site they picked — is written once by the people who deploy the console and never changes, and asking a model to redraw it on request spends a turn to produce a fixed answer, differently each time.

The console already has the surface for a fixed thing a click opens: `content-frame` serves configured pages, and the sidebar's navigation menu lists them. A composed view is the same gesture over different content. What is missing is on three sides at once.

- **A deployment cannot write one.** `show_component` accepts a spec from a model. There is no way to put the same spec in `cordis.yml`, and no assurance that one written there would be a spec the tool would have accepted — a deployment would learn that a view was malformed when a user clicked it.
- **The menu reads one catalog.** `readContentPages` fetches `content-frame`'s settings and nothing else, and `openPage` runs `show-content-page` because a page is the only thing a row can be.
- **A workflow's snapshot cannot say what it captured.** `navSnapshot` is `string[]`: page ids, replayed by running `show-content-page` on each. A view stop in that array would be replayed as a page id and silently do nothing.

## Decision

**A configured view and a model's call are one spec, judged by one pass.** `Config.views` takes `{id, title, spec}` entries and runs each through `validateComponentCall` — the same function the tool body runs, ids and titles included, not a looser configuration-only check. A deployment whose view names a component the catalog does not carry, or binds a property the component reads back, fails at load with the sentence the model would have been given. The alternative was a second validator for configured views, which is a second set of rules to keep in step with the first and a second way for the two to disagree about what a spec is.

**A view reaches the column through a command, and the command writes the record.** `show-content-view <id>` appends `content-component/shown` carrying `{entryId, title, spec, by: 'user'}` — the view's id is the entry id, recorded once under the name the column keys on, and the same `component` extractor folds it into the same entry kind a `tool/call` folds into. The click is the sidebar running a command against a session, exactly as `show-content-page` already is, so it gets the durable `command/run`/`command/done` pairing for free and the column replays from the log alone.

**The whole spec is recorded, not the view id.** An entry is self-contained, the way a call's arguments are. A view the deployment later edits or drops still replays as what the user actually saw, and no reader has to resolve a log against a `cordis.yml` it does not have.

**The event is required on read, not ignorable.** `Session.append` has no way to set the envelope's `ignorable` marker — that flag is read by `dsh-session`'s own validation and written by nothing a plugin can reach — so this event joins `content/shown` and `content-surface/dismissed` as one a runtime must know. It is registered in `KNOWN_SESSION_EVENT_TYPES` and `docs/persistence-catalog.md` in this change, and the limitation is written in the package README: a separately built runtime that excluded this package would refuse a log carrying the event rather than skip it. Making it genuinely ignorable means changing `dsh-session`'s append signature, which is upstream and out of this line's reach.

**The spec never travels the route.** `GET /component-surface/views` answers `{views: [{id, title}], homeView?}` and nothing more. What a click puts in the column is appended on the host out of the same index the route lists, so a page cannot ask for a view the deployment did not configure, and the spec has exactly one way in. The route exists at all because a browser half receives no cordis config — the boot manifest carries plugin names, not their `config` blocks.

**The menu merges two catalogs and dispatches per kind.** `readContentPages` and `readContentViews` each read their owner's route, each row carrying `kind`; `mergeNavCatalogs` concatenates pages then views, each in its own declaration order. There is no `order` configuration field: navigation order follows deployment configuration and is never user-reordered, and a fixed source order keeps that true across the pair without a third field to keep in step. A route that is unreachable, non-200, or unusable contributes zero rows rather than taking the sidebar down — composing only one of the two owning packages is an ordinary deployment.

**Two automatic homes fail loud at load.** The content column shows one thing at a time, so a deployment naming both `homePage` and `homeView` has expressed an intent this shell cannot carry out. `mergeNavCatalogs` throws, in `apply()` before any registration, rather than silently honouring whichever route was read first and leaving the other configured value doing nothing with nothing to say why.

**`navSnapshot` changes shape and refuses the old one.** It is `{kind, entryId}[]`. A stored `string[]` is refused by name — at the settings `validate` hook, at the route's 400, and at the browser's own wire read — rather than reinterpreted as page ids, which is what every stored one meant. The repository's pre-release stance rejects old on-disk formats outright, and a document the process silently reinterprets is one nothing ever converts. The refusal names `pnpm --filter @deepseek-ai/dsh-experimental-server-sidebar run convert-nav-snapshot <settings file> [--dry-run]`, shipped in this change as `src/bin.ts` over `src/nav-snapshot-migration.ts`: it rewrites each stored id as a `page` stop, seeds an empty `groups` list, keeps key order and every comment away from a rewritten value through `yaml`'s document model (a comment attached to a rewritten `navSnapshot` value goes with the node it replaces), and is idempotent.

**A capture keeps only what the menu lists.** `captureNavSnapshot` takes the merged catalog and drops every entry it does not carry. The content column holds more than navigation: a chart the agent drew, a component the model showed itself with `show_component` — whose id is free-form model output, not a configured view — and an entry whose page or view the deployment has since dropped. A snapshot is replayed by re-running each stop's own command, and both commands refuse an id the deployment does not configure, so recording any of those three would store a stop whose replay can only warn. Filtering on the entry kind alone was not enough: `show_component` lands as the same `component` kind a menu click does.

**The converter lives in `src/bin.ts`, not `scripts/`.** `packages/*/*/src/bin.ts` is an existing repository convention: it is inside the package's own tsconfig `include`, excluded from vitest coverage, and — through the package script that runs it — a knip entry. `packages/*/*/scripts/**` is in no compiler face's include and is not a knip entry, so a converter there would be unchecked by both.

**Groups land as data, with no interface.** `ServerMenuSettings` gains `groups: ServerMenuGroup[]`, a workflow gains `groupId?`, and `TEMPORARY_GROUP_ID` is reserved: always resolvable, never stored, refused if a stored group claims it. Nothing renders a group. The format change ships one slice ahead of the interface that reads it because it rides the same refusal the `navSnapshot` change already forces — an operator converts once, not twice.

**Two files carry the change the sidebar could not avoid.** `session-resolution.ts` is untouched: the two kinds resolve a session identically, and the whole difference between them is one dispatch table in `open-nav.ts`. `nav-snapshot.ts` becomes the single home of the one translation the sidebar spans — navigation kind (`page`/`view`) to content-surface entry kind (`page`/`component`) — because folding a projection into a snapshot was already its job. The reverse table is derived from the forward one, so the pair cannot drift, and `workflow-actions.ts` takes its clean-draft judgement from the same function rather than restating `'component'`.

## Alternatives considered

**Serving the spec on the catalog route and letting the browser append it.** Tempting because the sidebar would then need no command at all — it already holds a session id and could write the record itself. Rejected because it puts the spec in the page: a route that hands out specs is a route anything on the page can read one from, and an append built in the browser is a record the host never judged. The command keeps exactly one way in, and it is the same way `show-content-page` already uses.

**A configuration-only validator for views.** Considered because a deployment's spec has no model to give a message to, so the tool's model-facing refusals read oddly at boot. Rejected because the point of the feature is that a deployment can write what the model can write: two validators are two answers to "is this a valid spec", and the first time they disagree, a view that boots is one the tool would refuse or the reverse. The odd register in a load-time message is a smaller cost than that, and the message still names the path.

**Reading a stored `string[]` `navSnapshot` as page ids.** This is what every stored one meant, so it would be correct today and free. Rejected on the pre-release stance: a document the process silently upgrades on read is one that is never actually converted, so the compatibility branch is permanent, and the first stored view stop makes the guess wrong in a way nothing reports. The refusal is a one-time cost to an operator who is handed the command that fixes it.

**Letting the sidebar import `component-surface`'s route path and command name.** Rejected for the reason `nav-catalog.ts` and `http.ts` already record: a cross-package value import is not this repository's sanctioned way to couple two client-adjacent plugins. What replaces it is a copy plus a mechanical check — the sidebar's tests import the owning constants and compare, so a drift fails a test instead of silently shortening the menu.

**Picking one home when a deployment configures two.** Rejected because both orders are defensible and neither is discoverable: the deployment wrote two values and one of them would do nothing, with no place that says which or why.

**Shipping groups with their interface, or shipping the interface first.** Rejected in both directions. Shipping the interface first means a second stored-format change and a second conversion for the same operator. Shipping both means this slice carries a navigation redesign it has no acceptance criteria for. The durable shape rides the refusal the `navSnapshot` change already forces, and the interface follows.

## Consequences

**Bought.** A deployment writes the arrangement its customers open every morning, and it costs no model turn and produces the same result every time. The two catalogs are one menu with one merge rule. A workflow replays a mixed sequence of pages and views. A malformed configured view stops the boot rather than a click.

**Paid.** `content-component/shown` is a session event every build of this repository must know; a runtime assembled without this package refuses a log that carries one. `navSnapshot`'s format change is a hard break with a one-time operator step. The catalog route and the `show-content-page`/`show-content-view` names exist in two packages as literal copies held together by tests rather than by the compiler.

**Evidence.**

- `pnpm run build`, `pnpm run typecheck`, `pnpm run doc-sync` (28/28) green; `pnpm run lint` and `pnpm run hygiene` at their pre-existing `apps/desktop` baselines; `pnpm run duplication` at its pre-existing three clones.
- `pnpm vitest run packages/experimental`: 113 files, 1553 tests. Per-file 100% statement, branch, function and line coverage over `component-surface`, `component-kit`, `server-sidebar` and `content-column`.
- `pnpm run test:snapshot examples/content-console`: 14 scenarios unchanged. A configured view moves nothing model-visible — `show-content-view` is a command, and the ACP protocol this lane speaks has no method to invoke one — so the fixtures needed no re-recording; what the lane proves is that a composition carrying `views` boots at all, which is where a malformed spec would stop it.
- `pnpm run test:web:built server-sidebar`: 20 scenarios, including a new composition over both catalogs (`server-sidebar-views.overlay.yml`) driving the merged menu, the click, the layout, the binding, and the saved `{kind: 'view'}` stop. - The converter was run against a real settings document in both `--dry-run` and write modes: comments and key order preserved, second run a no-op.

## Known Limitations and Deferred Work

- **A composed view cannot be edited from the console.** A deployment edits `cordis.yml` and restarts. There is no authoring surface, and the review trigger is the first deployment that wants one — at which point the durable home for a view is the question this slice deliberately did not answer.
- **No views means no route.** The catalog route registers only when `views` is non-empty, so a sidebar reading it cannot tell "this row is composed and configures nothing" from "this row is absent" — both answer with the web server's SPA fallback. The sidebar degrades to a pages-only menu either way, which is the correct behaviour for both, but a diagnostic could not tell them apart.
- **Groups are stored and never drawn.** `groups` is also not yet writable through the server-menu route's POST patch, which accepts `workflows` and `workbenchSessionId` only. The slice that draws groups adds it to that allow-list in the same change.
- **A view stop replays by id.** A workflow re-created after its conversation is gone replays `show-content-view <id>` against the current configuration, so a view the deployment has since edited replays as it is now, not as it was. The stored `content-component/shown` record in the original conversation still carries what the user actually saw; the degraded re-creation cannot, because it is a fresh session with no such record to copy.
- **One workflow still binds one conversation**, and a chart the agent drew is still not captured in a snapshot. Both are the v1 boundaries the earlier slices recorded, unchanged here.
