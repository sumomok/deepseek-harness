# Agent Note：Windows 安装的时间花在哪，以及两次测错

Status: implemented

[English](2026-08-19-windows-install-cost.md) | 中文

## 问题

[把旧安装整目录改名移除](../bug-fix/2026-08-19-windows-update-max-path-uninstall-loop.zh.md)的做法会删掉整个目录再解压出一份新的，看上去很浪费：一次版本升级通常只改动载荷的一小部分，而安装器把全部 12452 个文件重写了一遍。问题是移除这一步是不是 Windows 安装慢的原因，而这值得用数字回答，因为两个显而易见的答案指向完全不同的修法——优化移除，或者放着不动去攻载荷。

为回答它做的两次测量，数字看着都没问题，但都是错的。

## 决定

移除不是成本所在。用真安装器、配一个便宜到不会改变答案的观测器测得：

| 阶段 | 全新安装 | 覆盖安装 | 差 |
|---|---|---|---|
| 启动 → 目录页出现 | 2.86 s | 13.85 s | +10.99 s |
| 「正在安装」→「安装完成」 | 53.56 s | 58.72 s | **+5.16 s** |

两次用的是同一个安装器、同一个目标目录、同一个观测器；操作者的点击都落在区间之外。这里所有数字都来自同一块 NVMe——C:、D:、E:、F: 是同一块 ZHITAI TiPlus5000 的分区——所以全文的「跨卷」指的是文件系统边界，不是第二个物理盘。这个区别不影响 MAX_PATH 那个故障，那是 `MoveFile` 的跨卷语义而非跨设备；但它确实意味着这些计时对机械盘什么都没说。移除旧版本的代价是 **58.72 秒安装里的 5.16 秒，占 8.8%**，而这个数字已经包含整目录改名、删除暂存树、以及旧卸载器自己的注册表与快捷方式清理。解压与落盘占掉另外的 91%。

两个目录页之间相差的那 11 秒不是安装变慢了。那是 `customInit` 的进程清扫在 `.onInit` 里等运行中的应用自行退出，超时才树杀，`dshQuitGraceSeconds` 为 10 是有意为之。这笔开销只在有人趁应用开着手动启动安装器时才付。应用内更新路径不付——那时应用早已自己退出，真实更新上从 `elevate.exe` 到暂存改名实测 3.36 秒。

载荷的代价来自它的**文件数**，不是体积。同样的 500.9 MB，以 12453 个文件搬运要 5.67 秒，以 10 个文件搬运只要 0.12 秒。**拷贝里 98% 是每文件开销**——创建一个 0.446 毫秒，删除一个 0.151 毫秒——而字节项小到它推出的 4174 MB/s 显然是文件缓存而不是设备。因此压缩设置、以及任何拿字节做交换的手段，在这里什么也买不到。机械盘上两个分量都会涨，但每文件那项涨两个数量级、每字节那项只涨一个，所以同一个分解说明文件数在那里更重要而不是更不重要；而由于移除与解压都受每文件约束，它们的比例会跨介质守恒，即便两个绝对值都成倍放大。

所以杠杆在载荷的文件数，不在移除，也不在这个仓库能触及的其他任何地方。安装器把载荷写了三遍——144 MB 的压缩包从可执行文件里写进 `%TEMP%`，约 500 MB 解压在它旁边，再把约 500 MB 拷进安装目录，两者不同卷时还是跨卷。这是上游的设计：`extractAppPackage.nsh` 为原子性而暂存到 `$PLUGINSDIR\7z-out`，而 blockmap 差量下载正是对那个 7z 包计算的。`APP_BUILD_DIR` 那条用 `File /r` 直写 `$OUTDIR` 的一次写入路径只对 portable 目标开放（`NsisTarget.js`），没有可替换解压的钩子，而本仓库不改上游。

下载已经被解决了，同样不是该看的地方。一次真实的 rc.12 → rc.13 更新报告 `Full: 142,014.31 KB, To download: 1,521.69 KB (1%)`——72 个变化块，从提示到「下载完毕」十秒。

## 两次测错

**观测器比它观测的东西还贵。** 最初的计时来自每 400 毫秒对安装目录做一次 `Get-ChildItem -Recurse -File` 采样。对这个载荷，一次这样的遍历要约 530 毫秒，于是观测器以 **133% 的占空比**、背靠背、毫无空闲地压在安装器正在写入的那棵树上。它把文件拷贝阶段报成 35.4 秒，而同等工作的真实耗时是 5.71 秒——**虚高约六倍**，而且恰恰在安装器最受文件数约束的地方最严重。输出里没有任何看起来不对的地方：阶段顺序合理，轮次之间离散度也小。

**隔离测量用更快的工具替代了真实实现。** 第二次尝试彻底去掉观测器，改为单独给各阶段计时：解压用 `7z.exe x`，拷贝用 `robocopy /MT:1`，各三轮，离散度很小。合计 22.52 秒，而安装器完成同样工作实际要 53.56 秒——**偏低 2.4 倍**。`7z.exe` 多线程解压 LZMA 而 `Nsis7z` 不会；`CopyFiles` 是 `SHFileOperation`，带着 `robocopy` 没有的每文件 shell 开销；而写 144 MB 压缩包用掉的 0.03 秒是文件缓存，不是磁盘。这个错误比前一个更危险，因为重复轮次之间的低方差读起来像是精确，而数据里没有任何信号提示「被测的东西不是发出去的东西」。

两者共同违反的规则是：**安装计时要么测的是真安装器，要么它是一个下界并且必须说明。** 用等价操作替代真实实现，替代本身就是一个误差项，而它不会出现在方差里。

## 怎么重新测

给安装器本身计时，并且只通过常数时间的调用去观察它——某个进程 id 是否存在，以及它的对话框里的静态控件写着什么。两者都是亚毫秒。枚举窗口从来不是问题，遍历安装目录才是。

```
launch installer → mark "process launched"
poll every 250 ms:
  process matching 'DSH Desktop Setup*' present?  → read its #32770 child Static texts
  text changed?                                   → mark it
  process gone, app process back?                 → mark and stop
```

两个测量脚本就放在打包流水线旁边：`apps/desktop/scripts/measure/time-run.ps1` 按上面的方式给一次安装或卸载计时，`apps/desktop/scripts/measure/shape.ps1` 是每文件／每字节的拆分。两者都没有接进任何闸门——需要数字时手动跑，这就是它们全部的契约。

该引用的区间是「正在安装」页到「完成」页之间那一段。之外的一切都是操作者在决定什么时候点击，而在上面记录的两次运行之间，这部分相差了 30 秒。

绝对值是暖缓存下的：载荷几分钟前刚被读过，而且安装本身无论如何都要读回它刚写进 `%TEMP%` 的东西，所以只有对安装器的首次读取对冷缓存敏感。真正的冷数据需要先重启，本次没有取。

## 备选方案

**优化移除。** 引出这个问题的那个改动。58.72 秒里的 5.16 秒，最多能赢 8.8%，实际远少于此——那个区间的大部分是旧卸载器在做注册表与快捷方式的工作，无论如何都得发生。

**跳过卸载，直接覆盖解压。** `CopyFiles` 本来就是就地覆盖，删除完全可以省掉。否决：新版本不再提供的文件会持续累积，而 `resources/server` 下陈旧的原生模块是真会出故障的问题，不是整洁与否的偏好。它只值约 2 秒。

**消除临时暂存。** 按隔离测量值 8.9 秒——除解压本身之外最大的单项。拿不到：没有钩子，替代路径只对 portable 开放，上游不改，而且暂存正是解压原子性与差量下载得以成立的前提。

**提升嵌套的 `node_modules`。** 曾被当作体积杠杆考虑，于是去量而不是去假设：嵌套树里约 1560 个文件中，1059 个是 `@mistralai/mistralai`，它在别处根本不存在；而被检查的五个重复包，**每一个都与顶层的同名包版本不同**——它们嵌套是因为必须嵌套。提升省下零个文件、零秒。它仍然值得做，但那是为了 [MAX_PATH 的余量](../bug-fix/2026-08-19-windows-update-max-path-uninstall-loop.zh.md)，是另一个问题。

## 影响

移除路径维持原样，而将来若有读者觉得「全删再全解压」很浪费，手上有一个数字说明浪费了多少：8.8%，其中大部分还不是删除。

载荷的文件数是长期存在的杠杆，也是这个仓库唯一能控制的那个。12452 个文件里有 12426 个是内嵌的服务端闭包；其中 11008 个（89%）是第三方包，1417 个是本仓库自己的——后者已经被 tsdown 打成每包两三个文件。流水线今天裁掉了 19274 个文件，再往下就是打包结构改动而不是调参，[把闭包里的第三方树收敛掉](../architecture/2026-08-19-self-contained-desktop-closure.zh.md)才是剩下那个数量级所在。

趁应用运行时手动启动的安装会多付约 11 秒，而应用内更新不会。那是进程清扫的宽限期，是「不粗暴杀死运行中的应用」换来的，属于有意的取舍。

不存在冷缓存下的数字。这里的数据是暖缓存那一档，对更新而言这是常见情形，但对一台刚开机的机器上的首次安装不是。
