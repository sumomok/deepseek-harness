# Agent Note: 基准推进时保留精确登记的历史上游合并

Status: implemented

[English](2026-11-16-bounded-historical-upstream-merges.md) | 中文

## 问题

[合并式补丁线](2026-09-24-merge-based-core-patch-line.zh.md)只在未发布上游合并的第二父精确等于当前声明的基准提交时接受它。推进基准后，先前已接受的合并仍留在第一父链上，却既不匹配新声明，也没有对应的发布 tag。重写合并会替换既有历史；把新基准的每个祖先都视为上游发布，又会接受未登记的合并。

## 决策

[历史上游合并清单](../../../../.claude/core-patches-upstream-merges.json)独立于[缺失 trailer 的历史身份](2026-11-13-bounded-historical-patch-identities.zh.md)，登记这一项既有批准。版本 1 格式要求一个截止点和恰好一项条目，包含完整小写的合并提交、其精确的第一父与上游父提交，以及非空理由。提交身份也约束 Git 标题与树，因此清单不需要标题字段。未知字段、解码后重复的键、错误标识及额外条目都会导致解析失败。

在声明的补丁线上，截止点必须是真实提交且位于 HEAD 的第一父链上。获批合并必须在该链上严格早于截止点，并且恰有登记的两个父提交。其上游父提交必须是当前声明基准的祖先。即使获批合并离开当前比较范围，这些检查仍执行。只有逐项登记的完整合并身份获得例外；祖先关系本身不授予任何批准。检查器不自动追加批准或推进截止点。

本决定部分取代了「基准推进后，每个历史未发布合并都必须有真实发布 tag」的旧规则。发布合并、精确的当前基准合并、树不变的接续、普通 trailer 与路径认领均保留原有规则。身份与合并线记录继续在役，因为它们仍拥有这些独立约束；固定的缺失 trailer 清单不变。

清单不存在时不授予例外。格式错误或不可读的清单在按分支跳过之前即失败。仓库引用检查器使用同一严格解析器，只豁免截止点以及条目中合并、第一父与上游身份对应的字符串 token。理由、其他文件和无效清单仍受检查，Unicode 转义文本也不例外。

## 考虑过的替代方案

**接受第二父是基准祖先的任意合并。** 这会授权每个未登记的祖先，而非保留那一项既有批准。第一父截止点只限制登记资格，本身不授予批准。

**伪造发布 tag、重写既有合并，或用树不变的接续替换它。** 这些做法会歪曲上游发布身份或改变既有历史，而不是登记那一项已接受的精确合并。

**复用缺失 trailer 清单。** 它只为已有且完全没有 trailer 的非合并提交提供 slug。合并批准改变的是另一条规则，因此拥有独立的格式、解析器与 Git 校验。

**让整个清单免于仓库引用检查。** 文件级豁免也会藏起理由中的哈希与组织 URL。精确的语法 token 豁免保留了这些检查。

## 后果

基准推进可以保留显式批准的历史合并，同时仍拒绝后续话题合并、其他上游祖先与 octopus 合并。扩大单项格式或移动截止点是需要审查的独立规则变更。测试通过临时 Git 仓库覆盖有效推进、未登记祖先、话题合并、错误父提交、截止点违规与 octopus；解析器和引用测试覆盖格式错误及转义输入。本例外没有完全取代任何在役记录，因此既有身份、历史身份与合并线三件套继续在役。
