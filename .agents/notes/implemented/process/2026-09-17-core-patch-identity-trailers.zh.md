# Agent Note: 核心补丁的身份是提交 trailer 里的 slug，不是提交哈希

Status: implemented

[English](2026-09-17-core-patch-identity-trailers.md) | 中文

## 问题

本 fork 在上游源码之上维护一条补丁线，登记在 `.claude/core-patches.md`。此前每条记录都用提交哈希标识自己的补丁：标题上带一个，逐轮小节里带该轮重放、退役、适配的每个提交的哈希。

哈希活不过这条线自身的维护动作。每轮滚动同步都把整条线变基到新的上游基座，重写它的全部提交，因此记录点名的每个哈希都在它描述的补丁移动的那一刻作废。对上一轮登记实测：它点名的 284 个哈希里，只有 72 个能解析成当时那条线上的提交；其余分别指向已退役分支、更早的补丁线或上游。读登记的人分不清哪个是哪个。

上游随后关上了剩下的那扇门。`scripts/verify-repository-references.ts` 在每个维护中的受版本控制文件里，拒绝任何能解析成本仓提交对象的十六进制串，提示是「use release tags or maintained repository links」。仅登记一份就占 267 行命中，其余来自四份 fork Agent Note 与一处源码注释。给该门禁加 `.claude/` 排除项的做法经评估后否决，理由见下。

## 决定

**补丁族的身份是一个 kebab-case slug**，全线唯一，由补丁标题派生。线上每个提交带且只带一条 `Patch: <slug>` trailer。登记按 slug 组织：每族一个 `## <slug> — <标题>` 小节，承载它一贯承载的五要素——改了什么、为什么、要达到的效果、退役条件，以及状态与所在线。

trailer 能活过变基，因为它是提交信息文本，`git rebase` 原样带过。因此 `git log --format=%(trailers:key=Patch,valueonly)` 跑在登记声明的范围上，任何一次变基之后都能列出这条线的补丁族——前提是那条声明指向本线当前坐落的那个合并提交。

**指向历史的写法按上游门禁的要求来。** 指向 fork 的改动写它的 slug，或写相对链接指向它的 Agent Note。指向上游的改动写上游 PR 号或发布 tag。

**`scripts/verify-core-patches.ts` 双向核对两侧。** 对声明的基座合并之上的每个提交：恰有一条 `Patch:` trailer，且它的值是登记里的 slug。对登记里状态为 `在役` 或 `局部退役` 的每条记录：线上至少有一个提交点名它。两个方向一起跑，因此改名一个 slug 会在两侧同时失败，而不是悄悄把一族拆成两条记录。门禁已登记进 `doc-sync`。本线的基座由登记里的第二条声明 `**基座合并**：#<号>` 给出，解析成 HEAD 自己的历史里唯一一个标题以 `Merge pull request #<号> ` 开头的 merge 提交，没有任何远端跟踪引用参与。浅克隆的截断历史够不到那个 merge，门禁打印 `skipped` 并退出 0，而不是猜一个基座。

## 备选方案

**给引用门禁的排除前缀加 `.claude/`。** 一行改动，登记继续用哈希。否决：这保住的是一个被本线自己的变基每轮摧毁一次的身份，上面那次实测就是代价——登记里四分之三的哈希早已不指向线上任何东西。而且该门禁会被永久打上补丁，因为 fork 有长期保留这条排除的理由。

**保留哈希，每次变基后重新解析。** 可以写脚本用 `git range-diff` 把旧哈希映射到新哈希并改写登记。否决：它给每轮同步加了一个失败方式静默的改写步骤（映射漏掉一条，留下的陈旧哈希仍能解析，只是指向错误的提交），而且它并不回答上游那道门禁——无论哈希是否最新，门禁都拒绝。

**用分支名标识补丁。** fork 本来就按功能命名分支。否决：分支在落地后删除，而一族的提交往往分散在好几轮的好几个分支上。

## 影响

补丁身份现在能活过定义这条线维护方式的那个操作，而线与登记不一致会成为门禁失败，不再依赖读者自己发现。`git log --grep` 对该 trailer 即可在任何基座上回答「哪些提交属于这条补丁」。

代价是登记不再记录哪个提交做了哪处改动。这个事实此前在实践中也拿不到——它在下一次变基时就过期了；确需点名某处具体改动时，由该补丁的 Agent Note 用散文点名。

线上每个提交都必须带 trailer，包括一行的文档订正；没有 trailer 的提交会被门禁拒绝。新增一族意味着要在它的第一个提交落地之前先加好记录，否则门禁会因未登记的 slug 失败。

## 复核后修订

**门禁有四处会放行真错误的口子，均已封上。** 它在任何分支上都直接取 `upstream/master..HEAD`，而它本身挂在 `doc-sync` 上：对同一个引用实测，`upstream/master..origin/develop` 是 631 个提交、其中 57 个 merge、零条 trailer 且本就不该有，所以这条线一并进去的当天，`doc-sync` 在别的分支上就会全红。现在它读登记声明的补丁线，与 checkout 所在分支比对，不相等即 `skipped`。它对 `upstream/master` 只验引用是否存在、不验它是不是本线的基座，引用过期会静默扩大范围、把上游自己的提交报成 trailer 违规；改成与 `git merge-base` 比对是错的修法，已在下面换掉。它手写的 trailer 扫描逐行读全文，于是「不在最后一段的 `Patch:`」在门禁这里通过、而 `git interpret-trailers` 根本看不见；小写 key git 读得出、门禁却报零条；正文里行首引用的一行示例被算成第二条 trailer——而讲这条约定的提交恰恰长这样。现在由 git 自己读 trailer。最后，不匹配记录格式的标题原先被静默忽略，一个半角连字符就能让整条记录连同「该补丁是否还在线上」这项检查一起蒸发。

另有两项是缺失而非损坏。登记标为退役、提交却仍在线上——登记宣称补丁已撤、代码不同意——原先不产生任何违规，现在会；merge 提交同理，现在有自己的违规文案，明说补丁线必须线性。

**基座不能从 `upstream/master` 推。** 第二轮复核实测了这种推断的后果。它前进（每次 `git fetch upstream` 之后的常态，上一轮的基座距当时的 `upstream/master` 有 666 个上游提交）时门禁失败，而 git 实际读到的范围完全正确——下一次 fetch 落地就会让本线的 `doc-sync` 与 `test:docs` 变红，而提示给的两条出路里「fetch」只会更红。它落后于真实基座时仍是 HEAD 的合并基座，基座判据照样接受它，范围撑到上游自己的提交上，门禁随即把那些提交报成 `trailer-count` 与 `merge-commit` 违规而失败——上一段描述的那个症状只是从基座判据挪到了违规清单，并没有被封上。基座现在由登记的声明给出、在 HEAD 自己的历史里解析，不读任何远端跟踪引用。同时封上四种读错登记的方式：围栏代码块里的声明格式示例会替换掉门禁实际比对的那条线，还打印 `skipped` 退出 0；CRLF 落盘会让全部记录蒸发且不产生任何违规；重复的声明行静默取第一条；以及 git 收下、slug 格式不收的 trailer 值——git 来者不拒，包括折行续写出来的值——会被当成 slug，并把一条发现拆成两行报告。

**门禁在 CI 里结构性地没有牙。** 它不再需要 upstream remote，但 `ci.yml` 只在 `pull_request` 上跑，`actions/checkout` 在该事件下留下的是 detached HEAD，`ci-master.yml` 的 push 触发只在 `master` 上跑：两条在各自的触发下都走到分支这条 skip。`ci-master.yml` 另可 `workflow_dispatch`，在补丁线上手动触发时按分支名全深度检出，门禁在那里是真比对的。漏 trailer、漏登记、slug 改名，只有在补丁线分支上跑 `doc-sync` 的人能抓到，否则抓不到。发布 tag 不能当替代基座：它是 `upstream/master` 的祖先而不是 `upstream/master`，拿它当基座会把上游自己的提交报成本线的违规。登记的身份规则一节写明了这条后果。

**登记重写删掉的不只是哈希。** 它同时整体删掉了八个章节、414 行——七个滚动同步轮次，外加一份稳定红的记录——而提交信息没有说。其中大部分是下一次变基就作废的逐提交历史。但有一部分在全仓没有第二个归宿：三项基座环境敏感的稳定红与「不修只记录」的决定、两次重落前风险预审、每轮都适用的冲突解决规则、三方核对脚本的四处已知盲区，以及旧会话可读性预审的做法。这些已恢复为登记的 `历史轮次` 一节，逐轮提交清单有意不恢复。
