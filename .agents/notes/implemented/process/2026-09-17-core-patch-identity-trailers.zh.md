# Agent Note: 核心补丁的身份是提交 trailer 里的 slug，不是提交哈希

Status: implemented

[English](2026-09-17-core-patch-identity-trailers.md) | 中文

## 问题

本 fork 在上游源码之上维护一条补丁线，登记在 `.claude/core-patches.md`。此前每条记录都用提交哈希标识自己的补丁：标题上带一个，逐轮小节里带该轮重放、退役、适配的每个提交的哈希。

哈希活不过这条线自身的维护动作。每轮滚动同步都把整条线变基到新的上游基座，重写它的全部提交，因此记录点名的每个哈希都在它描述的补丁移动的那一刻作废。对上一轮登记实测：它点名的 284 个哈希里，只有 72 个能解析成当时那条线上的提交；其余分别指向已退役分支、更早的补丁线或上游。读登记的人分不清哪个是哪个。

上游随后关上了剩下的那扇门。`scripts/verify-repository-references.ts` 在每个维护中的受版本控制文件里，拒绝任何能解析成本仓提交对象的十六进制串，提示是「use release tags or maintained repository links」。仅登记一份就占 267 行命中，其余来自四份 fork Agent Note 与一处源码注释。给该门禁加 `.claude/` 排除项的做法经评估后否决，理由见下。

## 决定

**补丁族的身份是一个 kebab-case slug**，全线唯一，由补丁标题派生。线上每个提交带且只带一条 `Patch: <slug>` trailer。登记按 slug 组织：每族一个 `## <slug> — <标题>` 小节，承载它一贯承载的五要素——改了什么、为什么、要达到的效果、退役条件，以及状态与所在线。

trailer 能活过变基，因为它是提交信息文本，`git rebase` 原样带过。因此 `git log --format=%(trailers:key=Patch,valueonly) upstream/master..HEAD` 在任何时刻、任何基座上都能列出这条线的补丁族。

**指向历史的写法按上游门禁的要求来。** 指向 fork 的改动写它的 slug，或写相对链接指向它的 Agent Note。指向上游的改动写上游 PR 号或发布 tag。

**`scripts/verify-core-patches.ts` 双向核对两侧。** 对 `upstream/master` 之上的每个提交：恰有一条 `Patch:` trailer，且 slug 在登记里。对登记里状态为 `在役` 或 `局部退役` 的每条记录：线上至少有一个提交点名它。两个方向一起跑，因此改名一个 slug 会在两侧同时失败，而不是悄悄把一族拆成两条记录。门禁已登记进 `doc-sync`。没有 `upstream/master` 引用时——浅克隆，或没有配置上游远端的检出——这条线的范围未知，门禁打印 `skipped: no upstream/master ref` 并退出 0，而不是猜一个基座。

## 备选方案

**给引用门禁的排除前缀加 `.claude/`。** 一行改动，登记继续用哈希。否决：这保住的是一个被本线自己的变基每轮摧毁一次的身份，上面那次实测就是代价——登记里四分之三的哈希早已不指向线上任何东西。而且该门禁会被永久打上补丁，因为 fork 有长期保留这条排除的理由。

**保留哈希，每次变基后重新解析。** 可以写脚本用 `git range-diff` 把旧哈希映射到新哈希并改写登记。否决：它给每轮同步加了一个失败方式静默的改写步骤（映射漏掉一条，留下的陈旧哈希仍能解析，只是指向错误的提交），而且它并不回答上游那道门禁——无论哈希是否最新，门禁都拒绝。

**用分支名标识补丁。** fork 本来就按功能命名分支。否决：分支在落地后删除，而一族的提交往往分散在好几轮的好几个分支上。

## 影响

补丁身份现在能活过定义这条线维护方式的那个操作，而线与登记不一致会成为门禁失败，不再依赖读者自己发现。`git log --grep` 对该 trailer 即可在任何基座上回答「哪些提交属于这条补丁」。

代价是登记不再记录哪个提交做了哪处改动。这个事实此前在实践中也拿不到——它在下一次变基时就过期了；确需点名某处具体改动时，由该补丁的 Agent Note 用散文点名。

线上每个提交都必须带 trailer，包括一行的文档订正；没有 trailer 的提交会被门禁拒绝。新增一族意味着要在它的第一个提交落地之前先加好记录，否则门禁会因未登记的 slug 失败。
