# Agent Note: Place the served UI's downloads instead of asking

Status: implemented

English | [中文](2026-09-03-desktop-download-handling.zh.md)

## Problem

Users reported that exporting a session log from the desktop client 「导出日志无法导出成功」.

[`dsh-session-log-export`](../../../../packages/session-query/session-log-export/README.md) exports a session tree as a ZIP over `GET /api/session.export?sessionId=…`, answered with `Content-Disposition: attachment`. Its browser half preflights with `HEAD`, hands the GET URL to a detached `<a download>`, and immediately reports 「Session 导出已开始下载」 — everything after that hand-off is the browser download manager's job, which the package's README states as a deliberate boundary: a descendant or attachment failure after the GET is accepted is reported by the download manager, not by the dialog.

The desktop window is a browser surface with no download manager behind it. [`apps/desktop/src/main.ts`](../../../../apps/desktop/src/main.ts) registered `setWindowOpenHandler` and `will-navigate` on the app window and nothing else; the only two `will-download` handlers in the shell belong to the hidden render window and the login window, each on its own ephemeral partition, and neither covers the default session the app window runs in. Electron's default routine therefore ran: a modal Save As sheet, over a page that had already declared the download started, naming a file the user had not asked to name and explaining nothing about where it came from. Dismissing the sheet dropped the export in silence while the page still read as success, and a transfer that failed mid-stream had nowhere to report at all — the role the upstream README hands to a download manager that does not exist here.

## Decision

The shell places what its own server serves, and leaves everything else alone.

[`apps/desktop/src/download-policy.ts`](../../../../apps/desktop/src/download-policy.ts) holds the whole decision as a pure function. `decideDownload` reads `DownloadItem.getURLChain()` and answers `{ kind: 'save', path }` or `{ kind: 'default', reason }`. Every hop of that chain must belong to the embedded server's origin — `ServerHandle.url`, which is an origin and nothing else — because the URL a transfer ended on says nothing about where it began: a download that starts at another site and redirects into the server is not the shell's to place, and one that starts at the server and redirects out of it is no longer the server's file. An empty chain is not served either.

Each hop's origin comes off the parsed URL rather than a scheme test, which is what makes the policy survive the export's own evolution: a `blob:` URL resolves to the origin of the page that minted it, so a page that fetches its own bytes with a progress bar and hands the result to an `<a download>` is downloading from itself and is placed on the same terms as a direct `/api` URL. `data:`, `about:`, `file:` and an opaque `blob:` all parse to the origin `null`, which no server origin can equal, so none of them is ever taken over.

The saved name is the download's own suggestion reduced to its last path segment, joined onto `app.getPath('downloads')`, and uniquified by `uniquePath`: ` (2)`, ` (3)` … inserted before the last dot-suffix, so `session.tar.gz` numbers as `session.tar (2).gz` and `.zshrc` as `.zshrc (2)`. A name is taken when it is on disk **or** when this process already gave it to a transfer that has not finished — the `claimed` set the shell passes in. The export's filename is derived from the session id, so two gestures on one session suggest the same name, and nothing is on disk under it until the first transfer writes its first byte; without the claim the second download would be handed the first one's path and overwrite it. The search is bounded, and a directory that holds every candidate yields `{ kind: 'default', reason: 'no-free-name' }` rather than a path that is already a file — the one thing worse than a sheet is an overwrite. Chromium sanitizes `DownloadItem.getFilename()` before the shell sees it; the policy strips separators and bare `.`/`..` segments again anyway, because it is the only step between a suggested name and a written path and has to hold on its own reading.

`main.ts` wires that decision into `createBootWindow`. `attachDownloadHandling` registers `will-download` on `window.webContents.session` — the default session, since the app window declares no partition — sets the save path on a `save` decision and adds it to the claim, and returns untouched on a `default` one, which leaves Electron's sheet exactly where it was. A `default` for another origin is the ordinary case and says nothing; a `no-free-name` writes `[desktop] download left to Electron: <filename> (no free name under <dir>)`, so the sheet the user then sees has a reason in the file they are asked to send. The listener is removed on the window's `closed` event: the session outlives the window, and macOS destroys and recreates the window on every trip through the Dock, so a listener left behind would accumulate one copy per trip. On `done` the claim is released, and `reportDownload` writes one line to the `dsh-server.log` sink — `[desktop] download saved: <path>`, or `[desktop] download cancelled|interrupted: <path>` — and announces the outcome.

The announcement goes through a second entry point in [`apps/desktop/src/notifications.ts`](../../../../apps/desktop/src/notifications.ts). `announceDownload` differs from the module's existing `announce` in the two ways a download needs: it posts on macOS as well, because a Dock badge carries neither the file's name nor a way to reach it, and it posts whether or not the window is attended, because the page says only that the download started and where it went is said here or nowhere. Clicking a completed notice calls `shell.showItemInFolder` on the saved path. Only the interrupted notice names a remedy — 「传输中断,请重新导出」 — since a transfer the user cancelled needs no instructions. The badge-and-bounce split for attention events is unchanged, and the module's own documentation now scopes itself to those.

[`apps/desktop/electron-builder.yml`](../../../../apps/desktop/electron-builder.yml) gains a `mac.extendInfo` block carrying `NSDownloadsFolderUsageDescription` in Chinese, matching the app's other user-facing strings. macOS gates `~/Downloads` behind TCC and raises its own consent prompt on the first write there; without the key the prompt names no reason. This is the file's first Info.plist string of any kind — the app declares no camera or microphone usage — so the block is new rather than extended.

## Testing

[`apps/desktop/tests/download-policy.spec.ts`](../../../../apps/desktop/tests/download-policy.spec.ts) covers the decision: a same-origin `/api` URL and a same-origin `blob:` URL are both placed; another port, another host, another scheme, a cross-origin `blob:`, and `data:`/`about:`/`file:`/opaque-`blob:` are all left to Electron; a chain that enters the server from elsewhere and one that leaves it are both refused while a two-hop chain inside the server is placed, and so is an empty chain; the suggested name is reduced to its last segment and falls back to `download` when it is only path syntax; the uniquifier counts from 2 past names on disk, names an unfinished transfer holds, and both together; and a predicate that answers true for everything yields `no-free-name` rather than an occupied path.

[`apps/desktop/tests/notifications.spec.ts`](../../../../apps/desktop/tests/notifications.spec.ts) covers `announceDownload` against a stand-in `electron`, because the promise it carries — a click that reveals the saved file — is a callback no log line can show: a completed notice registers a click that calls `shell.showItemInFolder` with the saved path, a failure notice registers no click at all, and a platform reporting no notification support gets none constructed.

The Electron half — which session the handler lands on, and whether the sheet is really gone — cannot be reached from a unit test and is covered by a real-process check instead: the built shell driven under Electron 43 against a scratch `$DSH_HOME`, clicking the session header's 「Session 日志」 button and reading the resulting file and log lines.

## Alternatives considered

**Keep the sheet and relabel the page's toast.** The honest version of "the browser will take it from here" on a shell with no download manager is to say something else, but the string belongs to an upstream package that has no way to know it is running inside a shell. Fixing it there means inventing a shell→page marker — an injected global, a header, a served capability flag — so the browser half can render a second wording. That is a new cross-boundary contract for a worse outcome: the user still gets a modal sheet nobody asked for, and a mid-stream failure still has nowhere to report.

**Intercept every download regardless of origin.** One handler for all downloads is simpler and removes the origin comparison entirely, but the window can reach any origin its page links to, and silently writing a file from an arbitrary site into the downloads folder without a prompt is a decision this shell has no standing to make. Restricting the takeover to the server the shell started itself keeps the new behavior inside what the shell already owns.

**Put the decision inline in the `will-download` handler.** The handler already has `item` and `app` in scope and the branch is short. Keeping it inline would leave the origin comparison, the sanitizer, and the uniquifier reachable only through a real Electron session — exactly the code that has to be exercised against `blob:`, `data:`, and collision cases, none of which a real-process check can enumerate.

**Reuse `announce` for the notice.** It already exists and already logs. It also suppresses itself while the window is focused, which is precisely when an export is clicked, and on macOS it posts a Dock badge with no text — so the file's name and location, the only content of the message, would never be shown.

**Ask once and remember a download folder.** A remembered folder is state to store, a settings surface to expose, and a migration when it moves. The system downloads folder is where a browser would have put the file, which is the behavior the page's own wording promises.

## Consequences

Users lose the location picker. A download from the embedded server lands in the system downloads folder with no way to redirect it from the shell, and the file must be moved afterwards. In exchange the upstream toast is true on the desktop for the first time: 「Session 导出已开始下载」 is followed by a download that actually completes, and by a notification that names the resulting file and reveals it. Both platforms behave the same way — the same folder, the same numbering, the same notification with the same click target — which is a departure from the deliberately platform-split handling of attention events in the same module.

Whether the macOS consent prompt appears with the new description was not verified on a signed build; the key is declared, and the real-process check ran against an unsigned development shell whose TCC identity is not the packaged app's. A packaged build is the only place that can confirm it.

Two facts found during the diagnosis are recorded here and not fixed. Three sessions in the reporting user's store still fail export with HTTP 500: they carry a custom `permissionRules/decision` event written by an old build of `@haoran/dsh-llm-permission-gateway` that never marked it `ignorable: true`, so the log refuses to load with `SessionFormatUnsupportedError` and the ZIP never starts. That is the plugin-audit rule in the fork's own standing orders — a third-party plugin's custom session events must be `ignorable: true` or they brick session logs on uninstall — reaching a user, and it is the plugin's to fix, not the shell's. Separately, the upstream archive names its media entries `media/sha256:<hex>.<ext>`; the colon is legal in a ZIP entry name and illegal in a Windows filename, so a Windows extractor either refuses those entries or rewrites them. Both are upstream or plugin defects that the shell's download handling neither causes nor hides.
