# Agent Note: 座位放弃过的调用要能重新接手

Status: implemented

[English](2026-09-03-content-seat-claim-restart.md) | 中文

## Problem

一台运行中的控制台，在大约 400 次调用里有 33 次把 `content_read` 与 `content_act` 答成「没有打开的控制台在展示这个会话的内容栏」，而控制台自始至终就摆在用户眼前。那份会话日志里的一条时间线排除了除「座位自己的竞领」之外的所有解释：

```
11:04:23.502  tool/call         content_act call_00_Q1rG…
11:04:23.504  approval/asked
11:05:02.385  approval/decided  allowed-once
11:05:05.397  tool/result       "No open console … (waited 3s)"
11:05:07.653  tool/call         content_read
11:05:07.941  tool/result       the page, read in 288ms
```

用户就在控制台前——审批是他点的——标签页连着、座位活着、宿主的等待也开着；而这次调用一次价都没出过，五秒后的新调用却 288ms 就答完了。宿主一侧逐跳走过，是干净的：投影折叠让这次调用在整整 41.9 秒里一直留在 pending，API 代理向每一个消费者广播、不按会话过滤，客户端不管会话有没有实例化都会应用投影帧，反向代理更是一条 4xx/5xx 都没记。

座位把「已经接手的调用」记在 `started` 里，于是再怎么重渲染也不会把一次调用变成两次认领。有两条路会把一个仍然开着的调用的 id 留在这个集合里：

- `started` 的修剪站在 effect 自己的两道 guard 后面。标签页不可见时——macOS Chrome 会把被遮挡的前台窗口报成 hidden——或者部署没配 `pageAccess` 时，修剪根本不再发生。此时待办列表只要有一帧抖空，竞领循环就会放弃，而 id 留在原地；等标签页回来、调用还在列表上，它被永久跳过。
- `claimRead` 一旦放弃，`answer` 就直接返回、不归还 id——被路由拒绝的出价、被别的标签页拿走的认领、离开了列表的调用、十分钟上限。这几种结局，调用都仍然在宿主那儿等着。

`content_act` 最容易同时踩中两条：它要等有人答完审批才登记等待，于是竞领窗口有用户拿主意那么长。

## Decision

放弃不等于回答。`started` 的修剪提到两道 guard 之前，`claimRead` 返回 undefined 时 `answer` 把 id 归还。只有「座位正在做这次调用」期间才记住它；否则下一帧带着这次调用的投影，就是座位重新出价的那一帧。

## Alternatives considered

**用定时器清 `started`。** 待办列表本来就说明了调用开没开着；换成时钟，要么给已经结算的调用重新出价，要么坐过宿主自己的窗口——这与「在 `claimTimeoutMs` 就放弃」是同一个错误，那个错误上一次修复已经去掉了。

**在 `claimRead` 内部重投，而不是返回。** 它那几个出口是不同的事实：拒绝了这次出价的路由也会拒绝下一次，被别的标签页拿走的调用不属于这个座位。知道「调用还在不在列表上」的是 effect 那一半，所以重试属于那里。

**只在标签页可见时修剪，改为在卸载时遗忘。** 座位卸载时 `started` 本来就随它一起没了；出问题的恰恰是「一直挂着、中间隐身了一段」的那个座位。

## Consequences

- 被拒过一次、或在标签页离开期间丢掉的出价，现在的代价约 200ms，而不是整次调用。
- 这个重试不是自触发的：在 `answer` 里删掉 id 并不会让 effect 重跑，所以重新出价要等下一帧投影。现场每次工具调用都会产生一帧，够用；而投影帧已经停了的调用，仍然以宿主自己的超时收尾。
- 让待办列表抖空的那个写入方没有钉死。客户端运行时里有好几个写入方都做得到——删掉某个投影存储、当前会话在索引里短暂缺席、刷新摘要时整体替换列表。值得单独查一次；这次改动界住的是「抖一下要付多少代价」。
- **可见性闸门仍然是单边否决，这次不改。** `document.visibilityState` 是 `hidden` 时座位什么都不认领，而 macOS Chrome 会把被遮挡的前台窗口报成 hidden——于是唯一开着的那个控制台什么都不答，模型收到的是「没有打开的控制台」，指向的是错的东西。改法是把可见性从否决改成优先，与宿主自己的 `PREFERRED_TAB_WINDOW_MS` 挂起同一个思路：不可见的座位在一个宽限窗口之后照样出价，让可见的标签页永远先赢。这次不做，因为它要改写一条已经写进文档、也有测试的行为，值得自己一篇 Note。触发条件：这次修复之后，仍有用户在控制台就摆在屏幕上的情况下收到「没有打开的控制台」；或者出现「同一会话开两个控制台、优先级真的决定了结果」的部署。

## Testing

`packages/experimental/content-frame/tests/content-read-executor.client.spec.tsx` 里两条用例，改动前红、改动后绿：一条是标签页隐身期间被放弃、标签页回来后重新出价；一条是出价被路由以 403 拒绝、下一帧投影为它重新出价。两套 executor 套件原有的每一条用例都没有改动。
