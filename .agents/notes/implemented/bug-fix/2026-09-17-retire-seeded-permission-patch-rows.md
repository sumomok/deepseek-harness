# Agent Note: The permission rows an old shell copied into the desktop profile are retired

Status: implemented

English | [中文](2026-09-17-retire-seeded-permission-patch-rows.zh.md)

## Problem

A desktop client running 0.1.0-rc.33 still offers the access modes of 2026-08: 仅可查看 / 工作区内修改 / 完全权限 / 自动审查, in that order, with `yolo-access` described as 沙箱完全关闭，文件系统与命令不再有操作系统层面的围墙…… `@haoran/dsh-llm-permission-gateway` 0.4.3 declares four rows in another order — walls, then no walls but still asked, then no walls and never asked — and its own name and description on the reviewed one. None of that reaches the machine.

The shadowing file is `~/.dsh/profiles/desktop-shell/cordis.patch.yml`, last written 2026-08-27, and it holds a `- id: permission` entry carrying the whole preset table plus a `llm-permission-gateway` row. That second row is an id-targeted `- id: llm-permission-gateway` rather than the package's own `- insert:`, which is the form a layer written against a build that already mounts the plugin takes. A profile's own patch layer is the last layer but one — every bundle layer applies before it — so an id-targeted entry there replaces the row's whole `config` and the plugin's table never takes effect. Nothing in the product takes a row back out of that file: `WITHDRAWN_WEB_BUNDLES` and `web-migration.json` reach bundle names and links, never the patch layer's contents.

The rows are the shell's own leavings, by the route [`copyPristineProfileFile`](../../../../apps/desktop-shell/src/profile-seed.ts) describes. The first sync a `desktop-shell` profile ever runs replaces its still-pristine patch template with the `web` profile's file verbatim, and on this machine the `web` layer was the hand-written one the [2026-08-22 gateway note](../feature/2026-08-22-desktop-builtin-permission-gateway.md) records: `yolo-access` and the gate paired by a comment asking a reader not to separate two blocks. 0.1.0-rc.21 moved both rows into the package (`1229bc8049`, `apps/desktop-server/vendor/haoran-dsh-llm-permission-gateway-0.1.3.tgz`), and six days later the first sync copied the machine's own copy of them into the profile that now shadows the package.

The exact bytes of that machine's file are not in this repository. Before this change landed, nothing in the tree carried the comment that file opens with, and the only files under `apps/` holding those two rows' full bytes were the three vendored gateway tarballs; the shell's own `PROFILE_PATCH_TEMPLATE` has always been the empty `[]` layer. What is recoverable is the 0.1.3 patch layer, whose two entries are field for field what the hand-written pairing declared, and the machine's own header comment paraphrases that file's own.

## Decision

`retireSeededPermissionRows` in `apps/desktop-shell/src/profile-seed.ts` runs once per profile, after `syncWebBundles` so a copy made this launch is retired on the same launch. It reads the profile's patch layer, takes out each entry that is still exactly one of the two rows the 0.1.3 layer declared, and writes the rest back.

Matching is by content, not by file bytes. Each top-level entry is parsed on its own by `js-yaml` under `FAILSAFE_SCHEMA`, and an entry the parse refuses — a tag, a duplicate key, a tab — is left alone.

`js-yaml` is the parser the loader reads a patch layer with. Its schema there is `yaml.JSON_SCHEMA.extend(JsExpr)`: `entryListSchema` in `vendor/include/src/index.ts`, reached as `userPatchesSchema` in `packages/boot/app-boot/src/index.ts`. The failsafe schema is not that schema. It refuses a superset of what that one refuses — `!!js` and every JSON tag, `!!int` and `!!bool` among them — and reads every scalar it accepts as a string, where the loader also resolves `5`, `true`, and `null` as a number, a boolean, and a null. Both differences are safe in this direction: a refusal leaves an entry alone, and every value in the three seeded rows is a plain string the two schemas read identically, so a match here holds what the loader would read there. The difference is therefore not observable through this module's own behaviour, and no test pins it; what the tests pin is that an entry carrying a number, a boolean, or a null still parses and still matches nothing. `44f6132b6d`'s message calls that schema the default one; this paragraph is the accurate statement.

What the parse reads is serialized with every mapping's keys sorted and compared against the two rows, so the same fields with the same values match whatever order they were written in. Order is not part of a copied row's identity — taking the row out is what puts the shipped preset order back.

A removal takes the entry, the comment run written directly above it, and the blank lines directly below it. Everything else in the file — other entries, `!!js` expressions, the owner's own prose — stays byte for byte where it was. A layer holding nothing else becomes the empty template again, and one left holding only comments gains the `[]` those comments annotated, because the loader reads this file as a top-level array. A layer still holding anything else is returned as it stands, so a file whose array was written `[]` rather than as a block sequence does not gain a second top-level node, and every answer ends in exactly one newline.

The gateway row is matched in both forms — the package's `- insert:` and the id-targeted `- id:` — each on the same terms, every field the shipped value. An entry that inserts the gateway beside other rows is recognized as carrying it and never removed, which is all recognition does for a row that is not the seeded one: it earns the skip line that names it. The id-targeted form is not the harmless duplicate it looks like: an id-targeted patch replaces the row's whole `config`, so a copy carrying 0.1.3's `provider` and `model` pins that judge route and drops every `Config` field a later release sets on its own row. A row that differs anywhere is its owner's and stays, with the reason in the log: `skipped cordis.patch.yml: the permission preset table is not the one this shell wrote; left exactly as it is`. The judge route on the gateway row counts — a `model` someone changed makes that row theirs. A removal prints `retired the permission preset table from cordis.patch.yml`, from the new `SeedReport.retired`.

The decision is recorded as `permissionPatch` in `web-migration.json` — `removed`, `kept`, or `absent` — and its presence is what stops a later launch reading the file. A profile with no marker at all gains none here: the marker's existence is what `syncWebBundles` reads as "this profile has synced before", and creating one would suppress the one-time copy of the web profile's own two files. Such a profile is read again next launch, which costs one file read and, in the common case, one comparison against the template: a layer still holding it decides `absent` without being parsed at all, and records that like any other decision.

## Alternatives considered

**Merge the plugin's table into the profile's layer instead of removing the entry.** It would keep whatever else the entry carries. Merging needs a writer as well as a reader — a round trip through the loader's dialect, `!!js` nodes included, that preserves comments — which is the second implementation of that schema `copyPristineProfileFile` declines when it copies a file rather than merging it. Reading one entry to identify it is a much smaller promise than rewriting one.

**Recognize the rows with a hand-written line scanner rather than a parser.** Around 140 lines read mappings, sequences, and simply quoted scalars without a dependency. `js-yaml` is already an `apps/desktop-shell` runtime dependency — `src/theme.ts` and `src/updater.ts` both import it — and is the parser the loader reads patch layers with, so it adds no package, no version, and no asar weight; hand-rolling buys nothing and owes the maintenance. A scanner is also the wrong half of this module to own untested: `apps/` is outside the coverage gate (`vitest.config.ts` includes `packages/*/*/src` only), so no gate makes its refusal branches run, and those branches are what decide whether a user's configuration is rewritten. Where a scanner's rules and the parser's disagree — a block scalar, a value carrying an inline ` #` comment — the parser is right by construction, because it is the one the loader will read that file with.

**Parse the whole file with `yaml` (eemeli) and cut by each node's `range`.** It gives byte offsets per top-level item, which would remove an entry without a line scan of this module's own. It is not resolvable from `apps/desktop-shell` — `yaml` is declared by three `packages/` workspaces, not by this app, so using it means adding a package to the asar. It also loses the per-entry granularity this needs: a duplicate key is a document-level error, and tab indentation yields `UNEXPECTED_TOKEN` with every entry folded into one item whose `range` is truncated, so cutting by that range would destroy the file. Recovering per-entry refusal means slicing and parsing per entry anyway, which is what `js-yaml` does here with no package added.

**Match the whole file against a shipped template, byte for byte.** It is the strictest possible rule and needs no recognizer. It would never fire: the bytes on the machine came from a hand-written `web` layer whose comment wording differs from the package's, and this repository has never held them. A rule that cannot match the one case it exists for is not a conservative rule.

**Stop the first sync from copying the `web` patch layer.** It prevents the next machine from acquiring these rows. It repairs no machine that already has them, and it gives up the copy's whole purpose, which is carrying the owner's own rows across with their plugins.

**Rename the preset id in the plugin so a stale copy cannot target it.** A copy keyed on `yolo-access` would stop shadowing a row named something else. `permission.defaultPreset` is stored under a closed union over this table's names and `SettingsProvider.register` rejects a stored section the schema no longer admits, so the rename makes the whole `permission` settings section fail to install for anyone who stored it — the reason the [四档访问方式 note](../feature/2026-09-17-gateway-four-access-modes.md) keeps the id.

**Remove the gateway row whatever its `config` says.** The row's identity is the plugin name, and the bundle layer declares the row anyway, so the profile's copy adds nothing but a duplicate. `provider` and `model` there are a judge route someone may have chosen deliberately, and this shell has no way to tell a route from a leftover. Leaving an edited row costs a log line; taking one out costs a setting nobody asked to lose.

**Create the marker for a profile that has never synced.** It would stop the per-launch re-read for a hand-edited layer that keeps a row. The marker's existence is a flag `syncWebBundles` already reads, and writing one early suppresses the one-time copy of `cordis.patch.yml` and `pnpm-workspace.yaml` for that profile. The re-read is a `readFileSync` and a string comparison.

## Consequences

A client that copied those rows over gets the shipped access-mode table back on its next launch, with no terminal and no hand-edited YAML, and keeps every other row in its patch layer. A client that edited either row keeps it and is told which one and why, once per launch until a marker exists to record the decision. The machine this was found on loses both rows: its gateway row is the id-targeted form, and every field in it is the shipped value.

`MigrationMarker` gains an optional field. It is a cross-component contract `@haoran/dsh-plugin-updates` reads, so the field is additive, absent until decided, and carried through by both `readMigrationMarker` and the marker `syncWebBundles` writes.

An entry the failsafe schema refuses is left alone, which is the safe direction but means a machine whose copy carries a tag, a duplicate key, or a tab in that entry keeps the shadow and says so in the log rather than being repaired.

## Testing

`apps/desktop-shell/tests/profile-seed.spec.ts` drives every case through `seedBuiltinBundles`, with the two rows staged verbatim from the 0.1.3 patch layer: both removed with the owner's own row and comment intact; the empty template restored when they were the whole file; a `[]` appended when only prose is left; an edited table kept with its skip line while the gateway row beside it still goes; a table whose fields were written in another order still matched; an edited judge route kept; a `!!js/eval` route kept; a marker that already carries a decision read and obeyed with the rows still in the file; a profile with no marker retired without gaining one; a layer still holding the template decided `absent` without a parse; the gateway row retired in its id-targeted form and kept when that form carries a route of its owner's; an unrelated entry whose own comment names the gateway read as no row of this shell's; an edited table named by the id it declares rather than by the gateway its description mentions; one trailing newline left when the removed rows ended the file; no second `[]` added to a layer that already had one; every entry that declares no row id of this shell's left alone, whether it is an empty node, a scalar, a nested sequence, an insert of two rows, or an insert of a row with no id; an entry carrying a number, a boolean, and a null parsed rather than refused; an entry whose own values name the gateway on a key line read as declaring nothing, which is what pins that the text is asked only where the parse refused; an insert carrying the gateway beside another row named in the log and left whole; and the blank lines a layer opened with dropped with the rows under them.
