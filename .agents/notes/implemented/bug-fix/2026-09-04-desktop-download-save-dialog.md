# Agent Note: Ask where an exported session log goes, and show it arriving

Status: implemented

English | [中文](2026-09-04-desktop-download-save-dialog.zh.md)

## Problem

Since [placing the served UI's downloads](2026-09-03-desktop-download-handling.md) the desktop shell has written them itself: a transfer whose whole redirect chain is same-origin with the embedded server goes straight into the system downloads folder under a de-duplicated name, and its outcome is announced with an Electron `Notification` that reveals the file when clicked.

On the reporting user's macOS 26 machine the exports completed and the announcement never arrived. `dsh-server.log` carried both expected lines — `[desktop] download saved: /Users/…/Downloads/dsh-session-session-9ca7767d-….zip` and the ` (2)` one beside it — and both ZIPs were on disk and valid. In the window the export panel said 「导出完成」 and then nothing happened at all. `~/Library/Preferences/com.apple.ncprefs.plist` holds no entry for `dev.dsh.desktop`, so the app was never registered with Notification Centre; `Notification.show()` is a silent no-op there and reports no failure. The only statement the shell made about a download — where the file went — was routed through a channel that posts nothing on that machine.

The invisible report was half of it. The other half is that there was nothing to fall back on, because the same change had also taken the choice away: the file sat in `~/Downloads` under a name the user never saw, and the question they actually asked — 「我文件呢?我选择保存位置呢?」 — had no answer anywhere in the window they were looking at.

## Decision

The shell asks where the file goes, then shows it arriving there. A download it takes over is answered by the shell's own save dialog and by the system file manager, not by a notification.

[`apps/desktop/src/download-policy.ts`](../../../../apps/desktop/src/download-policy.ts) still decides what is taken over, on the same terms: every hop of `DownloadItem.getURLChain()` must belong to the embedded server's origin, which covers the `blob:` URLs the export page mints for itself and excludes originless and cross-origin URLs. What changed is the answer. `decideDownload` returns `{ kind: 'ask', dialog }` rather than `{ kind: 'save', path }`, and `dialog` is the complete `SaveDialogOptions` the handler hands to `item.setSaveDialogOptions`: `title` 「保存文件」, `message` 「保存 `<文件名>`」 — both are set because each reaches one set of platforms, `message` being macOS-only (`@platform darwin` in `electron.d.ts`) — a 「保存」 button, and `defaultPath` in the system downloads folder under the download's own suggested name, still numbered ` (2)`, ` (3)` … past what is already on disk.

**The dialog names the file and constrains nothing about it.** Every attachment the embedded server serves reaches this handler, not only the session-log export. `dsh-better-sidebar`, which [`profile-seed.ts`](../../../../apps/desktop/src/profile-seed.ts) seeds into every desktop profile, answers `/sidebar/file?…&download=1` with `Content-Disposition: attachment` for the file tree's download command, the binary preview and the PDF toolbar — same origin, every hop. Wording that named the export and a `zip` filter would rename all of those: macOS maps `filters` onto `setAllowedFileTypes:` and Electron sets no `allowsOtherFileTypes`, so a panel offered `report.pdf` under a `zip` filter writes `report.zip`. The dialog therefore declares no filter, and carries the file's own name rather than a guess about what it is.

**The dialog replaced the two guards that silent writing needed.** The `claimed` set of in-flight paths is gone: it existed because two gestures on one session suggest the same name and nothing occupies it until the first transfer writes, so the second silent write would have landed on the first one's path. The shell no longer chooses any path — it proposes one, and the user confirms or retypes it — so a name the shell merely offered is not a claim on anything, and the path that gets written is one the shell does not know until the dialog closes. The `no-free-name` outcome is gone for the same reason: it existed so a folder with no free candidate got Electron's sheet rather than an overwrite, and now a full folder simply gets the plain name in a dialog the system guards with its own replace prompt. `DownloadDecision`'s `default` arm therefore carries no reason, and nothing about a taken-over download is written to the log before it ends.

`downloadOutcome` is the second pure function, and it decides all three endings. **Completed** writes `[desktop] download saved: <path>` with the path the user chose and asks for that file to be selected in the file manager — the visible half of the fix, and the one that does not depend on a permission the app may never have been granted. **Cancelled** writes one line and shows nothing: the user dismissed the dialog, which is them declining the download, and a confirmation of a decline is noise. **Interrupted** writes its line and puts up an error box — 「文件没有保存成功」 over 「`<文件名>`:写入失败,请检查保存位置后重试。」 — because a transfer that produced no file is the one ending the user cannot see for themselves. It reads as a write failure rather than a network one: these transfers come off loopback, and the export's bytes are already in the page's memory when its `blob:` download starts, so what can fail after the dialog closes is putting them on disk — a full volume, a location that is not writable, one that went away. A dialog dismissed before any path existed reports an empty `getSavePath()`, so the two failing endings name the download's suggested filename when there is no path to name.

[`apps/desktop/src/main.ts`](../../../../apps/desktop/src/main.ts) is wiring only: it builds the request, sets the dialog options on an `ask`, returns on a `default`, and on `done` writes `outcome.line`, calls `shell.showItemInFolder` when there is something to reveal, and calls `reportDownloadFailure` when there is something to report. That last one attaches the box to the app's own window the way this module's other dialogs do, and does not wait on it: the transfer is over either way, and the `done` handler must not hold the download session open behind a modal. The `NSDownloadsFolderUsageDescription` key in [`electron-builder.yml`](../../../../apps/desktop/electron-builder.yml) stays. macOS gates `~/Downloads` behind TCC, and the shell reaches it twice: the default path is de-duplicated by probing that folder, and Chromium starts writing the arriving bytes into the default downloads directory while the dialog is open (`components/download/internal/common/base_file.cc`, `default_directory`), whatever the user finally chooses.

`announceDownload` and `DownloadNotice` are deleted from [`apps/desktop/src/notifications.ts`](../../../../apps/desktop/src/notifications.ts), along with that module's `shell` import and the paragraph scoping its platform split against them. Nothing else called it, and no download reporting goes through a notification at all. The attention-event half of the module — the Windows toast, the macOS badge and bounce — is untouched.

## Testing

[`apps/desktop/tests/download-policy.spec.ts`](../../../../apps/desktop/tests/download-policy.spec.ts) covers both functions. For `decideDownload`: a same-origin `/api` URL and a same-origin `blob:` URL are taken over; another port, host or scheme, a cross-origin `blob:`, `data:`/`about:`/`file:`/opaque-`blob:`, a non-URL string, a chain that enters or leaves the server, and an empty chain are all left to Electron, while a two-hop chain inside the server is taken; the full dialog — title, message, button, default path, and the absence of any filter — is asserted twice, once for the export's `.zip` and once for a `report.pdf` coming off the sidebar's `?download=1` route, which is what pins the wording and the filter list against a download that is not a session log; the suggested name is reduced to its last segment and falls back to `download`; the offer is numbered past a name already in the folder, and a folder where every candidate is taken yields the plain name. For `downloadOutcome`: one test per ending, plus the two that pin what a failure names while `getSavePath()` is still empty.

[`apps/desktop/tests/notifications.spec.ts`](../../../../apps/desktop/tests/notifications.spec.ts) covers the launch-token cookie exchange and the backoff schedule over a minimal `electron` stand-in; the notification half of that module reaches into Electron the way the rest of the package does and is covered by the real-process check.

The Electron half — which session the handler lands on, whether the dialog really appears attached to the window, and whether the file manager comes forward — cannot be reached from a unit test. It awaits verification on a real machine against a packaged build.

## Alternatives considered

**Keep silent placement and fix the notification.** Registering the app with Notification Centre, or falling back to a dialog when `Notification.isSupported()` is false, would restore the report without touching where the file goes. `isSupported()` is not the predicate that failed: it answers true on macOS whether or not this app has an entry, so the case that broke is exactly the one the check does not detect. Anything reliable here ends up being the dialog anyway, and it would still leave the user with no say in where the file went.

**Reveal the file without asking, keeping the downloads folder.** This is the smallest fix for what was reported invisible, and it was rejected because it answers only half of what the user asked. 「我选择保存位置呢?」 is a request for the choice, not for a better report about a choice made for them; every browser on the machine offers it, and the shell's reason for withholding it — that a sheet appeared over a page which had already declared success — is addressed by a dialog that says what it is saving.

**Show the shell's own window instead of a native dialog.** A rendered picker could carry the export's own wording and match the app's theme. It cannot enumerate the filesystem from a browser surface with no preload and no Node integration, so it would need a new privileged route for exactly what the platform's save panel already does, with the panel's replace prompt and its TCC-granted write reimplemented behind it.

**Keep the in-flight `claimed` set as a guard on the offered name.** Two exports of one session started seconds apart still default to the same name, because both default paths are computed at `will-download` time, before either file exists. The set would spare the user a replace prompt, and nothing more: Electron's download-manager delegate sets the intermediate path equal to the target path, so there is no `.crdownload` stage and the first accepted save occupies its target immediately — the second dialog does warn. Keeping the set would mean tracking paths the shell does not own and cannot predict, since the user retypes the name whenever they want the file elsewhere, to guard against a prompt the system already raises.

**Report a broken transfer with a notification, and only the successful case with the file manager.** It reuses the existing channel for the case where there is no file to reveal. It also puts the one message the user cannot otherwise discover — the export they are waiting for is not coming — on the channel that was just found to be silent on a real user's machine.

## Consequences

Exporting a session log now costs one dialog. The transfer does not begin until the user answers it, and dismissing it cancels the export outright; the page's own 「导出完成」 line therefore precedes a step that can still end in nothing, which is the same gap the previous decision closed by removing the sheet. What replaces the guarantee is that every ending is now visible in the window the user is looking at: the file selected in the file manager, or an error box, or a dialog they themselves dismissed.

Both platforms behave the same way, and neither depends on notification permission the app may not hold. macOS and Windows show their own save panel, their own replace prompt, and their own file manager selection.

Two exports of one session default to the same name: both default paths are computed before either file exists, and the dialogs are serialized — a macOS sheet is modal to the window it is attached to, so the second opens only after the first is answered. What catches the collision is the system's replace prompt, which the second dialog raises because Electron's intermediate path is the target path and the first save has already occupied it. The user is asked rather than never told.

**Three platform facts the dialog inherits.** `message` is macOS-only, so Windows shows `title` alone; with no `filters` declared, the Windows panel's file-type list is empty and it saves whatever the name says. A macOS sheet is drawn on its parent window, so an export started just before the window is minimized or hidden looks stuck until the window comes back. And `shell.showItemInFolder` brings Finder or Explorer to the front, which takes focus away from the app at the moment the export finishes.

The macOS consent prompt for `~/Downloads` was not re-verified on a signed build. The key is declared, and the folder is now probed rather than written, so the prompt can arrive at a different moment than it did before; a packaged build is the only place that can confirm it.
