# Agent Note: Recover from the embedded server dying after startup

Status: implemented

English | [中文](2026-08-28-desktop-server-crash-recovery.zh.md)

## Problem

On a customer's Windows machine (rc.24) the embedded `dsh web` server child died silently sometime after startup. Nothing in `apps/desktop/src/server.ts` or `main.ts` held an exit listener on the child once `startServer` had resolved, so nothing logged the death and nothing restarted it. The window kept showing whatever the last-rendered page looked like — a normal-looking, fully frozen page — while `notifications.ts`'s two downlink WebSockets kept retrying the same fixed 3s interval against a server that was never coming back: 1318 log lines over 33+ minutes, two per retry, saying nothing new after the first pair.

## Decision

**Autopsy (`server.ts`, `main.ts`).** `ServerHandle` grows an `onExit(listener)` method; `startServer` now keeps a bounded rolling tail (`RECENT_OUTPUT_TAIL_LINES` = 15, fed continuously for the child's whole life, not the unbounded `collected` string the pre-URL path already used) and an `expectedExit` flag `stop()` sets before signaling the child. A listener registered through `onExit` receives `{ code, signal, expected, tail }` once, synchronously if the child had already exited. `main.ts`'s `attachSupervision()` logs `[desktop] server exited unexpectedly: code=<code> signal=<signal>` plus the tail for every exit `expected` is false for, and hands it to the recovery ladder; an expected exit (`stop()`, which the quit flow, the mandatory-update gate, and every rebind all route through) logs nothing extra.

**Recovery ladder (`apps/desktop/src/server-supervision.ts`, new module).** A pure reducer — `onUnexpectedServerExit`, `onRebindFailed`, `onRebindSucceeded` over a `SupervisorState` of `{ recentUnexpectedExits, rebindFailures }` — decides the next `SupervisorAction` (`recover` / `relaunch` / `stop`) from plain timestamps, no clock or timer of its own. `runRecoveryLadder` is the one caller-facing entry point: given the ladder's state, `now`, whether this process is itself an L1 relaunch, and `RecoveryHooks` (`rebind`, `sleep`, `notifyRecovering` — the same injected-hooks shape `download-retry.ts`'s `withRetry`/`RetryHooks` already uses), it drives one exit's whole outcome.

- **L0** rebinds in place: `REBIND_DELAYS_MS` = `[1_000, 5_000, 15_000]`, so up to 3 attempts. `main.ts`'s `performRebind()` is the one `rebind` implementation, used both by the ladder and by L2's manual retry: it calls `startServerWithQuarantine` with the recorded `activeServerSpec`, and on success reassigns the module-level `server`, calls `retargetWindows()` (`window.loadURL` on every `BrowserWindow` `isResizable()` says is the served-UI window — the same discriminator `main-window.ts` already uses), calls `setupNotifications` again against the new URL, and re-attaches supervision to the new child.
- **L1** relaunches once: 3 failed rebind attempts (`REBIND_DELAYS_MS` exhausted) **or** `UNEXPECTED_EXIT_ESCALATION_COUNT` (3) unexpected exits inside `UNEXPECTED_EXIT_WINDOW_MS` (10 minutes) — the second condition fires even when every individual rebind succeeded, because a server dying every few minutes is flapping, not stumbling once, and each successful rebind is already a visible interruption on its own. `relaunchForRecovery()` sets `quitting = true` (so the tray's close guard on Windows does not intercept the window closes `app.quit()` performs — mirrored from why `before-quit` itself raises `quitting` before anything else) then calls `app.relaunch({ args })` with `RECOVERY_RELAUNCH_FLAG` (`--dsh-recovery-relaunch`) appended to argv, and `app.quit()` — not `app.exit()` — so the ordinary `before-quit` teardown (closing the loopback services) still runs.
- **L2** stops automatically recovering: a recovery-relaunch instance (`isRecoveryRelaunchInstance(process.argv)`) that suffers an unexpected exit within `L2_GUARD_WINDOW_MS` (2 minutes) of its own start goes straight to `stop`, skipping L0 entirely. `runStoppedDialog()` shows a native `type: 'error'` dialog — 「后台服务多次崩溃，已停止自动恢复」, buttons 「重试」/「打开日志」 — and loops: 「重试」 calls `performRebind()` once and only reshows the dialog on failure; 「打开日志」 reveals the log file and always reshows it. Nothing here calls `app.relaunch` again, so there is no relaunch loop to bound.

**Reconnect backoff (`notifications.ts`).** The fixed 3s retry becomes exponential — `reconnectDelayMs(attempt) = min(RECONNECT_MAX_MS, RECONNECT_BASE_MS * RECONNECT_BACKOFF_FACTOR ** (attempt - 1))`, 3s → 6s → 12s → 24s → 48s → capped at 60s, reset to attempt 1 the moment a connection actually opens before it later closes. Only the first attempt and every `RECONNECT_LOG_EVERY`th (10th) one logs a line, now carrying the attempt count. Retargeting reuses the same close/reopen machinery: `setupNotifications` is idempotent-safe to call again — it stops whatever `Generation` (`{ stopped, sockets }`) is currently active (closing its sockets; any in-flight reconnect timer no-ops on its `stopped` flag when it later fires) before opening the new one, and the `app.on('browser-window-focus', …)` / `app.once('before-quit', …)` hooks bind exactly once ever, guarded by a module-level `appHooksBound` flag, so a second `setupNotifications` call (every L0/L2 rebind) does not duplicate them.

**Disconnect banner: not built.** `ConnectionState` (`'connected' | 'reconnecting'`) is produced by `packages/client/connection`'s `ConnectionController` and consumed only by `packages/client/runtime/src/client/index.ts`'s `onStateChange` handler, which calls `sessions.handleDisconnected()` on `'reconnecting'` and nothing else — unlike `onConnected`, which re-emits `ctx.emit('connection/reset')`, no client event or session-reader-visible field carries the state onward. No fork-owned surface (`apps/web`, the desktop's own preload/renderer, or a built-in plugin) can observe it without that. `packages/client/runtime` is upstream `packages/*` territory, off limits on this fork branch per the desktop/core split; the banner is deferred until that package re-emits the state (e.g. a `ctx.emit('connection/state', state)` beside the existing `connection/reset`), which routes through core-patches.

## Alternatives considered

**`vi.useFakeTimers()` for the ladder's tests, driving `main.ts`'s own timers.** Rejected: `main.ts` (like every other Electron-touching module in this package — `notifications.ts`, `tray.ts`, `updater.ts` included) has no unit test at all in this codebase; its own real-process behavior is what the desktop app's dev-mode run verifies. Extracting the ladder into `server-supervision.ts` as a pure reducer plus one hooks-driven orchestrator (`runRecoveryLadder`) — the same shape `download-retry.ts` already established — keeps the decision logic unit-tested with plain injected `sleep`/`rebind` functions and leaves `main.ts` as thin, untested-by-convention wiring.

**An env var for the L1 marker, inherited by `app.relaunch`'s spawned process.** Rejected in favor of an argv flag: `app.relaunch({ args })` is the documented, explicit mechanism for handing the next instance something; relying on whatever environment inheritance Electron's relaunch spawn happens to do is unstated behavior this decision would then depend on.

**Escalate to L1 only on exhausted rebind attempts, not on a raw unexpected-exit count.** Rejected: a server that dies, rebinds successfully, dies again, rebinds successfully, dies a third time never exhausts a single L0 sequence, yet is exactly the flapping case L1 exists for. `onUnexpectedServerExit` counts every unexpected exit inside the 10-minute window regardless of whether the rebind that followed it succeeded.

**Work around the missing `ConnectionState` seam from `apps/web` — e.g. poll `document.title` or scrape the DOM for a reconnecting affordance.** Rejected: the placement rule for this task is explicit that a banner needing an upstream seam is reported, not improvised around; a DOM-scrape banner would also silently break the moment the upstream markup it depends on changes.

## Consequences

An unexpected server death is now always in the log with its own line and a tail of what the server last said, is retried automatically with visible user feedback, and — if retrying keeps failing — ends at a decision the user makes rather than a silently frozen window or an infinite relaunch loop. Verified on this machine in dev mode against a scratch `DSH_HOME`: killing the server child with `SIGKILL` produces the autopsy line, the OS notification, a rebind on a new port, both notification streams reconnected to the new port (confirmed via `lsof` on the main and network-service processes), and the window showing the served UI again; three kills inside the window produce the marked `app.relaunch`; a further kill inside the L2 guard window of the relaunched instance produces the native dialog, and its 「重试」 button performs one successful manual rebind.

The disconnect banner itself did not ship — `packages/client/runtime`'s `onStateChange` handler needs to re-emit `ConnectionState` as a client-observable event before any fork-owned UI can consume it. `notifications.ts`'s reconnect log volume drops from two lines every fixed 3s (1318 lines over the field incident's 33 minutes) to two lines at attempt 1 and then two more every 10th attempt, at a backoff that reaches its 60s cap within about two minutes of a dead server rather than polling it every 3s indefinitely.
