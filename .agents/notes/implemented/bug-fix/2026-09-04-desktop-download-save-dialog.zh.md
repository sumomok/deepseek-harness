# Agent Note: 导出会话日志时先问存到哪里,再把落地的文件指出来

Status: implemented

[English](2026-09-04-desktop-download-save-dialog.md) | 中文

## Problem

自[由壳来安置所服务 UI 的下载](2026-09-03-desktop-download-handling.zh.md)起,桌面壳就自己写下这些文件:重定向链整条都与内嵌服务器同源的传输直接落进系统下载文件夹,用一个去过重的文件名,结果由一条 Electron `Notification` 播报,点它会定位到那个文件。

在报告问题的用户那台 macOS 26 机器上,导出完成了,播报却从未到达。`dsh-server.log` 里两行都在——`[desktop] download saved: /Users/…/Downloads/dsh-session-session-9ca7767d-….zip` 以及它旁边那条 ` (2)`——两个 ZIP 也都在盘上,而且是合法的。窗口里导出面板写着「导出完成」,然后什么都没发生。`~/Library/Preferences/com.apple.ncprefs.plist` 里根本没有 `dev.dsh.desktop` 这一条,也就是说这个应用从未在通知中心注册过;`Notification.show()` 在那里是一次静默的空操作,而且不报任何失败。壳对一次下载说过的唯一一句话——文件去了哪里——正好走在这台机器上什么都不投递的那条通道上。

看不见的播报只是一半。另一半是没有任何东西可以兜底,因为同一次改动还把选择权拿走了:文件躺在 `~/Downloads` 里,名字用户从没见过,而他真正问出口的那句——「我文件呢?我选择保存位置呢?」——在他正看着的那扇窗里没有任何答案。

## Decision

壳先问文件存到哪里,再把它落地的样子指出来。被接管的下载由壳自己的保存对话框和系统文件管理器来回答,而不是由一条通知。

[`apps/desktop/src/download-policy.ts`](../../../../apps/desktop/src/download-policy.ts) 仍然按原来的条件决定接管什么:`DownloadItem.getURLChain()` 的每一跳都必须属于内嵌服务器的 origin,这既包含导出页面为自己铸造的 `blob:` URL,也排除掉不带 origin 的与跨源的 URL。变的是答案。`decideDownload` 给出 `{ kind: 'ask', dialog }` 而不再是 `{ kind: 'save', path }`,`dialog` 就是处理器交给 `item.setSaveDialogOptions` 的那份完整 `SaveDialogOptions`:`title` 是「保存文件」,`message` 是「保存 `<文件名>`」——两个字段都给,是因为它们各自覆盖一批平台,`message` 只在 macOS 生效(`electron.d.ts` 标 `@platform darwin`)——一个「保存」按钮,以及落在系统下载文件夹里的 `defaultPath`,仍用下载自己建议的名字,并仍会越过盘上已有的名字编号成 ` (2)`、` (3)` ……。

**对话框只点名文件,不对它做任何约束。**内嵌服务器以附件形式发出的每一样东西都会走到这个处理器,不只是会话日志导出。[`profile-seed.ts`](../../../../apps/desktop/src/profile-seed.ts) 会把 `dsh-better-sidebar` 种进每一个桌面 profile,而它用 `Content-Disposition: attachment` 回答 `/sidebar/file?…&download=1`,服务于文件树的下载命令、二进制预览与 PDF 工具条——每一跳都同源。点名导出、再加一条 `zip` 过滤器的文案,会把这些全部改名:macOS 把 `filters` 映射成 `setAllowedFileTypes:`,而 Electron 不设 `allowsOtherFileTypes`,于是拿到 `report.pdf` 的面板在 `zip` 过滤器下写出的是 `report.zip`。因此这个对话框不声明任何过滤器,文案也只带上文件自己的名字,而不是对它是什么的一个猜测。

**对话框顶掉了「静默写盘」才需要的那两道保险。**那份记录在途路径的 `claimed` 集合没有了:它之所以存在,是因为对同一个会话点两次会建议出同一个名字,而在第一次传输写下之前没有任何东西占着它,于是第二次静默写盘就会落到第一次的路径上。现在壳不再选择任何路径——它只是提议一个,由用户确认或改写——所以壳仅仅提议过的名字并不构成对任何东西的认领,而真正被写下的那个路径,在对话框关闭之前壳并不知道。`no-free-name` 这个结局出于同样的理由消失了:它之所以存在,是为了让一个再没有空闲候选名的文件夹拿到 Electron 的面板而不是一次覆盖;如今装满的文件夹只会拿到那个光秃秃的名字,而对话框背后有系统自己的替换确认守着。于是 `DownloadDecision` 的 `default` 分支不再带原因,而被接管的下载在结束之前不会往日志里写任何东西。

`downloadOutcome` 是第二个纯函数,三种结局都由它决定。**完成**写下 `[desktop] download saved: <path>`,路径是用户自己选的那个,并请求在文件管理器里选中这个文件——这是这次修复看得见的那一半,也是唯一不依赖「应用可能从未被授予的权限」的那一半。**取消**只写一行,什么都不显示:用户划掉了对话框,那就是他拒绝了这次下载,而为一次拒绝再确认一遍是噪音。**中断**写下它那一行,并弹出一个错误框——「文件没有保存成功」,下面是「`<文件名>`:写入失败,请检查保存位置后重试。」——因为「没有产出文件」是用户唯一没法自己看出来的结局。它按写盘失败而不是网络失败来措辞:这些传输走的是环回,而导出的字节在它那次 `blob:` 下载开始时早已在页面内存里,所以对话框关闭之后还能失败的,是把它们放到盘上——卷满了、目标不可写、目标不在了。在路径存在之前就被划掉的对话框会报出一个空的 `getSavePath()`,所以两种失败结局在没有路径可点名时,点名下载建议的那个文件名。

[`apps/desktop/src/main.ts`](../../../../apps/desktop/src/main.ts) 只剩接线:组请求、在 `ask` 时把对话框选项设上去、在 `default` 时返回,并在 `done` 时写 `outcome.line`、有东西要指出来就调 `shell.showItemInFolder`、有东西要报告就调 `reportDownloadFailure`。最后这个按本模块其余对话框的做法把弹框挂在应用自己的窗口上,并且不等它的答复:传输横竖已经结束,而 `done` 处理器不能把下载会话堵在一个模态框后面。[`electron-builder.yml`](../../../../apps/desktop/electron-builder.yml) 里的 `NSDownloadsFolderUsageDescription` 保留。macOS 把 `~/Downloads` 拦在 TCC 后面,而壳有两处够到它:默认路径靠探查这个文件夹来去重;以及对话框还开着的时候,Chromium 就已经把到达的字节写进默认下载目录了(`components/download/internal/common/base_file.cc` 的 `default_directory`),不管用户最后选的是哪里。

`announceDownload` 与 `DownloadNotice` 从 [`apps/desktop/src/notifications.ts`](../../../../apps/desktop/src/notifications.ts) 里删掉了,连同该模块的 `shell` 导入,以及那段把平台分野的适用范围划在它们之外的文字。没有别的调用者,下载的结果也不经由任何通知播报。该模块负责注意力事件的那一半——Windows 的系统提示、macOS 的角标与弹跳——原样不动。

## Testing

[`apps/desktop/tests/download-policy.spec.ts`](../../../../apps/desktop/tests/download-policy.spec.ts) 覆盖这两个函数。`decideDownload` 这边:同源 `/api` URL 与同源 `blob:` URL 被接管;换端口、换主机、换 scheme,跨源 `blob:`,`data:`/`about:`/`file:`/不透明 `blob:`,一个根本不是 URL 的字符串,进入服务器与离开服务器的链,以及空链,一律留给 Electron,而服务器内部的两跳链被接管;整份对话框——标题、message、按钮、默认路径,以及「没有任何过滤器」这一点——整体断言两次,一次是导出的 `.zip`,一次是走侧栏 `?download=1` 路由的 `report.pdf`,后者正是把文案与过滤器清单钉在「不是会话日志的下载」上的那一条;建议的文件名被削到最后一段,只剩路径语法时回落到 `download`;提议的名字会越过文件夹里已有的同名文件编号,而一个所有候选名都被占满的文件夹给出那个光秃秃的名字。`downloadOutcome` 这边:每种结局一个测试,另加两个钉住 `getSavePath()` 仍为空时失败结局点名什么。

[`apps/desktop/tests/notifications.spec.ts`](../../../../apps/desktop/tests/notifications.spec.ts) 覆盖启动令牌的 cookie 交换与退避计划,跑在一个最小的 `electron` 替身上;该模块负责通知的那一半按本包其余部分的做法直接够进 Electron,由真机核对覆盖。

Electron 那一半——处理器落在哪个 session 上、对话框是不是真的挂在窗口上出现、文件管理器会不会走到前台——单元测试够不着,尚待在真机上对着打包构建验证。

## Alternatives considered

**保持静默写盘,把通知修好。**把应用注册进通知中心,或者在 `Notification.isSupported()` 为假时回落到一个对话框,都能在不动文件去向的前提下把播报救回来。可失效的那个判定并不是 `isSupported()`:在 macOS 上,无论本应用有没有条目它都答真,所以坏掉的恰恰是这个检查看不见的那种情况。任何在这里可靠的做法最后都会变成那个对话框,而且仍然不会让用户对文件去了哪里有任何发言权。

**不问,但把文件指出来,仍然存进下载文件夹。**这是针对「播报看不见」这件事的最小修法,被否决是因为它只答了用户问题的一半。「我选择保存位置呢?」要的是选择权,而不是关于一个替他做好的选择的更好播报;这台机器上每一个浏览器都提供这项选择,而壳当初收回它的理由——一张面板盖在一个已经宣布成功的页面上——由一个会说明自己在保存什么的对话框来解决。

**用壳自己的窗口代替原生对话框。**一个自绘的选择器可以带上导出功能自己的文案,也能跟随应用主题。但它在一个没有 preload、没有 Node 集成的浏览器面里列不出文件系统,于是需要为「平台的保存面板本来就在做的事」新开一条特权路由,还要在它后面把面板的替换确认与 TCC 授权写入重新实现一遍。

**保留在途 `claimed` 集合,当作对「提议的名字」的一道保险。**同一个会话相隔几秒发起的两次导出仍会默认到同一个名字,因为两个默认路径都是在 `will-download` 时算出的,那时哪个文件都还不存在。这个集合能省下的只是一次替换确认,再无其他:Electron 的下载管理器委托把中间路径设成与目标路径相同,所以没有 `.crdownload` 这一段,第一次保存被接受的瞬间目标路径上就有文件了——第二个对话框会提示。留着这个集合,意味着去追踪壳并不拥有、也预测不了的路径(用户想把文件放到别处时随时会改名),换来的只是挡掉一个系统本来就会弹的确认。

**中断用通知报,只有成功那一种走文件管理器。**这样能在「没有文件可指」的场合复用既有通道。但它也把用户唯一没法自己发现的那条消息——他正在等的导出不会来了——放在了刚刚被证实「在一台真实用户的机器上是静默的」那条通道上。

## Consequences

导出会话日志现在多了一个对话框。用户不回答它,传输就不开始;划掉它,导出就直接取消。于是页面自己那句「导出完成」前面站着一个仍然可能以「什么都没有」收场的步骤,而这正是上一版判定用「取消面板」堵上的那道缝。换来的是:每一种结局现在都出现在用户正看着的那扇窗里——文件管理器里被选中的文件、一个错误框,或者一个他自己划掉的对话框。

两个平台的行为一致,而且都不依赖应用可能并不持有的通知权限。macOS 与 Windows 各自弹自己的保存面板、自己的替换确认、自己的文件管理器选中。

同一个会话的两次导出会默认到同一个名字:两个默认路径都在任何文件存在之前算出,而两个对话框是串行的——macOS 的 sheet 对它挂着的那扇窗是模态的,第二个要等第一个被回答之后才打开。真正接住这次撞名的是系统的替换确认,第二个对话框会弹它,因为 Electron 的中间路径就是目标路径,第一次保存已经把它占住了。用户是被问了一句,而不是从头到尾不知情。

**对话框继承的三条平台事实。**`message` 只在 macOS 生效,所以 Windows 上只显示 `title`;由于不声明 `filters`,Windows 面板的文件类型下拉是空的,名字写什么就存什么。macOS 的 sheet 画在它的父窗口上,所以一次导出若恰好在窗口被最小化或隐藏之前发起,看上去会像卡住,直到窗口回来。而 `shell.showItemInFolder` 会把 Finder 或资源管理器拉到前台,于是导出完成的那一刻焦点会从应用上被夺走。

`~/Downloads` 的 macOS 授权弹窗没有在签名构建上重新验证过。这个键仍然声明着,而那个文件夹现在是被探查而不是被写入,所以弹窗到来的时机可能与从前不同;只有打包构建能确认这件事。
