# Agent Note: An unreadable attachment is recorded in the export archive

Status: implemented

[English](2026-09-04-export-records-unreadable-media.md) | 中文

## Problem

会话日志把每张图片存为一条 `ImageAttachmentRef`——附件 id、媒体类型、字节长度与像素尺寸——导出时会通过 `AttachmentStore.readImage` 把每个被引用的对象读回来，而这个读取会拿存储的字节逐字段核对上述全部内容。只要有一项对不上，读取就以 `AttachmentError` 拒绝，而 `sessionLogZipEntries` 任由这个拒绝抵达 ZIP 生产者。第一个字节发出之后，生产者唯一的应答就是 `controller.error`，于是一张图片就带走了整次下载：路由早已发出 `200` 与三个规模字段，响应体在归档中途被切断，页面只报告浏览器的 `network error`、没有任何 Host 给出的原因，也没有任何内容落盘。原因同样无处可查——失败在流内部抛出并被吞掉，Host 日志从头到尾看不见它。

这不是假想，也不是存储的错。仓外插件 `@haoran/dsh-screenshot` 的 0.5.0 版本把 JPEG 字节按 `image/png` 声明保存；它写下的每一条引用都带着这个错误的媒体类型，而 0.5.1 的修复够不到已经写进日志的引用。在一个真实会话上，一张 426 KB 的截图就让一份 6.1 MB 的日志——本身毫无问题的日志——永久无法导出。已存储对象失效的其他每一种方式表现完全相同：对象在存储底下被删除或被改写，或者存储根本打不开它。

导出自身的承诺也不支持旧行为。拒绝交付被截断的归档，正是会话日志值得信任的原因；而当一张图片读不出来时，归档仍然完整持有的恰恰就是这份会话日志。让下载失败，等于拿一份用户读得懂的完整日志去换取一无所有。

## Decision

`sessionLogZipEntries` 改为经由 [`src/archive.ts`](../../../../packages/session-query/session-log-export/src/archive.ts) 中的 `mediaEntry` 读取每个媒体对象，它把被拒绝的读取变成一条归档条目，而不是一个抛出的失败。这条条目是位于 `media/<attachmentId>.<ext>.error.txt` 的文本——即媒体条目自身的路径加一个后缀，因此记录就落在图片本该在的位置，且不可能与已存储对象撞名：一个附件 id 只会产出两者之一，绝不会同时产出。它的各行写明日志持有的那条引用——附件 id、媒体类型、字节长度、宽、高——随后是失败本身。归档继续并正常结束，因此下载成功，其中其余每个文件都准确无误。

取消不是「读不出来的附件」。有两处检查共同保证这一点，且其中任何一处单独都足以覆盖被中止的情形：`mediaEntry` 的处理分支在记录任何东西之前先调用 `signal?.throwIfAborted()`，而 `sessionLogZipEntries` 的循环在每次 `await` 之后、yield 之前又对同一个 signal 复查一次。循环里那次并不多余——它覆盖的是「signal 已中止但读取仍然成功」的那条路径——因此两处都保留。于是被中止的请求或离开的响应消费者仍然会终止压缩器并让流出错，与改动前完全一致。读不出来的子会话日志同样仍让流出错：缺失的会话日志是归档存在意义所在的那份历史缺了一块，而缺失的图片只是一条消息缺了一块。

记录只引用 `AttachmentError` 的 `code` 与 `message`，不引用其他任何来源的。`AttachmentError` 的声明类要求它的 message 在描述失败时不含原始字节与主机路径，这正是把那段文字抄进一个会被浏览器下载的文件的依据；而 code 区分了「对象不存在」与「字节不再与其引用相符」，也正是能识别出上文那种缺陷的区分。其他任何失败都不记录它自己的文字——文件系统错误的 message 会写出绝对主机路径，而路由在它的 500 分支上出于同一个理由刻意不把这类文字回显给浏览器。测试套件通过导出四种不同形状的失败、并断言归档里既没有 `code:` 行也没有主机路径，把这条区分钉死。

路由声明的规模不变，且条目数依旧准确：无论哪条路径，测量都为每条媒体引用产出一个条目。测量从不打开已存储的对象——它取每条引用记录的 `bytes`——因此流最终读不出来的图片，仍按记录的大小计入，而不是按它那条记录占用的几百字节计入。于是两个规模字段对该条目偏高，页面拿收到的字节去除以一个大于实际响应体的线上估算值，进度条因此走得比传输更慢，最后从它停下的位置直接跳到完成。在促成本次改动的那个真实会话上，响应体 468779 字节而声明值为 1281573，完成前的最后一帧报告 0.5——由条目度量托着（两个条目完成了一个），因为字节度量已经掉到它下面。方向与「压得比标定更松的归档」相同，线上估算值对那种归档本就会提前完成。让这些总数变精确的唯一办法是在测量阶段重读每一张已存储图片，而这正是[导出进度 Note](../feature/2026-09-03-session-export-progress.zh.md) 已经拒绝支付的代价。

## Alternatives considered

**跳过读不出来的图片，不放任何东西代替它。** 归档会看起来完整、却悄悄少了一个文件，而日志仍然引用着一个没有条目应答的 id。当初选择大声失败，正是为了绝不在不声明的情况下少导出；一条具名的记录以一个条目的代价守住了这个承诺。

**写下记录，但结束时仍让导出失败。** 这保留了「一次导出要么整体成功、要么失败」的规则，同时让原因可读。可原因在实际中读不到：失败的下载不保存任何内容，于是记录刚被产出就被丢弃，页面显示的依旧是 `network error`。

**改为修复引用——重新探测对象并按其真实媒体类型导出。** 这只救得了促成本次改动的那一种缺陷，且仅此一种。它会让导出变成附件元数据的写入者，需要导出包并不拥有的探测能力，而且对被删除或打不开的对象毫无帮助。救援已有的坏引用作为一个数据问题被单独考虑过，并已被否决。

**把失败写进会话日志而不是归档。** 一条会话事件能让失败在应用内可见、并可从日志重建。但它会在一次只读的导出过程中写入一份持久日志；而用户此刻看的正是这次导出，失败应当落在他们会去找的地方。

**把条目命名为 `media/<attachmentId>.error.txt`，不带图片扩展名。** 更短，但它不再读作「本该是 `media/<id>.png` 的那个文件」，而且当同一个 id 出现第二条使用不同媒体类型的引用时会撞名。

## Consequences

附件全部可读的会话，其导出与改动前逐字节相同。原本会撕裂的导出现在会完成，归档中多出一个文本文件，写明什么读不出来。面板的失败态含义不变：本次改动之后，它只在连接失败、取消，或子会话日志读不出来时报告传输撕裂。

打开归档的用户看到的是失败而不是图片，这正是预期的报告方式——响应一旦开始，Host 侧的附件失败再没有别的通道能抵达他们。[导出进度 Note](../feature/2026-09-03-session-export-progress.zh.md) 记下的 `network error` 限制，对仍会撕裂的那些失败保持不变。

`archive.host.spec.ts` 把行为钉死：一份两条引用分别落成一个图片条目与一条记录的归档，连同记录的精确文本、声明的条目数与字节总数；四种非 `AttachmentError` 的失败形状，每一种都在不带 code、不带 message 的情况下被记录；以及一次落在媒体读取过程中的取消，它仍让流出错。包内逐文件覆盖率保持 100%。

整机装配由 `apps/web/tests/navigation-panes.e2e.ts` 中新增的第二个种子会话覆盖。它的用户消息引用 `sha256:` 加六十四个零——对 `attachment-local` 的引用格式合法，而对应对象从未被写入——因此真实路由、真实存储与真实页面端到端产出 `ATTACHMENT_NOT_FOUND`。该用例断言 `200`、声明的条目数为 2、归档的两个条目、记录里的 `code` 与 `reason` 行，以及页面上的 `Export complete` 面板。它不需要 golden，也不需要录制模型调用：没有任何模型调用能产出一条指向不存在对象的引用，故种子是手写的。

当上游落地等价能力——一次能容忍读不出来的附件的导出——或上游提供修复这类引用的手段时，本补丁退役。
