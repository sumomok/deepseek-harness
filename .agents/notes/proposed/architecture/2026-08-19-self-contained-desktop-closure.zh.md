# Agent Note：为桌面服务端闭包增加一个自包含的 deploy 构建面

Status: proposed

[English](2026-08-19-self-contained-desktop-closure.md) | 中文

## 问题

一次 Windows 安装的时间几乎完全花在文件数上。[用真安装器测得](../../implemented/testing/2026-08-19-windows-install-cost.md)，把载荷的 500.9 MB 以 12453 个文件搬运要 5.67 秒，而同样的字节以 10 个文件搬运只要 0.12 秒：**拷贝里 98% 是每文件开销**，创建一个 0.446 毫秒、删除一个 0.151 毫秒。安装器要付两遍这个代价，一遍解压进 `%TEMP%`、一遍拷进安装目录，这就是 NVMe 上一次全新安装 53.56 秒的主体。机械盘上每文件那项涨两个数量级、每字节那项只涨一个，所以同一个测量说明文件数在那里更重要而不是更不重要。

包里 12452 个文件中有 12426 个是内嵌的服务端闭包——Electron 本身、内置 Node 运行时和应用可执行文件都是少数几个大文件，对文件数毫无贡献。闭包内部的构成是：

| | 包数 | 文件数 | 占比 |
|---|---|---|---|
| 第三方 | 319 | 11008 | 89% |
| `@deepseek-ai/*` | 199 | 1417 | 11% |

本仓库自己的包不是问题：tsdown 已经把每个包打成 `lib/index.js` 加一个 invariant 模块和类型声明，它们的 `files` 字段也是这么写的。需要被打包器收敛掉的是那 11008 个第三方文件——光 `@earendil-works/pi-ai` 就有 1481 个，`@mixmark-io/domino` 1018 个，`typebox` 692 个，`openai` 464 个，`shiki` 442 个，`@shikijs/langs` 363 个。

最显而易见的做法——把服务端打成一个文件——走不通。运行时是 Cordis，而 `@deepseek-ai/cordis-plugin-loader` 在启动时读取配置、**按包名解析插件**，`cordis-plugin-include` 还允许一份配置引入另一份。一个静态单包里没有任何东西能让配置里写的名字解析到，而插件生态本身就是产品。

另一个显而易见的做法——在构建时把依赖打进每个包——与发布冲突。219 个 workspace 包全部可发布，没有一个是 `private`，把第三方代码内联进去会改变 npm 消费者收到的东西：npm 再也无法去重的重复依赖、被我们构建时刻锁死的版本，以及与库消费者需求无关的包体积。

## 提案

在现有的 `host` 与 `client` 之外增加第三个构建面——`DSH_BUILD_FACE deploy`——只为桌面打包流水线产出自包含的产物。npm 产物保持 external，保持今天的样子。

`tsdown.config.ts` 本来就按 `env.DSH_BUILD_FACE` 分支，而 `apps/desktop/scripts/package.ts` 本来就通过自己的 `pnpm deploy` 步骤铺出闭包，所以两端的接缝都已存在。deploy 面与 `host` 只差一点：第三方依赖为 `noExternal`，于是每个包的入口自带它 import 的东西。原生模块仍然 external、仍然散着，因为它们是 `.node` 与 `.exe`，任何打包器都内联不了，而且它们的加载器按路径解析。

闭包会变成：

| | 现在 | 提案后 |
|---|---|---|
| `@deepseek-ai/*` | 1417 文件 | ~400（199 包 × ~2） |
| 第三方 | 11008 文件 | 被内联 |
| 原生二进制 | 12 文件 | 12，不变 |
| 前端静态资源 | 90 文件 | 90，不变 |
| **合计** | **12426** | **~500** |

按实测的每文件创建 0.446 毫秒、每次安装两遍创建计算，这大约能从当前安装里换回 11 秒。而在机械盘上——每文件项本就是主导——同样的削减值好几分钟。

插件模型不受触碰：加载器仍然按名解析 `@deepseek-ai/dsh-agent-loop`，仍然找到一个同名目录和其中的入口。变的只是那个入口里装着什么。

## 哪些必须散着，以及为什么

**原生模块。** `node-pty` 的预编译产物、`@koromix/koffi-win32-x64`、带着 `libvips-42.dll` 的 `@img/sharp-win32-x64`，以及 `@vscode/ripgrep-win32-x64` 的 `rg.exe`——12 个文件，27 MB。它们的 JavaScript 是拼路径去找二进制的，所以加载器与二进制都必须以真实文件留在可预期的位置。这正是打包流水线的 `PLATFORM_DIR_RULES` 已经在按目标平台裁剪的那类东西。

**前端静态资源。** `@deepseek-ai/dsh-web-frontend/dist` 是 90 个按路径经 HTTP 提供的文件。它们是数据，不是模块。

**任何在运行时被动态解析的东西。** `shiki` 按名加载语法与主题文件；这样做的包无法被完全内联，必须保留它的加载器要去够的东西。这正是本提案在交付前必须找出来的那一类故障，也是为什么验收要落在一次真实启动上，而不是落在文件数上。

## 备选方案

**在 `pnpm deploy` 之后就地打包每个第三方包。** 改写铺好的闭包，而不改我们自己的构建方式。否决：第三方的 `exports` 映射是任意的，消费者会 import 子路径（`@babel/runtime/helpers/x`、`shiki/langs/js`），而要为 319 个别人写的包保住每一条可达子路径，其暴露面远大于从我们自己的入口打包——那里的 import 图是我们自己的。

**把整个服务端入口打成一个文件。** 可能得到的最小闭包。否决：这恰恰是 Cordis 加载器唯一无法配合的形态，因为配置点名的插件必须在运行时作为可解析的包存在。

**让包本身在 `host` 面就自包含。** 只需一套构建而不是两套。基于上面的发布理由否决——为了一个桌面独有的收益去改动 219 个公开的 npm 产物。

**裁得更狠。** 流水线已经按后缀与平台裁掉了 19274 个文件。剩下的是服务端真正会加载的运行时 JavaScript；除打包之外没有别的裁法。

**什么都不做。** 站得住脚：NVMe 上 53.56 秒并不痛苦，而用户真正在网络上等待的下载部分，靠 blockmap 已经只有载荷的 1%。要动手的理由是机械盘上的放大系数，以及文件数是这个仓库唯一能控制的杠杆。

## 验收标准

铺出的闭包文件数低于 1000，由打包流水线测量，并打印在现有那行「最深相对路径」旁边。

`verifyStagedBoot` 在 deploy 面的载荷上通过——一次真实的 `web --port 0` 启动、URL 行、以及一次首页拉取——这正是能抓住「打包破坏了动态解析」的闸门。桌面组合列出的每个插件都必须能加载，而不只是启动路径碰到的那些，所以这道启动检查要增加一条对加载器已解析插件集合的断言。

安装耗时在改动前后各测一次，用[安装成本那份 Agent Note](../../implemented/testing/2026-08-19-windows-install-cost.md) 里的方法——真安装器，只通过常数时间调用观察，引用「正在安装」页到「完成」页之间那一段。

npm 产物与今天 `host` 面产出的字节完全一致，以此证明 deploy 面没有改变任何发往包消费者的东西。

MAX_PATH 余量应当变好而不是变差：收敛掉 `@earendil-works/pi-ai` 的嵌套树，就移除了那条 208 字符的路径——正是它让当前载荷距安装器的解压预算只剩 4 个字符。

## 风险

**第三方包内部的动态解析。** 最主要的一个。一个按路径读自己文件、或 `require` 运行时计算出的名字的包，在打包后会静默失效，而且可能只在启动检查够不到的代码路径上失效。缓解手段是上面那条插件集合断言加上现有的快照套件；而诚实的立场是：正因为有这个风险，这件事才应该是单独一轮，而不是搭在别的改动上。

**字节增长。** 内联会让共享依赖在各包之间重复；69 MB 的 JavaScript 可能变成两三倍。按测量这是该做的交换——字节在两种介质上都几乎不要钱——但它确实会让首次下载变大，而 blockmap 帮不上这个忙。接受之前值得先量一下。

**同名不同版本的重复依赖。** 这本来就存在，而且本来就是对的：被检查的五棵嵌套树，每一棵都与顶层同名包**版本不同**。按包内联恰好保留了每个包各自解析到的版本，这比朴素提升所做的扁平化更忠实。

**两个构建面都要保持诚实。** 一个只有桌面用的构建面是日常开发不会走的路径，它会腐烂。「npm 产物字节一致」这条验收标准，正是用来防止两者在无人察觉中漂移出不同行为的。
