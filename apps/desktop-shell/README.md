# @deepseek-ai/dsh-desktop-shell

English | [中文](README.zh.md)

Desktop client: an Electron shell whose main process starts the embedded web server — the pnpm-deployed closure of [apps/desktop-server](../desktop-server/README.md) running on a bundled real Node runtime (never Electron's own Node, so the server keeps the tested engines line, `node:sqlite`, and the stock N-API prebuilds) — passes `--no-open` so the server never hands the address to the system browser, waits for the `dsh web:` URL line, and opens the served UI in a native window. The window is a plain browser surface: no preload, no Node integration; external links open in the system browser. Quitting tears the server process tree down (SIGTERM with a kill escalation; `taskkill /T` on Windows).

**The workspace package is named `@deepseek-ai/dsh-desktop-shell`, while the installed application is named `@deepseek-ai/dsh-desktop`**: upstream ships its own `@deepseek-ai/dsh-desktop` and occupies `apps/desktop`, but Electron derives the application's `userData`, `sessionData`, macOS `logs` directory and updater cache directory from the application name, so renaming it would put every installed version's cookies, login partitions and `desktop-state.json` out of reach. `extraMetadata.name` in `electron-builder.yml` pins the packaged half, `src/app-identity.ts` pins a source-tree launch, and `tests/artifact-names.spec.ts` requires the two to agree.

## Building installable packages

```sh
pnpm exec tsx apps/desktop-shell/scripts/package.ts --mac        # zip + dmg (arm64), runnable on this machine
pnpm exec tsx apps/desktop-shell/scripts/package.ts --win        # NSIS installer (x64), cross-packaged from macOS
```

Products land in `apps/desktop-shell/dist-app/`. The pipeline stages the server by the python/sdk-runtime recipe (legacy hoisted `pnpm deploy`, restore hoists, materialize symlinks), prunes host-compiled native `build/` trees so loads go through the multi-platform prebuilds, fetches the Windows x64 members of platform-split optional dependencies the macOS install skipped (named `win32-x64`, or `win-x64` as sherpa-onnx names them; a member declared by a range is fetched at the version of the member the host installed), and stages the Node runtime per platform (`--skip-repo-build` / `--skip-deploy` reuse existing artifacts). The repository build is `pnpm run build` with `DSH_CLIENT_TITLE=北冥`, the browser title in every UI language (`scripts/client-build.ts`); a run whose client build record or `apps/web/dist/index.html` lacks that title stops before staging, `--skip-repo-build` included. `@deepseek-ai/dsh-desktop-app` is bundled after that check; its browser half embeds no client build value. A payload gate runs before each payload's smoke test: every platform rule must drop at least one directory, every platform-split directory must name the target it ships in, and no surviving module may resolve a pruned package by name. Every run, `--skip-deploy` included, also stops when the staged LibreOffice kit declares, for `darwin-arm64` or `win32-x64`, an engine `ENGINE_DOWNLOADS` does not register (see Office engine service), which a fresh deploy can stage when a newer kit has been released. Registering that engine takes its published tarball size and `dist.integrity` and a conversion checked with that version; otherwise `--skip-deploy` reuses a staging the check accepts. A run without `--skip-deploy` deletes `staging/server` before it deploys, so a run the check stops leaves the rejected kit staged; a staging the check accepts has to be copied elsewhere before such a run and copied back to `staging/server` before `--skip-deploy` reuses it.

**A run builds the platforms it is named, never the ones it could guess**: `--mac`, `--win`, or both, and a run given neither stops before it builds anything. It ends by checking that every file this version owes for those platforms — the mac zip and dmg, the Windows installer, and each one's `.blockmap` — is in `dist-app`, non-empty, and **written since this run started**, printing the verified list and naming anything missing, empty, or left over. `dist-app` is never cleared, so it holds every past version, and a repackage of one version after a fix finds that version's own files already there under exactly the names expected: presence alone cannot tell a platform whose build did not run from one whose artifact is last run's. The expected names are electron-builder's defaults for the declared targets, held in `scripts/artifact-names.ts` and pinned against `electron-builder.yml` by `tests/artifact-names.spec.ts`.

**The whole build runs against a throwaway `$DSH_HOME`** it creates and deletes, so no server it starts edits the machine's own harness state — `prepareProfile` rewrites a profile's root config and `healProfilesModuleFallback` re-points every flat-fallback symlink at the staging tree this build is about to delete. The boot gate seeds that home exactly as the shell seeds a real one and then requires every built-in plugin that declares a browser half among the client modules the served index names, so what it proves is a property of the payload rather than of the build machine's own profile.

**The boot gate runs the staged server as an installed shell would, and the staged tree must hold the installation's whole closure.** The staged boot and `--dump-config` run without `NODE_PATH`, `npm_*` and `PNPM_*`: pnpm's `.bin` shims export a `NODE_PATH` naming the workspace's `node_modules/.pnpm/node_modules`, and a server inheriting it resolves anything the payload lacks from the build checkout. `verifyStaging` fails when the staged tree lacks any production dependency or required peer of `@deepseek-ai/dsh`, followed through each package's own and excluding the withheld packages, and each finished payload is held to the `@deepseek-ai` part of that closure, since `scripts/bundle-closure.ts` inlines third-party packages. pnpm's legacy deployer places `@deepseek-ai/dsh` beside the deploy source with some of its production dependencies, `@deepseek-ai/dsh-base` among them, only in its nested `node_modules`; `restoreLegacyHoists` copies those into the staged tree through `scripts/legacy-hoists.ts`. The deploy installs no peers, so `apps/desktop-server/package.json` lists the Service Definition packages the closure names only as peers.

## Closing the window, and being called back

**On Windows the close button asks what it should mean**, once: 「最小化到托盘」 or 「退出应用」, with 「记住我的选择」. Unchecked, the answer covers that one close; checked, it goes into `desktop-state.json` as `closeAction` and every later close follows it without asking, until the tray menu's 「关闭时询问」 clears it. The minimize button is untouched — it stays the ordinary taskbar minimize. The tray icon exists from launch, so 「最小化到托盘」 names something already on screen and **检查更新** / **退出** stay reachable while the window is hidden; the menu is 打开 / 检查更新 / 关闭时询问 / 退出, localized like the menu bar. Every quit — from the tray, from a remembered answer, from an update — runs the same `before-quit` teardown that stops the server, and an update dialog shows the window before attaching to it, because a window-modal dialog owned by a hidden window can be neither seen nor found. macOS keeps its own idiom: closing leaves the app in the Dock and `activate` reopens the window, so there is no menu-bar icon.

**The client says when a session wants you back.** Two moments qualify — a session finished running, and a session is waiting for an approval or an answer — and neither interrupts while the window is focused. Both are read from the server the shell already started, over `/api/remote.mux`, the same WebSocket the browser UI consumes, as one `$events` stream on it; nothing was added upstream for this, and the stream replays what is still pending when reopened, so each request announces itself once. Each message names its session by the title `session/list` reports when the message is raised, and calls it 「会话」 when the session has no title yet or the lookup fails; a failed lookup writes one `dsh-server.log` line carrying the reason the lookup failed. Windows shows a system toast that raises the window when clicked, and an approval's toast carries two buttons: 「拒绝」 answers that request from the toast — the same `$events/result` answer the page's own approval card sends, so the card goes away with it — and 「去看看」 raises the window, while there is no 「批准」 because the toast names the tool and nothing else and an approval belongs in front of what it approves. **Every toast the shell raises is taken down the moment it has been acted on or its request is over**, because Windows would otherwise keep it in the action centre with whatever buttons it carries live: a button was pressed on it, the shell's own minute-long grace answer went out, the request was cancelled, or the shell stopped watching that server. A button pressed after that — the press that arrives more than a minute after the toast is the ordinary case, since a banner reaches the action centre in seconds — raises the window instead of answering, which is where the user sees whether the card is still there to answer. A button on a toast that survived an app restart reaches no delivery at all: the shell does not register Electron's cold-start activation handler, and a freshly started shell has no delivery to match a press to. macOS shows a Dock badge and bounces once, and posts nothing to notification centre — a dozen finished turns would be a dozen banners to dismiss, while the badge says how many and clears when the window is focused. The badge counts finished runs plus the requests still waiting, one each: a request comes off the count when it is cancelled — someone answered it in the window or on another client — or when the shell stops watching that server, and the count never goes below zero. The shell's own grace answer leaves the request on the count, because the page still holds that request and the server sends no cancel to a client that has already answered; focusing the window clears it.

**A notification opens the app, not the session.** The web UI has no URL routing, so the shell has nowhere to navigate; the sidebar's own pending and completed markers identify the session that asked.

**The served UI's downloads are asked about once, and shown afterwards.** The window is a browser surface without a browser's download manager, so Electron answers a download with a Save As sheet that explains nothing — while the page that started it has already said it started, the session-log export announcing 「Session 导出已开始下载」 the moment the transfer begins. A transfer whose every redirect hop is same-origin with the embedded server therefore gets the shell's own save dialog: 「保存文件」 with 「保存 `<文件名>`」 beside it, a 「保存」 button, and the system downloads folder under the name the download suggests — with ` (2)`, ` (3)` … inserted before the last dot-suffix when that name is taken — and the file can go anywhere from there. **The dialog declares no file-type filter.** Everything the server serves as an attachment arrives here — the session-log export, the sidebar's workspace-file downloads, whatever a later plugin adds — and a filter would rename the ones it did not anticipate, because macOS maps `filters` onto `setAllowedFileTypes:` and Electron sets no `allowsOtherFileTypes`. A completed transfer is then selected in the system file manager: the shell shows where the file went rather than announcing it, because a notification is silent on a machine that never granted the app permission to post one. Dismissing the dialog cancels the download and says nothing further; a transfer that fails to write gets an error box naming the file. Each of the three writes one `dsh-server.log` line. Same-origin covers the `blob:` URLs a page mints for itself, whose origin is the page's own; a `data:` URL carries no origin and is never taken over, and neither is a transfer from any other origin, nor one that starts elsewhere and redirects in or starts at the server and redirects out — those keep Electron's default, sheet and all, because a file this shell did not serve is not its to place. macOS gates the downloads folder behind TCC, so `NSDownloadsFolderUsageDescription` in `electron-builder.yml` gives the system's consent prompt a reason to show: Chromium writes the arriving bytes into the default downloads directory while the dialog is still open, wherever the user finally sends them.

## Updates

Installed clients read a static feed — an electron-builder `generic` provider directory holding the manifests and the artifacts they name:

```
https://lhr.ink/dsh-updates/win/     latest.yml  + the NSIS installer + its blockmap
https://lhr.ink/dsh-updates/mac/     latest-mac.yml + the zipped app
```

The feed has no server side: the manifest *is* the decision procedure, so nginx serving a directory implements all of it. The feed URL lives in two places — `electron-builder.yml`, which generates the manifests and the packaged `app-update.yml`, and `src/updater.ts`, which reads them at runtime — so moving the feed means changing both. `channel: latest` is explicit on both ends; the default names the channel after the running version's prerelease tag, which would rename the channel at every stage of the release cycle.

**The transfer is quiet; only an installable update is not.** A silent check — 15 s after launch, every four hours, from **帮助 → 检查更新**, and from the Settings entry — starts the transfer of whatever it finds without asking first. Nothing about that transfer reaches the screen: no dialog, no window, no taskbar or Dock progress, no request for attention. Its end is the one visible state — an update downloaded and verified — which the shell reports over the update service below and the Settings window draws. **No install happens without the user deciding it**, on quit or anywhere else: `autoInstallOnAppQuit` is off, and the app replaces itself only in the seconds after someone clicks the button in that window. That click is the consent, so nothing asks a second time, and an update left uninstalled stays on disk and is reported again on the next launch. 帮助 → 检查更新 keeps its place and its label, runs the same silent check, and answers 「已是最新版本」 or 「无法检查更新」 — the two states nothing else shows. The 「无法检查更新」 detail is the failure's first message line, then a `错误码:` line naming the codes down its `cause` chain (`ENOTFOUND`, `HTTP_ERROR_503`, `DSH_TRANSFER_CUT ← UND_ERR_SOCKET`) or the `TimeoutError`/`AbortError` of a request given up on; a failure that carries neither gets no code line. A check that found an update says nothing: the update is already on the Settings row, whose button is what installs it. On the download page a manual check that finds an update asks 「发现新版本 / 去下载」 instead, because that tier has no other way to hand the download over.

**The dialogs that are left are the mandatory ones and the unsigned-macOS hand-off.** On Windows each is attached to the app's own window, because an unparented dialog is free to open behind whatever the user is working in, which is how an update prompt can exist without being seen; on macOS they are deliberately unparented, because a parented dialog there is a sheet that anything raising the parent window — a click on the Dock icon — ends as if its first button had been pressed. Either way an app that is not in front asks for attention first: a flashing taskbar button on Windows, one Dock bounce on macOS. No optional update reaches that path.

**The install is neither silent nor a wizard.** There are three things it could be, and the middle one is the only one that is both honest and click-free:

| | What the user sees | Why not |
|---|---|---|
| Full wizard | Directory page, progress, finish page | Re-asks what the click already answered; reads as a reinstall |
| Silent (`/S`) | Nothing — until something fails | An install with no surface cannot report itself, and NSIS shows its uninstall-failure box anyway (`handleUninstallResult`'s MessageBox carries no `/SD`), so the one thing that reaches the user is an error from nowhere |
| **Progress only** | One progress window, no question, app comes back | — |

`quitAndInstall(false, true)` picks the third. What removes the wizard around it is not silence: the directory page skips itself on an `--updated` run through the template's own `skipPageIfUpdated`, `build/installer.nsh` skips the finish page the same way, and MUI's `SetAutoClose true` closes the window when the section ends. Restarting the app is then ours to do — the template's relaunch is `${if} ${isForceRun} ${andIf} ${Silent}`, which a visible install never satisfies — so `customFinishPage` starts it through `ExecShellAsUser`, which drops the installer's elevated token. `$INSTDIR` is read in `.onInit` from `HKLM\SOFTWARE\<APP_GUID>\InstallLocation`, the value the install section writes, and falls back to `%ProgramFiles%\DSH Desktop` when that value is absent — so an update lands where the app already is exactly as long as that key survived the install that put it there.

**Windows installs for all users, so the update elevates.** `perMachine: true` plus `packElevateHelper: true` puts `isAdminRightsRequired` in the manifest, and the updater then launches the installer through `elevate.exe`. On a machine with ordinary UAC settings that is **one confirmation dialog per install**; on a machine whose UAC is set to "Never notify" it is granted silently and nothing appears. Without the elevation the per-machine uninstall of the old version aborts — one of the two ways to reach `Failed to uninstall old application files: 2`.

**The other way is the old uninstaller's staging path, and it is `build/installer.nsh` that keeps it short.** Updating runs the *old* uninstaller with `--updated`, whose uninstall section moves every file in the install directory into `$PLUGINSDIR\old-install` before deleting anything. `$PLUGINSDIR` lives under `%TEMP%`, so each staged path is that prefix plus the file's path relative to the install directory — 34 characters longer for an install to `D:\soft\DSH Desktop`, against a payload whose deepest file already sits 208 characters down. 261 characters is one past MAX_PATH, NSIS is not long-path aware, and the move fails with `ERROR_PATH_NOT_FOUND` — reported by the template as `File is busy`, which it is not. Five retries later the installer shows 「DSH Desktop 无法关闭」 over a Retry that runs the same doomed attempt, because the overlong path is the same path every time. `customRemoveFiles` replaces that staging: the install directory is renamed **whole** into a sibling of itself and deleted there, so every path below it keeps the length it already had and the move stays on one volume. `customInit` still clears the old version's processes first — the app, its `node.exe` server, and `elevate.exe`, which the updater starts from the app's own `resources` directory and which waits there for the whole install — because a live process turns that delete into a staging directory left on disk and lets the extract write over files the old version is still reading. It kills `elevate.exe` at once (without `/T`, since the installer is its child), then gives the app and its server 10 s to leave on their own and tree-kills what is left. Around it, a quit bounds its server stop (4 s on Windows, inside the installer's own patience; 10 s elsewhere) and exits regardless, and each launch kills any server a previous run left behind, matched on the full path of this install's bundled Node binary rather than the `node` image name.

**The step that asks whether the app is still running can answer "all of them".** The template's own "is it still running" step takes a file name and, on its PowerShell branch, ignores it: it counts the processes whose executable path starts with `$INSTDIR` and answers yes for any count above zero. The prefix is used with no trailing separator, and `String.StartsWith("")` is true of every string — so an `$INSTDIR` that did not resolve matches the whole machine, the installer included. Its kill step walks that same set with `Stop-Process -Force`, most of which fails, finds survivors on the next pass, and ends at 「DSH Desktop 无法关闭。请手动关闭它,然后单击重试以继续」, whose Retry re-enters the identical loop. That is not what produced the dialog described above — the machine that reported it was watched at 250 ms through a failing install, which showed five `old-uninstaller.exe` runs and no process check at all, and its `$INSTDIR` read `D:\soft\DSH Desktop` straight off the wizard. The over-match is real all the same, and cheap to refuse.

`build/installer.nsh` (picked up from `buildResources` by name) therefore defines `customCheckAppRunning`, which replaces that step outright — in the installer before it uninstalls the old version, and in the uninstaller before it starts moving files, since both reach it through the same macro. It stops `elevate.exe` first, alone and without `/T` (this installer is its child, so a tree kill would end the install, and stopping it first detaches this process from the app's descendants), then gives the app and its server 10 s to leave on their own and tree-kills what is left, because the server's own children hold the same files it does. Three rules bound it: `$INSTDIR` is used as a prefix only when it is an absolute path, longer than a volume root, that exists and holds this product's executable, and then only with a separator appended; this process's pid is excluded from every match; and nothing opens a dialog, because a box the user cannot satisfy is how the built-in version dead-ends. Where the prefix is not trustworthy the sweep matches exact image names instead — `elevate.exe`, reached through this process's own ancestor chain, and the app, tree-killed — and never a bare `node.exe`, which on any machine belongs to someone else. Around all of it, a quit bounds its server stop (4 s on Windows, inside the installer's own patience; 10 s elsewhere) and exits regardless, and each launch kills any server a previous run left behind, matched on the full path of this install's bundled Node binary rather than the `node` image name.

**The new build says so.** Each launch records its version in `desktop-state.json` under the user data directory, and a launch that finds an older version there — which is what an update that restarted the app by itself looks like — puts one line on the boot page: 「已更新到 vX.Y.Z」. Nothing else changes; there is no dialog to dismiss.

**When an install fails**, the downloaded installer is still on disk under `%LOCALAPPDATA%\@deepseek-aidsh-desktop-updater\pending\`. Running it by hand — right-click, **Run as administrator** — installs the same build the update was carrying, and the app keeps every session either way. The reason to run it elevated is that a hand-started installer has no `elevate.exe` to ask for the rights the per-machine uninstall needs.

**Once an install lands, the next launch removes it from `pending`.** electron-updater empties that directory only when a download fails or the cached record stops matching the feed, so the installed zip or installer — the whole artifact — otherwise stays until the next update starts downloading. The install click records the staged artifact's file name and sha512 with the running version in `desktop-state.json`; the first launch of a newer version empties `pending` while its `update-info.json` still names that artifact, then forgets the record. The same version launching again means the install did not land, and the file stays for the retry this paragraph's predecessor describes; a record naming a different artifact is a later download, and is kept. An entry the relaunching Windows installer still holds is named in the log and the record is kept, so the next launch tries again. The differential baselines in the cache directory root (`update.zip`, `installer.exe`, `package.7z`, `current.blockmap`) are never touched. An install started by a build older than this change recorded nothing, so its artifact is still left for the next update's download to clear.

**When even that stops at 「无法关闭」**, the install directory recorded for the product is missing, and writing it back is enough to let an older installer through:

```
reg add "HKLM\SOFTWARE\e36966b0-1805-5ec4-9648-404e09da7db1" /v InstallLocation /t REG_SZ /d "D:\soft\DSH Desktop" /f /reg:64
```

The key name is the GUID electron-builder derives from `appId`, and it is the only place the installer reads the directory from — the `Uninstall` entry beside it carries `DisplayName` and `UninstallString` and never an `InstallLocation`, so an empty one there means nothing. A missing value costs more than the message it produces. `uninstallOldVersion` hands the old uninstaller the right directory as `_?=`, derived from its `UninstallString`, and the uninstaller's own `initMultiUser` then overwrites `$INSTDIR` from the same empty key before its section runs — so it removes nothing while the new version extracts into the `%ProgramFiles%\DSH Desktop` fallback, relocating the app and leaving the old copy behind without saying so.

**macOS installs in place too, from a signed build.** Squirrel.Mac stages an update only when the replacement satisfies the running app's designated requirement, which is why the release build is signed (see the "Trust and signing" section below). The quiet check, the quiet transfer and the rule that only a click installs are the same as on Windows; what differs is the install itself. It takes around fifteen seconds with a bare screen for most of it — Squirrel unpacks and validates the bundle, and ShipIt cannot start swapping until every process of this app has exited — so the click puts up a standing 「正在安装 vX」 notice that says so, and hides the main window whose server is going away. **An installer that fails after the hand-off brings the app back** — Squirrel refusing the staged bundle, or the Windows installer not starting, both reach the updater's `error` event: the notice comes down, the update entry shows the failure and this run stops offering an in-place install, the quitting state is cleared, the server restarts through the ordinary start, and the window comes back. Under the mandatory launch block the served UI stays closed and a dialog offers installing again or quitting.

A build that is **not** signed keeps the old behavior: it compares versions itself and opens the download in the system browser, at launch or on a manual check, never mid-session. Which of the two runs is decided per check by whether `Contents/_CodeSignature/CodeResources` exists — signing writes it, the ad-hoc linker signature does not. A signed build whose in-place path fails in a way retrying cannot fix drops to the same download path for the rest of that run, with one line in the log, rather than ending the check in an error box.

**An interrupted download is retried, and then resumed.** electron-updater keeps nothing of a failed transfer: the full download sends no `Range` header, and any error unlinks the partial file and empties the pending directory. So `src/download-retry.ts` puts three whole attempts — at 2 s, 6 s and 18 s — in front of the failure, and nothing of it is on screen. Retried: a cut or refused connection, a DNS failure, a request timeout, any `net::ERR_…`, and a 5xx, 408, 425 or 429 from the feed. Not retried: an `ERR_UPDATER_*` refusal, an invalid signature, a checksum mismatch, a 4xx — and any failure the classifier does not recognize, which is fatal by default, so one unrecognized error cannot cost three more transfers of the whole artifact. The code is read down the failure's whole `cause` chain, because that is the only place a connection the peer **reset** is named when Node's `fetch` is what met it — it hands the caller a bare `TypeError: terminated` — and the outermost code decides, so a refusal wrapping a network failure is still a refusal. Two failures name their condition in neither place, and each has a rule of its own: a request given up on by `AbortSignal.timeout()` or by an abort is read off `name` — `TimeoutError`, `AbortError` — so one slow answer from the feed costs a retry rather than the macOS in-place tier for the rest of the run; and the status a refusal carried is attached to that failure as `HTTP_ERROR_<status>`, whose message is this repository's own Chinese prose that no pattern here reads, by the shell's own transfer, so a 503 from the feed is retried there and a 404 is not, and by the shell's own manifest read, which otherwise named a refused manifest nothing at all. A fatal failure keeps the tier rule above — macOS drops to the download page for the rest of the run and the check re-runs there.

**What an exhausted plan leads to is the shell's own transfer, which keeps what already arrived.** `src/resumable-download.ts` asks the feed for `bytes=<have>-` with an `If-Range` validator, appends to a `.part` file, hashes as it writes, and verifies the finished file against the manifest's own base64 sha512; a longer, slower plan of its own — 2 s, 10 s, 30 s, 2 min, 5 min — covers an outage that outlasts a route change, because each of its attempts costs a request rather than the artifact. What that plan retries is the transfer being cut: a peer that reset or closed the connection under the body, a connection silent past the 60 s idle bound, and a body that ended short of the length its answer promised — all three raised under one code this shell owns, so the decision rests on nothing a message says. A `206` beginning somewhere the request did not ask for, two passes both answered `416`, and a completed file whose sha512 is not the manifest's are final, because the next attempt meets the same answer. `src/pending-cache.ts` then stages the verified file at `<cacheDir>/pending/<fileName>` with the `update-info.json` electron-updater writes there, and the transfer calls `downloadUpdate()` once more: the library validates the cache, takes the file from it, and emits `update-downloaded` without opening a socket. The library's own transfer always goes first, because it is the half that can download a differential update — on a machine with the previous artifact cached that is single-digit percentages of the bytes, which no resumable full download beats. `.part` files are keyed by version and artifact name and live in the cache directory root, never in `pending`, which any failure inside electron-updater's own download empties; a `.part` left by a version the feed has moved on from is dropped when the next transfer starts. Two things this does not change: the first update after a fresh install still transfers the whole artifact, because the differential path needs the previous `update.zip` in the cache directory, and the mandatory launch block takes no resumable fallback, because the app is shut until the transfer returns. **A precondition to revisit before Authenticode**: electron-updater runs `verifySignature` inside the download task, so the cache short-circuit skips it. This product signs no Windows executable (`electron-builder.yml` sets `signExecutable: false` and no `publisherName`, and `verifySignature` returns null without one), so the check skipped is one that does nothing today — but a build that starts signing must verify the staged file itself. Every retry and the verdict that ends one go to `dsh-server.log`. electron-updater's own lines go to the same file, except its `debug` channel: a differential download dumps its whole block plan through that channel — in one observed update, around 650 lines of JSON naming no version, size or failure — while the `info` lines summarizing the same plan (`File has N changed blocks`, `Full: … To download: … (P%)`) are kept. Two `debug` lines are kept with them, under a `debug:` marker, because nothing else records what they say: `nativeUpdater.update-downloaded`, the only sign that Squirrel finished staging a macOS update, and `updater cache dir: <path>`, which names the directory that decides whether the next update can be differential. The one line electron-updater writes there that carries a stack for a failure it has already recovered from is rewritten rather than passed on: on Windows and macOS alike, `Cannot download differentially, fallback to full download` arrives with a stack trace under the word `error` for an update that then completes by full download, and `src/updater-log.ts` reduces it to one line naming the reason.

**A differential download that asks for more than one range is patched.** electron-updater 6.8.9 attaches no `error` listener to the multipart response its plan issues for more than one byte range, so a connection cut mid-transfer raises an `error` event nothing is listening for — an uncaught exception in the main process, which is Electron's own 「A JavaScript error occurred in the main process」 box over an update that then completes by full download anyway. `patches/electron-updater@6.8.9.patch` carries the upstream one-line fix (electron-builder commit `5eed26b2a9cfd06a1dbe207b25a46ce2c0b05ae9`, PR #10021) until a release ships it. `tests/electron-updater-multipart.spec.ts` pins the behavior against the copy in `node_modules` and stays green either way; what asks for the patch back is pnpm, which fails the install when a bump leaves this exact-version patch unused or unapplicable.

**An interrupted check is retried too, on a plan of its own.** A check transfers one small manifest, so an interruption costs a request rather than the whole artifact, and two retries — at 1 s and 3 s — are the plan; four seconds of waiting also fits inside the fifteen the mandatory launch gate allows, so a gate that meets a dropped connection reaches its verdict from a retry rather than from its own timeout. What is retried is what the download retries, decided by the same classifier. A transient failure that outlives the retries costs that one check and nothing else: **macOS keeps the in-place tier**, the launch gate falls back to reading `latest-mac.yml` itself, and the next check tries in place again. Only a failure retrying cannot fix — an `ERR_UPDATER_*` refusal, a feed carrying no manifest for this channel — drops macOS to the download page for the rest of the run.

### Mandatory updates

The manifests carry one field of this product's own, `minimumVersion`: a client older than it must update before it can be used.

| | Windows | macOS |
|---|---|---|
| **At launch** | The UI is not shown, the server is torn down, and the download starts without being asked. A failed download offers a retry beside quitting. | A blocking dialog offers the download or quitting; the app does not open either way. |
| **Mid-session** | Downloads immediately, with one dialog saying so; the finished download can still be deferred. | One prompt; the next launch blocks. |

An unreachable feed **opens** the gate rather than closing it — a network fault must never lock someone out of their own machine. The line is set explicitly at publish time and then carries forward on its own, so forgetting the flag cannot silently drop it.

### Publishing

```sh
pnpm exec tsx apps/desktop-shell/scripts/publish-update.ts --notes notes.txt             # ship the built version
pnpm exec tsx apps/desktop-shell/scripts/publish-update.ts --notes notes.txt --dry-run   # verify without uploading
pnpm exec tsx apps/desktop-shell/scripts/publish-update.ts --notes notes.txt --minimum-version 0.1.0-rc.8
pnpm exec tsx apps/desktop-shell/scripts/publish-update.ts --notes notes.txt --republish  # repair a cut-off upload
pnpm exec tsx apps/desktop-shell/scripts/publish-update.ts --notes notes.txt --no-prune   # leave every old version in place
pnpm exec tsx apps/desktop-shell/scripts/publish-update.ts --notes notes.txt --no-tag     # leave the shipped commit untagged
```

The script refuses a `dist-app` that disagrees with `package.json`, re-verifies the installer's NSIS integrity CRC, and asserts the build supersedes what the feed serves. Uploads go **artifacts first, checksummed on both ends, manifests last**, so a client polling mid-publish reads the previous manifest naming the previous artifacts — never a manifest pointing at a file still uploading. It also drops manifest entries for artifacts it does not upload: the macOS build lists a dmg beside the zip and only the zip is published, so leaving that entry in would put a 404 in the feed.

**The feed prunes itself, and the two kinds of file are kept to different depths.** Once both manifests are read back from the feed serving the new version, each channel directory is listed and cut to two rules: **the newest two versions keep their artifact, the newest ten keep their `.blockmap`**. Only one of the two is ever fetched from the feed during an update — electron-updater downloads the new version's blockmap, but reads the old version's from the client's own cache and falls back to the feed only when that copy is gone, and it opens the old *artifact* from that cache too, never over the network. So an old artifact (138–174 MB) is there for a rollback or a manual download, while an old blockmap (145–181 KB) is insurance for a client whose cache lost one; keeping both to the same depth would pay the first price for the second benefit. Nothing is deleted until the publish has succeeded, versions are ordered by semver precedence rather than by name (`0.1.0-rc.9` is older than `0.1.0-rc.10`), the manifests and everything this publish uploaded are never candidates, and a name that does not parse into a version is logged and left alone. `--no-prune` skips the whole step; `--dry-run` prints exactly what would go and what would stay and deletes nothing. The decision is `scripts/prune-feed.ts` — a pure function, tested without a server in `tests/prune-feed.spec.ts`.

**A publish that succeeded tags the commit it shipped.** Once both manifests read back and the prune has run, the release is tagged `desktop-v<version>` — annotated, with the release notes as the message, so `git tag -n` shows what shipped — and the tag is pushed to `origin`. Whether that can happen is settled before the first byte goes up: an uncommitted change to a tracked file, a `desktop-v<version>` already pointing at another commit here or on `origin`, or no `origin` at all refuses the publish outright, while the artifacts are still local and re-running costs nothing. Untracked files are not uncommitted changes here — the release runs write their own logs into the worktree and an ignored `.env` lives there permanently, and neither can change what the build compiles.

**Which side already carries the tag decides what runs**, and `origin` is authoritative because it is the copy every other clone reads: nobody carries it, so it is created here and pushed; only this repository carries it at HEAD, so it is pushed; only `origin` carries it at HEAD, so it is fetched, because a second annotated object made here for a name `origin` already publishes is a push git rejects; both carry it at HEAD, so no git runs at all. The last two are the ordinary case when several worktrees of one repository publish. A tag step that fails after the feed is serving says in as many words that the artifacts **are** published and only the tag did not follow, prints the one command that finishes it by hand, and exits non-zero. `--no-tag` skips the step and its preflight; `--dry-run` prints what it would tag and touches nothing. The decision is `scripts/release-tag.ts` — a pure function, tested without a repository in `tests/release-tag.spec.ts`.

On the update host the feed is `/var/www/dsh-updates/{win,mac}`, served by a single appended `location /dsh-updates/` with an `alias`. That nginx has a custom prefix (`/data/third_party/nginx`), is built without the rewrite module, and its master is not under systemd — reload it with `nginx -s reload`, never `systemctl`. The directory carries no BasicAuth because electron-updater sends no credentials.

## Trust and signing

**macOS builds are signed by a self-signed certificate this project holds.** `scripts/sign-mac.cjs` runs `codesign` from the `afterPack` hook, because electron-builder's own pass filters identities through `security find-identity -v` and an untrusted self-signed certificate never survives that filter. `codesign` has no such rule; what it does require is that the identity's keychain be in the user's keychain search list, so the script creates a keychain per build, adds it, signs, and restores the search list in a `finally`. The identity is read from `~/Library/Application Support/dsh-desktop-signing/dsh-desktop-signing.p12` unless `DSH_MAC_SIGNING_P12` and `DSH_MAC_SIGNING_P12_PASSWORD` name another; a missing one **fails the build**, and `DSH_MAC_SIGN=0` is the explicit way to ask for an unsigned one. The certificate is what the update path validates against, so it must not be rotated: its fingerprint is inside the designated requirement every installed client checks.

It is not a Developer ID certificate and the app is not notarized, so Gatekeeper still wants a right-click-open (or `xattr -dr com.apple.quarantine`) for a copy a **browser** downloaded; an update installed by Squirrel is not quarantined and needs neither. Windows artifacts are unsigned and SmartScreen shows its unknown-publisher prompt. The Windows package is cross-built and structurally verified only — smoke-test it on a real Windows machine before handing it to anyone.

This bounds what the update feed can promise. TLS authenticates the server and each manifest's sha512 binds artifact to manifest, so nothing can be tampered with in transit. What the artifacts carry is a signature this project made, not one an operating system will vouch for, so write access to `/var/www/dsh-updates` is still write access to every client's next installer — a macOS client will refuse a bundle signed by anything else, but it has no opinion about *which* build signed by this certificate it is given. Closing that gap means Authenticode on Windows and Developer ID plus notarization on macOS.

Updating one means committing a new tarball and pointing its specifier at it.

The row would come from one version and the code from the other; the launch reports that rather than repairing it, below.

The one that does not is `@haoran/dsh-default-model`: a default model is composition the loader reads, which the page never loads. The build's boot gate reads that declaration from the payload instead of a list: every built-in that has a browser half must be among the client modules the served index names. The boot is no proof for the rest: a bundle the profile names and the Loader cannot resolve is skipped, with one `skipping profile bundle "<name>": …` line on the server's stderr, and the boot continues, so a server that printed its URL line may still be running without `@haoran/dsh-default-model` or the composition layer named after the built-ins.

**The shell boots its own profile, `desktop-shell`, and creates it before it starts the server.** `desktop-shell` has no shipped template, so nothing creates it on demand and the server refuses to boot a profile that does not exist; `src/profile-seed.ts` runs first and writes the three files `initProfile` writes — the manifest, `cordis.patch.yml`, and the `pnpm-workspace.yaml` whose `hoisted` linker is what lets a plugin installed later share the installation's one cordis. The manifest lists `@deepseek-ai/dsh-base`, `@deepseek-ai/dsh-web-app`, the fourteen built-ins, and `@deepseek-ai/dsh-desktop-app`, so `loadProfile` applies each of their `cordis.patch.yml` layers; its `dsh.profile.shipped` names the fourteen, which the Plugins page lists; and each built-in is linked into `$DSH_HOME/profiles/node_modules`, the flat fallback the Loader reaches by the ordinary parent walk from the profile directory it resolves plugin specifiers against. Every write is idempotent: a name already listed is not added twice, a correct link is left alone, an existing file is never rewritten, and syncing the `web` profile below is the only thing that writes a dependency entry or replaces a file the shell wrote. The manifest is written by rename, so an interrupted launch leaves the previous one intact. One line goes to `dsh-server.log` when a launch changed something or left a built-in switched off, and nothing otherwise.

**The profile was called `desktop` until 0.1.0-rc.32, and an installed client's is renamed on its first launch of this build.** Upstream's own Electron application reserves that name — `apps/cli` now refuses `--profile desktop` from every other caller — so `$DSH_HOME/profiles/desktop` becomes `$DSH_HOME/profiles/desktop-shell` in one directory rename that carries the manifest, your `cordis.patch.yml`, `web-migration.json`, and every plugin the profile had; the links inside it name absolute targets, so they keep resolving from the new path. The manifest's `name` is rewritten with it, and that field is also the whole test of whose directory it is: this shell wrote `dsh-profile-desktop` there and upstream's application writes `@deepseek-ai/dsh-desktop-runtime`, so a `desktop` profile carrying anything else is left exactly as it is. A launch that renamed one logs `renamed the desktop profile into place`. A rename that cannot happen — something already standing at the new path — leaves the old directory where it is, says so in the log, and seeds a fresh `desktop-shell`: the plugins you keep in `web` are synced into it again by the sync below, while an edited patch layer and anything installed into the old profile alone stay behind at the old path.

**The last bundle in that list is this product's own composition layer.** `@deepseek-ai/dsh-desktop-app` ([apps/desktop-app](../desktop-app/README.md)) is one `cordis.patch.yml` holding the rows the shipped `dsh-base` and `dsh-web-app` bundles leave to whoever deploys them, plus the one plugin module its own `desktop-server-log` row mounts. It is named after every built-in plugin because its rows target rows those plugins insert, and a row can only patch one a layer before it inserted; that position also lets a row here override every bundle layer above. In an existing profile a missing built-in plugin that the profile's `dsh.profile.shipped` record does not name — one a new build adds, or any missing one in a profile no earlier build recorded — is inserted before this layer rather than appended, while one the record names stays out because the Plugins page switched it off, unless it is a required built-in, which goes back in either way, and a launch that finds a built-in plugin listed after it moves the layer after that plugin. It is not last for good: the same launch appends the plugins it migrates from the `web` profile after it, and the Plugins page appends a bundle it installs there too. Three user layers apply after every bundle layer, in this order — `$DSH_HOME/profiles/desktop-shell/cordis.patch.yml`, then `$DSH_HOME/cordis.patch.yml`, then any `--patch` overlay. Each of its rows is described below by the id it patches. `session-query-sqlite` turns on full-text search over conversation content: the shipped bundles set its `openAt` to `never`, so sidebar search matches session titles and Workspace names only, and this layer sets it to `first-search` over a durable index at `~/.dsh/session-search/desktop.db`. Nothing opens at startup; the first search of a run builds or reconciles the index and every search after it reads only what changed. `llm-deepseek` gets a `retryPolicy.backoff.maxDelayMs` of five minutes, up from the shipped ten seconds. That number is the longest `Retry-After` a rate-limited request will sit out: `@deepseek-ai/dsh-llm-retry` waits out a 429 the provider attached a delay to only while that delay fits under the ceiling, and a `normal` policy that finds it too long lets the turn fail with the rate-limit error instead — which the shipped ten seconds does to the 30-to-120-second windows DeepSeek actually returns. Local backoff is untouched by the change, still five retries topping out under nine seconds, and the transcript counts the wait down in seconds while it runs. To change any of them, restate the whole row in your own patch layer — an id-targeted patch replaces the whole `config`, so a restatement of the search row has to carry `path` as well, and one of the provider row has to carry the model catalog the built-in default-model layer sets on it. That catalog is one row, `deepseek-flash`, restating the shipped adapter's own row for that id field for field: the name and the line under it are this deployment's, and everything else — the context window, the input modalities, `systemPromptUpdate: in-history`, which is what lets a mid-session prompt change append after the cached history instead of rewriting the first message, and `toolUpdate: addition-only`, which lets a tool that joins mid-session arrive as an addition after the cached history — is the adapter's own value, repeated because a whole-table replacement drops what it does not repeat. The row sets no image budget, as the adapter's own row sets none. `vision-switch` gets its `target` named as `deepseek-official` / `deepseek-flash`, the model `agent-default-model` starts every session on, so an image sent on a model without vision moves the session to the model it would have started on rather than to a constant compiled into the plugin; it restates `enabled: true` beside it, the plugin's only other field. `llm-permission-gateway` restates the gateway's fallback route, `provider: deepseek-official` and `model: deepseek-flash`, the gate's two required fields: reviews run on the gate's `judgeProvider` / `judgeModel`, whose schema defaults name the same pair, and fall back to this one for a stored route no adapter serves or an effort the picked model does not offer. A judge choice saved from the gateway's settings page or `/review`, or imported from an older `settings.yaml`, writes that row's whole config into `$DSH_HOME/profiles/desktop-shell/cordis.patch.yml`, and from then on this row no longer reaches that machine. The same row adds `plugin_manager` to the gateway's `alwaysAsk`, restating the gateway's own `browser_auth` entry beside it, because the field replaces the gateway's default map. `plugin-manager` sets `pnpmCommand` to the pnpm launcher the shell names in `DSH_DESKTOP_PNPM` and `requiredModules` to `@haoran/dsh-crash-resume`, the same list as `REQUIRED_WEB_BUNDLES` in `src/profile-seed.ts`, and keeps dsh-base's `disabled` expression, so upstream's plugin installer and its sidebar page stay on; "Plugin management" below has the whole arrangement. `office-to-pdf` carries no row: the shipped row stays on, and its converters use the engine the shell downloads on request, described under "Office engine service" below. `ui-chat` sets `transcriptView: compact`, so a work-details group's header names its categories only; a Chat display preference saved in Settings writes that row's config into the profile's own patch layer, and from then on this row no longer reaches that machine. The layer also inserts `desktop-server-log`, which appends the server's own logger records — errors, info, and warnings from every plugin, named loggers such as `auto-compact` included — to `dsh-server.log` as lines starting `[server-log]`; the shell names the file to the server child in `DSH_DESKTOP_SERVER_LOG`, and the row stays off without it.

A profile the shell does not recognize is left exactly as it is, and the launch continues without the built-in plugins: an unparsable manifest is left for the server's own diagnostic, a manifest that declares no bundle list is treated as hand-composed, and a real directory sitting where a link belongs is reported rather than removed. A profile directory that cannot be written at all is the one thing the launch cannot work around; the log line says so, and the server's own diagnostic follows it.

**A built-in this build withdrew is taken back out of the profile that has it.** The server skips a name in `dsh.profile.bundles` it cannot resolve and writes one `skipping profile bundle "<name>": …` line to its stderr on every boot, so an upgrade that simply stopped shipping a package would leave that name, and that line, in every profile the old build seeded. `WITHDRAWN_WEB_BUNDLES` in `src/profile-seed.ts` names those packages; a launch drops such a name from the manifest, and removes the flat-fallback link it made for it. Only the shell's own leavings go: a link into anything other than this build's payload stays, and so does the bundle entry whenever the package still resolves — a copy you installed with `dsh plugin --profile desktop-shell add` is left in place under the ownership that put it there. Such a copy is the author's published release, without the changes this repository applied to the tarball it shipped. `@sumomok/dsh-edit-rerun` is the first entry; it shipped in 0.1.0-rc.21's own pre-release builds and was withdrawn before that version was published. `dsh-better-sidebar` is the second; it shipped through 0.1.0-rc.32, and 0.1.0-rc.33 withdrew it in favour of upstream's own `ui-sidebar-right`. `dsh-at-file` is the third; it shipped through 0.1.0-rc.33, and 0.1.0-rc.34 withdrew it in favour of upstream's own `@` references — the composer's `ui-reference` menu, whose files `file-reference-local` serves.

**The plugins you install into the CLI's `web` profile stay in step with the desktop profile, on every launch.** Every build before 0.1.0-rc.17 booted `web`, and every build from rc.17 through rc.22 created a desktop profile holding that build's built-ins and nothing you had added, so an upgrade from either left your own plugins in a profile the shell no longer composes; a plugin you install into `web` after that keeps arriving in `desktop-shell` on the next launch, the same way. Every launch reads `~/.dsh/profiles/web/package.json` and takes every name in its `dsh.profile.bundles` that is not one of the two in-box bundles, not a built-in above, not withdrawn, and not already tracked: `~/.dsh/profiles/desktop-shell/node_modules/<name>` gets a link to the web profile's own copy, and — only when the package mounts cleanly — the name is appended to the desktop manifest's `dsh.profile.bundles` and the version the web profile declared for it is copied into `dependencies`. Nothing is installed and nothing is copied — the web profile stays the one place the package lives, so `dsh plugin --profile web add <package>@latest` still updates the copy both profiles mount, and a machine with no package manager needs none. `web-migration.json` in the desktop profile is the shell's own record of what it has synced, and the cross-component contract `@haoran/dsh-plugin-updates` reads to show what follows:

```json
{
  "from": "web",
  "migrated": ["dsh-toolbox"],
  "defective": [{ "name": "dsh-broken", "kind": "entry-missing", "detail": "…", "at": 1756100000000 }],
  "removed": ["dsh-taken-off-desktop"],
  "permissionPatch": "removed"
}
```

An older marker with only `from` and `migrated` reads as if `defective` and `removed` were empty arrays. Only the very first sync a profile ever runs — the one that finds no `web-migration.json` at all — copies `cordis.patch.yml` and `pnpm-workspace.yaml` wholesale from the paragraph below; every later sync leaves both files exactly as they are, so nothing here overwrites an edit you made since.

**A plugin that cannot mount is disabled, never dropped and never silently absent.** A package under active development is a git install without a build step run yet, a version that stopped declaring `dsh.bundle`, or one the server's own loader refused at import time — three distinct field cases. The server skips such a plugin and keeps running, so a name `dsh.profile.bundles` kept would be missing on every boot with nothing on screen to say so. So a name in that state stays linked — inspectable, repairable — but out of `dsh.profile.bundles`, and its entry moves into the marker's `defective` list with one of three kinds: `entry-missing` (the manifest's `exports` or `main` names an entry file that is not on disk — the unbuilt-git-install case), `not-a-bundle` (the installed version dropped `dsh.bundle`), or `load-failed` (the server did not load it — read from that boot's own output, below). The log line is `disabled migrated <name>: <reason>`, one line per name, with the reason distinct per kind.

**Deleting the desktop-side link is a removal, not a loss.** A name whose link you take out of `~/.dsh/profiles/desktop-shell/node_modules/` while the web profile still holds a healthy copy moves into the marker's `removed` list — `removed <name>: no longer linked in the desktop profile; still installed in the web profile, so it will not return on its own` — and stays there: a tombstone, never re-synced automatically. A name whose web copy is gone too is dropped from the marker with nothing left to track.

**Your `web` patch layer comes with the first sync, unless you have written one of your own.** While `~/.dsh/profiles/desktop-shell/cordis.patch.yml` is still the empty template the shell writes, the web profile's file replaces it verbatim — comments, `!!js` expressions, and all — and `pnpm-workspace.yaml` follows the same rule. Once you have edited the desktop's copy, neither file is touched and the log names the plugins whose rows to carry over by hand: `skipped cordis.patch.yml: the desktop copy is already edited; carry the web profile's rows for dsh-toolbox over by hand`. Nothing is ever merged — a patch layer is YAML only the loader's own schema reads, and combining two of them would be a second implementation of that schema.

**The `yolo-access` preset table an older build copied in is taken back out, once.** That first sync carried whatever the `web` layer held, and on the machine this pairing came from that was the `permission` preset table and the `llm-permission-gateway` row, both of which `@haoran/dsh-llm-permission-gateway` has declared in its own bundle layer since 0.1.3. The gateway row is taken in either form a patch layer writes it — the package's own `- insert:`, and the top-level `- id:` an id-targeted copy takes — while every field in it is still the shipped value. The id-targeted form is the one worth taking out rather than a harmless duplicate: such a patch replaces the row's whole `config`, so a copy carrying 0.1.3's two fields keeps pinning that judge route and drops whatever a later release sets on its own row. An entry that inserts the gateway beside other rows is never one of yours to lose either way — it is named in the log and left where it is. Every bundle layer applies before your patch layer, so the copy shadows the shipped table: the access-mode control keeps offering the 0.1.3 rows, in the 0.1.3 order and wording, on a build whose plugin declares four rows in another. A launch removes such a row while it is still what was copied — every field and every value, whatever order they were written in — and takes with it the comment run written directly above it, with no blank line between. Every other entry and every other comment stays where it is, `!!js` expressions and all; `retired the permission preset table from cordis.patch.yml` says so. A row edited anywhere, the gateway's judge route included, is yours and stays: `skipped cordis.patch.yml: the permission preset table is not the one this shell wrote; left exactly as it is`. The decision — including the `absent` a layer still holding the empty template reaches without being parsed — is recorded as `permissionPatch` in `web-migration.json`, so no later launch reads the file again. A profile that has never synced has no record to write into, and is read once per launch instead.

**The settings a 0.1.0-rc.33 client kept in `~/.dsh/settings.yaml` are prepared for the server's one-time import, once.** From 0.1.0-rc.34 the server renames that file to `settings.yaml.imported` on its first start and writes each section into the profile row whose id is the section name; a section with no such row, or with one key that row does not take as a live setting, stays behind in the renamed file, which nothing reads again. So before that server starts, `src/settings-migration.ts` first moves the file to `settings.yaml.pre-rc34`, the untouched original, and then writes the rewritten copy back as `settings.yaml`. `agent-presets` becomes `agent-preset-registry` with `selectedDefault`, `code` renamed `ptc`, except where mode selection was off: that client's new sessions ran the deployment default, `standard`, and still do. `ui-theme` is written into the profile's own `ui-theme` row, which the boot page reads. The withdrawn `at-file` section turns the `ui-reference` row off where @ references were off, and its exact file names join the `file-reference-local` row's `excludedDirectories` after the fifteen directories that row excludes by default; nothing in the new @ references hides a file by name, so such a name only hides a directory called that. The gateway, auto-compact, MCP server and balance sections keep only the settings their plugins take, each with a value its plugin accepts. The balance section's `prices` table is dropped as well: the plugin prices from its maintainer's read-only feed and only logs a warning about a stored table, which it does not read. An `llm-deepseek.baseURL` on `api.deepseek.com` is a chat-completions address this build's adapter does not speak, so it is dropped in favour of the adapter's own; any other address is kept, and the window says, over the loaded app, that it may need changing; the marker keeps that message until you have dismissed it, so a launch that stops before the app loads shows it on the next one. A gateway `- insert:` row an earlier launch kept because it had been edited becomes an id-targeted row with the same config, since the gateway's own bundle already inserts that id; that row, and any id-targeted gateway row whose `config` has no `alwaysAsk`, gets the desktop layer's `alwaysAsk` map. Where `web-migration.json` exists without its `permissionPatch`, the gateway rows wait for the launch whose seeding has taken the copied permission rows out of the patch layer, so that a seeded copy is never rewritten into a row that step no longer recognizes; a profile without that file never received those rows, and its gateway rows are completed on the same launch. Every value dropped is listed with the reason in `settings-migration.json` in the desktop profile, a record of its own beside `web-migration.json`, whose `state` turns `done` at the end. A launch whose migration stops after the move starts its server with no `settings.yaml`, so that server imports nothing and runs on the profile's rows and the shipped defaults for that one launch; the next launch writes the migrated copy from `settings.yaml.pre-rc34` for the server to import. The server never imports the file as the rc.33 client left it. When another profile's server imported the file first, the shell copies `settings.yaml.imported` to `settings.yaml.pre-rc34` once and migrates it, so this profile imports it too; a `settings-migration.json` that cannot be read copies nothing. Every file this writes is readable by you alone, because those settings hold MCP server environment values.

**A migrated plugin the server would now refuse is taken out of the bundle list, the same way.** The package sits in a directory you own and keep changing: emptying or reinstalling the `web` profile leaves the link dangling, and updating the package there can replace it with a version that is not a plugin bundle at all. So every launch re-checks every name in `migrated` against the same `bundleDefect` predicate, and — depending on what it finds — disables it as defective, tombstones it as removed, or drops it outright: `dropped migrated dsh-toolbox: no longer resolves in the web profile` is the one case with nothing left to show, because both the desktop link and the web copy are gone. A name you have since taken over yourself keeps its entry, whether that is a copy from `dsh plugin --profile desktop-shell add`, a link of your own at that path, or a package this build started shipping. What is not checked is whether a plugin installed under an older harness suits this one: its unmet peers fall through to the flat fallback this installation heals, so it shares this build's cordis, but nothing here can answer whether its code matches this build's API.

**A migrated plugin the server did not load is recorded from that boot's own output, and stays off from then on.** Admission catches an unbuilt install and a package that stopped being a bundle, but not every way the server can refuse one — the field case is `Cannot find module '…/lib/index.js'` for a git install with `src/*.ts` committed and no `lib/` at all, and the compatibility check refuses a package whose `@deepseek-ai/dsh` peer range excludes this build. The server reports each of these and keeps running without the plugin, on one of three stderr lines: a row of its startup audit block, `<id> (<name>): failed to import`; `<bin>: skipping profile bundle "<name>": <reason>`; or `<bin>: disabling profile plugin row "<id>": <reason>`, which names a row, so the shell looks the id up in each migrated package's own bundle layer. The audit block can arrive after the URL line, so the shell reads every line of both streams for as long as the server runs. A name this shell migrated moves into `defective` with kind `load-failed` and out of `dsh.profile.bundles`, and the shell logs `disabled migrated <name> after it failed to load (<detail>); it stays off from the next launch`; that boot runs without it and nothing restarts. The detail of an import failure is only `failed to import`: the import error itself goes to the server's own logger, whose records the `desktop-server-log` row appends to `dsh-server.log`, an error logged before that row mounted included. A boot that exits before its URL line after naming a migrated plugin is started again once, logged as `disabled migrated <name> after it failed to load; retrying startup`; a module the output does not name, or a second failure, reaches the ordinary boot-failure page.

**No screen shows a defective or removed plugin.** The line that records one in `dsh-server.log` is the only place it appears. To bring one back, delete its entry from `defective` or `removed` in `~/.dsh/profiles/desktop-shell/web-migration.json`; the next launch admits it again when it mounts.

**The desktop's profile is separate from the CLI's; the rest of the harness home is not.** Sessions, credentials, and model settings live at the root of `$DSH_HOME`, so a terminal `dsh web` and the desktop window read the same ones. What is separate is which plugins are mounted: `dsh web` composes `$DSH_HOME/profiles/web/`, which the desktop never writes to. To give the CLI these plugins as well, install them there with `dsh plugin --profile web add <package>`. Coming the other way, the fourteen above are already in the desktop profile and the sync above keeps bringing the rest across; anything you add to `web` reaches `desktop-shell` on your next launch, or immediately with `dsh plugin --profile desktop-shell add <package>`, and is listed under `dependencies` in `~/.dsh/profiles/web/package.json`.

**If you installed one of these plugins yourself before this build**, the profile's own `node_modules` still holds that copy, and the Loader finds it before the shipped one while the patch layer keeps coming from the payload. The launch says so — `warning: profile copy @sumomok/dsh-quote-message@0.3.1 shadows the shipped 0.4.0 module` — and changes nothing, because the profile's dependencies belong to whoever installed them. `dsh plugin --profile desktop-shell remove <name>` drops the profile's copy and leaves the shipped one, which is the state a fresh install has.

**To turn one off, use its switch on the Plugins page.** The page lists the fourteen under **Installed** with a **Built-in** tag, a switch for the whole plugin, its version, and its component rows with their own switches, and offers no uninstall. Each launch writes the fourteen names into `dsh.profile.shipped` in `~/.dsh/profiles/desktop-shell/package.json`, and the switch removes a name from `dsh.profile.bundles` only, so a later launch finds it recorded and leaves it off; a launch that finds it switched back on keeps it on. The link to the payload stays, so a new build's version reaches it while it is off. `@haoran/dsh-crash-resume` is the exception: the desktop composition layer names it in the `plugin-manager` row's `requiredModules`, so its switch and its component row's switch are locked, it has no uninstall, and the page reads **This app needs it; it cannot be switched off or uninstalled.**; a profile that switched it off before gets it back on the next launch. Disabling its `crash-resume` row in the patch layer below still turns it off, and neither the page nor the `plugin_manager` tool can turn that row back on; deleting the row from the file does. A `plugin-manager` row in that patch layer that restates the row's `config` without `requiredModules` removes the lock the same way, because a patch replaces the whole `config`. To turn off a single component instead, disable its row in `$DSH_HOME/profiles/desktop-shell/cordis.patch.yml` — `screenshot` for the capture tool, `ui-quote-message` for quoting, and `balance` for the balance chip:

```yaml
- id: screenshot
  disabled: true
```

`@` mentions of files and sessions are no built-in: they are upstream's `ui-reference` row, which the same file disables the same way.

**The gateway is the one built-in whose row you should not disable on its own.** Its patch layer contributes two rows — the gate, and the preset table that adds 自动审查 — and disabling the gate leaves that row in the control with nothing behind it: a mode named for review that turns the sandbox off and reviews nothing, which is strictly worse than 完全权限, where the `never` approval policy at least refuses what the sandbox would have raised. Select another access mode first, and restate the `permission` row's `presets` in your own `cordis.patch.yml` without `yolo-access` if you want it gone from the control as well; an id-targeted patch replaces the whole `config`, so that restatement has to carry the presets you keep.

## The render service

**The shell lends its own Chromium to the server**, so a screenshot does not depend on whether the machine has Chrome or Edge installed. Before it spawns the server, the main process opens an HTTP listener on `127.0.0.1` and an ephemeral port, mints a 32-byte token, and puts both in the environment of that one child — `DSH_DESKTOP_RENDER_ENDPOINT` and `DSH_DESKTOP_RENDER_TOKEN`, never on the shell's own `process.env`, so no other process the user starts inherits them. `@haoran/dsh-screenshot` reads them on every call. A harness that finds neither renders through a headless system browser instead, which is what every non-desktop install does; a launch whose listener could not be opened logs one line and continues, and its screenshots take that same fallback.

The render request is `POST /render`, with `authorization: Bearer <token>`, `content-type: application/json`, and the body `{ url, width, height, fullPage?, delayMs?, timeoutMs?, onTimeout?, blockHosts?, headers?, cookies?, userAgent?, partition? }`; the three sign-in routes below carry the same two headers and a JSON body of their own. Everything `POST /render` can be answered with:

| Answer | When |
|---|---|
| `200 image/png` | The capture, as PNG bytes, at exactly the requested viewport size — or, for a request that sent `onTimeout: "capture"`, what the page had painted when its deadline passed |
| `400` | Not JSON, not an object, a body over 64 KB, a field of the wrong type, `width` or `height` outside 16–4096, `delayMs` outside 0–10000, `timeoutMs` outside 1000–120000, an `onTimeout` other than `fail` or `capture`, a `blockHosts` entry that is not a host pattern or that matches the page's own host, a `url` that is not absolute, a `headers` or `cookies` entry outside its bounds or its grammar, a `userAgent` that is empty, over 512 characters, or not a header value, or a `partition` that is not a string or is over 278 characters |
| `401` | Missing or wrong bearer token |
| `404` | Any path or method other than the four routes |
| `422` | A well-formed URL whose scheme is not `http`, `https`, or `file`, `headers`/`cookies` on a `file:` URL, a `partition` outside `persist:dsh-render-login-<registrable-domain>`, or a `partition` on a `file:` URL or beside `cookies` |
| `500` | The page failed to load or the capture failed; the line carries the Chromium error code |
| `503` | Four requests are already accepted |
| `504` | The request passed its deadline with no pixels to answer; the line says what the render was waiting for |

Every failure body is one line of `text/plain`, because its reader is a tool that quotes it into the message the model sees.

**Every answer a render reached carries a report** on `x-dsh-render-report`: the whole record as JSON, percent-encoded so that `decodeURIComponent` returns it exactly, on the 200, on the 500 that refuses a failed render, and on the 504. A refusal no render was started for — a validation 400 or 422, a 401, a 404, the 503 — carries none. A header rather than a body, because the two answers that need it most already own their body; a caller reads one structure whichever way the render ended.

| Field | What it says |
|---|---|
| `version` | `1`; a reader that does not know the number ignores the rest |
| `outcome` | `complete`, `timeout` (both the 504 and a partial 200), or `failed` |
| `phase` | `queued`, `navigating`, `loaded`, `delaying`, `measuring`, `resizing`, `capturing` |
| `elapsedMs`, `deadlineMs` | How long the request had been accepted, against the deadline it was running under |
| `requestedUrl`, `mainDocument` | What was asked for, and `{ url, status, redirected, title }` of where the main frame ended — `null` until it reports a navigation |
| `loadEventFired`, `firstPaint` | Whether the load event fired, and whether the window had painted a frame |
| `requests` | `{ total, completed, failed, pending, blocked }`, counting requests that reached the wire and, separately, the ones `blockHosts` cancelled |
| `pending`, `failed` | Up to 5 each: `{ url, type, ageMs }` oldest first, and `{ url, type, error, status }` in the order they failed |
| `hosts` | Up to 5 `{ host, pending, failed, blocked, maxAgeMs }`, most pending first — which is what a caller puts into `blockHosts` |
| `console` | `{ errors, warnings, samples }`, with up to 3 error messages quoted |
| `mainFrameError`, `renderer` | `{ code, description }` from `did-fail-load`, and `{ gone, unresponsive }` from the render process |
| `capture` | `{ partial, width, height }` of the pixels this answer carries, or `null` when it carries none |

**The encoding escapes `%` as well**, on this header and on `x-dsh-render-landed-url`, so what goes on the wire is exactly what `decodeURIComponent` inverts: a URL carrying `%20` would otherwise come back with a space in it, and one carrying a bare `%zz` would throw the reader's decode and cost it the whole value. A reader of either header decodes it; nothing else does, since neither is ever read as a URL directly.

The header is bounded by construction rather than cut to fit, because a cut header is JSON nobody can parse: every list is capped in count, every URL, host, and title at 96 bytes of the encoded header, every message at 160, and each cut string ends in an ellipsis. With every list full the header measures 4.2 KB, under a 6 KB ceiling. The cap counts encoded bytes rather than characters, so a page whose URLs and title are in Chinese, or full of escapes, fits the same ceiling — a character outside printable ASCII costs three bytes there, and so does a `%`.

**A request owns its deadline.** `timeoutMs` is measured from acceptance, between 1000 and 120000; a request that names none gets 25 seconds, which is what every caller written before the field existed gets. A number outside the bounds is refused rather than quietly moved, because a caller that asked for three minutes and silently got two would arm its own abort on the number it sent and give up before the answer arrived. Callers that name one own the relationship the other way round: `@haoran/dsh-screenshot` arms its fetch abort at `timeoutMs + 5000`, so the shell's answer always arrives first.

**`onTimeout: "capture"` turns a passed deadline into pixels.** At the deadline the shell takes `capturePage()` of what the window had painted, and answers 200 with that image and `outcome: "timeout"`, `capture.partial: true` — a page whose avatars hang has usually laid out everything else, and that image plus the report is a better answer than a sentence. Only a request that asked for it can receive a partial image, so a caller that reads 200 as "this is the finished page" is never wrong. The capture is capped at 3 seconds and the render is abandoned either way; if it fails or runs past the cap, the answer is the ordinary 504 with its report. The queue advances the moment the deadline passes, not when the capture ends, so a capture that hangs delays nothing but itself.

**`blockHosts` is the remedy the report names.** It is a list of up to 32 host patterns — an exact host, or `*.suffix` matching that suffix's subdomains and not the suffix itself, each at most 253 characters, matched case-insensitively — whose requests are cancelled in `onBeforeRequest` before they go out and counted in `requests.blocked`. A pattern matching the host of the page being rendered is refused with a 400 naming it, since a render that cancels its own document would fail with nothing to say. This is the one blocking `webRequest` hook the shell registers, and only for a request that carries the field: a render that names no `blockHosts` is timed exactly as it was without the feature.

**A request may carry the session the page needs.** `cookies` is an array of up to 32 `{ name, value, domain, path?, secure?, httpOnly?, expirationDate? }` — Chromium's own members, so a caller sends what it exported from a browser — set on the render's own session before the load. They reach the page's subresources as well as its document, which is the point: a signed-in page whose images all 401 is not the page anyone asked to see. `domain` is required and is what each cookie is scoped to, so one request carries the cookies of every host its page talks to; `path` defaults to `/` rather than to RFC 6265's default-path, which is the directory the cookie was stored from rather than the site — a cookie left at `/app/issues/` reaches none of the `/api/…` requests the page makes. `headers` is a name→value map put on the main-frame navigation only, which is what a bearer token or a host override needs; a `cookie` header is refused by name and pointed at `cookies`, since one sent that way would cover the document and nothing in it. Cookies and headers are bounded together at 24 entries and 8 KB, names must be HTTP tokens, header values are visible ASCII plus space and tab (a newline would append a header nobody sent, because `loadURL` takes them as one newline-separated string), and cookie values are RFC 6265 cookie-octets. A refusal never quotes a cookie value back, because that value is the credential the field exists to carry.

**Each render holds its own cookie store.** The window's partition name carries a fresh UUID and no `persist:` prefix, so the session is created with the window, lives in memory, and is destroyed with it: the caller supplies the credential, the shell keeps none, one render's cookies cannot be read by the next, and nothing is written to disk. The smoke proves the second half rather than assuming it — a render with a session cookie, then the same URL with none, which the site answers with its sign-in redirect again. The exception is a request that names a login partition: it renders in that persistent store, which is the one render session written to disk.

**A page behind a sign-in is captured after the user has signed in to it.** A partition that starts empty renders it logged out, and nobody has exported its cookies to send in `cookies`. `POST /login-grant` takes `{ url, partition }` and answers `{ nonce, expiresInMs }`; it opens nothing. The url's host must be the partition's registrable domain or a subdomain of it, or the grant is refused, because a pair that disagreed would file one site's cookies under another site's name. A nonce is single-use, spendable for 30 seconds, and at most 8 may be outstanding — a grant past that is a 503.

**`POST /login` takes `{ nonce }` and answers `{ landedUrl, sameSite }`** when the user closes the window. The page and the partition were fixed when the nonce was minted, so nothing in this body chooses them. One window is open at a time and a second call is a 503, checked before the nonce is spent so a caller that retries still holds it. An unknown, spent, or expired nonce is a 403; a 504 says the ten-minute login deadline passed or the shell is shutting down.

**`DELETE /login-sessions` is signing out.** It takes `{ partition }`, calls `clearStorageData()` on it — the cookies, the caches, and every storage backend Chromium keeps for a partition — and answers `{ partition, cleared: true }`. The only partition all four routes accept is `persist:dsh-render-login-<registrable-domain>`, the domain lowercase and computed by the caller, so a caller can neither read nor erase the partition the user's own window runs in.

**The sign-in window is visible and names the site that is asking.** Its title is locked to the current origin on `did-navigate`, `did-redirect-navigation`, `did-navigate-in-page`, and `page-title-updated`, whose default it cancels so the page cannot write its own title; it is `resizable: false`, which is also how the shell tells the app's own window apart from every other. Permission requests, permission checks, downloads, and audio are refused exactly as in a render window, devtools stay off, and `sandbox`, `contextIsolation`, and the absence of Node integration are untouched. Two things are relaxed: a window the page opens becomes a navigation of this same window rather than being dropped, which carries an OAuth hand-off through with no second window opening, and dialogs work, because a real sign-in reports a wrong password through `alert()` and `confirm()` and the user is looking at this window.

**The login partition is the one thing this service lets persist.** Its values live in Chromium's own encrypted profile store under the app's userData directory; nothing in the shell reads a cookie value out of it, and no route returns one. A render naming a partition carries no `cookies` of its own, because writing a caller's jar into a store that outlives the request would persist a credential on its behalf.

**`userAgent` is what the render says it is.** Electron's own default is `…Chrome/150.0.7871.224 Electron/43.4.0 Safari/537.36`, which tells every page the agent looks at that it is being looked at by this shell — and some sites answer a different page for it. A request that names one gets it on both the session and the web contents before the load, so the document, its subresources, and `navigator.userAgent` all report it; a request that names none keeps the default. It must be a non-empty header value of at most 512 characters.

**A `200` says where the render landed** when the main frame ended somewhere other than the requested URL, on `x-dsh-render-landed-url`, percent-encoded the same way as the report and cut at 96 characters. A screenshot of a sign-in page is a correct render of the wrong page and the pixels do not say which of the two it is; the plugin turns this header into one sentence in the tool result naming `cookies` and `headers`. No header is sent when the frame stayed where it was pointed, comparing normalized URLs, so the trailing slash Chromium adds to an origin is not a redirect.

**The capture is the size that was asked for.** `capturePage` returns a bitmap at the display's scale factor — 2 on a Retina Mac, 1 on most Windows machines — so a request for 1440x900 would otherwise answer a different image on each. The window keeps that native scale, because forcing one is a process-wide switch that would reach the user's own window, and the capture is resized to the requested CSS pixels before it is encoded: a full-page one to the requested width and the height it measured. Downsampling a 2x capture costs nothing a 1x render would have had.

**A 504 names what the page was waiting for**, so a caller can tell a hung image from a dead proxy from a wedged renderer. The line says which phase the render was in — queued, loading the page, or already past the load event and waiting out `delayMs`, measuring, resizing, or capturing — and, while the page is still loading, the main document's HTTP status, where the main frame landed when that is not where the request pointed, and up to three of the requests still in flight with their Chromium resource type: `render timed out after 25000ms: main document 200, load event not fired, 7 requests pending: [image] https://www.gravatar.com/avatar/…, [image] …, [script] … (+4 more)`. Each URL is cut at 96 characters and the whole line at 500, which is what `@haoran/dsh-screenshot` quotes into the model's message; the report header says the same thing in a structure. The render itself is unchanged by any of it: the shell reads it from main-process events — `did-navigate`, `did-redirect-navigation`, `page-title-updated`, `ready-to-show`, `did-fail-load`, `console-message`, `render-process-gone`, `unresponsive` — and the session's non-blocking `webRequest` hooks, which observe requests without holding them.

**Each render gets a hidden window that shares nothing with the app's own.** Its session has no `persist:` prefix, so it lives in memory and dies with the window: a rendered page cannot read or write the cookies, storage, or caches of the window the user is working in, and nothing it stores outlives the request. A request that names a login partition runs in that persistent store instead, and everything else on this list still applies to it. There is no Node integration, no `webview`, no devtools; every permission request is denied, and every download and every window the page tries to open is refused. Dialogs are disabled, so `alert()`, `confirm()`, and `prompt()` open no native modal on a window the user cannot see and block no page thread behind one, and the window is muted, so an autoplaying `<audio>` element reaches no speakers. The window is destroyed on the reply, on a load failure, and on the deadline.

**What bounds it**: one render at a time, four accepted requests at once (one rendering and three waiting), a deadline measured from acceptance rather than from the start of the render — the request's own `timeoutMs`, 25 seconds by default and 120 seconds at most — and 3 seconds for a partial capture at that deadline. A `fullPage` capture measures `document.documentElement.scrollHeight` and resizes to it, clamped at 8192 px, because a document with an infinite scroller reports a height that grows while it is measured.

**Three mechanisms bound who reaches the service.** The listener binds loopback, so nothing off the machine connects to it at all. The token is compared in constant time, so a local process that finds the port cannot use the service without it. No CORS header is ever sent while every path and method outside the four routes answers 404, so the preflight that an `authorization` header and a JSON content type force a browser to send is refused — which is what keeps a page in the user's own browser out.

After a build, this checks the half the unit suite cannot — that a hidden window paints at all:

```sh
pnpm --filter @deepseek-ai/dsh-desktop-shell run build:ts
pnpm --filter @deepseek-ai/dsh-desktop-shell run render-smoke
```

It renders a local file in a real Electron and checks that the capture is exactly the requested viewport whatever the display's scale factor is, that a full-page capture is taller than it, and the 401, 422, and 500 answers. One case serves a page that redirects everyone without a session to its sign-in page, and checks all three outcomes against a real Chromium: without a session the reply carries the landing header, with a cookie and with a header it does not. The next serves a page under `/app/issues/` with one image beside it and one under `/api/`, and asserts what that site received rather than what came back as pixels: the cookie is on all three requests, and an extra header is on the navigation and on neither image. A page that calls `console.error` proves that `console-message` and the page title reach the report. The rest point a page at a local listener that accepts the connection and never answers, which is what no injected renderer can stand in for: under `onTimeout: "capture"` the reply is a 200 whose PNG decodes at the requested size with `outcome: "timeout"` and the hanging host named, with `blockHosts` naming that host it completes in under a tenth of a second with `requests.blocked` at 1, and left alone the 504 names that image in its line and in its report.

## Plugin management

**Upstream's plugin manager installs, enables, disables, and removes plugins.** The desktop composition layer leaves dsh-base's `plugin-manager` Host row and dsh-web-app's sidebar **Plugins** page on, so the page acts on the `desktop-shell` profile's bundles the way it does on any profile-backed `dsh web`, and the web app's cordis preset mounts the `plugin_manager` agent tool over the same service. The page has no per-package update action and no undo. The built-ins are seeded, not installed, and move when the application is updated.

**An install runs the pnpm the installer shipped, through a launcher script.** `scripts/package.ts` stages the `pnpm` version the repository's own `packageManager` pins into `staging/pnpm` with `npm pack`, and both platforms' launcher scripts from `src/pnpm-launcher.ts` into `staging/pnpm-launchers`; `verifyStaging` requires both scripts, and the macOS one executable. `scripts/after-pack.cjs` copies pnpm to `resources/runtime/pnpm` — extraResources cannot carry it, because pnpm's own tree contains a `node_modules` and the builder's copier hard-excludes those — and the target platform's script to `resources/runtime/dsh-pnpm` or `resources/runtime/dsh-pnpm.cmd`. The script runs `runtime/pnpm/bin/pnpm.mjs` under `runtime/node` with `runtime/` first on `PATH`, because `pnpm.mjs` starts with `#!/usr/bin/env node` and the machine has no Node, and the plugin manager's `pnpmCommand` names one executable with no arguments of its own. The shell gives the server child alone `DSH_DESKTOP_PNPM=<script path>`, and the desktop layer's `plugin-manager` row reads it as `pnpmCommand: !!js process.env.DSH_DESKTOP_PNPM ?? 'pnpm'`. A development launch sets nothing, and `pnpm` on `PATH` is used.

**Upstream's auto-review stays off even when the Plugins page installs it.** The payload withholds `@deepseek-ai/dsh-experimental-auto-review`, and a registry can still supply it; its layer would mount upstream's Auto beside the permission gateway, which reads the same knob pair, so one call would be reviewed twice. Every launch keeps this row, under a comment saying what it is for, in `$DSH_HOME/profiles/desktop-shell/cordis.patch.yml`, which applies after every bundle layer:

```yaml
- id: auto-review
  disabled: true
```

An `auto-review` row there that says anything else — the Plugins page's enable writes `disabled: false` onto this one — is left as it is, with one line in the launch log. Deleting the row lasts only until the next launch. While the package is not installed, `dsh --profile desktop-shell --dump-config` prints `patch: entry "auto-review" not found` for the row, and the server runs without it.

**Every `plugin_manager` call goes to a person.** One call can install code that runs outside the workspace sandbox, or disable a row — the permission gateway's own included. The desktop layer's `llm-permission-gateway` row therefore adds `plugin_manager` to the gateway's `alwaysAsk`, beside the gateway's own `browser_auth` entry, which it restates. Under 自动审查 and the walled modes the gateway asks you before any review model sees the call, with a sentence naming what it can change. Under 完全权限 nothing asks.

## Voice input

**Voice input ships switched off, as upstream ships it.** `@deepseek-ai/dsh-experimental-voice-input-bundle` is one of upstream's `OPTIONAL_BUNDLES`: the payload carries it, no bundle selects it, and upstream's **Plugins** page offers it for a person to switch on. Its layer adds the speech-to-text service, the local SenseVoice recognizer, the HTTP API, and the microphone button in the input box. Switching it on downloads nothing.

**The recognition model is downloaded when a person asks for it, not shipped.** A microphone click before the model is ready opens a prompt that leads to the voice input's plugin details, and its **Download and prepare** button fetches the INT8 SenseVoice model (about 239 MB), its `tokens.txt` (about 0.3 MB), and the Silero VAD model (about 1.8 MB), each pinned to a revision and checked against its sha256. The sources are `huggingface.co` and `hf-mirror.com`: by default the recognizer sends each a `HEAD` request, tries the first that answers, and falls back to the other; a source picked on the card is used alone. The files land under `$DSH_HOME/speech-to-text/sensevoice/models/`. A machine that reaches neither source cannot use voice input.

**Each payload carries its own platform's recognizer runtime.** Recognition runs in a worker the server starts with the bundled Node runtime, which loads `sherpa-onnx-node` and the platform member beside it: `sherpa-onnx-darwin-arm64` (about 34 MB, with `libonnxruntime.dylib`) in the macOS payload, `sherpa-onnx-win-x64` (about 23 MB) in the Windows payload. The member is loaded by a relative path the reachability walk cannot see, so `NATIVE` in `scripts/bundle-closure.ts` names both, and the top-level rule in `scripts/platform-dir-rules.ts` keeps only the target's own. On macOS the libraries load under the `disable-library-validation` entitlement, as sharp's and koffi's do.

**The microphone is recorded by the app window, and only the served UI there may open it.** The page records through `getUserMedia`. `src/microphone-permissions.ts` answers `media` requests on the app window's session: granted to the served UI's main frame in the app window, for audio alone, refused to every other frame and origin; every other permission keeps Electron's default. On macOS a granted request first asks the system, whose prompt shows the `NSMicrophoneUsageDescription` sentence from `electron-builder.yml`; the signed app carries the `com.apple.security.device.audio-input` entitlement, without which the hardened runtime refuses the microphone without asking. Windows needs no declaration; the system privacy setting that lets desktop apps use the microphone must be on.

## Update service

**The shell owns the update channel and the embedded server draws the Settings window**, so the one place a user can see an update and act on it is on the far side of a loopback listener. This is the second one beside the render service, opened and passed the same way: an HTTP listener on `127.0.0.1` and an ephemeral port, a 32-byte token, and both reaching the server child's environment alone — `DSH_DESKTOP_UPDATE_ENDPOINT` and `DSH_DESKTOP_UPDATE_TOKEN`, never the shell's own `process.env`. A harness that reads neither reports the capability unavailable and shows no update entry, which is what every `dsh web` on a server does. The two services are separate because they lend different powers, and this one lends the heavier: `/install` replaces the whole application.

Four routes. `GET /state` and three `POST`s, none of which reads a request body; all four carry `authorization: Bearer <token>`.

| Route | Answer |
|---|---|
| `GET /state` | `200 application/json` — the snapshot below |
| `POST /check` | `202 application/json` — the snapshot; a check runs in the background and downloads what it finds |
| `POST /download` | `202 application/json` — the snapshot; the transfer of the version already found is started or restarted, and a check runs first when no version is known |
| `POST /install` | `202 application/json` — `{ "ok": true }`, written before anything stops; the server goes down and the installer takes over on the next tick. `409` when the phase is not `ready` |
| any other path or method | `404`, decided before the token, so a caller that cannot authenticate learns nothing about what is offered |
| a missing or wrong token | `401` |

The snapshot is one JSON object. `phase` and `currentVersion` are always present; every other field is **omitted rather than sent as null** when it does not apply, so a reader tells "no value" from "value zero" by presence.

| Field | Type | When |
|---|---|---|
| `phase` | `"idle" \| "checking" \| "downloading" \| "ready" \| "failed"` | always |
| `currentVersion` | string | always — the running build |
| `latestVersion` | string | when a check saw a version ahead of the running build |
| `releaseNotes` | string | when the manifest carries notes for `latestVersion` |
| `percent` | number, 0–100 | `downloading` only |
| `transferredBytes` | number | `downloading` only |
| `totalBytes` | number | `downloading` only, once the transfer knows the artifact's size |
| `reason` | string | `failed` only — one diagnostic line in the shell's own words, not localized copy |
| `checkedAt` | string | ISO 8601 timestamp of the last completed check |

**`ready` is the only phase worth showing prominently.** It is the one state in which an update is downloaded, verified against the manifest's sha512, and installable by a click; `downloading` carries both `percent` and its byte counts so a settings page can show them to someone who went looking, and nothing about it belongs in a sidebar or a badge. `ready` also survives every later check, so a scheduled check does not take a finished update back off the screen. `failed` covers two situations the `reason` tells apart: a check or transfer the network defeated, which the next check starts over from, and a build that cannot install an update at all — a source-tree launch, or a macOS build whose in-place path failed — which nothing this run changes. Five phases is the whole set the shell sends; a reader that also needs a state for "this deployment has no update channel" owns that value itself, because the shell only ever answers for a channel it has.

**`POST /install` opens no dialog, and answers before it acts.** The click in the Settings window is the consent, and a native confirmation would only repeat the question that click answered; the route is refused outside `ready`, so the only thing it can install is an artifact whose checksum already matched the manifest. `{ "ok": true }` goes on the wire first and the install is scheduled for the next tick, because the install stops the embedded server and hands the machine to an installer that replaces this process — a caller still waiting on the response would read the dropped socket as a failed install.

**The `/install` token is in reach of every plugin the server runs.** It is injected into the server child's environment, so any code in that process — a third-party plugin included, and those declare no approval gates of their own — can call the route. What that buys is bounded: the app quits and installs an update whose sha512 electron-updater has already compared byte for byte against the feed's manifest (`DownloadedUpdateHelper.getValidCachedUpdateFile`), and which macOS additionally refuses unless it satisfies the running bundle's designated requirement. It is not a way to run code of the caller's choosing; the worst it costs is a restart nobody asked for. It opens no native confirmation because it installs only the one artifact the feed published, never a package a caller names. An audit of a third-party plugin therefore covers whether it reads `DSH_DESKTOP_UPDATE_TOKEN`.

## Office engine service

**The payload carries no LibreOffice engine; the shell downloads the one the shipped kit declares when the person asks for it.** `@deepseek-ai/dsh-office-to-pdf` converts Word and PowerPoint files for the right Sidebar's document tab through `@deepseek-ai/libreoffice-kit`, and `platformDirRules` drops every one of the kit's engines from both payloads: `@deepseek-ai/libreoffice-kit-darwin-arm64` is a 64 MB download and 145 MB unpacked, `-win32-x64` 68 MB and 182 MB. `src/office-engine.ts` reads the engine's name and exact version from the shipped kit's own `optionalDependencies`, reached through `@deepseek-ai/dsh` → `dsh-web-app` → `dsh-office-to-pdf` → the kit, so a kit upgrade moves the download with it once `ENGINE_DOWNLOADS` registers the engine version the new kit declares. `ENGINE_DOWNLOADS` records both desktop targets' published tarball size, which the confirmation quotes in whole MiB, and sha512 integrity, the registry's `dist.integrity`, at two kit versions: the workspace installs the kit at the version `pnpm-lock.yaml` pins (0.1.1), and the packaged closure comes from the legacy hoisted `pnpm deploy`, which does not take that pin and resolves the kit's `^0.1.1` range to the highest release that is at least pnpm's `minimumReleaseAge` (one day unless configured) old when the deploy runs, so a later deploy can stage a newer kit; the staging deployed on 2026-10-01 holds 0.1.3. A version the table lacks is not offered: `/state` reads `unsupported` and the log says the version is not registered yet. A test fails when the workspace kit names an engine version the table lacks, and a package run stops after `verifyStaging` when the staged kit names one for `darwin-arm64` or `win32-x64` (`scripts/office-engine-gate.ts`), printing the declared version and the missing `<package>@<version>` entry; the run also stops when the kit resolves from outside the staged tree.

**Where the engine lives.** One directory per version under `<data directory>/engines/office/`. The data directory is `$DSH_HOME` (default `~/.dsh`) today; `main.ts` passes it to `officeEngineRoot` rather than the module reading it, so a moved data directory carries the engine with it. The kit resolves its engine from its own directory and reads no path from configuration, so the shell names `<root>/<version>/node_modules` first in the server child's `NODE_PATH` from launch on, whether or not the engine is installed yet. Node reads `NODE_PATH` once at startup and caches only resolutions that succeed, and `office-to-pdf` drops a converter whose creation failed, so the first conversion after a download finds the engine without a restart. The same path goes in `DSH_DESKTOP_OFFICE_ENGINE_MODULES`; `@haoran/dsh-office-preview-notice`'s host half removes that entry from `process.env.NODE_PATH` when it applies, so the processes the server starts do not inherit it, while the server keeps resolving through it. Every launch, before the server starts, removes each version directory but the one the kit declares, registered or not, and each staging directory an interrupted download left under the root, also when the launch offers no engine; when the kit declares no exact version for the host or cannot be read, no version is kept. Nothing else under the root is touched.

**How it arrives.** The shell runs the shipped pnpm as `runtime/node runtime/pnpm/bin/pnpm.mjs add <engine>@<version> --ignore-workspace --ignore-scripts --reporter=ndjson --config.node-linker=hoisted --store-dir=<staging>/.pnpm-store` in a staging directory created inside the root, with `runtime/` first on `PATH`; a development launch uses `pnpm` on `PATH`. It spawns `pnpm.mjs` under the bundled Node rather than `dsh-pnpm.cmd`, which Node cannot spawn on Windows without a shell, so a cancel stops pnpm itself. pnpm checks the tarball against the integrity the registry metadata lists, filters by `os` and `cpu`, keeps the executable bits the kit checks, and reads the user's own `.npmrc`, so a mirror or proxy configured there applies; `--config.lockfile=true` keeps that file from suppressing the lockfile. The download never goes through Electron's session, which would mark every file it writes with macOS's quarantine attribute. The shell then compares the integrity the run's `pnpm-lock.yaml` records for the engine with the one `ENGINE_DOWNLOADS` pins, and refuses the install and removes the staging directory when the record is missing or differs, so metadata naming another tarball is not installed. It checks the engine's version, its `prebuilds.json`, and the executable that manifest names (a file, with an execute bit outside Windows), removes the run's own package store so the engine is on disk once, and renames the staging directory into place. The rename stays on one volume, so the version directory either does not exist or holds the whole engine; a rename an on-access scanner holds (`EPERM`, `EBUSY`, `EACCES`) is retried nine times at 500 ms intervals, about 4.5 seconds. Progress comes from pnpm's `pnpm:fetching-progress` records. One download may run for 30 minutes.

**The loopback service is a third listener beside the render and update services**, opened and passed the same way with a token of its own: `DSH_DESKTOP_OFFICE_ENGINE_ENDPOINT` and `DSH_DESKTOP_OFFICE_ENGINE_TOKEN` reach the server child's environment alone. No route reads a request body.

| Route | Answer |
|---|---|
| `GET /state` | `200 application/json` — the snapshot below |
| `POST /install` | `202 application/json` — the snapshot, now `confirming`. A native confirmation goes up, parented to the main window, and the download starts only on its **下载** button; **取消** is the default button and the answer Escape gives. `409` with `code` `unsupported`, `installed`, `confirming`, `installing`, or `declined-recently` — for 30 seconds (`DECLINE_COOLDOWN_MS`) after the person declines, without asking again |
| `POST /cancel` | `202 application/json` — the snapshot; pnpm is stopped and the staging directory removed. `409` with `code` `not-running` when no download is running |
| any other path or method | `404`, decided before the token |
| a missing or wrong token | `401` |

A `409` body is `application/json` `{ code, message }`: `code` is what a caller branches on, and `message` is one sentence for logs. The snapshot carries `phase` always, and `version`, `downloadBytes`, `transferredBytes`, `totalBytes`, and `reason` when they apply. `phase` is `unsupported` (the kit builds no native engine for this host, declares none, or declares a version not registered yet; `reason` says which), `absent`, `confirming`, `installing`, `installed` (read from disk on every request; an engine whose executable is gone or not executable reads `absent`), or `failed` (`reason` in the shell's own words; the download can be asked for again). A cancelled download reads `absent`. A caller names nothing: the package and version are the kit's, so no request can install anything else, and none installs without the confirmation. A quit aborts a running download, and the next launch removes the staging directory it left.

## Server environment

The server starts in the user's home directory with the GUI-inherited environment plus the standard shell PATH entries (macOS GUI apps launch with launchd's minimal PATH). `DEEPSEEK_API_KEY` resolves through the normal credential chain (environment → managed store → `.env`), so a first run without a key still boots into the UI, where the models settings page can store one. Server output is appended to the app's log directory (`dsh-server.log`), which **帮助 → 查看日志** opens; the boot page reports startup phases only and prints no path. A main-process exception or unhandled rejection is appended there too: `src/crash-log.ts` registers the handlers as soon as that file is open and before the updater and the server start, and an exception still opens the box — for an `Error`, the same title and body Electron composes; for a value that is not one, `String(value)` where Electron would print `undefined: undefined`. The launch chain runs inside `whenReady`, so its own failures arrive as a rejection rather than as an exception and are caught and reported the same way, with the box; before the log file is open that report's line goes to stderr. Nothing in a launch is silent, and nothing about a crash changes on screen.

**A packaged launch names its installation directory to the server.** `src/install-dir.ts` adds `DSH_DESKTOP_INSTALL_DIR` to the server child's environment, and to nothing else: on macOS the `.app` bundle, two levels above `process.resourcesPath` (`Contents/Resources`); on Windows and Linux the directory holding `resources/`. It is set for the permission gateway, whose vendored 0.5.3 lists that directory in its review prompt among the app's own directories: the review model is told to turn a call it recognizes as writing into, moving, or deleting one of them into a question to you, wherever the gateway reviews calls. That is an instruction to the review model rather than a check the gateway enforces, and under 完全权限 nothing is reviewed. A development launch has no installation and sets nothing, never an empty value. `dsh-server.log` records the value in one `install dir:` line. The desktop composition layer names the same directory in the model's system prompt.

**Every launch names the shell's own directories to the server.** `src/app-dirs.ts` adds three variables to the server child's environment, and to nothing else: `DSH_DESKTOP_USER_DATA_DIR`, Electron's `userData` (preferences, cookies, login partitions, `desktop-state.json`); `DSH_DESKTOP_LOG_DIR`, the directory `dsh-server.log` and the crash reports are written to, which on macOS is `~/Library/Logs/@deepseek-ai/dsh-desktop`, outside `userData`; and `DSH_DESKTOP_UPDATE_CACHE_DIR`, electron-updater's download cache from `updaterCacheDir()`, under `~/Library/Caches`, `%LOCALAPPDATA%`, or `~/.cache`. An empty path sets no variable. `dsh-server.log` records each in one line named after its variable. The desktop composition layer (`@deepseek-ai/dsh-desktop-app`) lists them in the model's system prompt as directories not to modify, move, or delete, and the permission gateway's review prompt lists them beside the installation directory; `tests/app-dirs.spec.ts` pins the variables and the server launch that carries them.

**A server that dies leaves its last lines and, for a fatal error, a report.** The shell starts the server's Node with `--report-on-fatalerror --report-uncaught-exception --report-directory=<log directory> --report-exclude-env --report-exclude-network` on its own command line, so a V8 fatal error — running out of memory above all — writes a `report.<date>.<time>.<pid>.<seq>.json` beside `dsh-server.log`, without the environment, where the provider key lives, and without the network interfaces. The flags are arguments of that one process rather than `NODE_OPTIONS`, which every Node program the agent runs would inherit. An exception produces a report only before the CLI installs its own handler; after that, the handler's stderr line in `dsh-server.log` is the record. A native crash that bypasses V8, such as Windows exit `0xC0000409`, writes no report. The `server exited unexpectedly` line waits until both output pipes of the dead server have closed, or 2 s after its exit when a process it started still holds them, so its tail carries what the server wrote last; a boot that exits before its URL line is reported on the same terms, so the quarantine scan under Built-in plugins reads its whole output.

**A window that cannot load the served UI says so, on screen and in the log.** Every app window writes `dsh-server.log` lines for its own page: `window loaded <origin and path>` on `did-finish-load` — or `window showed the error page for <origin and path>` when the main frame failed since its last navigation started, because Chromium then commits an error page and reports that as finished too — `window load failed: <code> <description> (<origin and path>, main frame|subframe)` on `did-fail-load`, and one line each for `render-process-gone` (with its reason and exit code), `unresponsive`, and `responsive`. A URL is logged by origin and path only, because the served UI's carries the launch token. Every load of the served UI — the first one, a reopened window's, and the retarget after a server rebind — goes through `src/window-load.ts`: a main-frame load of the served UI's origin that fails is retried once, 1 s later, with the same URL, and a second failure loads the boot page again with its last phase, 连接界面, marked failed and `界面没有加载出来:<description> (<code>)` under it. Only a new load — the next URL the shell hands the window — restores the retry; a finished load does not, because Chromium reports a failed load finished too, for the error page it commits under the same URL. `ERR_ABORTED` (-3) is a load another navigation replaced and is logged without a retry. `did-fail-load` reports network-level failures only — a refused or reset connection, DNS, certificates — and an HTTP error status loads as a page, so that case shows only as a `window loaded` line followed by nothing.

**The server listens on the port the previous launch's server used, so the served UI keeps its origin.** Everything the web client keeps in the browser belongs to the origin `http://127.0.0.1:<port>`: custom shortcuts (`dsh.keybindings.v1` in localStorage), the transcript width, right-sidebar layouts, and the sign-in cookie. The shell records the running server's port as `serverPort` in `desktop-state.json` (`setServerPort` in `src/desktop-state.ts`), and the next launch passes it as `--port` through `src/server-port.ts`, after the orphaned-server sweep and after the render, update, and Office engine services have bound their own ports. The port counts as free only when a listen succeeds on `127.0.0.1`, `0.0.0.0` and `::` (an address family the machine lacks is skipped), because on macOS a listener on a wildcard address does not stop a listen on `127.0.0.1`. A remembered port that is not free, or that another process takes before the server binds it (the server then exits with `listen EADDRINUSE`), falls back to `--port 0`: that launch starts on a new, empty origin, as every launch did before, and its port is remembered for the next one. The shell does not copy browser storage to the new origin, because Electron has no main-process API that copies one origin's localStorage to another. An unexpected server exit forgets the remembered port, and a crash rebind takes a port the system picks and remembers that one; the next paragraph says why. A state-file write flushes a temporary file and renames it over the old one, retrying briefly when another process holds the file (Windows antivirus and indexers do), and a write that still fails is logged. `dsh-server.log` records the choice in one `server port:` line ([Agent Note](../../.agents/notes/implemented/feature/2026-09-27-desktop-shell-stable-origin.md)).

**The shell removes its browser-session cookies before each launch's server starts, when the server exits unexpectedly, and as the app quits.** The served UI keeps one persistent `dsh-auth-<hash of host and port>` cookie per server it signs into, and a launch or a crash rebind on a new port adds one under a new name; the browser sends cookies by host and not by port, so all of them go out with every request to `127.0.0.1`. Around sixty of them push the request header past Node's 16 KB limit, the server answers the plugin bundle request with 431, and the window reports `Failed to load plugins`. The cookie is also not bound to the process that issued it: it is signed with a secret the Harness home keeps and names its host and port, so it stays valid, until it expires, for a later server on the same port, which is the port the next launch asks for. A local process could take a copy only by listening on that port while the window is still sending requests there with the server gone; the web client keeps reconnecting as long as the window is open. So `src/server-lifecycle.ts` orders the steps: an unexpected server exit first forgets the remembered port and removes the cookies, and only then runs the recovery ladder, so a rebind, a whole-app relaunch and the stop dialog all start with no remembered dead port and no cookie to send; a crash rebind takes a port the system picks; a quit removes the cookies and then stops the server, waiting at most 500 ms for the removal and sending the stop either way; and bringing the app to the front — Dock, tray, notification, second launch — does nothing once a quit has begun, so no new cookie is issued for a server about to be gone. A copy taken before a removal is not revoked by it. `src/auth-cookies.ts` removes every `dsh-auth-*` cookie on `127.0.0.1`, each at its own path; other cookies on the host stay. A removal that fails writes one line to `dsh-server.log` and the launch, recovery or quit continues.

**A stop the shell makes on purpose leaves a sentinel for the crash-resume plugin.** The `@haoran/dsh-crash-resume` server plugin continues a turn that a server crash cut short and holds one that a stop request cut short, and the session log alone cannot tell the two apart. So `src/crash-resume-sentinel.ts` writes `<Harness home>/crash-resume/intentional-stop.json`, one line of `{"version":1,"at":<epoch ms>,"by":"shell","reason":"quit"|"update"|"shutdown"}`, before the shell stops the server for a quit, for an update install, or because a mandatory update blocks the launch (`reason` is `update` only for that last one), and when the system announces a shutdown, restart or log-off (`shutdown`; `src/session-end.ts` hears a window's `session-end` on Windows, where no quit runs, and `powerMonitor`'s `shutdown` on macOS and Linux); the Harness home is resolved from the shell's own `DSH_HOME`, which the server inherits. The write is synchronous and atomic — a temporary file in the same directory, fsynced and renamed over the sentinel — so it is on disk before the stop goes out. On Windows it is the only writer, because `taskkill /T /F` runs no server code; on macOS the plugin writes the same file on SIGTERM too, and whichever rename lands last leaves one complete copy. It is written only while the server's child is still running: the shell keeps a crashed server's handle through the recovery ladder and the stop dialog, so a quit, an update install or a shutdown after a crash writes nothing, and neither do the unexpected exit itself, the relaunch after repeated crashes, a start that timed out, or the orphan sweep. A write that fails logs one `[desktop] crash-resume sentinel:` line to `dsh-server.log` and the quit goes on; the next start may then continue one turn it should have held. The next server reads and deletes the file; without the plugin installed the file stays, one line long, and nothing reads it. After an update install that failed, the restarted server finds the sentinel of the stop before it and holds the turns that stop interrupted ([Agent Note](../../.agents/notes/implemented/feature/2026-09-27-desktop-shell-crash-resume-sentinel.md)).

**The boot page and the installing notice follow the app's theme.** Both palettes are the web UI's own tokens, so the splash and the app it hands over to are the same two colors in either mode. The appearance is resolved before the window exists — `backgroundColor` is what paints while the page loads — in this order: the durable `ui-theme` preference when it is an explicit `light` or `dark`, otherwise the system (`nativeTheme.shouldUseDarkColors`), which is also what its default `system` means. The preference is the `ui-theme` row of `~/.dsh/profiles/desktop-shell/cordis.patch.yml`; a profile without that row — the first launch after upgrading from 0.1.0-rc.33, before the settings migration has run — reads `ui-theme.preference` from `~/.dsh/settings.yaml` instead. **An explicit setting wins over the system.** **帮助 → 关于** names the build and its update feed. Menu-bar labels follow `app.getLocale()` (Chinese or English); dialogs stay Chinese.

**The served UI's own loading page speaks the app's language and names the product.** Between the boot page and the first rendered view the window shows the web client's pre-locale loading page (`packages/client/web/src/boot-page.ts`), whose `HARNESS`, `Loading plugins…` and `Failed to load plugins` are fixed English. `src/app-boot-text.ts` inserts a stylesheet into every page of the app window, on `did-navigate` and again on `dom-ready`, that draws those three texts at size zero and paints `北冥`, `正在加载插件…` and `插件加载失败` in their place, or `Beiming` and the English texts. The language is the one chosen in the settings — the `locale` row of the desktop profile's patch layer, else `settings.yaml`, read like the theme preference — and, with no choice stored, `app.getLocale()`. It is read for each page load, so a language changed in the settings applies from the next reload or launch. The stylesheet selects by the page's `data-dsh-boot` and `data-dsh-boot-spinner` attributes and child order, not by generated class names, and matches nothing on other pages; `tests/app-boot-text.client.spec.ts` runs the selectors against the web client's own `BootPage`, so a change to that page's structure fails there. The window still has no preload.

## Known Limitations and Deferred Work

- A notification cannot open the session it is about: the web UI keeps the selected session in memory and puts nothing in the URL, so there is no address for the shell to load. Closing this needs the web client to accept a session in its URL; the shell side is then one `loadURL` argument.
- macOS is signed but not notarized, so a browser-downloaded copy still needs a right-click-open on its first run. Notarization needs an Apple Developer account; the update path does not.
- Windows arm64 and Linux desktop targets are unbuilt; node-pty prebuilds cover win32-arm64, so the arm64 gap is packaging work only.
- A dev launch (`pnpm --filter @deepseek-ai/dsh-desktop-shell exec electron lib/main.js`) uses the checkout's built CLI and the PATH Node, not the staged resources. It also needs `pnpm --filter @deepseek-ai/dsh-desktop-app run bundle` first, because the `desktop-brand` and `desktop-server-log` rows import that package's `lib/`, which the repository build does not produce.
- The log is rotated only at launch: a `dsh-server.log` past 10 MiB becomes `dsh-server.log.1`, replacing the one before, and only the newest five diagnostic reports stay (`src/log-retention.ts`). One long run can grow the file past 10 MiB until the next launch, and the server's logger records now reach it as well as the server's output.
- The render service is per-launch and serial. Four requests are accepted at a time and one renders, so a page that takes its whole deadline to load holds the slot and the requests queued behind it get only what is left of their own — which a caller raising `timeoutMs` to the 120-second ceiling spends on everything queued behind it too.
- A partial capture is what the compositor had painted, which for a page still fetching its stylesheet is an unstyled document rather than a half-drawn one. The report says whether anything painted at all (`firstPaint`) and whether the load event fired; the pixels do not.
- The shell's viewport floor is 16 px per edge, where `@haoran/dsh-screenshot` itself allows 1. A `screenshot` call for a smaller viewport is answered 400 on the desktop and rendered by a system browser everywhere else.
- Only the shell's render service can carry `headers` and `cookies`. The plugin's other backend is a one-shot `--screenshot` browser command line with no way to set either, so on an install without this service such a call is refused rather than rendered logged out.
- One sign-in window is open at a time. A second `POST /login` is answered 503 rather than queued, so a caller that needs two sign-ins does them one after the other.
- A login partition is never expired or collected by the shell. What a user signed in with stays on disk until something calls `DELETE /login-sessions` for that partition.
- A built-in plugin cannot be pinned to another version from the profile. Installing the same name with `dsh plugin --profile desktop-shell add` puts a copy in the profile's own `node_modules`, which the Loader finds first, while `resolveBundleDir` still reads the patch layer from the installation — the row would then come from one version and the code from another.
- Upstream's Plugins page has no per-package update action and no undo. A plugin that arrived through the `web` profile updates with `dsh plugin --profile web add <package>@latest`, which reaches the desktop through the link the sync keeps.
- A migrated plugin the shell disabled or tombstoned is named once in `dsh-server.log` and nowhere on screen.
- `plugin_manager` reaches a person only while the gateway's composed `config` carries the desktop layer's `alwaysAsk`. A gateway row in the profile's own patch layer whose `config` sets an `alwaysAsk` of its own replaces that map, and `src/settings-migration.ts` leaves such a row as it is.
- Keeping a switched-off built-in off depends on the core patch `launcher-shipped-bundles`, which makes the Plugins page list the built-ins. A build without it lists none, while `plugin_manager` `set_bundle` with `enabled: false` can still switch one off, and that built-in then stays off with nothing on screen to switch it back on; the two ship together.
- A built-in plugin switched back on from the Plugins page is appended after the composition layer, so the composition layer's rows for it apply only from the next launch, which moves the layer after it.
- A built-in plugin switched off while a build did not carry it drops out of `dsh.profile.shipped`; the next build that carries it again adds it back switched on.
- The Windows voice-input runtime is packaged and checked for presence only. Whether `sherpa-onnx.node` finds its DLLs in `sherpa-onnx-win-x64` is known only after a recording on a real Windows machine.
- The bundled pnpm is a version pinned at build time and updated only when the repository's own `packageManager` moves. It adds about 19 MB to each platform's payload, natives for all four of its platforms included, because it publishes as one tarball.
- A renderer that crashes or stops responding is logged and nothing more: the window is not reloaded, because a reload of a renderer that ran out of memory repeats the same load.
- Custom shortcuts accept only the browser's set of combinations, and any other is refused with 「此浏览器暂不支持该组合」, because the served UI runs in the web client's `web` shortcut runtime. The `desktop` runtime needs `data-platform` on the document plus a `dshDesktop` bridge and a native key interceptor, and `dshDesktop` is also the marker that turns off the Models page's first-run credential onboarding and welcome notice and turns on the account plugin; the [Agent Note](../../.agents/notes/implemented/feature/2026-09-27-desktop-shell-stable-origin.md) records the design, under Shortcut combinations, and why it is not adopted.
- A screen reader can read the served UI's loading page twice: the replaced English text stays in the document, drawn at size zero, and the replacement is `::after` content, which accessibility trees also expose. A stylesheet cannot set `aria-hidden`, and the page belongs to `packages/client/web`.
- Under macOS App Translocation — the first launch of a quarantined copy straight from Downloads — `DSH_DESKTOP_INSTALL_DIR` names the temporary translocated path macOS runs the app from, not the `.app` the user sees; moving the app to Applications before the first launch avoids it.
- While `@haoran/dsh-office-preview-notice` is not loaded — removed, disabled, or failing to load — the processes the server starts inherit the engine's `NODE_PATH` entry.
- The Windows download has not run on real hardware: Defender scanning the unpacked engine, the `win32-x64` engine for kit 0.1.3 converting, and path length under the hoisted layout are unverified.
