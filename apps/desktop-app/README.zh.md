# @deepseek-ai/dsh-desktop-app

[English](README.md) | 中文

桌面应用自己的组合层。`@deepseek-ai/dsh-base` 与 `@deepseek-ai/dsh-web-app` 是每个 `dsh web` 部署共用的出厂组合包，两者都刻意把一部分行留在不偏向任何具体部署的取值上；本包就是桌面应用替自己做出这些选择的地方。除一个插件模块外，整个包就是 `cordis.patch.yml` 加上指向它的 `dsh.bundle.patch` 清单字段，因此 `loadProfile` 读取该层时不导入任何模块；那个模块只由挂载它的那一行导入。`apps/desktop-server` 把它列为依赖，使它进入 `pnpm deploy` materialize 出的载荷；`apps/desktop-shell/src/profile-seed.ts` 把它排在 `BUILTIN_WEB_BUNDLES` 末位，于是无论全新 profile 还是升级而来的 profile，它在桌面 profile 的 `dsh.profile.bundles` 里都排在 dsh-base、dsh-web-app 与每一个内置插件层之后。那里的末位只是那一次播种时的末位，不是永远的末位：从 `web` profile 迁移过来、或从插件页装上的插件，都会追加在它之后。还有三个用户层在更后面生效——profile 自己的 `cordis.patch.yml`，然后是 `$DSH_HOME/cordis.patch.yml`，然后是任何 `--patch` overlay——所以这里的一行是用户可以替换的部署默认值，而不是无法摆脱的设定。下面按每一行所改的 id 说明。`session-query-sqlite` 打开了对话正文的全文搜索（`openAt: first-search`，落在一份持久的派生索引上），而出厂组合包把它关着。`llm-deepseek` 把 `retryPolicy.backoff.maxDelayMs` 从十秒抬到五分钟，也就是一个被限流的请求在整回合失败之前愿意等完的最长 `Retry-After`；这个上限落在供应商那一行，是因为真正执行等待的 `@deepseek-ai/dsh-llm-retry` 自己不接受任何配置，收到 `retryPolicy` 键时会直接报错说明这一点。这个上限约束的是单次等待，而一个 step 最多重试五次，所以单个 step 最坏坐等 25 分钟，按这里针对的那些窗口是 2.5 到 10 分钟；每一次等待都在用户停止本回合的那一刻结束，等待期间转录里一直在倒数；算式见 [Agent Note](../../.agents/notes/implemented/feature/2026-09-06-desktop-composition-layer-content-search.zh.md)。那一行还重述了下方某个内置插件层加在同一个 id 上的模型目录，因为 patch 替换的是整个 `config`。那份目录只有 `deepseek-flash` 一行，而 `@deepseek-ai/dsh-llm-deepseek` 如今自带同 id 的一行，所以这次重述是把出厂那一行逐字段重复一遍，只自己命名名字与它下面那句：整表替换会丢掉它没有重复的每一个字段，而其中 `systemPromptUpdate: in-history` 一旦丢失，代价是一份还热着的前缀缓存。`vision-switch` 点名在不支持视觉的模型上发图片时会话切到的模型，也就是会话起步的那个。`llm-permission-gateway` 点名权限网关的审查跑在哪个模型上，并把 `plugin_manager` 加进网关总是交给人的调用里；因为 `alwaysAsk` 会替换默认表，这一行还重述了网关自带的 `browser_auth` 一项。`plugin-manager` 把上游插件安装器指向壳在 `DSH_DESKTOP_PNPM` 里点名的 pnpm 启动脚本，开发启动时退回 `PATH` 上的 `pnpm`。`office-to-pdf` 被关掉，因为载荷里没有 LibreOffice 引擎。`ui-chat` 让工作详情以紧凑方式起步。该层唯一一条插入而非修改的行 `desktop-server-log` 挂载 `@deepseek-ai/dsh-desktop-app/server-log`（`src/server-log.ts`，由本包自己的 `build:ts` 编译，打包流程在 deploy 之前调用它）：它在根 logger 服务上注册一个 exporter——这个服务由整棵树的每个上下文共用——把级别不高于 `level: 2` 的每条记录追加到壳在 `DSH_DESKTOP_SERVER_LOG` 里点名的文件，也就是 `dsh-server.log`。cordis 的级别顺序是 ERROR 0 < INFO 1 < WARN 2 < DEBUG 3，所以这个阈值保留 error、info 与 warn，丢掉 debug。壳只给服务器子进程设这个变量，所以不经壳的启动不会打开这一行。exporter 自己写文件，每条记录追加一次、以 `[server-log]` 开头，而不是打印出来，因为壳在服务器的 stdout 与 stderr 里找就绪行，并把两路输出都抄进同一个文件。挂载时它先追加 logger 自己的缓冲区里阈值以内的记录；那个缓冲区按 INFO 收记录，所以这一行挂载之前、启动期间记下的 warn 会丢失。`apps/desktop-shell/tests/desktop-composition-layer.spec.ts` 组合真实的各层，断言桌面 profile 最终得到的取值，把那份重述的目录与它下方的那份逐项比对，并把这一行与出厂适配器自己那一行逐键比对，于是上游新加的字段会在那里失败。外壳见 [apps/desktop-shell](../desktop-shell/README.zh.md)，载荷见 [apps/desktop-server](../desktop-server/README.zh.md)。
